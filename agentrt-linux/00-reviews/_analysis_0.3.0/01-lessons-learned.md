## 2. 关键架构决策共识

### 2.1 IRON 铁律体系（5+9 项）

**共识 IRON-1~5（0.1.1 奠基铁律，2026-07-04 确立）**：
1. 禁止新特性（0.1.1 为纯文档奠基版本）
2. 禁止桩函数桩文件
3. 禁止绕开功能限制的编译集成
4. 禁止简化功能
5. 禁止未实现的功能设计

**共识 IRON-8（版本铁律，2026-07-05 确立）**：
- 0.1.1 之后直接过渡到 1.0.1，禁止 0.1.2/0.2.0/0.3.0/1.0.0 任何中间过渡版本
- 禁止兼容别名头/兼容层/双轨制
- 一切以生产就绪为目标

**共识 IRON-9 v2（代码共享三层模型，2026-07-07 确立）**：
- **[SC] 共享契约层**：agentrt ↔ agentrt-linux 完全共享代码（6 个头文件）
- **[SS] 语义同源层**：API 签名同源，实现独立
- **[IND] 完全独立层**：完全独立实现

**[SC] 共享契约层 6 个头文件清单**：
1. `include/airymax/bpf_struct_ops.h` — struct_ops 状态机 + common_value
2. `include/airymax/memory_types.h` — MemoryRovol L1-L4 + GFP 掩码 + PMEM 持久化
3. `include/airymax/security_types.h` — capability 38 ID + LSM 254 ID + Cupolas blob
4. `include/airymax/cognition_types.h` — CoreLoopThree + Thinkdual + LLM 推理阶段
5. `include/airymax/sched.h` — SCHED_EXT=7 + 任务描述符（magic 0x41475453 'AGTS'）+ vtime
6. `include/airymax/ipc.h` — IPC magic（0x41524531 'ARE1'）+ 128B 消息头 + SQE/CQE

## 3. 工程标准与规范共识

### 3.1 双源融合裁决共识

**共识 DS-1（"Linux 6.6 为基、seL4 为鉴"工程取向）**：
- 编码风格层：完全采纳 OLK-6.6（Tab 8 / snake_case / 最小 typedef / K&R / 80 列 / errno+goto / kernel-doc）
- seL4 编码约定（4 空格 / camelCase / 重度 typedef）因与 Linux 6.6 基线冲突被整体拒绝
- seL4 影响仅在架构层被选择性借鉴（ES-SEL4-1~5 + ES-SEL4-7）

**共识 DS-2（双源融合 16 维度裁决）**：
- 11 维度采纳 OLK-6.6（#1-#11：缩进/命名/typedef/大括号/行宽/错误处理/注释/UAPI/并发/内存/字符串拷贝）
- 3 维度借鉴 seL4 架构层（#12 架构组织三层 / #15 形式化验证 / #16 capability+IPC 融合）
- 2 维度借鉴 seL4 P2 增强（#13 接口契约 XML / #14 bitfield codegen）

### 3.2 微内核思想来源共识

**共识 MK-1（微内核来源收紧，ADR-014 确立）**：
- 微内核核心思想**仅来源于 seL4**
- 不引入 Zircon / Minix3，避免工程思想在哲学和逻辑学层面的多元化冲突
- seL4 的 5 项架构层工程思想（ES-SEL4-1~5）：极简原则 / capability 单一模型 / 服务用户态化 / 消息传递 IPC / 形式化验证

**⚠️ 待修复不一致**：
- 公开方案文档（docs/AirymaxOS/10-architecture/03-microkernel-strategy.md）已实现 seL4 唯一来源
- 闭源参考文档（docs-closed/03-microkernel-design-ref/04-microkernel-strategy.md）仍提及 "seL4 + Zircon + Minix3 综合对照"——需修复为 seL4 唯一

## 5. 关键教训总结

### 5.1 架构层面教训

**教训 L-01：io_uring 误用于 kthread 间通信**
- **问题**：早期设计将 io_uring 用于内核线程间通信，导致架构方向错误
- **根因**：io_uring 是用户态-内核态通信机制，不适合 kthread 间通信
- **修复**：kthread 间通信改用 kfifo + wait_event_interruptible
- **启示**：技术选型必须理解机制的本质语义，不能仅因"流行"就滥用

**教训 L-02：MGLRU 2.0 违规使用**
- **问题**：方案文档中 8 处出现"MGLRU 2.0"，违反 BAN-361 禁词规则
- **根因**：MGLRU 没有官方 2.0 版本号，使用非标准版本号引发混淆
- **修复**：全部改为"MGLRU 多代 LRU"
- **启示**：技术术语必须使用官方标准名称，禁止自创版本号

**教训 L-03：SCHED_AGENT 编号冲突**
- **问题**：SCHED_AGENT=7 与 OLK-6.6 已有的 SCHED_EXT=7 编号冲突
- **根因**：未在早期检查编号唯一性
- **修复**：删除 SCHED_AGENT 宏，统一使用 SCHED_EXT=7，SCHED_AGENT 仅作策略名
- **启示**：所有编号（系统调用号/调度类号/中断号）必须建立全局唯一注册表

**教训 L-04：corekern/ 与上游 kernel/ 关系未声明**
- **问题**：v0.2.4 审查发现 corekern/ 与上游 kernel/ 的关系未明确声明
- **根因**：设计文档未明确 corekern/ 是"替代"还是"协同"上游 kernel/
- **修复**：明确声明 corekern/ 与上游 kernel/ 协同（非替代），corekern/ 仅 4 原子机制
- **启示**：新增抽象层必须明确与现有层的关系（替代/协同/包装/扩展）

### 5.2 文档管理教训

**教训 L-05：README 索引与实际文件不匹配**
- **问题**：P1 模块 README 普遍声称"仅完成 README 占位"，但实际已有 3~5 份实质文档
- **根因**：文档创建后未同步更新 README 索引
- **修复**：全部 6 个 P1 模块 README 索引更新
- **启示**：文档创建/修改后必须立即更新索引，建立"文档即代码"的 CI 检查

**教训 L-06：文件命名冲突**
- **问题**：180-i18n 和 190-distribution 模块存在编号重复文件（两个 02、两个 03）
- **根因**：多轮文档创建未检查编号唯一性
- **修复**：180-i18n 重命名为 01~05 顺序；190-distribution 合并重复文件
- **启示**：文件编号必须全局唯一，建立命名冲突检测脚本

**教训 L-07：交叉引用失效**
- **问题**：文件重命名后交叉引用未同步更新
- **根因**：无自动化引用检查机制
- **修复**：全仓 grep 扫描并更新所有受影响引用
- **启示**：文件重命名必须建立"引用影响分析"流程

### 5.3 命名规范教训

**教训 L-08：agentos_ → agentrt_ 改名规模低估**
- **问题**：改名涉及 472 个文件、13037 次前缀替换，规模远超预期
- **根因**：早期命名选择未考虑长期影响
- **修复**：全仓批量替换，不留兼容别名
- **启示**：核心命名（前缀/ABI/路径）一旦确立极难更改，必须在项目启动时慎重决策

**教训 L-09：150-cloud-native 目录名不一致**
- **问题**：15 处文档引用"150-cloud-native"，实际目录为"150-cloudnative"
- **根因**：目录名含连字符与否未统一
- **修复**：全部统一为"150-cloudnative"（无连字符）
- **启示**：目录命名必须统一风格（连字符/下划线/无分隔），建立命名规范检查

### 5.4 工程思想教训

**教训 L-10：微内核来源多元化导致哲学冲突**
- **问题**：早期同时参考 seL4 + Zircon + Minix3，导致工程思想在哲学层面冲突
- **根因**：三个微内核设计哲学差异巨大（seL4 形式化验证 / Zircon 面向对象 / Minix3 自愈）
- **修复**：收紧为仅 seL4（ADR-014），避免多元化冲突
- **启示**：工程思想来源必须单一化，避免"哲学拼凑"导致的逻辑不一致

**教训 L-11：开源文档表述过于目的性**
- **问题**：AirymaxStandards 开放标准库中使用"生态护城河"、"确立为业界事实标准"等过于明显化表述
- **根因**：未区分"内部战略"与"对外表述"
- **修复**：改为"共同推动更亲和、更高水准的 Agent 技术标准与工程规范，促进开源生态繁荣"
- **启示**：公开文档的每一个字、每一段话都要经得起第三方推敲

**教训 L-12：openEuler 表述引发抄袭争议风险**
- **问题**：技术方案中直接使用 openEuler 相关表述，可能引发抄袭争议
- **根因**：未区分"技术参考"与"代码共享"
- **修复**：完全排除 openEuler 直接表述，改为"主流 Linux 发行版"描述性表述
- **启示**：技术参考与代码共享必须严格区分，公开文档避免直接引用可能引发争议的项目名

1. **编号唯一性**：所有编号（系统调用/调度类/中断/文件）必须建立全局注册表，CI 强制检查
2. **命名一致性**：目录名/文件名/变量名必须统一风格，建立命名规范检查脚本
3. **索引同步**：文档创建/修改后必须立即更新 README 索引，CI 检查索引与实际文件匹配
4. **引用校验**：文件重命名后必须全仓 grep 扫描引用，CI 检查引用有效性
5. **术语规范**：技术术语必须使用官方标准名称，建立禁词清单
