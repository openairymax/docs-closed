### 5.2 详细演进方案

#### 5.2.1 代码品味哲学层深化

在阶段二新增的 `11-code-taste-philosophy.md` 基础上，补充更多隐性智慧：

- 错误处理路径应和正常路径一样清晰
- 数据结构设计是编程的核心（"Bad programmers worry about the code. Good programmers worry about data structures"）
- 命名是设计的一部分
- 注释应解释"为什么"，而非"是什么"
- 防御性编程的边界

#### 5.2.2 形式化验证框架

基于 ES-SEL4-5（形式化验证驱动），建立关键路径不变量检查框架：

1. **corekern 4 原子机制不变量**：
   - task：任务状态机不变量
   - memory：内存分配/释放不变量
   - ipc：消息传递不变量
   - time：时间调度不变量

2. **[SC] 共享契约层不变量**：
   - `airy_ipc_msg_hdr` 大小 = 128 字节（已有 `_Static_assert`）
   - `airy_task_desc.magic` = 0x41475453
   - capability 操作 7 种完备性

3. **不变量检查工具**：
   - 编译时：`_Static_assert` / `BUILD_BUG_ON`
   - 运行时：`BUG_ON`（已禁用）→ `WARN_ON_ONCE` + 恢复代码
   - 测试时：KUnit 不变量测试

**注意**：全量形式化验证（Isabelle/HOL）不现实，仅对关键路径做不变量检查。

#### 5.2.3 capability + LSM 融合模型论证

论证 agent-linux 同时使用 capability（seL4 借鉴）和 LSM（Linux 6.6 原生）的合理性：

1. **capability 层**：细粒度权限控制（agent spawn / GPU sched / NPU access）
2. **LSM 层**：系统级安全策略（hooks 252 ID）
3. **融合点**：capability 操作触发 LSM 钩子
4. **避免双重检查**：capability 检查通过后，LSM 钩子不再重复检查同一权限

#### 5.2.4 服务用户态化风险评估

评估 ES-SEL4-3（服务用户态化）的落地风险：

1. **VFS 用户态化**：性能影响 + 兼容性
2. **网络栈用户态化**：性能影响 + 协议兼容性
3. **驱动用户态化**：设备覆盖范围 + 性能影响
