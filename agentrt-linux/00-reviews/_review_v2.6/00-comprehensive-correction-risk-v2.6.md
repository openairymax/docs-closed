## 3. 第三方风险评估全面分析（任务 2）

### 3.1 安全风险评估

#### 3.1.1 io_uring 历史漏洞与攻击面

**风险等级：⚠️ 部分真实**

**评估**：io_uring 历史上确实有多个 CVE。agentrt-linux 的加固设计覆盖了已知攻击向量，但依赖 io_uring 作为安全边界增加了一层复杂性。关键防护机制：

- `06-io-uring-hardening.md` 设计了 io_uring 加固层
- `08-threat-model.md` 定义了威胁模型
- C-S9 Badge 校验在 io_uring 的 `IORING_OP_URING_CMD` 回调中内联执行
- SQE128 模式无额外用户态内存访问

| 风险维度 | 是否覆盖 | 评估 |
|----------|---------|------|
| CVE 级历史漏洞 | ⚠️ 部分覆盖 | 未独立第三方审计 |
| 攻击面控制 | ✅ 已覆盖 | SQE128 + registered buffers 限制攻击路径 |
| fastpath 绕过导致 Capability 绕过 | ✅ 已有防护 | C-S9 内联校验是唯一执行点（H4 硬约束） |
| io_uring 与 capability 系统耦合 | ⚠️ 结构性风险 | 上游 io_uring 变动影响安全模型（第三方指出的"强耦合"论点有效） |

**改进建议**：考虑建立 io_uring CVE 追踪清单，每个新 CVE 发布时检查是否影响 Airymax 的攻击面。

#### 3.1.2 LSM 集成点绕过风险

**风险等级：⚠️ 部分真实**

**评估**：第三方指出的三个具体风险点验证结果：

| 风险 | 现状 | 评估 |
|------|------|------|
| 其他路径绕过 LSM（direct kernel ABI/module/bpf） | ⚠️ 未充分文档化 | LSM 加载顺序/互操作未明确定义 |
| LSM 加载顺序/互操作 | ❌ 缺失 | 设计文档中无此定义 |
| LSM hook 覆盖完整性 | ⚠️ 待确认 | 声明 250 个 hook + 5 核心 + 5 supplemental = 10 个已实现 |

**关键 gap**：`07-airy-lsm-design.md` 声明了 250 个 LSM hook 目标，但 v2.3 代码中仅实现 10 个（5 核心 + 5 supplemental）。M1 阶段需实现剩余 240 个 hook。在此过渡期，LSM 覆盖不完整意味着存在绕过路径。

#### 3.1.3 Badge/RandomTag/Epoch 竞态

**风险等级：✅ 已有充分防护**

| 风险 | 设计防护 | 评估 |
|------|---------|------|
| RandomTag 不重复性 | `get_random_u64()` 内核 CSPRNG（64-bit 碰撞概率 ~1/2^64） | ✅ 充分 |
| Epoch 原子撤销竞态 | `atomic_inc(&airy_cap_global_epoch)` O(1)，C-S9 读取 epoch + badage 在 fastpath 内联 | ✅ 充分 |
| 旧令牌误用（ABA） | badge_randtag + badge_epoch 双因子校验 | ✅ 充分 |
| TOCTOU | C-S9 是纯读取零副作用（OS-KER-225），校验通过前不修改任何状态 | ✅ 充分 |

#### 3.1.4 sec_d 单点故障

**风险等级：⚠️ 部分真实**

| 风险 | 现状 | 评估 |
|------|------|------|
| 单进程崩溃 | 无高可用设计 | ⚠️ 真实 gap |
| 崩溃恢复 | 无 watchdog/macro_d 设计 | ⚠️ 真实 gap |
| 唯一写者瓶颈 | 设计简化了并发模型 | ✅ 工程权衡合理 |

**改进建议**：M1 阶段补充 sec_d watchdog 和崩溃恢复策略。

### 3.2 可维护性风险评估

#### 3.2.1 完整 fork 维护成本

**风险等级：⚠️ 部分真实**

- **~260 个专属补丁**，其中 sched/ (~50) 和 io_uring/ (~40) 是上游高频变动区域
- 每两周 minor merge 需要对 ~90 个高冲突补丁进行人工审查
- **6.6→7.1 大版本迁移**：8 项 breaking changes 已识别，但迁移计划仅标注"2027+"，缺乏量化排期

#### 3.2.2 syscall 编号跨架构维护

**风险等级：⚠️ 部分真实**

- 当前 `unistd.h` (453-456) 和 `syscall_64.tbl` (454-457) 之间存在 **1 的偏移**（P0-014）
- arm64/riscv64/loongarch64 的 syscall 表需要与 x86 同步
- 跨架构维护负担未被充分文档化

### 3.3 可观测性风险评估

#### 3.3.1 fastpath 内联校验不可观测

**风险等级：⚠️ 部分真实**

- C-S9 是 ~10ns 内联校验，通常被编译器优化为寄存器操作
- 内联函数无法被 kprobe 挂载
- 设计文档中存在 `airy_ipc_fastpath_probe` debugfs tracepoint 声明，但细节不充分

**改进建议**：为 fastpath 关键步骤添加 `trace_airy_ipc_fastpath_*` tracepoints（每个 ~50ns，在 158ns 总延迟中可接受）

#### 3.3.2 传统审计工具失效

- `trace_id` 字段（OpenTelemetry 兼容）可覆盖 IPC 消息的分布式追踪，但不覆盖 fastpath 执行本身
- Prometheus 指标设计（调度延迟、抢占统计）存在但不覆盖 IPC fastpath 级别

### 3.4 可靠性风险评估

#### 3.4.1 资源生命周期管理

**风险等级：⚠️ 部分真实**

- registered buffer 无显式生命周期状态机
- capability 撤销与资源释放之间无关联设计
- frozen ring 机制提供资源隔离边界（✅），但不解决泄漏

#### 3.4.2 回退路径完整性

**风险等级：✅ 已有充分防护**

- 调度层面：5 种触发条件 + 分级超时保护（5s/30s/60s）
- IPC 层面：[DSL] 降级模式（`capability_badge=0`，跳过 C-S9）
- fastpath 层面：fastpath → slowpath io-wq 接管（~158ns → ~600ns-5.5μs）
- 唯一 gap：多层回退协调未文档化

### 3.5 设计可辩护性评估

#### 3.5.1 io_uring 作为 IPC 数据面——"有争议"

**评估：设计文档中的论据充分且一致。**

| 论证维度 | 结论 |
|----------|------|
| 性能 | ~158ns (io_uring) vs ~1μs (syscall)，6.3x 提升 |
| 架构简洁性 | 消除"控制面/数据面双平面"，syscall 从 12 精简到 4 |
| 生态复用 | 零拷贝、异步、registered buffers、SQPOLL 全部复用，无需自建 |
| 第三方"强耦合"疑虑 | **合理**——上游 io_uring 变动会影响安全模型。但这是有意识的设计权衡，而非疏忽 |

**结论**：争议点（io_uring 与安全模型的耦合）是真实存在的工程权衡，文档中有充分论证。选择 io_uring 而非自建 syscall 是经过性能、架构、生态三维分析后的有意识决策。

#### 3.5.2 静态固定大小 capability 表——"有争议"

**评估：选型依据存在但不足，多租户扩展路径缺失。**

| 维度 | 现状 |
|------|------|
| 选型依据 | 1024 = 当前需求 × 10（agent < 100），但未文档化此计算过程 |
| 性能理由 | 静态数组 O(1) 索引（10ns fastpath 关键），vs radix_tree 不可接受延迟 |
| 扩展路径 | **未设计**——从 1024 到 65536 的 agent_id 扩展方案未预留 |
| 云环境适用性 | per-node Badge + 水平扩展（可辩护），但 per-agent resource quota 未设计 |

**结论**：1024 槽位的选择在当前阶段是合理的工程权衡，但缺乏"扩展到 65536 agent"的设计预留说明令第三方疑虑合理。

#### 3.5.3 纯 C LSM（放弃 BPF-LSM）——"可辩护"

**评估：论据充分但可进一步加强。**

| 论点 | 评估 |
|------|------|
| sched_ext 在 6.6 不可用 | ✅ 客观事实 |
| 确定性执行路径 | ✅ C 代码编译后行为确定，BPF verifier+JIT 引入不确定性 |
| 形式化验证友好 | ✅ seL4 传统——C 适合静态分析 |
| 与 BPF-LSM 的完整对比 | ❌ 缺失——无对比决策文档 |

## 5. 审查结论

### 5.1 误判纠错结论

**审查报告质量整体较高，误判集中在代码已存在的后期轮次（v2.3/v2.4）。**

- v2.2 及之前的 ~20 轮审查中，**无任何可确认的误判**——所有"缺失"断言均基于"0 行代码"事实
- v2.3 有 2 项误判（"30+ 文档统一 v1.0.1"和"IRON-8 已满足"），但 12 P0 + 30 P1 的修复声明经抽样验证 93.3% 真实
- v2.4 有 6 项误判，已在 v2.5 全部纠正
- v2.5 纠正 v2.4 误判后，发现 4 项真实问题（P0-014 + IRON-8 + codegen + ABI）

### 5.2 第三方风险评估结论

第三方提出的风险中：
- **io_uring"强耦合"风险**：真实存在，但设计文档中有充分论证，属于有意识的设计权衡
- **1024 槽位扩展性**：选型依据不够透明，但技术理由（fastpath O(1) 性能）坚实
- **纯 C LSM 选择**：论据充分，sched_ext 不可用是客观事实，BPF 不确定性对安全的负面影响是合理考量
- **可观测性 gap**：fastpath 内联校验的观察性设计不足是最需要立即补充的
- **上游维护成本**：~260 个补丁在 sched/io_uring 高频变动区的维护是长期风险，当前文档不足以充分评估

### 5.3 整体判定

**agentrt-linux 在架构层面设计完整且逻辑自洽。第三方风险大部分已在设计层面有应对，但工程实现细节和长期维护策略需要补充。**

M1 前置条件：
1. 修复 5 项 P0 真实问题（§4.2）
2. 补充 8 项第三方风险 gap（§4.3）
