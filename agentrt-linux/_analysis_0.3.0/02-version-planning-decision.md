## 3. 发现的问题

### 3.1 P1 问题：§8.2/8.3 与 §8.4.5 内部不一致

**问题描述**：

| 位置 | 表述 | 含义 |
|------|------|------|
| §8.2 版本规划表 | "2.x.x \| Linux 7.1 长期锁定" | 2.x.x 直接使用 7.1 |
| §8.3 内核基线演进 | "2.x.x \| Linux 7.1 长期锁定" | 2.x.x 直接使用 7.1 |
| §8.4.5 迁移路径 | "短期（2.x.x）保持 6.6 LTS 基线，将 7.1 关键 ABI 作为前瞻性接口预留" | 2.x.x 仍用 6.6 |

**矛盾分析**：§8.2/8.3 表述 2.x.x"长期锁定 Linux 7.1"，但 §8.4.5 迁移路径建议 2.x.x"短期保持 6.6 LTS 基线"。这两者直接矛盾。

**根因**：§8.4.5 的迁移路径基于 Linux 7.1 前瞻研究报告的建议（7.1 非 LTS，不建议立即迁移），而 §8.2/8.3 的表述是基于 ADR-013 的战略决策。两者未对齐。

### 3.2 P2 问题："长期锁定"措辞与 7.1 非 LTS 矛盾

**问题描述**：§8.2/8.3 表述 2.x.x"长期锁定 Linux 7.1"，但 §8.4.1 已明确标注 7.1 **非 LTS**。长期锁定一个非 LTS 版本风险较高（7.1 的维护周期约 2.5 个月即 EOL，符合非 LTS 常规节奏）。

**风险评估**：

| 风险 | 影响 | 概率 |
|------|------|------|
| 7.1 EOL 后无安全补丁 | 安全漏洞无法修复 | 高 |
| 7.1 bug 修复停止 | 稳定性问题累积 | 高 |
| 7.x LTS 发布后需再次迁移 | 迁移成本 | 中 |

### 3.3 P3 问题：缺少专门的性能测试规划

**问题描述**：§8.4.2 列出了 7.1 的功能能力映射，§8.4.3 列出了冲突与缓解，但缺少专门的**性能测试规划**——即 2.x.x 迁移至 7.1 后，如何验证性能不退化（或提升）。

### 3.4 P4 问题：迁移路径缺少验证检查点

**问题描述**：§8.4.5 迁移路径仅给出"短期/中期/长期"三阶段策略，但缺少每阶段的**验证检查点**——即如何确认前一阶段完成、可以进入下一阶段。

## 4. 修复方案

### 4.1 P1 修复：统一版本基线表述

**修复方向**：将 §8.2/8.3 的"长期锁定 Linux 7.1"修改为"以 Linux 7.x 系列为基线（从 7.1 起步，跟踪至 7.x LTS）"，与 §8.4.5 迁移路径对齐。

**理由**：
- 7.1 是 7.x 系列的起点（首个 stable），2.x.x 以 7.1 起步符合用户决策
- "7.x 系列"表述涵盖 7.1→7.x LTS 的演进，避免"长期锁定非 LTS"的风险
- 与 §8.4.5"短期保持 6.6 + 前瞻性预留 → 中期评估 7.x LTS → 长期全面 7.x"路径一致

**具体修复**：
- §8.2: "Linux 7.1 长期锁定" → "Linux 7.x 系列（从 7.1 起步，跟踪至 7.x LTS）"
- §8.3: "Linux 7.1 长期锁定" → "Linux 7.x 系列（从 7.1 起步）"
- §8.2 版本规划表备注栏补充迁移路径引用

### 4.2 P2 修复：明确 7.1 非 LTS 的风险应对

**修复方向**：在 §8.2 版本规划表为 2.x.x 增加风险应对说明。

**具体内容**：
- 2.x.x 初期以 7.1 为开发基线（利用 7.1 的 sched_ext cgroup 子调度器等能力）
- 跟踪 7.x stable 更新（7.1.x → 7.2 → ... → 7.x LTS）
- 7.x LTS 发布后（推测 7.4/7.5，2026 末确认）切换至 LTS
- 在 LTS 发布前，通过 agentrt-linux 自维护补丁保证安全

### 4.3 P3 修复：补充性能测试规划

**修复方向**：在 §8.4 增补 §8.4.6 性能测试规划。

## 5. 详细内核版本迁移路径规划

### 5.1 迁移总览

```
阶段 0：兼容性评估（1.x.x 后期）
  ├── defconfig 审计（6.6 → 7.1 配置差异）
  ├── breaking changes 评估（8 项）
  ├── 工具链基线评估（Rust 1.85 / Clang）
  └── 硬件支持清单评估
        |
        v
阶段 1：兼容层先行（1.x.x → 2.x.x 过渡）
  ├── airymax_kernel_cap_query() 框架实现
  ├── 10 项能力探测 + 降级路径
  ├── 接口契约前瞻性预留
  └── 在 6.6 上验证降级路径正确性
        |
        v
阶段 2：渐进式基线切换（2.x.x 初期）
  ├── 内核源码基线从 6.6 切换至 7.1
  ├── defconfig 适配（CONFIG_IPV6=y 等）
  ├── 自定义驱动迁移（buffer_head → folio）
  └── 编译验证 + 单元测试
        |
        v
阶段 3：功能验证（2.x.x 中期）
  ├── 全量回归测试套件（P0 100%）
  ├── 7.1 新能力功能验证（10 项）
  ├── breaking changes 影响验证
  └── 兼容性测试套件
        |
        v
阶段 4：性能测试（2.x.x 中后期）
  ├── 8 维度性能基准（见 §4.3）
  ├── 性能回归分析
  ├── 性能调优
  └── 性能 SLO 验证
        |
        v
阶段 5：7.x LTS 切换 + 旧基线 EOL（2.x.x 后期）
  ├── 7.x LTS 发布后切换至 LTS
  ├── 6.6 基线支持终止
  ├── 安全公告迁移
  └── 用户迁移通知
```

**决策 VP-3（2026-07-09 确认）**：

> agentrt-linux 版本规划采用双基线锁定策略（ADR-013）：
> - 1.x.x 全系列以 Linux 6.6 LTS 为内核基线（维护至 2027-12）
> - 2.x.x 全系列以 Linux 7.x 系列为内核基线（从 7.1 起步，跟踪至 7.x LTS）
> - 迁移遵循 5 阶段路径：兼容性评估 → 兼容层先行 → 渐进式基线切换 → 功能验证 → 性能测试 → 旧基线 EOL
> - 7.1 非 LTS 的风险通过"跟踪 stable 更新 + 自维护补丁 + 7.x LTS 发布后切换"缓解

### 7.3 与前瞻研究报告的对齐

Linux 7.1 前瞻研究报告（`_research_0.2.5/02-linux-7.1-forward-looking.md`）建议"2.x.x 不立即迁移，而是运行时能力探测 + 条件降级"。本决策报告将其理解为：

- 2.x.x **以 7.1 为开发基线**（利用 7.1 新能力），但通过 `airymax_kernel_cap_query()` 框架保持**降级兼容**（在 6.6 上也能运行）
- 这与"运行时能力探测 + 条件降级"不矛盾——7.1 是 2.x.x 的目标基线，能力探测是兼容性保障手段

### 8.1 核心结论

1. **版本规划已落地**：04-engineering-baseline.md + ADR-013 已记录双基线锁定策略，核心要求满足
2. **发现 4 项问题**：P1 表述不一致 / P2 非 LTS 风险 / P3 性能测试缺失 / P4 验证检查点缺失
3. **修复方案已制定**：5 项修复（FIX-01~05），统一为"7.x 系列从 7.1 起步"表述
4. **迁移路径已详述**：5 阶段路径 + 兼容性/功能/性能三维验证
