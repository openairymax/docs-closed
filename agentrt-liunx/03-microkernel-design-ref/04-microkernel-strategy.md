## 1. AirymaxOS 微内核化改造策略总览

### 1.1 改造哲学

AirymaxOS 的微内核化改造遵循以下核心哲学：

| 原则 | 说明 | 来源 |
|------|------|------|
| 渐进式改造 | 不从头重写，基于 Linux 内核逐步演进 | 工程可行性 |
| 机制与策略分离 | 内核保留机制，策略移到用户态 | Liedtke 原则 |
| 安全优先 | 每次改造提升安全隔离性 | seL4 安全哲学 |
| 性能不退化 | 改造后的性能不低于改造前 | 产业实践要求 |
| 兼容性保持 | 保持与宏内核的 ABI 兼容 | 生态保护 |

### 1.2 改造的驱动力

| 驱动力 | 说明 | 紧迫度 |
|--------|------|--------|
| AI Agent 安全隔离 | 数千个 Agent 并发时需要强隔离 | 高 |
| 故障隔离 | Agent 工具的崩溃不应影响系统 | 高 |
| 动态权限 | Agent 需要动态获取和收回权限 | 高 |
| 内核攻击面 | 宏内核攻击面过大，安全风险高 | 中 |
| 可验证性 | 关键路径需要形式化验证 | 中 |
| 能效优化 | Token 能效需要在 OS 层面优化 | 中 |

### 1.3 改造策略总图

```
                    当前状态 (Linux 6.6 宏内核)
                    ============================
                    内核态：所有驱动、FS、网络、调度
                    用户态：应用程序
                              |
                              | 阶段一：内核态机制最小化
                              v
                    阶段一状态 (1.0.1)
                    ===================
                    内核态：SCHED_AGENT + AgentsIPC + Cupolas 框架
                    用户态：Agent 调度策略 + 自定义 IPC 策略
                              |
                              | 阶段二：用户态服务化
                              v
                    阶段二状态 (1.0.2-1.1.x)
                    =========================
                    内核态：微内核核心 (调度 + IPC + 内存)
                    用户态：12 daemons → services 子仓
                              |
                              | 阶段三：驱动用户态化
                              v
                    阶段三状态 (1.2.x-2.0)
                    =======================
                    内核态：最小微内核 (~80K LOC)
                    用户态：驱动框架 + 所有服务
                              |
                              | 阶段四：形式化验证
                              v
                    最终状态 (2.0+)
                    ================
                    内核态：形式化验证的微内核
                    用户态：完整服务生态
```

## 2. 三代微内核横向对比表

### 2.1 核心特性对比

| 维度 | seL4 | Zircon | Minix3 | AirymaxOS | 备注 |
|------|------|--------|--------|-----------|------|
| **代码规模** | ~10K LOC | ~200K LOC | ~15K LOC | 目标 <80K LOC | 微内核越小越好，但 AI 场景需要适度扩展 |
| **形式化验证** | 全内核 Isabelle/HOL | 无 | 无 | 关键路径 Isabelle/HOL | 全内核验证成本过高，聚焦关键路径 |
| **安全模型** | Capability | Handle + Capability | POSIX 权限 | Capability 增强 | 结合 seL4 的严格性 + Zircon 的实用性 |
| **驱动模型** | 无原生驱动 | 用户态驱动框架 | 用户态驱动 | 用户态驱动框架 | 参考 Zircon 的 devhost 设计 |
| **IPC 机制** | 同步 | 同步 + 异步 | 消息传递 | 同步 + 异步 + io_uring 零拷贝 | 同时支持低延迟同步和零拷贝大块传输 |
| **调度模型** | MCS | 公平调度 | 轮询 | MCS + Agent 感知 | 混合关键度 + Agent 工作负载优化 |
| **内存管理** | 分区内存 | VMO 零拷贝 | 简单页表 | VMO 零拷贝 + KV 分页 | AI 推理场景的特殊需求 |
| **故障恢复** | 无内置 | 组件重启 | 自愈合 | 自愈合 + 优雅降级 | 参考 Minix3，增强 AI 场景 |
| **开发语言** | C | C/C++ | C | Rust | 内存安全由类型系统保证 |
| **适用场景** | 安全关键系统 | 消费设备 | 教学/嵌入式 | AI Agent 运行时 | 面向 AI 时代的 OS |

## 3. 微内核化改造路线

### 3.1 阶段一：内核态机制最小化

**目标**：将调度策略和 IPC 策略从内核态移到用户态，建立 SCHED_AGENT + AgentsIPC + Cupolas 基础框架。

**时间**：1.0.1 版本

**具体工作**：

| 工作项 | 说明 | 参考来源 | 工作量 |
|--------|------|----------|--------|
| SCHED_AGENT 调度类 | 基于 sched_ext 理念，实现 Agent 感知调度 | Linux sched_ext | 大 |
| AgentsIPC 框架 | 基于 io_uring 的高性能 Agent 间通信 | Linux io_uring | 大 |
| Cupolas 框架 | 用户态服务组织架构 | seL4 root task + Zircon component | 中 |
| eBPF 调度策略 | 用户态 BPF 程序实现自定义调度 | Linux eBPF | 中 |
| 内核裁剪 | 移除不需要的宏内核模块 | 自主 | 中 |

**关键设计决策**：

- SCHED_AGENT 作为新的调度类注册到内核，与 CFS、EEVDF 共存
- AgentsIPC 基于 io_uring 的共享环形缓冲，支持零拷贝消息传递
- Cupolas 作为用户态 root task，管理所有 Agent 和服务的生命周期

### 3.2 阶段二：用户态服务化

**目标**：将 12 个 daemons 从内核态迁移到 services 子仓，实现用户态服务化。

**时间**：1.0.2 - 1.1.x 版本

**12 daemons 迁移计划**：

| 编号 | Daemon | 功能 | 迁移难度 | 优先级 | 迁移后位置 |
|------|--------|------|----------|--------|-----------|
| D-01 | agentd | Agent 生命周期管理 | 中 | P0 | airymaxos-services/agentd |
| D-02 | schedd | Agent 调度守护 | 高 | P0 | airymaxos-services/schedd |
| D-03 | memd | 记忆管理守护 | 高 | P0 | airymaxos-services/memd |
| D-04 | cognitived | 认知计算守护 | 高 | P0 | airymaxos-services/cognitived |
| D-05 | securid | 安全策略守护 | 中 | P0 | airymaxos-services/securid |
| D-06 | netd | 网络通信守护 | 中 | P1 | airymaxos-services/netd |
| D-07 | fsd | 文件系统守护 | 高 | P1 | airymaxos-services/fsd |
| D-08 | toold | 工具管理守护 | 中 | P1 | airymaxos-services/toold |
| D-09 | monitord | 监控守护 | 低 | P1 | airymaxos-services/monitord |
| D-10 | logd | 日志守护 | 低 | P2 | airymaxos-services/logd |
| D-11 | configd | 配置管理守护 | 低 | P2 | airymaxos-services/configd |
| D-12 | cloudd | 云原生接口守护 | 中 | P2 | airymaxos-services/cloudd |

**迁移策略**：

1. 每个 daemon 先在当前内核中实现 IPC 接口
2. 然后逐步迁移到用户态，保持内核对旧接口的兼容
3. 迁移完成后移除内核中的旧实现

### 3.3 阶段三：驱动用户态化

**目标**：将关键驱动从内核态迁移到用户态 services 子仓。

**时间**：1.2.x - 2.0 版本

**驱动迁移计划**：

| 驱动类型 | 迁移策略 | 技术基础 | 优先级 |
|----------|----------|----------|--------|
| GPU 驱动 | 用户态 GPU 驱动框架 | VFIO + GPU 直通 | P0 |
| NPU 驱动 | 用户态 NPU 驱动框架 | 自主创新 | P0 |
| 网络驱动 | 用户态网络驱动 (DPDK/AF_XDP) | Linux 已有技术支持 | P1 |
| 存储驱动 | 用户态存储驱动 (SPDK) | Linux 已有技术支持 | P1 |
| 外设驱动 | 用户态外设驱动框架 | VFIO/libvfio | P2 |

### 3.4 阶段四：形式化验证

**目标**：对关键路径进行形式化验证。

**时间**：2.0+ 版本

**验证范围**：

| 验证对象 | 验证方法 | 验证目标 | 优先级 |
|----------|----------|----------|--------|
| IPC 消息传递 | Isabelle/HOL | 无死锁、无消息丢失 | P0 |
| Capability 系统 | Isabelle/HOL | 能力不可伪造、不可越权 | P0 |
| 调度器核心 | TLA+ 模型检查 | 活性、公平性 | P1 |
| 内存管理 | Isabelle/HOL | 无内存泄漏、无越界访问 | P1 |
| AgentsIPC 协议 | TLA+ 模型检查 | 消息顺序性、可靠性 | P2 |

## 5. 与宏内核的兼容性保证

### 5.1 ABI 兼容策略

| 接口类型 | 兼容策略 | 说明 |
|----------|----------|------|
| 系统调用 | 保持兼容 | 现有应用无需修改 |
| /proc 接口 | 保持兼容 | 确保监控工具正常工作 |
| /sys 接口 | 保持兼容 | 确保管理工具正常工作 |
| ioctl | 保持兼容 | 确保驱动兼容性 |
| 内核模块 API | 有限兼容 | 仅支持 Rust 模块 |

### 5.2 功能兼容策略

| 功能 | 兼容策略 | 备注 |
|------|----------|------|
| 文件系统 | 用户态实现，POSIX 兼容 | 通过 VFS 层兼容 |
| 网络栈 | 用户态实现，socket API 兼容 | 通过 LD_PRELOAD 兼容 |
| 进程管理 | 用户态实现，fork/exec 兼容 | 通过 Cupolas 兼容 |
| 内存管理 | 内核态实现，mmap 兼容 | 内核保留 |
| 设备驱动 | 用户态实现，/dev 兼容 | 通过设备代理兼容 |

### 5.3 性能兼容保证

| 性能指标 | 兼容目标 | 说明 |
|----------|----------|------|
| 系统调用延迟 | 不超过宏内核的 110% | IPC 开销补偿 |
| 吞吐量 | 不低于宏内核的 95% | 零拷贝设计补偿 |
| 内存占用 | 内核内存 < 50% 宏内核 | 用户态化减少内核内存 |
| 启动时间 | 不超过宏内核的 120% | 用户态服务启动开销 |

## 6. 风险与缓解策略

### 6.1 技术风险

| 风险 | 影响 | 概率 | 缓解策略 |
|------|------|------|----------|
| IPC 性能退化 | 整体系统性能下降 | 中 | io_uring 零拷贝，预分配共享内存 |
| 驱动兼容性 | 部分硬件不可用 | 高 | 保留内核态驱动回退路径 |
| 调度延迟增加 | Agent 响应变慢 | 中 | 调度器缓存优化，减少上下文切换 |
| 内存碎片 | NV 内存管理效率降低 | 中 | 基于 VMO 的零拷贝共享 |
| 形式化验证失败 | 关键路径需重新设计 | 低 | 在设计阶段使用 TLA+ 模型检查 |

### 6.2 项目风险

| 风险 | 影响 | 概率 | 缓解策略 |
|------|------|------|----------|
| 开发周期延长 | 交付延迟 | 中 | 渐进式交付，每阶段有可用版本 |
| 人员不足 | 进度受阻 | 中 | 优先 P0 工作，P2 工作可延迟 |
| 技术债务积累 | 后期维护困难 | 高 | 每阶段进行代码审查和重构 |
| 社区接受度 | 开源生态发展缓慢 | 中 | 保持与开源版的清晰差异说明 |

### 6.3 安全风险

| 风险 | 影响 | 概率 | 缓解策略 |
|------|------|------|----------|
| 能力泄露 | Agent 越权访问 | 低 | Capability 形式化验证 |
| IPC 消息劫持 | Agent 通信被截获 | 低 | 消息加密 + 完整性校验 |
| 侧信道攻击 | 敏感信息泄露 | 中 | 时间隔离 + 缓存分区 |
| 提权攻击 | 用户态服务被利用 | 中 | 最小权限原则 + 定期审计 |

## 7. 五维原则映射

AirymaxOS 的五维设计原则与微内核化改造的映射关系：

| 五维原则 | 维度说明 | 微内核化改造体现 | 改造阶段 |
|----------|----------|-----------------|----------|
| 最小化 | 内核态代码最小化 | 内核代码裁剪至 <80K LOC | 阶段一~三 |
| 隔离性 | 组件间强隔离 | 用户态服务隔离 + Capability 安全 | 阶段二~三 |

| 可扩展性 | 策略可扩展 | SCHED_AGENT + eBPF + Cupolas | 阶段一 |
| 能效 | Token 能效优先 | Token 能效调度 + 零拷贝 I/O | 阶段一~二 |

### 8.3 开源版与闭源版的协同
