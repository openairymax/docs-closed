>
> 依据：2026-10-31 在联想小新 Pro 14 IAH10（`83JK`，Core Ultra 9 285H，Arrow Lake-H）
> 实机验收 0.0.3 时采集的现场证据，以及 B50（Battlemage `8086:e212`）与 285H 两次
> 网卡固件事故的复盘。凡本文出现的判定，均可由文中给出的命令在目标机上复算。

## 0. 结论摘要

1. **六项观感缺陷归并为三条技术主线**，不是六个独立 bug：
   - **主线 A：内核基线不认识 285H 的 GPU**（`8086:7d51`）。i915 模块虽被载入，
     但没有任何该 ID 的 alias，于是 `0000:00:02.0` 无驱动、DRM 只剩 `simpledrm`。
     显示（a）与亮度（c）都是它的派生结果。
   - **主线 B：内核没编 I2C 控制器驱动**（`CONFIG_I2C_DESIGNWARE_PCI` 未开）。
     Arrow Lake-H 的五个 PCI I2C 控制器全部裸奔，触控板（d）因此在内核里根本不存在。
   - **主线 C：交付面缺陷**——内核命令行残留 `console=ttyAMA0`、Xorg 被强制
     `fbdev`、锁屏鉴权 helper 缺权限、`ukui-*` 在 `PATH` 缺 `/usr/sbin`、
     引导配置改在非活动副本上（D-07）。这一类不需要换内核，属 0.0.4 必修。
2. **键盘背光（e）不是硬件问题**：设备节点存在且可写，缺的是用户态入口。
3. **引导期分辨率能在不动内核的前提下闭合**：本轮热修后 `fb0` 由 1920×1080
   变为面板原生 2880×1800，X 侧随之跟随（§1.1）；剩余的模糊与卡顿是同一主线 A
   的 EDID/软渲染部分，不在 0.0.4 范围。
4. **Wi-Fi 固件的两次事故有同一个结构**：固件 API 号由驱动设备表**钉死**，
   不存在运行期协商；镜像侧与内核侧的 API 集合没有交集时，只能靠人工往机器上
   拷文件。通用化方案的核心是**把「镜像里必须有哪些固件」变成构建期可计算、
   装机后自检的断言**，而不是再补一次文件。

### 1.1 就地热修与复验（2026-10-31 夜间）

在 0.0.3 机器上做了一轮最小热修，只为**证明 D-01 / D-07 的因果链**，不是 0.0.4 的实现
（0.0.4 仍按 §6.3 的能力驱动方案重写）。每一步都重启复验：

| 步骤 | 动作 | 实测结果 |
|---|---|---|
| 1 | `/etc/default/grub` 与 `/etc/grub.d/01_airymax_display` 同时写入候选串与 `gfxpayload=keep` | 已落，两处逐字一致 |
| 2 | 候选串只用 `auto` | 重启后 `fb0 virtual_size` = `800,600`（**比原来更差**） |
| 3 | 改为降序候选表，`auto` 退到末位 | 重启后 `fb0` = `2880,1800`，`modes` = `U:2880x1800p-0` |
| 4 | 只跑 `grub2-mkconfig -o /boot/efi/EFI/openEuler/grub.cfg` | 重启后无任何变化 |
| 5 | `install -m 700` 同步 `/boot/efi/EFI/airymaxos/grub.cfg` 后重启 | 引导期生效；X 侧 `xrandr` 为 `current 2880 x 1800` |
| 6 | `display_mode.sh --report`（会话内） | `default 2880x1800 2880x1800 single-mode` |

两条可复用的结论：

- **`auto` 不等于「固件给最佳」**：本固件的 GOP 模式表首项是 `800x600`，`auto` 就取它。
  步骤 2 把分辨率从 1920x1080 拉低到 800x600，是「auto 优先」方案被实测否掉的直接证据。
- **改了不生效的根因在副本**：NVRAM `Boot0003 AirymaxOS` 指向
  `\EFI\airymaxos\shimx64.efi`，活动配置是 `/boot/efi/EFI/airymaxos/grub.cfg`；`grub2-mkconfig`
  默认只写 `/boot/efi/EFI/openEuler/grub.cfg`。这是交付面缺陷，登记为 D-07。
- X 侧无 KMS、只有一个模式，`--report` 按铁律 4 如实记 `single-mode`，不记 `policy`；
  该机上**不需要**为显示策略调解任何常数，也不应该解。

## 2. 逐项判定

### (a) 分辨率不适配、显示效果差

**根因**：主线 A。GPU 无驱动 → 无 KMS → 桌面只能在固件给出的 framebuffer 上画。

三点叠加，缺一不可：

1. **没有 KMS**：`i915` 无 `7d51` alias，`xe` 不在 6.6。开机时 `simpledrm` 接管
   `simple-framebuffer.0`，它继承的是固件 GOP 设好的 1920×1080，而非面板原生 2880×1800。
2. **没有 EDID**：`card0-Unknown-1/edid` 为 0 字节，`ukui-settings-daemon` 打
   `failed to get edid:`，控制中心拿不到可用模式列表。
3. **渲染全在 CPU**：`AIGLX: Screen 0 is not DRI2 capable`、只有 `swrast`，
   2880×1800 的面板上跑 1920×1080 的软渲染，既糊又卡。

**为什么不是显示策略的错**：0.0.3 的 `display_mode.sh` 取「策略首选 ∩ 输出确实广播」
（第 36 条经验）。这里输出只广播 1920×1080，策略会「收敛成功」，把「下层没能力」
伪装成「已按策略设好」。这正是第 42 条记录过的 B50 同型缺陷，在同一版本里第二次出现。

**已作的部分修复**：本轮把「固件 GOP 给多少」这一段从 1920×1080 提到 2880×1800
（热修细节与复验见 §1.1），因此 (a) 剩下的不可解部分是第 2、3 点——没有 EDID、
软渲染——它们只能靠 KMS（§5 已决策不在 0.0.4 动内核）。由此得到一条判据：
**引导期分辨率与内核显示栈必须分开验收**，前者可在 0.0.4 闭合，后者顺延。

### (b) 很多功能点不动

**根因**：不是单点，是四条派生链。控制中心插件本身齐全
（`/usr/lib64/ukui-control-center/` 26 个 `lib*.so`，含 `libdisplay`、`libpower`、
`libmouse`、`libnetconnect`、`libwlanconnect`），失效的是插件依赖的下层：

| 现象 | 下层事实 | 归属 |
|---|---|---|
| 分辨率下拉为空 / 改不动 | 无 KMS、无 EDID（见 a） | 主线 A |
| 亮度滑条无效 | `/sys/class/backlight` 为空 | 主线 A |
| 鼠标/触控板设置无对象 | 输入设备里没有触控板 | 主线 B |
| 锁屏后输密码进不去 | `ukui-screensaver-checkpass` 权限不足，PAM `setuid failed` | 主线 C |
| 系统设置里搜索类功能静默失败 | `ukui-search` 调 `sysctl` 报 `command not found`（`/usr/sbin` 不在其 PATH） | 主线 C |

**锁屏一项要单列**：它不是「不好用」，是「进不去」。`/usr/bin/ukui-screensaver-checkpass`
权限为 `0755 root:root`，PAM 账户阶段以非特权身份调用时 `setuid` 被拒。0.0.3 的
T12「免密提权」只验证了 `sudo -n`，没有覆盖「锁屏后能否解锁」，属验收口径缺口。

### (c) 屏幕亮度不能自动调节

**根因**：主线 A 的直接后果。背光设备由 KMS 驱动注册，`i915`/`xe` 不在位时
`/sys/class/backlight` 完全为空，`libpower` 的亮度滑条与自动亮度都失去落点。
`CONFIG_BACKLIGHT_PWM` 未开不是本条根因（该机走 `intel_backlight`），但属同一批
配置审计对象。

**判据**：修复后 `/sys/class/backlight` 下必须出现 `intel_backlight`，且
`brightness` 可写、写入后 `actual_brightness` 跟随。这是可脚本化的，纳入冒烟。

### (d) 触控板不能用

**根因**：主线 B，且**与桌面无关**——触控板在内核里就没有被枚举出来。

链条：触控板挂在 I2C-HID 上 → ACPI 的 `i2c_hid_acpi` 需要一个可用的 I2C adapter →
adapter 来自五个 PCI 控制器（`8086:7778/777a/777b/7750/7751`）→ 这些控制器由
`i2c-designware-pci` 驱动 → **该驱动在 6.6.157 的内核配置里被关掉**
（`# CONFIG_I2C_DESIGNWARE_PCI is not set`，`/lib/modules/.../i2c/busses/` 里也没有
`i2c-designware-pci.ko`）。

于是 `/sys/bus/i2c/devices` 只有一个 DMI/SMBus 的 `i2c-0`，`i2c_hid_acpi` 虽然载入
却无设备可绑，`/proc/bus/input/devices` 里自然没有触控板。

**修复分两步，都可独立验证**：

1. 打开 `CONFIG_I2C_DESIGNWARE_PCI=m`（配置项现有 `CONFIG_I2C_DESIGNWARE_CORE=m`
   与 `_PLATFORM=m`，只缺 PCI 这一支）。
2. 断言 `modinfo -F alias i2c-designware-pci | grep -c 8086:7778` 非 0。若为 0，
   说明基线驱动表的 PCI ID 也缺，需要补 ID（designware 是通用控制器，补 ID 风险低）。

**不要**把它当桌面问题去查 `libinput`：设备节点不存在时，`libinput list-devices`
什么都看不到，容易被误读成「桌面没启用触控板」。

### (e) 键盘背光不能用

**根因**：主线 C，**硬件与内核均正常**。

`/sys/class/leds/platform::kbd_backlight` 存在（`max_brightness=2`），
`echo 2 > brightness` 返回 0 且读回 2，说明 `ideapad_acpi` 已正确注册 LED 类设备。
缺的是用户态入口：镜像里没有 `brightnessctl`，UKUI 也没有对应的托盘项或
Fn 快捷键动作映射。

**修复**：交付一个最小的背光控制入口（`brightnessctl` 或等价小工具），
把 Fn 组合键经 `ideapad_acpi` 的 `sparse_keymap` 映射到该入口，并在控制中心
电源页暴露三档。验收判据是「按键后 `brightness` 数值改变」，不是「进程起来」。

### (f) 很多硬件不能用 / 整体适配差

逐设备实测，可分三类：

| 类别 | 设备 | 状态 |
|---|---|---|
| 缺驱动（换内核或补配置才能修） | GPU `7d51`、I2C 控制器五个、背光 | 不可用 |
| 硬件正常、缺用户态 | 键盘背光 | 可用但无入口 |
| 完全正常 | 音频 ALC287、蓝牙 `hci0`、摄像头 UVC、Wi-Fi BE200、NVMe、传感器 ISH | 可用 |

另外两个打包缺口（不阻断，但会让排障变难）：`usbutils` 未装（无 `lsusb`）、
`wireplumber` 未装（PipeWire 无会话管理器）。`lsof` 也缺。

### 附带：两个失败单元与内核命令行

1. **`systemd-vconsole-setup.service` 失败**，进而把 `airymax-desktop-ready.service`
   判负（后者把「任何 failed unit」当失败，属正确联动）。
   手工复现得到：`Failed to check VC /dev/tty1 keyboard mode: Device or resource busy`
   与 `Failed to lock /dev/console: Input/output error`。
2. **内核命令行是 x86 上的 ARM64 残留**：
   `console=ttyAMA0,115200` 出现在 `GRUB_CMDLINE_LINUX` 里，且 `console=` 出现三次
   （`tty0`、`ttyAMA0`、`ttyS0`）。`/sys/class/tty/console/active` 为 `tty0 ttyS0`，
   `ttyAMA0` 被忽略，但 `/dev/console` 的最终落点因此变得不可预期，上述 vconsole
   失败与它同源。这一条同时说明**安装期的串口参数泄漏进了已装系统**，
   0.0.3 的 T15「durable boot arguments」只断言「参数还在」，没有断言「参数该在」。

## 3. Wi-Fi / 固件通用化方案

### 3.1 两次事故的共同结构

| | B50 | 285H（本次） |
|---|---|---|
| 网卡 | 旧款 Intel | BE200 `8086:272b` |
| 驱动族 | `iwlwifi` | `iwlwifi`（`gl-c0-fm-c0`） |
| 镜像固件 | 与驱动 API 无交集 | 镜像只有 `-92/-100/-101`，驱动要 `-83` |
| 现场处置 | 人工补文件 | 人工补 `-83.ucode` + `.pnvm` |
| 结果 | 通了 | 通了，但留 `api flags index 2 larger than supported by driver` |

两次都不是「驱动坏了」，而是**三份事实没有对齐**：

```
设备 ID（内核驱动表） ── 决定 ──> 请求的固件文件名（含 API 号）
                                        │
镜像里的 linux-firmware 版本 ── 决定 ──> 实际存在的文件名
```

第三份事实是**内核版本**：它决定驱动表里的 API 号。三者只要有一处版本不同步，
结果就是「文件不存在」，而系统给出的现象只是「网卡不工作」，没有任何指向性。

### 3.2 关键结论：固件 API 号是「钉死的」，不是「协商的」

这是两次事故最重要的教训。`iwlwifi` 的 `iwl_cfg` 表为每个设备族写死一个
`fw_name` 与 API 号，运行期按该名字 `request_firmware()`，**不会**在多个 API
之间自动降级（少数设备族有 `-1` 回退，不能作为方案依赖）。

因此：

- 「镜像里多放几个版本」只在**跨内核版本**时有用；
- 对**同一个内核**，必须精确命中它要的那一个文件名；
- 反过来，**从内核模块反推所需文件名是可行的**：`modinfo -F firmware iwlwifi`
  会列出该模块可能请求的全部固件名。这给了我们一个构建期可计算的闭包。

### 3.3 构建期：把「固件闭包」变成门禁

新增 `ci/gates/fw-closure.sh`，对每个出厂内核执行：

1. 逐驱动取 `modinfo -F firmware <mod>`，得到「本内核可能请求的文件名全集」；
   覆盖对象至少含 `iwlwifi`、`iwlmvm`、`i915`、`xe`、`btusb`/`btintel`、
   `snd_sof_pci_intel_*`、`intel_ipu6`。
2. 与该内核 RPM 的 `Requires` 所钉的固件包内容求差集；
   差集非空即失败，并把缺失文件名逐条打印。
3. 对固件包做**版本与来源登记**：包 NVR、上游 tag、镜像 URL 与 sha256
   写进 `fw-manifest.txt`，随 ISO 一起发布。
4. **`.pnvm` 必须与 `.ucode` 成对断言**：`gl-*`/`ma-*` 族缺 pnvm 时固件能载入
   但射频不可用，现象比缺 ucode 更难查。规则是「凡出现 `X-<api>.ucode`，
   同一目录下必须有 `X.pnvm`（若该族需要）」。
5. 固件文件的 SELinux 标签在同一门禁里断言为 `lib_t`（`matchpathcon`），
   避免 Enforcing 下「文件在、载入失败」——这条是第 40 条经验的同型推广。

> 该门禁的价值在于：它把「装完才发现网卡不工作」提前到「构建时缺文件名」，
> 而后者的修复成本是改一行 `Requires`。

### 3.4 装机期：固件随内核走，不做「后补」

- **固件包与内核包同源同版**：`airymaxos-kernel-core` 显式 `Requires` 一个
  按内核构建的 `airymaxos-firmware-<kernel-abi>`，而不是依赖基底 `linux-firmware`
  的版本漂移。基底包可以继续存在（供其它设备用），但**关键驱动的固件不能只靠它**。
- **ISO 内置多内核时取并集**：若 0.0.4 采用 HWE 双内核（见 §5），ISO 必须同时
  携带两套内核各自所需的固件闭包；离线闭包求解时把固件包列入 `SCOPE_WHITELIST`，
  不能被「依赖已满足」裁掉。
- **禁止现场补文件**：任何在目标机上手工 `cp` 固件的修法，必须在当天转化为
  包内变更。这条要写进验收规程，否则同一问题会在下一台机器上重演。

### 3.5 运行期：可观测与失败必须响亮

1. `airy-observe` 增加 `firmware` 探针：对关键驱动输出「驱动期望的文件名集合」
   与「实际载入的文件名」，两者不一致即非零。
2. 冒烟用例增加两条断言（TAP）：
   - `dmesg` 中无 `no suitable firmware found` / `Failed to run INIT ucode`；
   - 无 `api flags index .* larger than supported by driver`（本次 285H 就有这条，
     它意味着「能跑但与驱动约定不符」，属必须消除的隐患）。
3. 设备不可用时**不得静默**：`airymax-desktop-ready.sh` 已有 `AIRYMAX-DESKTOP-FAIL`
   标记，把「固件缺失」也纳入同一出口，避免用户只看到「网卡图标是灰的」。

## 5. 已决策：0.0.4 不动内核

上一版列的三个方案（A 回移补丁 / B HWE 双内核 / C 抬基线）全部不采纳。0.0.4 的
边界是：**不抬基线、不做 HWE、不改内核 spec 与 `kernel/` 树、不做 DKMS 或任何
树外模块**。理由是这三条路都要在 0.0.x 阶段承担内核回归面，而当前版本的主要
风险来自交付面（登录、锁屏、显示策略、固件闭包），不是内核能力。

由此产生一条判定规则，贯穿全文与 §6：**凡修复需要新增/回移内核补丁、改内核
config、或引入树外模块，一律不开工，登记为「内核依赖」并顺延**；其余缺陷必须在
发行版层闭合，且判据用能力探测（`modinfo` / sysfs / EDID / xrandr）而不是版本号。

顺延项（0.0.4 不修，登记在目）：HW-01（i915 认 `8086:7d51`、`xe`、KMS、硬件
加速）、HW-02（`CONFIG_I2C_DESIGNWARE_PCI`）、HW-03 中依赖 KMS 注册背光的那一半。

## 6. 全量问题台账（0.0.4）

本节把 0.0.3 验收报告 §10、`0.0.4-任务输入清单.md` §4、以及本轮显示链路复盘的
全部缺陷收在一处，**按「通用修复」而不是「某台机器怎么坏」来组织**。带「内核」
一列的条目一律顺延（§5 的边界）。

### 6.1 通用性铁律

通用性不是措辞问题，它决定同一份镜像能不能装到下一台机器上。0.0.4 起以下五条
按硬约束执行，违反即视为未完成：

1. **判定只认能力，不认机型**：分支条件只能读 `modinfo`、sysfs、EDID、
   `xrandr`、`/proc/cmdline`。`8086:7d51`、`83JK`、`XiaoXinPro 14` 这类字面量
   只能出现在文档与测试夹具里，不能出现在配方、脚本、门禁的分支条件中。
2. **具体数值只能当候选，不能当结论**：允许在 GRUB 里列「常见分辨率并集」，
   但选中哪一个必须由固件/EDID 回报决定；不允许「把上限设成 285H 的原生值」。
3. **探测优先级固定**：EDID 首选模式 > KMS 连接器模式集 > `fb0`
   `virtual_size` > 静态候选并集。前一级拿不到才降级，降级必须留痕。
4. **无能力判定时不做收敛**：没有 KMS/EDID 就保持固件给的模式，不猜、不下调；
   `display_mode.sh` 的结论必须是 `single-mode`，不能记成 `policy`。
   把「下层没能力」记账成「策略生效」是 0.0.3 第二次踩到的同型缺陷（第 42 条）。
5. **判据必须机型无关**：验收脚本对任意一台机器都成立；需要机型特化时，说明
   该项是硬件使能而非发行版缺陷，登记到「内核依赖」列。

### 6.3 与通用性冲突的已落改动（必须在 0.0.4 内改掉）

本轮为在 285H 上取证，显示链路的改动用了「具体数值」推进，其中两处需要收回：

- **G-01（`GRUB` 候选串）**：高分档前置本身是通用手段——GOP 只会取候选串里
  **第一个被固件支持**的模式，把它当「候选」而不是「结论」并不违反铁律 2。要收回的是
  两条被实测否掉的设想（证据见 §1.1）：
  - **不能用 `videoinfo` 枚举**：GRUB 脚本没有命令替换，`videoinfo` 的输出无法进变量，
    只能在交互命令行里读；
  - **不能以 `auto` 为主力**：本固件的 `auto` 取到 `800x600`（GOP 模式表首项），
    比不设置还差，说明 `auto` 不是「固件给最佳」的同义词。
  通用化收口（0.0.4）：候选串是**唯一**手段，顺序固定为「常见分辨率降序并集 → `auto`
  末位兜底」；选中哪一个完全由固件决定。高分段机型落到高分项，只支持 1024x768 的老
  固件逐个不匹配后落到低分段或 `auto`，因此不需要任何机型分支。候选串里的每一项都只是
  候选（铁律 2），判据：两台固件能力不同的机器使用同一份候选串、不改代码；
  `fb0 virtual_size` 等于该机固件在候选串里第一个支持的项。
- **G-02（显示策略上限）**：`CAP_W=2880` / `CAP_H=1800` 是机型绑定值，直接违反
  铁律 2。替代规则按铁律 3 的探测优先级推导，全程无机型字面量：
  - **EDID 可用**（`xrandr` 输出行的物理尺寸不是 `0mm x 0mm`）：首选模式即面板原生，
    **原样保留**，不设上限。分辨率与 UI 缩放是两件事——原生分辨率下字太小应由缩放
    策略解决，而不是降分辨率；
  - **EDID 缺失**（`0mm x 0mm`、`Virtual-*`、`simpledrm`）：首选模式不可信
    （virtio 报 1280x800，宿主实际跑在 5120x2160），改取「该输出确实广播的常用
    分辨率阶梯」中的最大者；阶梯无匹配时保留首选，不做无法落地的切换；
  - **无 KMS**（`/sys/class/drm/*/device/driver` 为 `simple-framebuffer`）：不设上限、
    不收敛，保持 `fb0` 模式，`--report` 结论记 `single-mode`。
  - 阶梯只是候选并集（铁律 2），仅用作「无 EDID 时」的收敛目标，不承担机型判定。
  - 现有单测的语义在新规则下全部成立，只需把夹具说明改成「EDID 有无」：
    `test_4k_falls_back_to_1080p`（3840x2160、`0mm` → 1920x1080）、
    `test_16x10_ladder_honored`（3200x2000、`0mm` → 1920x1200）、
    `test_285h_native_kept`（2880x1800、`301mm` → 原生）。
  - 这条规则同时解释两个现场结果而无需分支：2880x1800 面板有 EDID → 保持原生；
    4K 外接在无 EDID 时取阶梯里的 1920x1080。
- **G-03（门禁去机型化）**：`session-closure` 增一条静态扫描，禁止配方与脚本
  出现「具体机型的原生分辨率/设备名」字面量（文档、测试夹具、注释白名单），
  防止下次再以「这台机器需要」为由写死。

### 6.4 验收矩阵（按能力选机，不按型号）

| 能力 | 判定依据 | 必跑项 |
|---|---|---|
| 有 KMS + EDID | `/sys/class/drm/*/device/driver` 非 `simple-framebuffer` 且 `edid` 非空、`xrandr` 物理尺寸非 `0mm x 0mm` | D-02（保留原生）、D-03、D-04、HW-03 用户态项 |
| 有 KMS、无 EDID | 驱动非 `simple-framebuffer` 但 `edid` 为空或物理尺寸 `0mm x 0mm` | D-02（阶梯收敛）、D-03、D-04 |
| 无 KMS（simpledrm） | 驱动为 `simple-framebuffer` | D-01、D-02（`single-mode` 记账）、D-03 回落路径、D-07 引导链 |
| 无 `/dev/fb0` | 设备不存在 | `xserver.sh` 的 `driver=none note=no-fb` 路径 |

矩阵按能力选机意味着：新机型接入时不需要改验收脚本，只需要报告它具备哪几项能力。
