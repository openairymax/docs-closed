## 2. 结论

三条事实同时成立：

1. **路径类命中两处，均为构建机路径**。全文复扫后，`/home/<name>` 形态
   命中 agent-linux `6294f5fd`（台架输出树）与 agentrt/atoms `aae57d3f`
   （本机出树构建目录），改写文本见 §3。其余命中属于产品语义：`/home/amuser`
   是镜像内用户家目录，`/mnt/sysimage`、`/mnt/sysroot` 是安装器与 chroot
   视角的挂载点，删掉会让提交失去意义。版权行里的 `SPHARX` 是权利主体，
   不是路径。
2. **低级措辞集中在四个仓**：`agent-workload/agentrt` 十行、`agent-linux`
   一行、`agent-workload/products` 两行、顶层仓一行，其余为零星。
3. **公开页面上不存在需要紧急撤回的信息**：没有凭据、没有内网地址、没有
   客户数据。

因此治理的目标是措辞质量，而不是事故处置。

## 4. 为什么不能只改这十五行

改写提交信息必然改变提交号，而子仓提交号被父仓以 gitlink 记录在树里。
发布树上的 gitlink 数量是实测值：

```
agent-linux v0.0.5 树   9 个（cloudnative cognition distro kernel memory
                              security services system tests-linux）
agent-workload HEAD     4 个（agentrt ecosystem products sdk）
airymaxhub HEAD         5 个（agent-linux agent-workload amax-compute docs tools）
```

于是改写 `agentrt` 的一行信息，会连带把 `agent-workload` 与顶层仓的对应
提交全部换号；改写 `agent-linux` 的正文则直接重写 `v0.0.5` tag 指向的提交。
两条链各自独立，但都必须重建对应的 tag：`v0.0.3`、`v0.0.4`、`v0.0.5`
三个 tag 的提交都在 `agent-linux` 链上，前两个 tag 的发行页同样需要重指。
已发布页面上的 ISO 由换号前的提交装配，重建 tag 之后页面与代码不再同源：
任何人都无法从 tag 反推出那份 ISO 的构建输入。

这与两件事直接冲突：

1. **本轮发版**：`v0.0.5` 的发布运行 `45348303545` 以
   `head_sha = 46019680d` 装配，改写会让这个提交不可达，制品与 tag 的对应
   关系当场断掉。
2. **工程标准**：OS-STD-106 禁止对 `develop` 强推。三端同步强推还需要
   同时完成，否则镜像仓与主仓漂移，而 AtomGit 是主平台。

所以改写只能在版本空窗期做，且必须是一次原子操作：先按住发版，再按
「叶子仓 → 父仓 → 顶层」顺序改写并重指 tag，最后三端同时强推。在此之前
发版自证册的 tag 行（对象 `56b1fcd17` → 提交 `46019680d`）保持不动。

长期项的判据已经明确：路径类判据零容忍，低级措辞按清单词表判负，主题
长度按 72 字节裁齐。落地形态是 `ci/checks/commit_msg.py` 与
`ci/gates/commit-msg.sh`，与既有自检同列，而不是写进评审习惯里——写进
习惯的规则不会被执行。门禁默认只判 HEAD，历史区间复扫走 `--range`，
发版后的原子改写可先用它验证输入集。负例由 `ci/tests/test_commit_msg.sh`
覆盖，随仓库级自检的回归组一起跑。

改写已于 2026-11-24 完成。各仓 `refs/original/*`（合计 112 条）、
`agent-linux` 的 `archive/pre-msg-rewrite` 分支与四处 stash 是改写前的
备份引用，只在本机存在。它们持有改写前的提交，`push --mirror`／
`push --all` 会把它们一并推到远端，这两个开关在本仓一律不用。删除它们
不影响发布物，失去的是旧文与新文的对照关系，因此暂按只读留存处理。
