# AirymaxOS 0.0.3 烧录方案设计

> **版本 v0.0.3** ｜ 2026-10-30 ｜ 密级：内部机密（docs-closed）
>
> Copyright (c) 2025-2026 SPHARX Ltd. All Rights Reserved.
>
> 本文件只回答一件事：从 ghcr 上的 OCI 分块到一块可引导的 U 盘，这段路为什么必须由
> `airy-flash` 承担，以及四个子命令各自的边界、输出契约与判定口径。ISO 如何产出与
> 发布、装机与桌面如何验收，见《0.0.3-验收发行方案.md》（§2、§3.6、§5.1、§9.3）。

## 1. 问题与结论

发布物是一个 3.43 GiB 的 isohybrid ISO，经 OCI 分块通道交付；用户手里没有「下载
完的 ISO」，只有一条 tag 和一份账本。真正容易出错的是外围四项判定：**这块盘能不
能写、这个包是不是发布物、写完是否逐字节一致、事后能不能复盘**。结论：**要做
Airymax 自有烧录工具**——写入仍是系统自带的顺序块 I/O，不存在第二种正确实现；
自研的是写入前后的判定与留证，这部分在通用工具里都不存在。

| # | 硬理由 | 技术事实 |
|---|---|---|
| 1 | `dd` / `balenaEtcher` 无法校验 OCI 分块账本 | 发布物由定长 layer 组成，账本逐块记录 `sha256`/`size`/`name`。`dd` 只认一个文件，表达不了「第 N 块坏了只重取这一块」；单层整文件取件一旦断流只能从头再来，而镜像有 3.43 GiB |
| 2 | 无法在写入前做设备预检 | `dd if=… of=/dev/sdX` 不判系统盘、挂载、只读、容量，把 `/dev/sda` 写成 `/dev/sdb` 不可逆。图形工具把 ISO 模式与 DD 模式的选择留给用户，选错会静默产出不可引导介质 |
| 3 | 无法给出可判定的回读证据 | `dd` 成功只等于「命令没报错」。CI 与留证需要一行可 grep 的结论、一个退出码、一份结构化记录；通用工具只留一段滚动终端输出 |

三项都落在同一处实现上：判定必须由真正执行写入的那段代码给出。`dd` 之后另跑一次
`sha256 -c` 只是把校验交给人的记忆，而人正是最不可靠的一环。

## 2. 分发的唯一真相

### 2.1 账本由谁产出、记录什么

`ci/gates/iso-publish.sh`（经 `ci/ci.sh iso-publish` 调用）在 `image-build.yml` 的
`accept` 之后执行，条件为 `success() && release_tag != '' && !acceptance`：只有双
固件装机与冷启动通过的字节才占用发行 tag。它把 ISO 切成定长 layer、`oras push` 到
`ghcr.io/openairymax/airymaxos-iso:<tag>`，推送后重拉 manifest、逐块比对 digest
（顺序敏感）并核对整体 sha256。账本 `iso-oci.txt` 与 ISO 同目录落盘：

```text
ref=ghcr.io/openairymax/airymaxos-iso
tag=v0.0.3
name=airymaxos-0.0.3-x86_64.iso
sha256=<整体 sha256>
size=<字节数>
chunk_size=201326592
chunks=<块数>
part=0000 sha256=<该块 sha256> size=<该块字节数> name=<该块文件名>
…
```

`part=` 序号必须从 0 连续递增：拼接按清单顺序进行，序号错位就是块错位。账本末尾另
有 `pull=` / `join=` 两行原生等价写法供无本工具的环境照抄，解析器不读它们。权威来
源是 OCI 清单本身（注解 `org.openairymax.iso.{name,sha256,size,chunk-size,chunks}`
+ 逐层 `digest`/`title`），`iso-oci.txt` 是同一份结论的离线副本。

### 2.2 从 ghcr 到 U 盘的链路

| 环节 | 承担者 | 产物 / 断言 |
|---|---|---|
| 产出 | `distro/ci/run-image-ci.sh`、`assemble` | ISO、`.sha256`、`payload-manifest.txt` |
| 切分、发布、记账 | `ci/gates/iso-publish.sh` | 定长 layer 推到 `airymaxos-iso:<tag>`；远端三元组与逐块 digest 复核通过，`iso-oci.txt` 随 artifact 归档 7 天 |
| 取回 | `airy-flash fetch --oci FILE --out DIR`（或 `--ref TAG`） | 分块 → 逐块核对 → 拼接 → 整体 sha256 核对 |
| 写入 | `airy-flash write --image F --device /dev/sdX --yes` | 块设备字节 + 回读结论 |
| 复核 | `airy-flash verify` 或 `AIRY-FLASH-PASS` 行 | 与镜像逐字节一致的证据 |

`fetch` 只信账本：缺字段、声明块数与实际块数不符、分块合计不等于 `size` 都在解析阶
段判 `EXIT_CHECK` 并中止，不做「大概是它」的猜测；字节到 U 盘全程无一次跳过校验。

## 3. 四子命令的职责边界

| 子命令 | 必填输入 | 可选输入 | 写设备 | 阶段序列 |
|---|---|---|---|---|
| `fetch` | `--oci FILE` 或 `--ref REG/REPO:TAG`（二选一） | `--out DIR`（默认 `.`）、`--force`、`--oras NAME`（默认 `oras`） | 否 | 拉取分块 / 校验分块 / 拼接镜像 / 校验镜像 |
| `plan` | `--image`、`--device` | 见下 | 否 | 校验镜像 |
| `write` | `--image`、`--device`、`--yes`（块设备） | 见下 + `--report` | 是 | 校验镜像 / 写入设备 / 刷盘同步 / 回读校验 |
| `verify` | `--image`、`--device` | 见下 | 否 | 校验镜像 / 回读校验 |

后三者共用：`--sha256`、`--sums`、`--verify {sample,full,none}`（默认 `sample`）、
`--allow-unverified`、`--allow-file`、`--report`、`--json`、`--no-progress`，以及
调试用 `--mounts`、`--sys-block`。摘要来源顺序：`--sha256` → `--sums` →
`<image>.sha256` → 同目录 `SHA256SUMS`。

- **`fetch`**：取账本 → 三条预检（`oras` 在 PATH、目录余量 ≥ `size + chunk_size +
  64 MiB`、块尺寸自洽）→ `oras pull <ref>:<tag> -o DIR` → 逐块核对 → 按序拼接（边拼
  边删已用块）→ 重算整体 sha256。账本有两个等价入口、必须二选一：`--oci FILE` 读离线
  副本，`--ref REG/REPO:TAG` 现场取清单（注解给元数据、逐层 `digest` 与 `title` 给账
  目），两条路落到同一个 `OciLedger`，任一不给或同时给都判 `EXIT_USAGE`。加 `--ref`
  的理由是制品只存 7 天且需登录：只拿到 tag 的用户不该因此无法取件。已有同名同字节数
  文件时只跑「校验镜像」，`--force` 才重取。失败语义：拉取或清单不可达为 `EXIT_IO`；
  缺块、块 sha 不符、清单矛盾为 `EXIT_CHECK`；账本读不到或输出目录建不了为
  `EXIT_USAGE`。
- **`plan`**：`probe_image`（非空普通文件）→ 解析期望摘要 → `probe_device` 只读
  sysfs 与 `/proc/mounts` → 六条预检 → 校验镜像摘要。系统盘按承载 `/`、`/boot`、
  `/boot/efi`、`/usr`、`/var` 的父磁盘反查，`/dev/mapper/*` 先落到 `/dev/dm-N`，分区
  再回溯整盘，不靠名字猜 `sdX`。任一 `[FAIL]` 判 `EXIT_CHECK`，文本固定为「预检未
  通过，未触碰目标设备」。
- **`write`**：`plan` 的全部判定 + 写入 + `fsync` + 回读。写块设备要求 root，在预检
  之前拦（`plan` 豁免）；覆盖整盘要 `--yes`，在预检之后拦——此时操作者已看清目标
  身份。未 root / 缺 `--yes` 为 `EXIT_USAGE`，摘要不符为 `EXIT_CHECK`（均未写入），
  写入、刷盘、回读失败为 `EXIT_IO` 并带失败偏移。
- **`verify`**：第一段仍是「校验镜像」，再按 `--verify` 读设备比对。`sample` 比头、
  中、尾三个 16 MiB 窗口，`full` 比整个镜像，`none` 跳过并标 `[SKIP]`。不一致报
  首个不一致的**绝对偏移**，判 `EXIT_IO`。

### 3.1 为什么 plan 与 write 必须分开

分开的判据不是「多一条命令」，而是**是否打开写句柄**：

1. 目标事实全部来自 `stat` 与 sysfs，`plan` 的整条路径没有一次 `open(device, "r+b")`，
   预检可以在实机上反复跑到全绿，代价为零。
2. `plan` 不要求 root，提权只发生在 `write`：操作者先以普通用户看完整判定，再决定
   是否提权，避免「sudo 之后才发现选错盘」。
3. 两者共用同一个预检函数，判定的名字、顺序、详情文本一字不差，「预检通过 ⇒ 可以
   写」这条不变式只有一处实现；`write` 第一段仍重算 sha256，`plan` 之后镜像被替换会
   在写入前判 `EXIT_CHECK`，不会静默写进介质。

## 4. 展示层设计

**七段固定结构**：标题 → 身份（映像 / 目标 / 模式）→ 预检 → 阶段 → 结果 → 下一步
→ 标记，顺序不随结果变化；失败时只少「下一步」。版式只有两条规则：字段块顶格对齐、
列表缩进 2；预检项与阶段共用 `[ OK ]/[SKIP]/[FAIL]` 标签列与 16 列名称列，宽度按
终端显示宽度算（CJK 记 2 列）。这是对「展示很乱」的直接回应：乱来自同类信息有多套
格式；把「一行一条判定」定为唯一格式后，阶段行、预检行、下一步行是同一种行，只有
标签不同。

**为什么阶段化**：耗时并不均质——`fsync` 常比写入还久，回读按窗口推进，校验镜像
是纯 CPU。单一进度条会把「等待」「无进展」「已失败」显示成同一种「没动」；拆成
阶段后每段都有起止、耗时与结论。TTY 画进度条（吞吐 + ETA），非 TTY 退化为 25% 桶
的整行里程碑（不写 `\r`，可直接 `grep`）；5 秒无新进展补一行「已等待 Ns」；十秒内
耗时保留一位小数，避免亚秒阶段被压成 `0s`。

**为什么每段必须有固定末行记号**：

```text
AIRY-FLASH-PASS command=write host=<主机名> image=<路径> sha256=<摘要> device=/dev/sdX
```

失败时同位置换成 `AIRY-FLASH-FAIL`。这行只写已有事实：`command=`/`host=` 恒有，
`image=`/`sha256=`/`device=` 按已探测内容出现，早期失败不留空字段；失败时摘要用期望
值兜底，保证凭这一行仍能把日志对回发布物。CI 只取日志尾行断言，不必解析七段；终端
日志、串口日志、artifact 三处检索方式相同。阶段行给人看，末行给脚本看。

**下一步与失败建议**：成功时按子命令给「下一步」——`plan` 提示加 `--yes` 写入，
`write` 给四条装机后核对（选盘按键、UEFI 条目、`hostname=airymaxos` 与 `uname -r`
的 `-alk` 后缀、登录策略），`verify` 提示一致即可插机，防止把「预检通过」误当成
「已经写好」。失败时不打「下一步」，而在「结果」段给「原因」与「建议」，建议来自
错误对象自带的可执行动作（先 `umount`、换线换口、`sudo` 重跑）。成败同一条收尾路径，
因此报告、标记行、建议行的位置与格式一致。

## 5. 两条介质路径

### 5.1 块设备与普通文件

| 维度 | U 盘（`--device /dev/sdX`） | 文件（`--allow-file`） |
|---|---|---|
| 事实来源 | sysfs（容量、型号、序列号、传输层、可移动、只读）+ `/proc/mounts` | `stat` |
| 预检 | 六条全部生效 | 「目标是块设备」「非只读」标 `[SKIP]`，其余仍判 |
| 权限 / 确认 | `write` 需 root，并需 `--yes` | 都不需要 |
| 写入 | 顺序覆盖整盘 | 顺序写入，末尾 `ftruncate` 到镜像长度 |

`--allow-file` 的语义是「把字节写进一个文件」，回读与 U 盘走同一套 `readback`，不产生
任何引导结论，不能替代 U 盘腿。

### 5.2 CI 的两种挂载形态

`install-test.sh --media` 决定同一份 ISO 如何暴露给固件：`cdrom`（默认）以 CD-ROM
挂载，固件走 El Torito 引导目录，不读分区表；`usb` 用 `qemu-xhci` + `usb-storage` 以
`if=none,format=raw,readonly=on` 裸盘挂载、`bootindex=1`，固件须先解析 MBR/GPT 找
ESP。isohybrid 的 El Torito、MBR `0xEF` 分区项、GPT 条目三处一致性只有 `usb` 能证伪。

0.0.3 出现过的事实是：El Torito 腿全绿，真机 U 盘装机失败——分区项与 GPT 条目的
对齐在 `-cdrom` 通路里根本不被读取。因此 `image-build.yml` 把 `--firmware uefi
--media usb` 放在双固件 CD-ROM 全量之前，介质布局缺陷在第一条腿上就地暴露；两种
形态的产物目录必须分开，轮次目录同名，混用会互相覆盖。

## 6. 通用化边界

工具要能交给任何持有同一份发布物的用户，因此源码里没有与本地开发环境绑定的常量：

- **无本地路径**：镜像、目标、输出目录、报告路径全部由参数给出；源码中只有
  `/proc/mounts` 与 `/sys/class/block` 两个标准接口的绝对路径，且可被 `--mounts` /
  `--sys-block` 覆盖（容器、异构 chroot、单元测试）。
- **无本地主机名**：`host=` 是运行时 `socket.gethostname()` 的观测值，用于把日志对回
  执行机，不是配置常量，也不参与判定。
- **无本地凭据**：工具内没有 token、用户名或 registry 口令，取件只调 `oras pull`，
  凭据来自调用方的 `oras login`；发布侧 `GHCR_TOKEN` 由 workflow 注入 `iso-publish.sh`。
- **无介质假设**：不按品牌、型号或目录布局分支；任何块设备走同一套预检与写入，整盘
  与系统盘一律按 sysfs 语义反查，不假设 `sdX` 命名。
- **不假设仓库位置**：单文件 `airy-flash-<ver>.pyz` 交付，运行时不需源码树，不写参数与报告之外的文件。

## 7. 判定与留证

**可复现烧录的判定**：同一发布物（同 `image.sha256`）、同一设备（同 `device.model`
/ `device.serial` / 字节数），连续两次 `verify` 必须都 `PASS` 且两次标记行的
`sha256=` 相同。`write` 的 `AIRY-FLASH-PASS` 只证明「已写入且回读一致」，不证明
「可引导」；引导与桌面由《0.0.3-验收发行方案.md》§2 的 L2/L3 判定。

| 证据 | 来源 | 关键字段 |
|---|---|---|
| 末行记号 | 每次运行必打 | `command`、`host`、`image`、`sha256`、`device` |
| 结构化报告 | `--report FILE`（`.json` 或 key=value，成败都落） | `result`、`image.sha256` / `.expected`、`device.model` / `.serial`、`check.*`、`stage.*` |
| 判定码 | 进程退出码 | `0` 成功 / `1` 预检或校验未通过（未写入） / `2` 用法或环境（未写入） / `3` 写入或回读失败（已写入） |
| 归档 | 发行目录 `flash-<dev>-<utc>.json` | 见验收发行方案 §9.3 |

报告同时记录期望摘要与实际摘要：失败时实际值可能为空而期望值恒在，凭它就能判断这
份记录对应哪个发布物。回读失败给首个不一致的绝对偏移：落在头部窗口指向分区表或 EFI
镜像被破坏，落在尾部指向镜像尾部或介质末段坏块；`3` 换口重做，`1`/`2` 按建议行重跑。

## 8. 已知限制

- 写块设备需要 root；`plan` 与 `--allow-file` 路径不需要。
- 目标设备不得有任何挂载点（含其分区）——桌面自动挂载会让「未挂载」判 `[FAIL]`，
  必须先 `umount`。
- 只做顺序覆盖写：不解析、不保留、不创建分区表，不做分区、格式化、引导修复或镜像
  转换。目标盘原有布局不在判定范围内，覆盖后即丢失。
- 只在 Linux 上实现：判定依赖 sysfs 与 `/proc/mounts`；其他平台没有对应能力，系统
  盘反查不成立，需人工确认整盘身份后再写入。
- 取回依赖外部 `oras`（`--oras` 可指定路径），两个账本入口都要它：`--oci` 只用它的
  `pull`，`--ref` 还要 `manifest fetch`；输出目录须有 `size + chunk_size + 64 MiB`
  余量，不足判 `[FAIL]` 且不进入拉取；重试由调用方决定，工具只建议「换镜像站重跑」。
- `--verify sample` 只比三个 16 MiB 窗口，不是全量证据；`--verify none` 跳过回读，
  `write` 的成功不再构成「逐字节一致」的证明，报告标 `[SKIP]`。
- `--ref` 以清单注解为元数据来源，因此只对带 `org.openairymax.iso.*` 注解的 tag 成立；
  早于分块实现的 tag 只有 `created` 注解，会被判 `EXIT_CHECK` 而不是猜着下载。
- 校验镜像与写入在同一进程内先后执行，两步之间仍存在镜像被替换的窗口；介质中途掉线
  由 `EXIT_IO` 报出失败偏移，不会静默截断。
