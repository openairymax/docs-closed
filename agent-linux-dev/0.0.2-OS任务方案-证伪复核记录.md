## 3. 已证实缺陷与系统性修复

### D-01 存量重复列项（最严重）

**现象**：方案按主图纸口径，把「已交付或大幅交付」的 WP **全额**计入 0.0.2 待建账本。

**反证证据**（逐条可复现）：

| 在范围 WP | 主图纸计 LOC/任务 | 仓库存量证据 | 存量占计 |
|---|---|---|---|
| A-01/A-02/A-03/A-04（548~551 入口） | 898+786+673+786 = 3,143 / 24 | `kernel/kernel/syscalls/{airy_syscalls.c,airy_invoke.h,airy_invoke_test.c}` 564 行，**548~551 四个入口均已存在**，并含 KUnit 用例 | ≈ 18%（入口部分≈100%） |
| A-05 Badge | 1,122 / 9 | `AIRY_CAP_BADGE` 2 文件 / 42 行 | 部分 |
| A-06 ipc_ring | 2,020 / 16 | `ipc_ring` 15 文件 / 109 命中 | 大幅 |
| A-20 eventfd | 786 / 6 | `airy_eventfd` 6 文件 | 大幅 |
| A-23/A-26 tracepoint/描述符表 | 1,010+1,234 / 18 | `airy_tracepoint` 0 命中；`airy_invoke_dispatch` 3 文件 | 部分 |
| A-33 corekern 装配 | 673 / 5 | `corekern` 18 文件 / 1,890 行 | 大幅 |
| B-01/B-02/B-03/B-05 | 1,409+1,315+939+845 = 4,508 / 35 | `cap_derive` 11 文件、`cap_check` 18 文件、`security/airy` 12 文件 2,357 行 | ≈ 52% |
| C-03 superv IPC | 1,112 / 9 | `airy_superv` 9 文件 / 45 命中；`superv` 目录 173 行 | 部分 |
| L-01/L-09/L-22 codegen 族 | 1,804+1,015+564 = 3,383 / 26 | `tools/codegen` **4,701 行**（含 Rust/Python/Go/TS SDK 绑定 + 统一 pipeline + pytest） | **≥100%（已超）** |
| L-03 DSL 编译器 | 1,804 / 14 | `tools/dsl` **2,137 行**（lexer/parser/semantics/codegen/compile + 6 pytest） | **≥100%（已超）** |
| L-04 [SC] 契约头与三路编译 | 2,256 / 18 | `tools/sc-tri-compile` 728 行 + 17 个契约头已落盘 | 大幅 |
| L-05 ABI 检查器 | 1,353 / 11 | `tools/abi-check` 588 行 | ≈ 43% |
| L-12 defconfig 矩阵 | 1,353 / 11 | 5 个 `airy_defconfig` 已落盘 | 大幅 |
| L-07 CI 流水线扩展 | 2,932 / 23 | 9 个 workflow 已落盘（含 codegen-verify / dsl-verify / sc-dual-ci） | 大幅 |

**量化**：在范围 63 WP 中，**约 20 个 WP（≈ 240 个任务、≈ 24,000 行列账）受本缺陷影响**；
真正未开工的是 `K-01`（`services/` 仅 1 个 `macro_d.c`）、`R1-01~R1-06`、`P-01`、
`M-01~M-24`（distro 仅有静态工件，无 RPM 流水线/镜像 CI）与 `V-01~V-11`。

**根因（系统性，非补丁）**：方案**混用了两套前提**——主图纸是「从零开始」的计划账本（其 §1.3 Phase 0
另立、不入账），而 0.0.2 是「资产已落地」的执行计划。直接沿用计划账本即产生重复列项，
违反方案自己在 §1.3 写下的准则「**不得把已完成项重复列为待建**」。

**系统性修复**：为 0.0.2 引入**存量抵扣（asset offset）**机制——
每个在范围 WP 先做 gap-check，产出三元证据（① 落点文件 ② 特征符号 ③ 实测行数 / 主图纸计 LOC），
只把**缺口任务**计入 0.0.2 账本；存量 ≥100% 的 WP 直接从账本剔除（标记 `ASSET-SATISFIED`）；
存量部分达成的 WP 按其**缺口分片区间**（如 `T<WP>-07…-14`）保留。该机制须写入生成器
（`bp_002_gen.py` 增 `ASSET_OFFSET` 表 + 断言「剔除后每个保留任务仍有前驱链」），并附逐 WP 证据台账。

### D-02 主图纸缺 initramfs/dracut 覆盖，0.0.2 直接继承该空洞（**阻塞项**）

**现象**：0.0.2 目标 ③「OS 能正常运行」在本方案内**无法闭环**。

**反证证据**：
- `grep -c 'initramfs\|dracut' agentrt-linux开发路线和进度.md` = **0**（主图纸零覆盖）；
- 而 `docs-linux/190-distribution/03-installer-design.md`、`190-distribution/01-rpm-packaging.md`、
  `100-operations/01-deployment.md`、`10-architecture/05-adrs.md` **均出现** initramfs/dracut，
  即设计侧有要求、施工侧无 WP 承接（**"方案有、图纸无"**，与主图纸 v3.2/v3.4 补录要修的缺口同类，唯独此条被漏）；
- 0.0.2 交付的是**自定义 airy 内核**（`A-30/A-33 + L-12 airy_defconfig + M-01 kernel spec`），
  自定义内核装进镜像后**必须配套生成 initramfs**，否则安装盘与已装系统均无法冷启动 → 直接击穿目标 ②/③。

**根因**：主图纸 M 模块的镜像链只覆盖到「基础镜像构建（M-14）+ 镜像 CI（M-13）」，未把
「内核 RPM → initramfs/dracut 生成 → 镜像注入」这一段任务化。

**系统性修复**：为 0.0.2 新增 WP `M-25 内核包与 initramfs 生成集成`（建议 LOC 1,200 / 10 任务，
泳道 DIST1，前驱 `M-14, L-12`，后继 `M-13`），并**回补进主图纸种子**（`bp_seed.py` 的 `WPS["M"]` +
`SUPP` 证据台账指向 `190-distribution/03-installer-design.md`），使图纸与方案库重新对齐。

### D-03 QG-03 桩扫描口径不可执行

**现象**：`grep 'TODO\|FIXME\|stub\|skeleton\|not implemented'` 会命中**上游 Linux 6.6 主线源码**。

**反证证据**（实测命中，全部为上游代码，非 Airymax 债务）：
`kernel/reboot.c:61` "Temporary stub that prevents linkage failure"、
`kernel/livepatch/transition.c:65` "just a stub"、`kernel/ptrace.c:155` FIXME、
`kernel/cgroup/cpuset.c:2681` TODO、`kernel/seccomp.c:1116` ENOSYS、`kernel/kallsyms_selftest.c:96` `stub_name[]`。

**后果**：按现写法 QG-03 必然长期全红 → 门禁被绕过 → 等同失效。

**系统性修复**：QG-03 判定范围限定为 **Airymax 自有路径白名单**：
`kernel/kernel/{syscalls,ipc,superv,corekern,log}/**`、`kernel/security/airy/**`、`kernel/init/airy_*.c`、
`kernel/include/uapi/linux/airymax/**`、`kernel/include/airymax/**`、`tools/**`、`distro/**`、
`services/** | system/** | tests-linux/**`；并明确 **ALK 铁律豁免**——上游文件内出现的
`stub/TODO/FIXME` 不计入本门禁（OS-IRON-003 只新增文件、不改主线，天然隔离）。

### D-04 方案与仓库的 548 语义漂移

**现象**：同一号段存在两种语义定义。

**反证证据**：
- 主图纸 / 本方案：`A-01 = syscall 548 airy_folding 入口与分发`；
- 仓库 `kernel/kernel/syscalls/airy_syscalls.c:165`：`SYSCALL 548: airy_sys_call — control-plane management entry`；
- `airy_folding`、`airy_badge`、`airy_sched_tac` 在 `kernel/` 中命中数均为 **0**。

**根因**：图纸命名取自早期设计稿，实现侧在落地时改名/改语义，**双向未对账**（主图纸缺少
「实现侧命名回写」环节）。

**系统性修复**：以**实现侧为准**修订图纸（A-01 更名为 `syscall 548 airy_sys_call 入口与分发`），
并在 `L-04` 的 DoD 中增加「**契约头 ↔ 图纸 WP 名** 双向一致性检查」，纳入 `sc-dual-ci.yml`；
同时在 0.0.2 方案 §2.2 增加一条「命名漂移勘误」记录（本项即为其证据）。

### D-05 A-33←A-30（x86_64-only）降级依据不足（**过裁**）

**反证证据**：`kernel/arch/{x86,arm64,riscv,sw_64,loongarch}/configs/airy_defconfig` **5 个均已落盘**；
`ci-airy.yml` 的 job 矩阵已含 `[x86_64, arm64, riscv, loongarch]`。即**多架构骨架已就位**，
把 0.0.2 裁到单架构属于**把已具备的能力误裁**，且与 §2.3「不重复列项」准则同源的过度保守。

**系统性修复**：把 §2.2 第 2 条由「A-33←A-30（x86_64-only，裁撤 A-31/A-32）」改为
「**A-33 保留 A-30 前驱；A-31/A-32/A-36 按存量抵扣后仅补缺口**」——即三架构接线若已具备则剔除，
未具备则保留缺口任务；架构放行仍以 x86_64 为验收架构（E1-02/E1-04），但**构建矩阵不裁**。

### D-06 §1.3 资产清单描述失真

**现象**：§1.3 低报了存量规模，直接诱发了 D-01。

**反证证据**：见 §1 证据基线（44 文件 5,741 行 vs 文中"11 个 .c"；17 头 vs 文中"12 个"）。

**系统性修复**：§1.3 改为**机器可复核的资产台账**（文件数 / 行数 / 特征符号由脚本采集，禁止人工描述），
并与 D-01 的 `ASSET_OFFSET` 表**共用同一份证据源**，保证"描述"与"抵扣"不脱节。

### D-07 里程碑口径三套并存（存疑）

**反证证据**：仓库源码注释使用「M1 scaffolding / pending M2 handler landings / pending M5 memory tiering」
（如 `airy_syscalls.c`），与主图纸 S0~S8、本方案 B0~B5 构成**三套编号**。

**系统性修复**：明确口径层级并在方案中声明——**仓库 M0~M9 = 实现侧内部里程碑（代码注释用）**、
**S0~S8 = 主图纸（1.0.1 施工轨）**、**B0~B5 = 0.0.2 bring-up 轨**；三者映射关系列为一张对照表，
避免跨文档讨论时各说各话。

## 6. 结论与放行意见

**结论**：0.0.2 方案的**结构（SSoT 同构、依赖双向可审、旁路边登记、诚实降级）成立**；
但其**账本口径不成立**——它把主图纸的「从零计划账本」直接当成了「存量已落地」的执行账本，
导致约 20 个 WP / 约 240 个任务重复列项（D-01），并继承了一个主图纸级阻塞空洞（D-02）。

**放行意见**：**不予放行施工**。须先完成 §5 的 P0 两项与 P1 四项修订，重跑生成器产出
`0.0.2版-OS任务方案.md` v0.0.3，并以**同一套证据源**复核修订后的账本，
确认「无重复列项、无未登记旁路边、initramfs 链闭合」后，再进入 Day-1 开发。

**下一步（供决策）**：
1. 执行 20 个受影响 WP 的 gap-check，产出 `ASSET_OFFSET` 证据台账；
2. 回补 `bp_seed.py`（新增 M-25）并重跑 `bp_gen.py` / `bp_002_gen.py`；
3. 出 v0.0.3 方案，再复核放行。
