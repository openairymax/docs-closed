## 1. 为什么不是引导器菜单

引导器菜单（grub 两个 `menuentry`）看起来更简单，但要把内核行复制成两份：
`10_linux` 生成的 `linux`/`initrd` 行里含发行版自己拼的参数集，第二份只能
抄一遍。抄出来的第二份必然与第一份漂移，症状是「文本模式那条偶尔起不来」，
而正常路径永远不经过它，回归也测不到。

引导器还按架构分叉：x86 与 ARM 分别是 `grub2-pc` 与 `grub2-efi`，RISC-V
若走 u-boot，菜单语法又换一套。三架构稳定运行是 0.0.4 的硬要求，把启动
选择放进引导器等于给每套固件各写一份实现。

因此选择在**内核起来之后、桌面拉起之前**做：一份 systemd 服务加一个
小终端程序，三个架构共用同一条路径，且能在 CI 用伪终端直接测。

## 2. 启动会话选择

### 2.1 组件

| 组件 | 位置 | 职责 |
|------|------|------|
| `airy-session-pick` | `system/bin`，装 `/usr/bin/` | 在终端上画选择页、读键、倒计时，写结论 |
| `airy-session-choice.service` | `system/units` | `graphical.target` 之前跑一次判定 |
| `display-manager` drop-in | `distro/desktop/` | 显式选 TUI 时跳过桌面 |
| `desktop_ready.sh` | `distro/desktop/` | 按模式判 GUI 或 TUI 就绪 |
| `boot-set` 清单 | `distro/presets/boot-set` | 服务随镜像启用，不另立清单 |

### 2.2 判定契约

- **唯一事实来源**是 `/run/airy-session/mode`，内容为 `gui` 或 `tui` 一行。
  下游只读这一个文件，不再各自推断。
- **缺文件即 GUI**。这是失败安全的默认：服务崩了、终端不可用、机器无键盘，
  结果都必须是「照常进桌面」，不能是「掉进文本模式」。
- **TUI 只能由用户显式选择产生**。因此跳过桌面的条件是
  `ConditionPathExists=!/run/airy-session/mode-tui`（一个只在用户选 TUI 时
  才出现的标记），而不是「有没有文件」。
- **不进倒计时的情况**：`/proc/cmdline` 含 `airymax.session=off`（验收镜像
  与自动化用），或进程拿不到任何可用终端。两种都直接写 `gui` 并退出，
  不占用 120 秒。

### 2.3 服务形态

```
[Unit]
Description=AirymaxOS session choice
DefaultDependencies=no
After=local-fs.target
Before=graphical.target display-manager.service
Conflicts=rescue.target

[Service]
Type=oneshot
RemainAfterExit=yes
StandardInput=tty-force
TTYPath=/dev/tty1
TTYReset=yes
TTYVHangup=yes
ExecStart=/usr/bin/airy-session-pick --timeout 120 --default gui

[Install]
WantedBy=sysinit.target
```

`StandardInput=tty-force` 让程序拿到真正的键盘输入而不是 journal 管道；
`TTYReset`/`TTYVHangup` 保证退出后 tty1 交还给 getty，不残留 raw 模式——
这是他类程序最常见的遗留缺陷：程序异常退出后终端回显全丢，用户以为机器坏了。

### 2.4 终端程序的判据

| 情形 | 行为 | 退出码 |
|------|------|--------|
| 120 秒内按 `G` 或回车 | 写 `gui` | 0 |
| 120 秒内按 `T` | 写 `tui` 与 `mode-tui` 标记 | 0 |
| 120 秒到 | 写 `gui`，不留 TUI 标记 | 0 |
| 没有可用终端（无 tty、无串口） | 写 `gui`，不等待 | 0 |
| `airymax.session=off` | 写 `gui`，不等待 | 0 |
| 写文件失败 | 不阻塞启动，退 0 并留一条 journal 记录 | 0 |

退出码只有 0：这一步**不允许失败阻断开机**。判定缺省的代价是「进了桌面」，
而不判定成功的代价是「机器起不来」，前者可接受，后者不可接受。

### 2.5 渲染

一屏之内完成，不滚屏，不写装饰性噪声：

```
AirymaxOS 0.0.5

  桌面模式（默认）   按 G 或回车
  文本模式            按 T

  剩余 120 秒后进入桌面模式
```

- 只用 ASCII 与既有 unicode 字体，颜色仅用于强调当前剩余秒数。
- 倒计时每秒原地重绘一行，不整屏重画。
- 不做动画、不做进度条：120 秒的窗口里，动画只会让「卡住」与「正常」难以区分。

### 2.6 下游改动

1. **display-manager** 增加 drop-in：
   `ConditionPathExists=!/run/airy-session/mode-tui`。显式选 TUI 时单元被
   条件跳过，`graphical.target` 照常到达（它不等 display-manager 完成）。
2. **`desktop_ready.sh`** 读同一文件：`gui` 走既有三级校验（失败记账、
   UKUI 会话定义、lightdm 与 X11 会话），`tui` 改为断言 `multi-user.target`
   已达成且 `getty@tty1` active，输出 `AIRYMAX-DESKTOP-READY mode=tui`。
   两种模式共用一份就绪输出格式，验收脚本不必分支。
3. **`airy-observe boot`** 增加一行 `session=<mode>`，让现场取证不必登进
   桌面才知道这台机器选了哪种模式。

## 3. 启动页与开机打印

### 3.1 问题

现有开机打印是逐行滚屏的 `step`/`mark` 混杂：同一件事在不同脚本里各自
起措辞，失败时只有一句自然语言，现场无法回答「卡在哪一步、这一步等多久
算卡」。285H 上两次 SSH 失联三分钟，正是因为没有任何一行说明「当前处于
哪一阶段、预期多久完成」。

### 3.2 打印契约

一份库 `/usr/lib/airymaxos/scripts/ui.sh` 是唯一输出实现：

```
ui_step <序号> <总数> <阶段名>
ui_ok   <阶段名> <关键值...>
ui_note <阶段名> <事实...>
ui_fail <阶段名> <判据...>
```

每行同时落 console 与 journal，格式固定：

```
[ 3/9 ] 电源与热治理      ok   landed=51/51 cap=100
[ 6/9 ] 运行时带宽        ok   runtime=950000 group=yes
[ 8/9 ] 桌面就绪          FAIL lightdm 未 active（mode=gui）
```

- 序号与总数让「卡住」变成可判读事实：停在第 7/9 就是卡在第 7 步。
- `ok`/`note`/`FAIL` 是稳定 token，CI 与现场脚本用同一字符串判定，不看措辞。
- 失败行必须带判据（缺什么、读到什么），不带「请检查配置」这类无法行动的话。
- 每阶段入口写一行带阶段名的 journal 记录，配套 60 秒心跳；心跳缺失即说明
  该阶段已越界。

### 3.3 阶段划分

开机阶段固定为九个，顺序即执行顺序，总数写进契约而不由各脚本自报：

`基础挂载` → `首启判定` → `数据分区` → `运行时带宽` → `换页上限` →
`电源与热治理` → `桌面与 RT 共存` → `桌面就绪` → `自检与取证`。

新增阶段必须同时改契约表与 `%check` 里的总数断言，否则判据与实现分叉。

### 3.4 引导期外观

- 沿用 `rhgb quiet`，把内核启动噪声交给 plymouth；未安装 plymouth 的剖面
  只保留 quiet，不打印无关的驱动探测行。
- grub 主题沿用 `01_airymax_display` 已落定的 gfxmode 与 gfxpayload，新增
  只做**字体与配色**，不引入第三方主题包，避免主题包与字体版本绑定。
- 不做开机动画。判断标准是：一屏之内能读出「到了哪一步、有没有失败」，
  任何会拖慢这一点的装饰都不做。

### 3.4.1 console 字形预算：ASCII 面与中文面分离

用户口径「开机的打印中、信息的展示，都有很多没有显示出来的乱码」。
2026-11-09 在 285H 上逐项取证，结论是**不是编码坏了，是排版面没有字形**：

| 观测 | 值 |
|---|---|
| `/etc/vconsole.conf` | `FONT="latarcyrheb-sun16"` |
| 基底 console 字体 | `/usr/lib/kbd/consolefonts` 212 个条目，CJK 字体 0 个 |
| journal 编码 | `journalctl -b -o cat \| iconv -f utf-8 -t utf-8` 返回 0；U+FFFD 0 条、ESC 0 条 |

VT 用 16 像素拉丁字体渲染中文，得到的只能是方块或空白——正是「没有显示
出来」的形态。VT 字体上限 512 个字形，一个常用汉字表就装不下，所以
「给 console 装一套中文字库」不是可行解，只能把两种读者分开。

契约（0.0.4 已实现 console 侧，本版补齐边界与强制）：

1. **console 与串口**：纯 ASCII，只出序号、稳定 token 与 `key=value` 事实。
   `ui.sh` 的 `_ui_ascii` 已在 tag 内兜底（非 ASCII 换 `?`），屏幕至少仍能
   读出 `[ 3/9 ] data ok mounted=/data`。
2. **journal 与桌面**：中文。读者是系统起来之后的运维与用户，终端编码正确。
3. **机器判读面**（TAP、串口还原、验收报告）：同 1。验收剖面当前仍有一处
   越界——验收上报单元以 `journal+console` 逐行转发 TAP 明细，而 TAP 里的
   `zh font: 文泉驿等宽微米黑` 是 CJK，落到本地屏即方块。处置：转发目标改为
   串口设备，console 只留一行 ASCII 结论（`AIRYMAX-SMOKE-PASS/FAIL`），
   两条通道各自满足自己的字形预算。
4. **单元禁用 `journal+console`**，除非在 `units_lint` 的豁免表内并写明理由。
   该组合把 journal 的人类措辞直接搬到 VT，是这类回归的唯一入口。

判据（`units_lint` 三条断言）：产品单元无 `journal+console`；console 行字节
集落在 `[ -~]`；验收剖面的例外只剩串口转发一条，且其行集同为 ASCII。

### 3.5 烧录期打印

装机侧沿用 `step`/`mark` 两段式，但收敛到同一份格式，且每步带序号；
`fail` 行必须带可定位的关键值（设备名、返回码、缺失路径）。目标是
「只要卡住，就知道卡在哪一件、缺什么东西」。

### 3.5.1 固件来源噪声：console 只留一行，逐条进 journal

`quiet` 只压 `KERN_INFO`/`KERN_DEBUG`，**`KERN_ERR` 照常落屏**。285H 一次
干净开机（6 小时 12 分，`tainted=0`）的 69 条 err 级记录全部由平台固件自述
矛盾产生，没有一条来自产品单元：

| 形态 | 条数 | 出处 |
|------|------|------|
| `AE_ALREADY_EXISTS, During name lookup/catalog` | 32 | xHCI RHUB 的 `_UPC`/`_PLD` 重复声明 |
| `AE_NOT_FOUND` 解不出符号 | 余量 | `_TZ.TZN._TMP` 引用不存在的 `MXTP`、`_SB.PCN.LPCB.MXTP` |
| `failed to add RAPL MMIO interface` | 1 | `proc_thermal_pci` 与固件能量计数器布局不合 |

这些行对用户不可行动（改不了固件），对开发可行动但已由 §4.6.1 的
`platform` 类记账；留在 console 上的唯一效果是把「第九阶段是否通过」
淹掉——这正是「开机打印看着乱」的另一半来源：不是编码坏，而是**判读面
被不可行动的行占满**。

处置分三层，都不改内核（守 ALK 净新增 0 行）：

1. **内核侧不动**。这些行是 ACPICA 在解析固件表时的自述矛盾，能改的只有
   「打印级别」：`dmesg -n` 全局降级会连带压掉真实驱动错误，
   `ignore_loglevel`/`log_buf_len` 只改缓冲不改事实，`acpi_osi=` 会改变
   固件走的代码路径（症状可能从日志搬进行为），三者都不解决问题本身。
2. **console 侧合并**。首启自检把本次 boot 的 err 行按 §4.1.2 三类归账，
   检测到非零 `platform` 类时只打印一行：

   ```
   [ 9/9 ] 自检与取证      note platform_err=69（固件自述矛盾，见 journalctl -k -b -p err）
   ```

   判据是「计数非零即可见」而不是「不打印」：静默丢弃会把真故障一起藏掉。
3. **journal 侧保真**。逐条原样保留，带 `_TRANSPORT=kernel` 与 boot id，
   `airy-observe boot` 输出分类计数与首条原文，现场不必自己数。

跨架构口径：三条形态分别对应 x86 ACPI、arm64 ACPI（服务器与部分开发板）
与 riscv64 ACPI 的同一类固件自述错误，判据写成「非产品来源的 err 行按类
计数并汇总一行」，不写任何具体 ASL 路径。设备树平台没有 ACPI 命名空间，
该计数自然为 0，不需要第二套分支。

### 3.7 开机分段基线（285H，0.0.4-7，2026-11-08 取证）

`systemd-analyze` 一次冷启动读数：

```
Startup finished in 7.962s (firmware) + 3.782s (loader) + 864ms (kernel)
 + 1.191s (initrd) + 1.899s (userspace) = 15.701s
graphical.target reached after 1.878s in userspace.
```

读法三条，避免把「不是我们的部分」算进优化目标：

| 段 | 值 | 归属 | 处置 |
|---|---|---|---|
| firmware | 7.96s | 平台固件 POST，不属操作系统 | 只登记，不进优化目标；实机建议开 Fast Boot，不能写进判据 |
| loader | 3.78s | GRUB | `GRUB_TIMEOUT=3` 是主因（≈3s 等待 + 0.7s 装载）。改 `grub_args.sh` 单点，不在镜像里散改 |
| kernel + initrd | 2.05s | 内核与 initramfs | 归一化到「不增加」 |
| userspace | 1.90s | systemd 单元 | `blame` 首位是设备节点等待（1.13s），不是单元自身耗时，不得据此裁单元 |

loader 的 3.78s 是**唯一可免费拿回的时间**：把 `GRUB_TIMEOUT` 降到 1s
可省约 2s，且不改变任何启动语义（菜单仍可按 Esc 唤出）。验收判据写成
「loader ≤ 2.0s」，不写「总时长 ≤ N 秒」——后者会被固件耗时漂移污染。

同一份 `critical-chain` 里还有一处 896ms，处置结论是**登记而不优化**：

```
graphical.target @1.878s
└─multi-user.target @1.878s
  └─plymouth-quit-wait.service @980ms +896ms
```

2026-11-07 在 285H 上取证：桌面剖面**确实装有 plymouth**
（`plymouth-22.02.122-2.oe2403sp3`，默认主题 `tribar`，`/dev/fb0` 由
`simpledrm` 提供，journal 有 `Starting Show Plymouth Boot Screen` 与
`Received SIGRTMIN+20 from PID … (plymouthd)`），即 `rhgb` 是有画面的，
不是空转。这 896ms 是 splash 收尾的串行等待，不是哪个单元写错：
`plymouth-quit.service` 是 `WantedBy=multi-user.target` 且
`Before=lightdm.service`，`plymouth-quit-wait.service` 的
`Before=multi-user.target` 让 `graphical.target` 必须等它；而 `plymouthd`
收到 quit 后仍要走完自己的收屏（同一次 boot 的 monotonic：SIGRTMIN+21 落于
3.60s 与 3.92s，`graphical.target` 在 4.08s）。

不拿掉它的理由是同一件事有两面：把这段换成 console 直写要删 `rhgb`，等于
取消产品既定的启动画面；而「卡住能定位」已由 `systemd/scripts/boot_watch.sh`
兜住——它判定卡住时先 `plymouth --hide-splash` 再印阶段行，splash 只在
「一切正常」时挡住文字。因此判据分两条，不混成一条：正常路径看
`loader ≤ 2.0s` 与 `userspace ≤ 2.0s`；异常路径看卡点报告是否在 60 秒内出现。
把 896ms 算进「可优化」会诱使实现去删画面，而删掉画面并不能改善真正卡住时
的可读性——那件事已经由 `boot_watch.sh` 解决。

#### 3.7.1 复核读数（285H，2026-11-10）

同机同口径再取一次，用于确认上表的处置是否真的落地：

```
Startup finished in 7.635s (firmware) + 2.271s (loader) + 946ms (kernel)
 + 1.327s (initrd) + 2.649s (userspace) = 14.830s
graphical.target reached after 2.171s in userspace.
```

两条结论：

- loader 从 3.782s 降到 2.271s，与 `GRUB_TIMEOUT` 单点下调一致，判据
  「loader ≤ 2.0s」已接近达成；kernel+initrd 2.273s，未增加。
- `blame` 首位换了人：`airymax-update-check.service` 15.708s。这一条与上表
  的「设备节点等待」性质不同——它是单元自身的执行超时（feed 请求打不通后
  等满超时再失败），属可优化项，处置归本版 §4.4 首启网络自检，不在此重开。

内核健康度同批取证：`hardware error`/`machine check`/`mce` 计数 0，NVMe
错误与超时 0，`thermal_zone` 读数 20–41°C。即当前 285H 的稳定性风险集中在
用户态单元与会话进程，不在内核。

## 4. 首启网络可得性（x86 / ARM / RISC-V 同步）

### 4.1 事实与根因

B50 与 285H 在第一次烧录后都出现过「装完没有网络」：桌面无无线入口，
`nmcli device wifi rescan` 无任何结果，最后只能靠手机 USB 网络共享取网。
0.0.4 在 285H 上取证到可直接定位的根因，不再是推测：

| 证据 | 值 |
|------|----|
| 内核要求的固件名 | `iwlwifi-gl-c0-fm-c0-83.ucode`（`dmesg`：`loaded firmware version 83.ec13314b.0 gl-c0-fm-c0-83.ucode`） |
| 包内实际布局 | `intel/iwlwifi/` 下 183 个文件 |
| 装完的镜像 | 固件根上只有 12 个手工扁平软链（`/usr/lib/firmware/iwlwifi-*.ucode -> intel/iwlwifi/...`，时间戳即现场手工创建） |
| 失败态 | 软链缺失时 `request_firmware` 失败，`iwlwifi` 不创建 `wlan*`，NetworkManager 也就无设备可扫 |

根因是**布局口径分叉**：内核按扁平名取固件，包按厂商目录安装，
0.0.3 的 `%post` 没有补齐全量扁平入口。这是**一类**问题，不是一块网卡的问题：
`i915`/`amdgpu`/`brcmfmac`/`ath11k`/`mt76`/`rtw88`/`rtw89` 都存在
「安装路径与请求名不一致」的可能，缺少扁平入口时表现为驱动静默不工作。

0.0.4 的口径已经不是「补 iwlwifi」，而是请求名驱动：
`distro/firmware/fw-flat.sh` 从模块树读 `modinfo -F firmware`，按驱动自报
的名字反查固件树、按真实后缀建扁平软链，`%posttrans` 调用并把
`flat=/miss=/fail=` 追加到 `/var/log/airymaxos/firmware-flat.log`
（spec `0.0.4-3`，回归在 `distro/tools/tests/test_fw_flat.py`）。因此
「厂商目录」这层常量在 0.0.4 树里已经不存在，本版不再重写这一层。

**真正的缺口是「没有按架构证明过一次」**：生成器在装机时按本机模块树
工作，三架构走同一段代码，但 `modinfo` 读的是哪一棵模块树取决于这次装的
镜像；x86 有 285H 的加减对照，aarch64 与 riscv64 从未跑过，`miss=` 行也
从未在任何架构上被当作判据消费。本版补的是**构建期按架构的覆盖断言**与
**运行期通用判据**，不是再补一条 `if`（见 §4.3、§4.5）。

### 4.1.1 第二类现象：固件宣告的 API 组超出驱动表（已改判，非缺陷）

扁平入口补齐后，285H 的无线可用（`wlp1s0f0` 起、NetworkManager 拿到地址），
但内核日志里有一行容易被当成缺陷的告警：

```
iwlwifi 0000:01:00.0: api flags index 2 larger than supported by driver
```

逐层核对后确认**这不是固件取不到，也不是版本错配**：

| 事实 | 出处 |
|------|------|
| 驱动认识的 API flags 位数 | `kernel/.../iwlwifi/fw/file.h:249-291`，枚举末项 `IWL_UCODE_TLV_API_BAND_IN_RX_DATA = 59`，`NUM_IWL_UCODE_TLV_API` 取值为 60（`128` 只是 sparse 的 `__CHECKER__` 分支） |
| 驱动接受的 word 下标 | `iwl-drv.c:448` 判 `api_index >= DIV_ROUND_UP(60, 32)`，即只接受 0、1（bit 0~63），越界仅 `IWL_WARN` 后 `return` |
| 该设备的驱动支持线 | `cfg/bz.c:13` `IWL_BZ_UCODE_API_MAX 83` |
| 实际载入的固件 | `loaded firmware version 83.ec13314b.0 gl-c0-fm-c0-83.ucode`，即**版本号正好等于支持线** |
| 其余就绪证据 | PNVM `752be616`、PHC 注册、`base HW address`、Bluetooth 同批就绪 |

结论：版本轴（83 = 83）完全对齐，告警只是固件按更新的 API 表编译、额外宣告
了一个驱动不认识的 word，驱动主动忽略后继续。随发行版固件比内核新而来的
这条告警是**常态**，任何装了当代 `linux-firmware` 的 6.6 内核机器都会出现。

同一段日志里的第二行更易被误读：

```
iwlwifi 0000:01:00.0: Detected Intel(R) TBD Bz device, REV=0x472
```

`TBD` 是驱动 `cfg/bz.c` 给该代际起的占位名（设备代号未公开时的惯例写法），
不是「PCI ID 缺项」，也不是「型号没认出来」。2026-11-09 复核：`lspci` 报
`8086:272b`，`dmesg` 同时给出 `PCI dev 272b/00f4` 与
`loaded firmware version 83.ec13314b.0`，三处自洽。判据因此按**证据组合**
写——设备 ID、固件载入、`wlp1s0f0` 出现——而不按日志里是否出现厂商型号名。
把 `TBD` 当缺陷去找补丁，只会得到一条改不掉的字面量。

该设备另有一处已修的不稳定：s2idle 往返后 D3cold 掉设备导致无线不回来。
内核 `c55e7fc9590d ("iwlwifi: pcie: keep 0x272b off D3cold across s2idle")`
已在 v0.0.4 内核树（`1d197a579729`）内，随内核 RPM 交付；本版只需把
「待机往返后无线仍在」加入 §4.7 的实机判据，不再改驱动。

因此 0.0.4 的 T21 原判据（日志里不得出现该行）属**判据错误**，已在
`distro 467d378 ("ci: judge wireless firmware by loaded evidence")` 改判为
正证据：内核枚举到的每个 iwlwifi 设备都必须有一行 `loaded firmware version`；
设备在而固件没载入，无论日志用哪句话解释，无线能力都不可用。该修正已在
v0.0.4 标签内（父仓 `8828b31` → distro `a34850f`），285H 上的失败来自
修改前的旧镜像（build `r42136960007`）。

仍然成立、且本版必须补的是**反方向**的供给缺口：包内若只有编号高于
`ucode_api_max` 的固件，驱动会以 `no suitable firmware found` 收场，那才是
装完没网的形态；`brcmfmac`、`ath11k`、`mt76`、`rtw89` 没有 in-driver 的
API word 表，判据只能落到「版本号区间内必有可用文件」。ARM 与 RISC-V 板卡
用的正是这些族，所以这条要按架构无关的不变式写，不是给 iwlwifi 打补丁。

### 4.1.2 第三类差异：T23 的预算不能只有一个数

2026-11-06 在 285H 上用最新判据对旧镜像（build `r42136960007`）实测：
`pass=24 fail=2`，T21 转绿（正证据生效），T26 判负且 183 条扁平入口全缺——
**这就是「第一次烧录后没网」的根因**：内核用扁平名取固件，包内只有
`intel/iwlwifi/` 子目录，`iwlwifi` 直接以取不到固件收场。旧镜像能上网，
是因为现场手工补了 12 条软链。

同一次实测里 T23 判负：`errors=78 owned=0 foreign=66 unknown=12 budget=2
packages=drift`。按开机时间窗（boot 后 3.5 分钟内）逐条核对，**真正属于这次
开机的外来 err 只有 6 条**：

| 条目 | 归类 | 证据 |
|------|------|------|
| `pulseaudio ... pid.c: Daemon already running.` ×2 | 基底会话 | 基底 UKUI 与产品 autostart 并发拉起，产品侧无单一 owner |
| `proc_thermal_pci 0000:00:04.0: failed to add RAPL MMIO interface` ×1 | 平台 | 内核 ↔ 平台固件边界，发行版不改固件消除不掉 |
| `dhclient ... Invalid domain name.` ×2、`parse_option_param: Bad format d` ×1 | 基底 | NM 后端走 `/sbin/dhclient`（openEuler 打包默认仍是 dhclient，`NetworkManager --print-config` 打印 `# dhcp=dhclient`），主机无域名时 FQDN 解析告警 |

其余 60 条来自本次诊断期间的人工探测（pid 2xxxx，13:34–13:48 的
`dhclient -6 -cf /tmp/t6.conf lo` 等），不属于产品行为，也不应在取证窗口内。
由此得两条设计结论：

1. **预算按类记账，不跨类合并**。`owned`（产品单元）恒 0；`platform`（内核 ↔
   固件边界）单列；`base`（基底会话/守护进程）单列且每条附「为何不是我们的」
   证据；`unknown` 必须为 0，出现即为判据失效而不是噪声。预算文件按
   `class=qemu|real` 分行，每行都带实测来历，仍只许下降。
2. **能消除的不记账**。`pulseaudio` 收归单一 owner；NM 后端显式改为
   `dhcp=internal`（NM 自带客户端，去掉 `dhclient` 的三条告警，也去掉一个
   已废弃的外部依赖）。平台类无法消除的才进 `platform` 预算，并注明
   主板/固件指纹，换机即失效——避免预算变成永久免罪符。

### 4.1.3 第四类事实：网络前端不在镜像内（与固件无关的第二条链）

固件链决定「有没有 `wlan*` 设备」，前端链决定「用户能不能看见并连上」。
2026-11-06 在 285H 上装的旧镜像（build `r42136960007`）只有一次开机，
`journalctl --list-boots` 的整个会话即为首启现场，时间线可直接把两条链拆开：

| 时刻 | 事实 | 出处 |
|------|------|------|
| 21:55 | 安装事务 1163 包，包集合内没有 `kylin-nm` | `dnf history list` ID 1 |
| 21:59:32 | NM 启动，`Loaded device plugin: NMWifiFactory`、建出 `wlp1s0f0`，无任何已保存连接 | `journalctl -b 0 -u NetworkManager` |
| 22:05:17 | 现场手写 `ifcfg-HUAWEI-Li` 后才关联 AP——没有任何图形入口，只能用命令行 | `ls -l /etc/sysconfig/network-scripts/` |
| 22:42 | 补装 `qt5-ukui-platformtheme` + `qt5-styles-ukui` | `dnf history list` ID 2 |
| 23:41 | 补装 `kylin-nm` 及伴包 `network-manager-applet`、`nm-connection-editor`、`libnma`、`libappindicator-gtk3`、`mobile-broadband-provider-info`、`kf5-networkmanager-qt` | `dnf history list` ID 3 |
| 23:41 后 | SNI 条目由 4 项变 8 项，右下角网络图标出现 | `org.kde.StatusNotifierWatcher.RegisteredStatusNotifierItems` |

结论：旧镜像的两条链同时断，症状都只是「没网」，修复面却完全不同——补固件
扁平入口解决设备枚举，补齐前端闭包解决用户入口。`kylin-nm` 是 0.0.4 施工期
才补进 comps 的（distro `2983685`），旧镜像必然缺失；v0.0.4 镜像内含该包，
并由 T28（控制中心三个网络模块 + 可执行）与 T30（三对「可执行 + autostart」）
双向判定，避免「包在而条目缺」这种无日志的静默失效（音量那件的 autostart
条目名是 `ukui-volume-control-applet.desktop`，由 `ukui-media-common` 提供，
与二进制不同名）。

跨架构含义：`kylin-nm` 是 x86_64 二进制，AArch64 与 RISC-V 的等价入口未必
同名、未必同仓。本版据此把前端判据表达为**能力入口**而不是包名——面板 SNI
必须有网络项、控制中心必须有网络模块；由哪个包提供不写进判据（W-A2）。
另有一条新装常态要进判据：首装没有任何已保存连接（上表 21:59 行），所以
W-N4 的「可联网」必须在零配置状态下成立，不能以「已有 profile」为前提。

### 4.1.4 第五类事实：142 秒空窗不是 NetworkManager 的缺陷

v0.0.4 首启现场（2026-11-07 11:34:49 开机）一度以「NetworkManager 全程
没有自动激活尝试」被记为缺陷。本次用文件出生时间加一次对照重启推翻了
这个判断：

| 事实 | 实测 | 出处 |
|------|------|------|
| `ifcfg-ziroom602` 与 `keys-ziroom602` 的出生时间 | 11:37:12.409，即开机后 143.66 秒 | `stat -c '%w'` |
| 同一时刻 NM 审计行 | `op="connection-add-activate" ... pid=1994`（kylin-nm） | `journalctl -b -1 -u NetworkManager` |
| 空窗期（3.89–143.66 秒）NM 日志 | 除设备就绪外无任何记录 | 同上 |
| 对照重启（profile 已存在） | 7.456 秒 `policy: auto-activating connection 'ziroom602'`，7.756 秒 `Activation: successful` 并取得 192.168.124.66 | 同上 |

两个被否定的猜想：`ifcfg-ziroom602` 里确实没有 `psk` 行，但
`keys-ziroom602`（`-rw-------`，`WPA_PSK=`）保存了密钥，`psk-flags=0`；
`autoconnect=yes`、`autoconnect-retries=-1`。密钥与自动连接开关都正常，
缺的只是「首启时根本没有这个连接」。同一份 NM 1.44.2、同一份 ifcfg-rh
插件，唯一变量是「有无已保存 profile」，结论只能落在 profile 的来源上：
装机全程离线（闭包在 ISO 内），anaconda 没有任何无线连接可写进目标系统，
镜像自身也不具备零配置联网能力。

这条事实把 W-N4 的判据钉在「零 profile」状态上，并追加一条产品要求：
首次开机必须给出可见的联网入口（面板 SNI + 控制中心网络模块）与一行可
定位的自检结论；「连不上」与「没有可连的东西」必须在日志里可区分。

同一现场记录的「右下角网络图标全部消失」仍未定性：重置面板进程后恢复，
clean reboot 之后不再复现；`org.ukui.panel.settings statusnotifierbutton`
的 schema 默认是 `true`，用户 dconf 无覆盖（`dconf dump /org/ukui/panel/`
为空），`panel.conf` 的 `statusnotifier` 插件与 `showApp` 白名单（含
`kylin-nm`）均正常，SNI watcher 的 `RegisteredStatusNotifierItems` 在重启
后有 7 项。该现象目前只有运行态证据，作为 W-N4 的观察项保留，不记为已
定位缺陷，也不允许用「默认值改 false」这类未证实的猜测去修。

还有一类现场证据必须在 W-N4 的判据里与「断网」分开：285H 本次开机第 20 分
23 秒，`iwlwifi` 连打 4 条 `Unhandled alg: 0x703`（接收侧出现未登记的加密
算法帧，多发生在组密钥重装或漫游瞬间），同期 NetworkManager 无 disconnect、
无重连，链路未中断。判据口径据此拆开：断网只认 `nmcli` 状态迁移与
`iwlwifi` 的 `Microcode SW error`、`firmware crash` 两类硬事件；`Unhandled
alg` 计入丢帧观测，不得当作断网证据，也不得因为出现它就判网络 FAIL。

### 4.2 设计原则

1. **单一事实源**：扁平清单只由一个生成器产出（安装期 `fw-flat.sh`，
   输入是本机模块树的 `modinfo -F firmware`），运行期复核、冒烟判据 T26
   与诊断工具三者消费同一份，任一处不得自持一张路径表。
2. **失败必须自证**：网络起不来时要能读出「缺哪个文件 / 哪个驱动没绑定 /
   哪个设备没有 carrier」，不允许只留一个「没网」的结论。
3. **架构无关**：判据与诊断只看 `/sys/class/net`、`/sys/bus/*/devices` 与
   `dmesg` 的固件加载事实，不写死 PCI ID 或厂商目录名。

### 4.3 W-N1 固件布局清单（SSoT）

已落地的形态（0.0.4 树，本版只扩不重写）：

- 安装期 `%{_libexecdir}/airymaxos/fw-flat.sh` 从模块树读
  `modinfo -F firmware`，按驱动自报的名字在固件树里反查（字符最短路径
  优先）、按真实后缀建软链，结果写进
  `%{_datadir}/airymaxos/firmware/firmware-flat.list`（`%ghost` 声明）。
- `airymaxos-firmware.spec` 的安装期脚本节只调这一支，不含任何厂商名常量；
  新增厂商由驱动的 `MODULE_FIRMWARE()` 自报请求名，不改脚本。
- 清单是生成器的产物，不落成构建期常量表；运行期复核、T26 与验收共用
  同一份，避免「测试和产品各写一套」。

本版新增的只有两条（其余口径沿用 0.0.4），细则分别落在 §4.3.1 与 §4.3.2：

1. **构建期按架构预演一次**：在 ISO 组装之前，用镜像将要装的同一份固件
   名字集与四个架构各自的模块请求名跑一遍补齐，把 `miss=` 当判负。
2. **`miss=` 进判据**：安装期日志的 `miss=` 由 T26 消费，非零即失败并附
   缺失的请求名原文，不再只是一个计数器。

当初设想的构建期方案（`gen-fw-manifest.py` 扫安装树、按前缀族归类）已在
0.0.4 施工中废弃。以下三条是废弃理由，保留在这里以免被重新提出：

- 按前缀族归类实为二级猜测：族规则本身就是厂商常量表，且压缩后缀
  （`.xz`/`.zst`）与内核请求名不同名，归类一旦漏项就静默失效。请求名是
  内核侧的既成事实，不是本项目的假设。
- 脚本必须与清单同包：只装脚本不调用则入口永远补不上，只调用不装则下次
  升级即断。
- 触发器必须是 `%%posttrans` 而非 `%%post`：rpm 按包顺序执行「装文件→
  %%post」，固件包先于 `linux-firmware` 落地时 `%%post` 看不到目标文件，
  只能静默跳过——这正是首装无网、升级后自愈的形态。

沿用 0.0.4 的其余判据：

- 软链不入包体：目标文件属 `linux-firmware`，同一路径被两个包持有会让
  dnf 事务直接失败。
- 判定拆成两项：门禁③「文件在」与门禁⑦「按裸名可取」（运行期按清单
  复核每条软链的指向），首装无网的两种形态各由一项拦。
- 回归：`distro/tools/tests/test_fw_flat.py` 覆盖补链接、最短路径优先、
  既有文件不覆盖、缺件记账、幂等、无请求即失败、复核通过/错链/缺项、
  用法错误；`test_fw_contract.py` 按可执行代码断言 `%%posttrans` 的调用、
  参数与 `Requires: kmod`，并禁止出现厂商目录。

版本区间覆盖（收口 §4.1.1）同属 W-N1，规则如下，仍在生成器一处实现：

- 生成器同时解析内核树得到每个固件族的**驱动支持区间**：`iwlwifi` 取
  `cfg/*.c` 的 `fw_name_pre` + `ucode_api_min`/`ucode_api_max`，其余族取
  `MODULE_FIRMWARE()` 的请求名集合；`iwlwifi` 另解析 `fw/file.h` 的
  `NUM_IWL_UCODE_TLV_API` 终值，只为报告「驱动可接受的 API word 上界」，
  不作为判负条件。
- 判据是**覆盖**而不是删除：每个族在 `[min, max]` 内至少要有一条可装入的
  文件；只有编号高于 `max` 的文件时判负（`reason=no-file-within-support-line`
  `family=<族> want=<min..max> have=<最高编号>`），构建期即失败，不等到装机。
- 高于 `max` 的文件照常入包并保留扁平入口：它们是内核升级后的现成资源，
  删掉既无收益又会让下一次升级缺件。
- 判据与清单同源：T26 查「清单内每项在固件根有入口」，覆盖断言查「区间内
  必有件」，两者都读 `%{_datadir}/airymaxos/firmware-flat.list` 的同一份
  族描述，不再各自 grep 目录。
- 该规则不写死厂商：新增族只需在生成器补一条解析规则；RISC-V/AArch64
  的 DT 板卡固件走同一条路径，不存在「只有 x86 才查」的分支。

### 4.3.1 构建期预演：在装机之前按架构判负

T26 只在该镜像自己的 rootfs 上复核「清单与入口一致」，回答不了「该架构
模块树请求的东西，固件树里到底有没有」——后者的输入是**别的架构的模块树**，
而四个架构的 kernel RPM 只在构建期同时在场。riscv64 没有实机兜底，ARM 的
板载无线在 QEMU 里也不出现，这一条因此只能在构建期拦。

判据的输入是两个**名字集**，不是两份文件树：

- 固件名字集：`rpm -qlp` 读镜像将要装的那个 `linux-firmware` RPM，只取
  `/usr/lib/firmware/` 下的条目，剥掉前缀后一行一个相对路径。
- 模块请求名：按架构把 `kernel-modules` 的 `*.ko*` 解到临时目录，用
  `modinfo -F firmware` 取 `MODULE_FIRMWARE()` 自报的名字（与安装期同一条
  取法，不另写解析）。

预演树是**空文件骨架**：按固件名字集逐条 `install -d` 建目录、`: >` 建同名
空文件。判据只看名字与相对路径（后缀决定入口名、相对路径长度决定最短优先），
不读内容，所以空文件与真文件的判定完全等价，代价从「复制数 GB 固件」降到
「建数千个空 inode」。

落点：`distro/ci/fw-preflight.sh`（随源码树交付，不入包）。

```
用法: fw-preflight.sh --firmware FILE --modules DIR --arch NAME
  --firmware  固件名字集，一行一个 /usr/lib/firmware 下的相对路径
  --modules   该架构模块树根（含 */kernel/.../*.ko*）
  --arch      报告用的架构名
退出码：0 全部命中；1 有请求名在骨架里查不到或骨架建不起来；2 用法错误
```

stdout 恰好一行自证，CI 与人工读同一行：

```
AIRYMAX-FW-PREFLIGHT arch=aarch64 flat=87 miss=0
```

缺件时逐条打印请求名原文（现场唯一能拿去 grep 的东西），以 1 退出：

```
AIRYMAX-FW-PREFLIGHT arch=riscv64 flat=0 miss=2
miss name=brcmfmac43455-sdio.bin
miss name=brcmfmac43455-sdio.txt
```

挂载点：`.github/workflows/image-build.yml` 的 L1，在 `Fetch release kernel
RPMs` 之后、`Build desktop ISO in container` 之前新增一步「Verify firmware
layout per architecture」。放这里而不是组装之后，是因为 ISO 组装要几十分钟，
本步只需几分钟；判负越早，失败代价越小。四个架构串行，每个架构一行自证，
任一行为负即整步失败。

不变量：预演用的是**同一份** `distro/firmware/fw-flat.sh`（直接调用，不复制
实现）与**同一个** `linux-firmware` RPM（与镜像组装取自同一处），因此预演
与装机不会各判一套。

回归：

- `distro/tools/tests/test_fw_preflight.py`：全命中（0 且行含 `miss=0`）、

### 4.3.2 安装期 `miss=` 进 T26：把「请求了但没有」判成失败

0.0.4 tag 的 T26 只做一件事：调 `fw-flat.sh check` 复核清单里每条入口的
指向。清单与入口一致即通过，而 `%posttrans` 落盘的 `flat=/miss=` 只在失败
行里作为附注 `tail -n 1` 打印，**从不参与判定**。后果是「驱动请求了、树里
没有」这一形态在验收里永远为绿——清单里根本不会出现这个请求名，check 自然
只验它有的那几条。

改法三处，共用一条解析：

- `%posttrans` 已把 `miss name=<请求名>` 逐条写进日志（stdout 与 stderr 同
  文件，`2>&1` 成立），实现不改。
- `t26_wifi_fw()` 增加第二步：取日志里**最后一条** `^flat=` 行解析
  `miss=`；非零即失败，并把该次 `apply` 期间的 `miss name=` 行原样附在失败
  行之后。
- 日志缺失或没有 `flat=` 行 → 失败，判据文本「fw-flat 未在目标系统执行」
  ——这正是 0.0.4-2 的真实形态（`%posttrans` 没跑到，入口不存在）。

失败文本（现场可直接抄去搜索）：

```
T26 FAIL flat=0 miss=2 log=/var/log/airymaxos/firmware-flat.log
  miss name=brcmfmac4356-pcie.bin
  miss name=brcmfmac4356-pcie.clm_blob
```

边界：只认最后一条 `flat=` 行。同一台机器可能经历多次升级，早期故障行不应
判当前失败；每次 `%posttrans` 都以 `mv` 覆盖整份清单，最后一条对应最后一次
事务，与清单状态同代。`flat=` 为 0 且 `miss=` 为 0 属正常——入口早已补齐时
本轮不新建任何链接。

单测（`distro/tools/tests/test_run_smoke.py`）：末行 `miss=2` 判负并带出两条
名字；末行 `miss=0` 通过；日志在但无 `flat=` 行判负；多次 apply（中间行
`miss=3`、末行 `miss=0`）判通过。

### 4.4 W-N2 首启网络自检（可定位）

新增 `airymax-net-doctor.service`（oneshot，`After=NetworkManager.service`，
`Before=graphical.target`，失败不阻塞桌面），在「本次开机没有任何可用网络」
时产出一行结论，写入 `/run/airymaxos/net.state`，并由冒烟与现场共用：

```
AIRYMAX-NET state=<no-device|no-firmware|no-carrier|no-ssid|dhcp-timeout>
             dev=<ifname> driver=<mod> fw=<ok|missing:path> rfkill=<n> hint=<...>
```

判定顺序即排障顺序：

| 状态 | 判据 | hint 内容 |
|------|------|-----------|
| `no-device` | 无 `wlan*`/`eth*`（除 lo） | 该总线上未绑定驱动的设备与 `uevent` 的 `DRIVER=` |
| `no-firmware` | `dmesg` 有 `Direct firmware load for <X> failed` | 缺的 `<X>` 原文与包内候选路径 |
| `no-carrier` | 设备存在、`carrier=0` | 关联的 phy 与 `rfkill` 软/硬阻塞计数 |
| `no-ssid` | 有 phy、`wpa_supplicant` 起、扫描为空 | 扫描次数与最近一次 `iw` 错误 |
| `dhcp-timeout` | 关联成功、未取得地址 | 租约等待秒数与 `nmcli` 设备状态 |

只读、无改动、不重试；它的价值是把「装完没网」压成一条可直接定位的行。

已知边界（2026-11-16 285H 取证）：实现里的 `dhcp-timeout` 只认「carrier=1
且无非 link-local 地址」，而 `iwlwifi` 在未关联时同样给 carrier=1。285H 在
开机第 4 秒判出 `state=dhcp-timeout`，3 秒后 wpa_supplicant 才完成 5GHz
关联并立即拿到租约（06:17:17.215 判定、06:17:20.163 关联、06:17:20.329
租约），日志里留下的结论是错的。W-N2 落地时「关联成功」要做成显式判据
（`iw dev <if> link` 或 NM 设备状态进入 ip-config），没有 DHCP 事务时给
`pending` 而不是 `dhcp-timeout`；否则这条判据在无线首联的机器上系统性误报，
现场会照着错误方向去查 DHCP。

### 4.5 W-N3 三架构口径

| 架构 | 主用无线/有线 | 本版必须成立的不变式 |
|------|---------------|----------------------|
| x86_64 | `iwlwifi`、`rtw88/89`、`r8169` | 该架构模块树声明的全部请求名在固件树里按扁平名可解析（`miss=0`），T26 与构建期预演同判据 |
| aarch64 | `brcmfmac`（`brcm/`）、`ath11k`（`ath11k/`）、`mt7921` | 同上；设备发现走设备树 `compatible`，不依赖 PCI ID，`no-device` 的诊断从 DT 节点起算 |
| riscv64 | 板载无线（板卡 DT 描述）、`r8169` | 同上；无条目即判负——该架构没有实机可兜底，构建期预演是唯一拦截点 |

三列的判据是同一句（请求名可解析），差异只在设备发现入口：x86 走
`/sys/bus/pci`，ARM/RISC-V 走 `/sys/firmware/devicetree/base`。判据实现
共用一份，架构差异不进入判据文本。

### 4.6 W-N4 首次联网体验

- 首次进入桌面即放开无线：`rfkill` 无软阻塞，`wpa_supplicant` 随
  NetworkManager 就绪，桌面的网络入口由 UKUI 原生组件提供，不自造面板。
- 入口要按**能力**判定而不是按包判定（§4.1.3）：面板
  `RegisteredStatusNotifierItems` 里必须有网络项、控制中心必须有网络模块，
  两者缺一即判负。首装没有任何已保存连接，所以判据必须从「零 profile」
  起算——旧镜像的失败正是「设备在、入口无」，命令行之外无路可走。
- 首启自检的结论同时落 `/run/airymaxos/net.state` 与串口一行，装机现场
  不需要登录即可判断是「无设备、缺固件」还是「没配 SSID」。
- 更新检查（UP-01）在 `no-device`/`no-firmware` 时必须判「未知」，
  不得把「没连上」记成「已是最新」，与 0.0.4 已定的退出码口径一致。

### 4.6.1 W-N5 开机 err 记账治理（承接 §4.1.2）

T23 目前只有一个数 `foreign_max=2`，而真机同一判据读到 66。数本身不是错的，
错在**把三种来历不同的 err 塞进同一个预算**：基底会话重复起守护进程、
平台固件边界的 ACPI/热区告警、以及人工探测产生的噪声，混在一个阈值下，
结果只能是「为让真机过而抬高阈值」或「真机永远判负」。两者都让判据失去
意义。因此本项不是调数，是换记账结构：

1. **预算文件按机器类别分行**：`err-budget` 从一行 `foreign_max=N` 改为
   `class=qemu` / `class=real` 两组，每组下按 `owned` / `platform` / `base`
   分条，每条附 `<机器指纹> <首次观测日期> <原文摘要>`。读取侧取与当前
   机器类别相符的一组；缺组即判负，不回退到另一组。
2. **`owned` 恒 0**。属产品单元的 err 一律视为缺陷，不给预算；出现即失败，
   修代码而不是加额度。
3. **`base` 与 `platform` 必须带归因证据**。`base` 每条要写明「为何不是
   我们的单元」（单元名、包名、上游出处）；`platform` 每条要带主板/固件
   指纹，换机即失效——同一块盘插到另一台机器上，`platform` 预算不继承。
4. **`unknown` 恒 0**。归不进三类的 err 说明判据的解析规则漏了形态，
   此时应改解析规则并补用例，不得默认算作噪声放过。
5. **能消除的不进预算**，本版先消两条：
   - `pulseaudio` 的 `pid.c: Daemon already running`（285H 每轮 2 条）。机理
     不是「会话与系统各起一次」——`rpm -ql pulseaudio` 里根本没有 systemd
     单元。pulseaudio 17 的 `/usr/bin/start-pulseaudio-x11` 已不再拉起守护
     进程，只经 `pactl` 加载 X11 模块，守护进程改由 libpulse 的 autospawn
     创建；会话启动瞬间多个客户端并发连接，一个赢得竞争，其余的留下
     `Daemon already running`（285H 实测 PID 2034/2275/2303 相隔 51ms，
     三者命令行同为 `/usr/bin/pulseaudio --start --log-target=syslog`）。
     收归单一 owner：产品自带 user 单元 `pulseaudio.service`（随
     `default.target` 启动、`--daemonize=no`），`client.conf.d` 置
     `autospawn = no`，`start-pulseaudio-x11` 保持只装 X11 模块——先起守护
     进程、后接客户端，竞争面从根上消失。同一处补
     `/etc/pulse/default.pa.d/`：基底 `pulseaudio-17.0` 未打包该目录，
     守护进程每次启动都打印一条 `stat()` 失败。
   - NetworkManager 的 DHCP 后端显式设为 `dhcp=internal`（NM 自带客户端），
     去掉 `dhclient` 的 `Invalid domain name.` 与 `parse_option_param: Bad
     format d` 三条，同时去掉一个上游已废弃的外部依赖。
6. **取证窗口与人工探测隔离**。判据只读「本次 boot 的 `_BOOT_ID`」条数，
   并在输出里带 `pid` 与 `comm`；现场需要手工探测时先写
   `/run/airymaxos/probe.mark`，该标记之后的条目不计入 T23。这条不是放宽，
   是把「人做过什么」变成可判定的边界，避免下一次又把 60 条人工噪声
   当成产品缺陷。

判据输出同步改为分账形态，一行读完就知道是「谁的问题」：

```
AIRYMAX-ERR owned=0 platform=1 base=2 unknown=0 budget=platform:1/base:2
```

## 5. 实机缺陷的架构无关化（承 0.0.4 §19 台账）

0.0.4 在 B50 与 285H 上抓到的缺陷全部是同一形态：**功能缺席而日志无错**。
装机成功、开机成功、无线可用、`systemctl --failed` 为 0，缺的那一块只在
人眼里。这类缺陷不受架构限制——成因不是某块硬件，而是判据只覆盖了链路的
一端。因此本版的处理口径不是「x86 修完再照抄到 ARM」，而是把每条缺陷
归到一个**失效形态**，判据写在形态上，三架构各自提供实例。

### 5.1 缺陷 → 失效形态 → 架构相关性

| 0.0.4 台账 | 现象 | 失效形态 | 架构相关性 | 处置 |
|---|---|---|---|---|
| 首装无网（B50 / 285H） | 装完没网络 | 布局分叉：内核按扁平名取固件，包按厂商目录安装 | 无关：目录名不同、形态相同 | §4 W-N1~W-N5 |
| D-08 | 右下角网络图标整块消失 | 闭包缺席：面板白名单按名等待 `kylin-nm`，包名不带 `ukui` 前缀，依赖求解不带入 | 无关：同一 RPM 集合，各架构同缺 | W-A2 |
| HW-02 | 触控板不出现 | 表项缺项：`intel-lpss-pci.c` 无 ARL-H 的 12 个 PCI ID，驱动不 probe，`dmesg` 一行错都没有 | 形态无关、表项相关：ARM/RISC-V 对应设备树 `compatible` 与板级驱动 | W-A1 |
| ARM/RISC-V 的同形缺口（2026-11-07 取证） | 同类设备在 ARM/RISC-V 上同样不出现 | 层缺席：`i2c-hid` 的 core 与全部传输层未编入内核，`I2C_HID` 菜单开着也无模块可绑 | 无关：同一份失效形态，缺的层不同 | §5.2.1 |
| N-04 / N-05 | 关于页版本名称、桌面版本号 | 口径分叉 / 二进制硬编码 | 无关：同一二进制 | N-04 已随 0.0.4 落，N-05 随 UKUI 4.24 |
| S-01 / S-02 | 空闲锁屏不生效、口令解不开 | 配置未生效：`/etc/dconf/profile/user` 缺 `system-db:local`；PAM 早期读不到 shadow | 无关 | 0.0.4 已落，本版补跨架构回归 |
| D-37（2026-11-07 取证） | 桌面进程崩溃，系统仍判绿 | 观测缺口：崩溃落进 coredump（`ibus-ui-gtk3` ×2、`peony` ×1），T23 只读 `systemctl --failed`，T24 只读网络，没人读崩溃记录 | 无关：同一批 UKUI 二进制与同一套会话脚本 | §5.7 W-A4 |
| deb 双击（2026-11-08 取证） | 双击 `.deb` 落归档管理器，只能用终端装 | 分派缺席：能力在 `airy-deb`，MIME 定义与 `.desktop` 均未登记 | 无关：两件产物都是 noarch，三架构同缺 | §5.12 W-A6 |

一句话概括：**凡是「硬件在、驱动没绑上」或「包在集合里、入口不在」的，
都按能力判定，不按型号判定。** 型号判定只能有一次，就是取证时写下具体
ID；写进判据的那一刻，换一块板子就失效。

### 5.1.1 ALK 开机 err 账目（285H，2026-11-08 取证）

用户问「ALK 内核运行是否稳定」。这个问题不能用「有没有 err」回答：本次
开机 `journalctl -p err -b` 有 112 条，其中内核自身占 1 条。把 112 条按
「谁报的错」拆开，才知道系统到底稳不稳：

| 签名 | 条数 | 是谁的错 | 处置 |
|---|---|---|---|
| `ACPI Error: AE_ALREADY_EXISTS`（name lookup） | 32 | 固件：DSDT 重复定义同名对象 | 非内核缺陷 |
| `ACPI BIOS Error (bug): Failure creating named object [...]`（`HSN`/`SSN` 的 `_UPC`/`_PLD`） | 32 | 固件：USB-C 连接器对象被定义两次 | 非内核缺陷 |
| `ACPI ... AE_NOT_FOUND`（`\_TZ.TZN._TMP` 中止、`\_SB.PCN.LPCB.MXTP` 无法解析） | 4 | 固件：方法体引用不存在的符号 | 非内核缺陷 |
| `upower-wake-up-usb-device.rules: Failed to write ATTR{.../power/wakeup}` | 34 | 用户态：规则对没有 `wakeup` 属性的子设备（`inputN`/`eventN`/`hidrawN`/`wakeupN`）照样写 | W-A3 闭包修：规则先判属性存在 |
| `receive_packet failed on wlp1s0f0: Network is down` | 2 | 会话时序：`wpa_supplicant` 先于 `NetworkManager` 起，发包时接口未 up | 并入 §4 首启网络时序 |
| `Can't lock single file, ukui-panel is already running!` | 2 | 会话：面板单实例守护与自启竞争 | §5.10 |
| `proc_thermal_pci: failed to add RAPL MMIO interface` | 1 | **内核**：MMIO 与 MSR 两条 RAPL 注册路径互斥 | 观测项，不影响调频；本轮登记，不改内核 |
| `ukui-control-center` 崩溃 dump、`[pulseaudio] Daemon already running`、`Failed to start ... smoke report`、`elfutils disabled` | 4 | 桌面与会话（见 §5.7 D-37） | W-A4 |
| `kex_exchange_identification: read: Connection reset by peer` | 1 | 取证工具自身：SSH 会话被重置 | 非系统项，剔除 |

结论按三条可判定判据给，不按「err 是否为零」给：

1. **无 oops / panic / soft lockup / hung task**：本轮 `grep -cE` 计数为 0。
2. **内核前缀的 err 只剩登记在册的已知项**：本轮只有 1 条 RAPL MMIO 注册
   竞争，与固件表无关，且调频走 MSR 路径不受影响。
3. **崩溃记录归桌面进程而非内核**：`coredumpctl` 本轮为
   `ukui-control-center` SIGABRT ×4、`ukui-kwin_x11` SIGSEGV ×1、
   `ibus-ui-gtk3` SIGSEGV ×3，全部是用户态。

前两条成立，故 ALK 6.6.161-alk 在 285H 上判为稳定；第三条里
`ukui-kwin_x11` 的 SIGSEGV 打中的是窗口管理器本身，属 §5.7 的观测面缺口，
不能因为「系统还在跑」而判绿。

由此得到一条对 §3 打印契约的约束：**开机打印不得把 ACPI 固件表错误渲染成
「内核有问题」**。这类条目在各架构上都会出现（x86 是 DSDT，ARM/RISC-V 是
设备树 overlay 冲突），数量随机型而变，写进判据会让同一棵树的判定随机器
漂移。它们的正确位置是 `note` 级明细，不计入失败判据；判据只看上面三条。

### 5.1.2 跨开机取证：挂起唤醒后 Wi-Fi 失效

上一节的账只覆盖当前开机。把 285H 近十余次开机逐条比，才看到另一类与
「网络问题」直接相关、但在单次开机账里永远不会出现的缺陷：

| 开机 | 起于 | `wiphy_resume` 告警 | 当次开机其它内核算例 |
|---|---|---|---|
| boot -10 | 11-07 17:43:03 | 2 条，18:45:45 | 前半段网络完好：17:45 成功关联（WPA2，2412MHz） |
| boot -9 | 11-07 20:13:59 | 2 条，20:46:14 | oops=0 |
| 其余 13 次开机 | — | 0 条 | oops=0 |

告警原文（boot -10，完整栈）：

```
iwlwifi 0000:01:00.0: Failed to start RT ucode: -110
iwlwifi 0000:01:00.0: mac start retry 2
------------[ cut here ]------------
Hardware became unavailable upon resume. This could be a software issue
prior to suspend or a hardware issue.
WARNING: CPU: 4 PID: 33647 at net/mac80211/util.c:2586
ieee80211_reconfig+0x94/0x1150 [mac80211]
wiphy_resume+0x7e/0x170 [cfg80211] → dpm_run_callback → __device_resume
RIP: 0010:drv_stop+0xbb/0xd0 [mac80211]
```

四点判读，每点都可复验：

1. **这批告警是修复前的基线，不是当前未决缺陷**。两条告警的时间是
   11-07 18:45:45 与 20:46:14；`iwlwifi: pcie: keep 0x272b off D3cold
   across s2idle`（`c55e7fc9590d`）落于同日 20:56，随
   `airymaxos-kernel-0.0.4-6`（构建于 11-08 11:38）装机。修复的做法是
   在 `iwl_pci_suspend` 里对 `8086:272b` 调 `pci_d3cold_disable`，因此
   设备醒着时 `d3cold_allowed` 仍读 1，只有挂起窗口内才是 0——不能用
   醒态读数判断修复在不在。
2. **不是首次开机的缺陷**。两次告警都发生在开机数十分钟后的唤醒时刻，
   首启关联本身是成功的。因此它**不能**用来解释 §4.1.3 的首启无前端，
   两者是并行的两条链。
3. **失败形态是「端点脱落 + 不可恢复」**。`Failed to start RT ucode:
   -110` 是唤醒路径上重放固件启动命令超时（ETIMEDOUT），寄存器随后全
   读成 `0xFFFFFFFF`；`ieee80211_reconfig` 在 `net/mac80211/util.c:2586`
   直接 WARN 并走 `drv_stop`，放弃重配。用户可见后果是「合盖再开，
   Wi-Fi 消失，图标空，必须重启」。
4. **它与架构无关**。mac80211 / cfg80211 是总线无关层；换成 ARM 的
   PCIe 或 SDIO 无线网卡，唤醒路径同一条，只是 `-110` 换成对应的传输
   错误码。判据必须按形态写，不能挂在 x86 型号上。

因此本版对这条**不再做一次修复**，而是把「修复是否成立」变成可复验
判据，并把同样的形态搬到另外两个架构：

| 事项 | 判据 |
|---|---|
| 唤醒循环 | 连续 5 次 s2idle + RTC 唤醒，每次 `dmesg` 无 `ieee80211_reconfig` 告警，且接口在唤醒后 5 秒内可 `iw dev` 读到 |
| 三架构同形 | ARM 与 RISC-V 各在带无线网卡的机器上复跑同一判据；无网卡的机器输出 `wifi=absent`，不得记为 SKIP |
| 记账 | err 账新增「唤醒后无线设备脱落」签名，独立计数，不与其它 `-110` 混算 |
| 自检 | 唤醒后 `wiphy` 健康探针输出 `wifi=ok` 或 `wifi=lost driver=<name>` |
| 恢复 | `wifi=lost` 时按驱动名重绑（remove + rescan）并重新 up；失败落 `FAIL wifi 重绑后仍无接口` |

自检与恢复两层是防御纵深，不替代内核修复：修复覆盖已知的 `272b`，探针
覆盖「下一次换型又出现同一形态」的情况。两者都只消费内核已有接口，不改
mac80211 行为，也不与内核侧任何改动冲突。

### 5.2 W-A1 能力探针（ACPI 与设备树双入口）

0.0.4 的 T29 已是这个形态，但只读 ACPI，且发现层与绑定层合在一个函数里。
本版拆成两层，三架构只换数据源：

| 层 | x86_64 | aarch64 / riscv64 |
|---|---|---|
| 发现层（固件描述有没有这块硬件） | `/sys/bus/acpi/devices/*/path` 的后缀（`TPAD`/`TPD0`/`TPD1`）与 `_HID` | `/sys/firmware/devicetree/base` 下 `status = "okay"` 且 `compatible` 命中触控板族（`elan,*`、`synaptics,*`、`goodix,*`） |
| 绑定层（内核有没有接上） | `/sys/bus/i2c/devices/*/driver`、`/proc/bus/input/devices` | 同左（I2C/SPI-HID 两族路径相同） |

判定：发现层有、绑定层无 → 失败，hint 必须同时给出节点路径与期望驱动名
（「缺哪个 ID / 哪条 `compatible`」直接可读）；发现层无 → 按能力不适用
通过，不记为 SKIP。HW-02 在 x86 上正是「发现层无」（LPSS 不建总线，ACPI
节点都不出现）与「绑定层无」两种表现并存，判据两种都要能说清。

交付物层面的同一教训（2026-11-07 在 285H 上取证）：现装镜像的内核包是
`airymaxos-kernel-{core,modules}-0.0.4-5`，构建时间 2026-11-06 12:38；
补 ID 的提交 c93c57a 落于当日 23:23。源码里的修复与镜像里的包差 11 小时，
现场表现是 `echo 0000:00:15.0 > /sys/bus/pci/drivers/intel-lpss/bind`
返回 `No such device`，而同一条链路的另一端一直健在——ACPI 节点
`\_SB_.PC00.I2C0.TPAD` 状态 15、`i2c_hid_acpi` 已加载、`i2c-designware-platform`
与 `hid-multitouch` 都在模块树里。因此源码层的表项断言挡不住**包龄差**，
只有交付物断言能兜住：发布 ISO 的内核包只允许来自该 tag 的 release run
（`release_tag`），`rpms_run` 仅限首个版本建页前使用，两处的
`%{version}-%{release}` 必须与 tag 的 release 资产名逐字相等。

### 5.2.1 配置层的同一缺口：ARM / RISC-V 的 I2C-HID 传输层整体缺席

W-A1 管的是「驱动在树内、没绑上」，还有一半在配置层：**驱动压根没编进内核**，
同样一行错都不打印。2026-11-07 直接读三份实际参与构建的基线（spec 的
`%global kbase`：x86_64/aarch64 用 `openeuler_defconfig`，riscv64 用
`defconfig`）得到下表。不从 `kernel/configs/euler_hw_*.config` 推：那三份在
树内无任何引用，不参与本发行版构建，拿它当证据会得出与实物不符的结论。

| 符号 | x86_64 | aarch64 | riscv64 |
|---|---|---|---|
| `CONFIG_I2C_HID` | `=m` | `=m` | 无此符号 |
| `CONFIG_I2C_HID_CORE` | `=m` | **缺**（无人 select） | 缺 |
| `CONFIG_I2C_HID_ACPI` | `=m` | **not set** | 缺 |
| `CONFIG_I2C_HID_OF` | not set | **not set** | 缺 |
| `CONFIG_I2C_HID_OF_ELAN` / `_GOODIX` | not set | **not set** | 缺 |
| `CONFIG_I2C_DESIGNWARE_PLATFORM` | `=m` | `=m` | 缺 |
| `CONFIG_MFD_INTEL_LPSS{,_ACPI,_PCI}` | `=y` | — | — |

出处：`kernel/arch/x86/configs/openeuler_defconfig` 4098-4103、4784-4786、
6596-6599；`kernel/arch/arm64/configs/openeuler_defconfig` 3885-3888、
5880-5884；`kernel/arch/riscv/configs/defconfig` 无相关行。

读法：`I2C_HID` 只是菜单开关，核心模块由 `CONFIG_I2C_HID_CORE` 构建
（`drivers/hid/i2c-hid/Makefile`：`obj-$(CONFIG_I2C_HID_CORE) += i2c-hid.o`），
而 CORE 只被四个传输层 select。aarch64 打开菜单、关掉全部传输层，结果是
`i2c-hid.ko` 与四个 transport 一个都不产出；riscv64 连菜单都没开。即 ARM 与
RISC-V 上任何 I2C-HID 触控板都是「硬件在、驱动不在、日志无错」，与 285H 的
HW-02 同一失效形态，只是缺的层不同：x86 缺 ID 表项，这两者缺整层模块。
上游 `arch/arm64/configs/defconfig:979-980` 开着 `I2C_HID_ACPI=m` 与
`I2C_HID_OF=m`，是 openEuler 的 arm64 基线把它们关掉的。

处置（进本版，与抬基线同一批配置变更，不再受 0.0.4 铁律①约束）：

1. 写进各自的 `arch/<kdir>/configs/airy_defconfig`，不改基线 defconfig：
   片段是我们自己的 SSoT，换基线时不丢。aarch64 加 `I2C_HID_ACPI=m`、
   `I2C_HID_OF=m`、`I2C_HID_OF_ELAN=m`、`I2C_HID_OF_GOODIX=m`；riscv64 加
   `I2C_HID=m`、`I2C_HID_OF=m`、`I2C_HID_OF_ELAN=m`、`I2C_HID_OF_GOODIX=m`、
   `I2C_DESIGNWARE_PLATFORM=m`。
2. `ci/gates/release-config.sh` 的 `REQUIRED` 改为按架构取表（现为四架构共用
   一份清单），断言「每个架构至少一条可用传输层且 CORE 被 select」，并断言
   x86 的 LPSS 三件与 `I2C_DESIGNWARE_PLATFORM` 仍在。本轮实测该脚本的
   `REQUIRED` 与 `REQUIRED_AGENT` 都不含这两族符号，缺了不会红。
3. 合并顺序与快照 README 的三步不变：新符号落在架构片段里，
   `common-agent.fragment` 继续不掺架构相关项。
4. 验证：三架构构建后 `modinfo -F filename i2c-hid` 有值，`i2c-hid-acpi` 与
   `i2c-hid-of` 在模块树内；riscv64 另断言 `i2c-designware-platform.ko` 存在。
   无 ARM/RISC-V 实机时，QEMU 加载对应 transport 并断言 `insmod` 成功、
   `/sys/bus/i2c/drivers/hid-over-i2c` 存在——判据层证据，不记作实机验收。

### 5.2.2 第三层：绑定之后还剩的两个判据

W-A1 与 §5.2.1 管到「设备出现、驱动绑上」为止。2026-11-09 在 285H 上取证，
发现链路两端都亮着、用户仍报「触控板不能用」，说明这一层之后还有两处没被
任何判据覆盖。

事实（本次开机，`journalctl --list-boots` 第 0 次，2026-11-08 18:08 起）：

| 层 | 读数 | 出处 |
|---|---|---|
| 内核发现 | `ELAN06FA:00 04F3:3293 Touchpad`，`handlers=event8`，`PROP=5`、`EV=1b` | `/proc/bus/input/devices` |
| 同一 HID 的第二集合 | `ELAN06FA:00 04F3:3293 Mouse`，`handlers=event7`、`mouse1` | 同上 |
| X 绑定 | `Using input driver 'libinput' for 'ELAN06FA:00 04F3:3293 Touchpad'` | `/var/log/Xorg.0.log` |
| libinput 状态 | `Device Enabled=1`、`Tapping Enabled=1`、`Click Method Enabled=1,0` | `xinput list-props` |
| 接触层 | `event8 - kernel bug: Touch jump detected and discarded.`（开机 18290 秒） | Xorg 日志唯一一条 EE |
| 设置层 | `click-method=fingers`、`tap-to-click=false` | `gsettings list-recursively` |

两条判据缺口：

1. **接触层**：`Touch jump` 是 libinput 对坐标突变的整帧丢弃，被丢弃的接触
   序列在释放前不再产生指针事件。设备「在」、驱动「绑着」，用户侧却是「按了
   没反应」。判据不能只看 `Device Enabled`，要看**按下后确有指针事件**：实机
   跑 `libinput debug-events --device /dev/input/eventN`，单指滑动须出
   `POINTER_MOTION`，轻击须出 `POINTER_BUTTON`；只出 `TOUCH_DOWN` 而无指针
   事件即判失败，并把 `Touch jump` 的条数一并附上。
2. **语义层**：`PROP=5` 是 `POINTER|BUTTONPAD`，即该板没有独立物理按键，
   点击必须由「轻击」或「按键区」产生。而设置层读到的 `tap-to-click=false`
   与 X 侧 `Tapping Enabled=1` 互相矛盾——两份事实源各说一套，最终以哪份为
   准取决于谁后写。本版口径：X 侧属性是唯一事实，`gsettings` 只做同步输入；
   判据是两者不一致即失败，不做默认取一。

另有一条待测项，本版只登记不下结论：同一 HID 设备向 X 交了 Mouse 与 Touchpad
两个节点，两者都由 libinput 接管。第二条集合是否参与指针加速，需要在实机上
用「只绑一条」与「两条都绑」两组 `POINTER_MOTION` 采样比对才可判定，不能从
描述符推断。判据形式已定（同一手指同一段位移，两组采样的位移量比值应接近
1）；未测出比值前不引入 udev 忽略规则，避免用补丁掩盖未定事实。

### 5.2.3 传输层健康度：IRQ 增量是最省成本的判据

§5.2.2 的两条判据都要人手指按压才能取到，远程排查因此缺少一个「此刻到底
有没有报文」的客观读数。2026-11-09 在 285H 上补取了一组不依赖按压的证据：

| 观测 | 读数 | 出处 |
|---|---|---|
| GPIO 中断累计 | `181: … 16847 … intel-gpio 182 ELAN06FA:00` | `/proc/interrupts` |
| 10 秒空闲增量 | 0（无人触碰，两次读数同为 16847） | 同一次开机 |
| 传输层告警 | 无 `IRQ triggered but there's no data`、无 `incomplete report` | `dmesg` |
| libinput 能力表 | 134×78mm、tap、clickfinger、`dwt-on`，无范围告警 | `libinput debug-events` |

读法来自源码而不是猜测：`i2c-hid-core.c` 的 quirk 表以 `HID_ANY_ID` 匹配
全部 ELAN 设备，恒命中 `NO_WAKEUP_AFTER_RESET | BOGUS_IRQ`；命中后输入寄存器
回 `0xffff` 只走一条 `dev_warn_once` 就返回，不产生任何输入事件。因此
「中断在响、数据无效」与「中断不来」在日志里是两个可分辨的形态：前者必有
那条告警，后者 IRQ 增量为 0。本次采样两者都不成立，只能说明**采样时刻**
传输层健康，不能说明按压时刻健康。

判据（进本版探针，`airy-probe` 输出 `input.touchpad`）：

1. 取 IRQ 号不写死，按 `/proc/bus/input/devices` 的 `ELAN…/eventN` 反查
   `/sys/class/input/eventN/device` 下的 GPIO 中断，读不到即跳过，不猜。
2. 按压 5 秒内 IRQ 增量 `>0` **且** libinput 出 `POINTER_MOTION` 或
   `POINTER_BUTTON` 才算通过；只有增量或只有事件都判失败——前者正是
   `BOGUS_IRQ` 空转的形态，后者说明中断不来自这块板。
3. 失败输出带三个值：增量、`dmesg` 里两条告警的条数、`Touch jump` 条数，
   现场据此区分「设备不说话」「设备说话但数据无效」「数据有效但被丢弃」。

远程能给出的上限就是基线；按压项必须留给实机，判据与输出格式先固化。

同一轮补取还消掉了两个会误导探针实现的假设：

- **EC 侧开关对内核不可见**：Lenovo 的 `VPC2004:00` 平台设备在 ALK
  6.6.161 的 `ideapad_acpi` 上只有 `camera_power`、`conservation_mode`、
  `fan_mode`、`fn_lock`、`usb_charging` 五个属性，**没有 `touchpad`**。
  因此「Fn+F6 把触控板关在 EC 里」这一形态，内核与 X 都看不出来：设备照样
  枚举、照样绑 libinput、配置层照样是 `touchpad-enabled=true`。探针不能把
  「设备在」当作「能用」，只能以按压时的 IRQ 增量为准（判据 2）。
- **输入节点会在开机后被重建**：同一块板先由 `hid-generic` 建立
  `input7/input9`，约 150ms 后 `hid-multitouch` 接管并重建为
  `input10/input12`。探针若在开机早期缓存 `handlers=eventN`，拿到的就是
  一个已被删除的节点，按压采样恒为 0——这正是「设备明明在、读数却是空」
  的一种假失败。判据 1 的节点反查必须在采样时刻现读。
- **一块板同时存在两个长期节点，且分类不同**：2026-11-09 08:xx 取样
  （uptime 28991s）仍见 `event7` 与 `event8` 并存，`udevadm info` 给出：

  | 节点 | 能力位图 | udev 分类 |
  |---|---|---|
  | `event7`（`input10`） | `EV=17 REL=3 KEY=30000`（左右键） | `ID_INPUT_MOUSE=1` + `ID_INPUT_POINTINGSTICK=1` |
  | `event8`（`input12`） | `EV=1b ABS=… KEY=e520 10000`（含 `BTN_LEFT`） | `ID_INPUT_TOUCHPAD=1`、133×77mm |

  `event7` 是 HID 描述符里遗留的兼容鼠标集合，被 udev/input_id 判成
  **指点杆**。于是「按 `ID_INPUT_TOUCHPAD` 找设备」与「按指点杆找设备」
  会命中不同节点：后者拿到的是一个只有相对轴的兼容节点，再等多久也读不到
  绝对坐标。探针的选择器因此固定为 `ID_INPUT_TOUCHPAD=1` 且带
  `ID_INPUT_WIDTH_MM`；找到指点杆节点时不报错、直接跳过，因为那是同一块板
  的第二个面。点按是否成立以 `event8` 的 `BTN_LEFT` 为准（`event7` 也有
  左右键位，但那是兼容集合，不代表 clickpad 的按键面）。

### 5.3 W-A2 闭包断言按「入口」而非「包名」

`kylin-nm` 的教训是包名与产品名不同源：不带 `ukui` 前缀，桌面元包与依赖
求解都不会带入，于是连「闭包里应该有它」这件事都没人写。判据若写成
「安装了名为 `kylin-nm` 的包」，下一个同类包照样漏。

- 每个桌面能力登记一行：**能力名 → 入口（可执行或 `.so`） → 提供它的包**。
- 入口清单构建期从 RPM 的 `%files` 生成，运行期冒烟与 CI 消费同一份，
  任何一处不得自持一张路径表（与 §4.2 的 SSoT 原则同构）。
- 路径按 `%files` 实测生成，不写死：x86 与 ARM/RISC-V 的库目录同为
  `lib64` 是事实，但「同为」不能靠约定，要靠清单里逐架构的真值。

#### 5.3.1 「首次烧录后连不上」的现场证据（2026-11-10，285H）

B50 与 285H 首烧后都出现网络异常，此前只有现象没有归因。本次在 285H 上按
「先取证再判断」取了三层读数，结论是**驱动与固件不是主因**：

| 读数 | 命令 | 观测 | 含义 |
|---|---|---|---|
| 链路层 | `journalctl -b -u wpa_supplicant` | 04:26 起成串 `CTRL-EVENT-DISCONNECTED ... reason=8`，在 `a2:1e:dd:d0:fb:58` 与 `…:54` 两个 BSSID 间来回 | `reason=8` 是 AP 侧去认证（BSS 迁移），不是本机主动断开 |
| 信号质量 | `iw dev wlp1s0f0 link` | `signal: -16 … -36 dBm`，EHT 160MHz | 信号极强，排除弱信号掉线 |
| 本机动作 | 同上时间段 | 少量 `reason=2`（`locally_generated`），与 kylin-nm 重配时刻重合 | 本机确有主动重连，但量级远小于 AP 侧踢线 |
| 省电 | `iw dev wlp1s0f0 get power_save` | `Power save: on` | 省电与 160MHz 叠加会放大 beacon 丢失窗口 |
| DHCP | `journalctl -b \| grep "Bad format"` | 每次启动 7 条 `parse_option_param: Bad format d` | dhclient 解析服务端选项时丢项，可能少装静态路由却「已连接」 |

由此得到的失效形态不是一条，而是三类，验收与设计必须分开：

1. **链路层被 AP 踢线**（`reason=8`）——本机无缺陷，但用户看到的是「网断了」。
   产品要做的是**快速重关联 + 明确的界面状态**，而不是等 30 秒探测超时。
2. **IP 层未就绪**——关联成功不等于能上网。判据必须落在地址、路由、网关
   可达三件事上，不能以「已连接」图标代替。
3. **DHCP 选项丢失**——`Bad format d` 属上游 dhclient 行为，但要挡住它的后果：
   租约落地后校验默认路由与 DNS 是否存在，缺任一即重试并记账。

对应的设计约束（并入 W-A2 判据）：状态机分「链路已关联 / IP 已就绪 / 外网
可达」三级，界面按级显示；每一级的上限时间单独记账，不以总时长掩盖单级卡死。

### 5.4 W-A3 同一份 TAP 在三架构镜像上执行

判据实现只有一份，执行场所三个：

1. **x86_64 实机**（285H）：全量冒烟，作为形态证据。
2. **aarch64 / riscv64**：同一脚本在交付镜像上执行，`AIRYMAX_SMOKE_ROOT`
   只用于单测沙箱，装机现场必须读真实根——用前缀跑过的绿不算证据。
3. **无实机时的下限**：QEMU + 板卡 DT 构造发现层与绑定层的样例树，
   断言判据在「有硬件无驱动」「无硬件」「全就绪」三态下的输出逐字正确。
   这是判据的单测，不是实机验收，两者在报告里分开记。

### 5.6 GPU：ARL-H 不是表项缺项，是代际缺项

0.0.4 台账 HW-01 记的是「内核基线不认识 285H 的 GPU」，本版必须回答
「补表项能不能解决」。2026-11-06 在 285H 上做过一次实测，结论是不能。

实测步骤与观测：

| 步骤 | 命令 / 产物 | 观测 |
|---|---|---|
| 依据 | 上游 `bddacdf4861c0586`「drm/i915: Add additional ARL PCI IDs」 | 把 0x7D41/0x7D51/0x7D67/0x7DD1 并入 MTL 表项，绑 `&mtl_info` |
| 编译 | 复制 `/usr/src/kernels/6.6.161-alk` 到用户目录，换入改后的 `include/drm/i915_pciids.h`，`make M=drivers/gpu/drm/i915 modules` | `i915.ko` 生成，`modinfo` 的 alias 命中 `pci:v00008086d00007D51`，vermagic 与在装内核一致 |
| 加载 | `modprobe -r i915` 后 `insmod i915.ko force_probe=7d51` | 命令后 20 秒内整机失去响应：ICMP 与 SSH 全不通，无 journal 落盘 |

这次只得到「不可用」这一个结论，**没有**得到挂死点：探测期挂死、显示
控制台接管与 simpledrm 拆除的竞争、Xorg 仍握 `fb0` 三者都会表现成同一
现象，事后无法区分。但这三条恰好指向同一条操作约束：

- **GPU 类驱动不允许在运行中的 framebuffer 会话里热绑验证。** 它要接管
  显示控制台，验证必须在冷启动早期完成，日志出口是串口而不是 SSH。
- **表项与能力是两件事。** ID 只让驱动「认识」设备；ARL-H 在 6.8 起还依赖
  display 版本识别、GT workaround 与 GuC/GSC 固件门槛（上游
  `67733d7a71503fd3`「drm/i915: ARL requires a newer GSC firmware」要求
  GSC 102.0.10.2356 起）。只补 ID 等于让驱动在没有这些前提时去碰硬件。

因此本版对 GPU 的处置是**抬基线**而不是补丁：内核基线升到 6.12 LTS，
ARL 原生在表内（`INTEL_ARL_H_IDS`），验收判据仍是 HW-01 的三条——alias
命中 `8086:7d51`、`/sys/class/drm` 出现具名连接器、GLX 不再是 `llvmpipe`。
0.0.4 保持现状（`simpledrm` + llvmpipe），不做任何 i915 改动。

### 5.7 W-A4 桌面进程崩溃的取证面

285H 的 0.0.4 镜像在 `6.6.161-alk` 上跑了 1 小时 50 分：`tainted=0`、
无 MCE、无 soft lockup、无 OOM，`systemctl --failed` 为 0——按现有判据
一切正常。但 `coredumpctl` 里有三条记录：

| 时刻（2026-11-06/07） | 进程 | 信号 |
|---|---|---|
| 11-06 22:15 | `peony` | SIGSEGV |
| 11-06 22:52 | `ibus-ui-gtk3` | SIGSEGV |
| 11-07 07:05 | `ibus-ui-gtk3` | SIGSEGV |

三者都在图形会话里，都不产生 failed 单元，因此**没有一个判据会看到它们**。
这与 D-08、HW-02 是同一失效形态：证据在盘上，判据不读。三架构共用同一批
UKUI 二进制与同一套会话脚本，崩溃形态不随架构变化。

判据设计（进本版，实现挂在 `airy-observe system` 的第四面）：

1. **来源**：`coredumpctl -b --no-pager --json=short`，读的是
   systemd-coredump 自己的索引，不扫目录、不解析 `.zst`。命令不可用或索引
   读不出，该面判 `unknown`——与 units/logs/packs 同一口径，`unknown` 绝不
   等于通过。
2. **时间界**：只认本次 boot（`-b`）。跨启动的旧记录不计入，否则一次崩溃
   会让之后每次开机都红，信号随即失效。
3. **归属分层**：`exe` 属于 `airymax-*`/`airy-*` 的自有崩溃恒为 0；图形
   会话进程（`UID=1000` 或 `_SYSTEMD_USER_UNIT` 落在 `session-*.scope`）
   按预算，预算与 T23 共用同一份版本化文件，按 `(exe, signal)` 去重后比较，
   同一崩溃反复出现只算一条。初值取 0.0.4 实测基线（两条），随后随版本
   单调降至 0。内核态崩溃（`exe` 为空或 `kernel`）单列，不计入本族。
4. **明细必须可归因**：每条至少给出 `exe`、`signal`、时刻、`PID`、`UID`，
   缺任一项即整面判 `unknown`。报告行形如
   `cores=2 ok=false` 加两行明细，`airy-observe system` 的 `state` 随之
   由 `ok` 变 `failed`。
5. **不得被单元面豁免**：`systemctl --failed` 为 0 不是豁免条件。D-37 的
   全部三条记录都发生在单元面为绿的时刻，这正是旧判据漏掉它们的直接原因。

验证：

| 层 | 用例 | 判据 |
|---|---|---|
| 单测 | 造三份 `coredumpctl --json` 样例（自有/会话/内核态） | 三态输出与预算比较逐字正确；缺字段判 `unknown` |
| 单测 | 跨 boot 记录 | 上一 boot 的崩溃不计入，本次 boot 计数不变 |
| 单测 | 去重 | 同一 `(exe, signal)` 三次崩溃只计一条，明细仍列三条 |
| CI | 三架构镜像 | 崩溃面在无 GUI 的镜像上输出 `cores=0` 且为 `ok`，不因无记录判 `unknown` |
| 285H | 冷启动后打开文件管理器与输入法 | 崩溃面与 `coredumpctl list` 条数一致；预算内为 `ok` 且明细可见，超预算即 `failed` |

### 5.8 N-05 关于页「桌面」行的来源与改法

0.0.4 交付的关于页（UKUI 控制面板 → 关于）有两行受限：

| 行 | 现状 | 判据 |
|---|---|---|
| 版本名称 | `/etc/os-release` 的 `VERSION="OpenAirymax 0.0.4"`，已符合要求 | 已随 0.0.4 落 |
| 桌面 | 只显示 `UKUI`，没有版本号 | N-05 |
| 用户 | 空行，`User:` 后没有任何内容 | N-06（2026-11-09 新增） |

**2026-11-09 实机复核（0.0.4-6，285H，`ffmpeg -f x11grab` 截取整屏）**：
关于页七行读数逐字为 `Version: OpenAirymax 0.0.4`、`Hostname: airymax-pc`、
`Kernel: Linux 6.6.161-alk`、`CPU: Intel(R) Core(TM) Ultra 9 285H`、
`Memory: 31GiB (24.9GiB available)`、`Desktop: UKUI`、`User:`（空）。
版本名称一项已达标；桌面一项与上一行判据一致；`User` 空行是本轮新发现的
缺陷，与「其他不动」不冲突——空值不是格式选择，是缺数据。

`User` 行的来源已取证，不是猜测。`libabout.so` 的字符串表里有
`org.freedesktop.Accounts`、`org.freedesktop.Accounts.User`、
`/org/freedesktop/Accounts/User1000` 与 `RealName`，且没有调用
`getpwuid` / `g_get_user_name` 的未定义符号——它读的是 AccountsService
的 `RealName` 属性，不是本机 passwd 库。实机读数为
`RealName = ""`（`busctl call ... Properties.Get ss ... RealName` 返回
`v s ""`），而 `getent passwd amuser` 的 GECOS 字段同样为空：
`amuser:x:1000:1001::/home/amuser:/bin/bash`。

根因在安装器建用户时没写 GECOS，AccountsService 便没有可回填的
`RealName`。修复点因此是 kickstart 的 `user --gecos`，不是控制面板；
判据写成两条：装机后 `getent passwd` 的 GECOS 非空，且关于页 `User`
行与 `RealName` 逐字一致。

2026-11-09 在 285H 上对 `libabout.so`
（`ukui-control-center-3.1.2-33.oe2403sp3`）反汇编取证，来源已经确定，
不是猜测。`About::setupDesktopComponent()`（`objdump -d`，0x24e90–0x25220）
是三分支：

1. 在 `QProcess::systemEnvironment()` 里找第一项以 `XDG_CURRENT_DESKTOP`
   开头的字符串；找不到，或按 `=` 切出的值为空 → `setText("UKUI")`。
2. 值里 `indexOf("UKUI") != -1` → **仍然** `setText("UKUI")`（字面量，
   版本被丢弃）。这正是「桌面只显示 UKUI」的根因。
3. 值里没有 `UKUI` 子串 → `setText(value)` 原样显示。

它不读任何版本文件；`ukui-session` 把该变量写成 `UKUI`，因此无条件落到
分支 2。

2026-11-07 的旧记载写成「含 `UKUI` 时把值原样写进标签」，与本次反汇编
不符，以本节为准。这个差别决定改法：把会话变量改成 `UKUI 4.0` 仍会命中
子串、仍走分支 2，版本照样被丢弃——只改环境变量无效。

因此 0.0.4 没有任何注入点：改配置、加 drop-in、写 `/etc/apt/ota_version`
都到不了这一行，而 0.0.4 交付的桌面栈实际是 3.x（`ukui-panel 3.1.0`、
`ukui-control-center 3.1.2`、`peony 3.10.0`），把 4.x 写死既无来源也不真实。
该项与 UKUI 4.24 自建闭包绑定，本版处理：

1. **上游补丁（必需）**：`ukui-patches/` 收一份 `ukui-control-center` 的
   源码补丁，把分支 2 的 `setText(字面量)` 改为 `setText(value)`，保留分支 1
   的字面量兜底。补丁按闭包 EVR 钉住，构建时断言该分支不再引用 4 字节
   字面量。只改会话变量而不打补丁无效，理由即分支 2。
2. **版本唯一来源**：闭包构建时把 `ukui-session-manager`（`/usr/bin/ukui-session`
   的属主包）的 RPM `Version` 写成生成头里的 `AIRY_UKUI_VER`，会话以
   `UKUI <major>.<minor>` 写入 `XDG_CURRENT_DESKTOP`。3.1 栈显示
   `UKUI 3.1`，4.24 栈显示 `UKUI 4.24`，不需要第二处改动。
3. **变更前的兼容审计**：闭包内所有读该变量的组件必须先确认用
   `startsWith`/`contains` 判定，而不是等值比较。审计入口是一条闭包内
   `XDG_CURRENT_DESKTOP` 的检索；出现与字面量 `UKUI` 的等值比较即先改
   消费侧，再改会话侧。`desktop_ready.sh` 与冒烟断言同步改为前缀匹配。
4. **验证**：镜像内 `rpm -q --qf '%{VERSION}' ukui-session-manager` 的主次
   版本号与关于页「桌面」行逐字一致；三架构同一判据。0.0.4 不动这一行，
   只把版本来源与补丁点登记在此，避免下一次再靠猜。

### 5.9 平台主题插件对无 QApplication 进程的崩溃

0.0.4-9 在发行侧止住了症状，缺陷本体留在上游组件，本节登记 0.0.5 的
收口口径。

已取证的链路（285H，0.0.4-7）：

- `ukui-session` 启动会话时把 `QT_QPA_PLATFORMTHEME=ukui` 写进环境，该
  变量经 systemd 用户管理器被全部用户单元继承；
- `plasma-kglobalaccel` 只有 `QCoreApplication`，仍按变量加载
  `libqt5-ukui-platformtheme.so`；插件的 QGSettings 字体回调对该进程调用
  `QApplication::setFont`，解引用空实例，每个启动周期 SIGSEGV 一次；
- core 栈三层固定：`libQt5Core`（`QGSettings::changed`）→ 插件 →
  `libQt5Widgets`（`QApplication::setFont`）。

0.0.4-9 的边界：用户单元 drop-in 对 `plasma-kglobalaccel.service` 做
`UnsetEnvironment`，变量不进进程即不加载插件。这不修插件，任何其他
非 GUI Qt 进程继承该变量仍会复现，故 0.0.5 必须处理本体。

| 项 | 判据 |
|---|---|
| 上游路径 | 先向 openKylin 报 issue，附本节 core 栈与最小复现（无 QApplication 的 Qt 进程 + 字体变更）；对齐修复版本号后决定是否仍需补丁 |
| 补丁条件 | 若上游不可及，按 `distro/ukui-patches/README.md` 三条落地：补丁钉 `qt5-ukui-platformtheme` 具体 EVR，随目录进构建，PR 附上游链接；修改触发 GPLv3 开源义务 |
| 接受口径 | 冷启动三轮后 `coredumpctl list` 无 `kglobalaccel5`；运行中切换字体（`gsettings set org.mate.interface font-name`）不产生新 core；drop-in 移除后仍成立 |
| 三架构 | 补丁随源码在四架构构建；aarch64/riscv64 若无该包则跳过构建，不以空补丁充数 |
| 回归 | 保留 0.0.4-9 的 drop-in 到补丁验证通过之后，避免修复窗口期重新引入崩溃 |

### 5.10 N-06 托盘图标：闭包修好之后仍有一层解析链

§5.1 把「右下角网络图标整块消失」记为 D-08（`kylin-nm` 不在闭包内）。
0.0.4-7 的 285H 取证表明**闭包已经修好、图标仍然不显示**，即同一现象后
还压着第二层缺陷。两层必须分开判定，否则第一层转绿会把第二层继续掩盖。

2026-11-08 取证（285H，`0.0.4-7`），逐条可直接复算：

| 事实 | 取证命令 | 结果 |
|---|---|---|
| 托盘程序在跑 | `ps -ef \| grep kylin-nm` | 在跑，PID 稳定 |
| 托盘条目已注册 | `gdbus` 读 `org.kde.StatusNotifierWatcher.RegisteredStatusNotifierItems` | 8 条，`kylin-nm` 在 `showApp` 白名单内 |

| 另一个主题键 | `gsettings get org.ukui.style icon-theme-name` | `ukui`（正常，但不被面板采用） |

这条链在 **GTK 一侧**成立：主题名 `menta` → 目录不存在 → 回退 `hicolor`
→ `hicolor` 没有 `network-wireless-*-symbolic` → 空白图标。但托盘是 Qt
（`ukui-panel`），Qt 走平台主题而非 `org.mate.interface`，所以它**不能**

| 验证 | 方法 | 结果 |
|---|---|---|
| 面板的 Qt 主题来源 | 读 `/proc/<ukui-panel>/environ` | `QT_QPA_PLATFORMTHEME=ukui` |
| Qt 实际主题名 | `QIcon.themeName()` | `ukui` |
| 托盘请求名能否解析 | 16 个候选名逐个 `QIcon.fromTheme()` | **16/16 命中**，含 `network-wireless-connected/offline/disconnected`、`nm-signal-00/100` |

即：主题目录存在、索引完整、请求名可解析，当前会话截图也显示 Wi-Fi 信号
图标正常渲染。所以 `org.mate.interface=menta` 是一个**独立的 GTK 侧缺陷**
（影响 GTK 程序的图标回退），钉死它仍要做，但它不是「网络图标没了」的
根因；该现象在 0.0.4-7 的本次开机中**未复现**。

0.0.4 的处置（release 8/9 已落，待新镜像复验）：

1. `99-airymaxos-default.gschema.override` 把 `org.mate.interface icon-theme`
   钉成 `ukui`，并在包 `%post` 里 `glib-compile-schemas`，使默认值生效；
2. `ukui-icon-theme-default` 建符号链接指向 `ukui`，覆盖锁屏二进制里写死的
   主题名；
3. 复验判据：登录后 `gsettings get org.mate.interface icon-theme` 为 `ukui`，
   且 `/usr/share/icons/ukui/16x16/status/nm-signal-*.png` 存在。

本版要补的是**判据本身的缺口**。现行 T25 只读 `org.ukui.style
icon-theme-name`：该键对 Qt 托盘是正确的取值面，取值也是 `ukui`，但「值为
`ukui`」不等于「图标能画出来」——它没有回答目录是否存在、请求名能否解析，
所以闭包缺主题包时仍判绿。改为三问同判，任一不成立即失败：

| 判据 | 读取面 | 失败含义 |
|---|---|---|
| 面板与 GTK 两侧的主题键已钉死 | `org.ukui.style icon-theme-name` 与 `org.mate.interface icon-theme` 均为 `ukui` | 任一侧被上游或用户值改回，Qt 与 GTK 显示两套图标 |
| 该主题目录存在 | `/usr/share/icons/ukui/index.theme` | 闭包缺主题包（`menta` 那次正是这一条） |
| 至少一个托盘请求名可解析 | 在面板环境下用 Qt 解析 `nm-signal-*` / `network-wireless-*` | 图标资源缺项 |

第三问必须**在面板的同一环境里**判定（`QT_QPA_PLATFORMTHEME=ukui`），不能
用 `ls` 代替：文件在、索引没编、或名字对不上，`ls` 全绿而托盘仍是空白。

三架构同判据：图标主题与托盘程序的包闭包与架构无关，唯一差异是
`16x16` 与 `22x22` 尺寸目录的取舍，判据按「任一只寸命中即通过」。

同轮还抓到一个**已复现的可见缺陷**，与上面的空白是两件事：

| 事实 | 值 |
|---|---|
| 资源 | `/usr/share/icons/ukui/scalable/status/battery-level-90-charging-symbolic.svg` |
| 实际内容 | 彩色：底板 `.st0{fill:#262626}`、电池体 `.st1{fill:#2AAA00}` |
| 症状 | 单色符号位里渲染成「深色圆角底板 + 绿色电池」，与相邻的音量、蓝牙、Wi-Fi 单色图标风格不一致 |

修法不是改上游主题包（会在升级时被覆盖），而是本版交付一层**覆盖主题**：
`index.theme` 里 `Inherits=ukui`，只放被替换的电池组 SVG，其余全部继承。
这样上游升级后新图标自动生效，只有明确要改的那几张是本仓事实。

### 5.11 W-A5 桌面能力按架构分派（浏览器为第一个实例）

用户口径「现在的桌面找不到浏览器了」在 0.0.4 已按「`firefox` 进 comps 默认组」
处理（`distro/comps/airymaxos-comps.xml:261`）。该处置在 x86_64 成立，但把
同一份 comps 交给另外两个架构时不成立——**这一层与 0.0.4 的实机缺陷同一形态：
功能缺席而日志无错**。

2026-11-08 直抓基底各段 primary 元数据逐包解析 NVRA（openEuler 24.03 LTS SP3）：

| 仓库段 | 包数 | `firefox` | `epiphany` |
|---|---|---|---|
| `everything/x86_64` | 18,986 | **0:140.6.0-1.oe2403sp3** | — |
| `everything/aarch64` | 18,892 | **0:140.6.0-1.oe2403sp3** | — |
| `everything/riscv64` | 18,502 | **缺** | — |
| `EPOL/main/x86_64` | 4,344 | — | 1:43.0-5.oe2403sp3 |
| `EPOL/main/aarch64` | 4,369 | — | 1:43.0-5.oe2403sp3 |
| `EPOL/main/riscv64/rva23/riscv64` | 4,067 | — | 1:43.0-5.oe2403sp3 |

两个结论都是实测，不是推断：`firefox` 在 riscv64 全缺（everything 与 EPOL 两段
都没有），而 `epiphany` 三架构齐备且版本一致。因此「comps 里写一行 `firefox`」
只能满足两个架构。

失效形态之所以隐蔽：`packagereq` 的类型是 `default`，dnf 对 default/optional
组的缺包只跳过，mandatory 才报错。于是 riscv64 镜像**装得成功、开机成功、
`systemctl --failed` 为 0**，只是桌面没有浏览器——与 D-08（`kylin-nm`）、
HW-02（LPSS 表项）完全同构：判据都不在链路末端。

处置口径与 §5.3 同一条原则：**判据写在能力上，包名只是每架构的一个实例**。

1. **SSoT 只有一份能力表**：`distro/caps/desktop-caps.yaml`，形如
   `browser: {x86_64: [firefox], aarch64: [firefox], riscv64: [epiphany]}`。
   每项还带**入口**（`/usr/bin/firefox`、`/usr/bin/epiphany`）与桌面文件
   （`/usr/share/applications/*.desktop`），与 §5.3 的入口清单同一结构。
2. **comps 由生成器产出，不手写三份**：`distro/caps/gen-comps.py` 读能力表
   与既有 comps 骨架，按架构生成 `airymaxos-comps-<arch>.xml`；生成物进
   `distro/lockfile/` 一并冻结。禁止把「三份 comps 互相对齐」当维护手段——
   三份手写必然漂移，症状是某个架构少一行而无人发现（`kylin-nm` 的成因）。
3. **构建期门禁** `ci/gates/desktop-caps.sh`：对每个架构断言每个能力的
   provider 至少一个可解析（`dnf -q repoquery --arch=<a> <pkg>` 非空），
   且入口路径在**该架构的包文件清单**里存在。缺一条即判红，不看组类型
   是否 `default`——这次正是 `default` 的宽容让缺陷穿过了构建。
4. **运行期判据** T25/T30 增加一问：从面板与开始菜单的**同一入口**
   （`.desktop` 文件的 `Exec`）解析，必须落在存在的可执行上；包名不作为
   判据，否则 RISC-V 上「装的是 epiphany、判的是 firefox」永远判负。
5. **三架构验证**：x86_64/aarch64 断言 `firefox` 入口存在，riscv64 断言
   `epiphany` 入口存在；三者都断言「从桌面入口点开至少一个窗口」在 QEMU
   判据层可复现，实机项按 §5.4 分开记。
6. **可见性判据**（2026-11-09 实机复核后改写）：每个架构还要断言「不搜索
   也能看到」——浏览器必须出现在面板 `[taskbar]` 的钉住项里（
   `apps\N\desktop` 指向的 `.desktop` 存在且其 `Exec` 可解析），桌面图标
   目录 `$(xdg-user-dir DESKTOP)` 只作补充判据。`ukui-panel` 3.1 没有
   `quicklaunch` 插件，钉住项的唯一落点就是 `apps\N\desktop`；并且桌面路径
   在中文会话里被本地化为 `~/桌面`，判据写死 `~/Desktop` 会恒判负。落点由
   镜像内的 `/etc/skel/.config/ukui/panel.conf` 预置，出厂即空的面板等于
   把装配工作转嫁给用户。

**2026-11-09 在 285H 上复核，这一层比「装没装」更深一层**：`firefox` 确实
装了（`/usr/bin/firefox`，`firefox-153.6.0`），`firefox.desktop` 也有效
（`Categories=Network;WebBrowser`、`Exec=firefox %u`、图标在 `ukui` 主题内），
`UkuiMenu.db` 里甚至有它的启动记录（`times=1`）。但用户仍然「找不到」：
面板 `panel.conf` 的 `[taskbar]` 组里只有一条空的 `apps\size=0`，而该版本
没有 `quicklaunch` 插件，起始栏读的就是这两组；`~/Desktop` 为空——桌面目录
已被本地化成 `~/桌面`，判据写死 `~/Desktop` 在中文会话里恒为空。于是**从
开屏到点开菜单之间没有任何一处入口**。x86_64 上缺的不是包，是**落点**；
只断言 `Exec` 能解析，仍然会判绿。

0.0.4 的处置已落地：`distro/desktop/skel/airymax-panel.conf` 随
`airymaxos-release` 装到 `/etc/skel/.config/ukui/panel.conf`，`[taskbar]`
钉住 `peony.desktop` 与 `firefox.desktop`（`apps\size=2`），
`[statusnotifier] showApp` 显式保留 `kylin-nm`。实机验证方式：替换配置后
`pkill -9 ukui-panel` 再 `setsid ukui-panel`，截屏可见面板左端出现两个钉住
项。跨架构这步仍归本节：riscv64 的钉住项要指向 `epiphany.desktop`，由第 1
条的能力表派生，模板里不写死 `firefox`。

### 5.12 W-A6 deb 包入口：双击安装（能力已有，分派层缺席）

用户口径「deb 包的安装也很不方便」。先纠正一处措辞：0.0.4 交付的
`airy-deb` 只有 `info` / `install` / `convert` 三个子命令，`install` 接受
`--ignore-scripts` 与 `--dry-run`，**没有** `--ask`；本节的 `--ask` 是本版
新增，不是对既有开关的描述。

事实（2026-11-08 取证）：

| 事实 | 证据 |
|---|---|
| 解包与转换能力齐备 | `system/services/airydeb/`（`archive`/`control`/`plan`/`spec`/`cli`），`distro/specs/airymaxos-system.spec:544` 打包 `%{_bindir}/airy-deb` |
| 桌面分派层没有承接者 | 全树无 `application/vnd.debian.binary-package` 定义、无 `.desktop` 的 `MimeType=`、无默认关联（`grep -rn 'debian.binary-package' distro system` 为空） |
| 实机落点 | 285H 双击 `.deb` 与 `.rpm` 均落 engrampa |
| 默认关联是两条死引用 | `/usr/share/applications/mimeapps.list`（属 `shared-mime-info-2.4-2.oe2403sp3`）写有 `application/vnd.debian.binary-package=org.gnome.FileRoller.desktop` 与 `application/x-rpm=gpk-install-local-file.desktop`，而这两个 id 在镜像内**都不存在**（`ls` 均 No such file） |
| 唯一声明者因此获胜 | `engrampa.desktop` 的 `MimeType=` 同时含 `application/vnd.debian.binary-package` 与 `application/x-rpm`，`gio mime` 对两者都只列出它，并把它标为 Recommended |

根因不是能力缺失，而是**桌面按 MIME 选处理程序，而这两种类型没有可用的
默认处理程序**：基底给的默认项指向不存在的 desktop id，注册表里唯一声明
了这两种类型的又是归档器，于是 deb 与 `.rpm` 同因、同落 engrampa。
engrampa 的行为本身是对的。这与 §5.3 的形态同一类：判据在能力上，实例在
包与桌面上。

这条机制决定了两件事，写设计时不能漏：

- **补一条默认项不等于修好**。若只写 `[Default Applications]` 而不复核
  `xdg-mime query default` 的实际返回值，死引用仍在注册表里，新的默认项
  一旦写错 id，症状与现在一模一样。判据必须是查询结果等于本项目的 id。
- **`.rpm` 不能只写在风险行里**。它与 `.deb` 是同一台机器上同一次取证
  出来的同一形态，只修一半等于把另一半留给用户。
- 285H 上 `/usr/bin/airy-deb` **不存在**（`rpm -qf` 无输出）：该机装的是
  `airymaxos-system-0.0.4-47`，早于本能力入包。0.0.4 tag 的 spec 已收录
  （`%files` 第 544 行、`%check` 第 302 行断言可执行），因此判据不能只看
  仓库，必须在新镜像的验收里跑一次 `test -x /usr/bin/airy-deb`。

为什么不能只「注册一个 `.desktop` 直接调 `airy-deb install`」：

1. `install` 要写 `/` 与 dnf 数据库，需要 root；桌面进程不是 root。
2. 无终端时 stdout/stderr 全部落空，失败只剩 journal 一行，用户看不到
   缺哪个依赖，与 §3 契约（失败必带判据且可判读）冲突。
3. 不确认就改系统，违反最小惊讶；`--dry-run` 只是打印，不构成确认。

设计（五处，全部 noarch，架构只影响 `rpmbuild`/`dnf` 是否在场）：

| 落点 | 内容 | 判据 |
|---|---|---|
| `/usr/share/mime/packages/airymaxos-deb.xml` | `application/vnd.debian.binary-package`，glob `*.deb`，并登记别名 `application/x-deb`（基底旧数据仍用别名）。`application/x-rpm` 基底已注册，不重复声明 | `xdg-mime query filetype x.deb` 输出前者；`.rpm` 仍为 `application/x-rpm` |
| `/usr/share/applications/airy-pkg-install.desktop` | `Terminal=true`，`MimeType=application/vnd.debian.binary-package;application/x-deb;application/x-rpm;`，`Exec=/usr/bin/airy-pkg install --ask %f` | `desktop-file-validate` 通过且三种类型都在 |
| `/usr/bin/airy-pkg` | 一个前台程序，按后缀分派：`.deb` 走 `airy-deb convert` 再 `dnf install`，`.rpm` 直接 `dnf install`。回显、确认、`pkexec` 提权三件事只有一份实现 | 单测两后缀各一例 |
| `/etc/xdg/mimeapps.list` | `[Default Applications]` 三行指向 `airy-pkg-install.desktop`。落 `/etc/xdg` 而不是 `/usr/share/applications/mimeapps.list`：后者属 `shared-mime-info` 包，改写它既与包所有权冲突、也会在升级时被覆盖；而 XDG 的查找顺序里 `XDG_CONFIG_DIRS`（`/etc/xdg`）先于 `XDG_DATA_DIRS/applications`，原生就能压过那两条死引用 | `xdg-mime query default` 对三种类型逐条等于 `airy-pkg-install.desktop` |
| `airy-deb install --ask` | 确认语义（见下），`airy-pkg` 复用同一实现 | 单测五情形 |

`--ask` 的契约：

- **先回显后执行**：包名/版本/架构、转换出的 RPM 路径、将执行的完整
  `dnf install` 命令行、目标 rootfs、将被执行或被 `--ignore-scripts`
  跳过的控制脚本清单。
- **只认显式肯定**：读一行，`y` / `yes`（大小写不敏感）才继续；其余
  一律视为取消。
- **无终端即拒绝**：`stdin` 不是 tty 时直接拒绝，**不**默认继续。桌面
  分派误把无终端上下文传进来时，宁可失败也不静默改系统。
- **提权只有一条路**：`euid != 0` 时以 `pkexec` 重入自身，不另立一个
  提权入口，避免「桌面调一套、终端调另一套」的漂移。
- **不新增退出码**：取消与非交互拒绝都返回既有 `EXIT_POLICY=5`，环境
  缺 `rpmbuild`/`dnf` 仍是 `EXIT_ENV=4`，参数冲突（`--ask` 与
  `--dry-run` 同给）仍是 `EXIT_USAGE=2`。码表只有 `err.py` 一处。
- **失败带判据**：依赖不满足时打印缺失包名与来源仓库，不退化成一句
  `dpkg: error`；提权被拒时打印 `pkexec` 的实际返回码。

验证：

| 层 | 用例 | 判据 |
|---|---|---|
| 静态 | `ci/gates/deb-entry.sh` | mime XML 可解析、`desktop-file-validate` 通过、`mimeapps.list` 有两条默认项、`airy-deb --help` 含三子命令 |
| 单测 | 伪终端喂 `y` / `n` / EOF；无 tty 直跑；`--ask --dry-run` | 分别为 0 / 5 / 5 / 5 / 2 |
| 单测 | `euid != 0` 时构造 `pkexec` 缺席 | 打印判据并返回 4，不尝试直写 `/` |
| 容器 | 造一个最小 deb（`dpkg-deb` 或等价），`install --dry-run` | 打印出 `dnf install <rpm>` 且不落盘 |
| QEMU 三架构 | `xdg-mime` 查询与 `gtk-launch` 注册 | x86_64/aarch64/riscv64 一致；三架构都断言 `rpmbuild` 与 `dnf` 在场，缺则门禁判红 |
| 285H | 双击样本 deb 与样本 rpm | 终端弹出、回显命令；`n` 取消无副作用，`y` 安装后 `rpm -q` 可查；两种后缀走同一条 `airy-pkg` 路径 |

风险：

| 风险 | 应对 |
|---|---|
| 会话里没有 polkit agent，`pkexec` 起不来 | 打印 `pkexec` 返回码与「请用 `sudo airy-deb install`」的可行动提示，不静默失败 |
| 全局默认关联被用户级 `~/.config/mimeapps.list` 覆盖 | 这是 XDG 的正常优先级，不是缺陷；只为新用户建立落点，不改已登录用户的既有选择 |
| 转出的 RPM 带 `%post`，`--ignore-scripts` 的语义被误用 | `--ask` 回显里单列「将被跳过的脚本」，跳过的每一条都写进 journal |
| `.rpm` 同样落 engrampa | 已确认同因（2026-11-09 取证，见本节事实表），不作为风险挂账，直接并入三类型设计 |

### 5.13 W-A7 验收夹具的退场：通过即退，失败保活

285H 是**用验收 ISO 装出来的机器**，这件事在 2026-11-09 的取证里第一次以
缺陷形态暴露：

| 观测 | 读数 | 出处 |
|---|---|---|
| 装机后单元仍在 | `airymax-smoke-report.service`、`airymax-alive.timer` 均 `enabled` + `active` | `systemctl is-enabled/is-active` |
| 每次开机重跑全套探针 | TAP 计划 26 项、`pass=25 fail=1`，`date=2026-11-08T10:08:33Z` | `/var/log/airymax/smoke.tap` |
| 唯一失败项 | `T23` 报 `units=1 failed`，失败单元正是 `airymax-smoke-report.service` 自己 | 同上 |
| 失败来源 | 装机镜像里的 `airymax_observe/sys.py` **没有** `exclude` 实现，`--exclude` 是死参数 | `grep -c exclude` = 0 |

T23 的自指不是设计缺陷的终点，而是它的最响亮形态：**验收夹具把自己算进了
「系统必须没有失败单元」这条判据里**。仓库侧的 `--exclude` 实现与
`run-smoke.sh` 的传参已经落地，新镜像不会再自指；但生命周期缺口仍在——一台
已经交付的机器，此后每次开机都要跑一遍全套探针，跑完还要往串口与 journal
写一份与本次开机无关的结论。这是把 CI 的观测面永久留在了产品机上。

本版的设计判据只有一条：**夹具必须自己退场，且只在通过时退场**。

1. 报告脚本判定 `AIRYMAX-SMOKE-PASS` 之后写
   `/var/lib/airymax/acceptance.done`，并对
   `airymax-smoke-report.service` 与 `airymax-alive.timer` 执行
   `systemctl disable --now`。只是 `disable`，不 `mask`：现场仍可
   `systemctl start` 手动复验，退场不等于销毁证据。
2. 判负时**不写**标记、不 disable，下一开机继续取证。失败现场只出现一次
   就消失，比不跑更糟——这正是本项目反复吃过的亏。
3. 两单元的 `ExecStart` 先查标记，存在即 `exit 0`（`ConditionPathExists=`
   只做单元级短路，脚本被手工调用时仍要能自判）。
4. `acceptance.done` 不进 `/etc`：它是运行期事实，重装即清空；用 `/var/lib`
   是为了跨 `/tmp` 清理与只读根分区策略保持不变。

验证：

| 层 | 用例 | 判据 |
|---|---|---|
| 单测 | 伪造 PASS 的 TAP | 写标记、两条 `systemctl disable` 被调用、退出码 0 |
| 单测 | 伪造 FAIL 的 TAP | 不写标记、不 disable、退出码 1 |
| 单测 | 标记存在时直接调用脚本 | 立即 0，不产生任何探针进程 |
| 285H | 验收 ISO 装机后连续两次开机 | 第一次 PASS 并退场；第二次 `systemctl --failed` 为空、串口无 TAP 转发 |

交付流程另外钉一条硬规则：**交付机一律用产品 ISO 重装，不得直接交付验收
ISO 装出来的系统**。夹具退场只是兜底，不是让验收介质变成产品介质的许可。

### 5.14 W-S1 四架构模块签名基线统一

这个缺口不是实机现象带出来的，而是 0.0.4 收尾核对 taint 时顺着位标志问下去
发现的：**同一次发行构建，四个架构的内核安全属性并不一致**。0.0.4 §16.4.17
已记录基线，本节给设计。

| 架构 | 基线 defconfig | `MODULE_SIG` | `MODULE_SIG_ALL` |
|---|---|---|---|
| x86_64 | `arch/x86/configs/openeuler_defconfig` | `y` | `y` |
| arm64 | `arch/arm64/configs/openeuler_defconfig` | `y` | `y` |
| riscv64 | `arch/riscv/configs/defconfig` | `n` | `n` |
| loongarch64 | `arch/loongarch/configs/loongson3_defconfig` | `n` | `n` |

`config MODULE_SIG` 在 `kernel/module/Kconfig` 没有 `default`，缺行即 `n`；
`distro/specs/kernel/airymaxos-kernel.spec` 只在 `CONFIG_MODULE_SIG_ALL=y` 时
校验签名、缺省不报错，`distro/scripts/build-kernel.sh` 也不改写任何
`CONFIG_MODULE_*`。于是 riscv64 / loongarch64 的内核里，
`kernel/module/main.c` 中设置 `E` 位的整段代码不编译——**签名校验不是「关了」，
是「不存在」**。这与 `docs-linux/10-architecture/08-threat-model.md` 第 5 条
「内核模块签名 `CONFIG_MODULE_SIG=y`」直接冲突，也让 KM-01 的
「`.module_sig` 全量」在两架构落入「未验证」而不是「通过」。

设计取舍：不在 `distro/kickstart` 或安装期补任何 sed 改写，那是把配置事实
藏进安装脚本，违背 SSoT。配置只从一处生长——**基底 defconfig 与
`kernel/configs/` 片段**。两条路径二选一，按「改动面最小且可复算」定：

1. 若上游 riscv64 / loongarch64 defconfig 在 0.0.5 基线上已带 `MODULE_SIG`，
   只补 `MODULE_SIG_ALL=y` 到架构片段，改动 1 行；
2. 若仍不带，在架构片段里成对写入 `CONFIG_MODULE_SIG=y` 与
   `CONFIG_MODULE_SIG_ALL=y`，并同时断言 `CONFIG_MODULE_SIG_FORCE` 保持
   `n`——过渡期允许未签名模块加载但必须留 `E` 痕，便于第三方驱动排障；
   `FORCE` 的启用留给后续版本单独决策，不在本版顺手打开。

成本必须诚实记账：`MODULE_SIG=y` 会把 PKCS#7、X.509 与 RSA 解析编进内核，
riscv64 / loongarch64 镜像体积与构建时间都会增加，需要在内核包体积预算里
预留，不能以「其他架构都有」为由不加核算。

验证三层，缺一不算完成：

| 层 | 用例 | 判据 |
|---|---|---|
| 配置 | 四架构构建后读 `.config` | `grep -x 'CONFIG_MODULE_SIG=y'` 与 `grep -x 'CONFIG_MODULE_SIG_ALL=y'` 四条全中 |
| 产物 | 四架构 RPM 内全部 `.ko` | 每个文件尾部含 `~Module signature appended~`，缺一即失败 |
| 流水线 | `ci/gates/module-signature.sh` | 接入 `image-build` 与 `release`，两处任一架构缺签名即红 |

第三条是本次核对暴露的另一个事实：门禁**实现已存在**（`ci/gates/module-signature.sh`
与 `ci/tests/test_module_signature.sh` 单测通过），但
`.github/workflows/*.yml` 里没有任何调用点。文件存在不等于门禁生效，本版把
「接线」列为本 WP 的验收项之一，不再单独记「已完成」。

实机面另有独立判据（285H，0.0.4 §16.4.17）：重装后
`cat /proc/sys/kernel/tainted` 为 `0`、`/sys/module/snd_hda_core/taint` 为空。
若新镜像仍出现 `E`，说明模块不是同一构建的签名产出，按 T6 判负。

## 6. TUI 全面建设（全 Rust，Agent-native 会话层）

### 6.1 定位

本版的 TUI 不是「把 CLI 输出画得好看」，而是**开机后唯一的用户态会话层**：

- 它与 0.0.6 桌面右侧 dock 的 TUI **不是同一个东西**。dock 复用 AirymaxRT；
  本版 boot TUI 独立，不链接 agentrt，不依赖 gateway。
- 它只消费 0.0.4 已冻结的接口，不新增内核 ABI（§6.6）。
- 它的目标是让 `docs-linux` 的用户态可观测功能「有入口、有结果、有失败判据」，
  而不是把 19 个模块全部重写一遍。

### 6.2 crate 划分

| crate | 职责 | 边界 |
|---|---|---|
| `boot-tui` | 终端渲染、布局、键盘事件循环、页面状态机 | 不解析意图语义 |
| `boot-ime` | 中文输入引擎：`AIRYIME1` 词典读取、全拼前缀检索、候选排序 | 独立进程；不链接 agentrt |
| `asr-gateway` | 录音设备独占、离线识别、结果注入 | 独立进程；模型缺失即显式不可用 |
| `intent` | Intent 校验、信任级别预检、路由到本地执行器 | 不做策略判定 |
| `airy-tui-exec` | 调 `airy-*` CLI 与 `--json` 契约，结果归一 | 不直接读写 `/dev` 或 sysfs |

五个 crate 必须各有 `Cargo.lock` 与 `rust-toolchain.toml`；`boot-tui` 是唯一被安装为
默认会话入口的二进制，其余四个可独立重启而不影响会话。

### 6.3 四通道输入

契约见 `docs-linux/30-interfaces/11-input-ingress.md`，本版只实现与验收，不另立 schema：

| 通道 | 本版范围 | 失败判据 |
|---|---|---|
| C1 键盘 + IME | 全键盘导航、中文提交、候选选择 | IME 退出后直通输入，状态栏 `ime=down` |
| C2 语音 | 触发、录音、离线识别、文本注入 | `asr=unavailable/busy/empty`，不伪造文本 |
| C3 外接 API | Unix socket + JSON Lines，单连接 | 背压 `-EAGAIN`；未知动作 `-EINVAL` |
| C4 批处理 | stdin 每行一个 Intent，供 CI | 单行失败不终止整批，末行汇总非零退出 |

四通道必须共享同一个 `trace_id` 语义与审批记录结构；不允许语音通道绕过审批。

### 6.4 中文输入

- 引擎：纯 Rust，读取既有 `AIRYIME1` 词典（24 字节头 + 词条 + 字符串池 + CRC32），
  实现全拼前缀匹配与词频降序。**不引入 librime/C++ 依赖**，避免把 GUI 输入法框架
  拖进无 GUI 的 tty1。
- 进程：独立 `boot-ime`，通过管道与 `boot-tui` 通信；崩溃不影响会话主循环。
- 数据：词典格式与现有资产同源，digest 进锁文件；缺失时降级为直通英文输入并报
  `ime=no-dict`，不得静默。
- 渲染：按东亚宽度计列；字形缺失显式报 `font=missing`（见接口册 §8）。

### 6.5 语音

- 本地离线模型，断网可用是硬要求；模型与运行时按 digest 校验。
- `asr-gateway` 独占录音设备，TUI 主进程不读 PCM。
- 识别结果按 `payload.kind=text` 注入；需要回放时保留 `audio-ref`（path + digest + 时长）。

### 6.6 只消费、不新增

本版允许消费的冻结面：

| 面 | 内容 | 约束 |
|---|---|---|
| syscall | `AIRY_SYS_CALL` / `ROVOL_CTL` / `SCHED_CTL` / `CLT_NOTIFY` 四个入口 | 不新增号段、不改 op 编码 |
| UAPI | `kernel/include/uapi/linux/airymax/` 下 19 份头文件 | 只读；不改布局 |
| CLI | `system/bin` 下 10 个 `airy-*` 入口 | 只调用；不改语义 |
| JSON 契约 | `airy-disk` / `airy-model status` / `airy-probe` / `airy-rt-cap` 的 `--json` | 只消费；字段不足时加适配层 |

TUI 不得直接读写 `/proc/sys/agentrt` 或 `/sys/kernel/security/airy/policy` 来做判定；
判定走既有安全通道，TUI 只展示结果与建议。

### 6.7 缺口登记与「无桩」判据

`docs-linux` 的 36 条功能面缺口以 `10-references/completeness-audit.md` 为唯一账。
本版对每条缺口只能有两种状态：

| 状态 | 含义 | 判据 |
|---|---|---|
| 可用 | 有端到端入口、有结果、有失败路径 | 目标机可复跑，日志带 `trace_id` |
| 缺口 | 明确登记，UI 显示不可用原因 | 界面出现 `unavailable:<原因>`，且账上有编号 |

禁止的第三种状态是「看起来能用」：返回固定文本、返回空列表、捕获异常后显示成功，
三者都按桩处理，评审直接判负。

### 6.8 验收

| # | 判据 | 方式 |
|---|---|---|
| T-1 | tty1 启动即进入 TUI，无需 X/Wayland | 目标机冷启动 |
| T-2 | 中文可输入、可选择候选、可显示 | 实机键入整句 |
| T-3 | 四通道各有成功与失败路径 | 接口册 §9 的 V-1/V-2 |
| T-4 | IME/ASR 进程被杀后可恢复或显式降级 | `kill -9` 后继续操作 |
| T-5 | 断网下全部功能可用 | 隔离网络 |
| T-6 | 无桩：36 条缺口逐条为「可用」或「缺口」 | 抽查 + 账本比对 |
| T-7 | 不新增内核面 | `git diff` 中 `kernel/` 为空 |

## 7. Rust 供应链前置（0.0.5 必做，不得后移）

### 7.1 工具链

- 版本：openEuler 24.03 LTS-SP3 仓库提供的 Rust 1.90。
- `ci/container/build-packages.txt` 必须显式加入 `rust` 与 `cargo`；当前 94 行中
  Rust 为 0 条，这是本版第一项施工（BC-061）。
- 不使用 rustup 在线安装；构建容器内直接用发行版包，保证断网可复现。

### 7.2 三件套

每个 Rust crate 必须同时具备：

1. `rust-toolchain.toml`：钉 1.90.0；
2. `Cargo.lock`：钉全部传递依赖；
3. `vendor/` 或离线 crates 源：钉可得性。

三者缺一，该 crate 不得进入 CI 构建。

### 7.3 门禁

新增 `ci/gates/lang-lock.sh`，判据：

- `distro/lockfile/lang-policy.yaml` 不变量成立（default=rust、kernel_rust=disabled、
  boundary=process）；
- planned 组件不得已有 `Cargo.toml`，present 组件必须三件套齐全；
- Rust 组件内不得出现 C/C++ 源文件；
- `legacy` 与 `exceptions` 必须带复查/过期版本；
- 有 present 组件时，`build-packages.txt` 必须含 `rust` 与 `cargo`。

尚无 present 组件时门禁以 `--allow-pending` 通过并显式打印「未就绪」，不得把
「零组件」当作「已完成」。

### 7.4 施工顺序

1. 工具链进清单 → 2. 三件套与 vendor → 3. `lang-lock` 进 CI → 4. 四个 crate 骨架 →
5. IME 引擎与词典 → 6. TUI 主循环与页面 → 7. 四通道接入 → 8. 缺口登记与验收。

顺序不可颠倒：先有可复现构建，再有 UI；否则「本地能跑、CI 不能跑」。

### 7.5 失败判据

| 情形 | 判据 |
|---|---|
| 容器内无 rust/cargo | 构建直接失败，不允许回退到 rustup |
| 锁文件与源码不一致 | `cargo build --locked` 失败即判负 |
| 组件内混入 C 源 | `lang-lock` 判负 |
| 断网无法构建 | vendor 缺失即判负 |

## 8. 非目标

- 不做登录前的图形选择界面（需要 X/Wayland 起来，与「桌面之前判定」矛盾）。
- 不做多用户会话选择、不做持久化默认项改写（`systemctl set-default` 不在
  这条路径上；默认永远是 GUI，选择只影响本次启动）。
- 不做开机动画、不做品牌化启动影片。

## 9. 风险与应对

| 风险 | 应对 |
|------|------|
| 终端程序异常退出后 tty 留在 raw 模式 | 服务侧 `TTYReset`/`TTYVHangup`，程序侧 `atexit` 恢复 termios；单测覆盖 |
| 验收镜像被 120 秒拖慢 | 验收剖面带 `airymax.session=off`；CI 断言冒烟耗时不上浮 |
| 服务在无终端机器上阻塞 | 拿不到终端即直接写 `gui`，不等待；单测覆盖 |
| 用户选了 TUI 但 `desktop_ready.sh` 仍按 GUI 判 | 判据改为读同一文件，两种模式共用输出格式 |
| 打印改动引入额外耗时 | 每阶段只有入口与结论两行，心跳一行；CI 对比总时长 |
| 构建期预演与实际装机环境不一致，预演通过而装机仍缺件 | 预演与装机跑同一支 `fw-flat.sh`、读同一份 `miss=` 语义；预演只决定「能不能出镜像」，装机日志的 `miss=` 仍由 T26 判负，两条通道互不代替 |
| 扁平软链与 `linux-firmware` 升级不同步 | 软链步骤放在 `%posttrans` 与清单同包，升级后自动补齐；T26 作为兜底判负 |
| doctor 误占开机时间 | 只在无网络时判定，有网络立即退出；CI 断言开机总时长不上浮 |
| ARM/RISC-V 无实机可验 | 本版以 QEMU + 板卡 DT 建立判据，实机到位后只补证据不改判据 |
| 预算分账后仍靠抬阈值过关 | `owned` 与 `unknown` 恒 0 使「抬」无处可抬；`platform` 预算绑主板指纹，换机失效；每条必须附证据行，缺证据的行在 CI 直接判负 |
| 人工探测再次污染取证 | 只认本次 boot 的 `_BOOT_ID`，并以 `/run/airymaxos/probe.mark` 划界；标记之后的条目不计入 |
| 能力探针在 ARM/RISC-V 上读错入口 | 发现层按「固件描述」抽象，DT 侧以 `status = "okay"` 过滤；`status` 缺失按 `okay` 处理（DT 规范默认值），有争议的节点在报告里逐条列出 |
| 扁平清单与真实模块树/固件树漂移 | 清单是安装期按两棵真实树生成的，没有手工表可漂移；兜底是 T26 按清单复核入口、安装期 `miss=` 记账，两侧任何一侧先缺都能被另一侧抓到 |
