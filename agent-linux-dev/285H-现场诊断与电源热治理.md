# 285H 现场诊断与电源热治理复核

> 记录 2026-11-02 至 11-03 在 285H（Airymax@192.168.3.19，6.6.157-alk，
> SELinux Enforcing）上的断连/重启取证、电源与热状态复核、0.0.4 装机验证
> 与实时性实测。所有结论只依据已经取到的现场输出，未取到的项目明确标为
> 「待取证」。

## 1. 结论摘要

1. 现有 4 个 boot 记录中，3 次重启均为 **clean reboot**
   （`systemd-reboot.service` 正常走完关机和重启目标），与双标记取证、
   grub 配置复验的人工重启一一对应，没有 panic、MCE、OOM 或掉电留下的
   异常记录。
2. 首次失联时 285H **AC 不在线**（`ACAD online=0`），电池
   `energy_now=20.68Wh`，放电功率 `30.07W`，按当时负载约 **41 分钟**耗尽。
   该镜像 **未安装 airymax-power**（release 早于 release 9），没有任何
   低电量告警或降档动作，电池耗尽时表现为整机直接断电。这条缺口已由
   release 10/11 的档位控制与低电量动作闭合。
3. 装到 **0.0.4-17** 后，`airy-power.timer` 为 active，
   `sudo airy-power apply` 返回 `state=ok landed=49/49 rc=0`，16 个核的
   `C3_ACPI` 全部 `disable=1`。电源治理在 285H 上首次完整生效。
4. **实时性根因是空闲深度**：285H 的 `C3_ACPI` 退出延迟 1048 µs，本身已
   超过软实时 1000 µs 预算。关闭深空闲后，典型最大延迟从 900–1000 µs
   降到 100–400 µs；16 核 `yes` 满载三轮为 **10 / 10 / 92 µs**。
5. 仍存在 **偶发毫秒级尖峰**（实测 7997/8610 µs，tracer 下 443079 µs）。
   已排除 direct reclaim（`allocstall`、`pgscan_direct` 不增长，`pswpin`
   仅 +6）、单一活跃模型（暂停 27B 实例后仍复现）与内核异常路径
   （`wakeup_rt` 栈均为正常调度路径）。尖峰与**内存超卖窗口**相关，
   属 0.0.4 X-05「桌面与 RT 共存」范围。
6. 内存超卖是硬事实：三个 `llama-server` 实例 RSS 合计约 **29.5 G /
   30 G 物理**，swap 已用 **11 G**，`MemFree` 长期 250–380 MB。这不是
   实时性问题，而是整机稳定性问题，必须靠资源治理而不是延迟调参解决。
7. 换页上限直到 release 30 才真正生效。此前三层缺陷叠加：升级路径没有
   任何组件启用新单元、部分落地被 `ExecStartPost` 语义连带跳过、写入被
   systemd 在每次 reload 写回 infinity。285H 实测定时器能在 80 秒内把
   上限自愈回 `32583151616`（§7.3）。

## 4. 实时性实测（X-04）

测量工具为 `airy-rt-lat`（`-p 90 -i 200 -D 30`），不绑核、不 pin，
与 `rt-accept.sh` 口径一致。全部单位为 µs。

| 场景 | 各轮最大延迟 | 判读 |
|------|-------------|------|
| 空闲 6×30 s | 162 / 317 / 31 / 436 / 165 / 110 | 全部 < 1000 |
| 16 核 `yes` 满载 3×30 s | 10 / 10 / 92 | 满载未恶化 |
| 干净 10×20 s | 91 / 20 / 85 / 118 / 133 / 378 / 67 / 303 / 194 / 106 | 全部 < 400，kswapd Δ≈0 |
| 带 `vmstat` 采样 6×30 s | 103 / 354 / 412 / **8610** / 849 / 198 | 尖峰非 direct reclaim |
| 暂停 27B 实例后 6×30 s | 227 / **7997** / 101 / 88 / 192 / 448 | 单一活跃模型不是唯一来源 |
| `wakeup_rt` tracer 6×30 s | 2233 / 10661 / **443079** / 4590 / 1385 / 278 | 栈为正常调度路径 |
| 三实例共存 15×30 s（release 32） | 478 / 562 / 749 / 608 / 347 / 417 / 315 / 226 / 84 / **1042** / 70 / 341 / **1855** / 344 / 289 | 13/15 达标，两次越线无回收签名 |

`wakeup_rt` 取到的 1362 µs 唤醒栈为 `__schedule` →
`exit_to_user_mode_loop` → `do_syscall_64`，即 python3 唤醒测量进程的
正常路径，没有锁竞争、缺页或驱动回调证据。tracer 自身的 `stacktrace`
开销会放大数字，443079 µs 不能当作系统延迟上限。

基线记录（`sudo python3 distro/tests/rt/baseline.py record --rounds 3
--duration 30`）为 281 / 55 / **1199**，`max_us=1199`、`limit_us=1000`、
`grade=soft`、`machine=83JK`。按 `baseline.py` 的口径，1/3 轮未达门禁，
数据照常落盘但**不能作为合格基线**。这份记录留在现场侧
（`/tmp/rt-285h-004.json`），不进源码树。

三实例共存的 15 轮在 release 32 上补测（2026-11-03 15:11–15:18，未暂停
任何模型，`loadavg` 13.6–15.4，swap 16359/16383 MB）。`allocstall_normal`
恒为 229、`pgscan_direct` 恒为 4175754，**十五轮内一次都没有增长**，因此
两次越线（1042、1855 µs）没有直接回收签名；同一窗口 `pswpout` 增加
463,721 页（约 1.8 GiB）、`pswpin` 增加 14,010 页（约 55 MiB），说明换页
写回全程在跑。判读如下：

1. 此前「SSH 失联约 3 分钟、ICMP 全丢」的整机 stall 在本窗口没有复现，
   `uptime` 连续、十五轮无一中断；release 19–31 的内存与换页边界把最坏
   情形从「整机停摆」压到「偶发 1–2 ms」。
2. 剩下的越线幅度是 1855 µs，只有此前 7997/8610 µs 的五分之一左右，
   且与 `pswpout` 持续增长同窗口——它来自换页写回，不是调度器或空闲深度。
3. 这类越线不能靠延迟参数消除：只要在用量长期贴着物理内存，换页写回就
   必然打断任何线程。收口方向是**减少并发入口**（同一模型多实例、多 slot
   把 RSS 叠到物理内存之上），属 X-05 的应用层准入，不是 OS 侧调参。

### 4.1 合格基线（release 35，模型暂停）

2026-11-03 15:57 在 285H 上重跑受控基线：三个 `llama-server` 全部停止，
系统空载（`loadavg` 0.0、`MemAvailable` 约 27 G），装的是
`airymaxos-system-0.0.4-35`，内核 6.6.157-alk。

```text
sudo python3 tests/rt/baseline.py record --rounds 3 --duration 30
{"duration_s": 30, "grade": "soft", "kernel": "6.6.157-alk", "limit_us": 1000,
```

三点判读：

1. 三轮全部达标，`max_us=123`，余量约为软实时预算的八倍。这份记录与

2. `grade` 仍是 `soft`，因为它描述的是**机型能力**（无 PREEMPT_RT、

## 6. 空闲深度根因与治理（release 17）

`C3_ACPI` 的退出延迟 1048 µs 与软实时预算 1000 µs 同量级，任何一次
进入 C3 后的唤醒都可能直接越线，这与「空闲/轻载时才出现 900–1000 µs、
满载反而 10–92 µs」的现象完全吻合——满载时 CPU 根本不进 C3。

治理策略写在 `system/services/airymax_power/idle.py`，与 governor/EPP
同级纳入同一份 `Knob` 证据链：

- 判据不是「禁用空闲」，而是「退出延迟 ≤ 1000 µs」；在预算内的
  `C1_ACPI`/`C2_ACPI` 保留，只关超预算的深态。
- 条件与档位一致：**AC 且热区未到 hot** 才收紧；电池或过热时恢复
  固件默认，不为实时性牺牲续航与散热。
- `inspect` 只读回读、`apply` 才写；`landed` 以回读的 `disable` 与
  延迟为准，不把「写过」当「生效」。

实机结果：16 核 `C3_ACPI disable=1`，`state=ok landed=49/49`，
典型延迟降到 100–400 µs。

## 7. 负载与内存超卖（X-05 范围）

现场三个 `llama-server` 实例：

| PID | 模型 | 端口 | 参数 | RSS | 备注 |
|-----|------|------|------|-----|------|
| 3288 | Qwen3.5-9B | 11435 | 12 线程 / 4 slots | 10.5 G | CPU 666% |
| 3289 | Qwen3.5-9B | 11436 | 子进程 | 1.0 G | — |
| 3656 | Qwen3.8-27B | 11437 | 4 线程 / 1 slot | 18.5 G | nice 19 |

合计 RSS ≈ 29.5 G，物理内存 30 G，`SwapFree` ≈ 5.1 G（已用 11 G），
`MemFree` 长期 250–380 MB，`MemAvailable` 约 14 G，`Dirty` 828 kB，
`kswapd0` 累计仅 8 s。内存相关参数：`swappiness=60`、
`min_free_kbytes=67584`、`watermark_scale_factor=10`、
`overcommit_memory=0`；THP `enabled=always`、`defrag=madvise`，
`compact_stall=4`、`compact_fail=4`、`pgmigrate_success=599320`。

判读：

1. `MemAvailable` 14 G 是「可回收」估算，不等于「可分配」；三个实例
   同时申请大页时仍会触发直接回收或 OOM，这正是毫秒尖峰出现的窗口。
2. `kswapd0` 累计 8 s 说明回收是**突发**而非持续，与「多数轮次正常、
   偶发一轮越线」的测量分布一致。
3. 这不是调 `swappiness` 能解决的问题。需要的是并发上限与内存配额：
   同一模型多实例、多 slot 会把 RSS 叠加到物理内存之上。

### 7.1 内存边界的落地（release 19）

边界声明在 `airymax-agent.slice`，`airy-llm.service` 只声明 `Slice=` 归属：

| 属性 | 取值 | 285H 上的实际落点 |
|------|------|------------------|
| `MemoryMax` | 90% | `memory.limit_in_bytes=29324836864` |
| `CPUWeight` | 100 | `cpu.shares`（与桌面基线 50 成 2:1） |
| `IOWeight` | 100 | `blkio.weight` |
| `TasksMax` | 80% | `pids.max=198184` |

**285H 是 cgroup v1 hybrid，不是 unified v2。** `/sys/fs/cgroup` 是 tmpfs，
没有 `cgroup2` 挂载，memory 控制器在 `/sys/fs/cgroup/memory`，
`memory.use_hierarchy=1`。这决定了哪些属性写得进去：

- `MemoryMax` 正常写入 `memory.limit_in_bytes`，`systemctl show` 回读
  与 cgroup 文件一致，硬上限有效；
- `MemoryHigh` 在 v1 上**不写** `memory.soft_limit_in_bytes`，实测值停在
  `9223372036854771712`。该属性是 v2 专有，声明它只会制造「有软限」的
  假象，因此 0.0.4 的 slice 里没有这一行（`grep -c '^MemoryHigh'` 为 0）；
- `MemorySwapMax` 在 v1 上只被 systemd 记录为属性，不写
  `memory.memsw.limit_in_bytes`，见 §7.2。

组内软限（`MemoryHigh`）是 v2 专有，要拿到它需要镜像切 unified cgroup v2，
这是镜像层决策，不在策略模块里假装生效。换页上限不需要切 v2，见 §7.2。

**读取路径是嵌套的。** `airymax-agent.slice` 的父 slice 是 `airymax.slice`，
现场路径为
`/sys/fs/cgroup/memory/airymax.slice/airymax-agent.slice/`；直接读
`/sys/fs/cgroup/memory/airymax-agent.slice` 会得到空目录，从而误判成
「限制没落地」。

**覆盖缺口（release 20/21 闭合）。** 现场三个 `llama-server` 由 AirymaxRT
从用户会话拉起，`/proc/3288/cgroup` 显示
`user.slice/user-1000.slice/session-4.scope`，`airy-llm.service` 并未 active。
release 19 的边界只覆盖「由单元拉起的推理」，不覆盖这条实际路径。release 20
把兜底上限放到共同的父节点 `user.slice`（85%），release 21 补上换页上限；
两条路径都在覆盖范围内，launcher 契约（`systemd-run --scope
--slice=airymax-agent.slice`）保留为后续收紧手段，不再是唯一出路。

**构建期的整机 stall 仍未消除。** 本轮在 285H 上 rpmbuild 期间两次 SSH
失联，各约 3 分钟，期间 ICMP 100% 丢包；恢复后 `uptime` 连续（07:12 起，
11:00 时 3:53），确认是 stall 而非重启。它与 §4 的偶发尖峰同源——内存
超卖窗口里内核在回收与分配之间长时间打转，网络栈与服务一起被拖住。7.1 的
边界在覆盖缺口闭合前不会真正生效，闭合后的现场取证见 §7.2。

### 7.2 换页上限的现场取证（release 22）

**systemd 不写换页上限。** 用瞬态服务取证（`MemoryMax=200M`、
`MemorySwapMax=300M`）：`systemctl show` 回报 314572800，`systemctl
set-property` 也接受该属性，但 `memory.memsw.limit_in_bytes` 仍是上限值
`9223372036854771712`。也就是说在 hybrid v1 上，`MemorySwapMax` 只被记录，
换页没有任何实际约束——release 21 的声明缺一个执行者。

**记账本身是通的。** 同一时刻 `user.slice` 的 `memory.usage_in_bytes` 约
28.6 G、`memory.memsw.usage_in_bytes` 约 44 G，差值即换页占用约 15.4 G；
`SwapTotal` 16 G、`SwapFree` 仅 962 MB。用「cmdline 缺 `swapaccount=1`」
解释不落地是错的，缺的是写入者，不是记账。`MemTotal` 31819488 kB、16 核、
load 8.87/9.19/10.35，`user.slice` 的 `memory.limit_in_bytes` 为
27695681536（85%），说明 release 20 的内存上限已在生效。

**memsw 不得低于内存上限。** 在 scratch group `airycap-t` 上实测：内存上限
为上限值时写 `memory.memsw.limit_in_bytes=1G` 返回 rc=1；先写
`memory.limit_in_bytes=512M`，再写 1G 成功并回读为 1073741824。启动早期
slice 目录是新建的、内存上限尚未写入，因此执行顺序必须是先内存后换页，
写反了会静默失败。

**在线状态是 `tight`，且这是正确行为。** release 22 的 `airy-rt-cap memcap`
以 `MemTotal` 换算声明（会话池 85% + 15% = 31819488 kB，即一份物理内存），
而现场 memsw 用量 43597242368（约 40.6 GiB），远超目标。此时硬压上限会把
常驻页立刻打进回收，等于用一次 OOM 换一个数字，因此命令报 `tight` 并保持
原值、返回 3。真正落地要在空载或重启后由 `ExecStartPost` 完成，这一点不能
靠在线强写。

**真实写入路径已验证。** 同一个命令对空的 `airymax-agent.slice` 执行
`--apply`，两侧都写入并回读一致：`memory.limit_in_bytes=29324836864`、
`memory.memsw.limit_in_bytes=32583151616`，状态 `applied`。会话语料同时报
`tight`，因此整体退出码为 3、`--json` 里 `layout=v1`、两条 step 分列
`applied` 与 `tight`。这是「能写就写、不能写就报」的预期形态。

**内核按页取整，目标必须先对齐（release 23）。** 首次在 285H 上落地时，
命令写入 29324840140 而回读 29324836864，差 3276 字节，执行者据此判为
「写入未生效」并报 `absent`，实际上限已经生效。根因是内核把上限向下取整到
页边界。修复放在换算处：百分比与绝对字节都先按 `SC_PAGE_SIZE` 向下对齐，
声明、写入、回读三者因此天然相等；memsw 合计由两个已对齐的分量相加，同样
对齐。release 22 装的第一次 `--apply` 就踩到了这条，正是「边开发边测试」
要发现的问题。

**0.0.3 镜像的启用缺口。** 285H 的 `airymaxos-release` 仍是 0.0.3-26，
`airymaxos-system` 已升到 0.0.4，两者的单元集合不同：0.0.3 的
`airymax-rt-budget.service` 仍处 enabled，0.0.4 的
`airy-rt-bandwidth.service`（`ExecStartPost` 所在单元）却是 disabled。
也就是说，光装 system 包不会让开机路径执行 memcap；现场已显式
`systemctl enable airy-rt-bandwidth.service` 对齐到 kickstart 的
`boot_set`。全新 0.0.4 装机由 kickstart 启用，不存在这条缺口；混合升级的
机器必须补这一步，否则换页上限只在手工执行时落地。

**启用之后暴露的时序问题。** 2026-11-03 把 285H 升到 `release 0.0.4-5` /
`system 0.0.4-27` 后，`rpm -q` 两侧都已是 0.0.4，
`airy-rt-bandwidth.service` 为 enabled。此时再读 `airy-rt-cap memcap`：

```
  airymax.slice/airymax-agent.slice        32583151616   -   differs
  user.slice                               32583151616   -   tight
```

`differs` 的含义不是「cgroup 不在」，而是「cgroup 在、值与目标不符」。
此前把 `differs` 读成「slice 未创建」是错的：`airymax-agent.slice` 的目录
一直都在（`/sys/fs/cgroup/memory/airymax.slice/airymax-agent.slice`），
`memory.limit_in_bytes` 已是 29324836864，只有
`memory.memsw.limit_in_bytes` 停在 `9223372036854771712`。真因是那句判断
本身——`airy-rt-bandwidth.service` 自安装起从未运行过一次，
`ExecStartPost` 自然也没跑过。会话池 `user.slice` 一直都在且用量已超目标，
所以那条路径正常判为 `tight`（在线用量已超目标，硬压等于用一次 OOM 换一个
数字）。写入时机与回退来源见 §7.3，收口见 §9 第 8 条。

### 7.3 上限写入活不过 reload（release 28–30）

**升级路径没有任何组件启用新单元。** preset 把自有栈逐个 `disable`，
启用只发生在 kickstart 的装机阶段；`%post` 只做 `daemon-reload`，
`airy-update` 不碰 systemd。于是在已运行的机器上升级 0.0.4 的新包，
新治理单元既不启用也不启动，症状是「治理静默缺席」——从任何服务状态都
看不出来，只能靠 `systemctl is-enabled` 逐个查。285H 上
`airy-rt-bandwidth.service` 从安装起一直是 `disabled`，这就是 §7.2 里
`differs` 的真正来源。

**修法是收敛到一份清单。** 清单 `boot-set` 随包落到
`/usr/lib/airymaxos/boot-set`，装机（两个 kickstart）与升级
（`%posttrans`）读同一份文件、跑同一段循环。`%posttrans` 在整笔事务装完
后运行，镜像合成 chroot 与装机阶段没有 `/run/systemd/system`，以此判据
跳过。release 28 在 285H 上实测：安装后逐项输出 `state=enabled`，包括
`lightdm.service`、`airymax-desktop-ready.service` 与换页上限所在单元。

**部分落地被判成失败，导致上限整条跳过。** 带宽预算在开机时必然只落
3/4 个 slice——`airymax-desktop.slice` 登录后才存在——命令返回 3。而
systemd 只在 `ExecStart` 成功后才执行 `ExecStartPost`，于是挂在后面的
`memcap` 从未执行，`memsw` 停在 infinity，`user.slice` 已用换页 13.8 G。
修法是按依赖拆分：上限只依赖 slice 目录，开机即可完整落地，独立成
`airy-rt-memcap.service`；带宽单元把退出码 3 声明为成功，它描述的是剖面
事实而不是启动失败。

**写进去也活不过一次 reload。** 上限写入成功后执行一次
`daemon-reload`，`memory.memsw.limit_in_bytes` 立刻回到
`9223372036854771712`；而手工改 `memory.limit_in_bytes` 不会影响它。
两侧对照把回退定位在 systemd 一侧：cgroup v1 上 systemd 不管理该文件，
每次 reload 按自己的视图重写。`systemctl enable` 内部就会 reload，装机、
升级同样会，所以一次性写入只是在下次 reload 之前有效。

**因此按周期重写（release 30）。** `airy-rt-memcap.timer` 每 60 秒重写
一次，服务去掉 `RemainAfterExit`，oneshot 退出后回到 inactive，
`OnUnitInactiveSec` 才能排下一次；同一拍顺带重试开机时因用量越界被拒的
slice——长任务下这正是那个状态。285H 上验证：停服务让定时器触发后
`memsw=32583151616`，`daemon-reload` 后回到 infinity，80 秒内自愈回
32583151616。

### 7.4 超用状态下不能留白（release 31）

release 30 让写入活了下来，但守卫本身还有一个语义缺陷：**只要在用量高于
目标，就拒绝任何写入**。285H 现场正是这个状态——声明的合计上限是
32583151616（31 GiB），而 `user.slice` 的 memsw 在用量是 43597242368
（40.6 GiB）。差值不是几十兆，而是库里已经装着 15 G 换页；换页内容不会
因为回收而减少，只有进程退出或被换回才会降。于是这一轮 `tight`、下一轮
还是 `tight`，守卫永久留白：**机器最需要上界的时候，恰恰一点上界都没有**。

结果是可观测的：`SwapTotal` 15 G 全满、`MemFree` 数百兆、`load1` 16.8，
任何一次大块分配都直接进全局回收。整机停顿不是「因为设了上限」，而是
「因为没设上限」。

**改法是余量封顶，而不是继续拒写。** 目标值低于在用量时，`--apply` 写入
`max(目标, 在用量 + 余量)` 并报新状态 `held`，余量取声明上限的 5%。三条
不变量保证这不会把配置动作变成事故：

1. **写入值永远不低于在用量**——所以不会触发当场回收，装包不会杀掉正在
   跑的模型；
2. **只收紧、不放松**——现值低于封顶值时保持原值不写，否则每轮都会把上限
   往上推一截，封顶会自己长成无穷大；
3. **用量回落后自然收敛**——在用量降到「目标 − 余量」以下，下一轮就写回
   声明目标，`held` → `applied`。

越过封顶的增长被挡在组内：内核在 `user.slice` 内回收，回收不动就杀组内
最大的任务，代价是一个实例，而不是整机停住两三分钟。只读判定仍报 `tight`，
因为限额确实不在目标上；`--apply` 的 `held` 只是「有上界、但不在目标」，
与 `tight` 同属退出码 3，门禁不会把它当成功。

```text
  airymax.slice/airymax-agent.slice  32583151616  held
  user.slice                         43700000000  held
```

**验证分两层。** 单元层用假 cgroup 树锁死三条不变量：
`test_tight_holds_above_usage`（封顶高于在用量）、`test_hold_never_raises`
（现值低于封顶时不抬）、`test_hold_converges`（用量清零后收回目标）；现场层
在 285H 上执行一次 `airy-rt-cap memcap --apply`，回读 `memsw` 应落在
「在用量」与「声明上限 × 1.1」之间，且模型进程不受影响——写入值高于在用量，
所以这一刻不会有任何回收发生。

现场两层都已取到。**手工层**：`--apply` 回读 `46049583104`，在用量
`44411355136`，三个 `llama-server`（PID 3288/3289/3656）RSS 不变，状态
`held`，整体退出码 3。**自愈层**：`systemctl daemon-reload` 把 memsw 写回
`9223372036854771712`，随后 `airy-rt-memcap.timer` 在 36 秒内重写回
`46050533376`（14:43:14 落盘、14:43:50 回读），`Result=success`、
`ExecMainStatus=3`。也就是说 reload 不再是缺陷，只是把上界临时抬高一级，
下一次 tick 收回来；两条路径的封顶值相差不到 1 MiB，是两次计算时在用量
不同所致，属于预期内的收紧过程。

### 8.1 散热设备的执行面（release 24）

285H 上有 22 个 `cooling_device`：4 个 `Fan`（`cooling_device1`–`4`）、
16 个 `Processor`（cpufreq 冷却，`max_state=3`）、1 个 `intel_powerclamp`
（`max_state=100`）、1 个其他。四个 `Fan` 是 ACPI `PNP0C0B` 风扇对象，
`max_state=1`，初始 `cur_state=0`，且没有任何 `thermal_zone` 绑定它们
（各 zone 的 `cdev*` 链接数为 0）——风扇转速由 EC 按固件策略决定。

**写一次就证明不可写。** 向 `cooling_device2/cur_state` 写 `1` 返回
`ENODEV`，`dmesg` 留下

```
ACPI Error: Aborting method \_TZ.FNCL due to previous error (AE_NOT_FOUND)
```

写后回读 `cur_state` 同样 `ENODEV`，此后的清单里 4 个风扇全部标记为
「存在但读不出档位」，`engaged` 恒为 0；风扇转速没有任何变化。也就是说
固件根本没有实现 `_TZ.FNCL`（风扇控制方法），**内核侧不存在可用的执行面**。

**结论与边界。** 散热闭环只能落在平台实现了的三处接口上：
`platform_profile`、`governor`/`EPP`、空闲深度（§6）。release 24 的
`airymax_power/cooling.py` 因此只读：列出设备、类型、`max_state`、
`cur_state`，读不出的照样列出并标为不可读，并且永不以写方式打开
`cur_state`（`test_cooling.py::test_read_only` 锁死）。现场
`airy-power status` 输出：

```
  cool fans=4 devices=22 readable=17 engaged=0
```

`readable=17` 正是「4 个风扇不可读 + 16 个处理器冷却 + 1 个压制器可读」，
与本节取证一致。

**顺带修正的排序缺陷。** `sysfs.order` 原先取最后一个下划线之后的整段作
序号，`thermal_zone2`、`cooling_device2` 都退化成 0，证据按字典序排列，
`zone10` 会排在 `zone2` 前面。改为取名字末尾的连续数字，报告顺序与硬件
编号一致。

**没有做的事。** 没有接管风扇，也没有把 `Processor` 冷却当作风扇来写：
后者是降频冷却，写它等于悄悄给 CPU 设上限，与「风扇不归我管」是两件事。
若将来要在过热时主动限频，那是一个独立的能力，需要独立的设计与门禁，
不能混在散热清单里。

### 8.2 整机硬件清点（release 25）

传感器与策略都建立在「设备到底在不在」之上，而此前没有任何一处把整机硬
件一次说清：`lspci` 只覆盖 PCI，`/sys/class/net` 只覆盖网卡，缺一类就少
一个判据。release 25 的 `airy-observe hardware` 只读 sysfs，把十二类设备
分三态列出：整类没有节点是 `absent`，设备状态原样取自 sysfs，rfkill 软硬
开关任一为 1 是 `blocked`（唯一可「启用」的状态）。必检项只有 cpu、block、
net 三类，其余九类在 ARM 与 RISC-V 开发板上未必齐全。

现场输出：

```
airy-observe state=ok groups=12 devices=53 missing=0 blocked=0
  cpu        16  cpu0=online cpu1=online cpu2=online cpu3=online +12
  block       6  nvme0n1=present nvme0n1p1=present nvme0n1p2=present nvme0n1p3=present +2
  net         2  lo=unknown wlp1s0f0=up
  rfkill      4  rfkill0=ready rfkill1=ready rfkill2=ready rfkill3=ready
  gpu         1  card0=present
  sound       1  card0=present
  usb         4  usb1=present usb2=present usb3=present usb4=present
  thermal     7  thermal_zone0=20000 thermal_zone1=44050 thermal_zone2=44050 thermal_zone3=42050 +3
  hwmon       6  hwmon0=present hwmon1=present hwmon2=present hwmon3=present +2
  power       4  ACAD=present BAT1=Not charging ucsi-source-psy-USBC000:001=present ucsi-source-psy-USBC000:002=present
  tpm         1  tpm0=present
  watchdog    1  watchdog0=inactive
```

**首跑暴露的三处映射缺陷。** 第一次在 285H 上执行时 `cpu` 被判 `absent`：
x86 没有 `/sys/class/cpu`，CPU 只出现在 `devices/system/cpu/` 下，改为按
`cpu*` 扫该目录，并用「名字剩余部分必须全是数字」挡掉同目录的 `cpufreq`
与 `cpuidle`。显卡同目录还混着 DRM 连接器（`card0-Unknown-1`），只认
`cardN`。rfkill 的四个节点里有两个 `bluetooth`，只报类型无法区分是哪一个
被关着，因此节点名与设备标签分开：`name` 是 sysfs 目录名，`label` 是设备
自报类型，人读输出用前者，JSON 两者都给。

**结论。** 285H 的十二类设备全部在位，没有被关断的无线电，电源侧同时看到
AC、电池与两个 USB-C 源，热区 7 个、hwmon 6 个与 §6 的取证一致。`BAT1`
状态 `Not charging` 与 §1 的「插电稳态、电量 98%」吻合，不是故障。

**装在一起才发现的名字冲突（release 27）。** release 25 把硬件清点装成
`/usr/bin/airy-observe`，而发行包早已用同一个名字出身份与分区报告。两个
包各装一个同名文件，release 0.0.4-4 与 system 0.0.4-26 同时升级时 rpm
直接报文件冲突，单独升级任一个也解不开。命令名只能有一个主人：硬件清点
改为 `airy-observe hardware`，转交 `python3 -m airymax_observe`，system
包只装模块与 `__main__`。285H 装 `release 0.0.4-5` / `system 0.0.4-27`
后复验：`airy-observe hardware` 报 `state=ok groups=12 devices=53`，
`airy-observe --section net` 照旧输出，`rpm -qf /usr/bin/airy-observe`
只剩发行包一个主人，`/etc/os-release` 的 `VERSION` 也随 release 包升到
0.0.4——混合升级时两侧版本终于一致。

### 8.3 整机停顿的取证（release 26）

§7.1 记过两次 rpmbuild 期间的失联，各约 3 分钟；§4 记过 7997/8610 µs 的
尖峰。两件事在日志上是**空白**：整机被内存回收与分配卡住时，`airy-power`
的巡检、`journald` 的落盘、SSH 的应答一起停摆，事后回看，这段时间里
没有任何一条记录能证明「机器卡过」。告警无从谈起，因为连「该响铃的时刻」
都没有留下。

唯一还成立的事实是：**本该按点醒来的周期任务没有按点醒来。** 巡检每
60 s 一次，唤醒时刻由 `CLOCK_BOOTTIME` 给出——它计入挂起，是单调且跨
挂起连续的时钟，比 `CLOCK_MONOTONIC` 更适合判断「真实过去了多久」。
`stall.watch()` 每次巡检只做三件事：读上一拍的写入、写本拍的时间戳、
用差值判断。间隔超出 `INTERVAL + SLACK = 90 s` 即判定整机停顿：超出的
那 30 s 余量覆盖 systemd 的 `AccuracySec` 抖量与短时调度延迟，避免把
正常抖动报成停顿。

留痕落在 `/run/airy-power/pause`，一行三个字段：实际间隔、超出预算的
秒数、UTC 时间。`/run` 在重启后清空，这条证据天然只描述「本次开机内
发生过什么」；写法是「最后一条覆盖前一条」，因为停顿的判据是「存在过」，
不是「发生过几次」——次数在心跳文件里可复算。

285H 实测（把心跳回拨 200 s 模拟一次停顿）：

```
first  None
normal None
pause  Pause(gap=200.0, over=110.0, at='2026-11-03T05:13:34Z')
recent Pause(gap=200.0, over=110.0, at='2026-11-03T05:13:34Z')
boottime 21693.342361157
```

`first` 与 `normal` 是首次运行与正常间隔，都不报；200 s 的间隔报出
`over=110.0`（200 − 90）；`recent` 从 `/run` 读回同一份记录，说明证据
在进程重启后仍可被 `airy-power status` 呈现。心跳不可写时（如指向
`/proc`）静默跳过，不因取证失败而让整轮评估报错——取证是旁路，不是
控制环的一环。

**边界。** 停顿已经发生，这一拍能做的只有记录；真正的动作在下一拍：
§7 的内存与换页上限把超卖窗口关掉，`stall` 只负责在窗口漏过去时留下
可复算的下界。把「过去的停顿」当成「当下要处置的故障」去加档、降频或
关机，只会用一次误动作换一个更差的结果。

### 8.4 一次失败被放大成两条（release 32）

复验 release 31 时，`systemctl --failed` 在 285H 上给出三条：

```
airy-disk-mount.service             failed
airy-incident@airy-disk-mount.service.service   failed
airymax-desktop-ready.service       failed
```

第一条是真故障：这台机器用 0.0.3 镜像手工安装，没有 `/data` 分区，
`airy-disk mount` 报 `no-entry` 并以 3 退出，单元按设计判失败。后两条是
**被它带出来的假故障**：

1. `airy-disk-mount.service` 带 `OnFailure=airy-incident@%n.service`，
   失败即拉起模板；
2. 模板 `ExecStart=/usr/sbin/airyctl`、`User=airy`，而 0.0.4 的 system
   包既不安装 `airyctl`（它属于 agentrt 载荷），也没有任何包创建 `airy`
   账户（装机账户是 `amuser`，285H 上连这个都没有）；
3. 模板因此以 `status=217/USER` 失败——它自己成了第二条 failed 单元；
4. `airymax-desktop-ready` 的就绪判据包含「没有 failed 单元」，于是一次
   数据盘缺失被读成整机未就绪。

这不是参数问题，是**接口面与载荷的边界没写清**。产品已经有一条成文先例：
`health_check.sh` 在 0.0.3 上对缺失的 agentrt 载荷记「跳过（不适用）」，
而不是报失败。失败处理模板缺同一道门。

修法只有一行，但要连测试与契约一起改：模板加
`ConditionPathExists=/usr/sbin/airyctl`，载荷缺席时 systemd 记
`Result=conditions`（既不是 failed，也不触发下一级），原始失败单元仍留在
`systemctl --failed` 里——**失败只能有一条记录，不能被处理链复制**。
`units_lint.py` 的模板契约、`test_units.py` 的反向用例（删掉这一行必须
报错）与 spec 的 `%check` 同时锁住该形态，避免下次被「清理注释」带走。

`User=airy` 保留不动：账户与 `airyctl` 同属 agentrt 载荷，载荷落地时由它
创建；OS 层只交付单元接口面，不在镜像里造一个没有主人的账户。

**实机复验（release 32，`airymaxos-system-0.0.4-32`）**：`reset-failed` 后
重启 `airy-disk-mount.service`，它照旧失败（`no-entry`，真实缺口），
随后：

```
$ systemctl show airy-incident@airy-disk-mount.service.service \
    -p ActiveState -p Result -p ConditionResult
ActiveState=inactive
Result=success
ConditionResult=no
$ systemctl --failed --no-legend
airy-disk-mount.service       loaded failed failed Mount AirymaxOS Data Partition
airymax-desktop-ready.service loaded failed failed AirymaxOS boot and desktop readiness probe
```

一次失败只留一条记录，处理链不再复制它。剩下这两条其实是同一条根因的
两个投影（§8.5）；本节当时把 `/data` 缺失读成「应报的真故障」，那是因为
判定口径还没分开「本机从无数据分区」与「记录丢了」——release 33 纠正了
这个口径。

### 8.5 旧布局的缺分区被报成故障（release 33）

重启复验后 `systemctl --failed` 只剩两条，且是同一条根因的两个投影：

```
airy-disk-mount.service        failed   mount  no-entry，退出码 3
airymax-desktop-ready.service  failed   AIRYMAX-DESKTOP-FAIL reason=boot
```

就绪探针只回答「开机单元全绿了吗」，`airy-disk-mount` 一红它就跟着红，
所以真正要修的是前者。现场布局：`nvme0n1` 953.9 G，`/` 70 G、`/home`
866.3 G，`/etc/fstab` 五条里没有 `/data`，`/var/lib/airymaxos/` 只有
`efi-brand` 与 `grub-args`，**没有 `install-disk.json`**——这台机器是
2026-10-31 由 anaconda 装成的 0.0.3 布局，从来没有数据分区。

缺陷在判定口径：`mount.judge()` 把「本机压根没有数据分区」与「有数据
分区但 fstab 丢了记录」并成同一个 `no-entry`。前者不需要修，后者必须修，
混在一起就是每次开机留一个无法消除的假故障，还会触发 `airy-incident@`
把真正的挂载失败淹没。

判据取安装期选盘记录的在场与否，而不是猜分区标签：记录由 `%pre` 写在
目标根，`%post --nochroot` 再复制一份，两个脚本都在 `set -eu` 下调用
`airy_keep`，写失败会中止安装——所以**有记录 ⇔ 0.0.4 装机 ⇔ `/data`
必须有**。据此分三态：

| 现场 | 判定 | 退出码 | 单元 |
|------|------|--------|------|
| 已挂载 | `mounted` | 0 | 绿 |
| 有记录、无 `/data` 记录项 | `no-entry` | 3 | 红，真故障 |
| 无记录、无 `/data` 记录项 | `unset` | 4 | 绿（不适用） |

单元加 `SuccessExitStatus=4`，与 `airy-disk-health.service` 已有的
`ConditionPathIsMountPoint=/data`（「装机未选数据盘不是故障」）同一口径。
契约锁进 `units_lint.py` 的 `DISK_MOUNT_PAIRS`，反向用例分别锁
`test_mount.py`（`judge`/`ensure` 不执行任何命令）与 `test_cli.py`
（退出码 3 与 4）。

缺失仍然可见，只是不再冒充故障：`mount unset` 的 advice 明说「数据分区
未启用，`/data` 下的内容会落在根分区」，`airy-disk status` 的 install 段
报 `absent`。这也决定了 285H 上不能直接改成 0.0.4 布局——把 `/home`
866 G 重划成 `/data` 是破坏性操作，必须由用户决定时机。

### 8.6 每次 SSH 连接都记一次登录失败（release 6 闭合）

复验过程中每个会话开头都打印一行 `The account is locked due to 3 failed
logins.`，追下去得到一条与「失联」高度相关的现场事实：

```
pam_unix(sshd:auth): authentication failure; ... rhost=192.168.3.6 user=root
pam_faillock(sshd:auth): Consecutive login failures for user root account temporarily locked
Accepted publickey for root from 192.168.3.6 port 46920 ssh2: ED25519 ...
```

即**公钥登录成功之前，PAM 的 auth 栈已经记了一条失败**。实测规律：一次
TCP 连接对应用户一条 `RHOST` 失败记录，root 与 `Airymax` 都一样；客户端
关掉 `PasswordAuthentication`、`KbdInteractiveAuthentication`、
`GSSAPIAuthentication` 后仍然一条不少，所以不是客户端试错密码造成的。

成因落在 PAM 栈的顺序上：`/etc/pam.d/password-auth` 是
`pam_faillock preauth → pam_unix sufficient → [default=die] pam_faillock
authfail → sufficient pam_faillock authsucc`。空口令让 `pam_unix` 失败，
`[default=die]` 立刻返回，**`authsucc` 永远走不到**，于是「成功登录清零
计数」这条兜底失效，计数只增不减。

后果不是「登不上」（公钥仍被接受），而是三点：① `deny=3
even_deny_root unlock_time=60` 让 root 与普通账号在连续三次连接后进入
60 秒锁定窗口，对方看到的是「密码正确也说账号被锁」；② 依赖口令的
`sudo`、`su`、控制台救援在这 60 秒内一并失效，机器真出问题时恰好最难
进；③ 自动化巡检本身就是高频连接，等于让治理机器长期处在锁定边缘，
这会把「账号被锁」误读成「机器不稳定」。

**根因取证。** 在 285H 以 `/usr/sbin/sshd -ddd -p 2222` 抓完整认证过程，
每次连接的日志顺序都是 `mm_auth_password` → `PAM: initializing for
"root"` → `PAM: password authentication failed for root` → `Failed none
for root`。调用方是 sshd 的 "none" 方法：它以空口令调一次 PAM，与客户端
是否尝试口令无关，这就是客户端关掉三种方式仍一条不少的原因。

**修法（release 6）。** 不改 PAM 栈，而是不让有口令的账户进入口令认证：
`50-airymax-sshd.conf` 全局 `PasswordAuthentication no`，在
`Match User amuser` 内单独放开 `PasswordAuthentication yes`，
`PermitEmptyPasswords yes` 保持全局。amuser 的探测是空口令对空口令，PAM
判定成功、不产生计数；root 不再进入口令认证，探测随之消失。
`/etc/pam.d` 一个字节都没有改。

285H 复验（`airymaxos-release-0.0.4-6`，配置层与真实连接两层）：

| 项目 | 现场值 |
|------|--------|
| `sshd -T -C user=root` | `passwordauthentication no` |
| `sshd -T -C user=amuser` | `passwordauthentication yes` |
| 重载前 | root 处于 `3 failed logins` 锁定窗口 |
| `faillock --reset` 后连续 5 次公钥连接 | 5/5 成功，`faillock` 表为空 |
| 近 6 分钟 `journalctl -u sshd` | `mm_auth_password` 0 条、`Failed none` 0 条 |

取舍：root 在本镜像上只接受公钥登录，交付口令只在本地控制台可用；远程
接管由 amuser（wheel + NOPASSWD sudo）承担。装机验收同步加了两条断言
（全局 `PasswordAuthentication no`、`Match User amuser` 存在），防止下一
版把策略改回去而无人发现。

### 8.7 准入判定上线（release 34）

§7 里三个实例叠加到 29.5 G 是整机问题的入口。release 34 在入口上加判定：
`airy-rt-cap admit --need SIZE` 只回答一个问题——新实例装不装得下，装不下
就拒绝并给出缺口，已在跑的实例一个都不动。

2026-11-03 15:47 在 285H（空载，`MemAvailable` 约 30.2 G）装 release 34
实测：

|------|---------|--------|

| `admit --need 40G` | `admit=refuse ... short=16027090944` | 3 |

### 8.8 准入接到启动路径（release 35）

release 34 只把判定做成命令，没有人调用它。release 35 把它接进
`airy-model serve`：判定通过后，从同一次清单读取里算出常驻量（全部资产
字节数加 2 GiB 引擎地板），再交给 `admit.check`；拒绝以退出码 75 结束，
与资产缺失的 78 分开。

285H 上没有 `/var/lib/airy-llm/manifest.json`（这台机器的模型是手工起的，
不走 `airy-llm.service`），因此用 `/tmp` 下的临时运行根验证部署后的代码：
权重与引擎用真实文件，九 B 权重以 bind mount 放进运行根，`manifest.json`
按实际尺寸与摘要生成，验证完卸载并删除。读数为真实数据，不是构造值。

| 步骤 | 关键输出 | 结论 |
|------|---------|------|
| `launch.plan`（9B，真实清单） | `state ready need 7828006112 argv 11` | 5,680,522,464 + 2,147,483,648，与地板一致 |
| `admit.check(need)` | `fit free 26914889728 short 0 reserve 3258318848` | 空载装得下 |
| `launch.run`（注入 4 GiB 可用内存） | `rc 75`，`admit: refuse need=7828006112 free=958447616 short=6869558496` | 拒绝且未拉起引擎 |
| 同上后的 `pgrep llama-server` | 0 | 拒绝发生在 exec 之前 |
| 资产用符号链接指向运行根之外 | `state failed reason ASSET_CORRUPT` | 只认解析后的真实位置，越界即硬失败 |

三点判读：

1. 地板 2 GiB 取自 §7 的现场差值（27B 单 slot 实例 RSS 18.5 G、权重约
   16.5 G），不是凭空的保守系数；多 slot 的放大部分仍由 slice 硬上限兜底。
2. 拒绝路径不写 cgroup、不碰在跑进程、不 exec 引擎，因此「装不下」不会
   被单元的重启策略放大成反复启动。
3. `unknown`（内存接口不可读）在启动路径上放行并留一行依据：让模型在
   任何环境下都起不来，比一次可观测、仍受 memsw 收口的越界更糟。

AirymaxRT 启动器一侧随后收口，见 §8.9。

### 8.9 启动器侧准入

AirymaxRT 的常驻进程由 `supervisor_d` 在登录会话里派生，不走
`airy-llm.service`，release 35 的门对这条路径无效。现在 `supervisor_d`
在 fork 之前调用同一份 `airy-rt-cap admit --json`，只读 `state` 与
`short`，保留量的算术不复刻到 C 侧——判据仍只有一处。

拒绝不是故障，是结论，因此单独给了 `wait` 态：只重判、不重派生、不计
连败。连败计数留给真正起不来的进程，否则一次内存紧张的窗口会把实例推进
FAILED，等内存回来还要人工 `activate`。重判周期
`AIRYRT_SUP_ADMIT_RETRY_MS` 缺省 30 秒；判定不可得（工具缺失、输出不可
解析）时放行并告警，与单元侧的 `unknown` 同一条理由。

2026-11-03 16:30 在 285H（`MemAvailable` 约 28 G、`reserve` 3.03 GiB）以
树外构建（`/root/sup-verify`，GCC 12.3，`-O3 -Werror`）实装验证：

| 步骤 | 关键输出 | 结论 |
|------|---------|------|
| `admit --need 29G --json` | `refuse need=31138512896 short=4385509376`，退出码 3 | 29 G 装不下，缺口 4.1 GiB |
| 声明 `AIRYRT_LAUNCH_MEM_llama_server=29G` | `llama_server wait fails=0`，`pgrep` 为 0 | 停在 `wait`，未派生、未计连败 |
| 重判周期 3 秒下的日志 | 每 3 秒一行 `admit: refuse ... short=...` | 只重判定，不重派生 |
| 改声明为 `3G` 重启 | `spawn llama_server pid=28549`，5 秒内 `healthy (sock=tcp:11435)` | 同一份门放行正常体量 |

常驻量随声明走：`airy-local model install` 把 `mem|<name>|<size>` 写进注册
表 `model.<name>.mem`，生成片段时转成 `AIRYRT_MANAGED_MEM`，再由
`agentrt-bootstrap.sh` 落成 `AIRYRT_LAUNCH_MEM_<NAME>`。片段收回体量时必须
出清该键，留着陈旧门槛会在换小模型后继续拒绝启动；未声明体量的进程不设
门槛，替用户猜体量只会造出无据的拒绝。目录里 9 G / 18 G 两个种子值分别
对应 §8.8 的 9B 判定值（7.83 G）与 §7 的 27B 单 slot RSS（18.5 G），模型
恢复后再取一轮真实 RSS 复核。

### 8.10 处理器性能上限闭环（release 36）

§8.1 已确认 285H 的 21 个散热设备全部固件托管、`_TZ.FNCL` 没有执行面；
盘点后整个系统里唯一可编程的连续执行器是 `intel_pstate` 的
`max_perf_pct` 与 `no_turbo`。governor/EPP/空闲深度都是离散档位，热
压到临界时需要的是「把功耗上限从 100% 压到 70%」这类连续收缩，而不是
换一档 governor。release 36 把这两个控制点接进同一轮评估，形成四阶
上限阶梯（由紧到松）：50%/turbo off、70%/off、90%/on、100%/on。

阶梯的输入是热余量、节流增速与整机负载三者的最严重档；电池或弱供电
整体压一阶（未知供电不压——把「读不到电源」当成电池，会让 285H 空载
时被误压到 50%）。滞回规则：收紧立即生效，放宽要求连续三轮评估都
宽松，状态记在 `/run/airy-power/ceiling`，重启即忘、不留过期判断。

2026-11-03 在 285H 以树内部署（`/root/airy-verify`，855 项单测全绿）
实测，两条链路各验一段：

| 场景 | 关键输出 | 结论 |
|------|---------|------|
| 空载 `status` | `state=ok source=ac charge=97% cap=100% turbo=on landed=51/51` | 上限控制点纳入后 51 个控制点全部落地 |
| 16 核 `yes` 负载 4 分钟 | `load=16.05`（strain WARN）→ `cap=90 ceil=2` | 负载 strain 驱动上限收紧，立即生效 |
| 撤负载后的恢复序列 | `ceil=2 1` → `ceil=2 2` → `cap=100 ceil=3 0` | 放宽严格按连续三次宽松评估执行 |
| 全程 `package_throttle_count` | 保持 4 不变 | 收紧发生在固件节流之前，SEN1 峰值 45.05 °C |

### 8.11 工具链预热的两个自锁环（CI 侧收口，不动镜像内容）

2026-11-03 的 image-build run `41613120035` 在「Warm toolchain cache」步失败，
`ci/gates/toolchain.sh` 三次都报
`timeout: failed to run command 'dnf_run': No such file or directory`。这是
**自证与执行写在同一段 shell 里**的典型形态：门禁把缓存自证拆成「先离线试装、
失败才进在线段、收尾再离线自证」，在线段写成 `timeout 3600 dnf_run online`，
而 `timeout(1)` 只执行外部命令，`dnf_run` 是 shell 函数——时限包在函数上，
函数根本没有被执行，于是在线段永远无法补齐工具链，三次重试等于三次空转。

修法是把时限从函数调用挪进命令数组：`dnf_run` 收两个参数（秒数、模式），
先用 `docker run` 组装数组，仅当秒数大于 0 时在数组头部插 `timeout`；
调用点改为 `dnf_run 0 offline` / `dnf_run 3600 online` / `dnf_run 0 offline`。
这样「限时」只作用于真正的外部进程，离线试装与收尾自证不限时（它们本来就
只做本地事务，限时只会把慢盘误判成缓存不全）。

第二个环与代码无关，是缓存键与环境状态的耦合。工具链缓存按
`hashFiles('ci/container/build-packages.txt')` 做键，此前无论 warm 成败都写
精确键；run 中途被取消时 `actions/cache/save` 仍会落一份半份缓存，而半份缓存
一旦落在精确键上，后续每轮 `cache-hit` 恒真、保存分支因
`if: ... != 'true'` 永不触发，每一轮都只能从公网补差且补不全——越补越慢、
越慢越容易被取消，形成自锁环。现场证据：run `41613120035`
命中键 `dnf-0a6143e5…` 的 371 MiB 半份缓存，离线自证立刻失败；该条目已于
同日删除（缓存 id `9710518053`）。

修法把「写入」绑定到「自证结果」而不是 job 成败：warm 步加 `id: warm`，
保存键在 `steps.warm.outcome == 'success'` 时取精确键，否则取
`dnf-<摘要>-partial-<run_id>` 滚动键，由 `restore-keys` 的 `dnf-` 前缀被
下一轮捡走。精确键从此只代表「这份缓存足以离线安装」，语义与门禁的
`toolchain offline proof` 对齐；半份缓存不再能冒充完整缓存。

回归用 `ci/tests/test_toolchain_gate.sh` 钉住调用序列而不是措辞：docker 桩
按预置计划逐次放行，只记录「第几次调用、什么模式」。三条用例分别断言冷缓存
第二次在线成功（`offline online clean online offline`）、在线三次都失败
（`offline online clean online clean online clean`）、命中完整缓存（`offline`）。
把在线段还原成旧写法时用例 2 立刻变红（序列退成 `offline clean clean clean`，
等价于函数从未执行），修复后三条全绿；`bash ci/lint.sh` 通过（14 个回归脚本）。

判读：这类失败的共同点不是「网络慢」，而是**把可观测的判据写在了它自己
无法执行的层上**——时限包住函数、缓存键不带自证结果。两者的修法都回到
「判据只看它真能观测到的东西」这条 0.0.4 铁律③。

### 8.13 内核稳定性与两条交付面日志缺陷（2026-11-09）

本节回答两个现场提问：ALK 内核是否稳定，以及开机日志里那些 `auth.err`
与 `dhclient` 告警究竟是什么。全部判据取自机上直接读取，不用版本号推断。

**内核稳定性。** `uname -r` 为 `6.6.161-alk`；`tainted=12288`（0x3000，
即 `TAINT_OOT_MODULE | TAINT_UNSIGNED_MODULE`），来源是机上早前手工替换的
`snd_hda_core`，不是发行镜像自带，重装即归零。`journalctl -k` 中
`BUG`/`Oops`/`panic`/`soft lockup`/`Call Trace` 计数均为 **0**。err 级
共 69 条，逐条归类后全部指向同一上层原因：**固件 DSDT 表自身缺陷**。

| 计数 | 原文 | 判读 |
|------|------|------|
| 32+10+10+4+4+2+2 | `ACPI Error: AE_ALREADY_EXISTS, Failure to create ... \_SB.PCN.XHCI.RHUB.HSN._UPC/_PLD` | 固件重复定义同名对象，内核按覆盖处理 |
| 2 | `ACPI Error: AE_NOT_FOUND ... \_TZ.TZN._TMP` | 固件温区缺温度方法 |
| 2 | `ACPI Error: AE_NOT_FOUND ... \_SB.PCN.LPCB.MXTP` | 固件引用不存在的设备 |
| 1 | `proc_thermal_pci: failed to add RAPL MMIO interface` | 固件把 RAPL MMIO 放在内核不认的位置，能量计数器不可用 |

判读：这四类都在固件侧，OS 侧没有可修的位置，也不影响设备可用性
（温区另有 `x86_pkg_temp` 可读，见 §2）。因此只登记为固件缺陷，不在
0.0.4 里加任何 ACPI 白名单或静音规则——那会把真正的 ACPI 错误一起吞掉。

**ldapdb 噪声（根因已定，修法在装配期）。** 每次有进程链接 libcurl 并
初始化 SASL（dnf 最典型），journal 固定出现两条 `auth.err`：

```
ldapdb_canonuser_plug_init() failed in sasl_canonuser_add_plugin(): invalid parameter supplied
_sasl_plugin_load failed on sasl_canonuser_init for plugin: ldapdb
```

触发链：`sasl_client_init` 扫 `/usr/lib64/sasl2` 全部插件 → `ldapdb` 的
canonuser 初始化要求 `ldapdb_uri` → 该键只从 `/etc/sasl2/<appname>.conf`
读，装机后该目录为空 → 初始化失败并各记一条。证据两条：

1. 写入 `/etc/sasl2/sasl2.conf`（全局名）后重跑 dnf，两条照旧出现。
   按 appname 取配置的实现不读全局文件，这条路走不通。
2. 移除 `/usr/lib64/sasl2/libldapdb.so*` 三条文件后重跑同一命令，
   `canonuser_plug_init` 计数由 **1 → 0**；恢复后由 **0 → 1**。

归属与删除边界：插件由 `cyrus-sasl-2.1.28-12.oe2403sp3` 提供（不是
`cyrus-sasl-lib`），`rpm -q --whatrequires cyrus-sasl` 在整机上无输出，
即镜像里没有任何东西需要这个纯服务端插件包。修法因此不是删文件，而是
**装配期不装这个包**：桌面形态没有 LDAP/Kerberos 认证后端，某插件无法
初始化却每次初始化都留两条 `auth.err`，本身就是交付面缺陷。落地判据三条：
`rpm -q cyrus-sasl` 非零、`/usr/lib64/libsasl2.so.3` 仍在、复跑 dnf 时
`canonuser_plug_init` 计数为 0。

**dhclient `Invalid domain name.`（待取证）。** 当前有 2 条，说明 DHCP
服务器下发的 `domain-name` 选项畸形（空标签或裸尾点），客户端按 RFC 拒绝
并记一行。定性需要抓一次 DHCP 交互报文，本次未做，登记为待取证，不凭
表象加客户端豁免。

    只有 6.6.157 内核、`sda3` 为 15.6 G swap，其后 40 G 未分区，无
    `LiveOS`/squashfs/`.treeinfo`）。整装验证要由流水线产出的 product ISO
    重做，不能用这块盘现有内容。
