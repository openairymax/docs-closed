## 0. 结论先行

1. **第一性问题不是慢，是不可归因。** 四次烧穿预算（run `40997227280` 240 分钟、
   `41023530128` 120 分钟被取消、`40866231339` >135 分钟、`41090215913` BIOS 腿
   4124 秒）都伴随同一形态：界面上只有一行总耗时，看不出停在哪一段。
2. **瓶颈已经迁移。** 10-29 的结论是「慢的不是构建，是取包」（构建段 14 → 38.9
   分钟全由闭包下载支配）；缓存落地后，本轮 `41155718658` 的 assemble 605 秒里，
   **固定开销 342 秒（57%）**、取数 95 秒（16%）、真正的组装 160 秒（27%）。
   继续只盯着取包，最多再省 16%。
3. **治理的抓手不是文档，是执行者。** 78 段内联 shell、恒不触发的 `sc-verify`、
   `kernel/**` 死判据、`ubuntu-latest` 回潮——共同点是「写下来的规则没有检查者」。
   量化现状：README 声明 13 行约定，执行者覆盖 10 行，**3 行无执行者**；
   README 写「规则 1–11」，脚本实为 12 条。
4. **供应链是唯一未经审查就能改变流水线行为的入口。** 8 条 workflow 共
   **40 处 `uses:`，全部是浮动 tag**（`@v4` / `@v1` / `@v0`），钉 SHA 数为 0。
5. **提速的单位不是「每版一个 delta 层」，是「内容寻址候选池」+「固定摘要的基础介质」。**
6. **「基础 + 中间 + 增量」已经采纳**，但「增量」的口径是「本轮 dnf 求解后还缺哪些包」，
   不是「两版发布物差哪些包」。
7. **分层构建（ostree / 分层 rootfs）不是 0.0.x 的提速手段**，是 0.1.x 自有基底的事。
8. **accept 三条腿保留串行**：并行只省约 8 分钟，代价是两份 QEMU 各 145 秒 +
   抢 4 核 + 「两条腿一起坏」的归因退化。
9. **「ISO 构建不超过 1 小时」成立的前提是 L2 的 `seed-` 通道**：装机段固定约
   26 分钟，缓存命中 10+26=36 分钟达标，冷启动 40+26=66 分钟必然超标。
10. **指标与天花板必须分离**：`timeout` 只杀卡死进程，达标看整链秒数。

## 1. 方法论

### 1.1 证据分级

本文件每条结论都标注证据级别，避免把推测写成事实：

| 级别 | 含义 | 例 |
|---|---|---|
| **E1** | 本轮或近期流水线的实测数据（API `jobs` 的 step 起止时间、制品内的 manifest） | assemble 605 秒、构建段 160 秒 |
| **E2** | 历史日志中的单点观测 | run `41090215913` BIOS 腿 4124 秒 |
| **E3** | 代码与配置的静态事实（可被任何人 `grep` 复算） | 40 处未钉 SHA、14×24.04 + 1×22.04 |
| **E4** | 推导与经验，尚未被测量 | 「free-disk 可省去 80 秒」 |

E4 条目全部集中在 §12「待证伪清单」，不得作为施工依据直接落地——先补测量，
再改代码。这条纪律直接对应用户要求「出现问题不能靠猜」。

### 1.2 样本量与口径

- assemble 的耗时样本：run `41090215913` 586 秒、`41155718658` 605 秒，**n=2**。
  因此本文件只谈「量级」与「构成占比」，**不声称 P95**，也不把 ±3.2% 的差异
  解释为性能回归。
- accept 的成功单腿样本：**n=1**（UEFI/USB 505 秒）。三条腿的成本按同量级推导，
  E1/E4 混合，须在下一轮补齐后改写。
- 字节量口径：闭包 ≈2.5 GB RPM；介质下载量 3.2 GiB（`image-build.yml` 注释）。

## 2. 历史卡点复盘

四张表，按「流水线形态 / 缓存与取数 / 判定与归因 / 交付与发布」分组。
每行必须能答出**拦截点**——没有被拦截的条目，就是本方案的施工项。

### 2.1 形态类：结构缺陷

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| 8 条 workflow 里曾有 **78 段内联 `run: \|`** | 每段单看都合理，合起来无人能在本地验证 | 逻辑下沉 `ci/gates/*.sh`（现 41 个 gate / 4550 行），预算内联归零 | 规则 1/2/3 + `workflow-budgets.txt` 棘轮 |
| `sc-verify` **恒不触发** | paths 全在 kernel gitlink 内部，父仓 diff 只呈现目录名 | 删除整条 workflow | 规则 11 |
| 四条几乎相同的 `python-verify --kind abi/codegen/dsl/farm` 薄壳 | 按目录枚举而不是按受检对象划分 | 并入 `os-chk-verify` 单 job，一次依赖安装、一次 pytest 扫全量 | 规则 1 + 预算表 |
| `ssot-verify` 的 PR 判据不是 push 判据的子集 | PR 侧多出的路径合并后不再被校验 | 判据对齐 | 规则 10 |
| `kernel-verify` 写 `kernel/**` | 同 `sc-verify` | 改为 `kernel` | 规则 11 |
| job 无 `timeout-minutes` | 默认 360 分钟被当成「不用管」 | 逐个补上，step 时限 < job 时限 | 规则 8 |
| 无 `concurrency:` | 旧 run 与新 HEAD 抢并发额度，排障读错日志 | PR 触发一律 `cancel-in-progress: true` | 规则 9 |
| 无顶层 `permissions:` | 令牌权限随仓库设置漂移 | 显式最小集 | 规则 7 |
| 四处各写 `apt-get` 与超时 | 网络卡死时一步烧光预算 | 收进 `ci/lib/apt.sh` | 规则 4 |
| gate 调用未 source 的 `need_cmd`，前置校验静默失效 | 四个 gate 没 source `host.sh` | 统一 source | 规则 6（run `40478538815`） |
| gate 名写错 / 缺 `# 用法:`，checkout 与预热后才 exit 2 | 分发器按文件名解析 | 补头注释 | 规则 12 |
| `ubuntu-latest` 浮动 | 标签一动，编译器 / shellcheck / Python 全变 | 固定 `ubuntu-24.04`（现 14 处） | **无执行者** → CI-13 |
| 唯一残留 `ubuntu-22.04`（`os-chk-verify`） | 理由成立（shellcheck 基线），但无机器校验 | 注释已写明 | **无执行者** → CI-13 |
| `nightly` 契约清单仍写 `ubuntu-latest` | 同一事实两处声明 | `896dd58` 手工对齐 | CI-09（生成器 / 交叉断言） |
| 门禁由标签形状推语义：`label.endswith("-latest")` | 换标签后上限断言静默失效，4320 分钟被判通过 | `5db52d4` 改读显式字段 | CI-10 + 规则 |

**这一组的结论**：15 行里 11 行已有执行者，剩下的 3 行（runner 固定、`-verify`
后缀语义、生命周期命名）只写在 `README.md` 的表里。而 README 说「规则 1–11」，
脚本实为 12 条——**文档与执行者已经漂移**。按项目自己的判据「没有被检查的约定
不是约定」，这三行要么补执行者，要么从文档删除，不允许长期挂空。

### 2.2 缓存类：把「快」当成「对」

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| 越慢越容易被取消，取消后缓存永不落盘，下一轮更慢 | `actions/cache` 保存挂在 job 成功态上（run `40997227280`） | 显式 `cache/save` + `always()` | workflow 注释 + `if:` |
| 固定键让半份池被永久固化；纯 `run_id` 键则 10 GiB 只够三轮 | 键不可变，两端都会出错 | 键 = 闭包定义摘要 + 池内容摘要 | `ci/gates/pool-state.sh` |
| 早退轮次把**空池**钉在 `restore-keys` 前缀最新位置（run `41056762297`） | 保存判据是「目录存在」 | `count == 0` 不保存 | `poolstate.outputs.count != '0'` |
| 缓存 564 MiB、制品 2321.7 MiB、**播种 0 秒**，构建段 40 分钟仍在拉包（run `41075519752`） | 以「目录非空」判完整，半份池同样非空 | 以池内**完成标记**为判据 | `ci/gates/pool-seed.sh` |
| 介质下载先下的大件把后一项挤成零头（run `40485745100`） | 只有总预算，无单件下限 | 总预算 5400 秒 + 每件保底 900 秒 | `media-fetch.sh --budget --floor` |
| 官方源跨洋链路整段停滞 55 分钟（run `39543892713`） | 单一来源 | 摘要白名单 + 国内镜像等价回退 | `distro/repo/mirrors.list` 唯一声明处 |
| 镜像站限速到 **29 KiB/s**（run `41023530128`，120 分钟被取消） | 取包是外部变量 | 180 分钟组装预算的依据；根治靠候选池 | 预算注释 + CI-11 |

**结论**：所有事故都不是「缓存不好用」，而是**把缓存的可用性当成了正确性**。
提速设计 §4 的六条硬约束就是这七行沉淀出的判据，任何新增加速手段必须先满足
它们才能合并。

### 2.3 判定与归因类：卡点必须落到步骤级

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| 三步合成一步，只有一行总耗时；CD-ROM 腿 70 分钟不知停在哪条（run `41121955316`） | Actions 只报 step 总耗时 | assemble 拆「预热 / 组装 / 收尾」，accept 按腿逐步 | 步骤名即结论；`run-<fw>-<n>` 互不覆盖 |
| job 超时是**强制取消**，取消态下 `if: failure()` 与 `if: always()` 都不执行 | 只设了 job 时限 | step 时限 < job 时限（75+180<300；三腿 240<360） | `image-build.yml` 逐条注释 |
| BIOS 腿 4124 秒一寸未进（run `41090215913`） | `isolinux.cfg` 的 `append` 缺 `console=ttyS0`，串口零字节 | `cfg_brand.py` 的 `i_serial_all` 补 `console=tty0 console=ttyS0,115200` | 串口标记 + TAP |
| 静态门禁排在 `free-disk` 之后，坏树能烧 240 分钟 | 成本排序错：最便宜的判据放在最贵动作之后 | `Static gates` 前移 | CI-06（`c905667`） |
| `release_tag` 写错要等 75 分钟预热才暴露 | 同上 | `Fetch release kernel RPMs` 前移 | 一分钟内失败 |
| 把「静态门禁跑了 5 分钟」当成卡死 | 没先取时间戳；实测 01:32:38→01:34:31 = **1 分 53 秒** | 先取时间戳再决定是否取消 | §1.1 观察纪律 |
| ISO 自己再编一次内核，载荷包与发行 `.sha256sum` 哈希分叉 | 内核有两条构建路径 | `release_tag` 非空时只下载 + 校验 | `ci/ci.sh release-rpms` |
| 给出 `if:` 表达式后 Actions 不再套用默认 `success()` | 语义盲区 | 显式写 `success() && …` | 发布步骤条件 |

**结论**：归因能力是设计出来的，不是事后翻日志翻出来的。三条硬要求：
①最便宜的判据先跑；②步骤边界 = 归因边界；③任何 `if:` 都显式写 `success()`。

### 2.4 交付与发布类

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| ISO 在 assemble 之后发布，等于把未经冷启动验证的字节挂成发行物 | 发布点画错 | 移到 accept 三腿全绿之后 | `if: success() && !inputs.acceptance` |
| 同 tag 重建会静默覆盖既有发行物 | 幂等判据不清 | 幂等 =（tag, digest）；覆盖只由 `replace: true` 开启 | `iso-publish --force` |
| 在陈旧 HEAD（`1ddc0d23`）上出过一版镜像（run `40834119367`） | dispatch 前不核对三远程 sha | 前置 gate 比对 `head_sha` 与 atomgit 分支 | CI-07（未落地） |
| 装机后无法回答「这是哪个 commit 产出的」 | 无 `BUILD_ID`、无 `/etc/airymaxos-build` | 组装期写入 + `%check` 断言 | REL-03（未落地） |
| 用验证机「先跑一下看看」 | 把 B50 当验收环境 | 铁律 8：一切集成先过流水线；B50 只是验证机 | 发布手册 |

### 2.5 分类学：五类根因与通用拦截

上面四张表可以收敛成五类根因。治理规则不针对单次事故，而是针对这五类：

| 类 | 表现 | 通用拦截 | 已落地 |
|---|---|---|---|
| A 无执行者 | 规则写在文档里，没人检查 | 规则必须有脚本、预算必须有棘轮 | 部分（3 行缺口） |

### 3.2 构成与瓶颈迁移

| 归类 | 秒 | 占比 | 说明 |
|---|---|---|---|
| 固定开销（checkout / 静态门禁 / 清盘 / 上传） | 342 | **57%** | 与载荷多少无关，每轮必付 |

对照 10-29 的定性（构建段 14 → 38.9 分钟，差异全在闭包下载）可以得出本轮最重要的
判断：**缓存把「取包」从支配项压到 16%，瓶颈已经迁到固定开销。** 这解释了为什么
「再优化闭包」收益有限，也解释了为什么 β 轮的绝对耗时（605 秒）与 10-30 基线
（586 秒）几乎持平——前者省下的是取数，后者从未被治理。

### 3.3 Amdahl：优化上限

以 605 秒为基数，各段的理论上限：

| 措施 | 现状 | 乐观终值 | 节省 | 相对整段 |
|---|---|---|---|---|
| checkout 改为稀疏/浅取（assemble 只需要 `distro`） | 90 | 25 | 65 | 10.7% |
| 静态门禁内部分段，去掉与 `os-chk-verify` 重复的 626 条工具用例 | 113 | 45 | 68 | 11.2% |
| free-disk 按实测需求裁剪 | 96 | 20 | 76 | 12.6% |
| 上传（压缩 0 已开，只能减量） | 42 | 42 | 0 | 0 |
| 组装再快一倍（不现实） | 160 | 80 | 80 | 13.2% |
| 取数全部归零（完美缓存） | 95 | 0 | 95 | 15.7% |

读法：**三项固定开销治理合计可省 209 秒（34.5%），比「组装再快一倍 + 取数归零」
（28.9%）还多。** 这正是「治理」与「提速」在本项目里是同一件事的量化依据。
上表三行均为 E4，必须先测量（§12）再落地。

## 4. 成本模型与敏感性（E4 推导，输入为 E1/E2/E3）

### 4.1 取包：时间由速率决定，不由代码决定

闭包 2.5 GB 在不同链路上的理论耗时：

| 链路速率 | 耗时 | 对应历史 |
|---|---|---|
| 29 KiB/s | ≈24 小时 | run `41023530128`（120 分钟取消） |
| 16–22 KiB/s | 33–45 小时 | 托管 runner 到国内镜像的实测区间 |
| 100 KiB/s | ≈7 小时 | |
| 1 MB/s | ≈42 分钟 | 接近 3.2 GiB 介质 43 分钟的下行速率 |
| 6–7 MB/s | ≈6–7 分钟 | 国内验证机实测（`closure-pool.sh` 播种） |

**结论**：这条链路的方差跨三个数量级，任何以「平均速率」为前提的预算都会失效；
唯一稳定的办法是把字节搬到可达路径上（候选池 / `seed-` 层），而不是加预算。

### 4.2 磁盘峰值

介质 3.2 GiB + 候选池 2.5 GB + 载荷与中间件 3 GB + ISO 3.7 GB ≈ **12.4 GB**
（提速设计 §4.6 记 10.3 GB，差异来自是否计入容器 tar；施工时以 `df` 实测为准）。
这是 free-disk 步骤的存在理由，也是它的优化边界（§3.3）。

### 4.3 「≤1 小时」的可行域

```
装机段固定成本 ≈ 505 + 520 + 520 = 26 min
缓存命中轮     = 10 + 26 = 36 min   ✓
冷启动轮       = 40 + 26 = 66 min   ✗
```

要在冷轮达标，组装段必须 ≤30 分钟。`actions/cache` 做不到——缓存条目 7 天未用即
失效，而「很久没构建」恰恰是最需要它的那一轮。唯一解是 L2 的 `seed-` 通道：
每小时探针（<50 KB）判断上游是否变化，变了才推层；构建侧先按 `input_key` 找
`seed-`，取不到回落 `actions/cache`，最后才全量收割。**预热挂掉最多多花一次取层
时间，不会退回公网，也不阻断发布。**

## 6. 候选方案研究与取舍（ADR）

对每个「行业上常见」的做法给出采纳与否，以及**量化理由**——不采纳也要写清代价，
避免下一轮有人重新提议。

| # | 候选 | 判定 | 理由 |
|---|---|---|---|
| 1 | **Reusable workflow**（`workflow_call`）去重 8 条 workflow 的公共段 | 不采纳 | 当前已无重复逻辑：内联块 0，公共段只剩 checkout + gate 调用两行；抽象后定位失败要多跳一层文件，违背「步骤边界=归因边界」 |
| 2 | **Composite action** 承载公共步骤 | 不采纳（同上） | 与 1 同因；且 composite 里的失败在 UI 上折成一行，直接损失归因 |
| 3 | **accept 三腿 matrix 并行** | 不采纳 | 只省 ≈8 分钟；代价是两份 QEMU 各 145 秒 + 抢 4 核 + 归因退化 |
| 4 | **自建常驻 runner** | 不采纳 | 与「标准环境可复现」直接冲突；托管 runner 的形态变化（是否给 `/dev/kvm`）本身就是必须被覆盖的变量 |
| 5 | **Bazel / Nix 式全量内容寻址** | 部分采纳 | 采纳其**思想**（键来自内容、缓存只给字节）；不引入工具链——本项目产物是 ISO，不是可增量链接的树，引入构建系统是把复杂度从流水线搬到别处 |
| 6 | **docker buildx 多层镜像缓存** | 不采纳（0.0.x） | 构建在容器里跑，但产物是 ISO；镜像层缓存解决的是「镜像构建慢」，与本项目瓶颈（固定开销 + 取包）不对应 |
| 7 | **内核编译 ccache** | 已在用 | `kernel-verify` / `airy-verify` 已接 `ccache-action`；image-build 走发行 RPM 复用，不需要 |
| 8 | **稀疏/浅取 checkout** | **采纳（快赢 W-1）** | assemble 只需要 `distro`，却做了 9 个子模块递归取：90 秒 → 估 25 秒 |
| 9 | **预烘 builder 镜像** | 维持 P2 | 工具链 34 秒（本轮），收益 < 维护成本（CI-04 已降级） |
| 10 | **SLSA provenance / attestation** | 采纳（CI-17） | ISO 已发 ghcr 却无来源证明；与 REL-03 的 `BUILD_ID` 同批落地，成本低 |

## 8. 实施顺序

每一步**单独 commit + 单独一次绿跑**，不得批量迁移后一次性验收（沿用 CI-05 口径）。

| 序 | 动作 | 判据 | 依赖 |
|---|---|---|---|
| W-1 | 稀疏/浅取 checkout（assemble 只初始化 `distro`） | assemble 的 checkout 段 ≤30 秒；T-GOV-1 仍绿 | 无 |
| W-2 | 静态门禁分段计时，识别 626 条工具用例占比 | 输出 `[timing] syntax/spec/comps/ks/preset/tests` 六行 | 无 |
| W-3 | free-disk 实测收益（`df` 前后对照） | 有前后差值，才允许裁剪 | 无 |
| 1 | **CI-13** 补规则 13/14/15，README 规则表改由脚本校验 | 加 `ubuntu-latest` 必红；改 README 规则行必红 | 无 |
| 2 | **CI-14** `uses:` 钉 40 位 SHA | 存在浮动 tag 必红 | 无 |
| 3 | **CI-15** `ci/gates/evidence.sh` 统一证据包 | 人为让 accept 失败，四件套齐全 | 无 |
| 4 | **CI-08** 段耗时 + `AIRY-BUILD-DRIFT` 进 manifest | 连跑两轮，超 2× 基线有标记 | 无 |
| 5 | **CI-07** dispatch 前比对三远程 sha | 构造陈旧 HEAD 必红 | 无 |
| 6 | **CI-16** 依 W-1~W-3 的实测落地削减固定开销 | assemble ≤360 秒 | W-1~W-3 |
| 7 | **CI-11 L1-a** 候选池抽象 + 校验 + 显式回退 | T-PAY-1/3/4/6 | 提速设计 §5 |
| 8 | **CI-11 L1-b** 接 `actions/cache`，两段式键 | T-PAY-2/7 | 7 |
| 9 | **CI-11 L2** `payload-publish`（先只 push）+ `payload-seed.yml` | T-PAY-5/8/9 | 8 |
| 10 | **CI-17** attestation + `BUILD_ID` 关联 | `oras manifest fetch` 可见证明；装机可反查 | REL-03 |

W-1~W-3 与 1–5 不改变产物字节，是纯治理与观测，可并行；6 依赖 W 的测量结果；
7–9 必须串行（每层没有上一层就无法验证「回退是否真的回退」）。
