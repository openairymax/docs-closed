## 0. 结论先行

1. **第一性问题不是慢，是不可归因。** 四次烧穿预算（run `40997227280` 240 分钟、
   `41023530128` 120 分钟被取消、`40866231339` >135 分钟、`41090215913` BIOS 腿
   4124 秒）都伴随同一形态：界面上只有一行总耗时，看不出停在哪一段。
2. **治理的抓手不是文档，是执行者。** 78 段内联 shell、恒不触发的 `sc-verify`、
   `kernel/**` 死判据、`ubuntu-latest` 回潮、唯一残留的 22.04——共同点是
   「写下来的规则没有检查者」。`ci/check-workflows.py` 头注释自己写了这句话：
   *「这些约束此前只存在于文档里，没有执行者」*。
3. **提速的单位不是「每版一个 delta 层」，是「内容寻址候选池」+「固定摘要的基础介质」。**
   论证见提速设计 §2，本文件只做形态判定（§3.1）。
4. **「基础 + 中间 + 增量」已经采纳**，但「增量」的口径是「本轮 dnf 求解后还缺哪些包」，
   不是「两版发布物差哪些包」。前者只需一张 sha256 表，后者要做层序与回滚。
5. **分层构建（ostree / 分层 rootfs）不是 0.0.x 的提速手段**，是 0.1.x 自有基底的事。
6. **顺序优化已有结论**：accept 三条腿保留串行。改 matrix 只省约 8 分钟，代价是
   QEMU 环境重复准备（各 145 秒）与「两条腿一起坏」的归因退化。
7. **「ISO 构建不超过 1 小时」成立的前提是 L2 的 `seed-` 通道。** 装机段固定约
   26 分钟；组装段缓存命中 10 分钟（合计 36 分钟达标），冷启动 40 分钟量级
   （合计 66 分钟超标）。不接 L2，这条指标在冷轮上必然失守。

## 1. 历史卡点复盘

四张表，按「流水线形态 / 缓存与取数 / 判定与归因 / 交付与发布」分组。每行必须能答出
**拦截点**——没有被拦截的条目，就是本方案的施工项。

### 1.1 形态类：结构缺陷

| 现象 | 根因 | 处置 | 拦截点 |

| `nightly` 契约清单仍写 `ubuntu-latest`，与 workflow 冲突 | 同一事实两处声明，无交叉断言 | `896dd58` 手工对齐 | CI-09（生成器 / 交叉断言） |

**这一组的结论**：14 行里有 11 行已经长出了执行者，剩下的 3 行（runner 固定、

不允许长期挂空。

### 1.2 缓存类：把「快」当成「对」

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| 越慢越容易被取消，取消后缓存永不落盘，下一轮更慢（自锁环） | `actions/cache` 的保存挂在 job 成功态上，run `40997227280` 被取消即丢 | 改为显式 `cache/save` + `always()`，与 job 成功态解耦 | `image-build.yml` step 注释 + `if: always()` |
| 固定键让「第一轮超时留下的半份池」被永久固化 | 键不可变，半份池一旦落盘就是该键的唯一内容 | 键 = 闭包定义摘要 + **池内容摘要**（`pool-state.sh`） | `ci/gates/pool-state.sh` |
| 改用纯 `run_id` 键则每轮一份完整副本，10 GiB 配额只够三轮 | 同上，另一端的错 | 同上（两段式键） | 同上 |
| 早退轮次把**空池**钉在 `restore-keys` 前缀最新位置，后续每轮从零开始（run `41056762297`） | 保存判据是「目录存在」而不是「池非空」 | `count == 0` 不保存 | `steps.poolstate.outputs.count != '0'` |
| 缓存 564 MiB、制品 2321.7 MiB，**播种 0 秒**，构建段 40 分钟仍在拉包（run `41075519752`） | 以「目录非空」判完整，中断轮次的半份池同样非空 | 以池内**完成标记**为判据 | `ci/gates/pool-seed.sh` |
| 介质下载先下的大件把后一项挤成零头（run `40485745100`） | 只有一个总预算，没有单件下限 | 总预算 5400 秒 + 每件保底 900 秒 | `ci/gates/media-fetch.sh --budget --floor` |
| 官方源跨洋链路整段停滞 55 分钟（run `39543892713`） | 单一来源 | 摘要白名单 + 国内镜像等价回退，摘要不符即弃 | `distro/repo/mirrors.list` 为唯一声明处 |
| 镜像站限速到 **29 KiB/s**（run `41023530128`，120 分钟被取消） | 取包时间是外部变量 | 组装段 180 分钟预算的依据；根治靠候选池（CI-11） | 预算注释 + CI-11 |

**这一组的结论**：所有事故都不是「缓存不好用」，而是**把缓存的可用性当成了正确性**。
提速设计 §4 的六条硬约束（缓存只给字节、元数据每轮新鲜、两种不一致语义分离、
回退显式、冷启动劣化 ≤5%、磁盘预算 10.3 GB）就是这四张表沉淀出来的判据，
任何新增加速手段必须先满足它们才能合并。

### 1.3 判定与归因类：卡点必须落到步骤级

| 现象 | 根因 | 处置 | 拦截点 |
|---|---|---|---|
| 三步合成一步，界面只有一行总耗时；CD-ROM 腿跑 70 分钟无法判断停在哪一条（run `41121955316`） | Actions 只报 step 总耗时 | assemble 拆「预热 / 组装 / 收尾」，accept 按腿逐步 | 步骤名即结论；`run-<fw>-<n>` 目录互不覆盖 |
| job 超时是**强制取消**，取消态下 `if: failure()` 的 log-dump 与 `if: always()` 的上传都不执行 | 只设了 job 时限，没有 step 时限 | step 时限 < job 时限（75+180 < 300；三腿 240 < 360） | `image-build.yml` 注释逐条写明依据 |
| BIOS 腿 4124 秒一寸未进（run `41090215913`） | `isolinux.cfg` 的 `append` 缺 `console=ttyS0`，串口日志零字节，门禁只能等到 3600 秒超时 | `cfg_brand.py` 的 `i_serial_all` 给所有 `append` 行补 `console=tty0 console=ttyS0,115200` | 串口标记 + TAP |
| 静态门禁排在 `free-disk` 之后，坏树照样能烧 240 分钟 | 成本排序错：最便宜的判据放在最贵动作之后 | `Static gates` 前移到 checkout 之后 | CI-06（已收口，`c905667`） |
| `release_tag` 写错 / 资产缺失 / 摘要不符，要等 75 分钟工具链预热完才暴露 | 同上 | `Fetch release kernel RPMs` 前移到整链最前 | 一分钟内失败 |
| 把「静态门禁跑了 5 分钟」当成卡死 | 没先取时间戳就下判断；实测 01:32:38 起跑、01:34:31 结束 = **1 分 53 秒** | 先取 `date -u` 与 step 起止时间，再决定是否取消 | 本文件 §2.3 的观察纪律 |
| ISO 自己再编一次内核，导致载荷中同名包与发行 `.sha256sum` 哈希分叉 | 内核有两条构建路径 | `release_tag` 非空时只下载 + 校验发行资产，不重建 | `ci/ci.sh release-rpms` |
| 门禁在串口零字节的情况下仍等满 3600 秒 | 判据是「等到标记」而不是「串口是否还活着」 | 心跳行 + 无输出超时 | `airy-record` / TAP 心跳 |

**这一组的结论**：归因能力是设计出来的，不是事后翻日志翻出来的。三条硬要求：
①**最便宜的判据先跑**；②**步骤边界 = 归因边界**（合成一步就只能得到一个总耗时）；
③**任何 `if:` 表达式都要显式写 `success()`**——给出 `if` 之后 Actions 不再套用默认
`success()`，`Publish ISO to ghcr.io` 曾因此会在装机失败时放行。

## 2. 治理规则

### 2.1 规则必须有执行者：现状对账

`README.md` 的命名与结构表有 13 行，`ci/check-workflows.py` 有 12 条规则，两者**不是
一一对应**，且 README 正文写的是「rules 1–11」。逐行对账：

| README 声明 | 执行者 | 状态 |
|---|---|---|
| 文件名 kebab-case | 规则 5 | 有 |
| `name:` 等于文件主干 | 规则 5 | 有 |
| 每 workflow ≤2 job | 规则 1 | 有 |
| 内联 `run` 预算 + 棘轮 | 规则 1/2 | 有 |
| YAML 是薄壳（禁已收编逻辑回流） | 规则 3 + `ALWAYS_FORBIDDEN` | 有 |
| 顶层显式 `permissions:` | 规则 7 | 有 |
| `concurrency:` + `cancel-in-progress: true` | 规则 9 | 有 |
| 每个 job 有 `timeout-minutes:` | 规则 8 | 有 |
| `pull_request` paths ⊆ `push` paths | 规则 10 | 有 |
| gitlink 只列目录名 | 规则 11 | 有 |
| 禁直接 `apt-get` | 规则 4 | 有 |
| 引用的 gate 存在且带 `# 用法:` | 规则 12 | 有 |
| **runner 固定（禁 `ubuntu-latest`）** | — | **无** |
| **`-verify` 后缀只给门禁** | — | **无** |
| **生命周期名 `image-build` / `nightly` / `release`** | — | **无** |

三条无执行者的规则，正好对应三类真实事故：`ubuntu-latest` 漂移（CI-09 的起因）、
`sc-verify` 混在门禁命名里却永不触发、以及生命周期 workflow 被当成门禁加 `-verify`。
**CI-13**：补规则 13（runner 白名单：只允许 `ubuntu-24.04`，例外必须写
`# runner-exception: <理由>` 且被单独列出）、规则 14（生命周期名白名单）、
规则 15（`-verify` 后缀与「是否 PR 门禁」一致）；同时把 README 的规则表改为
**由脚本生成或校验**，从根上消灭「文档说有 11 条、脚本有 12 条」这类漂移。

### 2.2 供应链：action 引用必须钉 SHA

8 条 workflow 目前全部用浮动 tag（`actions/checkout@v4`、`actions/cache@v4`、
`actions/upload-artifact@v4`、`oras-project/setup-oras@v1` 等）。tag 可被上游重指，
这是本项目唯一一条**未经审查就能改变流水线行为**的入口。行业做法（GitHub
官方 *Security hardening for GitHub Actions*）是钉 40 位 commit SHA + 由
Dependabot/Renovate 提 PR 升级。**CI-14**：规则 16 校验 `uses:` 必须为
`owner/repo@<40 hex>`；升级走 PR，diff 里能看见 SHA 变化。

### 2.3 失败归因纪律（对应「不能靠猜」）

1. **三问先行**：哪条腿 / 哪一步 / 最后一条 `AIRY-*` 标记是什么。答不出就不许重跑。
2. **先取时间戳**：用 step 的 `started_at` 与日志首末行，判断「慢」还是「死」。
   本项目已经发生过一次把 1 分 53 秒读成 5 分钟的误判。
3. **重跑不是诊断**：重跑只用于「已定位的偶发外部故障」，且必须记录前一次的失败点；
   否则等于用一次新样本覆盖掉唯一证据。
4. **取消态没有证据**：job 级超时是强制取消，`if: failure()` 与 `if: always()` 都不执行。
   因此**任何可能长跑的步骤必须先有 step 时限**，让「失败」发生在「取消」之前。
5. **证据包**：失败必须产出可离线复现的四件套——`tap.txt`、串口日志、`*-manifest.txt`、
   构建日志。**CI-15**：新增 `ci/gates/evidence.sh`，在 `always()` 上统一打包，
   替代当前逐段手写 upload 清单（现在两份 upload 的 glob 已经开始不一致）。

### 2.4 观测：指标进 manifest，不进记忆

- 每个 job 的段耗时写进 `build-manifest.txt` 与 step summary（CI-08）；
- 超基线 2 倍打 `AIRY-BUILD-DRIFT`（不失败，但必须在界面上看得见）；
- 命中率、`mode=link|copy`、字节来源分布（cache / ghcr / upstream）同表记录——
  否则「这轮快」永远无法区分是缓存生效还是上游恰好快。

## 3. 提速：形态选择与达标算式

### 3.1 用户提的三种形态，逐个判定

| 形态 | 判定 | 理由 | 落点 |
|---|---|---|---|
| **基础 + 中间 + 增量** | **采纳**（但「增量」换口径） | 增量若按「两版发布物之差」算，需要已知上一版的层序，且差集只有求解后才知道；按「本轮求解后缺哪些包」算，等价且只需一张 sha256 表 | 基础 = 固定介质；中间 = 工具链 + 候选池；增量 = 每轮补差 |
| **直接分层构建**（ostree / 分层 rootfs） | **不做（0.0.x）** | 分层服务的是**分发与原子回滚**，不是构建耗时；0.0.x 没有回滚语义 | 0.1.x 自有基底 |
| **按顺序进行**（串联分阶段） | **已是现状，继续** | accept 三腿串行已有论证：并行只省约 8 分钟，代价是两份 QEMU 各 145 秒 + 抢 4 核 + 归因退化 | `image-build.yml` accept 三腿 |

**一句话**：用户提的三种里，第一种被采纳但把「增量」的定义从「版本差」改成了
「求解差」；第二种属于 0.1.x；第三种已经在做，且有实测支撑不再改。

### 3.2 三段式在流水线上的具体映射

| 段 | 内容 | 键 / 判据 | 现状 |
|---|---|---|---|
| 基础 | openEuler netinst ISO + docker_img tar（3.2 GiB，跨轮不变） | 两个 sha256 写死在 workflow `env`，缓存键即摘要 | **已落** |
| 中间 | ① 工具链 dnf 缓存（231 包 / 256 MB）② 闭包候选池（≈2.5 GB / 1000+ RPM） | ① `build-packages.txt` 摘要 ② 闭包定义摘要 + 池内容摘要 | ① **已落**（`c335647`）② **施工中**（CI-11 / L1） |
| 增量 | 本轮求解后仍缺的包 + 每轮必须新鲜的 `repodata` | `payload-manifest.txt` 逐包 sha256 | 待 L1/L2 |

关键约束（转录自提速设计 §4，实施时不得放宽）：缓存只提供字节；`repodata` 每轮
新鲜下载；候选池不符 → 丢弃重下，重下仍不符 → `AIRY-PAYLOAD-DRIFT` 硬失败；
回退必须打印固定行；冷启动劣化 ≤5%；峰值磁盘 ≈10.3 GB。

### 3.3 耗时台账（当前唯一可信基线）

| 段 | 实测 | 来源 |
|---|---|---|
| assemble 全 job（缓存命中） | **586 s** | run `41090215913` |
| ├ checkout / 静态门禁 / 清盘 | 91 + 120 + 94 s | 同上 |
| ├ warm / 池恢复 / 组装 / 上传 | 35 + 14 + 173 + 27 s | 同上 |
| accept 全 job | **4855 s** | 同上 |
| ├ UEFI + USB 腿（成功） | **505 s** | 同上 |
| └ BIOS + CD-ROM 腿（失败，撞满 3600 s 装机上限） | 4124 s | 同上 |
| 单腿真实成本（装机 + 冷启动） | ≈505 s，另两条 CD-ROM 腿 ≈520 s 量级 | 推导自同一轮 |

### 3.4 指标（SLO）与天花板分离

| 段 | 指标 | 天花板（`timeout-minutes`） | 判定 |
|---|---|---|---|
| assemble（缓存命中） | ≤900 s | 300 | 超 2× 基线打 `AIRY-BUILD-DRIFT` |
| assemble（冷启动） | ≤1800 s（L2 落地后） | 300 | 30 分钟未进组装段即打标 |
| accept 全 job | ≤2100 s（三腿） | 360 | 单腿 80 分钟 step 时限 |
| **整链** | **≤3600 s** | — | 唯一对外口径 |

天花板的数值不动（300 / 360 是发布级例外），改变的是**判读方式**：从此「绿」
必须附带段耗时，只有整链 ≤60 分钟才算达标。这一步不新增任何流水线，只增加记录与标记。

### 3.5 为什么 L2 是「≤1 小时」的前提，而不是可选项

```
装机段固定成本 = 505 (UEFI/USB) + ~520 (BIOS/CDROM) + ~520 (UEFI/CDROM) ≈ 26 min
缓存命中轮     = 10 + 26 = 36 min   ✓
冷启动轮       = 40 + 26 = 66 min   ✗
```

要在冷轮上也 ≤60 分钟，组装段必须从 40 分钟压到 ≤30 分钟。L1（`actions/cache`）
做不到——缓存条目 7 天未用即失效，而「很久没构建」恰恰是最需要它的那一轮。
唯一解是 L2 的 `seed-` 通道：由每小时探针（<50 KB）判断上游是否变化，变了才推层，
构建侧先按 `input_key` 找 `seed-`，取不到再回落 `actions/cache`，最后才全量收割。
**预热挂掉最多多花一次取层时间，不会退回公网，也不会阻断发布。**

### 3.6 明确不做（与提速设计 §9 对齐）

- 不做「每版一个 delta 层」（复杂度高一个数量级，收益等价）；
- 不做整站镜像上游仓库（数十 GB 换不来任何东西，还背上镜像站责任）；
- 不做 `mkksiso` 阶段压缩调优（该段 I/O 绑定，RPM 已压缩）；
- 不做 ostree（0.0.x 无原子回滚语义）；
- 不缓存仓库元数据（唯一会把错误带进产物的路径）；
- 不自建常驻 runner（运维面与「标准环境」的可复现性直接冲突）。

## 4. 实施顺序

每一步**单独 commit + 单独一次绿跑**，不得批量迁移后一次性验收（沿用 CI-05 口径）。

| 序 | 动作 | 判据 | 依赖 |
|---|---|---|---|
| 1 | **CI-13** 补规则 13/14/15，README 规则表改由脚本校验 | 加一个 `ubuntu-latest` 必红；改 README 规则行必红 | 无 |
| 2 | **CI-14** `uses:` 钉 40 位 SHA（8 条 workflow 共 20 余处） | 存在浮动 tag 必红；PR 升级能看见 SHA diff | 无 |
| 3 | **CI-15** `ci/gates/evidence.sh` 统一证据包 | 人为让 accept 失败，四件套齐全 | 无 |
| 4 | **CI-08** 段耗时进 manifest + step summary + `AIRY-BUILD-DRIFT` | 连跑两轮，超基线 2× 有标记 | 无 |
| 5 | **CI-06 / CI-07** 收口：dispatch 前比对三远程 sha | 构造陈旧 HEAD 必红 | 无 |
| 6 | **CI-11 L1-a** 候选池抽象 + 校验语义 + 显式回退（只读本地目录） | T-PAY-1/3/4/6 | 提速设计 §5 |
| 7 | **CI-11 L1-b** 接 `actions/cache`，两段式键 | T-PAY-2/7 | 6 |
| 8 | **CI-11 L2** `payload-publish`（先只 push）+ `payload-seed.yml` | T-PAY-5/8/9 | 7 |
| 9 | 收口：整链 ≤60 分钟口径进发布手册 | 冷启动轮实测 ≤3600 s | 8 |

1–5 是治理，不改变任何产物字节，可并行推进；6–9 是提速，必须串行（每层没有
上一层就无法验证「回退是否真的回退」）。
