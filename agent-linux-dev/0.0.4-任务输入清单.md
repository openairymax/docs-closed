## 2. 0.0.3 遗留技术债（0.0.4 必做项）

| 编号 | 债 | 依据 | 完成判据 |
|---|---|---|---|
| FL-04 | 交付物把「介质」与「载荷」压成一个 3.7 GB 的 ISO，于是每次发版都要把每块 U 盘整盘重写一遍，而两版之间真正变化的只有载荷 | `image-build.yml` 的 `iso-publish` 与 `tools/airy-flash/README.md`：离线闭包（内核 + UKUI + 全部依赖）以 squashfs 全量嵌在 ISO 内，`fetch` 每次取满 3.7 GB | 评估两层交付：常驻「引导盘」（anaconda + kickstart + 取件器 + 网卡与 CA，目标 ≤1 GB，跨版本不重写）+ 内容寻址「载荷」（`airymaxos-payload:<ver>`，按 digest 钉住，装机时取回并校验）。三条判据缺一不可：①载荷以 digest 而非 `latest` 引用，装机后 `/etc/airymaxos-build` 记录该 digest；②断网仍可回落整包 ISO，不退化成只认网络；③同 digest 两次装机字节相同。三条不能同时满足则 0.0.4 保持整包 ISO，本项顺延，不得以「省盘」为由牺牲可复现性。**通道命名与 CI-11 的 L2 层共用 `airymaxos-payload`，但必须用 tag 前缀区分**：本项（装机期）用 `install-`，CI-11（构建期候选池）用 `build-`，禁止同名共存（见 `0.0.4-构建提速设计.md` §3） |

## 3. 0.0.3 的经验（值得沿用的做法）

1. **账本与文档分离**：生成器产出账本、人工只改种子，使得「范围回涨」「降级边失守」可被断言而不是被评审发现。
2. **门禁单入口**：`ci/ci.sh` 扫描 `ci/gates/*.sh`、解析 `# 用法:` 头注释，新增检查只需放一个文件；单行 `run: ci/ci.sh xxx` 不计入内联预算，倒逼逻辑下沉。
3. **发布前自证**：签名在另一台 runner 上完成，落盘字节可能被 artifact 打包解包改写，故 `release-verify` 在推 registry 之前重算摘要、署名与 notes 形态。这条是 0.0.3 最后落地、也最值得保留的一道。
4. **剖面语义**：`acceptance=true` 断言 `AIRYMAX-SMOKE-PASS`（会话内冒烟），`false` 断言 `AIRYMAX-DESKTOP-READY`（产品态）。同一套 workflow 用布尔输入区分验收与交付，避免两套脚本漂移。
5. **两包分立**：`airymaxos`（基础镜像）与 `airymaxos-iso`（安装镜像）是两个 OCI 包，tag 互不覆盖，3.43 GiB 的 ISO 得以绕开 Release 与 AtomGit 的单资产上限。
6. **实机只做取证**：B50 只做只读与装机复验，构建一律走 GitHub runner；本机 python3 无 pip/pytest/shellcheck，`ci/gates/python-verify.sh` 因此在 CI 上才有完整环境，本地只有 `check`/`plan` 这类单命令可跑（缺口见 `DEV-01`）。
7. **预算是配置面的函数**：内核配置一换，模块数与构建时间同向放大，封顶值必须跟着重标定。0.0.3 的 150 分钟是按 `defconfig` 时代定的，配置换了却没跟着改，代价是 2.5 小时整轮作废。
8. **先读日志时间戳，再改数字**：失败第一步是把 `##[group]` 段的起止时刻取出来算每腿耗时，而不是凭「大概慢」直接加倍。本次四腿数据直接决定了 210 这个值，也顺带证伪了「前置要 28 分钟」的旧说法（实测 5.3 分钟）。
9. **失败的归因要落到「预算与基线脱钩」这一层**：不砍架构、不拆 job、不放宽门禁，只把预算对齐实测。补丁式修法（例如把 loongarch64 挪到别的 job）会同时破坏「2 job 铁律」与「四架构同源构建」。
10. **本地跑不了 ≠ 没有覆盖**：先读门禁脚本的 `REQS`/`TESTS`，再查对应 run 的 step 结论，最后才下「缺覆盖」的判断。0.0.3 收尾时 `tools/airy-flash/tests/` 就是这样确认在 `os-chk-verify` 的 step 5 里真实执行的；反过来，若先删用例再补环境，覆盖会真的丢掉。
11. **通用性先按代码判，缺口多半在校验面或文档面**：被要求「通用化」时先 `grep` 本体：`airy_flash.py` 里 `B50`/`WSL`/私网段计数为 0、分支只读 sysfs，说明能力已通用，缺的是可读的边界声明（README 只有围绕验证机写的一节）。于是改文档、去掉写死的机器事实（如把「WSL 根盘是 `/dev/sdd`」改成不依赖具体主机），而不是给非 Linux 路径加桩分支来「显得通用」。
12. **在线依赖要么预烘、要么可重试**：组装期从外网装 1273 个包，等于把「整轮能不能跑完」交给第三方镜像的带宽与 HTTP/2 稳定性。慢但能完成，要用预算吸收；拿不到包（事务级失败），要用幂等重试或预烘镜像消除。两者不能混谈，否则会把一次网络抖动误记成组装缺陷，或把真实缺陷当成重跑就好。
13. **判断分支或文档是否陈旧，先看消费方 pin，而不是名字或默认分支**：`dev/hubs-01` 名字像临时分支，实为超级工程 pin 的活跃线；`main` 名字像主干、又是 GitHub 默认分支，实为落后六提交的旧线。只看分支名或默认分支，会得出「删 dev、留 main」的反向结论。
14. **改名或改流水线名后的引用收口，要进子仓逐个 grep，且须区分「旧名残留」与「合法旧名」**：仓库改名 `agentrt-linux → agent-linux`、流水线改名（`mgmt-orchestrator → mgmt-verify` 等）后，ripgrep 在超级工程根目录默认**跳过子模块**，被 pin 的叶仓 README 里残留的旧名与旧流水线名不会被发现，必须 `git -C <leaf> grep`。同时，根仓 README 的「renamed from `agentrt-linux`」是改名历史，`docs/docs-closed/agent-linux-dev/agentrt-linux*.md` 是真实存在的文件名，两者都属合法旧名，不得误改。

   0.0.3 收尾实测：`agent-linux` 的 `main` 上 `git grep agentrt-linux` 共 18 处，逐条核对后**全部属合法旧名**：`ssot-registry.yaml` 的 `roadmap_doc` 与 `tools/osaccrt/` 14 个 `.py` 的文件头引用的都是 `docs-closed/agent-linux-dev/agentrt-linux开发路线和进度.md`、`agentrt-linux验收实验任务卡草案.md`（`ls` 确认三份 `agentrt-linux*.md` 真实存在），`README.md`/`README_zh.md` 是改名历史，`tools/osaccrt/README.md` 是文件名引用。另 `openairymax/agentrt`（4 处，`sc-verify.yml` 镜像同步与 `await-agentrt-ci.py`）指用户态产品仓，与 `agentrt-linux` 无关。**结论：无需改动**，判定口径就此固定为「先 `ls` 验文件是否存在，再读上下文验是否为改名叙述」。

15. **修复落在构建树 ≠ 已交付，包清单类修复必须重造 ISO 才算闭环**：`7f2975f` 把无线用户态四件套写进 comps 与 `rpms.in.yaml`，生成器与单测都过，但**已发布的 ISO 是修复之前造的**，装机后依旧没有 `NetworkManager-wifi`。0.0.4 的判据是「重造 ISO 后真机 `nmcli device wifi list` 有输出」，而不是「comps 里有这行」。凡改动落到 comps / rpmdeps / kickstart 这类**只在装机时生效**的清单，验收一律以**新造制品的装机结果**为准，不得以源码树 grep 代替。
16. **配置项写对，还要触发条件成立：「写在配置里」与「运行期生效」是两回事**：`GRUB_GFXMODE` 已设但 GRUB 未 `loadfont` 与对应字体，图形模式不落地；`CONFIG_DRM_SIMPLEDRM` 即便设为 `=m`，6.6 的 `simpledrm.c` 只声明 of 匹配表、无 `platform:simple-framebuffer` modalias，udev 不会自动加载，EFI 帧缓冲永远不会变成 `/dev/dri/card0`。两起事故同源：只核对了「值对不对」，没核对「触发路径通不通」。0.0.4 的此类门禁须同时断言**值**与**触发条件**（字体文件存在、`=y` 而非 `=m`），并把「运行期是否出现预期设备/模式」作为装机腿的取证项。

17. **伪工具必须复刻真工具的选项语义到分支级，而不是只复刻常用路径**：给 `airy-flash` 配的伪 `lsblk` 最初把 `-d`（不展开子设备）实现成「只输出整盘」，导致脚本里 `lsblk -dnro TYPE <分区>` 查 `TYPE=part` 这一完全合法的用法在测试里拿到空输出，被误判成脚本缺陷。排障时先在临时目录手工复现伪工具行为再怀疑被测代码，本次即由此定位。0.0.4 给新工具配 fakes 时，每个用到的选项组合都要有一条实测记录，而不是按记忆实现。
18. **桩要打在最小面上，否则用例在更早阶段即告失败，测不到目标行为**：复刻「劣质介质吞写缓存」时，第一版伪 `dd` 无条件 `exit 0`，但镜像结构校验（`iso_pvd`/`iso_mbr`）本身也用 `dd` 读镜像头，用例直接死在「缺少 ISO 9660 PVD」，回读逻辑根本没被执行。改成 `DD_SWALLOW`：只把 `of=` 落点改到临时文件、读路径原样透传真实 `dd`（且落点必须是普通文件：`/dev/null` 上 `conv=fsync` 返回 EINVAL，又会掩盖真实路径）。判定「桩怎么打」的依据是**被测代码的全部调用点**，不是本用例的关注点。

19. **测试框架的缺省超时也是「预算」，同样不能从裸机照抄到模拟环境**：kselftest 上游 `runner.sh` 的 `kselftest_default_timeout=45` 是裸机口径；`pidfd_test` 内部有多段 `sleep(3)` 与自旋等待来校验时间窗，在纯 TCG 下累计耗时必然击穿 45 秒，门禁于是判 `not ok … # TIMEOUT 45 seconds`，而同一批其余 19 个用例全绿。修法不是放宽断言，而是把预算显式化，另加整批墙钟上界（`--wall`），使真死锁仍在有界时间内失败。与第 7 条同源：**凡是「超时」数字，都要写清它是在什么环境下测出来的**。

20. **被 SIGKILL 的用例在 TAP 里是零输出，不能据此判「hang」**：`ksft_print_header()` 的输出走管道时是全缓冲，进程被超时杀掉时缓冲区直接丢弃，于是失败用例只剩一行 `not ok` 加 `# TIMEOUT`，任何「没有输出就是卡死」的推断都不成立。0.0.3 因此绕了一段路才发现是预算问题而非内核缺陷。0.0.4 的运行时门禁对「无输出失败」须同时给出**单元耗时**与**是否被强杀**两个事实（例如按目标记 `date +%s` 起止），把「慢」与「死」在证据层就分开。

21. **长时间运行时门禁与静态分析共处一个 job，会让一次「慢」作废全部静态证据**：`kernel-verify` 的 28 格 Kbuild 矩阵、checkpatch、sparse、Coccinelle 全部通过，只因第 11 步 kselftest 单点超时，整个 job 判 failure，排障时不得不先证明「前 10 步没坏」。运行时测试与静态分析是两类信号，失败含义不同、耗时量级相差一个数量级，应拆成独立 job 并在汇总 job 里做聚合判定；拆分后单点失败只丢单点证据，且能并行压缩墙钟。

22. **全局超时覆盖会抹掉上游的分档语义，失败只会转移落点**：`run_kselftest.sh -o` 是**全局**覆盖，它同时改写了上游的两层预算：裸机缺省 45 秒，以及目录 `settings` 里的 `timeout=0`（无界/soak）。0.0.3 修完 pidfd 后失败项立刻平移到 `rseq/run_param_test.sh`：该目录被上游声明为无界，240 秒对它没有任何意义。系统性修法是**按目录落预算**（写进安装目录的 `settings`，不改源码树），上游已声明有限预算的目录一律尊重；纯浸泡脚本（一轮约 608 次进程启动）显式剔除，且剔除前断言用例名确实在清单里，使「少跑一个用例」在日志与账本里都可审计。判据固定为：`settings` 里 `timeout=0` 的目录属 soak 类，不进入有界 CI，改由实机浸泡覆盖。

23. **构建期断言的「字面量」要与出厂资产逐字对齐，且对齐检查必须提前到 lint**：`airymaxos-release` 的 `%check` 用带两个空格缩进的 `grep -qxF '  ConditionPathExists=…'` 断言 unit 指令，而 unit 源文件本身无缩进。`%check` 在 `rpmbuild` 尾部失败，`build-rpms` 随之中止，`airymaxos-system` 没进本地仓库，后续 closure 求解才报 `Unable to find a match`。一个缩进在日志里最终表现为「缺包」，排障时容易误向包依赖方向追查，徒劳无功。系统性修法是把同一条断言提前：lint 阶段扫描 `%check` 里所有 `grep -qxF '<字面量>' <构建树路径>`，逐条断言该字面量确实出现在对应出厂资产的行集合中，构建期只做重复确认。凡是「断言写法与资产写法各写一遍」的地方，都要有一条把两者绑起来的检查。

24. **库函数要放在「每个调用方都 source 的文件」里，并用静态检查钉住**：`need_cmd` 原先定义在 `ci/lib/host.sh`，而 `media-fetch.sh`、`container-load.sh`、`assemble.sh`、`release-rpms.sh` 只 source 了 `ci/lib/log.sh`，运行期报 `need_cmd: command not found`，前置工具校验被静默跳过，gate 以 127 退出后才在日志里露出。修法分两步：把只读宿主、不改状态的 `need_cmd` 移进 `log.sh`（每个 gate 都会 source 它），再给 `ci/check-workflows.py` 加一条规则：门禁调用的每个库函数必须来自它 source 的库。运行期才发现「函数不存在」，代价是一整轮构建；静态检查的代价是一次 lint。
25. **多个大件共用一份下载预算时，先到者会耗尽额度，后到者所剩无几；预算必须按项保底，并让落盘内容本身充当缓存**：run `40485745100` 的 `Fetch fixed openEuler media` 用单一 2700 秒预算串行取两件介质，ISO 单件耗 43 分钟便吃光全部额度，第二件 docker 镜像只剩 130 秒即被判「所有镜像源均不可得」，报错文案把排障方向引向镜像源，真实原因是预算分配。系统性修法三条同时落：①介质目录以内容摘要为键，命中即复用、不触网（`actions/cache@v4` 按两件 sha256 合成 key）；②单次尝试上限 = 剩余预算 − `FLOOR` × 后续项数，再夹到 `--cap`，任何一项都拿得到地板；③总预算按实测最坏值放宽（2700→5400 秒）。凡是「N 个不可分包共用一个 deadline」的地方，都要显式回答「后一项还剩多少」，否则排障会被错误文案带偏。

26. **新交付物一进流水线，物料账本必须在同一轮登记**：本次把 `airy-flash` 的 `.pyz` 接入发布链时，`release_manifest.py --check` 在本地就报出 `release.yml 产出 airy-flash-*.pyz 未在清单登记（未登记物料）`。这条门禁的价值不在清理旧债，而在**新增物料的当轮拦截**：若等发布轮才由 `release-verify` 发现，账本、notes 与 Release 页已经是三份互相矛盾的事实。故任何新产物在改动 `upload-artifact`/`action-gh-release` 的同一个提交里，必须同步补 `manifest.yaml` 的 active 条目与 `evidence` glob。

27. **用户文档里的文件名必须与生成器产物同形，且要有检查把两者绑住**：`build-iso.sh` 产 `airymaxos-<ver>-<arch>.iso`（全小写），而 `tools/airy-flash/README.md` 六处写成 `AirymaxOS-0.0.3-x86_64.iso`。大小写不一致在装机现场表现为「文件不存在」与 `sha256sum -c` 的对照失败，且极易被当成介质损坏。凡是文档出现文件名的位置，都应有一条与生成器的对齐检查（现有 `release_manifest.py` 的 evidence 双向比对已覆盖产物→清单方向，清单→文档方向仍缺）。

28. **实机复验前必须先核 NVR 与 `uname -r`，否则会把旧字节的问题记到新版本账上**：B50 上实测 `rpm -q airymaxos-kernel` 为 `0.0.3-2`、`uname -r` 为 `6.6.157-agentrt`，而当前配方 `%global kernel_local -alk`。也就是说这台机器跑的是改名前的内核，策略面（免密、锁屏、分辨率）已是新的，内核却不是：若只看「能登录、免密生效」就判 0.0.3 通过，内核归属这一项会被旧字节冒充。0.0.4 的实机取证须先落一张「期望 NVR / 实际 NVR / `uname -r` / `rpm -V` 摘要」对照表，任何一项不匹配即判 BLOCKED 并先重装，再谈功能判定。

29. **workflow 薄化要先挑「改完能被自身流水线验证」的文件**：`mgmt-verify.yml` 的 `push.paths` 含 `.github/**`，把两个 job 的内联断言下沉为 `ci/gates/mgmt-files.sh` 与 `ci/gates/mgmt-leaves.sh` 后，提交即触发该流水线自身，run `40504124097` 两个 job 全绿完成自证。而 `sc-verify.yml`（仅 PR 触发）、`release.yml`（仅 tag/dispatch 触发）改完没有低成本验证手段，一旦写错只能等下一次真实发布才暴露。故薄化顺序应由「可自证性」决定，而不是由内联段数多少决定：不可自证的文件先留内联，等有了 dispatch 演练通道再动。本轮内联合计 44 → 38，预算表按文件逐行跟随，棘轮回退检查会阻止「改完不更新预算」。

30. **门禁依赖外网工具时，「本地能跑」不等于「CI 能跑」**：`ci/gates/mgmt-leaves.sh` 的 markdownlint 段在本地因 `registry.npmjs.org` 不可达（`ETIMEDOUT`）无法执行，而 CI runner 可正常安装。此时不应给 gate 加 skip 分支：那会把门禁静默削弱，还掩盖了「本机缺环境」这一事实。正确做法是保持断言强度不变，改为逐段独立复验（本轮单独跑 `check-copyright.py` 与 `aggregate-subrepo-ci.py` 均 rc=0），并在文档里写明该 gate 的可重放边界：无网环境只能部分重放。凡 gate 引入新的外部工具依赖，都要在同一提交里回答「离线时哪几段可重放」。

31. **就绪判据必须与交付的座位策略同源，不能拿「最常见的那个形态」当唯一判据**：`desktop_ready.sh` 把 `Class=greeter` 钉死，而 `50-airymax.conf` 启用 autologin；lightdm 在 autologin 下**不创建 greeter 会话**，直接以 `lightdm-autologin` PAM 服务拉起 `Class=user` 的 X11 会话，探针于是永远等不到就绪标记。B 轮 run `40526252360` 双固件冷启动同因判负，诊断行给出的却是 `session=1 lightdm-autologin|user|x11|active`：根因不是超时也不是配置缺失，而是「判定者与被判定对象各持一套事实」。修法是判据取交付策略的并集（服务家族前缀、`Class∈{greeter,user}`、`State∈{active,online}`），并把该字面量写进 `%check` 防回退。凡「交付侧可配置、判定侧写死」的配对，都要有一条断言把两侧绑住。

32. **改交付资产必须同步升 `%release`，否则镜像无法自证「这版修了」**：`desktop_ready.sh` 由 `airymaxos-release` 包交付，只改脚本不升 `%release`，装机后 `rpm -q airymaxos-release` 仍是旧号，验收基准与实际字节对不上，等于把修复留在源码树。收口链条固定为「改资产 → 升 `%release` 并补 changelog → distro 提交 → agent-linux 子模块指针 → 重指 tag → 重建 Release」，任一环缺失都要重来一轮。本轮据此把 `0.0.3-8` 提到 `0.0.3-9`，并同步上调验收基准行。

33. **门禁不得在归一前重置调用方输入，归一化只能有一份事实**：B 轮 run `40567450252` 的 `Extract smoke TAP` 报「0 行」，可 `image-build.yml` 两个 job 的 `ACCEPTANCE` 传参完全正确，问题出在 `assemble.sh` 与 `accept.sh` 各自先写 `ACCEPTANCE=0` 再做 `0/1` 归一，调用方传入的 `true` 在第一步就被本地默认覆盖。后果不是参数报错，而是 B 轮装出产品 ISO、按 `AIRYMAX-DESKTOP-READY` 在 23 秒判完成，会话内冒烟从未执行，直到末端还原 TAP 为空才暴露。修法是把归一收敛成 `ci/lib/profile.sh` 的 `airy_profile()`（只读环境变量、未声明才兜底 0），三个调用方共用，并在 `ci/lint.sh` 里加六组输入的归一断言。凡「调用方可配、门禁可默认」的配对，默认值的写入位置必须晚于读入位置，或统一由单一函数只读提供。

34. **「不在适用范围」与「已完成」不能用同一个退出码，否则门禁只剩一句无条件 OK**：`efi_brand.sh` 对「缺 `efibootmgr`」「ESP 未挂载」这类**本可修复的部署缺陷**走 `skip` 并返回 `0`，与「BIOS 启动无需品牌化」同类退出；ks 侧只判 `rc == 0` 就打 `AIRYMAX-EFI-OK`，而脚本的 `--log` 落在安装器环境、随安装器消失，事后再无归因材料。run `40587295652` 的日志里 `AIRYMAX-EFI-OK` 与 ESP 内空无一物并存，三处叠加构成静默成功。修法三条同时落：退出码只留两档（`0` 完成或在适用范围外、`1` 在范围内但失败，缺 `efibootmgr` 归 `1`）；判据改成**目标根里的落地物**（`var/lib/airymaxos/efi-brand` 非空），不看退出码；日志写进目标根 `var/log/airymax/`，安装器消失后仍可取证。凡「门禁读的是退出码、日志落在临时环境」的配对，都要有一条以交付物本身为准的断言。

35. **装机期独有的能力不能延后到首启，且必须在目标根里执行**：ESP 与 NVRAM 写入依赖 `efivarfs` 与 `dosfs_t` 写权限，首启时 `init_t` 对 ESP 的 create 被 SELinux 拒（run `40574831975`），首启路径从原理上就做不到。而 `%post --nochroot` 默认看不到目标根的 ESP，于是「能跑」与「能改」缺一不可：先按目标根 `/etc/fstab` 把 ESP 挂回，再把 `/dev /proc /sys` `--rbind` 进去，`chroot` 后才执行品牌脚本，挂载集合记入 `owned` 并由 `trap … EXIT` 用 `umount -R` 还回。凡「安装时要改目标系统内的东西」的步骤，一律按「挂载齐 + chroot 进根 + 以根内文件为判据」三段式落地，不在安装器环境里直接改。

36. **显示模式的选择要和输出真实广播的模式求交，再受上限约束，不能直接套首选值**：`GRUB_GFXMODE` 与桌面首选分辨率是「期望」，而显示器实际广播的模式集是「可选项」，两者不交时要么黑屏要么被驱动静默回退，且回退结果与策略声明不一致。0.0.3 的落法是 `distro/desktop/display_mode.sh` 做单一策略源：取 `{上限内首选} ∪ {该输出确实广播且不超上限的常用档}`，宽高压序取最大、同尺寸首选优先，并给出 `--check` / `--plan` 两个可判定入口，使「取到了哪个模式、为什么取它」可被流水线断言而不是靠现场看。凡「策略侧写死一个值、设备侧另有能力集」的配对，取交集并让选择过程可复算。

37. **「收敛成功」不等于「最终生效」：会话里还有第二个写入者，入口须存活至最后一次写入完成**：验收 run `40610532780` 的 T10 在双固件上都失败，而串口里明确有 `settled after 1s`，`--settle` 内确实收敛了，45 秒后的 TAP 却读到 `Virtual-1:5120x2160`。第二写入者是 `ukui-settings-daemon` 的 xrandr 插件：它比 XDG autostart 更晚落地，按自身记录回写模式。桌面侧没有可预置的单写入点（kscreen 的 `monitors.xml` 按具体显示器指纹绑定，无法随镜像分发），所以系统性修法不是改桌面配置，而是把会话就绪后的入口从「收敛即退」改成「有界守护」：窗口内持续 re-scan、出现偏差即纠正、按 `drift`/`fixed`/`stuck` 计数，到期记一行汇总后退出，不常驻。凡「策略写入后仍有第三方可改写」的配对，验收必须覆盖**最后一次写入之后**的状态，判据时刻要晚于所有已知写入者。

38. **权限边界会把「看不见」报成「不存在」：探测端必须先证明自己能看见**：同一轮 T11 报 `shimx64.efi missing`，而固件日志记录从 `EFI/airymaxos/shimx64.efi` 引导成功，文件实际存在。根因是 ESP 按 `umask=077` 挂载（`drwx------ root root`），冒烟以交付用户 `airymax` 运行，`[ -f ]` 得到的是 EACCES，被写成 missing。修法在探测端而不在产品侧：`esp_ok()` 以父目录可读性作代理，可读时直接 `[ -s ]`，否则 `sudo -n test -s`（T12 已证免密提权可用），判定口径只此一处；诊断补 `esp=readable|sudo|denied` 与 `boot=<当前引导项>`，把「文件丢了」与「权限不足」在 TAP 一行里分开。凡「以文件存在性作判据」的探测，都要先回答「以什么身份、能看到哪一层」。

39. **派生介质的工具只应改动目标字节，且改动面必须可逐字节复核**：站点介质只需替换 `/ks.cfg`，`mkksiso` 却会重写 `isolinux/isolinux.cfg` 与 `EFI/BOOT/grub.cfg`，在每条 `append`/`linuxefi` 行尾追加 `inst.ks=hd:LABEL=<volid>:/ks.cfg <cmdline>`，未传 `-c` 时 `<cmdline>` 是字面量 `None`；底座本已含 `inst.ks`，同一键便出现两次，而「anaconda 把重复键解析成列表还是取末值」在构建侧无法证伪。改用 `xorriso -indev <iso> -outdev <out> -map <ks> /ks.cfg -boot_image any keep`：实测 2.4 秒，卷标、`sfdisk` 分区项（含 0xef 的 ESP 项）、引导配置字节全部不变，`/ks.cfg` 与源逐字节一致，可挂载复核。凡「派生一份已成形介质」的选择，先回答「它会改动哪些我不打算改的字节」，无法回答或无法复核的工具一律不用。

40. **`%post` 默认在目标根内 chroot 执行，路径按根书写；落盘之后还要恢复 SELinux 标签**：站点脚本按 `${ANA_INSTALL_PATH:-/mnt/sysimage}` 拼路径，在 chroot 语义下会于已装系统里造出 `/mnt/sysimage/home/...` 影子目录，运维公钥落到无人读取的位置，而安装日志全绿。同一脚本还须满足 `ks_lint` 的 `K008`（`%post` 首行 `set -eu`），且 `set -e` 与 `command -v … && cmd` 连用会在探测失败时直接中止，探测必须写成 `if … then … fi`。SELinux Enforcing 下用 heredoc 落盘的 `authorized_keys` 不带 `ssh_home_t`，sshd 拒用，需在同段内 `restorecon -R`（以 `command -v` 保护，未装 policycoreutils 时不中断安装）。系统性修法：站点脚本一律按「chroot 语义 + `set -eu` + 落盘后恢复标签」三段落地，并把「文件在哪、标签是什么」做成可回读的判据，而不是只看安装是否成功。

41. **安装介质上的可见文案也属于品牌面，但当前唯一的 ISO 生产链并不触碰它**：`build-iso.sh` 只把 `/ks.cfg` 换进底座，`isolinux.cfg` 与 `grub.cfg` 的菜单标题仍是底座发行版的原样；0.0.3 的品牌门禁只覆盖壁纸、主机名、`os-release` 与 ESP，故本轮不阻断。0.0.4 需在打包链里补一步菜单重写（或换用能同时替换 `ks` 与引导配置、且改动面可逐字节复核的路径），并把「开机与安装界面可见文案」纳入品牌门禁：否则品牌判定存在一块永远不被检查的盲区。

42. **GPU 不在内核基线的支持矩阵内时，桌面会退回 efifb，分辨率自适应随之失去落点**：B50 的独显是 `8086:e212`（子系统 `1ef7:b412`，Battlemage 家族），6.6 基线只带 `CONFIG_DRM_I915=m`、没有 XE，`modinfo -F alias i915 | grep -c E212` 得 0，`/sys/class/drm` 只剩 `version` 一个条目。X 因此挂在 `fb0: EFI VGA frame buffer device` 上：`xrandr` 只有一个 `default connected primary 1920x1080`、物理尺寸 `0mm x 0mm`、模式上限就是 1920x1080，并且每次查询都打 `Failed to get size of gamma for output default`。这不是显示策略的缺陷，是下层没有能力；但策略在单输出上仍会「收敛成功」，把「无 DRM 驱动」伪装成「已按策略设好」。0.0.4 两条同时落：①把「内核基线覆盖哪些 GPU 家族」写成发布前必须回答的支持矩阵；②策略在检测不到 DRM 输出时明确报「不适用」并退出，不参与收敛统计。凡「上层策略假定下层具备某能力」的配对，都要回答「下层缺这项能力时上层的判定是什么」。

43. **`reboot` 与 `halt` 是两件事，无人值守流程不能把「自重启」当作流程节点**：B50 上 anaconda 收尾的 `reboot` 落到 `reboot: System halted`，机器停住 37 分钟（`uptime -s 2026-10-28 13:31:21`，`last` 显示 12:53–13:31 停机），只能人工断电重上电。附带代价是这段时间的证据全部落在内存里：该机 journald 为 volatile（`/var/log/journal` 不存在，`journalctl --list-boots` 只有 IDX 0），重启后「上一次启动停在哪」已无从查证。0.0.4 的口径：串口终态出现即视为安装结束，后续引导由 `efibootmgr -n <条目号>` 加外部上电驱动；`BootOrder` 只由装机段的品牌化脚本改；持久日志作为排障前置条件，不当作可选项。

44. **启动观感属于产品面，且它由两处共同决定，缺一处就退回日志或黑屏**：真机反馈「开机的动效、打印行太乱」。实测 plymouth 早已在 initramfs 内（`lsinitrd` 命中 43 项），但默认主题是 `text`，bootloader 行又没有 `rhgb`，于是第一次冷启动看到的就是逐行滚动。两处缺一不可：`bootloader --append` 的 `rhgb quiet` 决定 plymouth 是否接管屏幕，`/usr/share/plymouth/themes/default.plymouth` 链接指向哪个主题决定接管后的观感（`ShowDelay` 由 openEuler 的 `plymouthd.defaults` 给出，已是 0）。0.0.4 应把「冷启动首屏」纳入验收取证（截图或串口对照），否则这类缺陷只能等用户反馈；另需注意 `quiet` 只压控制台 loglevel 到 4，告警仍打印、记录仍进 journal 与 `ttyS0`，`login:` 哨兵来自 agetty 不受影响，因此可作默认值。

45. **命令替换里给全局赋值等于没赋值，而「只测旁路开关」的用例恰好绕开出问题的路径**：产品轮 run `40667538822` 的 UEFI 装机在最后一个 `%post` 中止：串口是 `no grub config at  (ESP unmounted?)` 与 `按 ENTER 退出: AIRYMAX-GRUB-FAIL rc=1`，同一轮 BIOS 装机通过，因为非 EFI 走 early skip；TAP 因此 `pass=2 fail=2`，发布步骤被跳过，ghcr 上的 tag 仍指上一版。根因：`pick_cfg()` 在函数内给全局 `cfg` 赋值，调用方却写成 `cfg=$(pick_cfg)`：命令替换在子 shell 里执行，赋值随子 shell 一起消失，`cfg` 恒为空，随后 `regen()` 的前置检查判空失败，真正的生成步骤从未执行。单测与 lint 双绿的原因是 `%check` 只跑 `--no-regen`，恰好在 `regen` 之前退出。系统性口径两条：①需要返回值的 shell 函数只往 stdout 打印、由调用方赋值，函数内不碰同名全局；②凡「有副作用的阶段」都必须能被验收进入：把不可注入的外部依赖（生成器命令、`/etc` 查找根）提为参数，在临时目录里走完整条「生成 → 品牌副本 → 状态写入」路径，并覆盖生成失败回滚。只测前置改写等于没测。

46. **制品取回的唯一判据是摘要，通道可以替换：把「从哪取」与「取到了什么」分开**：B50 直连 `ghcr.io` 实测 21 KB/s（3.76 GB 需 49 小时），本机出口同样被压制（空闲 rx 35 KB/s，经本地中转 `37 KB/s`），aliyun/tuna 无可用字节。改走地区镜像 `ghcr.nju.edu.cn` 后 9.79 MB/s、4 分钟取完，且其清单里的 `layer.digest` 与发布值逐字相同，落盘 `sha256sum -c` 为 `OK`。故取件脚本按「地区镜像优先、`ghcr.io` 回落」登记候选，任何候选都必须过同一道摘要断言；失败重试只换通道，不放宽判据。0.0.4 应把候选清单做成可配置项（`AIRY_REGISTRY`），并在 `airy-flash fetch`（`FL-01`）里沿用同一顺序与同一断言。

47. **重新打包 isohybrid 镜像会丢掉末尾填充扇区，长度不补回即等于把 ESP 尾段切掉**：站点派生（`xorriso -indev … -outdev … -map ks /ks.cfg -boot_image any keep`）产物比产品 ISO 短 1.98 MB，MBR/GPT 尾部项仍按输入长度布局，于是 `libburn: SORRY: Read start address … larger than number of readable blocks`、`xorriso` 以 32 退出，被切掉的正是 ESP 所在段，写盘后不可引导，而派生阶段的「`/ks.cfg` 已替换」这个判据是满足的。系统修法两条：①`build()` 之后一律 `truncate -s <产品 ISO 字节数>` 补回原长，并以「产物长度相等」为断言；②工具退出码与「文件是否完整落地」是两件事，`extract_ks()` 只以目标文件存在且内容比对相等为判据，不为迁就 `SORRY` 放宽容错。附带一条排障口径：stdout 走块缓冲、stderr 直写，`die` 行会排在 `ks_lint clean` 之前，**阶段顺序以 `main()` 的调用序与缺失的收尾行为准**，不看日志先后。

48. **安装期的等待由 anaconda 独占屏幕，`squashfs` 解压阶段可以连着几分钟一行不刷新**：真机反馈「停在 9.755407 就不动了」「停在 `update rtc with system clock` 就不动了」，两次都不是卡死，而是 anaconda 从 U 盘读约 1.5 GB 的 `squashfs` 时没有任何进度输出，串口与屏幕同时静默。判断依据只能是旁证：风扇仍在转、`ssh` 仍可用、后续行仍会出现。这不是安装器缺陷，而是「长时间 I/O 期间没有可见反馈」这一类体验缺陷在安装段的复现，与桌面探针在等待期静默同源。0.0.4 口径：凡预计超过 10 秒的等待阶段，都必须有周期性的可见输出（进度或心跳行），且该输出由阶段自己产出，不依赖上层是否打印日志。

49. **被派生进程的失败会被误当成独立故障，根因需要按启动顺序回溯**：B50 的 `systemctl --failed` 同时列出 `lightdm.service`、`airymax-desktop-ready.service` 与 `plymouth-quit.service`，看似三个缺陷，实际只有一个是根因：BMG 无 KMS 驱动使 lightdm 反复重启，`plymouth-quit.service` 因 `Before=lightdm.service` 被反复拉起，5 次后撞 `start-limit-hit`。旁证：openEuler 的 `plymouth-quit.service` 本就是 `ExecStart=-/usr/bin/plymouth quit`（忽略退出码），给它加 drop-in 不会改变结果。0.0.4 口径：失败归因必须先取 `systemctl show -p NRestarts` 与单元依赖顺序，把「被谁反复拉起」与「自身为何失败」分开记账；派生失败只作为根因的旁证，不单独立项修复。

50. **0.0.3 的桌面验收改为换机执行，内核能力缺口按版本演进而非单机特判处理**：B50 的显卡是 Battlemage（`8086:e212`），6.6 基线既无该 PCI ID 的 i915 支持也无 XE，桌面只能落 `simpledrm`/`efifb`，桌面链必然失败。0.0.3 不为此改动内核基线（换内核属版本级决策），而是把该机降级为「烧录、安装、品牌、免密、启动可观测性」的取证机，桌面 T1–T5 换一台 i915 可驱动的机器执行。这是一条通用约束：验收矩阵按「能力是否具备」选择执行机，不为单台机器的硬件缺口定制镜像，硬件缺口登记为本条与第 42 条的版本输入。

51. **同一份 `grub.cfg` 有两个副本，只有被加载的那份生效：品牌目录若不被加载，字体与显示策略就落错地方**：B50 真实启动链是 `Boot0002 → \EFI\airymaxos\shimx64.efi → grubx64.efi（内嵌 `prefix=/EFI/openEuler`）→ 加载 `/boot/efi/EFI/openEuler/grub.cfg`，而品牌化脚本刷新的是 `EFI/airymaxos/grub.cfg`。0.0.3 的修法是让字体、`gfxmode`、`gfxterm` 都落在**实际生效的 prefix 目录**（`grub_args.sh` 已改，实测 `fb0 virtual_size` 为 `1920,1080`），但这只是把落点改对，两副本本身仍在。0.0.4 应在生成引导器时用 `grub2-mkimage --prefix=/EFI/airymaxos` 让品牌目录成为唯一加载点，装完 `EFI/openEuler/` 只保留内核与 cfg 的历史副本或直接消除，并以「`Boot####` 指向的 efi 内嵌 prefix == 唯一 cfg 所在目录」作断言。凡「配置有一份以上副本」的配对，必须先回答「运行时读的是哪一份」，再决定改哪一份。

52. **派生副本的时序决定内容新旧：复制必须晚于生成，否则每次装机复制的都是上一版内容**：`sync_brand` 若排在 `regen` 之前，复制出的品牌副本就是重建前的旧 cfg，而两处 cfg 都「存在且非空」，判据全绿。本轮主流程已固化为 `regen → sync_brand → verify` 并写入状态文件 `cfg=`，但 chroot 段重建前复制这条路径仍在。0.0.4 口径：派生/复制步骤一律排在被派生对象生成之后，且验收断言要落在「副本内容与源一致」（`cmp -s`）而不是「副本存在」。

53. **实时调度被拒的根因是 cgroup RT 带宽为 0，不是 unit 缺 `LimitRTPRIO`（本条已按 0.0.3 实测改写）**：B50 的 `journalctl -p err -b` 里 `rtkit-daemon` 反复打 `Failed to make ourselves RT: Operation not permitted`。早期归因「unit 缺 `LimitRTPRIO`」是错的：`CONFIG_RT_GROUP_SCHED=y` 且 cgroup v1 下，新建 cgroup 的 `cpu.rt_runtime_us` 默认写 0，其语义是「该组禁止使用 RT」而非「不限」，组内任何 `sched_setscheduler(SCHED_RR)` 都返回 EPERM。层级预算还有一条约束：子组之和不得超过父组，直接给 `user.slice` 写满 `950000` 会得到 EINVAL。0.0.3 已在 distro 层落码：`airymax-rt-budget.service` 在 `slices.target` 之后、`rtkit-daemon.service` 与 `display-manager.service` 之前执行 `rt_budget.sh`，按 `sched_rt_runtime_us / 5` 给四个 slice 各写一份，只写「已存在且可写」的 `cpu.rt_runtime_us`，失败不阻断启动，并打 `AIRYMAX-RT-BUDGET` 标记。实测写入 `system.slice` 与 `user.slice` 各 `240000` 后 `chrt -r 10 true` rc=0、重启 rtkit 后告警消失。0.0.4 的根治项是内核侧：要么按发行版场景重估 `CONFIG_RT_GROUP_SCHED`，要么在 cgroup 默认值上给出「不限」语义的显式策略，不走每个 slice 逐个补写的路径。

54. **桌面组件会带自己的模块参数，镜像侧没有那份配置也会被请求**：`pulseaudio` 打 `module-echo-cancel … aec_method=webrtc` 无效，`/etc/pulse` 与 `/usr/share/pulseaudio` 均无此配置，来源是 `/usr/bin/ukui-volume-control-applet-qt` 的调用参数，而 openEuler 的 pulseaudio 未编 webrtc AEC。同一进程还因被反复拉起打 `pid.c: Daemon already running.`。0.0.4 口径：桌面侧下发的模块参数要与本发行版实际编入的能力求交，或显式关闭该 applet 的 AEC 选项；不把「第三方组件自带默认值」当作镜像缺陷，但必须登记来源，避免下次重复排查。

55. **「包在位、单元存在、被兜底策略关掉」是同一类缺口，逐个打补丁不等于修复完成**：`pulseaudio: bluez5-util.c: GetManagedObjects() failed: Unit dbus-org.bluez.service not found`，而 `bluetooth.service` 为 inactive、`hci0` 存在：模块先于服务被探测；`dhclient` 的 `parse_option_param: Bad format d` 与 `Invalid domain name.` 发生在 DHCPACK 前后，而 NM 生成的 `/var/lib/NetworkManager/dhclient-wlp8s0.conf` 19 行内容正常、IP 正常取得。bluez 一侧 0.0.3 已消源：`comps` 核心组显式声明 `bluez`（避免元包漂移把「蓝牙不可用」放大成安装失败），启用清单只由 kickstart 的 `boot_set` 表达，`99-airymax-default-disable.preset` 的 `disable *` 兜底与上游 `99-default-disable.preset` 同语义故不动。dhclient 一侧仍是 0.0.4 项：按 option 编号定位上游解析告警，不通过放宽 loglevel 掩盖。通用口径：凡「包已在位、单元文件存在、却被 preset 兜底关掉」的服务，都要在安装配方的启用清单里显式登记，并让 `is-enabled` 成为装机断言。

56. **验收口径：首启进入桌面后 `journalctl -p err -b` 应为 0 行**：基准实测 45 行全部归因为第 53–55 条四类噪声（rtkit / webrtc AEC / bluez / dhclient），`systemctl --failed` 为空。0.0.3-19 已消源其中两类（rtkit 的 cgroup RT 带宽、bluez 的启用缺口），因此重装后的计数应显著下降，但剩余两类（webrtc AEC、dhclient 域名解析）仍须登记，0.0.4 的收敛目标不变，仍为 0 行。凡「无 failed unit」与「无错误日志」的差别，就是「功能可用」与「系统干净」的差别，两者都要有判据；重装验收时必须同时记录行数与逐行归类，只报一行总数无法判断是真正消源还是仅被压制。

57. **发布链的末尾没有「验签」这一步，只有「签名」这一步**：`release.yml` 的 `cosign push+sign` 与 GPG 内核包签名都在写侧，`release-verify` 只核对资产是否齐全，从不 `gpg --verify` 已产出的 RPM、也不 `cosign verify` 已推的 OCI。后果是「私钥口令错、签名文件为空、产物被后续步骤覆盖」这三类缺陷在 0.0.3 的发布链上均显示为通过。0.0.4 口径：发布流程的 DAG 终点必须是「读回并验证已发布对象」，且验证用例要包含一个故意损坏的负样本；`release-verify` 补 `gpg --verify` 与 `cosign verify` 的动作因 0.0.3 收尾期变更面过大而缓行，仍须登记在案，不得因「本轮没做」而被认为「不需要」。

58. **两个 workflow 共享 `release_tag` 却没有自动衔接，串联依赖人工**：ISO 由 `image-build` 产出并以 `iso-publish` 推到 ghcr，内核 RPM 与 Release 由 `release` 在 tag 推送时产出；`image-build` 的 `release_tag` 是手工 `workflow_dispatch` 输入，默认空。于是「打了 tag 但没人手动触发 image-build」就等于「Release 有了、ISO 还是上一版」，本轮 0.0.3 的 ghcr tag 一度指向前一版即此因。0.0.4 口径：由 `release` 在 `build-and-sign` 成功后以 `workflow_call` 或 `repository_dispatch` 触发 `image-build`，`release_tag` 从上游 job output 传入而非人手填；若保留手动入口，必须让「inputs 为空」直接失败，不留「空即最新」的隐式语义。

59. **同一份配方被两个 workflow 各编一次，成本翻倍而事实源只该有一份**：`kernel-verify` 的 defconfig 矩阵与 `airy-verify` 的 `airy_defconfig` 检查各自完整构建一轮内核，两者读的是同一份 `tools/defconfig-matrix` 与同一份 `ci/gates/kernel-airy.sh` 的 `REQUIRED_CONF`。0.0.3 已把触发面与比对对象对齐（两条流水线都在 `tools/defconfig-matrix/**` 变更时触发），但重复构建未消。0.0.4 口径：矩阵构建只留一处产出「配置差异报告」并作为 artifact 下传，另一处只读该报告做断言；判据是「同一输入不得被两次完整编译」，而不是「两个 workflow 都能过」。

60. **`nightly` 的六个 SKIP 是有意设计，不是欠账，但必须让「缺失」可被机器发现**：`formal-verify` / `soak-runner` / `chaos-runner` / `auto-bisect` / `create-revert-pr` / `ci-budget-check` 六个脚本尚未落地，六段 `if [ -f ] … else echo SKIP` 因此长期为真。契约由 `tools/nightly/manifest.yaml` 加 `nightly.py --check` 守护：脚本一旦出现而清单未转为 available，gate 直接失败。0.0.4 口径：保留该形态，但把「SKIP 累计天数」纳入观测，超过阈值即升级为立项项：长期空转也须设有上限。

61. **Runner 镜像版本曾在同一仓库内出现三个值，且没有任何一处说明为什么**：六个 workflow 混用 `ubuntu-latest`、`ubuntu-22.04`，0.0.3 统一钉到 `ubuntu-24.04`，仅 `os-chk-verify` 因 shellcheck 基线随镜像变动保留 22.04 并就地注释。教训不是「都要最新」，而是「版本是环境输入，必须钉住且给出理由」：`ubuntu-latest` 会在任意一次运行中把编译器、shellcheck、python 全部换掉，让「昨天能过」变成不可复现。0.0.4 口径：镜像升级当作版本级变更，与内核基线同表登记，不得在 workflow 内就地修改。

62. **镜像根已收敛为 `mirrors.list`，但 repo 文件里仍有 15 处字面量**：`distro/repo/mirrors.list` 是 SSoT，`distro/repo/airymax-os.repo` 的 `baseurl` 却仍是硬写的地区镜像地址，两者各自可被单独修改，真实漂移只是时间问题。0.0.3 的离线闭包收割让这条隐患不显形（ISO 内走 `file://`），装后联网便立刻生效。0.0.4 口径：`airymax-os.repo` 在打包期由 `mirrors.list` 生成，产物入 `%check` 比对，禁止手改生成物；凡「一份配置存在两处书写」的配对，都要有生成关系或一致性断言，二者必居其一。

63. **「取消在跑的构建再重派」是核对 head 之后的决策，而非重试手段**：`image-build` 的 `concurrency` 为 `cancel-in-progress: false`，同组新派发只会排队，不会替换在跑的那一轮：想让新提交的载荷生效，必须先取消旧轮。本轮之所以可以取消，判据是旧轮 head 不含本版载荷（无 `airy-bench` 与 `%release 22`），而非「它慢」。若旧轮已进入 `iso-publish` 或已推 tag，取消它等于把 ghcr 上的 tag 留在半旧字节上，此时正确动作是等在跑结束再用 `replace=true` 覆盖，而非提前掐断。0.0.4 口径：派发前先取「在跑 run 的 head sha」与「待派发的 head sha」对比，不同才谈取消；取消后必须以新的 run id 重新取证，不复用旧 run 的结论；`replace` 只在目标 tag 已被占且字节不同时置位，并在发布后回读 digest 断言与本地产物一致。
64. **镜像轮与门禁轮必须落在同一个 head 上，否则「全绿」是两份证据拼接出来的**：0.0.3 收尾期的静态门禁（`os-chk` / `nightly` / `distro-lint`）与镜像组装由不同触发面拉起，`push` 触发的门禁与 `workflow_dispatch` 触发的镜像对同一提交各跑一次是常态，但若镜像轮的 head 落后于门禁轮，镜像里就没有门禁刚验证过的那些字节。判据不是「两类 run 都成功」，而是「产出 ISO 的 run 的 `head_sha` == 最后一条门禁绿的 `head_sha`」；不相等时以镜像轮重跑为准，不允许引用更早门禁的绿色结论。0.0.4 口径：把该等式做进发布前置检查（比对 `image-build` 与最近一次 `-verify` 轮的 `head_sha`），不等即阻断 `iso-publish`。
