## 3. 0.0.3 的经验（值得沿用的做法）

1. **账本与文档分离**：生成器产出账本、人工只改种子，使得「范围回涨」「降级边失守」可被断言而不是被评审发现。
2. **门禁单入口**：`ci/ci.sh` 扫描 `ci/gates/*.sh`、解析 `# 用法:` 头注释，新增检查只需放一个文件；单行 `run: ci/ci.sh xxx` 不计入内联预算，倒逼逻辑下沉。
3. **发布前自证**：签名在另一台 runner 上完成，落盘字节可能被 artifact 打包解包改写，故 `release-verify` 在推 registry 之前重算摘要、署名与 notes 形态。这条是 0.0.3 最后落地、也最值得保留的一道。
4. **剖面语义**：`acceptance=true` 断言 `AIRYMAX-SMOKE-PASS`（会话内冒烟），`false` 断言 `AIRYMAX-DESKTOP-READY`（产品态）。同一套 workflow 用布尔输入区分验收与交付，避免两套脚本漂移。
5. **两包分立**：`airymaxos`（基础镜像）与 `airymaxos-iso`（安装镜像）是两个 OCI 包，tag 互不覆盖，3.43 GiB 的 ISO 得以绕开 Release 与 AtomGit 的单资产上限。
6. **实机只做取证**：B50 只做只读与装机复验，构建一律走 GitHub runner；本机 python3 无 pip/pytest/shellcheck，`ci/gates/python-verify.sh` 因此在 CI 上才有完整环境，本地只有 `check`/`plan` 这类单命令可跑（缺口见 `DEV-01`）。
7. **预算是配置面的函数**：内核配置一换，模块数与构建时间同向放大，封顶值必须跟着重标定。0.0.3 的 150 分钟是按 `defconfig` 时代定的，配置换了却没跟着改，代价是 2.5 小时整轮作废。
8. **先读日志时间戳，再改数字**：失败第一步是把 `##[group]` 段的起止时刻取出来算每腿耗时，而不是凭「大概慢」直接加倍。本次四腿数据直接决定了 210 这个值，也顺带证伪了「前置要 28 分钟」的旧说法（实测 5.3 分钟）。
9. **失败的归因要落到「预算与基线脱钩」这一层**：不砍架构、不拆 job、不放宽门禁，只把预算对齐实测。补丁式修法（比如把 loongarch64 挪到别的 job）会把「2 job 铁律」和「四架构同源构建」一起破坏。
10. **本地跑不了 ≠ 没有覆盖**：先读门禁脚本的 `REQS`/`TESTS`，再查对应 run 的 step 结论，最后才下「缺覆盖」的判断。0.0.3 收尾时 `tools/airy-flash/tests/` 就是这样确认在 `os-chk-verify` 的 step 5 里真实执行的；反过来，若先删用例再补环境，覆盖会真的丢掉。
11. **通用性先按代码判，缺口多半在校验面或文档面**：被要求「通用化」时先 `grep` 本体——`airy_flash.py` 里 `B50`/`WSL`/私网段计数为 0、分支只读 sysfs，说明能力已通用，缺的是可读的边界声明（README 只有围绕验证机写的一节）。于是改文档、去掉写死的机器事实（如把「WSL 根盘是 `/dev/sdd`」改成不依赖具体主机），而不是给非 Linux 路径加桩分支来「显得通用」。
12. **在线依赖要么预烘、要么可重试**：组装期从外网装 1273 个包，等于把「整轮能不能跑完」交给第三方镜像的带宽与 HTTP/2 稳定性。慢但能完成，要用预算吸收；拿不到包（事务级失败），要用幂等重试或预烘镜像消除。两者不能混谈，否则会把一次网络抖动误记成组装缺陷，或把真实缺陷当成重跑就好。
13. **判断分支或文档是否陈旧，先看消费方 pin，而不是名字或默认分支**：`dev/hubs-01` 名字像临时分支，实为超级工程 pin 的活跃线；`main` 名字像主干、又是 GitHub 默认分支，实为落后六提交的旧线。只看分支名或默认分支，会得出「删 dev、留 main」的反向结论。
14. **改名或改流水线名后的引用收口，要进子仓逐个 grep，且须区分「旧名残留」与「合法旧名」**：仓库改名 `agentrt-linux → agent-linux`、流水线改名（`mgmt-orchestrator → mgmt-verify` 等）后，ripgrep 在超级工程根目录默认**跳过子模块**，被 pin 的叶仓 README 里残留的旧名与旧流水线名不会被发现，必须 `git -C <leaf> grep`。同时，根仓 README 的「renamed from `agentrt-linux`」是改名历史，`docs/docs-closed/agent-linux-dev/agentrt-linux*.md` 是真实存在的文件名，两者都属合法旧名，不得误改。

   0.0.3 收尾实测：`agent-linux` 的 `main` 上 `git grep agentrt-linux` 共 18 处，逐条核对后**全部属合法旧名**——`ssot-registry.yaml` 的 `roadmap_doc` 与 `tools/osaccrt/` 14 个 `.py` 的文件头引用的都是 `docs-closed/agent-linux-dev/agentrt-linux开发路线和进度.md`、`agentrt-linux验收实验任务卡草案.md`（`ls` 确认三份 `agentrt-linux*.md` 真实存在），`README.md`/`README_zh.md` 是改名历史，`tools/osaccrt/README.md` 是文件名引用。另 `openairymax/agentrt`（4 处，`sc-verify.yml` 镜像同步与 `await-agentrt-ci.py`）指用户态产品仓，与 `agentrt-linux` 无关。**结论：无需改动**，判定口径就此固定为「先 `ls` 验文件是否存在，再读上下文验是否为改名叙述」。

15. **修复落在构建树 ≠ 已交付，包清单类修复必须重造 ISO 才算闭环**：`7f2975f` 把无线用户态三件套写进 comps 与 `rpms.in.yaml`，生成器与单测都过，但**已发布的 ISO 是修复之前造的**，装机后依旧没有 `NetworkManager-wifi`。0.0.4 的判据是「重造 ISO 后真机 `nmcli device wifi list` 有输出」，而不是「comps 里有这行」。凡改动落到 comps / rpmdeps / kickstart 这类**只在装机时生效**的清单，验收一律以**新造制品的装机结果**为准，不得以源码树 grep 代替。
16. **配置项写对，还要触发条件成立——「写在配置里」与「运行期生效」是两回事**：`GRUB_GFXMODE` 已设但 GRUB 未 `loadfont` 与对应字体，图形模式不落地；`CONFIG_DRM_SIMPLEDRM` 即便设为 `=m`，6.6 的 `simpledrm.c` 只声明 of 匹配表、无 `platform:simple-framebuffer` modalias，udev 不会自动加载，EFI 帧缓冲永远不会变成 `/dev/dri/card0`。两起事故同源：只核对了「值对不对」，没核对「触发路径通不通」。0.0.4 的此类门禁须同时断言**值**与**触发条件**（字体文件存在、`=y` 而非 `=m`），并把「运行期是否出现预期设备/模式」作为装机腿的取证项。

17. **伪工具必须复刻真工具的选项语义到分支级，而不是只复刻常用路径**：给 `airy-flash` 配的伪 `lsblk` 最初把 `-d`（不展开子设备）实现成「只输出整盘」，导致脚本里 `lsblk -dnro TYPE <分区>` 查 `TYPE=part` 这一完全合法的用法在测试里拿到空输出，被误判成脚本缺陷。排障时先在临时目录手工复现伪工具行为再怀疑被测代码，本次即由此定位。0.0.4 给新工具配 fakes 时，每个用到的选项组合都要有一条实测记录，而不是按记忆实现。
18. **桩要打在最小面上，否则用例死在更早的阶段、测不到目标行为**：复刻「劣质介质吞写缓存」时，第一版伪 `dd` 无条件 `exit 0`，但镜像结构校验（`iso_pvd`/`iso_mbr`）本身也用 `dd` 读镜像头，用例直接死在「缺少 ISO 9660 PVD」，回读逻辑根本没被执行。改成 `DD_SWALLOW`：只把 `of=` 落点改到临时文件、读路径原样透传真实 `dd`（且落点必须是普通文件——`/dev/null` 上 `conv=fsync` 返回 EINVAL，又会掩盖真实路径）。判定「桩怎么打」的依据是**被测代码的全部调用点**，不是本用例的关注点。
