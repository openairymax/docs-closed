> ①这三十轮到底踩过哪些坑；②哪些方向曾经错了、错在哪一步；③版本账还剩下哪些没定。

> 版本可判据**」三条重建，每条给出可复算证据；凡只有推断没有证据的，在 §6 显式标为待验证，

## 0. 一个总问题

三十轮讨论表面上是三个问题（基底怎么换、TUI 怎么做、版本怎么排），实质是同一个问题：

> **在 0.0.10–0.0.30 用自有闭包替换基底的这条长周期主线，能不能在 0.0.31 收口，
> 而不把 0.0.5 / 0.0.6 这两个当期交付拖死？**

三本台账都是这个总问题的分解：问题台账记「已经付出的代价」，方向台账记「已经改过的答案」，
版本台账记「还没定的边界」。政委的质询（§4）全部指向同一处：**判据是否可执行**。

## 4. 政委质询与答复

政委只问七个问题，每个都要求「拿判据来，不要拿计划来」。

**Q1：0.0.30 完成自有基底，与「永久双基底」是否矛盾？**
不矛盾，但措辞要改。「完成」指 L0–L3 达 S2、L4 达 S1（§3.1），不是「上游消失」。
0.1.1 只切默认发布形态，上游形态永久保留为追新与回退通道。
**遗留**：0.0.30 的「完成」与 0.1.1 的「默认切换」之间隔着一个 0.0.31 与 0.1.0，
这段窗口里两种形态谁承担 CVE 修复，账上没有答案。

**Q2：500–900 这个数至今是推算，凭什么当立法基础？**
不能当立法基础，只能当**预算区间**。它是 `comps` 递归 BuildRequires 的合理估计，
但没有一次 `repoquery --requires --resolve` 的全量实测。
处置：登记为 O-1，0.0.10 开工前必须产出实测闭包清单；实测与区间偏差 >20% 时，
§2.2 的替换窗口表整体重排，不得按原表硬推。

**Q3：0.0.5 同时要 TUI 全 Rust、190 份文档功能、四通道输入，是不是已经超载？**
是。当前账上 0.0.5 有：五个 crate、36 条功能缺口、KRN-01 与 I-27 两条需内核能力、
RISC-V 用户态补齐、以及「严禁桩」。这不是一个版本的量。
**答复**：0.0.5 按「用户态面 + 已有 ABI」口径收口（§1.2 裁定 1），且**不接受登记缺口**
（2026-11-17 裁定）。执行方式：M1/M2 双里程碑，M2 全绿才发版；凡需内核能力的
（KRN-01、I-27、12 条未定版本项、RISC-V 用户态）逐条**二选一**——抬基线纳入，
或显式移出范围并同步删 §0.2 总账分母（base-definition §7.2）。不得留作缺口。

**Q4：IME 方案一天翻两次，下一次翻车谁承担？**
翻转本身不贵：三次方案都还没写代码，沉没成本为 0。贵的是**第三次仍可能错**。
因此现口径配了三条可判负约束，而不是再写一段理由：
① `KeySource` 只产键码不产文本；② 无词典报 `ime=no-dict`，只允许显式 ASCII 直通；
③ `kill -9` 后 200 ms 内按 `seq` 重放不丢键（V-11）。
若这三条实测不过，方案作废重来，不以「已写进文档」为由保留。

**Q5：四件工具都没实现，文档里的 A-8/A-9/S-1–S-6/B-1–B-6 是判据还是意愿？**
目前是**意愿**。`profile_expand.py`、`base-parity.sh`、`signature-chain.sh`、
`abi_snapshot.py` 四件全部未落地，所以这些条目一条都不能标「达标」。
处置：工具先行——先实现 `profile_expand.py` 与 `base-parity.sh`（A-8 完全依赖它们），
再谈 0.0.10 窗口开工；`signature-chain.sh` 与 `abi_snapshot.py` 分别挂 0.0.24 与 0.0.16 前。

**Q6：0.0.6 的 dock 会不会长成第二个执行面？**
这是本项目已经犯过一次的错（历史：TUI 自持 `GatewayClient` 直连 RPC，状态所有权不在 CLI）。
现口径的防线是「共享契约不共享代码」，但这句话本身不可判定。
**答复**：0.0.6 立项时必须先写三条门禁再写界面——
① dock 不得 import boot TUI 的任何 runtime crate；② dock 不得本地持有任务状态，
状态只来自 gateway；③ 两条通路的 `airy.intent/1` 四通道 schema diff 仅允许 `source`/`trace_id`。
三条不过，dock 不开工。

**Q7：版本号从 0.0.21 改到 0.0.31，是战略调整还是工期通胀？**
两者都有，必须拆开看。**战略调整**是真实的：113 包闭包的替换纵深比首轮估计大一倍，
0.0.10–0.0.20 装不下 12 个域的 500–900 个源码包。**工期通胀**也是真实的：
0.0.13–0.0.15 在 §2.2 的窗口表里没有单列，属于「用版本号吸收未知量」。
处置：0.0.5 收口时必须把 0.0.13–0.0.15 的窗口表补齐；补不齐就承认这是空档，
而不是让它以「替换期」的名义存在。
