## 1. 定位

0.0.5 的发版自证回答一个问题：**这一版能不能挂 `v0.0.5` 的 tag**。它不评估功能
完成度——那是 §6 的任务账本与 §15 的验收判据；它只核对「发版所需的四组事实」是否
同时成立，并把结果与日志归档到同一目录。

发版流水线不新增检查（施工图纸 §10）：本门禁消费的全是既有门禁与既有产物，
`--rpm` 指向的包、`--evidence` 指向的实机读数、`--sbom` 指向的依赖清单，都由
对应 WP 产出。任何一组输入缺席，门禁退 5，而不是当作「跳过」。

## 2. 四组判据

| 组 | 判据 | 依据 | 失败示例 |
|---|---|---|---|
| 版本一致性 | `distro/release/os-release` 的 `VERSION_ID` 与 `release.spec` 的 `airy_version` 同源，基线为 `0.0.5`；给 `--tag` 时 tag 去 `v`、去 `-rcN` 后同一基线 | §15.4 | `VERSION_ID=0.0.4`；spec 与 os-release 各写一个版本；`v0.0.4` 的 tag 配 0.0.5 的树 |
| 供应链四件套 | `rust-toolchain.toml` 的 channel 等于 `ci/lib/tui-gate.sh` 的 `PIN`；工作区恰好一个 `Cargo.lock`（`vendor/`、`target/` 除外）；`vendor/`、`vendor.ledger`、`.cargo/config.toml` 齐备；给 `--sbom` 时组件数等于 `Cargo.lock` 的 `[[package]]` 条数 | AC-S1/S2/S3、QG-05 | 第二个 `Cargo.lock`；工具链写 1.89.0 而钉版仍是 1.90.0；SBOM 少记一个组件 |
| 打包清单 | 给 `--rpm` 时用 `rpm -qlpv` 逐条断言 §14.16 的目标路径：六个 TUI 入口必须是 `-rwx` 实体文件（软链判负）、三个 unit 与两个 drop-in、三个会话脚本、polkit 规则、`approvals.d` 目录、至少一个主题 `*.toml` | §14.16 | `boot-ime` 在包里是软链；缺 `airy-session-switch@.service`；主题目录为空 |
| 门禁全集 | 默认（发版口径）逐个执行 `ci/ci.sh <gate>`：`no-stub`、`dead-code`、`lang-lock`、`coupling-scan`、`tui-frame`、`ime-corpus`、`input-matrix`、`tui-e2e`，以及带 `--input` 的 `tui-field`；每个 gate 的日志落 `--out` | §9、§10 发版列 | 任一 gate 失败；`tui-field` 读到夹具而非实机记录 |

「发版口径」还要求 `--tag`、`--rpm`、`--evidence` 三者齐全。缺一项退 5，避免
用「少给输入」换一个绿色结论。`--static` 只核对仓库事实，末行明确打印
「不构成发版结论」，供日常自查与门禁回归使用。

## 3. 调用方式

发版轮次（在持有 RPM 与实机读数的发布机上）：

```bash
ci/gates/release-005.sh \
    --tag v0.0.5 \
    --rpm dist/rpm \
    --sbom sbom-agent-linux-0.0.5-rust.cdx.json \
    --evidence /var/lib/airymax/tui-field/2026-xx-xx \
    --out /var/lib/airymax/release/0.0.5
```

日常自查（任何一台开发机，无需 rpm 与实机）：

```bash
ci/gates/release-005.sh --static
```

两组调用的判据实现完全相同，差别只在于是否执行门禁全集与是否强制要求制品输入。
归档目录固定产出 `release-005-summary.txt`：

```
ver=<VERSION_ID>
tag=<tag 或 none>
mode=<release 或 static>
result=<pass 或 fail>
out=<归档目录>
```

退出码：`0` 通过；`1` 任一判据不成立；`5` 参数不满足（缺发版口径输入、目录或
文件不存在、未知参数）。`5` 与 `1` 分开，是为了让编排层能区分「输入没给全」与
「给了但不合格」——混成一个码会让重试策略无从选择。
