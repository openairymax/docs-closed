> 本文件回答两个问题：镜像构建还有哪些提速手段；「基底分层」该不该做、做在哪一层。
> 结论先行：**分层要做，但分层的单位是「内容寻址的候选取包池」，不是「每版一个 delta 层」**。

## 1. 瓶颈定性（用实测，不用推测）

同一棵树、同一套门禁，`Build desktop ISO in container` 一段的耗时：

| run | 该步耗时 | 备注 |
|---|---|---|
| `40818193756` | 14 min | 健康基线 |
| `40823015605` | 16.5 min | 健康 |
| `40834119367` | 38.9 min | 载荷段劣化 |
| `40839355885` | >46 min，被人工取消 | 载荷段静默 80 分钟 |
| `40866231339` | >135 min（进行中） | 无工具链缓存 + 镜像站劣化 |

段内构成（`40818193756` 日志逐分钟取样）：

| 段 | 实测 | 决定因素 |
|---|---|---|
| checkout / lint / 清盘 / 取介质（1.1 GB） | ~2 min | 固定 |
| 容器内 `dnf install` 工具链 | **25 s 下载**，231 包 / 256 MB | 镜像站 |
| 三个内部 RPM 构建 | ~1 min | CPU |
| **闭包收割（≈2.5 GB / 1000+ RPM）** | **8–12 min，无上界** | **公网镜像站** |
| `mkksiso` 重组 + `implantisomd5`（≈6 GB I/O） | 2–3 min | runner 磁盘 |

两条直接结论：

1. **慢的不是「构建」，是「取包」。** CPU 段合计不到 3 分钟，runners 侧的 I/O 段也在 3 分钟量级；全部不确定性都在公网取字节上。
2. **`ci/container/build-packages.txt` 的工具链不是瓶颈。** 健康网络下 25 秒。`0.0.4-任务输入清单.md` 的 CI-04（预烘 builder 镜像）据此降级：它解决的是「事务级失败」风险，不是耗时。

## 2. 为什么「每版一个 delta 层」不该做

容器镜像的 delta 层优化的是**分发**：让客户端只拉变化的层。但构建提速要的是**本地已有多少字节可以直接用**，这两件事目标不同。

- 计算 delta 需要知道「上一版到这一版差哪些包」，而这个差集**只有求解之后才知道**。
- 求解后既然已经知道差集，直接从本地候选池补齐缺的那几个包，效果与 delta 层完全等价。
- 代价差别却是一个数量级：delta 层要处理层序、合并、manifest 引用链、回滚；候选池只是「按文件名 + sha256 查表」。

因此本设计的分层单位定为：**一个内容寻址的整层，作为候选取包池（candidate pool）**。该层的 tag 由载荷清单摘要决定（见 §4），永远只对应某一份已验证的真实产物，不存在「tag 被覆盖」的语义。

## 3. 三层方案与收益

| 层 | 内容 | 预期收益 | 风险 | 归属 |
|---|---|---|---|---|
| L0 | 容器内 `/var/cache/dnf` 跨轮复用（工具链 256 MB） | ~1 min | 极低，不影响产物字节 | **0.0.3 已落**（`c335647`） |
| L1 | 闭包收割的候选池：本地目录 + `actions/cache` | 8–12 min → 1–2 min | 中（缓存污染、上游漂移） | 0.0.4 |
| L2 | 候选池的远程基底：`ghcr.io/openairymax/airymaxos-payload` 内容寻址层 | 冷 runner 也只需 40–60 s 取层 | 中（新增外部依赖，须可回落） | 0.0.4（层由构建成功后的 `push` 与 §8 的定时预热共同供给） |
| L3 | 产物层分层（ostree / 容器化 rootfs） | 增量交付 | 高（需原子回滚语义） | 0.1.x 自有基底 |

L2 与 FL-04（两层交付：常驻引导盘 + 装机期取载荷）共用同一个 `airymaxos-payload` 通道命名空间，但**层格式不同**：L2 服务构建期，层内是扁平 RPM 池；FL-04 服务装机期，须是可被 anaconda 消费的 repo 形态（含 `repodata/` 与 `comps`）。0.0.4 落地时必须显式区分 tag 前缀（L2 用 `build-`，FL-04 用 `install-`），禁止两拨人各推一个同名包。

## 4. 严谨性要求（这是操作系统，不是网站）

下面六条是硬约束，任何一条不满足即不得合并。

### 4.1 缓存不是正确性来源

候选池只提供**字节**，不提供**事实**：

- dnf 求解每轮真实执行，接受上游最新仓库内容；
- 仓库元数据（`repodata`）**每轮必须新鲜下载**，不得缓存。元数据过期会让求解结果与真实仓库不一致，进而少包——这是唯一会把错误带进产物的路径；
- 每个 RPM 在使用前用 `payload-manifest.txt` 里的 `rpm <sha256> <name>` 行校验。

### 4.2 缓存的键来自结果，校验兜住漂移

缓存目录与远端层的 tag 由「载荷清单摘要」决定：

```
payload_key = sha256(payload-manifest.txt)   # 已含 arch / comps / 每包 sha256
tag         = build-<oe_ver>-<payload_key 前 16 位>
```

这看似循环（清单由求解产生），但正确性不依赖键的准确性：**键只是「大概率的命中提示」，逐包 sha256 才是判据**。键不命中最多是多下一次；键误命中会被 sha256 拦下。

`actions/cache` 的键另加输入摘要前缀以便 restore：`payload-<arch>-<sha256(comps + rpms.in.yaml + ks + mirrors.list 的拼接)>`，`restore-keys` 用 `payload-<arch>-`。前缀只用于挑选候选目录，同样不做正确性假设。

### 4.3 两种「不一致」语义必须分开

| 情形 | 判定 | 动作 |
|---|---|---|
| 候选池里的包与清单 sha256 不符 | 缓存污染或上游漂移 | **丢弃该文件**，重新下载（不是错误） |
| 重新下载的包与清单 sha256 不符 | 同一输入树产出了不同字节 | **硬失败**，`AIRY-PAYLOAD-DRIFT` |

第二条是底线：不可复现的产物不得发布。注意这与「上游更新了包」不冲突——上游一旦更新，求解结果就变了，清单也会变，走的是「清单不同」这条正常分支。

### 4.4 回退必须显式

候选池不可用（目录缺失、`oras` 超时、层摘要不符）时，一律回落全量收割，并**打印固定格式的一行**供门禁与排障判读：

```
payload cache: miss|unavailable <原因> — falling back to full harvest
```

命中时同样打印 `payload cache: hit <n>/<total>`。静默降级不可接受——它会让人误以为「这轮很快」是常态。

### 4.5 冷启动不得劣化

首次构建多出的只有「校验 + 硬链接」。实现必须用硬链接（同文件系统）而非复制，并在候选池与载荷目录跨文件系统时退化为复制（此时在 manifest 记 `mode=copy`）。冷启动相对基线的劣化上限 5%。

### 4.6 磁盘预算要核算

| 项 | 体积 |
|---|---|
| 基础介质（已缓存） | 1.1 GB |
| 候选池 | ≈2.5 GB |
| 载荷 + 组装中间件 | ≈3 GB |
| ISO 产物 | 3.7 GB |
| **合计峰值** | **≈10.3 GB** |

`ci/gates/free-disk.sh` 的腾空间量须按此重算；`actions/cache` 单条上限 10 GB（压缩后）可用，但不得把候选池与介质放进同一条。

## 7. 实施顺序

1. **L1-a**：候选池抽象 + 校验语义 + 显式回退日志。先只读本地目录，不接 actions/cache。跑 T-PAY-1/3/4/6。
2. **L1-b**：接 `actions/cache`，键用 §4.2 的输入摘要前缀。跑 T-PAY-2/7，用两次真实绿跑作证。
3. **L2**：`payload-publish.sh` 的 `push`/`pull`。先只做 `push`（把每轮已验证的载荷推上去），观察若干轮确认层形态稳定，再打开 `pull`。随后接 §8 的 `payload-seed.yml`：先只开探针与 `push`，确认 tag 语义稳定后才允许 `seed-` 层参与 `pc_seed`。
4. **收口**：`build-manifest.txt` 记 payload 段耗时、命中率、`mode=link|copy`、来源分布（cache / ghcr / upstream）；step summary 打一行，超基线 2 倍打 `AIRY-BUILD-DRIFT`（与 CI-08 合并）。

每一步单独 commit + 单独一次绿跑，不得批量迁移后一次性验收（沿用 CI-05 的口径）。

## 8. 定时预热：给 L2 供料（`seed-` 通道）

L2 的层由谁推上去？上面只写了「每轮构建成功后 push」。这留了个空档：没人构建时池是空的，而最需要它的恰恰是「很久没构建、第一次冷启动」的那一轮。补一条定时流水线专供字节，但它的地位必须钉死。

### 8.1 不做的形态：整站镜像上游仓库

把启用的五段（`baseos` / `update` / `epol` / `epol-update` / `everything`）整段镜像到 ghcr，体积在数十 GB 量级——单 `everything` 就远超载荷全集 2.5 GB 一个数量级以上。而且一旦这么做，我们就成了镜像站：要承担更新滞后、上游撤回、保留与带宽的责任，却买不回任何东西，因为构建真正需要的只是求解结果里那一千个包。**镜像求解结果，不镜像仓库。**

### 8.2 四条字节来源，一条判据

| 优先级 | 来源 | tag | 权威性 |
|---|---|---|---|
| 1 | 本地候选池（L1） | — | 仅字节 |
| 2 | 上次已验证构建推的层 | `build-<oe>-<payload_key16>` | 仅字节，可反查到产出它的清单 |
| 3 | 定时预热的层 | `seed-<arch>-<input_key16>` | 仅字节，**不可反查** |
| 4 | 上游镜像 | — | 事实来源 |

四条都过同一道 sha256 闸门（§4.1 / §4.3），没有例外。`build-` 与 `seed-` 的唯一差别是**可追溯性**：`build-` 能从 tag 反查到那份 `payload-manifest.txt`，`seed-` 不能。因此 `seed-` 层永远不得被任何发布物料或装机流程引用；它坏了的最坏后果是这一轮构建回落到全量下载，而不是产物出错。

### 8.3 省带宽：由上游元数据摘要决定要不要跑

每天无条件拉 2.5 GB 是 75 GB/月，其中绝大多数轮次上游根本没变。探针只取各段的 `repodata/repomd.xml`（每段数 KB，五段合计不到 50 KB），拼出：

```
input_key = sha256(五段 repomd 摘要 + comps 摘要 + rpms.in.yaml 摘要 + ks 摘要 + mirrors.list 摘要)
tag       = seed-<arch>-<input_key 前 16 位>
```

目标 tag 已存在 → 直接退出，零下载。openEuler SP2 的 `update` 段以周为量级变动，实际推送约每月 4–8 次。**频率本身不是成本，无门控的频率才是。**

### 8.4 六条约束

1. **不得独立成为事实来源**：预热一律对**实时上游元数据**求解，不复用任何缓存的 repodata；产物只在被 sha256 命中时才被取用。
2. **不得阻断发布**：该 workflow 失败只表示「下次构建回落全量收割」，不设 `needs`、不进 release 门禁；连续失败 3 次才在 issue 告警。
3. **幂等**：同 `input_key` 不重复推送，推送前先查 tag。
4. **原子**：只在本轮 `cl_audit` 全通过、包数与 `count=` 相符之后才 push，禁止推半份。
5. **层可复现**：`tar --sort=name --mtime=@0 --owner=0 --group=0 --numeric-owner`，同字节集必然同 digest，便于去重与回读断言。
6. **推完回读**：pull 回来比对 `layer.digest`、文件数与逐包 sha256，不符即删 tag 并失败。

### 8.5 保留、预算与频率结论

- 每个出 ISO 的架构保留最近 4 个 `seed-`，外加被最近 3 份发布清单引用的全部 `build-`，其余按 tag 删除；GC 放在同一 gate 尾部，不新增 workflow，也不靠人删。
- 一条 `payload-seed.yml`，2 job 上限，内联 `run` 块 0，逻辑全在 `ci/gates/payload-seed.sh`；`ci/workflow-budgets.txt` 新增 `payload-seed.yml 0 2`。
- 存储：4 × 2.5 GB ≈ 10 GB `seed-` 加若干 `build-`。ghcr 公共包不计费，但保留策略必须自动执行。

| 频率 | 月流量 | 结论 |
|---|---|---|
| 每天全量 | 75 GB | 不做，绝大多数轮次上游没变 |
| 每 2 天全量 | 37 GB | 不做，同理 |
| 每 7 天全量 | 10 GB | 可行，但上游刚更新的那个窗口里构建仍会变慢 |
| **每天探针 + 变更才全量** | **≈10–20 GB** | **采用**（`cron: '17 3 * * *'`） |

## 9. 明确不做

- **不做「每版一个 delta 层」**：§2 已论证，收益与候选池等价、复杂度高一个数量级。
- **不做整站镜像上游仓库**：§8.1，体积与责任都不划算，收益为零。
- **不做 `mkksiso` 阶段的压缩调优**：该段是 I/O 绑定，RPM 本身已压缩，再压只增 CPU 不缩字节。
- **不做 ostree**：0.0.x 无原子回滚语义，属 0.1.x 自有基底。
- **不缓存仓库元数据**：§4.1，唯一会把错误带进产物的路径。
