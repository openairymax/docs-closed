## 1. 定位与结论

### 1.1 验收目标分解

验收总目标（用户口径）：**OS 能正常安装、OS 能正常启动、AirymaxOS 以 UKUI 作为 GUI
并能进入图形化桌面，桌面使用内置的 AirymaxOS 壁纸。**

| 0.0.3 目标 | 验收层 | 可观测判据 | 证据 |
|---|---|---|---|
| ① 初步实现完整的 AirymaxOS | L0 静态门禁 | 管理仓全部门禁 workflow 通过 | workflow 日志、门禁 TAP |
| ② OS 能正常安装 | L2 装机 | kickstart 全自动装机成功；分区/日志校验齐备 | `install-test` TAP、每轮串口日志 |
| ③ OS 能正常启动并运行 | L2 冷启动 | BIOS/UEFI 冷启动无 panic；关键单元 active | 串口日志、`systemctl` 快照 |
| ④ UKUI 图形化桌面能正常进入 | L3 桌面会话 | lightdm → 座位会话（autologin 直达 / 未启用时经 greeter）→ UKUI 会话三级登录成功；登录后 `run-smoke.sh` TAP 1..15 全 ok（T5 校验内置壁纸，T8/T9 校验主机名与发行版品牌，T10 校验分辨率策略，T11 EFI 品牌写入，T12 校验免密提权，T13 校验免密桌面，T14 校验运行期软件源，T15 校验启动参数可续） | `AIRYMAX-DESKTOP-READY`、`smoke.tap` |

目标 ②③④ 是本方案的核心；① 是前置门禁，不单独构成发行判据。X11 会话建立只是进入
UKUI 的中间态，**不能单独作为目标 ④ 的通过判据**；登录成功但壁纸不是内置 AirymaxOS
壁纸，同样判为目标 ④ 未达成。

L1「RPM/内核/ISO 组装」是 ②③④ 的前置条件，不是独立验收目标，但其产物完整性必须留档。

### 1.2 执行位置裁定

| 位置 | 能力 | 结论 |
|---|---|---|
| 本机（Ubuntu 26.04.1，8 vCPU / 9 GB） | 实测缺 `qemu-system-x86_64`、`qemu-img`、`mkksiso`、`createrepo_c`、`rpmbuild`、`dnf`，且无 `/dev/kvm` | **不承担 L1–L3**，只做代码修改、静态门禁与 git 推送 |
| 第二台物理机 | 需人工装机、人工取证、不可复现，且验收期间无人值守 | 仅作 P2 阶段的可选真机复验 |
| GitHub 托管 runner | 公开仓 4 vCPU / 16 GB / 14 GB SSD；具备 `/dev/kvm`；passwordless sudo；可访问 openEuler 在线仓库 | **承担 L1–L3 全部执行**（§3） |

**结论：0.0.3 的构建与装机验收在 GitHub 流水线完成，本机不执行任何产品构建。**

### 1.3 能力边界（必须如实登记）

- `AIRYMAX-DESKTOP-READY` 只证明 lightdm 已起、存在活动的座位会话
  （`lightdm*` 服务、`Class∈{greeter,user}`、`Type=x11`），
  **不等于 UKUI 已完全可用**。判据实现在 `distro/desktop/desktop_ready.sh`。
- `distro/ci/run-smoke.sh` 要求 `DISPLAY`、`XDG_SESSION_ID` 与 `ukui-session` 进程，
  必须在已登录会话内执行，SSH 远程执行不能替代。
- 产品 kickstart（`distro/kickstart/airymaxos-workstation.ks`）已启用
  `sshd.service`；autologin 由 `distro/desktop/lightdm/50-airymax.conf` 交付，
  验收夹具只断言、不另写一份配置。
- 因此，**`AIRYMAX-DESKTOP-READY` 仅能证明「X11 座位会话已建立」，
  不能证明「UKUI 能进入」**。目标 ④ 必须在验收夹具（§4）落地并完成登录后
  smoke 后才能判定 PASS；夹具未落地时目标 ④ 为 BLOCKED，发行顺延。

## 2. 验收层次与判据

| 层 | 入口 | 通过判据 | 证据 | 退出码 |
|---|---|---|---|---|
| L0 静态门禁 | `distro/ci/run-lint.sh`；管理仓 `ssot-verify` / `sc-verify` / `codegen-verify` / `dsl-verify` / `abi-verify` | 全部通过，无 FAIL | workflow 日志 | 0 / 非 0 |
| L1 组装 | `distro/ci/run-image-ci.sh --skip-install` | RPM、内核、ISO 全部产出；ISO 回读校验通过 | `image-ci-manifest.txt`、各段 TAP、ISO sha256 | 0 / 1 / 5 / 6 / 77 |
| L2 装机+冷启动 | `distro/scripts/install-test.sh` | 每轮装机在串口出现完成标记、冷启动达到 `--boot-marker`、串口无 `BOOT_FAIL` 与 `INST_ERR` | TAP 14、每轮串口日志 | 0 / 1 / 5 / 6 / 77 |
| L3 桌面会话 | `distro/ci/run-smoke.sh <target>` | TAP 1..15 十五条全 ok，无 `not ok`/`SKIP`；报告侧从 TAP 计划推导探针数，不复制常量 | `smoke.tap` | 0 / 1 / 77 |

L2 的 `BOOT_FAIL` 规则（`Kernel panic|Welcome to emergency mode|`
`dracut-initqueue.*timeout|AIRYMAX-BOOT-DEGRADED|AIRYMAX-DESKTOP-FAIL|`
`AIRYMAX-SMOKE-FAIL`）已随 P1 落地（distro `5e80019`），判定集在 distro
`ec30e87` 收敛，见 §4.3。串口里的「Failed to start」不进判定集：它在启动后
数秒即出现，据此提前收尾会让启动腿在桌面尚未拉起时结束，既掩盖「UKUI 能否
进入」的证据，也把单元失败与桌面失败混成同一结论。单元失败以会话内探针
`airymax-desktop-ready.service` 读到的 systemd 记账为准——无失败单元打印
`AIRYMAX-BOOT-HEALTH failed=0`，有则打印
`AIRYMAX-BOOT-DEGRADED failed=N units=a,b` 并非零退出；宿主机只用后者判负，
串口文本仅供归因（`install-test.sh` 的 `note_units` 列出失败单元名）。

装机判定只读串口日志：kickstart 的 `%post --log=` 会把脚本输出重定向到目标
系统文件而不经过串口，故完成标记由 `mark()` 显式写 `/dev/console`，`%post`
断言失败时由 `trap ... EXIT` 输出 `AIRYMAX-INSTALL-FAIL rc=$?`，该标记与上述
`BOOT_FAIL` 同属安装失败模式，命中即判负，不必等 `--install-timeout`。契约
细节见 `docs-linux` `03-installer-design.md` §9.3。

同一判定还覆盖 rpm 事务级错误（`Error in <TYPE> scriptlet`、`An error occurred
during the transaction`）：scriptlet 失败后 anaconda 停在 `按 ENTER 退出:`
等待输入而不退出进程，若只认 `AIRYMAX-INSTALL-FAIL`，失败会被拖成整个
`--install-timeout`。安装腿判负后该轮启动腿置 `skipped: install failed`，
不再在空盘上消耗 `--boot-timeout`；两条腿每 30 秒回显一次串口尾行，使失败
现场在 workflow 日志中直接可读。

### 2.1 内置壁纸的运行时判据

内置壁纸由 `airymaxos-release` 一次安装为三处事实（详见
`agent-linux/distro/desktop/README.md`「默认壁纸」）：

| 项 | 路径/键 | 通过判据 |
|---|---|---|
| 图像 | `/usr/share/backgrounds/airymaxos/airymaxos-default.jpg` | 存在、非空，sha256 为 `fee7f439834ac7dacfc75deaf80a1db1c4bc7459583248eecc87125d52a5ef18` |
| 注册表 | `/usr/share/ukui-background-properties/airymaxos-default.xml` | 含 `<!DOCTYPE wallpapers SYSTEM>`，`filename` 指向上述图像 |
| 默认背景 | `org.mate.background picture-filename` | 取值等于上述图像路径（`peony-qt-desktop` 据此绘制） |

T5 已随 `run-smoke.sh` 落地（distro 子仓 commit `59d9148`），在已登录会话内执行：

```bash
gsettings get org.mate.background picture-filename
sha256sum /usr/share/backgrounds/airymaxos/airymaxos-default.jpg
```

schema 或键缺失判 FAIL，不按 SKIP 处理——`mate-desktop-libs` 是
`ukui-settings-daemon` 的硬依赖，缺失即产品缺陷；校验 sha256 是为了防止镜像被
openEuler 默认壁纸替换后仍误判通过。

### 2.2 L1 载荷完整性判据

安装闭包由 `distro/scripts/lib/closure.sh` 在构建容器内求解：包规格与排除项从
kickstart 经 `distro/tools/ks_spec.py` 提取（SSoT，禁止另抄包名），再补 anaconda
无条件追加的 `@core`，用 `dnf install --downloadonly` 解出完整事务并收进
`/airymax/Packages`。L1 侧判据：

| 项 | 判据 | 失败含义 |
|---|---|---|
| 求解成功 | L1 日志含 `闭包收割: 新增 N` 且 N>0；`logs/closure.log` 无 `Error` | 事务不可解或仓库不可达，装机必然缺包 |
| 载荷自洽 | `payload-manifest.txt` 的 `count` 等于 ISO 内 `/airymax/Packages` 的 RPM 数；ISO 内 `repomd.xml` 与源目录逐字节一致 | 载荷与索引不同步，anaconda 解析失败 |
| 离线可装 | 装机串口日志不出现对 `repo.openeuler.org` 的取包失败（`Curl error`/`Cannot download`） | 闭包有缺口，须回到 L1 补包 |

安装器除配方显式条目外还有一组隐式需求，构建期必须用同一份定义求解，否则
会在装机现场才暴露缺失：

| 隐式需求 | 来源 | 落地方式 |
|---|---|---|
| 基础用户空间 | anaconda 在 `%packages` 未加 `--nocore` 时无条件追加 `@core` | 两个剖面统一 `%packages --nocore`，改由 comps 的 `airymax-core` 组显式供包（上游 core 组 mandatory/default 的投影，剔除上游身份包） |
| `grub2-tools` | anaconda `Bootloader` 段 | `airymax-core` 的 mandatory 条目；组内成员只按包名匹配，虚拟名不能入组 |
| `chrony` | anaconda 时区 NTP 配置 | `airymax-core` 的 mandatory 条目 |
| `grub2`（虚拟名）、`grub2-efi-*`、`shim-*`、`efibootmgr` | 引导器装载：`GRUB2.packages` 请求虚拟名 `grub2`，上游由架构相关包提供 | kickstart 无法按架构表达、`comps.dtd` 无 `arch` 属性，由 `closure.sh` 的 `cl_boot` 按架构收割补齐：x86_64 为 `grub2-pc`/`grub2-efi-x64`/`shim-x64`/`efibootmgr`，aarch64 为 `grub2-efi-aa64`/`shim-aa64`/`efibootmgr` |

`comps_lint` 的 C012/C013/C014 把这张表锁进 L0：`%packages` 未关闭隐式 `@core`
而 comps 未定义 `core`、关闭后缺少 `@airymax-core`、或组内缺少安装器所需包
（退化为 optional）都会在静态门禁失败。`ks_spec.py resolve` 再在闭包构建的
载荷上验一次：组内每个成员都必须能按包名解析到包，否则整份构建作废。

## 3. GitHub 执行方案

### 3.1 平台能力与硬约束

| 项 | 事实 | 对方案的影响 |
|---|---|---|
| runner 规格 | 公开仓 4 vCPU / 16 GB / 14 GB SSD；私有仓 2 vCPU / 8 GB / 14 GB | 磁盘是首要瓶颈；私有仓会把内核构建时间拉长约一倍 |
| KVM | 托管标准 runner 实测提供 `/dev/kvm`（run 39371790961 记录加速器 `kvm`） | `install-test.sh` 检测到 `/dev/kvm` 即 `-accel kvm`，缺失则回退 TCG；加速器写入 TAP 头与 manifest，预算仍按 TCG 最坏情况保留 |
| 磁盘 | 14 GB 有效空间，预装工具链占比较大 | 构建前清理 dotnet/Android SDK/ghc 等，可回收 20–30 GB |
| ISO 基线 | openEuler 24.03-LTS-SP2 netinst 约 1.0 GiB（完整 DVD 约 4.7 GB） | 只用 netinst 作为 `--iso-base`，禁止用完整 DVD |
| 网络 | 构建阶段需访问 `repo.openeuler.org` 求解并下载安装闭包；安装与冷启动阶段只读 ISO 内 `file://` 仓库 | 装机不再受 GitHub 出网抖动影响；脚本缺省 `install-timeout` 3600 秒，CI 按 §3.5 推导值显式传入 |
| 治理 | 管理仓每个 workflow 最多 2 job；CI 总时长 ≤60 分钟（OS-STD-TEST-011） | 镜像流水线必须走例外与手动触发（§3.6） |

### 3.2 流水线拓扑

新增 `agent-linux/.github/workflows/image-build.yml`：

| 项 | 取值 |
|---|---|
| 触发 | `workflow_dispatch`（必选）；`schedule` nightly（可选，默认关闭） |
| job 数 | 2（`assemble`、`accept`），满足 2-job 上限 |
| `assemble` | `ubuntu-24.04`，`timeout-minutes: 240`，产出 ISO 与清单（模块数随 openeuler_defconfig 涨到两千余，180 分钟会在编译尾段取消 job） |
| `accept` | `ubuntu-24.04`，`timeout-minutes: 300`，`needs: assemble`，执行装机、冷启动与 ISO 发布 |
| artifact | ISO、sha256、manifest、TAP、串口日志；保留 7 天 |
| 门禁定位 | 不进入 PR 门禁，不阻塞日常提交；仅作为发行前必过门禁 |

### 3.3 job `assemble`

1. `actions/checkout@v4`，`submodules: recursive`。
2. 释放磁盘（内联命令，不引入第三方 action）：
   删除 `/usr/share/dotnet`、`/usr/local/lib/android`、`/opt/ghc` 等预装工具链。
3. 下载 netinst ISO 并校验 sha256（来源与校验值固定写入 workflow，禁止浮动 latest）。
4. 以 openEuler 24.03-LTS-SP2 官方镜像启动构建容器，容器内安装
   `rpm-build`、`lorax`、`createrepo_c`、内核构建依赖（gcc/flex/bison/openssl-devel/
   elfutils-libelf-devel/bc/dwarves/cpio）。
5. 容器内执行（`--out` 必须是源码区外的挂载卷，满足 `scripts/lib/outdir.sh` 约束）：

   ```bash
   distro/ci/run-image-ci.sh --out /out --iso-base /iso/netinst.iso \
       --profile desktop --arch x86_64 --skip-install
   ```

6. 核对 `image-ci-manifest.txt` 与 ISO 回读结果（`/ks.cfg`、`inst.ks=`、`inst.stage2=`）。
7. 上传 artifact：ISO、sha256、manifest、各段 TAP 与日志。

`mkksiso` 需要 root 与 loop 设备，容器必须以 `--privileged` 运行；该容器只承担构建，
不改变「严禁在 airymaxhub 源码区内构建」的约束——源码以只读挂载进入，产物落在 `/out`。

### 3.4 job `accept`

1. `apt-get install -y qemu-system-x86 qemu-utils ovmf`。
2. 探测并放开 KVM：`[ -e /dev/kvm ]` 为真时执行 `sudo chmod 666 /dev/kvm`；
   为假时记录 `::warning::` 并按 TCG 继续（结果仍有效，但耗时显著上升）。
3. 下载 `assemble` 的 artifact，校验 sha256。
4. 执行：

   ```bash
   distro/scripts/install-test.sh --iso "$ISO" --out /out/install \
       --runs 1 --firmware both --boot-marker AIRYMAX-DESKTOP-READY \
       --install-timeout 3600 --boot-timeout 900
   ```

5. 上传 TAP、`install-manifest.txt` 与每轮串口日志；manifest 记录加速器与本次
   时限取值，失败时把 `BOOT_FAIL` 命中行提取为工作流注解。
6. P1 阶段追加第二轮：验收 ISO + `--boot-marker AIRYMAX-SMOKE-PASS`（§4.4）。

### 3.5 预算

| 段 | 估算耗时 | 说明 |
|---|---|---|
| 磁盘清理 + 拉取基础 ISO | 3–6 分钟 | 取决于 runner 出网带宽 |
| RPM + 内核构建 | 30–55 分钟 | x86_64 单架构，4 vCPU |
| ISO 组装 + 完整性校验 | 5–12 分钟 | `createrepo_c` + `mkksiso` |
| 装机（含在线仓库，单腿） | KVM 10–25 分钟 / TCG 40–70 分钟 | 双固件各装一次，共两腿 |
| 冷启动（单轮） | 3–6 分钟 | 双固件各启一次 |
| **合计** | **KVM 25–62 分钟 / TCG 90–152 分钟** | 两腿装机 + 两轮启动；超出 60 分钟 CI 预算 |

> **时限推导**：每腿装机 3600 秒、冷启动 900 秒，2×(3600+900) 秒 = 150 分钟，
> 加上 checkout、apt、artifact 下载等固定开销仍小于 300 分钟 job 上限。
> 安装腿失败时该轮启动腿跳过，最坏 2×3600 秒 = 120 分钟；rpm scriptlet 与
> 事务错误已在串口判定中快速判负（§2），不会真的耗尽单腿上限。
> `accept` 的 300 分钟与脚本的两个时限同源于这一条推导；不允许再把 job 上限
> 压回 120 分钟——它与两腿装机的失败上限等值，固定开销必然使其溢出并被
> 平台杀停，连取证步骤都来不及执行。

### 3.6 与 CI 预算、发布流水线的关系

- 60 分钟上限（OS-STD-TEST-011）适用于 PR 门禁；`image-build.yml` 按 `release.yml`
  先例申请发布级例外：`assemble` 180 分钟、`accept` 300 分钟，取值依据见 §3.5。
- 镜像验收**不设 `pull_request` 触发**，避免拖慢日常开发。
- ISO 不由 `release.yml` 产出（该流水线只做 4 架构内核 RPM、SBOM、SDK、OCI）。
- ISO 发行通道的现行结论：`image-build.yml` 由 `workflow_dispatch` 触发，
  `release_tag` 非空时组装 → 双固件装机与冷启动 → **通过后**才推到独立包
  `ghcr.io/openairymax/airymaxos-iso:<tag>`。被否决的做法留档：

  | 否决方案 | 理由 |
  |---|---|
  | 附加到 GitHub Release | 单资产上限 2 GiB，ISO 3.43 GiB |
  | 附加到 AtomGit releases | 网关 3 GiB 直接 `413` |
  | 与基础镜像共用 `airymaxos:<tag>` | 两包同 tag 互相覆盖，`oras pull` 与 `docker pull` 取回哪一个取决于最后一次写入 |
  | 人工下载 Actions artifact 再附加 | artifact 只保留 7 天，且人工环节无法在无人值守轮次复现 |

- 发布时机：`oras push` 挂在 `accept` job 的装机步骤之后，条件里显式写
  `success()`——给出 `if` 表达式后 Actions 不再套用默认 `success()`，否则
  装机失败也会照常发布。验收剖面（`acceptance=true`）自动登录并跑会话内
  冒烟，其 ISO 字节与产品 ISO 不同，因此**不占用发行 tag**。
- 不可变性：`ci/gates/iso-publish.sh` 先与本地产出 `.sha256` 对齐，再上传
  并断言远端 layer digest 等于本地 sha256；同 tag 已存在且摘要相同则跳过
  上传，摘要不同则失败（确需替换才加 `--force`）。layer digest 即文件
  sha256，registry 按内容寻址，「远端就是本地产物」由 registry 自证。
- 取件记录：落盘 `iso-oci.txt`（ref / tag / sha256 / size / layer / pull
  命令），与 `*.iso.sha256`、`payload-manifest.txt` 和两份 TAP 一同归档；
  消费者 `oras pull ghcr.io/openairymax/airymaxos-iso:v0.0.3 -o .` 后自行
  `sha256sum -c` 复核，三重核对见 `tools/airy-flash/README.md`。

## 4. UKUI「真进入」验收缺口与夹具

### 4.1 现状边界

| 事实 | 位置 | 后果 |
|---|---|---|
| 已声明 `user-session=ukui` 与 `autologin-user=airymax` | `distro/desktop/lightdm/50-airymax.conf` | 冷启动直接进桌面，不创建 greeter 会话 |
| 就绪探针按座位策略取并集（`Class∈{greeter,user}`） | `distro/desktop/desktop_ready.sh` | `AIRYMAX-DESKTOP-READY` 覆盖 autologin 与 greeter 两条路径（0.0.3 已修复） |

### 4.2 验收夹具设计（仅作用于验收 ISO）

夹具**不得进入产品 ISO**，通过验收专用 kickstart 叠加层与附加文件实现：

| 组件 | 落地方式 | 作用 |
|---|---|---|
| `airymaxos-acceptance.ks` | `tools/gen_accept_ks.py` 把 `ci/ks/acceptance.part` 插入产品配方最后一个 stop 命令之前，输出到 `${OUT}/acceptance/`（源码区外） | 保留产品配方为单一事实源，叠加层可幂等检测 |
| 座位策略断言 | `%post` 校验 `50-airymax.conf` 的 `autologin-user` / `autologin-session` 与 sshd 的 `PermitEmptyPasswords` | 产品资产退化成空时验收必须判负，不得自写一份配置顶上 |
| smoke 执行入口 | `%post` 写 `/etc/xdg/autostart/airymax-smoke.desktop` | 复用现有 XDG autostart 机制（与 fcitx 同路径），在真实会话内执行 |
| 夹具脚本 | `ci/fixture/` 随 `--add` 进入 ISO 根，`%post --nochroot` 从 `/run/install/repo/` 复制到 `/usr/lib/airymaxos/ci/` | 避免为测试单独构建 RPM，也不污染产品包 |
| 会话内 runner | `ci/fixture/airymax-smoke-run.sh` 调用 `ci/run-smoke.sh`，`timeout 180`，TAP 原子写入 `/var/log/airymax/smoke.tap` | 把 TAP 契约带进验收 ISO |
| 标记转发 | `airymax-smoke-report.service`（root oneshot）轮询 TAP 并输出 `AIRYMAX-SMOKE-PASS/FAIL` | 让宿主机 `install-test.sh` 经串口判定 |

### 4.3 与 greeter 判据的冲突（0.0.3 已收口）

autologin 会让 lightdm **跳过 greeter**，早期探针只认 `Class=greeter` 时
`airymax-desktop-ready.service` 必然失败，以 `AIRYMAX-DESKTOP-FAIL` 结束并被
`BOOT_FAIL` 命中——这是 0.0.3 B 轮 `40526252360` 双固件冷启动失败的唯一根因。

根因修复（不 mask、不打补丁）：`desktop_ready.sh` 的判据改为「服务家族前缀
`lightdm*` + `Class∈{greeter,user}` + `Type=x11` + `State∈{active,online}`」，
两类座位策略共用同一探针；`test_desktop_ready.py` 同步把 `lightdm-autologin|user`
钉为就绪、把 `Class=manager` 钉为拒绝。产品 ISO 与验收 ISO 因此不再需要两套判据：

- 产品剖面断言 `AIRYMAX-DESKTOP-READY`（会话已建立）；
- 验收剖面断言 `AIRYMAX-SMOKE-PASS`（会话内 TAP 1..15 全 ok）；
- `install-test.sh` 的 `BOOT_FAIL` 同时收录 `AIRYMAX-DESKTOP-FAIL` 与
  `AIRYMAX-SMOKE-FAIL`。

### 4.4 验收序列

| 轮次 | ISO | 固件 | 标记 | 证明 |
|---|---|---|---|---|
| A | 产品 ISO | bios + uefi | `AIRYMAX-DESKTOP-READY` | 产品路径的双固件 X11 座位会话就绪（autologin 直达） |
| B | 验收 ISO | bios | `AIRYMAX-SMOKE-PASS` | 已登录 UKUI 图形化桌面内 TAP 1..15 全 ok（T5 内置壁纸，T8 主机名，T9 发行版品牌，T10 分辨率策略，T11 EFI 品牌，T12 免密提权，T13 免密桌面，T14 运行期软件源，T15 启动参数） |

两轮均为 `--runs 1`。**B 轮是目标 ④「UKUI 能进入」的唯一通过依据，A 轮不能替代**；
A 轮证明产品路径的双固件启动与座位会话可达。若时间预算不足，A 轮可降级为
L1 组装时的静态校验，但 B 轮不得降级、不得省略，且发行说明必须同步披露改动。

B 轮由 `run-image-ci.sh --acceptance` 一次完成组装与验收：该参数先调用
`gen_accept_ks.py` 生成组合配方，再以 `--add ci/run-smoke.sh --add ci/fixture`
注入夹具，并把启动标记切到 `AIRYMAX-SMOKE-PASS`。它与 `--ks` 互斥，
且必须提供 `--iso-base`；不得对预构建 ISO 追加夹具。

### 5.3 发行流程

实现顺序与「先验收后发布」的直觉相反，原因是内核 RPM 与 ISO 走两条不同的
流水线，而 ISO 必须装配成与发行版本同一份内核：

1. 任务台账 78/78 收口（已完成）。
2. L0 静态门禁全绿。
3. 打 tag `v0.0.3` 触发 `release.yml`，产出内核 RPM（4 架构）、SBOM、SDK
   tarball 与 OCI 基础镜像；run 结束后把 GitHub Release 置为 **prerelease**：
   此时 G-UKUI-1 尚未取证，不得出现在 latest。
4. 手动触发 `image-build.yml` 的 B 轮（`acceptance=true`、`release_tag=v0.0.3`），
   内核包取自第 3 步的 Release 并按 `.sha256sum` 校验，断言
   `AIRYMAX-SMOKE-PASS`；未 PASS 则停在 prerelease，不得进入下一步。
5. 触发产品轮（`acceptance=false`、`release_tag=v0.0.3`），ISO 在双固件装机
   与冷启动通过后发布到 `ghcr.io/openairymax/airymaxos-iso:v0.0.3`。
6. 用 SSoT 渲染的文本覆盖 Release body（`release_manifest.py --notes`），
   取消 prerelease，标记 latest。
7. 按 §9 完成复核与归档，含 B50 实盘烧录的复核记录。

### 8.1 发行收口规程（tag 与构建同源）

`release.yml` 由 tag 推送触发，构建的是 tag 指向的 commit。一旦在 tag 之后还有
提交进入 `main`，再次触发的制品就与 tag 不再同源，验收报告里的 commit 号也会
对不上。收口必须按下面四步走，不得靠「再跑一次」蒙混：

1. **定桩**：确认目标 commit 上 `kernel-verify`、`airy-verify`、`os-chk-verify`、
   `mgmt-verify`、`codegen-verify`、`ssot-verify` 全绿；记录该 commit 的完整 sha。
2. **重指**：`git tag -f -a vX.Y.Z -m "AirymaxOS vX.Y.Z" <sha>` 后
   `git push -f <remote> vX.Y.Z`。旧 tag 产物与验收记录一并作废，需重新生成。
3. **重建**：tag 推送即新建 `release` run；`concurrency.group: release-${tag}`
   配 `cancel-in-progress: true`，会自动顶掉仍在飞行的旧 run，无需手工取消。
4. **对账**：run 的 `head_sha` 必须等于第 1 步记录的 sha，Release 页附件、
   `image-build` 的 ISO 与 `ghcr.io/openairymax/airymaxos{,-iso}:vX.Y.Z` 的
   构建提交必须同一个；三者任一不一致即判 BLOCKED。

ISO 侧同源：`image-build.yml` 的 `release_tag` 输入必须填同一个 `vX.Y.Z`，
其 `payload-manifest.txt` 记录的 commit 与内核 RPM 的 NVR 一并归档，作为
「可复现烧录」的取证链。
