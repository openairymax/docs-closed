## 第一章：关键决策与设计原则

### 1.1 五大关键决策

本方案由以下五项不可动摇的关键决策驱动：

| # | 决策 | 内涵 |
|---|------|------|
| **决策一** | `AgentOS/` → **AgentRT**；`agentos/` 不变 | 外层目录更名为 AgentRT（Agent Runtime Platform），内层 `agentos/` 作为"智能体原生操作系统"品牌名保留。项目独有的命名体系（Atoms, CoreKern, CoreLoopThree, Cupolas, TaskFlow, HeapStore, MemoryRovol）全数保留，不做任何修改 |
| **决策二** | **分离生态层、整合 SDK、移动部署配置** | C 核心代码与 Python 生态层明确分层；四种语言 SDK 整合为统一 `sdk/` 目录；部署配置独立为 `deploy/` 目录 |
| **决策三** | **先整合已有资产，再新建缺失能力** | 不推倒重来。Manager（11 JSON Schema 配置中心）、OpenLab（Agent 市场 + 应用框架）、toolkit（4 语言 SDK）、ops/deploy/（Docker + K8s）均已有成熟实现，先完成整合连接，再补齐缺失 |
| **决策四** | **commons 是统一基础库，不可随意变动** | `agentos/commons/` 是整个项目的类型权威源和基础设施层，其目录结构、文档、代码均需保持稳定。即便某些子目录当前仅有 README.md，也不得随意删除——它们代表已规划的架构占位 |
| **决策五** | **MemoryRovol 独立成库** | MemoryRovol 是 AgentRT 的商业化核心，拥有 L1-L4 四层记忆架构和提供商可拔插模式。其源码保持在独立仓库（`MemoryRovol/`），`agentos/atoms/memoryrovol/` 仅保留轻量桥接层 |

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **命名美学优先** | Atoms/CoreKern/CoreLoopThree/Cupolas/TaskFlow/HeapStore/MemoryRovol 是项目独有的命名体系，代表设计哲学。任何来自参考项目的技术概念融入时，必须赋予适合 AgentOS 体系的新名称 |
| **C 核心不动摇** | CoreKern、CoreLoopThree、Cupolas、Syscall、TaskFlow、HeapStore 保持纯 C 实现。C 语言边界 = { Agent 运行时执行引擎 } ∪ { 关键基础设施 } ∪ { FFI Bridge } |
| **生态层用最适合的语言** | Manager 和 OpenLab 保持 Python；CLI 用 Rust（单二进制分发）；Prompt 模板用 YAML；Plugin SDK 支持 Rust 和 Python |
| **Provider 模式** | 可拔插架构贯穿始终：MemoryRovol 通过 `memory_provider.h` 提供商业/开源切换；LLM 通过 `agentos.yaml` 声明式接入；插件通过 Plugin SDK trait 注册 |
| **零抄袭风险** | 所有整合进 AgentRT 的外部技术要点，必须重新命名和重新设计接口，与参考项目（openclaw, claude-code, atomcode, openJiuwen, agent-memory-demo, hermes-agent）保持明确隔离 |

### 1.3 命名隔离策略

| 参考项目技术概念 | AgentRT 中的名称 | 说明 |
|-----------------|-----------------|------|
| openclaw Plugin System | **AgentRT Plugin SDK** （`agentos_plugin_api_t`） | 全新的 C FFI 接口设计，不复制参考项目的类型定义 |
| openclaw Hook System | **AgentRT Hook 系统** （`hook_manager.c`） | 独立设计的生命周期事件模型 |
| agent-memory-demo Prompt 模板 | **AgentRT Prompt 模板库** （`ecosystem/prompts/`） | 基于 Manager YAML Schema 体系的 Prompt 管理 |
| openJiuwen Pregel 图计算 | **TaskFlow** （已存在） | 项目自有命名，BSP 超步模型 |
| atomcode CLI/TUI | **AgentRT CLI** （`sdk/cli/`）| 全新 Rust 实现，独立命令体系 |
| openJiuwen Agent Store | **OpenLab Markets** （已存在） | 项目自有命名和架构 |
| openclaw 声明式配置 | **Manager Schema 体系** （已存在） | 基于 JSON Schema 的三层配置覆盖 |

## 第二章：目录结构重组方案

### 2.1 重组原则

1. **外层改名**：`AgentOS/` → `AgentRT/`（唯一的外层改名）
2. **内层不变**：`agentos/` 及其下所有 C 核心目录名全数保留（commons/, atoms/, corekern/, coreloopthree/, cupolas/, syscall/, taskflow/, frameworks/, daemon/, gateway/, heapstore/, protocols/, memory/, memoryrovol/）
3. **生态分离**：Python 生态层组件（Manager, OpenLab）从 `agentos/` 移至顶层 `ecosystem/`
4. **SDK 整合**：四语言 SDK 从 `agentos/toolkit/` 移至顶层 `sdk/`；根级 `toolkit/`（Python 工具链）也随之整合
5. **部署独立**：`ops/deploy/` 移至顶层 `deploy/`
6. **保持兼容**：所有移动操作需同步更新 import 路径、CMakeLists.txt、CI 脚本、文档引用

### 2.5 commons 的特殊处理

`agentos/commons/` 是整个 AgentOS 的**统一基础库**。根据决策四，其处理原则如下：

| 原则 | 说明 |
|------|------|
| **不删除任何目录** | `utils/` 下的 18 个子目录，无论是否仅有 README.md，均代表已规划的架构占位。删除占位目录 = 破坏架构完整性 |
| **不修改目录结构** | commons 的 `platform/` + `include/` + `utils/` + `tests/` 四层结构保持稳定 |
| **可新增、可补充实现** | 对于仅有 README.md 的子目录（如 cache, compat, cost, network, platform, quality, resource, security, strategy, uuid），可在后续版本中补充 .c/.h 实现，但不删除目录本身 |
| **类型系统不可变** | `include/agentos_types.h` 是全项目唯一类型定义权威源，任何类型变更需全局影响评估 |
| **内存管理宏不可变** | `AGENTOS_MALLOC` / `AGENTOS_FREE` / `AGENTOS_CALLOC` 已在全项目落地，不可回退 |

## 第五章：四项关键缺失能力

### 5.1 Hook 系统

#### 5.1.1 设计目标

在 Agent 运行时的关键生命周期节点注入用户自定义逻辑。Hook 系统参考 openclaw `hooks.ts` 的事件模型，但使用 AgentRT 独立的生命周期事件定义和 C 语言实现。

#### 5.1.2 Hook 生命周期事件

```
Agent 生命周期:
├── on_agent_init        ← Agent 初始化
├── on_agent_start       ← Agent 开始执行
├── ┌─── 循环 ───┐
│   │ on_cognition_start  ← 认知阶段开始
│   │ on_intent_parsed    ← 意图解析完成
│   │ on_plan_generated   ← 计划生成完成
│   │ on_tool_call        ← 工具调用前（可拦截）
│   │ on_tool_result      ← 工具调用后
│   │ on_cognition_end    ← 认知阶段结束
│   │ on_memory_write     ← 记忆写入前
│   │ on_memory_evolve    ← 记忆演化后
│   └────────┘
├── on_agent_stop        ← Agent 停止
├── on_agent_error       ← Agent 错误（可中断流程）
└── on_agent_destroy     ← Agent 销毁

LLM 生命周期:
├── on_llm_request       ← LLM 请求发送前（可修改 prompt）
├── on_llm_response      ← LLM 响应接收后（可过滤/增强）
└── on_llm_error         ← LLM 调用失败（可重试/切换）

MemoryRovol 生命周期:
├── on_l1_write          ← L1 原始数据写入前
├── on_l2_embed          ← L2 嵌入生成后
├── on_l3_bind           ← L3 实体绑定后
└── on_l4_rule           ← L4 规则发现后

安全事件:
├── on_permission_check  ← 权限检查时
├── on_sanitize          ← 输入净化时
└── on_audit             ← 审计记录写入时
```

#### 5.1.3 Hook 配置

通过 Manager 的 YAML 配置体系管理：

```yaml
hooks:
  enabled: true
  hook_dirs:
    - "/etc/agentos/hooks.d/"
    - "~/.agentos/hooks/"
  global_hooks:
    on_tool_call:
      - hook: "security_audit"
        priority: 100
      - hook: "cost_tracker"
        priority: 50
    on_llm_request:
      - hook: "prompt_injector"
        priority: 200
    on_agent_error:
      - hook: "alert_notifier"
        priority: 10
```

#### 5.1.4 实现架构

```
hook_d (daemon/hook_d/)
├── hook_registry.c       ← Hook 注册表（按事件分类）
├── hook_executor.c       ← 顺序/并行执行 Hook 链
├── hook_interceptor.c    ← 拦截型 Hook 处理器（可阻止操作）
└── hook_timeout.c        ← Hook 执行超时保护（默认 5s）
```

三种 Hook 实现模式：
- **Shell Hook**：可执行脚本，接收 JSON via stdin
- **Python Hook**：基于 Python Plugin SDK 的 `HookPlugin` 基类
- **Webhook**：HTTP POST 到外部服务，支持签名和重试

#### 5.1.5 官方 Hook 集合（`ecosystem/hooks/`）

### 5.2 Plugin 系统

#### 5.2.1 设计目标

支持通过 Plugin SDK（Rust/Python）扩展 AgentRT，无需修改 C 核心代码。Plugin 模型包含三种类型：Provider（LLM 提供商）、Tool（工具）、Hook（生命周期钩子）。

#### 5.2.2 Plugin 模型

```
Plugin = Manifest + Type + Implementation

Manifest (plugin.yaml):
  name: "my-custom-tool"
  version: "1.0.0"
  type: "tool"                   # tool | provider | hook
  language: "rust"               # rust | python
  description: "..."
  author: "community"
  entrypoint:
    rust: "target/release/libmy_plugin.so"
    python: "plugin.py"
  permissions:
    - network:api.example.com
    - filesystem:read:/tmp
  config_schema:
    api_key:
      type: string
      env: "MY_API_KEY"
```

#### 5.2.3 C FFI Bridge

Rust/Python 插件通过稳定的 C ABI 与 AgentRT 核心通信：

```c
// agentos/atoms/corekern/include/agentos_plugin_bridge.h

typedef struct agentos_plugin_api_t {
    // 日志
    void (*log)(int level, const char *message);
    
    // 内存管理
    void* (*alloc)(size_t size);
    void  (*free)(void *ptr);
    
    // LLM 调用（回调到 llm_d）
    int (*llm_chat)(const char *request_json, char **response_json);
    
    // MemoryRovol 访问
    int (*memory_write)(const char *record_json, char **record_id);
    int (*memory_read)(const char *record_id, char **record_json);
    int (*memory_search)(const char *query_json, char **results_json);
    
    // 错误处理
    void (*error_push)(int code, const char *message, const char *file, int line);
    
    // 遥测
    void (*telemetry_emit)(const char *metric_name, double value);
} agentos_plugin_api_t;
```

```
│   ├── lib.rs                        ← 重导出
```

#### 5.2.5 实现架构

```
plugin_d (daemon/plugin_d/)
├── plugin_discovery.c    ← 扫描 plugin_dirs 发现插件
├── plugin_loader.c       ← 加载 .so/.dylib (Rust) 或 import (Python)
├── plugin_validator.c    ← 校验 manifest、权限、依赖、兼容性
├── plugin_lifecycle.c    ← Discovery → Load → Validate → Activate → Run → Deactivate → Unload
└── plugin_registry.c     ← 注册到 provider_registry / tool_registry / hook_registry
```

#### 5.2.6 Plugin 生命周期

```
Discovery → Load → Validate → Activate → [Run] → Deactivate → Unload

1. Discovery: agentos 启动时扫描 plugin_dirs
2. Load: 读取 plugin.yaml manifest
3. Validate: 检查权限、依赖、兼容性
4. Activate: 注册到对应的注册表
5. Run: 插件在 Agent 运行时被调用
6. Deactivate: 热卸载或关闭时注销
7. Unload: 释放资源
```

#### 5.3.4 Prompt 加载与使用

```c
// 加载 Prompt 模板（带缓存）
agentos_prompt_t *prompt = agentos_prompt_load("memory/extract_facts", "1.0.0");

// 渲染 Prompt（变量替换）
char *rendered = agentos_prompt_render(prompt, 
    AGENTOS_PROMPT_VAR("conversation_text", conversation_text));

// 调用 LLM
agentos_llm_response_t *resp = agentos_llm_chat(rendered, 
    prompt->temperature, prompt->max_tokens);
```

## 第八章：总结

### 8.1 核心逻辑

> **AgentRT v0.1.1 的核心任务 = 结构重组（AgentOS→AgentRT + 生态分离 + SDK 整合 + 部署独立）+ 核心连接（FFI Bridge + Manager/OpenLab 与 C 核心的联动）+ 补齐四项关键缺失能力（Hook/Plugin/Prompt/CLI）。**
>
> **不需要推倒重来任何已有系统。不需要修改任何既有命名。不需要删除 commons 的任何文件。MemoryRovol 保持独立商业化路径。**

### 8.2 命名隔离保证

- 所有整合进 AgentRT 的参考项目技术要点均赋予与 AgentOS 体系一致的新名称
- 不复制参考项目的接口定义、类型结构、文件结构
- Hook 系统 = 独立的生命周期事件模型 + C 实现
- Plugin 系统 = 全新的 `agentos_plugin_api_t` C FFI 接口
- Prompt 体系 = 基于 Manager YAML Schema 的独立格式
- CLI = 全新 Rust 实现的独立命令体系
