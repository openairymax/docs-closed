## 0. 全链根因模型（九项根因链终态）

蓝图调度挂死不是单点故障，而是**九项缺陷的串联放大**：任一环超时/失败/静默，都会让上层把"慢"放大成"挂死"。九项根因链在预备期已全部定位，其中六项已修复并验证：

### 2.1 预算链终态（已固化，防回归基线）

```
tool 执行 20s < runner IPC 30s < agent_d invoke 170s < CLI 总预算 180s
```

- 任何一层预算不得 ≥ 上层剩余预算（p11 修复的倒挂缺陷）；
- agent\_d SIGTERM 路径：中断当前 invoke → 级联杀 runner 子进程 → join 回收（p10）；
- `platform_compat.c` `airy_daemon_read_request` 8MB 循环读、`daemon_rpc_client.c` 16MB 上限、`binder_internal.h` zero-copy（p9\~p12 批次）；
- 大 payload IPC 读取改为循环读，修复 daemon 侧 request 截断。

### 2.3 runner LLM 截断根因与修复（p6，已闭环 + 防回归）

**现象**：fs\_write 大 payload 时内容截断，蓝图节点空转挂死，16 轮烧尽后 `TOOL_LOOP_OVERFLOW`。

**根因链（全部位于 runner 执行体 LLM 客户端层，不经过 llm\_d——LLMClient aiohttp 直连厂商端点，llm\_d 流式聚合嫌疑彻底排除）**：

1. 厂商默认输出上限截断 arguments JSON；
2. `finish_reason` 完全未检查；
3. `json.loads` 失败后静默降级 `{"_raw": …}`，截断信号被吞；
4. 指纹检测对「每次截断内容不同」不敏感（指纹含 raw\_args，每次都不同 → 永不判重）。

**修复（三处系统性修复，非补丁）**：

- `orchestration/core/llm.py`：`_resolve_max_tokens()`（显式参数 > `$AIRY_LLM_MAX_TOKENS` > None 不发送，沿用厂商默认）；`chat()` payload 按解析结果发送/省略 `max_tokens`（L250-263、L344-346）；
- `orchestration/agents/llm.py`：`execute()` 检测 `finish_reason in ("length", "max_tokens")`（L203-204）——截断且 args JSON 损坏 → **立即 fast-fail** **`TOOL_ARGS_TRUNCATED`，不烧轮次**（L251-266）；纯 content 截断 → 显式标记 + `metrics.truncated`（L206-223）；
- `_invoke_tool` 畸形 args 显式回传错误 JSON（`invalid tool arguments JSON` + `arguments_head`），废弃 `_raw` 静默降级（L408-419）。

**测试**：`test_llm_client.py` TestResolveMaxTokens 4 用例 + TestChatPayload 3 用例（fake aiohttp 经 `sys.modules` 注入命中懒导入，L358）；`test_llm_agent.py` 4 用例覆盖 fast-fail 不烧轮次 / 合法不误杀 / content 标记 / 畸形显式回传。**全量回归 158 passed**。

**残余登记**：本修复只覆盖「截断」这一类连败；⑤ 的通用连败 fast-fail（连续异型错误熔断）仍开放，归 §3.1 R1。

## 3. 本版施工清单

### 3.1 R1 蓝图调度挂死收尾（④⑤⑨）

**R1-a tool\_d 并发与取消模型（④）—— 已落地（含本轮根因收口）**

- 现状：tool\_d 执行面单线程；p9 的有界化只保证「单个工具必返回」，不保证「一个慢工具不拖死其它会话」。
- 施工：执行面改造为有界并发（worker 池）+ 每任务携带 deadline（p9 已注入的预算参数复用）+ 取消语义（deadline 到期即终止该工具执行并回报，不影响 worker 池其它任务）。
- 验收：并发两个会话，其一注入超时工具，另一会话工具调用不受影响；被取消工具返回明确取消错误码。

**本轮根因收口（单点 deadline 全链同源）**

p9 落地的池解决了「隔离」，但 deadline 存在**双口径**：池按 `max(meta, executor_timeout)` 等待，
而执行面外部 execvp 路径只取 `executor_timeout`。后果有三：per-tool 预算被忽略（外部路径按默认值计时）、
被判超时的进程其实仍在跑（detach 变成"假取消"）、`max_workers` 配置面是死字段。收口为**唯一 deadline 所有者**：

- `executor_budget_ms(exec, meta)` 成为唯一取值面：per-tool 元数据优先，未声明回退 `executor_timeout_sec`。
  三条路径同源——内置路径 `btimeout_ms`、外部 execvp 路径 `timeout_ms`（经
  `tool_execute_args_t.timeout_ms` → `airy_sandbox_invoke` → `sys_tool_execute` →
  `airy_process_run_capture`，进程到期即 SIGKILL）、池等待 `wait_budget_ms`。
- `executor_pool.c` 的等待预算改为 `executor_budget_ms(...) + WAIT_SLACK_MS (+ 交互审批上限)`：
  slack 只需覆盖 SIGKILL 后的 drain/reap 窗口，进程期限与等待期限 lockstep。
- 缺口 ④ 接线：worker 数来源优先级 **env** **`AIRY_TOOL_EXEC_WORKERS`** **>** **`executor.max_workers`** **> 内置默认 2**
  （越界回落默认），`executor_max_workers()` 为取值 API，`tool_executor_create` 不再硬写 1。
- 缺口 ⑤ 清理：删除 `tool_builtin_internal.h` 中陈旧的 single-worker 注释，注释与池化并发模型一致。
- 缺口 ①（tool\_d cancel RPC）裁决：**不扩 IPC**。真终止由进程级 deadline 负责（到期 SIGKILL），
  detach 降格为「工具在预算内未返回（阻塞于不可中断系统调用）」的兜底；`agent_d`/`sched_d` 已有 cancel 先例，
  `tool_d` 的 cancel 通道属后续版本项，本版不做重复通路。

**验收证据**：`test_executor_pool.c` 新增 `test_pool_per_tool_budget`（meta=1s 而 executor 默认 30s →
必须在 \~1s 内被真终止并返回 `TOOL_RESULT_CLASS_NORMAL_FAIL` + `timed out`），手工运行实测
`per-tool budget 1s terminated in 1022ms`；定向 `ctest -R "test_executor_pool|test_pool_e2e"` 2/2 Passed；
全量回归 **216/216（100%）**，Total 139.13s，退出码 0。

**R1-b LLM 工具循环通用连败 fast-fail（⑤ 非截断类）—— 已落地**

- 现状：截断类已 fast-fail（p6）；但连续 N 轮「非截断型失败」（如网络错、429、无效响应交替出现）仍会烧满 16 轮。
- 施工：在 `orchestration/agents/llm.py` 工具循环内加**连败计数器**：连续 `K`（建议 3）轮任何失败型结果（fast-fail、异常、无效响应）即熔断，返回 `TOOL_LOOP_CONSECUTIVE_FAILURES`，错误信息汇总最后 K 个原因。与既有指纹检测（同参同果）互补：指纹管「原地打转」，连败计数管「反复跌倒」。
- 验收：脚本化 LLM 连续返回 3 次失败 → 第 3 轮熔断，`llm.calls == 3`，不达 16。

**落地实现**（`1d900f5 airy/llm: circuit-break the tool loop on consecutive tool failures`，本轮补齐契约面）：

- `DEFAULT_TOOL_FAIL_LIMIT = 3` + `_tool_fail_limit()`（env `AIRY_TOOL_FAIL_LIMIT` 可调，非法值 / <1 回退默认）；
- 计数口径：`_result_is_error()` 判定工具结果错误载荷（`{"error": ...}` JSON；纯文本不判失败，
  宁可漏判不误杀）；成功即清零，`_invoke_tool` 的未注册 / 畸形参数 / 异常三类错误同样计入；
- 熔断回报：`error_code = TOOL_LOOP_CONSECUTIVE_FAILURES`（与 `TOOL_LOOP_DETECTED` /
  `TOOL_LOOP_OVERFLOW` 同族），错误信息经 `_error_brief()` 折叠汇总**最后 K 个原因**
  （形如 `fs_write: no such file: a.txt | fs_write: ... | ...`），上层无需回捞工具日志即可判读；
- 与同指纹检测互补：指纹管「同参同果原地打转」（3 次警告 / 4 次终止），连败计数管
  「次次失败但参数各异」的系统性故障；截断类仍走既有 `TOOL_ARGS_TRUNCATED` 即时 fast-fail，不占连败额度。

**验收证据**：`tests/orchestration/test_llm_agent.py::TestLLMAgentConsecutiveFailures` 4 用例
（3 连败熔断 + `llm.calls == 3` 且错误含 3 条原因摘要；成功清零不熔断；纯文本不计失败；
`AIRY_TOOL_FAIL_LIMIT=1` 单败即熔断 + 非法值回退）。单文件 8 passed；全量 **187 passed, 1 skipped**。

**R1-c 角色词汇表 SSoT（⑨ C 侧）**

- 现状：Python 侧 `ROLE_ALIASES` 兜底已生效；C 侧各处角色字符串字面量仍可能漂移。
- 施工：C 侧角色名收敛到单一头文件常量（与 Python `ROLE_ALIASES` 逐一对齐），全仓字面量替换；CI 加 grep 门禁禁止新增裸字面量。
- 验收：grep 全仓 C 源码角色字面量仅存于 SSoT 头；GCCP + 蓝图 e2e 复验。

### 3.2 R2 蓝图语义正确性（p4 定位的三缺陷）

预备期端到端审查发现：即便调度不挂死，**DAG 产物在语义层面不可信**。三缺陷：

**A. 规划降级为纯校验（最重）**

- 现象：`reactive` 路径的规则表与兜底动作表**全部是校验类动作**，且规则以英文关键词匹配——中文任务几乎必然全 miss → 退化为「逐条校验型 DAG」，无法完成生成型任务。
- 施工：规则表与兜底动作表补全生成型动作集；关键词匹配支持中文同义词（或改由 LLM 规划兜底，规划失败不得静默降级为校验集）。
- 验收：中文生成型任务（如 GCCP 实题）产出的 DAG 包含生成类节点且最终产物非空。

**B. 上游产出不注入下游输入**

- 现象：`sched_dag_agent_input` 仅回填节点自身 goal，上游节点 output 不进入下游 input → 多节点 DAG 各自为战，产物无法衔接。
- 施工：DAG 执行器在派发下游节点时，将直接上游的 output（受长度预算约束）注入其 agent input。
- 验收：两节点依赖链 e2e——下游产物引用上游产出内容。
- 状态：**已落地**（daemons `2bb03bf`）；预算按直接上游数等分，共享预算不被单一大产物独占；`test_dag_upstream_inject` / `test_dag_upstream_inject_par` 覆盖链式与扇入两种图。

**C. DAG success 语义 = 进程级成功**

- 现象：节点进程退出码 0 即记 success，语义级失败（产物为空/工具全败/LLM 拒答）误报成功，蓝图结果不可信。
- 施工：节点成功判定增加语义校验（产物存在性与非空由节点类型定义；失败时节点标记 `semantic_failed` 并向上汇总），蓝图终态区分 `success / semantic_failed / failed`。
- 验收：注入「产物为空」场景 → 蓝图终态非 success。
- 状态：**已落地**（daemons `979dfd8` + agentrt `262bbf5a5`）；新增终态 `SCHED_DAG_NODE_SEMANTIC_FAILED` / `SCHED_DAG_STATUS_SEMANTIC_FAILED`，语义失败不级联（仅 FATAL 全图终止），下游由可达性传播置 CANCELED；状态名表按枚举值取模索引并以 `_Static_assert` 守门；CLI 侧经 `cli_state_terminal()` / `cli_state_failed()` 统一消费，`semantic_failed` 呈现为失败而非绿勾。`test_dag_semantic_failed` 覆盖「空产物 → 节点语义失败 + 独立分支继续 + 下游取消 + 图终态 semantic\_failed」。

#### 3.4.1 R4-① 定性行：sched\_d 200ms CLIENT-ACCEPT 洪泛

- **定性：缺陷（客户端侧），根因在 CLI，不在 daemon。**
- 根因：CLI 蓝图板卡轮询 `for(;;)` 以 200ms 节拍、每轮发起**两次完全重复的** **`sched.dag_status`** **RPC**——
  - 状态面 `cli_dag_poll_remote()` 一次；
  - 节点面 `cli_dag_node_board_tick()` / `cli_dag_board_snapshot()` 各自再发一次。
  即约 10 req/s 的短连接直达 sched\_d，触发 `daemons/common/src/daemon/daemon_event_driver.c:86` 的 `CLIENT-ACCEPT` 逐连接埋点洪泛。
- 修复（**快照 SSoT**，`tools/airy_cli/src/core/cli_dag.c`）：
  - 新增不透明句柄 `cli_dag_snapshot_t` 与 `cli_dag_snapshot_fetch()`（**唯一 RPC 出口**）/ `cli_dag_snapshot_free()`（**唯一释放点**）；
  - `cli_dag_snapshot_poll()`（状态面）与 `cli_dag_node_board_tick()` / `cli_dag_board_snapshot()`（节点面）**共用同一份** **`snap->root`**，读端只读、不再释放；
  - `airy_cli_taskflow.c` 板卡轮询每轮 `fetch` 一次 → 两条消费路径共用 → `free`。
- 证据：全仓 `sched.dag_status` 字面量调用点唯一化（仅 `cli_dag.c` 单处）；`airy_cli` 目标编译通过；`cli_gw_e2e` / `cli_chat_usage` 2/2 Passed。
- 历史关联：`44b70e919「airy/cli: back off dag_status polling to stop daemon flood」` 仅对 `cli_dag_wait_remote` 引入 200ms→1.6s 指数退避（MAX\_POLLS 36000→4500），**未消除板卡轮询的重复双 RPC**；本次为根因消除。

#### 3.5.1 对标基准：Claude Code 的三条结构事实

一手输入：`works-engineering/Claude产品结构.md`（241 行）。该文件揭示的三条结构事实，
直接决定本方案的**排序**与**形态**：

1. **单入口多模式，不存在第二个用户面程序**：`claude`（REPL）/ `-p`（headless）/
   `-c` / `-r` / `--from-pr` / `attach <id>` / `mcp` / `daemon` / `update` 皆同一入口的模式分流。
   启动哲学是「**薄入口 + 重模式提前分流 + 主模块延迟加载**」——
   `claude mcp` 永不加载 React REPL，重型模块（OTel ~400KB + gRPC ~700KB）动态 `import()`。
2. **两条渲染路径，一份渲染层**：经典（行式，输出进滚动历史）+ 全屏（备用屏，输入框固定底部），
   由**同一渲染引擎**提供，`/tui fullscreen` 或 `CLAUDE_CODE_NO_FLICKER=1` 切换。
   **不存在两份全屏实现**；终端是「另一个前端容器」，不是文本输出设备。
3. **先稳主路径，再抽共享能力**：`QueryEngine.ts`（约 46K 行）已存在但**主路径不走它**——
   策略原话是「**先把 REPL 路径做稳，再把共享能力向外抽取**」。

**由此纠正的施工排序**：airymax 的真正瓶颈**不是"缺抽象层"**，而是
**入口三套并存 + 状态所有权错置**（审批权威在 `tool_d`、会话权威在 `mem_d`，
而 C 侧 CLI 对二者**零用户面视图**）。故 R5 内部顺序**固定**为：

```
G6 入口唯一化  →  G4/G5 视图归一（前端只读 + 回传 daemon 权威）
              →  G3 客户端归一（agentrt-rs）  →  G1/G2/G7 目录·渲染·元数据收口
```

即**抽象抽取排在最后**——与第 3 条事实一致；先把「唯一入口 + 正确所有权」做稳，
再谈共享能力外抽。（此顺序修订 §7 施工顺序，理由见本节。）

#### 3.5.3 子进程等价形态的接线契约（用户裁定 ④ 的落地语义）

CLI 为父进程、持有除终端以外的一切；TUI 为子进程、持有终端：

| 关注点 | CLI（父，`airy_cli`） | TUI（子，`agentrt-tui`） |
| ------ | -------------------- | ----------------------- |
| 模式决策 | **唯一**（`--tui` 与否 / TTY 探测 / `AIRYRT_FORCE_CLI`） | 无 |
| gateway 客户端 | **唯一**持有（`cli_gw`，A-IPC） | **无**（不持协议客户端） |
| 审批 | **唯一**决议权（`tool.pending` / `tool.approve`） | 只渲染 + 回传按键 |
| 会话 / 记忆 | **唯一**读取 `mem.recent` 并装配视图 | 只渲染 |
| 终端（备用屏 / 原始输入 / 鼠标） | 无 | **唯一**持有 |
| 输入回路 | 收 TUI 上报的按键/文本事件 | 只收事件、只回输入 |

- **通道**：CLI ⇄ TUI 采用**继承 fd 上的 JSON Lines 事件流**（CLI→TUI 事件 / TUI→CLI 输入）。
- **判据说明（必须登记）**：该通道位于「**TUI 是 CLI 的渲染层**」这一**同层内部边界**，
  不属服务面通信，故**通信铁律（全链统一 A-IPC）不适用**；此为**已登记例外**，
  须写入门禁 T2/T5 判据集，避免后续评审反复。
- **失败可判读（判据④）**：TUI 子进程退出码 ≠ 0 时，CLI **只报错、不接力**——
  删除现有 `airymaxrt:1430-1488` 的「TUI `rc!=0` → 自动续接 `airy_cli`」逻辑。
  该逻辑会制造**双份终端状态**（备用屏未还原 + 第二套 UI 接管）与**用户面不一致**，
  是"运行不稳定"的直接来源之一。
