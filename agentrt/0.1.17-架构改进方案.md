## 0. 全链根因模型（九项根因链终态）

蓝图调度挂死不是单点故障，而是**九项缺陷的串联放大**：任一环超时/失败/静默，都会让上层把"慢"放大成"挂死"。九项根因链在预备期已全部定位，其中六项已修复并验证：

| # | 根因 | 状态 | 证据 / 修复 |
|---|------|------|------------|
| ① | tool_d `fs_grep` 无界扫描，大目录下单次工具调用即耗尽全部预算 | ✅ 已修（p9） | builtin 工具全量有界化：签名统一 + deadline 注入 + 噪音目录排除 |
| ② | IPC 双向超时不对称（请求方远短于执行方），慢工具被请求方先行放弃 | ✅ 已修（p9） | 预算链统一（见 §2.1） |
| ③ | runner 侧 `[Errno 2]` 连环失败（工作目录被清理后每轮工具调用必炸） | ✅ 已修（p12） | workspace chdir 状态机 + SyscallProxy 恢复 |
| ④ | tool_d 执行面单线程，单个工具被占即全服务停摆，且无取消能力 | ⬜ **本版 §3.1 R1** | 预备期仅完成有界化（①），并发/取消模型未动 |
| ⑤ | runner LLM 工具循环连败无 fast-fail，16 轮烧尽才返 | ◐ 截断类已修（p6）；**通用连败本版 §3.1 R1** | 指纹检测（同参同果连续重复）已有，但异型连败（连续不同错误）无熔断 |
| ⑥ | runner BrokenPipe（daemon 先退，runner 写 IPC 必炸，错误掩盖真因） | ✅ 已修（p10） | agent_d SIGTERM 优雅关停：中断 invoke + 级联杀子进程 + join |
| ⑦ | CLI 300s 总预算 > agent_d invoke 预算倒挂，上层先断、下层空转 | ✅ 已修（p11） | 跨层预算统筹（见 §2.1） |
| ⑧ | workspace 隔离未生效（runner 在错误目录执行，产物交叉污染） | ✅ 已修（p12） | chdir 状态机 + processor 角色词汇统一 |
| ⑨ | 角色词汇表不一致（C 侧角色名与 Python 侧 `ROLE_ALIASES` 不对齐，部分请求被静默降级） | ◐ Python 侧已兜底；**C 侧统一本版 §3.1 R1** | 单侧别名表是补丁式收敛，须回到单一 SSoT |

**结论**：①③⑥⑦⑧ 五项已闭环；②随预算链闭环；残余 **④（tool_d 并发/取消）、⑤（通用连败 fast-fail）、⑨（C 侧角色词汇表 SSoT）** 三项，构成本版 R1。

### 2.1 预算链终态（已固化，防回归基线）

```
tool 执行 20s < runner IPC 30s < agent_d invoke 170s < CLI 总预算 180s
```

- 任何一层预算不得 ≥ 上层剩余预算（p11 修复的倒挂缺陷）；
- agent_d SIGTERM 路径：中断当前 invoke → 级联杀 runner 子进程 → join 回收（p10）；
- `platform_compat.c` `airy_daemon_read_request` 8MB 循环读、`daemon_rpc_client.c` 16MB 上限、`binder_internal.h` zero-copy（p9~p12 批次）；
- 大 payload IPC 读取改为循环读，修复 daemon 侧 request 截断。

### 2.3 runner LLM 截断根因与修复（p6，已闭环 + 防回归）

**现象**：fs_write 大 payload 时内容截断，蓝图节点空转挂死，16 轮烧尽后 `TOOL_LOOP_OVERFLOW`。

**根因链（全部位于 runner 执行体 LLM 客户端层，不经过 llm_d——LLMClient aiohttp 直连厂商端点，llm_d 流式聚合嫌疑彻底排除）**：

1. 厂商默认输出上限截断 arguments JSON；
2. `finish_reason` 完全未检查；
3. `json.loads` 失败后静默降级 `{"_raw": …}`，截断信号被吞；
4. 指纹检测对「每次截断内容不同」不敏感（指纹含 raw_args，每次都不同 → 永不判重）。

**修复（三处系统性修复，非补丁）**：

- `orchestration/core/llm.py`：`_resolve_max_tokens()`（显式参数 > `$AIRY_LLM_MAX_TOKENS` > None 不发送，沿用厂商默认）；`chat()` payload 按解析结果发送/省略 `max_tokens`（L250-263、L344-346）；
- `orchestration/agents/llm.py`：`execute()` 检测 `finish_reason in ("length", "max_tokens")`（L203-204）——截断且 args JSON 损坏 → **立即 fast-fail `TOOL_ARGS_TRUNCATED`，不烧轮次**（L251-266）；纯 content 截断 → 显式标记 + `metrics.truncated`（L206-223）；
- `_invoke_tool` 畸形 args 显式回传错误 JSON（`invalid tool arguments JSON` + `arguments_head`），废弃 `_raw` 静默降级（L408-419）。

**测试**：`test_llm_client.py` TestResolveMaxTokens 4 用例 + TestChatPayload 3 用例（fake aiohttp 经 `sys.modules` 注入命中懒导入，L358）；`test_llm_agent.py` 4 用例覆盖 fast-fail 不烧轮次 / 合法不误杀 / content 标记 / 畸形显式回传。**全量回归 158 passed**。

**残余登记**：本修复只覆盖「截断」这一类连败；⑤ 的通用连败 fast-fail（连续异型错误熔断）仍开放，归 §3.1 R1。

## 3. 本版施工清单

### 3.1 R1 蓝图调度挂死收尾（④⑤⑨）

**R1-a tool_d 并发与取消模型（④）**

- 现状：tool_d 执行面单线程；p9 的有界化只保证「单个工具必返回」，不保证「一个慢工具不拖死其它会话」。
- 施工：执行面改造为有界并发（worker 池）+ 每任务携带 deadline（p9 已注入的预算参数复用）+ 取消语义（deadline 到期即终止该工具执行并回报，不影响 worker 池其它任务）。
- 验收：并发两个会话，其一注入超时工具，另一会话工具调用不受影响；被取消工具返回明确取消错误码。

**R1-b LLM 工具循环通用连败 fast-fail（⑤ 非截断类）**

- 现状：截断类已 fast-fail（p6）；但连续 N 轮「非截断型失败」（如网络错、429、无效响应交替出现）仍会烧满 16 轮。
- 施工：在 `orchestration/agents/llm.py` 工具循环内加**连败计数器**：连续 `K`（建议 3）轮任何失败型结果（fast-fail、异常、无效响应）即熔断，返回 `TOOL_LOOP_CONSECUTIVE_FAILURES`，错误信息汇总最后 K 个原因。与既有指纹检测（同参同果）互补：指纹管「原地打转」，连败计数管「反复跌倒」。
- 验收：脚本化 LLM 连续返回 3 次失败 → 第 3 轮熔断，`llm.calls == 3`，不达 16。

**R1-c 角色词汇表 SSoT（⑨ C 侧）**

- 现状：Python 侧 `ROLE_ALIASES` 兜底已生效；C 侧各处角色字符串字面量仍可能漂移。
- 施工：C 侧角色名收敛到单一头文件常量（与 Python `ROLE_ALIASES` 逐一对齐），全仓字面量替换；CI 加 grep 门禁禁止新增裸字面量。
- 验收：grep 全仓 C 源码角色字面量仅存于 SSoT 头；GCCP + 蓝图 e2e 复验。

### 3.2 R2 蓝图语义正确性（p4 定位的三缺陷）

预备期端到端审查发现：即便调度不挂死，**DAG 产物在语义层面不可信**。三缺陷：

**A. 规划降级为纯校验（最重）**

- 现象：`reactive` 路径的规则表与兜底动作表**全部是校验类动作**，且规则以英文关键词匹配——中文任务几乎必然全 miss → 退化为「逐条校验型 DAG」，无法完成生成型任务。
- 施工：规则表与兜底动作表补全生成型动作集；关键词匹配支持中文同义词（或改由 LLM 规划兜底，规划失败不得静默降级为校验集）。
- 验收：中文生成型任务（如 GCCP 实题）产出的 DAG 包含生成类节点且最终产物非空。

**B. 上游产出不注入下游输入**

- 现象：`sched_dag_agent_input` 仅回填节点自身 goal，上游节点 output 不进入下游 input → 多节点 DAG 各自为战，产物无法衔接。
- 施工：DAG 执行器在派发下游节点时，将直接上游的 output（受长度预算约束）注入其 agent input。
- 验收：两节点依赖链 e2e——下游产物引用上游产出内容。

**C. DAG success 语义 = 进程级成功**

- 现象：节点进程退出码 0 即记 success，语义级失败（产物为空/工具全败/LLM 拒答）误报成功，蓝图结果不可信。
- 施工：节点成功判定增加语义校验（产物存在性与非空由节点类型定义；失败时节点标记 `semantic_failed` 并向上汇总），蓝图终态区分 `success / semantic_failed / failed`。
- 验收：注入「产物为空」场景 → 蓝图终态非 success。

**依赖关系**：B 依赖 A（校验型 DAG 无产出可注入）；C 独立。R2 完成前，蓝图调度「能跑」但「结果不可用」——这是用户「五大功能不可用」体感的另一半根因，与 R1 同为生产级收敛的必要条件。

### 3.3 R3 runner LLM 路径与 llm_d 双路径收口

- 现状：runner 执行体 LLM 调用走 LLMClient aiohttp 直连厂商（p6 取证确证）；C 侧服务走 gateway → llm_d。同一产品两条 LLM 路径，配置源、重试、可观测、截断防护各自演化（p6 的 `$AIRY_LLM_MAX_TOKENS` 修复即只覆盖 runner 侧）。
- 施工（分两步，本版完成第一步）：
  1. **本版**：配置面统一——runner 侧读取与 `model.yaml` 同源的 base_url/key/model 解析（经 gateway 只读接口或共享解析库），消除双份配置漂移；可观测统一——runner 侧 token 用量与截断事件上报到与 llm_d 同一日志/指标面。
  2. **登记**：runner 全流量收编经 llm_d（含流式）作为后续版本项，需先证流式吞吐与超时语义不回归（0.2.x §9 llm_d 条目保序）。
- 验收：修改 `model.yaml` 的 model/base_url，runner 侧新会话即生效（无需改环境变量）。

### 3.4 R4 预备期待归因项（观测缺陷，须先取证后施工）

| 项 | 现象 | 本版动作 |
|----|------|---------|
| sched_d 200ms CLIENT-ACCEPT 洪泛 | p2 e2e 复验中观测到 sched_d 以 200ms 周期刷 CLIENT-ACCEPT 日志，来源未定位 | 先取证（抓 IPC 收发面 + 日志埋点），定性为缺陷或设计行为；缺陷则修 |

纪律：**先归因再动手**，严禁在未定性前打补丁。
