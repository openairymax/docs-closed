## 2. Shell 脚本便携性

### 2.1 `head -z` 不可移植问题

**问题发现**：`quality-gate.sh` 中使用 `head -z -N` 语法限制 `find -print0` 的输出行数，在部分 shell 环境中产生 `head: invalid trailing option -- 1` 错误。

**根本原因**：`head -z` 的 `-N` 数字参数格式（如 `-100`）与 `-z` 选项组合时，部分 shell 实现将 `-100` 解析为独立的选项参数而非行数参数。

**不良模式**：
```bash
find . -name "*.c" -print0 | head -z -100
```

**正确模式**：
```bash
local count=0
while IFS= read -r -d '' file; do
    [[ $count -ge 100 ]] && break
    # 处理文件...
    ((count++)) || true
done < <(find . -name "*.c" -print0)
```

**影响范围**：`quality-gate.sh` 中 5 处 `head -z` 调用，涉及 clang-format、Python 质量检查、安全扫描三个检查门。

**教训**：
- 优先使用 `while read` 循环 + 计数器 break 替代 `head -z` 管道
- `((count++)) || true` 防止 `set -e` 下计数器溢出退出
- 此模式同时适用于 `head -z` 和 `tail -z` 的替代

## 3. 安全扫描误报治理

### 3.1 Base64 模式超敏感匹配

**问题发现**：安全扫描使用正则 `[A-Za-z0-9+/]{40,}={0,2}` 检测潜在 Base64 编码的密钥，但该模式也匹配文件路径、Python 变量名等，产生 **14 处 critical 误报**。

**误报来源**：
- Python 脚本中的 `BASE_DIR = "/home/..."` 等文件路径
- Quality gate 脚本中的 `banned_functions.h` 路径
- Shell 脚本中的 `cd /path/to/project` 命令

**修复措施**：
1. 从安全扫描模式列表中移除 `[A-Za-z0-9+/]{40,}={0,2}` 正则
2. 将 `scripts/` 目录从安全扫描中排除（dev tools 非生产代码）
3. 保留精准的密钥模式：`AKIA[0-9A-Z]{16}`、`password\s*=...`、`api_key\s*=...`

**教训**：
- 安全扫描正则必须经过充分测试，避免超敏感模式
- 区分 dev tools 和生产代码的扫描范围
- 14 critical → 0 critical 的改进验证了排除策略的有效性

### 3.2 `safe_strcpy` 误匹配 `strcpy`

**问题发现**：危险函数扫描使用 `grep -q "strcpy("` 检测 `strcpy` 调用，但 `safe_strcpy(` 作为安全封装函数也被匹配，产生 **9 处误报**。

**不良模式**：
```bash
# 会匹配 safe_strcpy、my_strcpy 等
grep -q "strcpy(" "$file"
```

**正确模式**：
```bash
# 使用 Perl 正则词边界，仅匹配独立单词 strcpy
grep -qP "\bstrcpy\s*\(" "$file"
```

**教训**：
- 字符串匹配必须使用词边界 `\b` 避免子串误报
- `\bstrcpy\s*\(` 模式同时处理了 `strcpy(` 和 `strcpy (` 的格式差异
- 同样适用于 `sprintf`/`safe_sprintf`、`system`/`ecosystem` 等场景

### 3.3 `fprintf` 双重检查冗余

**问题发现**：`fprintf` 同时出现在 BAN-77（专项检查）和 dangerous-func 扫描中，产生重复告警。

**修复措施**：从 dangerous-func 列表中移除 `fprintf(`，由 BAN-77 独立负责 `fprintf` 残留检测。

**教训**：每个检查项应有唯一责任人，避免多门禁重复告警。

## 4. CI/CD 流水线设计

### 4.1 质量门禁与 CI 双轨制统一

**问题发现**：`quality-gate.sh --strict` 已实现 20 项检查，但 CI 流水线中未接入，导致本地通过的质量门禁在 CI 中无法自动验证。

**修复措施**：
- AgentOS CI 新增 `quality-gate` job，运行 `bash scripts/ci/pipeline/quality-gate.sh --strict`
- quality-gate 结果纳入 `result` job 依赖，失败则 CI 失败
- `quality-report.json` 作为 artifact 上传，保留 7 天

**CI 架构设计原则**：
```
ci.yml
├── build-and-test     (编译 + ctest)
├── ban-scan           (BAN 规则专项扫描)
├── clang-tidy         (静态分析)
├── cppcheck           (静态分析)
├── quality-gate       (20 项综合质量门禁) ← 新增
├── python-checks      (BAN-80~82)
└── result             (汇总所有 job 结果)
```

**教训**：
- CI 质量门禁应统一入口，`quality-gate.sh` 作为唯一真实来源
- 每个 job 的 dependencies 链必须完整，避免 `result` job 遗漏依赖
- artifact 上传使用 `if: always()` 确保失败时也能获取报告

### 4.2 `continue-on-error` 静默绕过

**问题发现**：`e2e.yml` 中 `npm ci` 步骤设置 `continue-on-error: true`，导致 npm 依赖安装失败时整个 job 不报错，后续步骤在缺失依赖的状态下也会失败，但 CI 标记为通过。

**修复措施**：移除 `continue-on-error: true`，让构建失败直接暴露。

**教训**：
- `continue-on-error` 应仅用于非关键步骤（如可选 lint、coverage 上报）
- 构建依赖步骤（`npm ci`、`pip install`、`cmake`）绝不应使用 `continue-on-error`
- 定期审计所有 CI workflow 中的 `|| true` 和 `continue-on-error` 使用

### 4.3 MemoryRovol 质量门禁设计

**问题发现**：MemoryRovol CI 仅有 BAN-60/61/62/58/59 专项检查，缺少 fprintf 残留、内存调用合规、代码格式化等基础检查。

**新增检查项**：

| 检查项 | 内容 | 严重级别 |
|--------|------|----------|
| BAN-MR01 | fprintf 0残留扫描 | error（阻断） |
| BAN-MR02 | raw malloc/free/realloc/calloc 0残留 | error（阻断） |
| BAN-MR03 | clang-format 合规 | warning（不阻断） |

**教训**：
- 子模块 CI 应与主模块 CI 保持对齐的质量标准
- result job 统一管控所有依赖，确保任一失败时 CI 整体失败

## 5. 错误码标准化

### 5.1 未定义错误码导致编译失败

**问题发现**：`weighted.c` 中使用 `AGENTOS_ERR_SCHED_NO_AGENT` 错误码，但该错误码**未在任何头文件中定义**，导致 `WARNINGS_AS_ERRORS=ON` 编译失败。

**代码位置**：[weighted.c](file:///home/spharx/SpharxWorks/OpenAirymax/AgentOS/agentos/daemon/sched_d/src/strategies/weighted.c)

**不良模式**：
```c
// 局部定义，仅此文件可用，且未在 error.h 注册
#ifndef AGENTOS_ERR_SCHED_NO_AGENT
#define AGENTOS_ERR_SCHED_NO_AGENT (-2001)
#endif
```

**修复措施**：将 `AGENTOS_ERR_SCHED_NO_AGENT` 替换为已注册的标准错误码 `AGENTOS_ERR_NOT_FOUND (-6)`。

**语义映射**：
- `AGENTOS_ERR_SCHED_NO_AGENT` → `AGENTOS_ERR_NOT_FOUND`：无可用 agent = 资源未找到

**教训**：
- 所有错误码必须先在 `error.h` 中注册，不允许局部定义
- 语义相近的错误码应复用，避免为每个模块创建专属错误码
- 编译时 `WARNINGS_AS_ERRORS=ON` 能有效捕获此类问题

## 8. 编译兼容性深度修复

### 8.1 `-include` 注入导致 `_GNU_SOURCE` 等 Feature Test Macros 失效

**问题发现**：MemoryRovol strict 模式编译时，`platform_compat.c` 中 `pthread_setname_np` 产生隐式函数声明错误。该函数需要 `_GNU_SOURCE` 宏，但 `platform_compat.c` 在文件顶部 `#define _GNU_SOURCE` 时已来不及。

**根本原因**：`banned_functions.h` 通过 CMake 的 `-include` 选项注入，在**任何源文件代码之前**被预处理器展开。`banned_functions.h` 内部 `#include <stdio.h>` 等系统头文件时，`_GNU_SOURCE` 尚未定义，导致后续 `platform_compat.c` 中 `#define _GNU_SOURCE` 对已展开的系统头文件无效。

**不良模式**：
```c
// platform_compat.c - 第 1 行
#define _GNU_SOURCE  // ← 太晚了，banned_functions.h 已展开

#include <pthread.h>
// pthread_setname_np 未声明！
```

```cmake
# MemoryRovol CMakeLists.txt - 缺少 feature test macros
add_compile_options(-include ${AGENTOS_INCLUDE_DIR}/.../banned_functions.h)
# 没有 _GNU_SOURCE 定义
```

**正确模式**：
```cmake
# 必须在 CMake 级别定义 feature test macros
if(UNIX AND NOT APPLE)
    add_compile_definitions(
        _POSIX_C_SOURCE=200809L
        _XOPEN_SOURCE=700
        _GNU_SOURCE
    )
endif()

# 然后再注入 banned_functions.h
if(AGENTOS_COMPLIANCE_STRICT)
    add_compile_options(-include ${AGENTOS_INCLUDE_DIR}/.../banned_functions.h)
endif()
```

**教训**：
- `-include` 注入的头文件在所有源文件代码之前展开，改变了 include 顺序
- 所有 feature test macros（`_GNU_SOURCE`、`_POSIX_C_SOURCE`、`_XOPEN_SOURCE`）必须在 **CMake 级别**通过 `add_compile_definitions` 定义
- 跨模块必须保持 feature test macros 一致（AgentOS 与 MemoryRovol 均已对齐）

### 8.2 OSS 模式预处理器守卫遗漏

**问题发现**：MemoryRovol 以 `MEMORYROVOL_OSS=ON` 编译时，`memoryrovol.c` 中 `forget_strategy`、`forget_lambda`、`forget_threshold`、`forget_check_interval` 四个变量和 `force` 参数产生 `-Wunused-but-set-variable` / `-Wunused-parameter` 警告，`WARNINGS_AS_ERRORS=ON` 下编译失败。

**根本原因**：这些变量仅在 `#ifndef MEMORYROVOL_OSS` 块内使用，但变量声明和赋值在块外，OSS 模式下成为死代码。

**不良模式**：
```c
// 变量声明在 OSS 守卫外
uint32_t forget_strategy = AGENTOS_FORGET_EBBINGHAUS;
double   forget_lambda   = DEFAULT_FORGET_LAMBDA;
// ...

#ifndef MEMORYROVOL_OSS
    // 仅在 PRO 模式下使用 forget_strategy 等
    if (forget_strategy == ...) { ... }
#endif
```

```c
// force 参数在 OSS 模式下未使用
agentos_error_t agentos_memoryrov_evolve(handle, int force)
{
    // OSS 模式下 force 未被引用
}
```

**正确模式**：
```c
// 方案 A：变量声明也放入守卫
#ifndef MEMORYROVOL_OSS
    uint32_t forget_strategy = AGENTOS_FORGET_EBBINGHAUS;
    double   forget_lambda   = DEFAULT_FORGET_LAMBDA;
    // ...
#endif
```

```c
// 方案 B：显式 (void) 抑制未使用参数警告
agentos_error_t agentos_memoryrov_evolve(handle, int force)
{
#ifdef MEMORYROVOL_OSS
    (void)force;
#endif
    // ...
}
```

**教训**：
- 条件编译的变量声明和赋值必须与使用点保持相同的 `#ifdef` 守卫
- 优选方案 A（变量声明入守卫），方案 B（`(void)cast`）仅在参数场景使用
- 每次新增 OSS/PRO 条件编译块时，必须同步检查变量声明是否匹配

### 8.3 `AGENTOS_COMPLIANCE_IMPL` 豁免机制

**问题发现**：MemoryRovol strict 模式编译时，AgentOS 的 `memory.c`（实现 `AGENTOS_MALLOC` / `AGENTOS_FREE` 宏）被 `banned_functions.h` 毒化，无法使用 `malloc`、`free`、`fprintf` 等原始函数。但 `memory.c` 正是这些宏的**实现层**，必须合法使用原始函数。

**根本原因**：`banned_functions.h` 通过 `-include` 全局注入，`memory.c` 作为被链接的外部源文件也受其影响。`banned_functions.h` 已有 `#ifndef AGENTOS_COMPLIANCE_IMPL` 豁免检查，但 `memory.c` 无法在源文件级别定义该宏（`-include` 先于源文件展开）。

**解决方案**：通过 CMake 的 `set_source_files_properties` 在编译器级别为特定文件注入豁免宏：

```cmake
if(AGENTOS_COMPLIANCE_STRICT)
    set_source_files_properties(
        ${AGENTOS_ROOT_ABS}/AgentOS/agentos/commons/utils/memory/src/memory.c
        PROPERTIES COMPILE_DEFINITIONS "AGENTOS_COMPLIANCE_IMPL"
    )
endif()
```

**教训**：
- `set_source_files_properties` 是精确豁免单个文件的最佳方式，比全局 `ifdef` 更干净
- 豁免宏必须在编译器级别定义（`-D`），因为 `-include` 注入先于源文件 `#define`
- 合规基础设施的实现文件（如 `memory.c`、`svc_logger.h`）需要明确的豁免标记

### 8.4 Strict 模式揭示隐藏的 `#include` 缺失

**问题发现**：AgentOS strict 模式 clean rebuild 时，`config_compat.c` 在 20+ 处使用 `AGENTOS_EINVAL` 但编译报错 `'AGENTOS_EINVAL' undeclared`。普通模式编译却无此问题。

**根本原因**：普通模式下，`config_compat.c` 通过间接 include 链偶然获取了 `AGENTOS_EINVAL` 的定义。strict 模式注入 `banned_functions.h` 改变了 include 展开顺序，导致间接依赖断裂，暴露了直接 `#include "error.h"` 缺失的问题。

**不良模式**：
```c
#include "config_compat.h"
#include "core_config.h"
// 缺少 #include "error.h" — 但通过间接 include 链偶然可用
#include <stdio.h>
```

**正确模式**：
```c
#include "config_compat.h"
#include "core_config.h"
#include "error.h"     // ← 显式 include，不依赖间接链
#include <stdio.h>
```

**教训**：
- 每个源文件应**显式 include** 其直接使用的所有头文件，不依赖间接 include 链
- Strict 模式是检测 "偶然可用" include 链的终极工具
- 同模块其他文件（`core_config.c`、`config_source.c`、`config_service.c`）均已正确 include `error.h`，`config_compat.c` 是遗漏的离群点

## 9. 并行测试竞态条件

### 9.1 `mkdir` + 硬编码路径 → `mkdtemp` 竞态

**问题发现**：`ctest -j` 并行运行 MemoryRovol 测试时，`test_memoryrovol_core` 间歇性 SEGFAULT。串行运行 `./test_memoryrovol_core` 或 `ctest`（无 `-j`）时 12/12 全部通过。

**根本原因**：`storage.c` 中 `agentos_layer1_raw_create_async` 在路径为 `NULL` 时，调用 `mkdir()` 创建硬编码目录 `/var/tmp/agentos/agentos_l1_test_XXXXXX`（字面量 `XXXXXX`，非 `mkdtemp` 模板）。多个并行测试进程共享同一目录，互相删除/修改对方的文件，导致文件损坏和 SEGFAULT。

**不良模式**：
```c
// 硬编码共享目录 - 多进程冲突
snprintf(path, sizeof(path), "%s/agentos_l1_test_XXXXXX", tmpdir);
mkdir(path, 0755);  // 所有进程创建同一目录！
```

**正确模式**：
```c
// mkdtemp 将 "XXXXXX" 替换为随机字符，生成唯一目录
snprintf(path, sizeof(path), "%s/agentos_l1_test_XXXXXX", tmpdir);
if (mkdtemp(path) == NULL) {
    // 处理错误
    return AGENTOS_EIO;
}
// path 现在是 "/var/tmp/agentos/agentos_l1_test_aB3xYz" 等唯一路径
```

**代码位置**：[storage.c](file:///home/spharx/SpharxWorks/OpenAirymax/MemoryRovol/src/layer1_raw/storage.c#L107-L128)

**教训**：
- `XXXXXX` 后缀模板必须配合 `mkdtemp()`（POSIX）或 `_mktemp_s()`（Windows）使用，绝不能配合 `mkdir()`
- 这是一个**生产级 bug**：如果两个生产实例同时运行，也会因为共享目录而冲突
- 修复后并行 `ctest -j` 10/10 100% 通过

### 9.2 并行测试是发布前的必要验证

**经验**：串行测试无法暴露资源竞争问题。`ctest -j$(nproc)` 应作为发布前标准验证步骤。

**并行测试策略**：
- CI 默认使用 `ctest -j$(nproc)` 最大化并行度
- 发现间歇性失败时，先用 `ctest`（串行）排除逻辑错误，再用 `ctest -j` 定位竞态
- 修复后至少运行 3 次并行测试确认稳定性

**教训**：
- 串行测试通过 ≠ 并行测试通过，二者覆盖不同的 bug 类别
- 临时目录、共享文件、端口绑定等资源必须使用唯一标识符
- 发布前检查清单应包含并行测试验证

## 10. 跨模块 BAN 合规一致性

### 10.1 POSIX Feature Test Macros 跨模块对齐

**问题发现**：MemoryRovol 的 CMakeLists.txt 缺少 `_GNU_SOURCE` 等 feature test macros 定义，而 AgentOS 的 CMakeLists.txt 已包含完整定义。导致 strict 模式下 MemoryRovol 编译失败。

**修复措施**：将 AgentOS 的 feature test macros 定义完整复制到 MemoryRovol CMakeLists.txt，包括 Linux 和 macOS 两套宏定义。

**教训**：
- 子模块的 CMake 编译配置必须与主模块保持对齐
- Feature test macros 属于编译基础设施，不是模块特定配置
- 建议将 feature test macros 提取为共享 CMake 模块，避免跨模块复制粘贴

### 10.2 CMake 缓存污染导致非 Strict 构建注入毒化头文件

**问题发现**：在 MemoryRovol-build 目录中先以 `AGENTOS_COMPLIANCE_STRICT=ON` 构建，再以 `AGENTOS_COMPLIANCE_STRICT=OFF` 重新构建时，测试文件仍被 `banned_functions.h` 毒化，导致测试编译失败。

**根本原因**：CMake 缓存了 `AGENTOS_COMPLIANCE_STRICT=ON` 的值。即使后续 cmake 命令指定 `OFF`，缓存值优先于命令行参数。

**修复措施**：切换 strict/non-strict 模式前必须删除 CMake 缓存：
```bash
rm -f CMakeCache.txt
cmake ../MemoryRovol -DAGENTOS_COMPLIANCE_STRICT=OFF ...
```

**教训**：
- CMake 的 `-D` 参数仅在缓存不存在时设置初始值，已有缓存时不会覆盖
- 建议使用独立的 build 目录（`build/` 和 `build-strict/`）避免缓存冲突
- CI 中每个 job 使用独立 build 目录，彻底消除缓存污染

### 10.3 `fprintf` → `fputs + snprintf` 迁移模式

**问题发现**：MemoryRovol `license.c` 中有 12 处 `fprintf` 调用，违反 BAN-77 规则。

**迁移模式**：
```c
// 不良：直接 fprintf
fprintf(fp, "usage_%s=%llu\n", meter_names[i], 
        (unsigned long long) g_metering_ctx.quota.usage[i]);

// 正确：snprintf + fputs
char buf[256];
snprintf(buf, sizeof(buf), "usage_%s=%llu\n", meter_names[i], 
         (unsigned long long) g_metering_ctx.quota.usage[i]);
fputs(buf, fp);
```

**教训**：
- `snprintf` 的 `sizeof(buf)` 参数提供缓冲区溢出保护
- `fputs` 比 `fprintf(fp, "%s", buf)` 更简洁高效
- 对于固定格式的行写入，`fputs` + `snprintf` 是 `fprintf` 的标准替代模式

## 11. 内存迁移与错误码规模化治理

### 11.1 `malloc/free/calloc/realloc` → `AGENTOS_*` 宏迁移策略

**问题背景**：v0.1.0 工程规范要求所有内存分配必须通过 `AGENTOS_MALLOC` / `AGENTOS_FREE` / `AGENTOS_CALLOC` / `AGENTOS_REALLOC` 宏，以便统一管理内存追踪、泄漏检测和合规审计。但代码库中广泛使用原始 `malloc`/`free` 调用。

**规模化迁移方法**：
1. **自动化脚本扫描**：编写 Python 脚本扫描所有 `.c`/`.h` 文件，识别 `malloc(`/`free(`/`calloc(`/`realloc(` 调用
2. **分类处理**：
   - 测试文件（`tests/`、`test/`）：白名单豁免
   - 基础设施实现文件（`memory.c`、`memory_debug.c`）：通过 `AGENTOS_COMPLIANCE_IMPL` 豁免
   - 日志系统实现文件（`service_logging.c`）：通过文件级豁免
   - 其他生产代码：全量替换为 `AGENTOS_*` 宏
3. **验证机制**：编译时通过 `banned_functions.h` 的 `#pragma GCC poison` 阻断任何遗漏的原始调用

**内存兼容层设计** (`memory_compat.h`)：
```c
// 统一的错误返回值标准化
#define AGENTOS_MALLOC(size)        agentos_malloc_debug(size, __FILE__, __LINE__)
#define AGENTOS_FREE(ptr)           agentos_free_debug(ptr, __FILE__, __LINE__)
#define AGENTOS_CALLOC(nmemb, size) agentos_calloc_debug(nmemb, size, __FILE__, __LINE__)
#define AGENTOS_REALLOC(ptr, size)  agentos_realloc_debug(ptr, size, __FILE__, __LINE__)
```

**教训**：
- 迁移前先建立完整的豁免清单，避免误伤基础设施代码
- 禁止在 `#ifndef` 守卫中局部定义 `AGENTOS_MALLOC` 等宏（会导致行为不一致）
- 内存宏应包含 `__FILE__` / `__LINE__` 调试信息，便于泄漏追踪
- 迁移后运行 `ctest --timeout` 检测内存泄漏和超时问题

### 11.2 `return -1` → `AGENTOS_E*` 错误码迁移

**问题背景**：v0.1.0 之前大量函数使用 `return -1` 表示错误，缺乏语义化错误码，无法区分"参数无效"、"内存不足"、"资源未找到"等不同错误场景。

**迁移策略**：
1. **语义映射表**：
   | 原始模式 | 目标错误码 | 语义 |
   |----------|-----------|------|
   | `return -1` (参数校验) | `AGENTOS_EINVAL (-2)` | 无效参数 |
   | `return -1` (内存分配失败) | `AGENTOS_ENOMEM (-3)` | 内存不足 |
   | `return -1` (资源未找到) | `AGENTOS_ERR_NOT_FOUND (-6)` | 资源未找到 |
   | `return -1` (权限不足) | `AGENTOS_ERR_PERMISSION (-7)` | 权限不足 |
   | `return -1` (IO错误) | `AGENTOS_EIO (-9)` | 输入输出错误 |

2. **自动化脚本**：编写 `fix_return_neg_N.py` 扫描所有 `return -1` 并按上下文替换
3. **验证方法**：`grep -rn 'return -1' agentos/ --include='*.c' | grep -v '/tests/' | grep -v '/examples/'`

**教训**：
- 不要在所有场景使用同一个默认错误码——必须根据上下文选择语义正确的错误码
- 错误码迁移后必须运行全量测试，确保错误处理路径未被破坏
- 部分 `return -1` 出现在 `main()` 函数中是合法的，不应被替换

### 11.3 `error_push_ex` 自动化注入

**问题背景**：错误处理规范要求每个错误返回点前调用 `error_push_ex` 宏，记录错误发生的文件、行号和函数名，实现错误可追溯。但手动添加 400+ 处调用不现实。

**自动化注入方法**：
- 编写 `inject_error_push_ex.py` 脚本，解析 C 代码的 AST 结构
- 识别 `return AGENTOS_E*` 模式，在前一行插入 `error_push_ex(AGENTOS_ERROR_ORIGIN, error_code)`
- 跳过已有 `error_push_ex` 的行（避免重复注入）
- 跳过 `return AGENTOS_SUCCESS` 的路径（成功路径不需要错误上下文）

**注入结果**：
- 覆盖 37 个文件，注入 459 处 `error_push_ex`
- 最终全量覆盖 478 处（含手动添加的 19 处）

**教训**：
- 自动化注入脚本必须支持幂等性（重复运行不产生重复注入）
- 注入后必须编译验证，因为脚本可能无法处理所有 C 语法边界情况
- 增量注入优于全量注入：先注入 atoms/cupolas 层，再逐步扩展到其他层

## 12. Shell 脚本规范化与 shellcheck 治理

### 12.1 shellcheck 警告从 158 → 29 → 0 的治理路径

**问题背景**：项目中的 Shell 脚本（`ops/`、`dev/`、`scripts/`）缺乏 shebang 声明、shellcheck 指令和变量引用规范，产生 158 处 shellcheck 警告。

**治理策略**：

**第一阶段（158 → 29）**：
- 为所有 `.sh` 文件添加 `#!/usr/bin/env bash` shebang
- 为所有 `.sh` 文件添加 `# shellcheck shell=bash` 指令
- 修复明显的 SC2086（变量未加引号）和 SC2164（`cd` 未检查失败）

**第二阶段（29 → 0）**：
- 修复 `$()` 嵌套中的变量引用问题
- 修复 `read` 命令的 `-r` 选项缺失
- 修复数组引用中的引号问题

**关键修复模式**：
```bash
# 不良：变量未加引号
cd $DIR

# 正确：变量加引号 + 错误处理
cd "$DIR" || { echo "Failed to cd to $DIR"; exit 1; }

# 不良：read 缺少 -r
while IFS= read line; do

# 正确：read 使用 -r 避免反斜杠转义
while IFS= read -r line; do
```

**教训**：
- shellcheck 治理应分阶段进行：先修复结构性缺陷（shebang/指令），再修复语义问题
- 每个脚本修复后立即运行 `shellcheck` 验证
- 在 CI 中集成 `shellcheck` 作为强制检查，防止回归

### 12.2 Shell 脚本 shebang 与 shellcheck 指令规范

**标准模板**：
```bash
#!/usr/bin/env bash
# shellcheck shell=bash
# shellcheck disable=SC1090,SC1091  # source 外部文件时禁用
set -euo pipefail
```

**教训**：
- `#!/usr/bin/env bash` 优于 `#!/bin/bash`（更好的跨平台兼容性）
- `set -euo pipefail` 是安全 Shell 脚本的基础
- `# shellcheck shell=bash` 显式声明 shell 类型，避免 shellcheck 误判

## 13. 桩函数消除与算法落地时机

### 13.1 桩函数 (Stub) 的系统性消除

**问题背景**：代码库中存在多个返回 `ENOTSUP` 或 `AGENTOS_SUCCESS` 的占位函数（桩函数），这些函数在功能上不可用，但编译通过，给测试和生产带来隐性风险。

**识别方法**：
```bash
# 查找所有返回 ENOTSUP 的桩函数
grep -rn 'return.*ENOTSUP\|return.*ENOSYS' --include='*.c' agentos/ | grep -v '/tests/'

# 查找返回 SUCCESS 但函数体为空的桩函数
grep -B2 'return.*AGENTOS_SUCCESS' --include='*.c' agentos/ | grep -v '/tests/'
```

**消除策略**：
1. 评估桩函数是否为 v0.1.0 必需功能
2. 必需功能 → 实现真实算法
3. 非必需功能 → 标记为 `AGENTOS_ENOSYS` 并在文档中说明

**典型案例：持久同调计算器 (Persistence Calculator)**：
- 原桩函数：`return ENOTSUP`
- 实现方案：Union-Find 数据结构 + 边排序的 0D 持久同调算法
- 输入：`distance_matrix`（距离矩阵）
- 输出：`out_features`（持久同调特征数组）
- 函数签名：`agentos_error_t agentos_persistence_calculator_compute(calc, distance_matrix, count, out_features, out_count)`

**教训**：
- 桩函数消除前必须评估功能优先级（P0/P1/P2）
- 实现算法时需要同步编写单元测试，验证正确性
- 函数签名变更（如参数类型从 `int` 改为 `size_t`）需同步更新所有调用方

### 13.2 算法落地的函数签名设计

**问题发现**：持久同调计算器在实现真实算法时，原桩函数的参数类型 `int` 被改为 `size_t`，但调用方未同步更新，导致编译失败。

**教训**：
- 函数签名变更必须全局搜索所有调用方
- 使用 `size_t` 而非 `int` 表示计数参数（更安全、更语义化）
- 算法实现前先设计完整的接口文档，包括参数校验规则

## 14. CMake 高级编译选项技巧

### 14.1 `SHELL:` 前缀合并编译选项

**问题发现**：`target_compile_options` 中 `-include` 和头文件路径被 CMake 自动分离为两个独立选项，导致编译失败。

**不良模式**：
```cmake
# CMake 将 -include 和 path 分离为两个选项
target_compile_options(agentos_memoryrovol PRIVATE
    -include
    ${CMAKE_CURRENT_SOURCE_DIR}/agentos_mr_force_includes.h
)
# 实际编译命令：-include /path/to/header.h  ← 分离导致错误
```

**正确模式**：
```cmake
# 使用 SHELL: 前缀将选项合并为一个字符串
target_compile_options(agentos_memoryrovol PRIVATE
    "SHELL:-include ${CMAKE_CURRENT_SOURCE_DIR}/agentos_mr_force_includes.h"
)
# 实际编译命令：-include/path/to/header.h  ← 正确合并
```

**适用场景**：
- `-include` + 头文件路径
- `-Xlinker` + 链接器参数
- `-Wl,` + 链接器选项
- 任何需要"选项+值"作为单个参数传递的场景

**教训**：
- CMake 的 `target_compile_options` 默认按空格分割参数
- `SHELL:` 前缀强制 CMake 将后续内容作为单个参数传递给编译器
- 此技巧同样适用于 `target_link_options`

### 14.2 `add_compile_definitions` vs `add_compile_options -D`

**问题发现**：`add_compile_definitions(_GNU_SOURCE)` 和 `add_compile_options(-D_GNU_SOURCE)` 看似等价，但在某些 CMake 生成器中行为不同。

**推荐**：
```cmake
# 推荐：add_compile_definitions 更简洁，语义更明确
add_compile_definitions(
    _POSIX_C_SOURCE=200809L
    _XOPEN_SOURCE=700
    _GNU_SOURCE
)

# 备选：add_compile_options -D 适用于需要精确控制选项顺序的场景
add_compile_options(-D_POSIX_C_SOURCE=200809L -D_XOPEN_SOURCE=700 -D_GNU_SOURCE)
```

**教训**：
- 优先使用 `add_compile_definitions` 定义 feature test macros
- `add_compile_options` 用于需要精确控制顺序或与其他选项组合的场景

### 14.3 `set_source_files_properties` 精确豁免

**使用模式**：
```cmake
# 为单个源文件设置编译选项或定义
set_source_files_properties(
    ${CMAKE_SOURCE_DIR}/path/to/special_file.c
    PROPERTIES
        COMPILE_DEFINITIONS "AGENTOS_COMPLIANCE_IMPL;NO_BAN_CHECK"
        COMPILE_FLAGS "-Wno-error=unused-parameter"
)
```

**适用场景**：
- 合规基础设施实现文件的豁免（如 `memory.c`）
- 第三方代码的警告抑制
- 特殊编译单元的标志位设置

**教训**：
- `COMPILE_DEFINITIONS` 使用分号分隔多个宏定义
- `COMPILE_FLAGS` 不经过 CMake 转义，直接传递给编译器
- 文件级豁免优于全局豁免，减少影响范围

### 16.4 ACC 验收终审的教训

1. **提前规划验收标准**：ACC 标准应在开发初期制定，而非发布前仓促验证
2. **自动化验证脚本可复用**：逐项验收的脚本可沉淀为 CI 检查项，防止后续版本回归
3. **指标分类管理**：将验收标准分为"阻断性"（0残留）和"可接受范围"（如覆盖率阈值），优先处理阻断性指标
4. **交叉验证消除盲区**：单一工具的扫描结果不可完全信赖，多工具交叉验证是发现盲区的有效手段
5. **证据留存**：每次验收的扫描命令和输出应留存，便于审计和问题回溯

## 17. BAN 规则体系治理与自动化扫描

### 17.1 BAN 规则从 18 到 21 的演进路径

**问题背景**：v0.1.0 初期仅有 18 条 BAN（Banned/Blocked）规则，随着深度修复推进，识别出 3 个新的扫描盲区，BAN 规则扩充至 21 条。

**演进路径**：

| 阶段 | BAN 规则数 | 新增规则 | 触发原因 |
|------|-----------|----------|----------|
| 初始 | 18 | — | 基础规范建立 |
| v23.7.0 | 19 | BAN-77 fprintf 残留 | `fprintf` 迁移遗漏 |
| v23.9.0 | 20 | BAN-78 strict compile | Strict 模式编译失败暴露 |
| v23.9.0 | 21 | BAN-76 fprintf poison | 编译时阻断 fprintf 使用 |

**BAN 规则分类体系**：
- **编译时阻断（Compile-time）**：BAN-70~76（banned_functions.h poison），BAN-78（strict compile）— 无法绕过
- **扫描阻断（Scan-time）**：BAN-33, 43, 57~62, 77 — CI 扫描失败则构建失败
- **警告提醒（Warning）**：BAN-MR03 等 — 不阻断构建，但记录问题

### 17.2 BAN-80/81/82：Python flake8 + bandit 集成

**问题背景**：项目中 Python 脚本（`scripts/`、`ops/`、`openlab/`）缺乏代码规范检查和安全扫描，存在变量名遮蔽内置函数、f-string 缺失、潜在安全漏洞等问题。

**BAN-80：flake8 内置函数遮蔽检查**：
```bash
# 检测变量名遮蔽 Python 内置函数（如 id, type, list, str）
flake8 --select=A001,A002,A003 scripts/ ops/ openlab/
```

**BAN-81：flake8 f-string 缺失检查**：
```bash
# 检测可转为 f-string 的 .format() 和 % 格式化
flake8 --select=C0209 scripts/ ops/ openlab/
```

**BAN-82：bandit 安全扫描**：
```bash
# 检测常见 Python 安全漏洞
bandit -r scripts/ ops/ openlab/ -ll -s B101,B303,B311
# -s 排除：assert（B101）、md5（B303）、伪随机数（B311）等已评估的低风险项
```

**集成到 quality-gate.sh**：
```bash
check_python_flake8_shadow() {
    local count
    count=$(flake8 scripts/ ops/ --select=A001,A002,A003 --count 2>/dev/null) || true
    if [ "$count" -gt 0 ]; then
        echo "FAIL: BAN-80 - flake8 shadow builtins: $count issue(s)"
        return 1
    fi
    return 0
}
```

**教训**：
- Python 也应纳入质量门禁体系，使用与 C 代码同等级别的检查标准
- flake8 的 `--select` 选项支持精准检查，避免引入过多无关规则
- bandit 的 `-s` 排除机制适用于已评估的低风险项，避免误报泛滥

### 17.3 BAN 规则优先级分类与执行策略

**分类原则**：
| 优先级 | 分类 | 执行时机 | 失败后果 |
|--------|------|----------|----------|
| P0-Critical | 编译时阻断 | 每次编译 | 编译失败 |
| P0-Block | 扫描阻断 | CI 每次提交 | CI 失败 |
| P1-Warn | 扫描警告 | CI 每次提交 | 记录告警 |
| P2-Info | 信息提示 | 定期审计 | 仅报告 |

**执行策略**：
- P0 规则：`quality-gate.sh --strict` 中执行，异常退出码
- P1 规则：`quality-gate.sh` 默认模式中执行，stderr 输出
- P2 规则：通过 cron 定期审计，不在每次 CI 中运行

**教训**：
- 规则的严重级别应与其修复成本匹配：低成本修复的高危问题应设为 P0
- 新增规则时应先以 P1-Warn 运行 1-2 轮 CI，确认无误报后再升级为 P0-Block
- 编译时阻断（P0-Critical）是最强力的保障手段，应优先用于高危模式

### 17.4 多模块 BAN 合规一致性自动化

**问题背景**：AgentOS、MemoryRovol、Desktop 三个模块各自维护 BAN 检查，规则不统一导致合规标准不一致。

**解决方案**：将核心 BAN 规则提取到共享的 `quality-gate.sh` 中，各模块 CI 统一调用：
```yaml
# 各模块 CI 统一入口
- name: Quality Gate
  run: bash ${GITHUB_WORKSPACE}/AgentOS/scripts/ci/pipeline/quality-gate.sh --strict
```

**教训**：
- BAN 规则应集中管理，避免各模块各自维护导致标准分裂
- 模块特定规则（如 BAN-MR01~03）可在共享脚本中通过参数控制启用/禁用
- CI 配置应引用主仓库的共享脚本，确保规则更新自动传播到所有模块

## 18. 错误码值冲突治理与定义统一

### 18.1 AGENTOS_EINVAL 双重定义冲突

**问题发现**：`permission_cache.c` 和 `circuit_breaker.c` 中局部定义了 `AGENTOS_EINVAL = -1`，与 `error.h` 中标准定义 `AGENTOS_EINVAL = -2` 冲突，导致错误码语义混乱——同一个错误码在不同文件中代表不同的值。

**冲突根源**：
```c
// permission_cache.c — 局部定义，值为 -1
#ifndef AGENTOS_EINVAL
#define AGENTOS_EINVAL (-1)
#endif

// circuit_breaker.c — 同样的局部定义模式
#ifndef AGENTOS_EINVAL
#define AGENTOS_EINVAL (-1)
#endif

// error_compat.h — 全局标准定义，值为 -2
#define AGENTOS_EINVAL (-2)
```

**问题影响**：
- 如果 `error_compat.h` 先被 include，则局部 `#ifndef` 守卫跳过，使用标准值 `-2`
- 如果 `error_compat.h` 后被 include，则局部定义生效（`-1`），但与其他文件的 `-2` 不一致
- 跨文件错误码比较时产生不可预测的行为

**修复措施**：
1. 删除 `permission_cache.c` 和 `circuit_breaker.c` 中的局部 `#ifndef` 定义
2. 在文件头部添加 `#include "error_compat.h"` 使用标准错误码
3. 将 `return -1` / `return AGENTOS_EINVAL`（旧值 -1）替换为 `return AGENTOS_EINVAL`（新值 -2）

**检测命令**：
```bash
# 检测所有局部错误码定义
grep -rn '#ifndef AGENTOS_E\|#define AGENTOS_E' --include='*.c' --include='*.h' \
  | grep -v 'error_compat.h\|error.h\|/tests/'
```

### 18.2 局部定义 vs 全局注册的检测方法

**自动化检测脚本** (`check_local_error_codes.sh`)：
```bash
#!/usr/bin/env bash
# shellcheck shell=bash
set -euo pipefail

# 扫描所有局部 #define AGENTOS_E* 或 AGENTOS_ERR_* 
LOCAL_DEFS=$(grep -rn '#define AGENTOS_E\|#define AGENTOS_ERR_' \
  --include='*.c' --include='*.h' \
  | grep -v 'error_compat.h' \
  | grep -v 'error.h' \
  | grep -v '/tests/' \
  | grep -v '_IMPL\|_COMPAT') || true

if [ -n "$LOCAL_DEFS" ]; then
    echo "FAIL: Local error code definitions detected:"
    echo "$LOCAL_DEFS"
    echo "All error codes must be defined in error_compat.h or error.h"
    exit 1
fi
echo "PASS: No local error code definitions"
```

### 18.3 交叉验证策略

**多层验证机制**：
1. **编译时**：`WARNINGS_AS_ERRORS=ON` 捕获未声明的错误码使用
2. **静态扫描**：脚本扫描局部 `#define AGENTOS_E*` 模式
3. **运行时**：断言 `err >= AGENTOS_ERR_MAX || err <= AGENTOS_SUCCESS` 确保错误码在合法范围内

**教训**：
- 错误码的 `#ifndef` 守卫模式是危险的反模式——它允许局部覆盖全局定义
- 所有错误码必须在单一头文件（`error_compat.h` 或 `error.h`）中集中定义
- 编译时检测 + 静态扫描 + 运行时断言 三层防护是防止错误码值漂移的最佳实践
- 新增错误码时应遵循：先在头文件中注册 → 再在代码中使用，而非反过来

### 18.4 错误码定义集中化原则

**标准模式**：
```c
// error_compat.h — 唯一的错误码定义源
#define AGENTOS_SUCCESS              (0)
#define AGENTOS_EFAILURE            (-1)
#define AGENTOS_EINVAL              (-2)
#define AGENTOS_ENOMEM              (-3)
#define AGENTOS_ERR_TIMEOUT         (-4)
#define AGENTOS_ERR_NOT_FOUND       (-6)
#define AGENTOS_ERR_PERMISSION      (-7)
#define AGENTOS_EIO                 (-9)
// ... 所有错误码必须在此注册
```

**教训**：
- 集中定义不是限制，而是保障——确保所有代码对同一个错误码的理解一致
- 跨模块使用错误码时，必须在共同依赖的 base 层头文件中定义
- 错误码值的分配应预留扩展空间（注意 -5、-8 为预留值）

## 19. 关键经验总结

### 19.1 工程原则

1. **单一真实来源**：质量门禁脚本是 CI 和本地开发的唯一入口，CI 必须调用同一脚本
2. **失败即暴露**：不使用 `|| true`、`continue-on-error` 掩盖问题
3. **词边界精准匹配**：所有字符串搜索必须考虑子串匹配问题
4. **错误码集中注册**：不允许局部定义，必须通过 `error.h` 统一管理
5. **增量格式化**：代码格式化分批进行，每次格式化后立即编译验证
6. **Strict 模式是终极真相揭示器**：普通模式编译可能隐藏 include 缺失、间接依赖断裂等问题，只有 strict 模式 `-include banned_functions.h` 改变编译单元顺序后才能暴露
7. **显式 include 原则**：每个源文件应显式 include 其直接使用的所有头文件，不依赖间接 include 链
8. **并行测试是发布前的必要验证**：`ctest -j$(nproc)` 必须纳入发布前检查清单
9. **CMake 编译基础设施必须跨模块对齐**：feature test macros、banned_functions.h 注入逻辑、WARNINGS_AS_ERRORS 等应在所有子模块中保持一致
10. **独立 build 目录**：strict 和 non-strict 模式使用独立 build 目录，避免 CMake 缓存污染
11. **镜像版本锁定**：生产环境绝不使用 `:latest` 标签，所有基础镜像必须锁定到 minor 版本
12. **基础镜像版本统一**：全项目的基础镜像版本（Ubuntu、Python、Nginx）应统一管理，避免模块间版本不一致
13. **前端日志集中管理**：禁止直接使用 `console.log`，必须通过集中式日志工具，支持环境变量控制日志级别
14. **环境变量注入外部端点**：所有 API URL、WebSocket 地址等外部端点必须通过环境变量注入，禁止硬编码
15. **增量测试覆盖**：按业务价值排序，优先覆盖高交互频率组件，每次聚焦 2-3 个组件渐进提升
16. **Mock 复用**：将通用 mock（Tauri API、i18n、动画库）提取为共享模块，避免测试文件中重复定义

### 19.2 检查清单

在每次发布前，执行以下验证：

```bash
# 1. 编译验证（普通模式）
cmake -B build -DWARNINGS_AS_ERRORS=ON -DBUILD_TESTS=ON
cmake --build build -j$(nproc)

# 2. 编译验证（strict 模式）
cmake -B build-strict -DAGENTOS_COMPLIANCE_STRICT=ON -DWARNINGS_AS_ERRORS=ON
cmake --build build-strict -j$(nproc)

# 3. 测试验证（并行）
cd build && ctest --output-on-failure -j$(nproc)

# 4. 前端测试覆盖率
cd Desktop && npx vitest --coverage

# 5. 质量门禁
bash scripts/ci/pipeline/quality-gate.sh --strict

# 6. CI 审计
grep -rn '|| true' .github/workflows/
grep -rn 'continue-on-error' .github/workflows/

# 7. Docker 镜像版本审计
grep -rn ':latest' --include='*.yml' --include='Dockerfile*' .
grep -rn 'nginx:alpine\|FROM ubuntu:' --include='Dockerfile*' .

# 8. 前端代码规范检查
cd Desktop && npx eslint . && npx tsc --noEmit
```

### 19.3 禁止事项

- ❌ 局部定义错误码（`#ifndef AGENTOS_ERR_XXX`）
- ❌ 使用 `head -z -N` 便携性不确定的语法
- ❌ 安全扫描使用超敏感正则（如 `[A-Za-z0-9+/]{40,}`）
- ❌ 危险函数扫描不使用词边界
- ❌ CI 步骤使用 `continue-on-error: true` 掩盖依赖安装失败
- ❌ CI 质量门禁与本地脚本不一致
- ❌ 使用 `mkdir()` + 硬编码 `XXXXXX` 路径（应使用 `mkdtemp()`）
- ❌ 在源文件中定义 feature test macros（应在 CMake 级别定义）
- ❌ 依赖间接 include 链获取符号（应显式 include 直接依赖的头文件）
- ❌ 在同一个 build 目录中切换 strict/non-strict 模式而不删除 CMake 缓存
- ❌ 生产环境使用 `:latest` 镜像标签
- ❌ 基础镜像不锁定 minor 版本（如 `nginx:alpine`、`ubuntu:22.04`）
- ❌ 跨服务使用不一致的基础镜像版本（如 Python 3.11 与 3.12 混用）
- ❌ 前端直接使用 `console.log` 而不过集中式日志工具
- ❌ 硬编码 API URL 或 WebSocket 地址在源码中
- ❌ 测试中每个文件重复定义相同的 mock（应提取为共享模块）

## 20. Docker 镜像版本管理与依赖标准化

### 20.1 `:latest` 标签生产环境不可用

**问题发现**：项目多处 docker-compose 和 Dockerfile 中使用 `:latest` 标签，包括生产环境配置文件。`latest` 标签指向的镜像内容随时间变化，无法保证构建的可重现性和回滚能力。

**影响范围**：10+ docker-compose 文件，涉及 staging、production、gateway、deploy 等多个部署环境。

**不良模式**：
```yaml
# docker-compose.prod.yml — 生产环境使用 latest
image: ${DOCKER_REGISTRY:-spharx}/agentos-desktop:${AGENTOS_VERSION:-latest}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-atoms:${VERSION:-latest}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-gateway:${VERSION:-latest}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-daemon:${VERSION:-latest}
```

```yaml
# gateway docker-compose.yml
image: ghcr.io/spharx/agentos/gateway:${BUILD_VERSION:-latest}
```

**正确模式**：
```yaml
# 显式版本号，默认值指向固定版本
image: ${DOCKER_REGISTRY:-spharx}/agentos-desktop:${AGENTOS_VERSION:-0.1.0}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-atoms:${VERSION:-0.1.0}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-gateway:${VERSION:-0.1.0}
image: ${DOCKER_REGISTRY:-ghcr.io/spharx}/agentos-daemon:${VERSION:-0.1.0}
image: ghcr.io/spharx/agentos/gateway:${BUILD_VERSION:-0.1.0}
```

**教训**：
- 生产环境绝不允许 `:latest` 标签；每个部署必须指向明确的版本号
- 环境变量默认值应设置为最新稳定版本，而非 `latest`
- 版本号策略：开发/测试环境可用 `latest`，staging 和 production 必须固定版本
- 发布流程中应包含镜像标签审计步骤

### 20.2 基础镜像未锁定版本

**问题发现**：生产环境配置中使用 `nginx:alpine` 未锁定 minor 版本，多个 Dockerfile 使用 `ubuntu:22.04`（非最新 LTS），OpenLab 使用 `python:3.11-slim` 与其他服务（Python 3.12）不一致。

**不良模式**：
```yaml
# 未锁定版本的 nginx
image: nginx:alpine
```

```dockerfile
# 使用过时的 LTS 版本
FROM ubuntu:22.04 AS base
FROM ubuntu:22.04 AS runtime
```

```dockerfile
# Python 版本与项目其他服务不一致
FROM python:3.11-slim AS base
```

**正确模式**：
```yaml
# 锁定 minor 版本
image: nginx:1.27-alpine
```

```dockerfile
# 使用最新 LTS
FROM ubuntu:24.04 AS base
FROM ubuntu:24.04 AS runtime
```

```dockerfile
# 统一 Python 版本
FROM python:3.12-slim AS base
```

**影响范围**：
- `AgentOS/scripts/ops/deploy/Dockerfile.kernel`：Ubuntu 22.04 → 24.04
- `AgentOS/scripts/ops/deploy/Dockerfile.service`：Ubuntu 22.04 → 24.04
- `AgentOS/agentos/daemon/Dockerfile.ci`：Ubuntu 22.04 → 24.04
- `AgentOS/agentos/openlab/Dockerfile`：Python 3.11 → 3.12
- `AgentOS/scripts/ops/deploy/docker-compose.prod.yml`：nginx:alpine → nginx:1.27-alpine

**教训**：
- 基础镜像必须锁定到 minor 版本以保证可重现构建
- 全项目的基础镜像版本应统一管理，避免模块间版本不一致
- Ubuntu LTS 版本应跟随最新稳定版（当前为 24.04）
- Python 版本应跨所有服务保持一致，避免依赖兼容性问题
- 建议在 CI 中增加基础镜像版本检查步骤

### 20.3 镜像版本审计命令

**审计方法**：
```bash
# 扫描所有 :latest 标签
grep -rn ':latest' --include='*.yml' --include='Dockerfile*' .

# 扫描未锁定版本的基础镜像
grep -rn 'nginx:alpine\|ubuntu:[0-9]' --include='*.yml' --include='Dockerfile*' .

# 扫描 FROM 指令中的版本
grep -rn '^FROM ' --include='Dockerfile*' .
```

**审计结果**（修复后）：
| 类别 | 修复前 | 修复后 |
|------|--------|--------|
| `:latest` 标签 | 10+ | 0 |
| 未锁定 nginx | 2 | 0 |
| Ubuntu 22.04 | 6 | 0 |
| Python 版本不一致 | 1 | 0 |

## 21. 前端代码规范化

### 21.1 `console.log` 零化与集中式日志

**问题发现**：桌面客户端（React + TypeScript + Tauri）中存在 **67 处** `console.log` 直接调用，散布于组件、页面、hooks 和工具函数中。这些调用在生产环境中可能泄露内部状态信息，且缺乏统一的日志级别控制和格式化。

**不良模式**：
```typescript
// 散布在各处的 console.log
console.log('fetching data...');
console.log('error:', error);
console.log('state updated:', newState);
```

**修复措施**：创建集中式日志工具 `logger.ts`，将所有 `console.log` 迁移为结构化日志调用：

```typescript
// src/utils/logger.ts
enum LogLevel {
  DEBUG = 0,
  INFO = 1,
  WARN = 2,
  ERROR = 3,
  NONE = 4,
}

const CURRENT_LEVEL = import.meta.env.VITE_LOG_LEVEL 
  ? parseInt(import.meta.env.VITE_LOG_LEVEL) 
  : import.meta.env.PROD ? LogLevel.WARN : LogLevel.DEBUG;

export const logger = {
  debug: (...args: unknown[]) => {
    if (CURRENT_LEVEL <= LogLevel.DEBUG) console.debug('[DEBUG]', ...args);
  },
  info: (...args: unknown[]) => {
    if (CURRENT_LEVEL <= LogLevel.INFO) console.info('[INFO]', ...args);
  },
  warn: (...args: unknown[]) => {
    if (CURRENT_LEVEL <= LogLevel.WARN) console.warn('[WARN]', ...args);
  },
  error: (...args: unknown[]) => {
    if (CURRENT_LEVEL <= LogLevel.ERROR) console.error('[ERROR]', ...args);
  },
};
```

**迁移策略**：
- 组件渲染中的调试日志 → `logger.debug()`
- 数据获取/状态变更 → `logger.info()`
- 可恢复错误 → `logger.warn()`
- 不可恢复错误 → `logger.error()`

**教训**：
- 前端项目应尽早建立集中式日志规范，避免后期大规模迁移
- 日志级别应根据环境变量和生产/开发模式自动切换
- 生产环境默认最低日志级别为 WARN，减少信息泄露风险
- 集中式日志工具便于后续接入远程日志收集服务

### 21.2 硬编码 URL 消除

**问题发现**：桌面客户端中多处 API 端点以硬编码字符串形式内联在代码中，导致：
- 环境切换时需要修改源码
- 不同部署环境下 URL 不一致
- 安全审计难以追踪所有外部请求目标

**不良模式**：
```typescript
// 硬编码 API URL
const response = await fetch('http://localhost:8080/api/v1/agents');
const ws = new WebSocket('ws://localhost:8080/ws');
```

**修复措施**：创建环境变量配置文件 `.env.example`，将所有 API 端点通过 Vite 环境变量注入：

```bash
# .env.example
VITE_API_BASE_URL=http://localhost:8080
VITE_WS_URL=ws://localhost:8080
VITE_AUTH_ENDPOINT=/api/v1/auth
VITE_AGENTS_ENDPOINT=/api/v1/agents
```

```typescript
// 使用环境变量
const API_BASE = import.meta.env.VITE_API_BASE_URL;
const response = await fetch(`${API_BASE}${import.meta.env.VITE_AGENTS_ENDPOINT}`);
```

**教训**：
- 所有外部端点 URL 必须通过环境变量注入，禁止硬编码
- 提供 `.env.example` 模板文件，文档化所有必需的环境变量
- 在 CI 中增加硬编码 URL 扫描步骤（如检测 `http://`、`https://` 字面量）
- 桌面客户端使用 Tauri 时，可通过 Tauri command 将后端 URL 从 Rust 侧传递给前端

## 24. AGENTOS_E* 错误码本地重定义深度清理 (v23.14.0)

### 24.1 问题发现

**背景**：经过多轮 BAN 合规修复后，代码库中 raw malloc/free、printf/fprintf、return -N 魔数已全部清零。但深入扫描发现了一个系统性陷阱：**AGENTOS_EINVAL/EFAIL 本地重定义**。

**问题表现**：35 个文件通过 `#ifndef AGENTOS_EINVAL` 守卫，在本地定义 `AGENTOS_EINVAL (-1)` 作为 fallback 值。当 error.h 未正确包含时，这些 fallback 值不一致：

```c
// error.h 中的标准定义
#define AGENTOS_EINVAL  AGENTOS_ERR_INVALID_PARAM  // = (-2)

// 各文件中的本地 fallback（不一致）
#ifndef AGENTOS_EINVAL
#define AGENTOS_EINVAL (-1)  // 错误！应为 (-2)
#endif
```

**影响范围**：
- 5 个文件存在**重复定义块**（同一文件出现两次 `#ifndef AGENTOS_EINVAL`）
- gateway_compat.h 的 fallback 值与 error.h 完全不匹配（EFAIL=-17, ENOMEM=-12, EINVAL=-1）
- 6 个文件缺少 `#include "error.h"`，完全依赖本地 fallback

### 23.2 修复策略

**三阶段修复**：

**第一阶段 — 直接删除**（13 个文件）：
已有 `#include "error.h"` 的文件，直接删除 `#ifndef AGENTOS_EINVAL/EFAIL` 降级定义块。

**第二阶段 — 添加头文件+删除**（6 个文件）：
缺少 `#include "error.h"` 的文件，先添加头文件，再删除本地定义。

**第三阶段 — 重复定义清理**（5 个文件）：
estimator.c、controller.c、budget.c、strategy_common.c、token_standard.c 各含 2 组重复定义，全部删除。

### 23.3 gateway_compat.h 重构

**修复前**：
```c
#ifndef AGENTOS_EFAIL
#define AGENTOS_EFAIL (-17)   // 与 error.h 不一致
#endif
#ifndef AGENTOS_ENOMEM
#define AGENTOS_ENOMEM (-12)  // 与 error.h 不一致
#endif
#ifndef AGENTOS_EINVAL
#define AGENTOS_EINVAL (-1)   // 与 error.h 不一致
#endif
```

**修复后**：
```c
#include "error.h"  // 统一来源，消除不一致

#ifndef AGENTOS_SUCCESS
#define AGENTOS_SUCCESS 0
#endif
```

**影响**：9 个通过 gateway_compat.h 间接包含的文件受益。

### 23.4 教训

- **`#ifndef` 守卫是双刃剑**：提供 fallback 的同时掩盖了错误码不一致的风险
- **错误码必须有单一来源**：所有 AGENTOS_E* 定义必须来自 error.h，不允许本地 fallback
- **重复定义是代码腐化的信号**：5 个文件的重复定义表明代码经历了多次不加验证的修改
- **交叉验证是唯一可靠的验证手段**：grep 扫描 `#define AGENTOS_EINVAL (-1)` 是发现此类问题的唯一方式

## 25. strndup 合规与 BAN 规则扩展 (v23.16.0)

### 24.1 问题发现

**背景**：深度的 BAN 合规扫描发现，banned_functions.h 缺少对 `strndup` 的毒化。虽然 `strdup` 已被 `#pragma GCC poison` 禁止，但其变体 `strndup` 未被覆盖，导致 3 个生产文件存在原始 `strndup()` 调用。

**漏洞影响**：
- gateway/src/utils/syscall_router.c:764 — `strndup(input, len)`
- gateway/src/utils/gateway_protocol_handler.c:726 — `strndup(request_data, request_size)`
- protocols/core/transformers/src/protocol_transformers.c:78 — `strndup(start, len)`

同时，gateway_protocol_handler.c:729 存在 `return -2` 魔数，应替换为 `AGENTOS_ERR_OUT_OF_MEMORY`。

### 24.2 修复方案

**strndup 替换**：
```c
// 修复前
*jsonrpc_out = strndup(request_data, request_size);
return *jsonrpc_out ? 0 : -2;

// 修复后
*jsonrpc_out = AGENTOS_STRNDUP(request_data, request_size);
return *jsonrpc_out ? 0 : AGENTOS_ERR_OUT_OF_MEMORY;
```

**banned_functions.h 三层扩展**：

1. **Poison 层**（strict 模式编译时阻断）：
```c
#pragma GCC poison strndup
```

2. **Deprecated 层**（非 strict 模式编译警告）：
```c
__attribute__((deprecated("Use AGENTOS_STRNDUP instead")))
static inline char *__banned_strndup(const char *s, size_t n) { return (strndup)(s, n); }
```

3. **Macro 覆盖层**（自动替换）：
```c
#define strndup(s, n)   __banned_strndup(s, n)
```

### 24.3 验收结果

| 指标 | 目标 | 实际 | 状态 |
|------|------|------|------|
| 生产代码 raw strndup | 0 | 0 | ✅ |
| banned_functions.h strndup 毒化 | 已添加 | 已添加 | ✅ |
| 编译 (strict) | 0 error 0 warning | 0 error 0 warning | ✅ |
| ctest | 97/97 | 97/97 | ✅ |

### 24.4 教训

- **BAN 规则必须覆盖函数族的所有变体**：`strdup` → `strndup`、`sprintf` → `snprintf`/`vsprintf`/`asprintf`
- **每次添加新 banned function 后必须全量编译验证**：确认所有调用方已替换为 AGENTOS_* 宏
- **memory_compat.h 必须与 banned_functions.h 同步更新**：新增 AGENTOS_STRNDUP 宏提供合规替代方案
