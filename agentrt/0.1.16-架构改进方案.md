> 状态：**全部落地并验证**（2026-09-13，三次收口）。P0/P1/P2 逐项实施完成；原登记为「遗留」的 4 项
> （N-1/N-3 运行级回归、CI-2、U-02、TUI 技能库与向导配置收敛）**全部在本轮闭环，无一项顺延后续版本**。
> 目标版本：**0.1.16**。
> 基线：agentrt `VERSION=0.1.15`；承接文档 `0.1.9 / 0.1.11 / 0.1.12 / 0.1.13 / 0.1.13-生产级就绪审查 / 0.1.15`。
> 范围：记忆面（CLI/gateway）UTF-8 字节截断链修复 + 存量损坏数据清理 + 供应商 400/422 分诊 + 发布链 U-01/U-02 残余 + CI 附录 B.7 三项 + **CLI 核心 / TUI 增强架构级改造（TUI 记忆收敛 gateway `mem.*`；TUI 技能库收敛 gateway `mem.*`(`kind=skill`)；TUI 向导/模型配置收敛 `model.yaml` + `secrets.env`）**。

## 0. 立项触发

v0.1.15（含覆盖重发版）后，社区仍反馈七类问题：

1. **运行不稳定**：长对话/长回复下终端失能、流式中断；
2. **安装问题**：全新 bootstrap 与升级路径的分歧；
3. **更新问题**：版本指针滞后窗口、rc/beta 通道制品缺失；
4. **联网问题**：`Failed to parse the request body as JSON: … invalid unicode code point`（HTTP 400）被上报为"网络失败"；
5. **功能不全**：声明与实现不一致（如 CLI/TUI "共享记忆库"）；
6. **工具无法正常有效使用**：工具结果/参数面在多字节内容下失效；
7. **CLI 与 TUI 偏离决策**：「CLI 是核心与基础，TUI 是可选增强体验」的历史决策与前端实现分叉。

本轮以**源码取证 + 实例数据校验**为唯一依据，逐条定性。**七类中 1/4/6 收敛到同一根因**（下 N-1）。

**★ 最新决策（2026-09-13，用户裁定，覆盖此前"另行立项"口径）**：**CLI 是核心，TUI 是可选的增强；0.1.16 完成该架构级改造。** 据此，第 7 类不再停留在"修正不实注释 / 登记后续项"，而是**本轮落地架构性收敛**：TUI 降格为 CLI 的渲染层，不得持有任何独立存储/组织逻辑；一切平台能力经 gateway 翻译到 daemon（`mem.*` → mem_d），TUI 与 CLI 共享同一后端、同一存储、同一 schema。落地见 §2.3 D-1/D-2/D-3 与 §4 台账。

## 3. N-1 详述（本方案最重要的一节）

### 3.1 缺陷形状（六处同形）

注入侧（读回并拼 system 段）：

```c
size_t n = dlen < 200 ? dlen : 200;              /* ← 字节数，非字符数 */
snprintf(out_buf + off, out_size - off, "\n- %.*s", (int)n, rec);
```

写回侧（本轮对话落盘）：

```c
char content[1800];
int n = snprintf(content, sizeof(content), "用户: %s\nAgentRT: %s", input, reply);
...
if (n > 1600)
    n = 1600;                                    /* ← 在中文字符内部截断 */
content[n] = '\0';
```

metadata 侧（gateway reasoning 存档，**第 6 处**）：

```c
size_t rl = strlen(sctx->reasoning);
if (rl > 600)
    rl = 600;                                    /* ← 字节数，切断汉字/emoji */
/* gw_json_escape_append 对 >= 0x20 的字节原样拷贝、不做 UTF-8 校验：
 * 半个多字节序列被直接写进 metadata JSON。 */
gw_json_escape_append(meta + mn, cap - mn, sctx->reasoning, rl);
```

`%.*s` 与 `content[n] = '\0'` 的**精度/下标都是字节**。中文字符 3 字节、emoji 4 字节，"恰好切在字符内部"是**常态而非边界用例**。

### 3.2 数据实证（独立复现）

对实例 `mem.jsonl` 逐行按 200 字节截断后做 UTF-8 严格解码：

- **17/42** 行产生非法序列（截断点多落在 position 198-199）；
- **3 行** 已落盘非法（第 7/9/11 行，`len:1799`，尾部含 `�`，来源 `source:"gateway"` → 命中 gateway 写回路径 `:189-195`）；
- **3 条** `source:"cli"` 长记录恰封顶 1600 → 命中 CLI 写回路径 `:234-236`。

### 3.3 因果链（与实机日志同源）

```
[写回] 1600 字节截断（CLI 或 gateway，未做 UTF-8 边界回退/清洗）
  → mem.jsonl 落入非法 UTF-8 记录
  → [下轮注入] mem.search/mem.get 召回该记录 → 200 字节截断（同样切坏）
  → 拼入 messages[].content → cJSON 原样输出非法字节
  → llm_d 转发 provider → HTTP 400
       "Failed to parse the request body as JSON:
        messages[2].content: invalid unicode code point at line 1 column 5259"
  → CLI 映射为 AIRY_ERR_IO → 误报"读写/网络错误"
```

### 3.4 修复（复用仓内既有范式，零新 API）

| 位置 | 现状 | 修复后 |
|---|---|---|
| `cli_chat_memory.c:132` | `n = dlen<200?dlen:200` | `n = cli_utf8_safe_len(rec, 200)` |
| `cli_chat_memory.c:204` | 同上（`data`） | `n = cli_utf8_safe_len(data, 200)` |
| `cli_chat_memory.c:234-236` | `if (n>1600) n=1600;` | `n = (int)cli_utf8_safe_len(content, 1600)` |
| `cli_chat_memory.c:290-291` | 同上 | 同上 |

### 4.2 §3.2 损坏行 `len:1799` 归因（据实更正）

上一稿曾将 `len:1799` 归因于「未 clamp 的 `syscall_router_memory.c` 直写」。本轮**逐行复核该文件 307 行后确认该归因不成立**：

- `gateway/src/utils/syscall/syscall_router_memory.c` 的 `route_memory_methods()` 对 `mem.write` 仅做 `data->valuestring` + `strlen` 原样取参，其内部 `airy_sys_memory_write(const void*, size_t, const char*, char**)`（`:122`）经 `syscall_svc_call_unwrap("mem","write",…)` **纯 IPC 转发**、无任何截断或长度改写 → 它在结构上**不可能制造** `len:1799`。故「直写候选」不成立（纠正依据为文件本体，非"文件不存在"）。

**据实结论**：`1799 = sizeof("char content[1800]") − 1`，正是记录体组装缓冲在**满缓冲**时的最大可写字节数，即"按 `strlen(content)` 全量写出、未施加 1600 上限"的旧组装路径产物。产生这样一条 1800 字节缓冲的写入者**只有两处**：CLI `cli_chat_memory.c` 与 gateway `gateway_sse_memory.c`（二者均为 `char content[1800]`）。现存两处写入者在本轮均已完成「1600 上限 + UTF-8 边界回退 + `sanitize` 清洗」，`strlen` 恒 ≤ 1600 → **当前代码库在结构上不可能再生 `len:1799`**。

> 说明：该批损坏落盘于修复前，且仓库历史经 squash（`git log -- <file>` 无细粒度记录），无法回溯到确切的旧代码版本。故此处以**「枚举全部现存写入者 + 证明其不可能产出该长度」**作为收敛依据（见 §3.2 数据实证与 §2.2 N-1/§3.4 修复面），不以不可复现的历史代码作断言。
