## 0. 立项背景与定位

### 0.0 术语对照表（与 0.1.18 §0.0 同源）

本方案统一使用标准计算机术语；项目内惯用语在下表定义，正文不再另行解释。

| 本方案用语 | 标准术语 / 定义 |
|---|---|
| 适配实现（原"方言"） | provider adapter：针对不同 LLM 服务商 API 差异（鉴权、流式分帧、usage 字段、工具调用格式）的协议适配层，位于 `providers/adapters/`，纯函数、无 I/O |
| 样板改造（原"打样"） | pilot implementation：以 llm_d 为试点完成的结构改造，作为其余 daemon 的参考模板 |
| 遗留冗余（原"化石"） | 被替代方案取代、已无存在必要的历史实现（如 deepseek.c 与 local.c 的克隆代码） |
| 死代码（原"死码"） | dead code：无任何调用方的代码（以 `nm` + grep 双确认） |
| 清理（原"出清"） | 依据证据清单删除死代码/遗留冗余的施工动作 |
| 收敛（原"收口"） | 把分散/暴露的实现点合并到唯一权威位置（SSoT），关闭越权暴露面 |
| 平铺（原"散置"） | 源文件未分子目录、直接堆叠在 `src/` 顶层的布局 |
| 跨层违规调用（原"越界"） | 绕过分层契约的直接调用（如 service 层绕过注册表直连 HTTP 或 mem_d） |
| 无效参数/无效路径（原"幻影"） | phantom：已声明但从未生效的配置参数，或指向不存在目标的路径 |
| 误导性 API（原"撒谎式 API"） | 接口行为与名称/日志承诺不符（如 reload_config 不读文件却报"已重新加载"） |
| 质量门禁（"门禁"） | CI 中可机器断言的验收规则（本方案 V 系列判据） |
| 台账 | 每条变更附 `文件:行` 级证据的逐项清单，是减重验收的凭据 |
| SSoT | Single Source of Truth，单一事实源：同一知识全仓只存一处 |
| 下沉 | 把跨模块重复实现移入底层公共库（commons/atoms），消费方改为链接公共实现 |
| 画像（profile） | 描述组件策略选择的声明式配置（模型画像、调度画像等） |
| 名实一致 | 文档声明与实际实现一致（如 README 方法表 vs 实际注册数） |
| ops 注入 | 依赖倒置：跨 daemon 能力复用经零依赖 micro-lib 函数表（airy_*_ops）在装配期注入，取代对兄弟服务库的直接链接 |
| 七域 | llm_d 样板确立的目录结构模板：bootstrap / rpc / config / 机制核心域 / 策略子域 / adapter / 专项域，各 daemon 按需裁剪 |
| commons（统一基础库） | 全仓唯一零依赖基元库（安全基元 / 三平台抽象 / [SC] 契约），位于 `agentrt/commons/`；**注意与 `daemons/common`（服务层内聚公共代码，16,939 行）区分**——后者是 V16.6 裁决对象，前者是下沉件权威落点 |
| 原子化组件 | 一组件 = 一目录 = 单一职责公开头 + 实现 + 独立单测；组件依赖成 DAG、零外部依赖（deps.txt 白名单制） |
| 功能矩阵 | atoms 完备化核对基准：`组件 × 能力 × 平台（Linux/macOS/Windows）× 真实消费者` 四列表 |
| 外置（relocation） | 把代码/数据搬出 agentrt 范围（迁 ecosystem 或系统依赖），功能由承接方保持等价提供——是搬移不是删除 |
| 计量口径调整（scope） | 改变统计边界（三方件转系统依赖、跨目录合并口径拆分等），不改代码，只改"计入哪一层"的判据 |
| 功能守恒 | feature preservation：二版裁定一切手段的总约束——对外可见行为与能力集合零变化（§2.4） |

### 0.2 本版使命（用户裁定，2026-09-20）

> 「开始编写 0.1.19 版本改进方案，首要工程是完成 daemons 的整体减重。」

三句话拆解：

1. **整体**——不是逐模块零敲碎打，而是 16 模块（+新建 supervisor\_d）在同一张目标表、同一套门禁、同一条施工流水线下同步推进；
2. **减重**——减的是带 `文件:行` 证据的死代码 / 跨模块重复 / 单实现抽象（V16.14 台账制），**不是凑指标删功能、删测试、删策略**（V16.16）；
3. **结构**——体量只是结果，本版的实体工作是**七域结构模板落地**：每个 daemon 从"顶层平铺"收敛为 `bootstrap / rpc / config / 机制核心域 / 策略子域` 的标准形态（llm\_d 样板改造的推广，V16.9）。

**扩展裁定（同日补，2026-09-20，c/d/e 三条）**——本版由 daemons 单层扩展为三层系统性工程：

| 层 | 系统定位 | 本版使命 | 施工线 |
|----|----------|----------|--------|
| **daemons 用户态服务层** | agentrt 策略面 | 整体减重（87,705 → ≤43,853，−50%）+ 七域结构标准化 | T / S / D 线（§3.1–§3.3）+ W 线（§3.4） |
| **commons 统一基础库** | 全仓唯一零依赖基元库（0.1.14 裁定：不砍反而要加强） | 持续原子化组件、能力最小化模块、最小完备化，并对整体减肥（74,341 → ≤52,039，−30%） | K 线（§4.18） |
| **atoms 微核心系统层** | 跨 Linux/macOS/Windows 用户态微核心（Linux 可选内核加速经 ops 注入） | 持续增强功能与能力、全量完备化，整体减肥并避免死代码（86,302 → ≤60,411，−30%） | A 线（§4.19） |

**二版量化裁定（同日再补，2026-09-20）**——「daemons 体积减 50%，commons 体积减 30%，atoms 体积减 30%，所有功能都不能变。请详细的阅读 AirymaxRT 的所有源代码，思考方案。」三要点：① 三层目标从结构判据升级为**硬性体积指标**（§2.1，含全源码勘察后的可达性论证）；② **功能守恒为最高约束**（§2.4、V19.13）——任何减量/搬移/口径动作前后，对外能力、RPC 方法面、契约注册表、错误码语义逐项守恒，禁止为指标删功能；③ 本裁定基于五路全源码勘察（成果固化于 §4.20）落档 §9.2，**覆盖 0.1.18 表一目标值**，表一下调为中间检查点。

## 2. 目标与不变量

### 2.1 总目标（2026-09-20 二版裁定：三层硬性体积指标）

**硬性目标**（计量口径 = §1.1；功能守恒为凌驾一切体积指标的约束，§2.4）：

| 层 | 基线 | 终验目标 | 需达成减量 |
|----|------:|---------:|-----------:|
| daemons | 87,705 | ≤43,853 | **−43,852（−50%）** |
| commons | 74,341 | ≤52,039 | **−22,302（−30%）** |
| atoms | 86,302 | ≤60,411 | **−25,891（−30%）** |
| 三层合计 | 248,348 | ≤156,303 | −92,045（−37.1%） |

**三类计量**（每层减量按类分别记账，禁止混计凑数）：

| 类 | 定义 | 对三层合计的作用 | 机器判据 |
|----|------|------------------|----------|
| **净减** | 真删除：死代码 / 重复实现 / 冗余抽象 / 双轨清退 | 总量下降 | `文件:行` 台账 + grep/nm 复测双零 |
| **归位** | 代码移出层范围、功能由承接方等价提供（外置 ecosystem、下沉共享运行时） | 视承接方而定：**收敛型承接方**（N 份重复 → 1 份共享）扣减承接件成本后仍是净减；**层间平移为零和**，承接层须有一一冲销 | 承接方真实消费者 + 移出侧零引用 + V19.13 守恒对照 |
| **口径** | 统计边界变化（三方件转系统依赖、target 拆分澄清），代码与功能不动 | 不变 | W 线逐项公示（§3.4）+ 代码零变更证明 |

**可达性结论（五路全源码勘察，证据台账 §4.20；开工由 M19.0 复测定稿）**：

- **atoms：基本可达**。净减证据 ≈24,500–26,300（coreloopthree ≈11,041 + 其余组件 ≈13,500），兑现条件 = taskflow 收敛到 14-API 真实存活面（净减 ≈4,200）+ K-3/K-5 清零；K-4 ipc 域 ≈1,600 为向 commons 既有 ipc 件（139 消费者）的收敛归位，承接成本已计入 K 线。
- **commons：纯净减不可达**。净减证据 ≈6,200（−8.3%）+ 待复核估算 ≈1,200–2,100（F18 三轨兼容、F19 memory 头）；三类合计（W1 nghttp2 5,999 口径 + W3 token/sd 外迁 ≈1,900）上限 ≈17,400–18,400（−23%~−25%），**缺口 3,900–4,900**——剩余手段只有对活大件做函数级减脂（config\_unified 9,060 / ipc 7,087 / sync 6,310 / memory 5,428，精华区、R9 高风险），或按裁定修正目标值（§9.2 开放事项①）。
- **daemons：缺口最大，本版的三层目标实质上就是 daemons 问题**。净减证据 ≈17,900–20,300（表一账 12,700 + 新发现 5,200–7,600，重复计数由 M19.0 复测裁定）+ W4 口径 2,527 + W2 归位 ≈700 ≈ 21,100–23,500（24%–27%）；**剩余 ≈20,400–22,700 缺口唯一可指望的补口是 W5 handler 组收敛归位**（16 daemon 的 RPC/业务 handler 壳收敛到共享运行时 + 声明式方法表，理论上限待承接件设计实测）。W5 不成立则 daemons −50% 在功能守恒下**不可达**（§9.2 开放事项②）。

**表一下调**：0.1.18 §12.16.10 表一逐模块目标值下调为**中间检查点**（施工进度参考）——§4 逐模块台账仍引用表一数字作为施工中尺，但最终验收一律以上表硬性目标为准；本下调落档 §9.2，对应修订 §9.1 纪律第 5 条。
