## 1. 技术前提：原生 ARM64 runner（2026-09-05 已定案）

- GitHub 官方原生 ARM64 runner `ubuntu-24.04-arm` / `ubuntu-22.04-arm` 已 GA：public repo 免费 4 vCPU（2025-08 GA；2026-01 起 private repo 也可用）。
- **armv7 无需 QEMU**：aarch64 内核 CONFIG_COMPAT 原生执行 AArch32 用户态（GitHub arm64 runner 的 Cobalt 100 CPU 实证支持；社区数据 QEMU 6-8min → 原生 2min）。
- x86-32 从不需要 QEMU（x86-64 CPU 硬件兼容 i386）；当前 x86-32 腿 10.5min 全是自编 deps，镜像化即解决。
- **仅 riscv64 仍需 QEMU**（无原生 hosted runner，0.3.x 评估；镜像/仓库名 qemu 字样暂保留）。
- **先行试点已完成**（build-toolchain-images.yml，2026-09-05）：
  - matrix 三腿（arm64/arm32 → `ubuntu-24.04-arm`，amd64 → `ubuntu-latest`），commit abf90ef01 + 12d19858a。
  - run 11 实测：arm64 3.6min ✅、amd64 3.5min ✅（旧 QEMU 路径 88min 的同类工作负载）。
  - 教训入册：job 级 if 不支持 matrix context（0.2.x 附录 B-6）；容器内 `uname -m` 返回宿主架构，判定必须用 TARGETARCH。

| release 腿 | 现状 | 0.1.12 目标 |
|---|---|---|
| linux-x86-64 | 镜像化 + ubuntu-latest（179c4e956） | 维持 |

| windows/macos 腿 | 原生 runner（无容器） | 维持 + B1/B2 探针 |

### 3.2 AArch32 compat 探测（稳定优先）

- arm-32 腿容器内首步 fail-fast 探测：
  ```bash
  # aarch64 内核 AArch32 compat 探测：armhf loader 必须可执行
  test -x /lib/ld-linux-armhf.so.3 || { echo "::error::AArch32 compat 不可用"; exit 1; }
  ```
- 探测失败（runner 内核/机型变更等未知风险）：腿标记失败并回落旧 QEMU 路径（保留 fallback job 定义，注释化切换开关）。
- 全部架构判定用 Docker `TARGETARCH`/buildx `--platform`，禁止 `uname -m`。

### 3.3 glibc 基线不变

- 原生 runner **仅当宿主**，构建仍在 `ubuntu:20.04`（arm64/armv7）容器内执行——glibc 2.31 基线、产物兼容性不变。
- 严禁直接在 runner 裸环境构建（runner ubuntu-24.04 glibc 2.39，产物将绑高版本 glibc，破坏 arm-32/arm-64 设备兼容）。

### 4.2 Windows 探针前置（B1.1/B2 不预写 leg）

- B1.1：MSVC `/std:c11` + stdatomic compat 映射 vs atoms 内存域全量换 compat atomic API，两案探针实证定案。
  - rc.2 静态普查（2026-09-05）：`_Atomic` 关键字全仓仅 2 处（corekern `refcount.h:34` `uint32_t _Atomic refcount`、coreloopthree `hook_metrics_handler.c:39` `static _Atomic uint64_t`），其余均为 `atomic_int/atomic_long` 等类型别名（可由 corekern 既有 stdatomic.h shim 以 `typedef volatile` + Interlocked 映射）。**案 B（compat API）只需收敛 2 处 `_Atomic` 关键字为 compat 类型，成本极小，倾向定案**；MSVC 至今未实现 `_Atomic`（`/experimental:c11atomics` 仍不完整），案 A 不可行性基本坐实。
- B2：x86 工具集可用性 + vcpkg `x86-windows` triplet + stdatomic 同源问题，探针绿后才建 leg。

## 5. 流水线深度优化（拆分/复用/整合研究）

### 5.1 release.yml 大文件治理（现 ~1300 行，8 构建腿 + release + publish）

**现状取证**（2026-09-05 全文通读）：

- release.yml 8 腿：linux-x86-64(L39) / macos-arm-64(L144) / macos-x86-64(L253) / windows-x86-64(L355) / riscv-64(L498) / arm-64(L629) / linux-32(L751) / arm-32(L882)，加 release(L978) + publish(L1102)。
- **漂移实锤**：L247 自注"macOS 双腿打包步骤同构，仅 platform 标记与制品名不同"；四条 Linux 容器腿共享 Checkout→Init-submodules→docker run(tee+ERR trap)→Package→Upload 五段骨架，Package 步骤 8 腿各抄一份（config/modules/platform 标记仅差一行）；build-test.yml 另有 3 同构腿（linux-build-test-coverage/macos-build/windows-build）——P3 双实现漂移面 = 11 处近似拷贝。
- **矩阵化受限原因**（L33-38 已载）：Actions 容器作业仅 Linux runner；macos/windows 必须独立 job；此前 job 级 if × matrix 又被 B-6 判死，故现状以拷贝换正确性。

**方案细化**：

- **B（composite actions，先行，低风险）**——治逻辑复用，零编排变更：
  - `actions/lf-build-container`：docker run + `set -euo pipefail` + tee 日志 + ERR trap annotation 模板（参数：image-ref@digest、platform、log 名、容器内脚本）——消灭 4 腿 shell 引号陷阱重复。
  - `actions/lf-package`：Package + sha256 + upload-artifact（参数：version、platform、staging 目录）——8 腿 Package 归一，platform 标记/制品名作参数。
  - `actions/init-deps`：Checkout + init-submodules 包裹。
  - build-test.yml 同源调用 → P3 关闭；每抽一个 action 跑一次 rc 全链回归。
- **A（workflow_call 拆腿，后行，仅当 B 后仍 >800 行）**——治编排边界：
  - 拆 `release-linux.yml` / `release-macos.yml` / `release-windows.yml`（workflow_call + inputs: version/dispatch-only 腿开关），主文件留 needs 拓扑 + Environment 审批 + concurrency。
  - 已知代价：跨 workflow needs 只回传总体结论，腿级 UI 可见性下降；publish 的 `release` Environment 审批必须留在主文件（审批语义 = 发布安全阀，D2 不可下沉）。
  - **决策**：默认只做 B；A 仅在 B 落地后行数仍超标且编排复杂度（needs 表达式）持续增长时再评估，避免拆分本身成为新漂移源。

### 5.2 效率项（沿 0.2.x 阶段 I 承接）

| 项 | 内容 | 预期收益 |
