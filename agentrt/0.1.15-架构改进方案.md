## 0. 立项触发：一次真实崩溃，暴露了"验收断层"

### 0.1 现场

用户以普通中文提问「什么是特别国债」，TUI 正常流式输出若干行后：

```
[Super Agent]  16:33:07
    [MODE:CHAT]

    特别国债，是指由中央财政（财政部）为特定用途发行、专款专用的国债。…
    1. 专款专用：募集资金有指定用途，不用于▍
                                            thread 'main' (67560) panicked at src/app/mode.rs:31:18:
 end byte index 64 is not a char boundary; it is inside '部' (bytes 62..65 of string)
```

随后终端进入不可交互态：shell 提示符出现，但连按 `^C` 仅回显字面 `^C`、无法中断/退出，用户需关闭终端或手动 `reset`。

### 0.2 两个根因（均为语言级确定性缺陷，非偶发）

**根因 A — 字节切片越界 panic**

`airymaxhub/agent-workload/sdk/tui/src/app/mode.rs#L30-L31`：

```rust
let win = t.len().min(64);   // ← 字节长度，不是字符长度
let head = &t[..win];        // ← win 落在多字节字符内部 ⇒ Rust 判定非字符边界 ⇒ panic
```

该窗口是为"开头 64 字符内定位 `[MODE:` 标记"而设（见 L21-L24 注释「容错（2026-08-26 修复）」），但**把字符意图误写成字节算术**。中文按 3 字节/字编码，`t.len() > 64` 且第 64 字节非边界是**常态**——即"中文回复稍长即崩"，不是边界用例。

调用点：`src/app/task.rs#L345` `parse_mode_detail(&response.response)` —— 位于**每一次对话回复的主路径**上。

同类缺陷（同一 bug 类，需一并审计）：`src/main.rs#L961-L963`

```rust
fn truncate_str(s: &str, max: usize) -> &str {
    if s.len() <= max { s } else { &s[..max] }   // ← 同样按字节切
}
```

调用点 `src/main.rs#L571`（`debug!` 输出用户输入）。默认 `RUST_LOG` 为 info 时该分支不展开，**一旦开 `RUST_LOG=debug` 即同崩**——属潜伏同族。

**根因 B — 终端生命周期无守卫，panic 即失能**

`src/main.rs#L259-L331`：`enable_raw_mode()` + `EnterAlternateScreen` + `Hide` 在 L261-L279 置位；还原动作写在 `run_app` 返回**之后**（L317-L331），且：

- **无 `Drop` 守卫**：全仓 `impl Drop` 仅 3 处（`memory.rs:346` MemoryRovol、`ime.rs:178` ImeEngine、`main.rs:71` 测试用 Home），**没有任何终端守卫类型**；
- **无 panic hook**：全仓 `panic::set_hook` / `catch_unwind` **零命中**；
- `Cargo.toml#L73-L75` 明确「保持 panic=unwind 以便错误可观测」，即 panic 走 unwind 展开。

三者叠加的必然结果：panic 沿 `run_app(...).await` 展开、越过 `run_tui` 尾部的还原代码（不是返回路径，无 landing pad），**raw mode 与 alt screen 均未撤销** → 线规程未恢复 → `Ctrl+C` 不再产生 SIGINT 而只被终端回显为 `^C` → 用户"退不出去"。**该失能是根因 A 的确定性后果，而非独立偶发。**

- **影响面**：终端用户面 100%。产品对外第一触点（对话）对中文用户**不可用**；且故障态需要用户具备 `reset` 知识才能自救。

### 0.3 这次崩溃为什么没被拦住（本方案的核心论点）

`0.1.9-架构改进方案.md#L581-L597` 记载 M5「TUI 强化」W1-W8 **全部标注 ✅ 闭环**，`L610` 记「cargo 1.97.1 … `cargo test --offline` **147 单元 + 31 集成全绿、零告警**」，`L560` 记「W1-W8 TUI 强化 ①闭环」。同一份文档 `L597` 又写：

> 「M5 遗留：**无**（验收三线……均已具备可执行形态；**对话回归需运行态 gateway，随 0.1.9 集成验证批次执行**）」

即：**唯一能覆盖该缺陷的验收线（真实对话回归）被显式顺延，而遗留被记为"无"**。旁证是测试数据形态——`src/memory.rs#L557-L589` 的 `parse_mode_detail` 用例只覆盖两种输入：长度 < 64 字节的短串，或 80 个 ASCII `x`（>64 字节但每字节都是边界）。**没有任何用例喂入"长度 >64 且第 64 字节落在多字节字符内"的中文串**，所以 CI（`sdk/tui/.github/workflows/ci.yml` L31-L34 `cargo test --all`）必然全绿。

> **结论：这不是"测试太少"，而是"验收口径与用户路径错位"——门禁测的是函数在合成输入下的行为，不是产品在真实输入下的行为。**
>
> 这与本仓历轮反复出现的同一模式同源：0.1.9 十八项以架构结构性指标验收（依赖方向/模块归位/门禁在位），运行时安全与健壮性不在口径内（见第五轮审查结论 §五）。

### 4.4 WS-4 IPC 整体裁决（已定稿：启用接线，分阶段执行；批次 2 修复 → 批次 3 接线）

**裁决（2026-09-10，用户定稿）**：**IPC 是 Airymax 的产品特点，是 AirymaxRT 与 AirymaxOS 共享的核心机制**——依据 AirymaxOS 侧 IRON-9 v3 四层共享模型与代码实物收敛现状，**裁定 B（启用接线）**，选项 A（归档移除）**作废**：本库与共享契约已发生字节级收敛，不存在"归档"的决策空间。

**决策依据（设计思想 + 代码实物）**：

1. **设计思想层**（权威源：`docs/AirymaxOS/10-architecture/06-iron9-shared-model.md`）：
   - IPC 头 `airymax/ipc.h`（Layout C v4，128B 冻结布局、`AIRY_IPC_MAGIC`）属 **[SC] 共享契约层** 12 头之一，物理 SSoT 在 `include/uapi/linux/airymax/`，agentrt 侧经 sc-dual-ci 逐字节镜像维护（`commons/include/airymax/`）；
   - IPC 传输语义（channel / request-response / notification）属 **[SS] 语义同源层**；双端实现（agentrt：POSIX MQ + mmap/共享内存 + 信号量；agent-linux：io_uring）属 **[IND] 独立层**——"magic 同源、布局独立"正是该模型的预期形态；
   - AirymaxOS 侧已备完整韧性设计：数据面自治（Ring 生命周期与控制面解耦、Badge 离线校验）+ 控制面 Reconciliation（≤30s 最终一致，超时降级 [DSL]）。
2. **代码实物层**（四轮审查复核，推翻前情"死库"定性）：
   - **库在构建内**：`commons/utils/ipc` 7 源文件 + `circuit_breaker.c` 全部编入 `airy_common` 静态库（`commons/CMakeLists.txt#L140-190`）——缺陷不是"不存在"，而是"随构建扩散"，归档论的收益前提（移出构建消除潜伏面）已不成立；
   - **magic 收敛已落地**：`atoms/corekern/include/are_ipc.h#L47`（S-3 收敛，2026-08-15，L2 头字节级复用 Layout C v4）与 `commons/utils/ipc/ipc_common.h#L25`（P0-05 收敛，`#include <airymax/ipc.h>`）——该库是 Airymax IPC 体系组成部分（`docs/AirymaxOS/50-engineering-standards/120-cross-project-code-sharing.md` §4.1 收敛表在案）；
   - **corekern L1 真实存在**：`atoms/corekern` 持有 L1 内核级 IPC（`are_ipc.c`/`binder_channel`/`binder_registry`/buffer+OOM 池），40B `airy_kernel_ipc_message_t` + L2 服务信封 overlay 到 reserved[72]，与 commons 层构成"L1 传输 + L2 服务"双层架构。（**八轮定稿取证更正 2026-09-11**：L1 通道实现为 `src/ipc/binder_channel.c`（502 行，`include/ipc.h` 声明的 `airy_ipc_*` 族，40B 消息体定义于 `ipc.h:77-83`）；`are_ipc.c`（336 行）实测仅 7 个纯编解码函数（`are_ipc.c:102-320`：header_init/checksum_compute/header_validate/message_create/message_destroy/msg_type_str/proto_str），**无任何传输 API**——其定性为 L2 信封实现，非 L1 通道；锚点以 §4.4.1 定稿为准）
3. **缺口定性（如实）**：gateway（自有 TCP JSON-RPC）与 daemons（自有 `svc_ipc_init`，实为 HTTP URL）**均未调用** commons ipc 库 API（`ipc_channel_create` 生产零调用方）——是**实现未接线**，非设计废弃；部分文档声称的完成度与零接线并存，须在阶段 3 如实化。

**附记 2（corekern 运行状态取证 + 原生设计对照，2026-09-10 五轮复验，用户问"目前是否在正常运行？"）**：

**结论：corekern 在 agentrt 生产面为「随构建链接在、机制刻意未通电」——不是"正在正常运行"，也不是"死库"。**

运行状态证据链（分目录取证，全仓 grep 不可信）：
- **链接在**：`airy_core`（STATIC）编入构建并被消费——`tools/airy_cli/CMakeLists.txt#L101/L112/L126` 直接链接（另 L196 测试目标链 airy_coreloopthree）；`daemons/sched_d/CMakeLists.txt#L109` 直接链接 `airy_core` + L100-106 whole-archive 链 `airy_coreloopthree`；coreloopthree→airy_core PUBLIC 传播 `AIRY_USE_SCHEDULER_THREAD_IMPL`（sched_d L126-130 注释自证传播链）。gateway 仅 PRIVATE include 其头目录、不链库（`gateway/CMakeLists.txt#L184-192`）；notify_d 等业务 daemon 经 `airy_common + svc_common`（`daemons/common/CMakeLists.txt`），不直接触达。
- **机制未通电**：微内核统一入口 `airy_init()`（幂等，"Must be called before any other API"，`airy_rt.h`）及五原子 init（`airy_task_init`/`airy_ipc_init`/`airy_mem_init`/`airy_oom_init`/`airy_observability_init`）在 `tools/airy_cli`、`daemons/`、`gateway/` 三域**全部零生产调用**。三处刻意绕行自证：① `sched_d/CMakeLists.txt#L126-130` 显式 `-UAIRY_USE_SCHEDULER_THREAD_IMPL`，注释自述"sched_d 未初始化 corekern scheduler"；② `gateway_d/src/service.c#L12-17` 绕行改调 `airy_platform_thread_*`（避免落到无公开声明的 corekern scheduler 内部函数）；③ `tools/airy_cli` 对 `airy_task_plan_t/airy_task_node_t` 的 30 处命中全是 taskflow 数据结构消费（计划序列化/CLI DAG），任务执行走 `cli_dag_submit_remote`→sched_d 远程 DAG，**不经 corekern 调度器**。
- **定性**：与 commons/utils/ipc 的「已构建未接线」同构但层次更深——连测试外调用都没有，仅符号链接与数据结构消费。判定用词：**链接期参与、运行期旁路**。

**为什么未使用（四层原因，2026-09-10 追问取证）**：

1. **历史时序：先有生产面，后有微核心**。corekern 于 2026-03-25 以「新增内核 Lite 版」进入代码树（`git log --diff-filter=A`：`82b8fcb89`/`422e6037d`/`a18cfdab2`，同日发 v1.0.0.6 生产就绪版本）；而生产执行通路（commons 平台线程层、gateway 自有 TCP JSON-RPC、sched_d 远程 DAG）**在此之前已建成运行**。微核心从未获得"迁移窗口"——没有任何里程碑立项"把生产面迁到 corekern 调度器上"。
2. **战略定位：储备基石，非当前执行引擎**。0.1.7 规划红线「不砍 corekern/commons」（`agentrt-0.1.7-plan-registration-20260830.md#L154`）；重构建议书明确「corekern/commons 不砍反而加强——[SC] 契约 + 微核心原语 + **未来 agent-linux 跨态复用的基石**」（`研究插件项目并重构建议.md#L1209`）。corekern 被定位为面向 AirymaxOS 跨态复用的原语储备，而非 agentrt 生产面的运行载体。两套分配器并存的裁决（0.1.7 P0-5 遗留：corekern mem=微核心原语 3,687 行 / commons mem=用户态门面 4,037 行，语义不同并行保留）同证此定位。**（本项定位描述与「并行保留」裁决已于六轮复验被用户升级裁定推翻，见附记 4——corekern 不是储备，是唯一主权核心；"并行保留"改为"commons 同名域限期回归"。）**
3. **工程事实：链进去的是"符号依赖"，不是"调度器使用"**。生产二进制链 `airy_core` 的真实原因是下游符号引用（memoryrovol 引 `airy_time_monotonic_ns` 等，`50-engineering-standards/11-log-convergence-plan.md#L110`）+ coreloopthree 数据结构依赖；`AIRY_USE_SCHEDULER_THREAD_IMPL` 的 PUBLIC 传播造成"链接即传染"，各消费方以 `-U` 撤销或绕行调用防御——是"刻意保持旁路"，非遗忘。
4. **验收机制：结构性口径放行了该状态**。历轮验收检查"库在构建内/头文件在位/依赖方向"，从不检查"运行时是否跑在 corekern 上"（§7.3 P-A/P-B 模式），故"链接在、未通电"连续存活未被任何门禁捕获。

归属判据（由模型导出，四条）：

1. **内核机制 → corekern 主权**：调度、内存管理核心（arena/slab/tcache/pool/OOM）、IPC 快速通道、单调时钟源、内核同步原语。commons **不得另立第二实现**（这正是"不能迁移到 commons"的实质）。
2. **OS 差异屏蔽 + 通用轮子 → commons 合法域**：平台原语封装、路径、事件循环（epoll/kqueue/win）、日志/metrics/trace 落地格式、错误码表、通用数据结构工具。
3. **委托原则**：commons 侧凡需内核机制者，必须**调用 corekern**，不得平行自研（如平台时钟垫片应委托 corekern 时钟源，而非自带第二套实现）。
4. **依赖方向铁律**：corekern **不得依赖** commons / atoms / heapstore（裸金属前提）；允许方向是 corekern ← commons/atoms 依赖 corekern。

**一、四判据定稿（用户裁定，升格为工程铁律）**

1. **内核机制归 corekern 主权**——调度、内存管理核心、IPC 快速通道、单调时钟源、内核同步原语；commons 不得另立第二实现。
2. **OS 差异屏蔽与通用轮子归 commons**——平台原语封装、路径、事件循环、日志/metrics/trace 落地格式、错误码表、通用数据结构。
3. **commons 需内核机制者必须"委托"而非自研**——垫片可留、机制不得复制。
4. **corekern 不得依赖 commons/atoms/heapstore**（裸金属前提）；唯一合法依赖方向为 `commons/atoms → corekern`。

### 4.8 WS-8 corekern 全量启用（新增工作流；用户裁定 2026-09-10：目标为全量启用）

**目标态**：corekern 由「构建在、运行旁路」转为**全量启用**——① 依赖反转、可独立编译、具备裸金属能力；② 全部服务面运行时经 corekern 初始化并跑在其机制上；③ commons 侧不存在 corekern 内核机制的平行实现；④ IPC 四层全部通电，无摆设。

**研究新增关键发现（现网已违反既有规范，须并入本工作流）**：

1. **K-3 被违反**：daemon↔daemon 与 gateway→daemon 当前走裸 `AF_UNIX` socket + JSON-RPC 直连（`daemon_rpc_client.c:119`、`gateway_biz_forward.c:93`），而 K-3 明令"禁止守护进程之间建立直接通信通道"。
2. **S-2 规则 3 被违反**：atoms 内部模块（coreloopthree ↔ syscall ↔ taskflow ↔ memory）为直接函数调用 + PUBLIC 链接，未经 corekern IPC。这解释了 `atoms/taskflow/README.md:322` 为何声称依赖 CoreKern 调度——**设计上确应如此**（故该 README 属"目标态声明"，非纯错误，但须标注当前态）。**实证更正（2026-09-12 勘察）**：四模块实际为**零循环单向 DAG**（coreloopthree→{taskflow, memory, core}、syscall→{coreloopthree, core, memory}；taskflow/memory 为零出边叶子），非双向耦合网；跨模块消费全部经公开头单向接口，memory 面为 `airy_memory_provider_t` vtable 注入抽象（`provider.h:74-138`）——处置见 8.4.3 状态。
3. **ARC-02 被违反**：`corekern → airy_heapstore`（heapstore 属上层模块）。
4. **架构张力（已裁定 2026-09-10：dual-mode 双模）**：CROSS-01/03 要求"POSIX 线程/时间必须经 commons/platform 抽象"，与判据 4"corekern 不得依赖 commons"冲突。**裁定 dual-mode**：corekern 内部定义平台抽象接口，提供两种实现——用户态构建时 shim 实现**委托 commons/platform**（满足 CROSS-01/03）；裸金属构建时 **freestanding 实现**（不依赖标准库/commons，依据 Freestanding 模式，满足判据 4）。机制本体（调度/时钟源/同步语义）统一在 corekern，commons/platform 仅为垫片转发。执行见 8.0.3。
5. **与五句话铁律的关系澄清（防表面冲突）**：铁律「一切客户端访问走 gateway，绝对严格禁止直连 daemon/运行时库」约束的是**客户端**（TUI/CLI/SDK）；**gateway 属服务面**（协议翻译层，非客户端），其调用 `airy_init()` 并作为 `are_ipc` 一端与 daemon 通信**不构成违反铁律**——否则本工作流阶段 3.3（gateway→daemon 改经 `are_ipc`）与阶段 4.1（gateway 通电）将与铁律表面冲突。此定位须在阶段 3 之前与 WS-7 一并回写（gateway = 服务面，不是客户端）。

### 7.2 一个刺眼的纵向事实：TUI 对话链"四连故障"

1. **0.1.12 期**：TUI 普通对话走 legacy `chat_stream`，gateway 收尾帧缺失 → 第二次对话永挂（`0.1.13#L300-L313`）；
2. **0.1.13 期**：`agent.run_stream: empty result`、CLI/TUI 工具不可用（`0.1.13#L742`）；
3. **v0.1.12 stable 发布物**：为修复前 TUI（`0.1.13#L410-L415`）——**发布物 ≠ 源码树**；
4. **本轮**：中文长回复流式必崩 + 终端失能（P0-7/P0-8）。

四次的共同点：**全部发生在"对话"这条唯一的用户主路径上**，且每次都出现在"TUI 强化已闭环"的声明之后。

### 7.3 成因：四个反复出现的结构性模式

- **P-A 验收口径漂移**——用可自动化的结构指标，替代不可自动化的运行时行为。0.1.9 十八项测依赖方向/模块归位/门禁在位；M5 测"147+31 单元集成"；0.2.x §12 测平台矩阵。**六轮中没有任何一轮把"真实中文长回复对话"列入出口条件**。P0-7 因此可以在 CI 全绿的前提下上线。
- **P-B 门禁在位 ≠ 门禁强制**——9 个 quality-gate 脚本实体位于**产品仓之外**（`airymaxhub/tools/scripts/ci/quality/gates/`），agentrt 及各 leaf 仓 workflow **零接线**。0.1.13 自认「R 系列全部可绕过发布门禁」「运行时验证缺位」。
- **P-C 结构指标守恒、安全盲区守恒**——从 0.1.9 到 0.2.x，**连续六个里程碑**无任何运行时安全/健壮性门禁立项。于是同一类缺陷被稳定再生：P0-3（栈地址 free）→ S1（栈溢出）→ P0-7（切片 panic）都是"内存/边界"族，无一处被机器化门禁捕获，全部靠人工审查发现。
- **P-D 运行时验证顺延且账面无痕**——延迟执行项被写进正文叙述，遗留栏却记"无"。账面因此自我一致，断链只在实际运行时暴露。

### 7.4 机制解释：为什么这个模式能连续存续六个里程碑

因为**账面只有二元状态（闭环 / 未闭环），而"具备可执行形态"被记为闭环**。0.1.9 `L597` 是完美样本：「验收三线……**均已具备可执行形态**；对话回归需运行态 gateway，随……**批次执行**」——同句里前半句记为闭环，后半句（真正的验证）被顺延，而结论写「遗留：无」。

**更深一层的证据**：P0-7 不是"从未修过"，而是**一次修复制造的**。`mode.rs#L21-L24` 的注释写明这是「容错（**2026-08-26 修复**）」——该提交为修正"LLM 带前导文本时模式判定失败"而引入了 64 字节窗口，**因无边界用例回归而把功能缺陷换成了崩溃缺陷**。这证明：在当前机制下，**每一次点修复都在制造新的未验证面**。

> 所以 0.1.15 的关键不是"再加一批检查项"，而是给账面加上第三态：**已跑 / 未跑**（T-05），并让运行时门禁成为 required（T-04）。否则第七个里程碑仍会产出同类结论。

### 7.7 复盘结论

- 工程质量**不是全面落后**：C2'→C2e 的 CLI 瘦身（1092KB→555KB，有提交链与体积实证）、W6 构建期 fail-closed 禁链门禁、tool_d 原子写（fsync+rename）、PEP 缓存的 fail-closed 降级——这些都是**达到工业水准的样本**。
- 真正落后的是**"验证机制"本身**：能自动化的被满足，不能自动化的被记为已闭环；安全与健壮性从未进入出口条件；发布物与源码树出现过不一致。
- 因此 0.1.15 的成败判据不是"关闭了多少 P0"，而是**是否建立了"运行时行为必须被实际执行"的账面第三态**。
