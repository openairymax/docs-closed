## 附录 B：教训库（近 150 轮共识沉淀）

### B-1 workflow 半成品 commit 陷阱（2026-09-05 实证）

- **现象**：commit 541128176 声称 4 处修改，实际仅 2 处落盘（头注释 + push 固定 PLATFORMS），`inputs.platforms default` 与 `case amd64 分支` 缺失 → 所有选 amd64 的 run 落入 `*)` exit 1（run 33972726250 / 33973185771 双败）。
- **曾被误判**：dispatch 使用的 workflow 文件版本传播延迟（假设被 12min 后复现推翻）。
- **决定性排查路径**：run head_sha → `GET /commits/main` 确认远端 head → `GET /contents/<path>?ref=main` 拉远端内容 → 与本地 `git show HEAD:file` + 工作区 grep **三方比对** → 定位 commit 内容本身不完整。
- **纪律**：workflow 修改后本地 grep 断言关键分支存在；推送后 contents API 核对远端；commit 前 `git diff` 逐 hunk 自查。

### B-2 GHCR digest 钉版流程

- buildx 单平台 push 产出 **OCI index**；取 digest：`GET /v2/<name>/manifests/<tag>` 带 `Accept: application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.list.v2+json` 多类型头 → 读 `docker-content-digest` 响应头。
- release.yml 引用形态：`<tag>@sha256:<digest>`（钉版 tag 与 auto-`<run_number>` tag 分离，push 自动构建不覆盖钉版）。

### B-3 容器化腿改造固定模式（x86-64 对齐 arm-64 模板）

- host 只做 Checkout / Init submodules / Package(tar.gz) / Upload；Configure→Build→Install→TUI→finalize 全进容器。
- **finalize 必须容器内做**：host 无 `/usr/local` 自编译库，ldd 收集必 not found。
- `BUILD_DIR=/tmp/airy-build`（BAN-33 树外）；bootstrap cp 迁至 host Package 步骤。
- 容器脚本头 `set -euo pipefail`（0.1.9 教训：无它则静默失败产出空 stage）；`exec > >(tee …)` + ERR trap 回显最后 30 行。
- TUI 构建走 `build-tui.sh` SSoT（header 注入 + cargo 缺失兜底 + 失败降级不阻断）。

### B-4 环境约束

- MITM 代理环境：api.github.com 解析 127.0.0.1、TLS CA 不可信 → 所有 curl 必加 `-k`；瞬时 502 sleep 5 重试。
- 本地 remote-tracking ref 可能过期（`git status -sb` ahead 显示误导），以 `GET /commits/main` 为准。
- 验证不下早结论：run 未到目标 step 时日志缺失属正常，以 run conclusion + 产物（如 GHCR tag 出现）为准。

### B-5 发布完整性契约（D0 的历史来源）

- 门禁语义诚实：gate / experimental 分层，experimental 不阻塞 release.needs（E6），但升 gate 前必须连续绿实证（G3）。
- 正式 tag 不首跑未验证链路：两条新腿（x86-64 镜像化、arm-32 镜像化）经 rc.2 全链验证后才上 v0.1.11 正式 tag。
- 每完成一个小任务回顾大任务全部内容；系统性修复而非打补丁（0.1.11 rc.1 libcjson 修复为范例：五门禁腿全绿回归验证）。

### B-6 GitHub Actions matrix 陷阱（2026-09-05 run 10 实证）

- **job 级 `if` 不支持 matrix context**：`if: matrix.platform == …` 在 workflow 解析期直接报 `Unrecognized named-value: 'matrix'`，**run 整体 failure 且无任何 job**（不是构建失败，是解析失败）。
- 正确模式：首 step 计算 filter 写 `GITHUB_OUTPUT`，后续 step 逐一 `if: steps.<id>.outputs.<x> == 'true'`（matrix context 在 step 级 if/run 可用）。
- 附带教训：dispatch 422 与 push run 无 jobs 是同根因；"run failure 但 jobs 列表为空"先查 workflow 语法，不要往构建环境猜。
- 原生 ARM runner 补充：容器内 `uname -m` 返回宿主架构（arm64 runner 上一律 aarch64），armv7 判定必须用 `docker buildx --platform` / TARGETARCH / 编译器 `-dumpmachine`，不得用 uname。**实证升级（run #11）**：该陷阱不止影响自写探测脚本——OpenSSL `./config` 内部同样信 uname，AArch32 compat 下误选 linux-aarch64 目标启用 AArch64 汇编（`ldp x21,x22,[sp,#48]'），armv7 汇编器全量报 bad instruction。修复：tools 18f6bb3 "build: pin OpenSSL armv4 target by compiler, not uname"（arm-* dumpmachine → 显式 `perl Configure linux-armv4`，与 QEMU 路径实际所选目标一致，无行为漂移）。

### B-7 MSVC x86-32 移植雷区三件套（G3 probe-3 实证，2026-09-08）

- **ssize_t 双重 typedef**：`cmake/windows_preinclude.h` 已按 `_SSIZE_T_DEFINED` 约定以 `SSIZE_T` 定义 ssize_t 并置位宏；`commons/utils/string/string_compat.h` 又在 `#ifdef _WIN32` 下无条件 `typedef intptr_t ssize_t` → MSVC C4142（benign redefinition），x86-32 leg 被 /WX 升 C2220，**一次杀掉 57 个 TU**。纪律：任何自定义 POSIX 兼容 typedef 必须尊重平台已建立的守卫宏（`_SSIZE_T_DEFINED` 等），include 顺序任意时恰好一个定义生效。
- **size_t 32 位窄化**：`uint64_t → size_t` 隐式转换在 x64（size_t=64bit）无声放行，x86-32（size_t=32bit）触发 C4244 → /WX 升 C2220（svc_logger.h max_size → max_file_size，4 处）。纪律：64 位文件尺寸/长度字段赋给 size_t 必须显式 cast 并确认语义（Windows 侧 size 语义本为 size_t，显式 cast 即为定案）。
- **线程入口 `DWORD WINAPI` 反模式**：平台层契约 `airy_thread_func_t = void *(*)(void *)`（commons/platform/include/platform_process.h），Windows 侧由 `airy_thread_start_routine`（platform_sync.c）以 ctx 参数块适配 CreateThread 的 `__stdcall` 并管理 join/detach 状态机；daemon 直接写 `#ifdef _WIN32 static DWORD WINAPI fn(LPVOID)` 传给 `airy_thread_create`，x64 因 MSVC 忽略 __stdcall 差异侥幸编译，x86-32 必炸 C2440 硬错误（monit_d info_rpc.c、notify_d main.c）。纪律：业务层线程入口一律可移植签名；直调 CreateThread 仅允许 corekern 真原生路径（atoms/corekern/scheduler_windows.c）。
- **归因方法教训**：对 CI 错误集做 head 截断式 grep 必然误判——probe-3 曾把 svc_logger C4244（4 处）当主杀，实际主杀是 string_compat C4142（57 处），且 C2440 硬错误完全漏检。修复设计前必须先对全量 log 做错误码分类计数：`grep -oE "[a-z_/.-]+\.[ch]\([0-9]+,[0-9]+\): (error|warning) C[0-9]+" | sort | uniq -c | sort -rn`。

### B-8 同文件并行编辑竞态（工具层事故，2026-09-08 实证）

- **现象**：同一批并行调用中对**同一文件**发出两次 SearchReplace，两次各自报"成功"，但第二次以陈旧基线写回，静默覆盖第一次编辑（info_rpc.c 与 notify_d main.c 的签名编辑各被 return 编辑冲掉）。
- **检测路径**：`git diff --stat` 数量与预期不符（预期 -13/+4，实际 4+/4-）→ grep 仍见旧符号 → Read 确认终态。
- **纪律**：同文件多处编辑必须**串行**发出；每轮编辑完成后以 `git diff --stat` 对账关键文件；不同文件之间方可并行。
- **二次实证（2026-09-08，publish-mirror.sh）**：同一批 6 个并行 SearchReplace 编辑同一脚本，各报成功但快照回写互相覆盖（仅首个存活）；随后第 7 个清理编辑以陈旧基线匹配，把编辑区写成半旧半新混合文本（`...= "True"if [ -n "$REL_ID" ]; then`），`bash -n` 直接语法报错。修复：Read 终态现状 → 单次串行 SearchReplace 整段重写。教训升级：**并行编辑同一文件的破坏不止"后写覆盖先写"，还会让后续清理编辑拿到错位锚点造成语法级损坏**；同文件串行纪律无例外。

### B-9 Mach-O 依赖解析"行跳"必漏一端（exe/dylib 头结构差异，2026-09-08 G4b run13 实证）

- **现象**：bundle-macos-dylibs.sh `deps_of()` 用 `otool -L | tail -n +3` 收集依赖。该行跳只对 dylib 成立（输出第 1 行路径行 + 第 2 行 LC_ID_DYLIB）；**可执行文件（MH_EXECUTE）无 id 行，第 2 行即第一条 LC_LOAD_\* 依赖** → bin/ 每个 daemon 首位依赖漏收集、漏改写、漏 fail-closed 校验（三处同源 deps_of，全盲）。rc4-9 修复"dylib id 行误当依赖"时引入此偏移。
- **唯一崩溃点机制**：libmicrohttpd 仅被 gateway_d 首位依赖引用 → 未入包；其余 daemon 首依赖（curl/sqlite/ssl/yaml）经传递依赖入包 + install.sh DYLD 兜底在干净机可解析幸存。G4b run13 双腿 phase4 同死于 `dyld: Library not loaded: libmicrohttpd.12.dylib`（gateway_d）。
- **取证链**（区分"构建期假绿"与"发布链陈旧"）：install.sh 注释 → tools SSoT 脚本 → 构建日志 "[OK]"（假绿）→ atomgit 真包与 **GitHub 原始 artifact 同坏**（排除 asset 陈旧）→ 全 bin/ 14 daemon 各恰残留一条绝对路径、顺序=load command 首条 → 铁证。
- **修复**：deps_of 改 `otool -l` awk 枚举 LC_LOAD_DYLIB / LC_LOAD_WEAK_DYLIB / LC_LOAD_UPWARD_DYLIB（天然不含 LC_ID_DYLIB，exe/dylib 统一正确）；rpath 用 `path` 字段不动。tools `7a778a7`；mock 单测须复刻两类头结构（exe 两段头 / dylib 三段头）。
- **纪律**：行跳式文本解析隐含"文件类型固定"假设；凡解析 Mach-O/ELF 头，枚举 load commands 而非跳行。构建机/同机 smoke "可启"是弱证据（构建机 brew 在盘可兜底假绿），干净宿主/真机强核验（G4b）不可省。

### B-10 发布产物同源 sha 漂移与覆盖通道疑点（0.1.13 rc6 实证）

- **现象**：atomgit release asset sha256 `49d09956…` ≠ GitHub artifact 内层 tar.gz sha256 `f42427dc…`（同源坏包两路对证时发现）。候选 = publish 阶段重打包/重压缩，或 atomgit 附件"先删后传"覆盖残留——publish-release.sh L354-355 已有 0.1.10 实证注释："同名附件覆盖上传不可靠——upload_url 每次签发全新 OBS key，PUT 后 release 附件记录未切绑"。
- **纪律**：发布后必须做 artifact↔asset 同源 sha 断言（manifest 与安装器验签以 asset 为准，源头 sha 只作诊断）；覆盖/重发通道缺陷持续登记，随 K 组评估直传替代方案。

### B-11 release leg 并发争抢瞬时取消（rc8 windows-x86-64 实证，2026-09-08）

- **现象**：rc8（run72）`build-windows-x86-64` 开跑 1 秒即 `cancelled`（completed_at−started_at=0s、零步骤、attempt=1），同 run 的 windows-x86-32 延后 4.5 分钟才启动；同刻有 doc push 触发的 build-test windows 腿与 release 双 windows 腿争 `ci-windows-runner-bus`（cancel-in-progress:false）。rc9（run73）同配置未重现、x86-64 正常入跑 → 判定为双 workflow 同组争抢的瞬时取消态。
- **纪律**：共享 concurrency 组（cancel-in-progress:false）在双 workflow 齐发时仍可能出现"排队 job 被瞬时取消"；发布窗口应避免并发 main push（I4 docs-only 分流 + E3 限流组沿用）；该症状复现时优先查同组占用者与 runner 分配时序，勿先怀疑 workflow 语法/构建环境。

### B-12 atomgit Release 附件通道语义（rc9 publish 实证，2026-09-08）

- **探测通道**：atomgit 对匿名 HEAD 请求**一律 401**（连已成功上传的附件也被拒），HEAD 探测完全不可用；唯一可靠探测是 **GET + `Range: bytes=0-0`**——`404`=对象不存在（上传未完成）、`302`/`200`=已完成（302 跟随后返回 206）。curl 探测模板：`curl -sk -o /dev/null -w '%{http_code}' -r 0-0 -L "<asset_url>"`。
- **上传通道瓶颈**：atomgit 附件直传实测单连接限速 **15–30 KB/s**（约 32MB 的 windows-x64 zip 需 30+ 分钟）；无进度多路复用，任何一次连接重置即从零或部分续传，publish 总时长被单条慢速通道支配。U-1 看门狗（tools 5c7c194：`curl --speed-limit 1024 --speed-time 240` + `UPLOAD_RETRY=4`）语义 = "4 分钟内平均速率 <1KB/s 判死重试"，只能防死链，不能提速。
- **踩坑记录**：attempt1 两个 windows zip 连续 4 次 curl exit 18（传输中断）烧尽重试 → publish job 失败；attempt3 借助 atomgit 附件上传支持断点续传的窗口期以 15–30KB/s 缓慢补齐。**纪律**：发布窗口给 windows 大包腿预留 ≥2h 超时；探测一律 GET Range，勿信 HEAD 状态码；提速根治靠 U-2 分片直传 / U-3 主通道拓扑评估（成文于 K 组）。
- **镜像回填语义**（M13 publish-mirror.sh）：Gitee 无附件删除 API，同名附件存在即跳过+告警（不做覆盖）；GH release 资产同名同大小跳过、同名不同大小删后重传；元数据每次 PATCH 对齐；tag 前置校验 fail-closed（GH `GET /git/ref/tags/<ver>`、Gitee tags 列表断言），任一端资产缺失即聚合失败非零退出，FETCH_MISSING=1 时从 atomgit 回填缺件。

### B-14 失败取证盲区：尾部窗口被停机日志占据（rc10 G4b arm 腿实证，2026-09-08）

- **现象**：G4b run 34267790966 arm-64 腿失败，gateway_d 启动 ~2s 即优雅 shutdown（main.c:676 INFO，非 fatal ERROR 路径）；失败取证仅取 gateway_d.out 尾部 30 行，被 stop 序列（service.c:380-412）完全占据，启动期 MHD 版本对照行、HTTP start 失败 ERROR 行、shutdown 触发源全部丢失 → 根因不可定案。
- **机制**：dump_file 保尾特性（9 段 × 1100B）设计上要求核心证据殿后，但"尾部 N 行"取的是**日志尾部**而非**关键期**——优雅停机场景下停机日志量恰好挤占启动窗口。
- **修复**（主仓 82b024784，verify 脚本在主仓故免出包即可重诊）：EV 块新增 gateway_d.out 全文关键行 grep（MHD/microhttpd/HTTP gateway/ERROR/fatal/EBUSY/bind/shutting/start，head -40）+ 全文头 25 行（启动参数回显）。
- **纪律**：优雅停机型失败的取证必须"尾部 + 关键行全文检索"双通道；单一 tail 窗口在长生命周期进程上有系统性盲区——**死点证据可在日志头部（启动期窗口），非保尾窗口可达**，关键行 grep 是唯一不依赖窗口位置的手段。
