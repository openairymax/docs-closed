## 2. 阶段 F：架构遗留收敛（L9/L10）

### F1 — hall 事件流三份 writer SSoT 收敛（L9）

- **现状**：hall 事件流存在三份独立 writer 实现，语义漂移风险（0.1.11 §6 台账原样后移，触发条件"0.1.11 发布链闭环后立项"已满足）。
- **动作**：取证三 writer 的调用方与差异矩阵 → 收敛为单一 writer 模块（其余改为薄封装或删除）→ 调用方全量切换 → 防回归断言（事件 schema 契约测试）。
- **验收**：全仓仅一处事件流写入实现；三调用方 e2e 通过；schema 契约测试入 build-test 门禁。

### F2 — `AIRY_API` 双权威源收敛（L10①）

- **现状**：`AIRY_API` 存在双权威定义源，同 guard 问题（与 L10② 同族）。
- **动作**：判定单一权威源（以消费者实际解析顺序为准）→ 另一源降级为引用或删除 → guard 单头化。
- **验收**：grep 全仓仅一处权威定义；guard 校验单头；文档同步。

### F3 — gateway 同 guard 双头收敛（L10②）

- **现状**：gateway 与 F2 同族——同一 guard 语义两处定义两处校验。
- **动作**：随 F2 一并收敛（同批施工，同族问题避免两次打扰调用方）。
- **验收**：guard 单头；双头防御性重复删除后全链 e2e 绿。

## 3. 阶段 G：平台矩阵完备（D2）

### G1 — windows-x86-64 MSVC stdatomic 探针（B1.1）

- **现状**：windows leg experimental failure 不阻塞发布，硬阻塞 = atoms C11 `stdatomic`（`refcount.h` 的 `_Atomic`，MSVC C2143/C2059 级联）。rc.1 实证：windows-x86-64 continue-on-error failure（B1/B2 已知问题）。
- **动作**：两案探针（需 windows runner 实证）：① `/std:c11` + stdatomic compat 映射层；② atoms 内存域全量换 compat atomic API。按探针结果定案，B1.2 门禁绿后移除 policy 跳过置 required。
- **验收**：windows-x86-64 在 tag run 自动构建绿且 required。

### G2 — windows-x86-32 探针（B2）

- **现状**：零验证；需 MSVC x86 工具集（`-A Win32`）+ vcpkg `x86-windows` triplet；stdatomic 同源问题。
- **动作**：探针先行（工具集可用性、triplet 依赖、stdatomic 同源），不预写 leg；探针绿后建 leg 入矩阵。
- **验收**：windows-x86-32 产物可安装（install.ps1 已含分支）。

### G3 — linux-arm-32 升 gate（B3）

- **现状**：arm-32 为 experimental continue-on-error（E6 解耦，不在 release.needs）；工具链镜像化后构建时长问题已解，剩余为稳定性观测。
- **动作**：arm32 镜像接线后连续 2 个 rc run 绿 → 置 gate 入 release.needs；qemu 超时护栏沿用。
- **验收**：正式版 tag run 中 arm-32 required 且绿。

### G4 — macOS dylib 自包含收口（B5）

- **现状**：macOS 包运行时依赖本机 brew 前缀，未接 lib-package.sh 体系。
- **动作**：lib-package.sh 增 darwin 分支（otool -L 递归收集 + 系统库豁免），build-macos-* 打包接入；包内自包含校验。
- **验收**：macos-arm-64/x86-64 制品在干净 macOS 上 daemon 群可启。

### G5 — 全矩阵产物可安装核验

- **现状**：发布门禁验证"构建成功"，未逐包验证"可安装可启动"。
- **动作**：三平台安装器/更新器对全部 32/64 包做安装 → 启动 → 卸载核验；libcjson 修复（rc.1）纳入回归。
- **验收**：核验脚本入发布预检；任一包失败即发布失败。

## 4. 阶段 H：发布链纵深

### H1 — yank / 重发原子化（C4）

- `publish-release.sh --yank <tag>`（DEL 附件 + 标记 yanked + manifest 排除）；同 tag 重发自动先 DEL 再 PUT（atomgit 附件无覆盖语义，实测）。
- **验收**：yank 后更新器立即无法选中该版本；重发无残留旧附件。

### H2 — 安装/更新/运行 e2e 并入发布门禁（C5）

- 三 shell（bash/zsh/fish）安装、binary 模式启动、`airymaxrt update` 走真实 manifest 验签链、卸载清理；`latest/manifest.*.json` 与安装器快照一致性入发布预检。
- **验收**：发布 job 内一键跑通。

### H3 — atomgit → GitHub tag 镜像通道（A4 遗留）

- **现状**：v0.1.10 曾出现 tag force-move 后未自动同步（手工 REST DELETE+POST 才触发 run 33939952174）。
- **动作**：sync-mirror 对 `main` 与 `refs/tags/*` 双触发；atomgit webhook → `repository_dispatch`；失败告警 + SOP fallback 文档化。
- **验收**：atomgit 打 tag 后 GH Release run 连续 3 次自动出现。

## 5. 阶段 I：流水线效率二期（拆分细化提速主线，D0/D3）

> 用户诉求（2026-09-05）："现在的流水线实在太慢了，是否可以进行拆分、细化的方式
> 进行提速？同时要保证流水线构建、发布的完整性。" 本阶段即系统性回应：
> E1 镜像化已把最大头（qemu 重编 deps 88min）消解，二期把剩余碎片逐项拆细。

### I0 — 原生 ARM runner 全迁移（D5，**提前至 0.1.12 承接**）

- **现状**：GitHub 官方原生 ARM64 runner `ubuntu-24.04-arm` 已 GA（public repo 免费 4 vCPU，2025-08 GA）。2026-09-05 已在 build-toolchain-images.yml 完成三腿 matrix 试点改造（arm64/arm32 → ubuntu-24.04-arm，amd64 → ubuntu-latest），关键教训：**job 级 if 不支持 matrix context**（workflow 解析失败，run 10 实证），须用首 step filter 模式。
- **技术要点**：① arm64 目标本机构建（零 QEMU）；② arm32（linux/arm/v7）在 arm64 runner 上**无需 QEMU**——aarch64 内核 CONFIG_COMPAT 原生执行 AArch32 用户态（Cobalt 100 CPU 实证，社区数据 QEMU 6-8min → 原生 2min）；③ amd64 维持本机；④ 仅 riscv64 无原生 hosted runner，仍走 QEMU（0.3.x 评估，镜像/仓库名 qemu 字样暂保留）；⑤ 容器内 `uname -m` 返回宿主架构（aarch64），**架构判定必须用 Docker TARGETARCH**，不得用 uname；⑥ ubuntu:20.04 容器基线保 glibc 2.31 不变。
- **动作（0.1.12）**：release.yml 全部 Linux 腿（arm-64/arm-32/x86-32/x86-64）切原生 runner 路径；arm-32 腿加 AArch32 compat 探测（`test -x /lib/ld-linux-armhf.so.3` 类 fail-fast），探测失败回落 QEMU（稳定优先）；x86-32 无需 QEMU（x86-64 CPU 硬件兼容 i386）。
- **验收**：release 各 Linux 腿无 setup-qemu step（riscv64 除外）；arm-32 腿 ≤5min；全矩阵 rc 验证绿后上正式 tag。

### I1 — linux-x86-32 工具链镜像化（E1 收尾）

- **现状**：x86-32 腿仍逐轮 apt + 自编 deps（10.5min，386 模拟），E1 三 Dockerfile 计划中唯一未做项。
- **动作**：新增 `qemu-toolchain/x8632` Dockerfile（FROM `debian:bullseye-20240812-slim` 钉版，构建期执行 x86-32 腿一致 apt 清单 + lib-builddeps.sh）→ build-toolchain-images.yml 增 x8632 平台键 → GHCR 产出 `x8632-<date>-<bump>` 钉版镜像 → release.yml x86-32 腿切 `docker run`。
- **验收**：x86-32 腿 ≤4min；产物 sha256 与原链路一致；leg 绿。

### I2 — rustup/cargo 固化进工具链镜像（TUI 构建依赖前移）

- **现状**：arm-64/amd64 镜像化腿内仍有内联 rustup 安装 + cargo 构建（每轮下载 toolchain，见 release.yml arm-64 腿容器脚本）；x86-64 腿依赖镜像内 rustup。
- **动作**：三镜像 Dockerfile 构建期固化 rustup + stable toolchain + cargo（含目标 host triple）；腿内脚本删除 rustup 安装段，仅保留 `build-tui.sh`（SSoT：header 注入 + cargo 缺失兜底 + 失败降级）。
- **验收**：镜像化腿日志无 rustup 下载段；TUI 产物正常入 stage/bin。
- **注意**：`CARGO_TARGET_DIR` 指向容器 `/tmp`，禁止落源码树（0.1.11 教训）。

### I3 — 原生腿依赖缓存（E4）

- windows leg：vcpkg binary cache（`VCPKG_BINARY_SOURCES`），随 G1/G2 施工联动。
- linux-x86-64 / macos legs：actions/cache 缓存 apt/brew 层与 cmake 构建产物（可选，量化收益后施工）。
- **验收**：二次 run 原生腿耗时下降可量化；缓存 miss 时链路仍绿（fail-open 不阻塞）。

### I4 — 触发面瘦身（E5）

- **现状**：全量 build-test（mac/windows coverage）逐 push 跑，占用 hosted 配额（macos-15-intel 排队曾达 80min）。
- **动作**：paths 过滤分流——docs-only push 跳过重型腿（mac/windows/qemu）；release tag 与 release 分支变更才跑全矩阵；build-toolchain-images 保持 dispatch-only（push 仅 auto tag 构建，不覆盖钉版）。
- **验收**：docs-only push 不触发重型腿；全矩阵仅在发布相关变更时占用 hosted runner。

### I5 — workflow 收敛 / 复合 action（D1）

- **现状**：build-test 与 release 平台构建逻辑两处维护，0.1.10/0.1.11 多次"release 独有缺陷晚暴露"（如 rc.1 的 libcjson 缺失在 build-test 侧无覆盖）。
- **动作**：平台构建逻辑抽共享脚本或 composite action（`.github/actions/build-<plat>`），两侧同源调用；门禁依赖图（needs 拓扑）显式注释化。
- **验收**：同一平台逻辑全仓单一实现；release 侧修改不再能独立漂移。

### I6 — 发布墙钟目标与度量

- 0.1.11 出口目标（≤30min）达成情况在 rc.2 实测记录；0.2.x 目标：**正式 tag run 墙钟 ≤ 15min**（arm-32 gate 化 + x86-32 镜像化 + 原生腿缓存后）。
- 度量方式：每次 release run 记录各腿耗时入附录 A 基线表（滚动更新）。

## 附录 B：教训库（近 150 轮共识沉淀）

### B-1 workflow 半成品 commit 陷阱（2026-09-05 实证）

- **现象**：commit 541128176 声称 4 处修改，实际仅 2 处落盘（头注释 + push 固定 PLATFORMS），`inputs.platforms default` 与 `case amd64 分支` 缺失 → 所有选 amd64 的 run 落入 `*)` exit 1（run 33972726250 / 33973185771 双败）。
- **曾被误判**：dispatch 使用的 workflow 文件版本传播延迟（假设被 12min 后复现推翻）。
- **决定性排查路径**：run head_sha → `GET /commits/main` 确认远端 head → `GET /contents/<path>?ref=main` 拉远端内容 → 与本地 `git show HEAD:file` + 工作区 grep **三方比对** → 定位 commit 内容本身不完整。
- **纪律**：workflow 修改后本地 grep 断言关键分支存在；推送后 contents API 核对远端；commit 前 `git diff` 逐 hunk 自查。

### B-2 GHCR digest 钉版流程

- buildx 单平台 push 产出 **OCI index**；取 digest：`GET /v2/<name>/manifests/<tag>` 带 `Accept: application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.list.v2+json` 多类型头 → 读 `docker-content-digest` 响应头。
- release.yml 引用形态：`<tag>@sha256:<digest>`（钉版 tag 与 auto-`<run_number>` tag 分离，push 自动构建不覆盖钉版）。

### B-3 容器化腿改造固定模式（x86-64 对齐 arm-64 模板）

- host 只做 Checkout / Init submodules / Package(tar.gz) / Upload；Configure→Build→Install→TUI→finalize 全进容器。
- **finalize 必须容器内做**：host 无 `/usr/local` 自编译库，ldd 收集必 not found。
- `BUILD_DIR=/tmp/airy-build`（BAN-33 树外）；bootstrap cp 迁至 host Package 步骤。
- 容器脚本头 `set -euo pipefail`（0.1.9 教训：无它则静默失败产出空 stage）；`exec > >(tee …)` + ERR trap 回显最后 30 行。
- TUI 构建走 `build-tui.sh` SSoT（header 注入 + cargo 缺失兜底 + 失败降级不阻断）。

### B-4 环境约束

- MITM 代理环境：api.github.com 解析 127.0.0.1、TLS CA 不可信 → 所有 curl 必加 `-k`；瞬时 502 sleep 5 重试。
- 本地 remote-tracking ref 可能过期（`git status -sb` ahead 显示误导），以 `GET /commits/main` 为准。
- 验证不下早结论：run 未到目标 step 时日志缺失属正常，以 run conclusion + 产物（如 GHCR tag 出现）为准。

### B-5 发布完整性契约（D0 的历史来源）

- 门禁语义诚实：gate / experimental 分层，experimental 不阻塞 release.needs（E6），但升 gate 前必须连续绿实证（G3）。
- 正式 tag 不首跑未验证链路：两条新腿（x86-64 镜像化、arm-32 镜像化）经 rc.2 全链验证后才上 v0.1.11 正式 tag。
- 每完成一个小任务回顾大任务全部内容；系统性修复而非打补丁（0.1.11 rc.1 libcjson 修复为范例：五门禁腿全绿回归验证）。

### B-6 GitHub Actions matrix 陷阱（2026-09-05 run 10 实证）

- **job 级 `if` 不支持 matrix context**：`if: matrix.platform == …` 在 workflow 解析期直接报 `Unrecognized named-value: 'matrix'`，**run 整体 failure 且无任何 job**（不是构建失败，是解析失败）。
- 正确模式：首 step 计算 filter 写 `GITHUB_OUTPUT`，后续 step 逐一 `if: steps.<id>.outputs.<x> == 'true'`（matrix context 在 step 级 if/run 可用）。
- 附带教训：dispatch 422 与 push run 无 jobs 是同根因；"run failure 但 jobs 列表为空"先查 workflow 语法，不要往构建环境猜。
- 原生 ARM runner 补充：容器内 `uname -m` 返回宿主架构（arm64 runner 上一律 aarch64），armv7 判定必须用 `docker buildx --platform` / TARGETARCH / 编译器 `-dumpmachine`，不得用 uname。**实证升级（run #11）**：该陷阱不止影响自写探测脚本——OpenSSL `./config` 内部同样信 uname，AArch32 compat 下误选 linux-aarch64 目标启用 AArch64 汇编（`ldp x21,x22,[sp,#48]'），armv7 汇编器全量报 bad instruction。修复：tools 18f6bb3 "build: pin OpenSSL armv4 target by compiler, not uname"（arm-* dumpmachine → 显式 `perl Configure linux-armv4`，与 QEMU 路径实际所选目标一致，无行为漂移）。
