## 0. 裁定基线（不可违背）

1. 标准术语：atoms=微核心系统层、corekern=微核心、commons=统一基础库、
   daemons=用户态服务层、heapstore=运行时数据存储层、gateway=系统协议网关层。
2. 五句话铁律：TUI 渲染、CLI 组织、gateway 翻译、daemon 干活、内核机制只被
   daemon 服务面访问；TUI 是 CLI 的增强包（渲染层）；整个 agentrt 的通信都要
   使用自己的 A-IPC 设计。
3. 用户裁决（2026-09-14）：CLI 进程内 corekern **不保留例外，全量收回**；
   施工顺序 B7 → B1 → B3 → B2+B4 → B5 → B6 → B8；先设计后施工。
4. 严禁打补丁和往后续版本顺延；0.1.16 内收口。

## 3. B1 设计：payload 层落地

### 3.1 规范矛盾裁决（必须先定）

`02-ipc-protocol.md` §3 自称「payload 协议类型由 payload 体首字段携带」，
但其定义的 5 个结构体**首字段均非 type**（如 REQUEST 首字段是 request_id）。
设计裁决（回写规范时一并修正）：

- payload 线格式 = **4 字节判别头 + 结构体体**：
  `struct airy_ipc_payload { __u32 type; __u32 reserved; __u8 body[]; }`，
  `type ∈ {0x0001 REQUEST … 0x0005 CONTROL}`（`AIRY_IPC_PT_*` 宏，与规范
  §3 表格同值）；
- 规范中 5 个结构体 = `body` 段（即「体」），字段零改动，保持与文档逐字段
  同构；文档措辞由「体首字段」修正为「payload 首部判别字段」。

### 3.2 [SC] 契约层新增（commons/include/airymax/ipc.h）

只新增、不改既有布局（128B 头冻结不动）：

1. `AIRY_IPC_PT_REQUEST/RESPONSE/EVENT/STREAM/CONTROL` 五宏（0x0001–0x0005）；
2. `struct airy_ipc_payload`（8B 判别头）+ 5 个 body 结构体，字段与规范 §3.1–3.5
   完全一致（uint64_t request_id / uint32_t method_id / uint32_t timeout_ms /
   柔性数组 params 等）；
3. `AIRY_IPC_STREAM_FLAG_FIN/RST/MORE`、`AIRY_IPC_CTRL_HELLO…FLOW_ON` 常量组；
4. `_Static_assert` 锁判别头：`sizeof(airy_ipc_payload)==8`、`type @ offset 0`、
   各 body 结构体首字段 8 字节对齐。

### 3.3 L2 桥升级（daemons/common/src/daemon/daemon_l2_bridge.c）

- `daemon_l2_envelope_encode/decode` 增 type 参数：payload 前置
  `airy_ipc_payload` 判别头；**既有 JSON-RPC 文本标记为 PT_REQUEST/
  PT_RESPONSE**，线格式变更随本版本双侧同步发布（L2 为 opt-in 灰度通道、
  非默认，无存量兼容负担；overlay version 字段同步 +1 作机器判别）；
- 新增三 API（与 `daemon_l2_rpc_call` 同层）：
  - `daemon_l2_event_publish(channel, topic_id, priority, payload)` → PT_EVENT；
  - `daemon_l2_stream_open/send/close(stream_id, seq, flags, chunk)` → PT_STREAM，
    flags 映射 FIN/RST/MORE；
  - `daemon_l2_ctrl(channel, opcode, arg)` → PT_CONTROL（HELLO/PING/PONG/
    FLOW_OFF/ON 即插即用）；
- daemon 侧 `daemon_l1_server`（L1 mount）同步接受 EVENT 订阅与 STREAM 双向。

### 3.4 退出判据

- [SC] 头新增结构全部过 `_Static_assert` 与既有合规严格模式（`-Werror`、
  banned_functions）；
- 新增 ctest：L2 桥 EVENT 发布/订阅往返、STREAM 分片重组（乱序拒收/EOF/
  RST）、CONTROL PING/PONG、类型判别错误注入（未知 type 拒收）；
- 规范文档回写：判别字段措辞修正 + 「已实现」状态标注（归 B8）。

## 5. B2+B4 设计：CLI 收回与构建收口

### 5.1 B2 取证结论（本设计实测，风险重估）

CLI 对 corekern 的**运行时机制消费近乎为零**：

- `airy_loop_*`（loop 引擎）定义在 **coreloopthree 自身**（`loop/loop.c`），
  非微核心；`airy_task_plan_t` 亦为 coreloopthree 类型（`cognition.h:119`）；
- 真正的微核心机制调用仅 `airy_time_*`（无状态时钟函数，4 个符号）；
- `AIRY_CALLOC` 等 = libc malloc 包装（`alloc.c:213` AIRY_MALLOC 直通），
  无池化状态依赖；
- `airy_ipc_*`/`airy_oom_*`/`airy_persist_*` 在 coreloopthree **零函数调用**
  （31 处命中均为类型/注释）。

结论：`airy_init()` 在 CLI 内**实际只提供日志初始化与状态位**，摘除是低风险
动作；历史「地基归位」的实质需求（拿 coreloopthree/契约层头文件）已由 atoms
自身 CMake 接口目标满足，corekern include 属借道残留。

### 5.2 迁移步骤

1. `main.c`：删除 `airy_init()`/`airy_shutdown()` 调用与 `airy_rt.h`；
   启动诊断改为 gateway 连通性探测（「badge=0 降级」概念一并废除）；
2. CLI 源码 5 处 `airy_rt.h` → 换窄头（coreloopthree / `airymax/` 契约头；
   逐文件核对类型来源）；
3. `tools/airy_cli/CMakeLists.txt`：删 `airy_atoms`（:102/:113/:124）与
   corekern include（:154-158）；
4. `link-whitelist.txt:50`：`airy_cli` 行删 `airy_atoms`；
5. `main.c:176-195` 注释提及的 8.4.2 运行门禁 grep 串同步更新（搜
   「corekern core initialized」消费点）；
6. 施工时验证两处登记项：`AIRY_LOG_*` 未 airy_init 时的默认行为；CLI 全量
   ctest 回归。

### 5.3 B4 构建收口

1. 根 CMakeLists：删除 :789/:805/:833 三处 `atoms/corekern/include` 全局
   注入；改为 atoms 内部目标（corekern 库自身 + coreloopthree 经 atoms
   CMake 接口获取所需头，不暴露 corekern 头）；
2. :1032 `install(DIRECTORY … include/agentrt/corekern)` 移除（内核头不进
   发布面；agent-linux 的 uapi 走其自身发行）；
3. `link-whitelist.txt` 头注补第 2 句判据：「客户端目标禁链 airy_atoms /
   corekern；违规即为缺陷」；
4. 门禁 N 组（入 verify_release_gates.sh）：
   - N1 白名单机器断言：解析 link-whitelist 行，对每 target grep 其
     CMake `target_link_libraries`，出现白名单外库即红；
   - N2 AF_UNIX 文件白名单（§4.3）；
   - N3 CLI 零内核符号：`nm`/`strings` 扫描 airy_cli 产物不得出现
     `airy_init`/`airy_oom_*`/`airy_persist_*` 内核机制符号。

### 5.4 退出判据

- CLI 构建、链接、ctest 全绿；N1–N3 门禁全绿；
- `airy_init` 在 CLI/TUI 树内零引用（grep 门禁）；
- daemons 服务面（tool_d/sched_d 等）链 `airy_atoms` 行为不变。
