# agentrt 0.1.18 架构改进方案（TUI 渲染引擎化 · 分层解耦）

> 状态：**立项**（头号工程裁决已下，本方案为施工基准；0.1.17 收敛完成并发布后进入施工）。
> 基线：承接 agentrt `VERSION=0.1.17`；上游依据 `0.1.17-架构改进方案.md`、`0.1.17-收敛问题点.md`、`0.2.x-架构改进方案.md`。
> 范围：**TUI 渲染引擎化（对标 Ink fork 四层：DOM 模型 → 紧凑存储 → 脏区域 → 限流）+ agentrt 式更深层次分解 + markdown 能力强化 + 绘图/画板强化 + IME 提示可见化 + >800 行大文件拆分 + 六份外部工程材料的工程思想映射（§11）**。
> 编写纪律：**每项必须附一手证据（文件:行 / 命令实测）**；负面结论须双验证；验收口径落在"运行时行为"，不得以结构性指标替代。
> 立项触发：用户裁定——**「TUI 渲染引擎化」作为 0.1.18 的头号工程**；历史教训是**过度耦合导致单点故障放大为全面死机**，违背 agentrt 成为行业标准底座的目标。

## 0. 立项背景与历史教训

### 0.1 为什么是渲染引擎化

TUI 是 CLI 的**增强包**，是 CLI 的**渲染层**（五句话铁律）。它承载的是"用户对系统的全部视觉与交互感知"。渲染层一旦与数据层、协议层、业务状态机耦合，任何一处的抖动都会直接表现为**界面卡死**——而用户对"系统是否可用"的判定，几乎完全来自这一层。

社区反馈中"对话卡死 / 对话卡出系统 / TUI 不能有效渲染 markdown / 不能画图 / 输入法看不到提示"等一大批问题，表象各异，根因同源：**渲染路径是单体全帧重算，没有层次分解，没有差分，没有限流，没有故障隔离**。

### 0.2 历史教训（本项目已付出代价）

| 教训 | 表现 | 本次对策 |
|------|------|----------|
| 过度耦合 → 全面死机 | 单点渲染阻塞即造成整屏冻结，会话仍在跑但用户已无法操作 | 层间**单向依赖 + 快照传递**，渲染层故障不得回传影响核心（§3、§5 W10） |
| 补丁式收敛 → 反复回归 | 逐条修 markdown、逐条修闪烁，问题换个入口又出现 | 回到**单一模型 + 单一排版权威**（L1/L2），一次修根（§4） |
| 无差分 → 长会话必然卡 | 消息越多每帧成本越高，直到超出帧预算 | **脏区域 + 单元格缓冲**（L2/L3），每帧成本与增量成正比（§3.3） |
| 无隔离 → 演示与生产同形 | 功能"看起来在"，生产级不稳定 | **运行时行为验收**，禁止结构性指标替代（§7） |

### 0.3 对标与超越

对标 Ink fork 的四层分层：

```
Ink fork：  DOM 模型  →  紧凑存储  →  脏区域  →  限流
agentrt：   L1 视图树 →  L2 单元格缓冲 → L3 差异 → L4 帧调度
            （另加 L0 协议层 / L5 合成层 / L6 组件层，共六层）
```

agentrt 的分层**更彻底**：Ink 的 DOM 模型仍与 React 协调器共享进程内状态，agentrt 把"协议"（L0）与"合成"（L5）也各自独立成层，使**层次可独立替换、可独立测试、可独立降级**。这是"除了核心，一切都是服务"在渲染域的落地，也是"功能模块可大规模拔插而不影响核心"的落地。

## 1. 现状取证（一手证据）

### 1.1 渲染路径

| # | 事实 | 一手证据 |
|---|------|----------|
| E1 | 渲染入口为**单体全帧函数**，签名 `render(f: &mut Frame, app: &mut App)`，直接可变借用全局 App | `sdk/tui/src/ui.rs:51` |
| E2 | 主循环共 **3 处** `terminal.draw(\|f\| ui::render(f, app))`，无条件全帧重绘 | `sdk/tui/src/main.rs:445 / 651 / 846` |
| E3 | 空闲节拍固定 `Duration::from_millis(100)`，无帧预算、无合帧、无优先级 | `sdk/tui/src/main.rs:442` |
| E4 | **每条消息、每一帧**都重新调用 `crate::markdown::render(&msg.content, INDENT, width, base)`，无任何解析结果缓存 | `sdk/tui/src/panels/chat/block.rs:170` |
| E5 | 轮询节拍为硬编码常量（大厅 1000ms / 审批 1500ms），与渲染节拍无协同 | `sdk/tui/src/app/poll.rs:212 / 451` |

**E4 是性能缺陷的核心**：设可见消息 n 条、平均长度 L，则每帧解析成本为 O(n·L)，随会话增长线性上升；而实际每帧变化量通常仅 O(1) 行（流式追加的最后一个 token）。**成本与增量完全脱钩**，这是长会话"越用越卡"的直接机制。

## 2. 目标与不变量

### 2.1 目标

1. **渲染成本与增量成正比**：长会话下帧成本不随总消息数增长。
2. **层次可独立替换/测试/降级**：任一渲染层失效不导致整屏冻结。
3. **视觉一致性**：宽度权威唯一，全角/CJK/组合字符对齐无偏差。
4. **能力补齐**：markdown 覆盖日常写作全要素；绘图支持函数表达式与多曲线。
5. **交互可见**：IME 状态/候选有明确可见反馈（或明确移除并给出替代提示）。
6. **数据可读**（§11 映射新增）：上下文成本、语义缓存与语言网关状态、扩展组件注册态在用户面**可读**；数据缺失呈现为"不可用"，不得伪零。

### 2.2 不变量（不可违反）

| # | 不变量 | 理由 |
|---|--------|------|
| N1 | 渲染层**只消费不可变快照**，不得持有或修改业务状态 | 故障隔离；消除可变借用耦合（E1） |
| N2 | 渲染层**不直连协议**，一切数据经 gateway（A-IPC） | 五句话铁律：gateway 翻译，TUI 只渲染 |
| N3 | 渲染层故障**不得**阻断会话推进与 daemon 存活 | 历史教训：不全面死机 |
| N4 | 宽度权威**唯一**，禁止多处各自计算 | 对齐正确性 |
| N5 | 未核实的能力**不得**以演示形态存在 | 严禁桩实现 |
| N6 | 核心不感知渲染层存在，可整体拔插 | "除了核心，一切都是服务" |

## 3. 目标架构（六层）

```
┌───────────────────────────────────────────────────────────────────┐
│ L6 组件层      chat / board / config / events / help / memory      │
│                声明式：由数据生成视图节点，不直接画单元格           │
├───────────────────────────────────────────────────────────────────┤
│ L5 合成层      Compositor：视图树 → 后端绘制指令 → ratatui backend  │
├───────────────────────────────────────────────────────────────────┤
│ L4 调度层      Scheduler：帧预算 / 限流 / 合帧 / 优先级 / 丢弃      │
├───────────────────────────────────────────────────────────────────┤
│ L3 差异层      Diff：前帧 CellGrid vs 后帧 → DirtyRegion            │
├───────────────────────────────────────────────────────────────────┤
│ L2 排版层      Layout：视图树 → CellGrid（紧凑存储，宽度权威）      │
├───────────────────────────────────────────────────────────────────┤
│ L1 视图模型层  ViewTree：Node{kind, props, key, children}          │
├───────────────────────────────────────────────────────────────────┤
│ L0 协议层       agentrt-rs（client + run_stream）+ gateway A-IPC    │
└───────────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向：L6 → L5 → L4 → L3 → L2 → L1 → L0**。反向依赖一律禁止（L1 不得引用 L3；L2 不得引用 L6；L0 不得感知任何上层）。

### 3.1 L0 协议层（边界不变）

- 复用既有 `agentrt-rs`（`client::ClientBuilder` / `run_stream::{gen, run_stream_events}`），**不新增第三份 wire 常量**。
- 输出统一为**领域事件**（`DomainEvent`），不向上暴露 JSON 结构与字段名。
- 该层已在 0.1.17 G3 完成归一，本版**仅补**"事件 → 视图数据"的适配，不动协议。

### 3.2 L1 视图模型层（对标 Ink 的 DOM 模型）

```rust
pub enum NodeKind { Block, Row, Col, Text, Span, Table, Plot, Code, Input, List }

pub struct Node {
    pub key: Key,             // 稳定标识：差分与缓存的锚点
    pub kind: NodeKind,
    pub style: Style,
    pub children: Vec<Node>,
}

pub struct ViewTree { pub root: Node }
```

要点：

- **`key` 是稳定标识**，由数据身份派生（如 `msg.id` 或 `msg.id + 内容版本号`），**不得**用数组下标——下标会随插入错位，导致差分失效。
- 视图树**不可变**：每帧由"数据快照 → 视图树"纯函数生成（`build(snapshot) -> ViewTree`）。
- **markdown 解析结果挂在 `key` 上缓存**（解决 E4）：解析是纯函数，`(key, content_hash, width) → Vec<Node>`，命中即复用；内容不变的旧消息**永不重解析**。

### 3.3 L2 排版层（对标 Ink 的紧凑存储）

- 产出 `CellGrid`：`Vec<Cell>` 一维紧凑数组 + `width/height`，`Cell{ch, fg, bg, mods}`。
- **宽度权威唯一**：`unicode-width` 的显示宽度在**本层**统一裁决，上层不得自行截断/填充。
- 表格、绘图、换行、缩进全部在本层完成，输出**已是终端可直接消费的单元格**。
- 缓存：`CellGrid` 按 `(node.key, content_hash, width)` 缓存，与 L1 缓存键对齐。
- **驻留池**（§11 映射补入）：字符 / 样式 / 超链接三类字符串在**本层单次排版内去重**，`Cell` 仅存池索引，重复内容（长表格、高频样式）不重复占内存。

### 3.4 L3 差异层（对标 Ink 的脏区域）

- `diff(prev: &CellGrid, next: &CellGrid) -> Vec<Rect>`：逐行/逐块比对，产出最小脏矩形集合。
- 无变化 → **零绘制**（当前 E2/E3 为无条件全帧重绘）。
- 流式追加场景退化为"末行若干行脏"，成本 O(增量)。

### 3.5 L4 调度层（对标 Ink 的限流）

- **帧预算**：单帧排版+合成时间上限（超预算则降级为"仅重绘脏区中最旧的一块"，保证永不阻塞）。
- **合帧**：高频繁事件（token delta）在窗口内合并，一帧只画最终态。
- **优先级**：输入回显 > 流式输出 > 面板刷新 > 后台轮询（E5 的轮询节拍纳入统一调度，不再各自硬编码）。
- **背压**：事件队列超限时丢弃"中间态"事件，保留首尾（渲染层可丢帧，业务层不可丢事件）。
- **空闲降频**（§11 映射补入）：无输入且无待处理事件时降到低频节拍。终端无"失焦"语义，**不得**照搬外部材料的失焦降帧概念。

### 3.6 L5 合成层

- 消费 `DirtyRegion` + `CellGrid`，转换为 ratatui 绘制指令，**唯一**调用 `terminal.draw`。
- 该层是**唯一**允许触碰 ratatui 后端的层（便于后端替换，例如未来切换 alt-screen 策略）。
- **输出合并**（§11 映射补入）：相邻同属性单元格合并为一次写出，减少后端写调用次数。
- **可选硬件滚动**：后端支持时启用以减少整屏重绘；不支持则退化为普通重绘，**不作为正确性依赖**。

### 3.7 L6 组件层

- 每个面板/组件只做一件事：**`(数据快照) -> ViewTree`**。
- 组件不得直接画单元格、不得读文件、不得发请求、不得持有可变全局。

## 4. 层间契约（SSoT）

| 契约 | 生产者 → 消费者 | 形态 | 约束 |
|------|-----------------|------|------|
| `Snapshot` | L0/L6 → L1 | 不可变数据 | 只读；禁止在渲染期修改 |
| `build(snapshot) -> ViewTree` | L1 | 纯函数 | 无 IO、无锁、无时间依赖 |
| `layout(ViewTree, area) -> CellGrid` | L2 | 纯函数 | 宽度唯一裁决点 |
| `diff(&CellGrid, &CellGrid) -> Vec<Rect>` | L3 | 纯函数 | 空差异即零绘制 |
| `schedule(events) -> FramePlan` | L4 | 有状态 | 唯一节拍权威 |
| `compose(&CellGrid, Vec<Rect>)` | L5 | 副作用收敛点 | 唯一 `terminal.draw` |
| `CacheKey = (node.key, content_hash, width)` | L1/L2 | 值 | 三者任一变化才失效 |

**纯函数化是分层可测试的前提**：L1/L2/L3 全部为纯函数，可脱离终端与网络做快照测试（golden test）。

## 5. 工作包

### W1 视图模型层落地（L1）

- 引入 `Node`/`ViewTree`/`Key`；建立 `build(snapshot)` 纯函数入口。
- 建立 markdown 解析缓存（`key + content_hash + width`）：**直接消除 E4**。
- 验收：同内容消息二次渲染不触发解析（计数器实证）。

### W2 排版层落地（L2）

- `CellGrid` 紧凑存储 + 唯一宽度权威。
- 表格/换行/缩进/绘图全部下沉至本层，`ui.rs` 各 `render_*` 退化为"生成节点"。
- 验收：CJK + 全角标点 + 组合字符混排，右边界零溢出（属性测试）。

### W3 差异层落地（L3）

- `diff` 产出脏矩形；空差异零绘制。
- 验收：静态界面下连续 1000 帧的绘制次数为 0（计数实证）。

### W4 调度层落地（L4）

- 帧预算 + 合帧 + 优先级 + 背压；`poll.rs` 两处硬编码节拍并入统一调度。
- 验收：token 高频流式下 CPU 占用与帧率可配置且有上限；输入回显延迟不劣化。

### W5 组件层迁移（L6）

- 逐个迁移 `panels/*`（board/chat/config/events/help/memory）与 `ui.rs` 9 个 `render_*` 到"数据 → 节点"。
- 迁移**逐个进行、可独立回归**，不做一次性大爆炸改造。

### W6 markdown 能力强化

## 8. 风险与门禁

| 风险 | 影响 | 对策 |
|------|------|------|
| 迁移期双路径并存 | 两套渲染同时存在，状态不一致 | 逐个面板迁移，迁移即删除旧路径，不留兼容层 |
| 缓存键设计不当 | 内容更新但缓存未失效（显示陈旧） | 键含 `content_hash`；建立"内容变更必失效"用例 |
| 脏区域计算错误 | 残影/花屏 | diff 单测 + 快照回归；脏区**宁大勿漏** |
| 帧预算过紧 | 界面迟滞 | 预算可配置；降级策略优先保证输入回显 |
| 表达式求值安全 | 任意执行风险 | 受限解释器：白名单 + 步数/深度上界 |
| 拆分引入回归 | 行为漂移 | 拆分前后跑同一快照回归，**行为零差异** |

**门禁**：每层落地后必须通过该层验收项（§7）；未通过不得进入下一层。

1. **严禁在 `airymaxhub` 源码区内做任何产品编译/集成/构建**；构建产物必须在源码区外，验证后立即清理。

| 裁决 | 含义 |

agentrt 的**机制面已经很强**（见 §11.5 证据），缺的几乎全是**声明面、合并语义与成本账**。这决定了本章裁决的分布：机制类多为"已具备"，声明类多为"改造/采纳"，且绝大多数**不属于渲染域**。

### 11.8 深层思考：对 agentrt 系统架构的五条结论

1. **"机制强、声明弱"是当前架构的真实画像。** Subagents / Hooks / MCP / Plugins 都有可用机制，但都没有"可读、可版本化、可多级合并"的声明面。没有声明面，能力只能靠命令逐条调用，无法沉淀为生态，与"让更多开发者简单开发、繁荣生态"的目标直接冲突。**补声明面不增加内核复杂度**：声明面属于用户态服务层，内核不感知，符合"除了核心，一切都是服务"。

2. **SSoT 缺位是"反复回归"的结构性根因。** 同一概念出现多套命名或多套入口的实例已反复出现：记忆分层四套命名、命令面三套不一致（选项面 6 项 vs `CLI_COMMANDS` 33 项）、配置键有 schema 无消费者。**结论：任何新能力落地前，先判定"该概念是否已有权威定义"，有则改权威，不在别处另开一套。**

3. **上下文成本必须成为一等可观测指标。** agentrt 已有台账预算（`32768` / `0.8`）、语义缓存阈值（`0.85`，`daemons/mem_d/src/engine/cache.c:29`）、压缩 L1/L2、语言网关校准与路由（`atoms/coreloopthree/src/lang_gateway/calibrator.c:330`、`lang_router.c:97`），但没有把成本**归因到组件/请求级**。外部材料把归因写得很清楚：常驻类每次请求都付费、按需类仅在调用时付费、隔离类天然不占主上下文、钩子类近零成本。**这直接决定扩展组件的引入纪律**：常驻内容必须极简，重内容必须按需。

4. **"未置位的能力不得宣称"应可核验。** 本轮取证反复遇到同一形态：能力位为 0（`atoms/memory/provider.h:32-38`）、摘要 L3 明示不实现（`compress.c:8-9`）、TUI 输入法 feature 为空开关而注释仍称默认启用。**这不是实现缺陷，而是"名实一致"纪律的执行问题**。凡对外宣称的能力，必须能在用户面被调用、在运行时可观测。

5. **渲染域是"名实一致"的最终裁判。** 用户判定系统是否可用，几乎全部经由渲染层。因此 W11–W13 不是装饰性面板，而是把"能力是否真的接线"暴露到用户面：**凡是无法在界面稳定呈现的能力，就不算交付**。这也是本版对"行业标准底座"目标的直接贡献——底座的可信度，由最外层可见。
