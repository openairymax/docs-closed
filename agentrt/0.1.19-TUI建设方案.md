# 0.1.19 TUI 建设方案

> **文档定位**：`sdk/tui` **体验面**（全屏终端 UI）的详细建设方案——边界、接线契约、C 版清理、六域建设、机制设计、能力矩阵、验收。
> **底本**：`0.1.19-架构改进方案.md` §5（TUI · CLI 体验面），本文为其展开与落地细化。
> **纲领**：**机制与策略极致分离** —— 命令组织属**机制**（留守 `agentrt`），终端渲染属**体验**（迁 `sdk/tui`）。
> **一条铁律**：**TUI 只是 CLI 的渲染**（铁律 14，零业务决策）。
> **两本账**：机制账（`agentrt/` 八模块 < 100,000 行硬门禁）与体验账（`sdk/tui`，**不设总量上限**）**互不抵扣**。
> **主要读者**：Airymax 核心开发组

## §1 边界裁定：TUI 只是 CLI 的渲染

### 1.1 核心等式

```
TUI 输出 = fold(CLI 事件流)
```

**体验面唯一化是既定的，只在 `sdk/tui`。** TUI 不产生业务、不做决策，只把 CLI 事件流折叠成屏幕。

### 1.2 三条边界

| 边 | 内容 | 反例（禁止） |
|----|------|-------------|
| **纯投影** | TUI 是 CLI 事件流的**纯投影**，**零业务决策** —— 不判断、不重试、不裁剪业务 | TUI 内自行重试网络请求、自行裁决审批、自行裁剪历史 |
| **接线契约** | **CLI 父进程持除终端外的一切**（状态、会话、业务），**TUI 子进程唯一持终端**；通道 = **继承 fd 上的 JSON Lines** | TUI 子进程持有会话状态 / 业务状态 |
| **单所有者** | 同一终端同时只有一个持有者；切换须经所有权移交（`lifecycle::singleowner`） | 父子同时向终端写 |

### 1.3 命令面与渲染面的切分

| 归属 | 内容 | 落点 | 记账 |
|------|------|------|------|
| **机制**（留核） | 命令面：解析、路由、命令语义（`cmd` / `core` / `chat`）+ readline 行式 + CLI 必需头 | `agentrt/tools/airy_cli` | 机制账（留守 11,406） |
| **体验**（出走） | 全屏渲染、组件、键位、交互流、平台基建 | `sdk/tui`（Rust） | 体验账（不设上限） |

**判定路径四问**（逐项分流）：① 机制还是策略？→ ② 填哪个格？→ ③ 够格当件吗？→ ④ 经哪个面暴露？命令组织是机制故留，终端渲染是体验故走。

## §2 接线契约（0.1.17 定，本版沿用）

### 2.1 契约内容

| 项 | 约定 |
|----|------|
| **父进程（CLI）** | 持**除终端外的一切**：状态、会话、业务、审批、退出码 |
| **子进程（TUI）** | **唯一持终端**；只渲染、只收键位，不持业务状态 |
| **通道** | **继承 fd 上的 JSON Lines**（不是新开 socket、不是 RPC） |
| **所有权** | 同一终端同一时刻单所有者；切换经 `lifecycle::singleowner` 显式移交 |
| **退出码** | 只由 CLI 父进程产生（`exit::StatusTable` 冻结表），TUI 不产退出码 |

### 2.2 数据流

```
CLI 父进程                         TUI 子进程
  │                                  │
  │  ── JSON Lines（继承 fd）──────▶  │  事件流 event[]
  │                                  │      │
  │                                  │      ▼
  │                                  │  fold(events) → 屏
  │  ◀──── 键位 / 交互上行 ──────────  │  （零业务决策）
  │                                  │
  │  业务决策、状态、审批、退出码       │  纯投影
```

### 2.3 与「组合件承载」的关系

TUI 侧不引入独立业务逻辑；事件流消费属**体验面内部**的组合（渲染引擎 + markdown + 组件库 + 交互流），仍遵守「组合一律经组合件承载，禁薄胶水串联」——`sdk/tui` 内部每个渲染管线是有实体、有测试的组合件，不是散落 `if` 串联。

### 4.2 渲染引擎化目录树

```

├── engine/{block, layout, term}.rs
```

**引擎化三原则**（承接 ZCode 分层）：引擎管 cell diff / 布局，业务只投事件；「帧后慢初始化」「引用不变不重绘」「viewportCulling」三招直接采用；断点常量进 `budget.rs`。

**四行 id 模板**即 minimax id 模板表（§8.2）在 `agentrt` 语境的子集；`sdk/tui` 沿用「upsert + 强制保留 `createdAtMs` + 乐观同 id join」。

## §5 关键机制设计

### 5.1 渲染：单时钟 + 幂等 cell

| 机制 | 设计 |
|------|------|
| **单时钟** | 全屏只有一个时钟源驱动投影，避免多源竞态 |
| **cell 幂等** | 稳定字符串 id 为唯一键 upsert，重复投影幂等合并；渲染缓存 key = `cell:{id}`，签名不变整行复用 |
| **revision CAS 门闩** | 每类交互一个单调 revision + `expectedRevision`；迟到快照天然被丢弃，防「旧快照覆盖新事件」 |
| **渲染拉模型** | 事件回调里 `updateChrome(snapshot)` + `requestRender()`，store 不驱动像素 |
| **引用不变 = 不重绘** | 语义无变化返回原引用，跳过重绘 |
| **帧界合并** | delta 累积 → 一次落库；帧率闸 16ms 节流；用户输入可抢占立即渲染 |

### 5.2 交互流九机制

| # | 机制 | 内容 |
|---|------|------|
| 1 | 三道闸 2048 | 队列 / 缓存有界（2048 上限） |
| 2 | 终态防回退 | 已终态 cell 不接受倒退更新 |
| 3 | delta 帧界合并 | 文本 delta 累积合并，帧界一次落库 |
| 4 | 守卫共享 `streamProjected` | 流式投影标记共享，防双写 |
| 5 | 乐观 join | `optimistic:user:{request_id}` 占位，真实 turn 落地后原地改同 id cell 归并；失败撤销 |
| 6 | 审批队列化 | 审批请求入队串行处理 |
| 7 | epoch 自愈 | 连接代际 `generation+1` → 每 session 重放 `runtime/reconcileSession` |
| 8 | 并发闸 `KeyedSerialExecutor` | per-key 串行、跨 key 并发；准入预算有界；reset 断链自愈 |
| 9 | 多 agent 面板防环 4 段 | `STATUS_PRIORITY` + 深度钳位 32，防渲染环 |

### 5.3 预算常量 `budget.rs`（全部有界）

`budget.rs` 集中 **27 项常量**（布局、帧、缓存上限），**全部有界**。继承 minimax「**预算即常量、裁剪记 `originalBytes`**」语义，27 项为本工程集中整理（目标态；现状散布约 12 文件实测 37 项）。

**常量分域（承接 minimax 形态）**：

| 域 | 代表常量 |
|----|---------|
| 渲染 / 帧 | `MIN_RENDER_INTERVAL_MS = 16`、`MAX_RENDER_WRITE_CHARS = 1MiB`、`THINKING_PREVIEW_MAX_CHARS = 2,000` |
| 投影窗口 | `maxInitialTurns = 30`、`maxCellsPerTurn = 120`、`maxProjectedTurns = 60`、`maxProjectedCells = 1,000` |
| 缓存 | `WIDTH_CACHE_SIZE = 512`、`MAX_OSC52_ENCODED_LENGTH = 100,000`、`MAX_DEDUPE_KEYS = 256` |
| 队列 / 历史 | `RETAINED_TURNS_LIMIT = 8`、`MAX_CLOSED_QUESTIONNAIRE_IDS = 128`、`MAX_PARENT_DEPTH = 32`、`CHILD_HISTORY_LIMIT = 200` |
| 输入 / 输出 | `MAX_OUTPUT_CHARACTERS = 64KiB`、`MAX_TOOL_TEXT_BYTES = 64KiB`、`DOUBLE_ESCAPE_WINDOW_MS = 500`、`DEFAULT_LIVE_PUBLISH_INTERVAL_MS = 250` |

**裁剪语义**：超 `MAX_TOOL_TEXT_BYTES` 时**保留头尾各半 + 中间插 `\n… [truncated: N bytes total] …\n`**，UTF-8 按字节安全截断，并记 `originalBytes` 供后续增量合并前缀对齐。展示值钳位（如 `TUI_AGENT_COUNT_MAX = 9,999`）。

## §6 能力矩阵与可用性整改

### 6.1 能力矩阵（定目标，不定行数）

| 条 | 内容 |
|----|------|
| **矩阵无空格** | 能力矩阵（对标 Claude TUI）**不留空格**，有空格即补 |
| **对标 golden** | **≥ 100 条** Claude 对标 golden |
| **质量门照常** | ≤ 800 行/文件、复杂度、golden 全绿 |

> **不设总量上限的含义**：**矩阵完整性优先于行数**。若补空格需要 110k 行，就写 110k 行；**禁止为「压体积」而删体验**。行数只作为**结果预期**（100k ~ 135k）用于对照世界级实现是否合理。
>
> **世界级参照系**：`notcurses` ≈ 60k、`tmux` ≈ 75k、`ncurses` ≈ 180k——说明「丰富」需要多少代码是合理的。

### 6.3 借鉴判据五条

只取机制，不搬框架：

1. 只搬**机制**，不搬框架；
2. 策略**数据化**；
3. **一切有界**（缓存、队列、重试皆有上限）；
4. **fail-closed 优先**（不确定就拒绝）；
5. **诊断不顶替原始错误**（原始错误必须可追溯）。

## §8 三参考项目机制对标

> **取证源码位置**：`works-engineering/.engineer-reference/user-reference/{ZCode-main, minimax-code-main, deepseek-harness-master}`。每条给出「参考项目实际做法 → 我们的等价落地」。

### 8.1 ZCode（OpenTUI + React 19，~13,350 行）

**① 帧驱动渲染器 + reconciler 双层**

ZCode 用 `createCliRenderer({targetFps: 30, useMouse: true, ...})` 创建帧驱动渲染器，再 `createRoot(renderer)` 把组件树投影到布局树；渲染循环、flexbox 布局、cell 级增量重绘都归引擎。

- **首帧即生命周期钩子**：慢初始化挂到首个 `FRAME` 事件之后（"No runtime work can block the first paint"）。
- **引用不变 = 不重绘**：reducer 语义无变化返回原引用。
- **滚动视口裁剪**：`viewportCulling: true`。
- **响应式断点**：`SIDEBAR_WIDTH = 42`、`SIDEBAR_AUTO_VISIBLE_BREAKPOINT = 120` 列；diff 120 列切 split/unified。
- **CJK 双宽测量**：逐码点判 2 列。

→ **落地**：`engine/{block,layout,term}.rs` 三件承接同一分层；三招直接采用；断点常量进 `budget.rs`。

**② shiki 进终端：token 化 → 富文本段**

用 `shiki.codeToTokens` 拿 token 的 `color/fontStyle/content`，逐段映射为 `TextChunk{fg,bg,attributes}`，色深量化交给引擎；三层缓存 + 超时降级（`withTimeout(..., 2_500)`）；属性位映射 `BOLD=1 / ITALIC=4 / UNDERLINE=8 / STRIKETHROUGH=128`；双引擎分工（代码块走 shiki，markdown 正文走内置 `SyntaxStyle.fromTheme`）；消费端 `cacheKey` 校验丢弃过期结果。

→ **落地**：`sdk/tui/markdown` 四能力沿用「高亮产物 = 富文本段、`theme\0lang\0content` 语义 key、超时降级纯色」三原则；主题 token 20 语义色 × 13 tone 承接其语义 token 划分。

**③ 三模式降级 + 能力探测源优先级链**

- **Markdown 三模式**：`markdown → code → plain`，按运行时组件能力探测。
- **主题探测源优先级链**：用户 preference → `renderer.themeMode` → `waitForThemeMode(250ms)`（OSC 明暗查询）→ `getPalette({size:16, timeout:350ms})`（亮度公式 `(299R+587G+114B)/1000 > 128 → light`）→ 默认 dark。**每级带超时、失败返回 null、探测与首帧并发**，晚到结果经事件热更新主题。
- **剪贴板双通道**：先 OSC 52，失败退平台原生命令链（darwin `pbcopy`；linux `wl-copy → xclip → xsel`；win32 powershell）。
- **TTY 判定**：非 TTY 拒进 TUI。

→ **落地**：`airy/tui::downgrade`（三模式）+ 平台基建八条的「探测三源分级」「色深决策链」「OSC52 上限」「通知方法表」逐一对应；`inline + alt-screen 双渲染器可回滚切换` 承接其「探测并发、晚到热修、随时回滚」形态。

**④ 键位路由优先级链**：单一 `useKeyboard` 回调内做优先级链（release 丢弃 → 只读子代理视图 → 审批弹窗 → 选择弹窗 → 侧栏 → 双击 Ctrl+C 守卫 → Ctrl-Y 复制 → Shift-Tab 模式切换 → 补全链 → Esc 逐层关闭），每层 `consumeKey(key)` 标记消费。→ 我们的 `KeyRoute` 级联数据表 + 双击 Ctrl+C guard + 两段式 leader 的直接来源。

### 8.2 minimax-code（TypeScript）

**① TuiStateStore：Redux 极简单向数据流**

`dispatch(action)` → 纯函数 `reduceTuiState` → `{state, effects}`，副作用由 `TuiEffectRunner` 串行消化。状态含 `connection{phase, generation}`、`TuiSessionViewState{execution 四 Map、四个 revision 计数、closedQuestionnaireIds}`。**revision CAS 门闩**：`if (session.runRevision !== action.expectedRunRevision) return session;`——迟到快照天然被丢弃。渲染拉模型：flow 事件回调里 `updateChrome(snapshot)` + `requestRender()`。

→ **落地**：`airy/tui::monoclock`——全屏由单一时钟驱动投影，状态单源 + 每类交互一个单调 revision + `expectedRevision` 门闩，原样采用。

**② cell id 幂等**

以稳定字符串 id 为唯一键 upsert（`orderedIds + cells Map`），渲染缓存 key = `cell:{id}`。**id 模板（`kind:turnId[:业务键]` 三段式）**：

| id 模板 | 证据 |
|---------|------|
| `tool:${turnId}:${toolCall.id ?? name:index}` | `turn-tool-projection.ts:137-139` |
| `optimistic:user:${requestId}` | `turn-projection.ts:95,108,118` |
| `assistant:${turnId}[:${n}]` / `thinking:${turnId}[:${n}]` | `turn-live-projection.ts:378-381`、`turn-live-state.ts:72-76` |
| `user:${turnId}` / `history:user:${messageId}` | `app.ts:390`、`turn-user-projection.ts:40` |
| `permission:${requestId}` / `terminal-error:${turnId}:${seq}` | `interaction-flow.ts:320`、`runtime-event-flow.ts:893` |

- **幂等 upsert**：已存在则 `mergeCell`（强制 `id`/`createdAtMs` 不被覆盖），不存在才入序。
- **乐观 join 回真实**：`optimistic:user:{requestId}` 占位，真实 turn 落地后**原地改同 id cell 的 turnId** 归并，失败撤销——乐观与真实**共享同一存储原语**，无需双列表对账。
- **渲染签名优先 per-cell revision**（O(1)），未命中才序列化字段。

→ **落地**：`airy/tui::cellid` 四行 id 即此表子集；`sdk/tui` 沿用「upsert + 强制保留 `createdAtMs` + 乐观同 id join」。

**③ 预算常量：「预算即常量、常量即边界」**

实测**不存在**集中 27 项模块；真实形态 = 显式预算模块 `tool-payload-budget.ts` + 各文件头 `const` 上限（100+ 个）。核心常量见 §5.3。**裁剪语义**：超 `MAX_TOOL_TEXT_BYTES` 时保留头尾各半 + 中间插截断标记，UTF-8 按字节安全截断，记 `originalBytes`。

→ **落地**：`airy/tui::budget`——`budget.rs` 集中常量，**全部有界**；截断记 `originalBytes`、保留头尾、展示值钳位三招照搬。

**④ KeyedSerialExecutor**

按 key 维护 **promise 尾链**实现 per-key 串行、跨 key 并发：

```ts
const previous = tails.get(key);
tails.set(key, current);
try { await previous; return await task(controller.signal); }
finally { release(); if (tails.get(key) === current) tails.delete(key); }
```

- **准入闸有界**：`detached ≤2/键、≤32 总；admitted ≤64/键、≤256 总`，超限抛 `requestCancelled`——**队列本身有界**。
- **取消不等于泄漏**：abort 时 detach 幽灵续跑 + 计数钳制，`reset` 断链自愈。
- 四个执行器按操作类别隔离 key 冲突域。

→ **落地**：`airy/ipc::concurrency-gate` 落 **agentrt ipc 侧**（跨 daemon 并发闸），形态 = 尾链串行 + 准入预算 + reset 断链三件套。

**⑤ 帧界合并与 epoch 自愈**：delta 合帧（累积 → 一次落库）+ 帧率闸（`requestRender` 16ms 节流，用户输入 `requestImmediateRender` 抢占）；epoch 自愈 = 连接代际 `generation+1` → 每 session 重放 + 交互 revision CAS。→ 九机制「delta 帧界合并 / epoch 自愈 / 审批队列化 / 多 agent 面板防环 4 段」（`STATUS_PRIORITY` + 深度钳位 32）逐一对应。

### 8.3 deepseek-harness（TypeScript）

**① Capability Folding（能力折叠）**：工具按 scope 链影子叠加 + 掩码交集求可见目录；展示模式为 `code` 时整个目录折叠为单个 `run_code` 传输层，模型直调其他工具**确定性拒绝**。**关键纪律**：折叠调用在**策略管线之前**终止——审批永不对必败调用表态。展开时 `run_code` 子派发带 `parent` token 旁路折叠，逐子调用落事件可重建。**fold 两段式**：先纯校验生成 `SurfacePlan`，再 `applySurfacePlan` 原子提交；增量与全量重放共享同一转移函数。

→ **落地**：`airy/cli::twogate`（双闸校验）承接「折叠/展开共用同一谓词 + 必败调用在策略前终结」；策略注入单通道与 capability seam（Service/Provider/Consumer 三角色）同构。

**② 审批 fold fail-closed**：`ApprovalPolicy = 'ask' | 'never'` 二值闭联集；**`'never'` 在派发任何 answerer 之前由服务自身裁决为 `'rejected'`**（不用 listener 做 gate——注册顺序可绕过）。全路径 fail-closed 收敛：无 answerer / 抛错 / 返回越界值 / 无 agent / 无审批服务，一律 `'unavailable'` 或 deny。未知策略双重点卡（setter 抛 `TypeError` + schema 校验）。审计对 fold 进事件流（`approval/asked` → `decide()` → `approval/decided`，要求 turn 内闭合）。失败可区分（`'rejected'`=人说不、`'unavailable'`=渠道坏），但出口只有拒绝。

→ **落地**：`airy/approval::failclosed` 的 `Policy::Never → 确定性 Rejected`；`airy/exit::StatusTable` 穷尽枚举承接 `assertNever` 纪律。

**③ 一切有界 + headless settle 落账**：上限断言在契约边界（`assertBudget(value)` 构造时 loud fail；并发 `maxParallelSubCalls` 默认 10，非正整数即抛）；锁重试 `20ms → 200ms 指数退避 / 2s 总超时`，到期抛错而非猜测；超时→结构化落账（`TOOL_TIMEOUT`）；**headless settle**：`whenIdle()` 等静默 → `sessions.flush()` 落盘屏障 → **从已落盘事件区间折叠**出输出与退出码（`turn/end completed → 0，否则 1`）——**退出码只从落盘账本派生**，与输出不可能分叉；**中断即补账**：崩溃恢复不删历史，追加确定性合成事件补齐开放边界，时间戳复用最后事件，**永不伪造未来时间**。

→ **落地**：`airy/cli::headless`（超时仍 settle 落账）；`budget.rs` 全部有界；错误码表（`TOOL_TIMEOUT` 等结构化码 + `assertNever`）进 `StatusTable`。

**④ 单一真相源事件流（`fold(events)` 的理论根）**：`Session.log` append-only，`seq = log.length` 全局连续；`surfaceOp` 标记决定事件进不进模型可见面；**运行时断言「模型可见 ⟺ 已记录」**。→ 我们的 `TUI 输出 = fold(CLI 事件流)` 等式与「`streamProjected` 标记防双写」同源。
