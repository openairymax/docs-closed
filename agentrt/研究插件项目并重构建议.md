# 一、总体定位：Qoder 插件生态的两个来源

- `qoder-bundler/`：官方随 IDE/CLI 打包的**内置插件**（security-scan、computer-use、qoder-create-plugin、better-harness）。manifest 同时存在两份：仓库根 `plugin.json`（发布用，带 `marketplaceName`/`defaultEnabled`）与 `.qoder-plugin/plugin.json`（运行时清单）。security-scan 还以 npm 包 `@ali/security-scan` 发布（`package.json` 的 `files` 字段精确控制打包内容）。
- `qoder-marketplace/`：从市场拉取缓存的**第三方/官方 skill 包**（superpowers、redis-development、qmind-knowledge-cn）。结构更接近"skill 目录 + 可选 hooks/rules"，多数只有 `.qoder-plugin/plugin.json`。

# 二、逐插件调研

## 1. security-scan（qoder-bundler，v0.8.1）

**定位**：Qoder 安全审查插件。三档能力：L1 编辑时正则模式告警（PostToolUse hook 触发）、L2 轻量 diff 审查、L3 深度 commit-range 审查（push/PR/merge 前隐式 gate）。所有逻辑都在一个自举下载的跨平台 `qodersec` 二进制中。

**目录结构**：
```
security-scan/
  plugin.json                  # 发布 manifest（= .qoder-plugin/plugin.json + marketplaceName/defaultEnabled）
  package.json                 # npm 包元数据（@ali/security-scan，postinstall 脚本）
  .qoder-plugin/
    plugin.json                # 运行时清单：hooks/skills 声明
    qoder-hooks.json           # SessionStart + PostToolUse hook 配置
  bin/                         # qodersec-launch.cmd/.sh、bootstrap.sh/.cmd、security-scan-settings.sh/.cmd
  skills/security-scan/SKILL.md
  scripts/postinstall.sh
  config.yaml.example / security-patterns.yaml.example
  README.md / assets/logo.svg
```

**核心机制要点**：
- **运行时清单**（`.qoder-plugin/plugin.json`）：`name/version/displayName/description/author/license/logo/keywords/category/tags` + `"hooks": "./.qoder-plugin/qoder-hooks.json"` + `"skills": ["./skills/security-scan"]`。
- **Hooks 配置**（`qoder-hooks.json`）：三层生命周期：
  - `SessionStart`：执行 `"${QODER_PLUGIN_ROOT}/bin/qodersec-launch.cmd" ensure-deps --hook-event SessionStart`，`timeout: 120`（会话启动时确保依赖已装）。
  - `PostToolUse`：`matcher: "Edit|Write|MultiEdit|NotebookEdit"`，命令 `.../qodersec-launch.cmd review --platform=qoder`（编辑后实时告警）。
  - `Stop`：空数组（占位）。
  - 关键设计：hook 命令通过 **`${QODER_PLUGIN_ROOT}` 占位符**定位插件根，由运行时注入。
- **Launcher/Bootstrap 分层**（`bin/qodersec-launch.sh`）：launcher 负责导出 `QODER_PLUGIN_ROOT`、钉扎 CLI 版本（`QODERSEC_CLI_VERSION_GLOBAL=0.8.0` 等环境变量）、比对已装版本、版本不符时调 `bootstrap.sh` 下载（curl/wget → OSS 签名端点 → 解包改名 `qodersec` → 写 `qodersec-version.json`）；用 `CODESEC_REVIEW_SUBPROCESS=1` 防止 SDK 内层 qodercli 递归触发 hooks。config 种子策略：按插件版本 marker（`.config-version`）决定是否把 `config.yaml.example` 复制为 `~/.qodersec/config.yaml`。
- **Settings 解析隔离**（`bin/security-scan-settings.sh` → `qodersec review settings --platform=qoder --format=json`）：SKILL.md 规定只能消费 JSON 字段 `status/host/l2_enabled/l3_enabled`，`true` 才启用，fail-closed；禁止 agent 直接读 `settings.json`/`app-config.json` 或自行解析。
- **SKILL.md（路由式 workflow）**：这是最值得研究的部分——不是"步骤清单"，而是**带状态的意图路由决策树**：
  - 6 条显式路由优先级（全仓扫描→指定路径→显式 L2→显式 L3→裸 `/security-scan` 用固定三选 picker→隐式 push/PR/merge handoff gate）。
  - 强制工具调用契约：必须用 `AskUserQuestion`（`question` 字段非空、选项顺序固定），禁止文本模拟。
  - 状态机：`AWAITING_REMEDIATION_DECISION`（先展示全部 findings 再问修不修）→ `POST_FIX_HALT`（修完必须停，等待新用户消息）→ `SCAN_SKIPPED_FOR_CURRENT_HANDOFF`（内存态，新 commit 清除）。
  - 静默执行原则：不暴露 qodersec 命令、stdout、JSON、内部路由；唯一可透出的 notice 是 `qoder_credits_exhausted`（白名单）。
  - 资源门：扫描超时 1800s、10,000 行规模上限（超限直接告知，不重试不拆分）；禁止 `git add && commit && push` 合并命令（绕过 scan gate）。

**借鉴价值**：hooks 与 skill 双通道配合（hook 做确定性实时检查、skill 做 agentic 审查）、意图路由+固定 picker+隐式 gate 三层触发、工具调用强约束、fail-closed 配置、自举下载二进制 + 版本钉扎 + 防递归注入。

## 2. computer-use（qoder-bundler，v1.0.1）

**定位**：通过 Qoder Computer Use 控制 Windows 桌面应用（UI Automation 状态 + 截图）。**纯 MCP 插件，无 hooks、无脚本逻辑**——能力全部由 MCP server 暴露。

**目录结构**：
```
computer-use/
  .qoder-plugin/plugin.json
  .mcp.json                       # MCP server 声明（STDIO）
  bin/computer-use-client-launcher.cmd
  skills/computer-use/SKILL.md
```

**核心机制要点**：
- **清单**（`.qoder-plugin/plugin.json`）：`"mcpServers": "./.mcp.json"` + `"skills": "./skills/"`；亮点是 **`interface` 对象**（marketplace UI 元数据：`displayName/shortDescription/longDescription/developerName/category/capabilities/defaultPrompt/brandColor/screenshots`，`defaultPrompt` 是给用户看的示例 prompt 列表）。
- **MCP 集成方式**（`.mcp.json`）：STDIO 协议——`command: "./bin/computer-use-client-launcher.cmd"`、`args: []`、`cwd: "."`、`env_vars: ["QODER_HOME"]`（声明需要透传的环境变量）。
- **Launcher**（`bin/*.cmd`）：解析 `QODER_HOME`（默认 `%USERPROFILE%\.qoder-cn`），在共享运行时目录 `bin/qoder-cn-computer-use/QoderComputerUse.exe`（含 1.0.1 legacy 路径回退）中定位客户端，设置 `QODER_CUA_LOG_MODE=ide` 等环境变量后 exec。即：**MCP server 的可执行体由宿主共享运行时提供，插件只做定位与包装**。
- **SKILL.md**：极简（约 8 行），只写行为原则：先 `get_app_state` 再行动、优先 element-index 动作、UI Automation 不全才用截图、有专用 API/CLI 时优先。

**借鉴价值**：MCP 作为插件能力面的"一等公民"（`mcpServers` 直接进 manifest）；MCP server 通过 launcher 复用宿主共享运行时并声明 `env_vars` 白名单；`interface` 元数据支撑市场展示与 defaultPrompt。

## 3. qoder-create-plugin（qoder-bundler，v0.1.0）

**定位**：元插件（"造插件的插件"）。把 GitHub SKILL.md、本地 SKILL.md、市场 skill URL、skills.sh、粘贴内容、已有插件目录转换为可分发 Qoder 原生插件。`visibility: "hidden"`（对用户不可见）。

**目录结构**：
```
qoder-create-plugin/
  plugin.json                       # 极简：name/version/description/marketplaceName/defaultEnabled/visibility
  skills/create-plugin/
    SKILL.md                        # 转换工作流
    scripts/validate_qoder_plugin.py  # 离线校验器
    references/
      qoder-plugin-manifest.md      # manifest 规范
      qoder-components.md           # 组件打包规则
      validation-and-packaging.md   # 校验与打包
      source-resolution.md          # 输入解析
```

**核心机制要点**（这是"插件格式规范"的一手权威来源）：
- **最小 manifest 模板**：`name/displayName/version/description/descriptionZh/author/homepage/repository/logo/keywords/category/tags/skills`；按需追加 `rules/agents/commands/hooks/mcpServers`。
- **路径规则**：组件路径必须以 `./` 开头、不得含 `..`、不得绝对路径；JSON 组件路径以 `.json` 结尾；命令源必须是 `.md`。
- **命名规范**：插件目录名与 `plugin.json.name` 必须一致，kebab-case；中文源保留中文展示文本但技术标识用 kebab-case。
- **Skill 拆分策略**：单一工作流=单 skill（即使带 scripts/references/hooks/rules）；仅当多个独立可调用工作流或内部 helper 才拆多 skill。
- **组件打包规则**（`qoder-components.md`）：
  - Skills：frontmatter 推荐 `name/version/description/description_zh/user-invocable/argument-hint`。
  - Agents：`agents/*.md`，frontmatter 含 `name/description/tools/model/skills/mcpServers`（子代理角色，不转成 skill）。
  - Rules：项目标准/文件级约束注入，`rules/` 目录；Qoder 规则存 `.qoder/rules`，100,000 字符上限，自然语言，优先级高于 `AGENTS.md`。
  - Hooks：`hooks/hooks.json` + `hooks/<script>.sh`；**hook 脚本 stdin 收 JSON、退出码语义：`0` 允许/继续、`2` 阻止（blockable 事件）、其他=非阻塞错误**。
  - MCP：`mcp.json` + 有凭据时配 `CONNECTORS.md`；STDIO 本地命令 / SSE / Streamable HTTP 远程；凭据用 `<YOUR_TOKEN>` 占位 + 文档化。
- **离线校验器**（`validate_qoder_plugin.py`）：纯 Python、不依赖 qodercli；检查清单存在/JSON 合法/`name`+`version` 必填/组件路径不越界且真实存在/每个 SKILL.md 有 `name`+`description` frontmatter/命令是 md/MCP JSON 含 server 定义/zip 根直接含 `.qoder-plugin/plugin.json`/禁止 `.codex-plugin`/`.cursor-plugin`/`.claude-plugin` 与本地运行时状态（`settings.local.json`、`__MACOSX`、`.DS_Store`）。
- **打包**：zip 根必须直接含 `.qoder-plugin/plugin.json`；`qodercli plugin validate/install` 仅作兼容性证据，非质量门。

**借鉴价值**：一套可机器校验的插件规范（manifest 字段白名单、路径规则、frontmatter 必填项、禁止清单）+ 离线 validator 先行、运行时 smoke 后置的分级验证策略；"skill 目录=单一可调用单元，其余组件为可选附件"的极简心智模型。

## 4. redis-development（qoder-marketplace，redis/1.0.0）

**定位**：Redis 官方的 AI Agent 最佳实践知识包——**规则库型 skill**。29 条规则 × 11 个类别，按影响度分级，专为 LLM/agent 生成与重构代码时遵循而写。

**目录结构**：
```
redis-development/
  SKILL.md                  # 入口索引：类别-优先级表 + 规则清单
  metadata.json             # version/organization/date/abstract/references
  AGENTS.md                 # 编译产物（全部规则展开的完整文档，约 2200 行）
  README.md                 # 维护说明（npm run build 生成 AGENTS.md）
  rules/                    # 单规则文件（29 个）+ 3 个元文件
    _template.md            # 新规则模板
    _sections.md            # 类别元数据（前缀→标题/影响/描述）
    _contributing.md        # 写作规范（被排除出构建）
    data-*.md, ram-*.md, conn-*.md, json-*.md, rqe-*.md,
    vector-*.md, semantic-cache-*.md, stream-*.md, cluster-*.md,
    security-*.md, observe-*.md
  assets/logo.png
```

**核心机制要点**：
- **规则文件组织**：**文件名前缀即类别路由**（`data-`/`ram-`/`rqe-`/`vector-`…），`_sections.md` 定义前缀→标题/影响/描述映射，SKILL.md 按优先级排序索引。规则 frontmatter：`title/impact/impactDescription(带量化)/tags/description/alwaysApply`。
- **规则模板**（`_template.md`）：统一结构 = 问题说明 + **Correct 示例（先给）** + 二选一模式（Pattern A "Incorrect"：反模式有害时；Pattern B "When to use / When NOT needed"：可选特性时）+ 参考链接。`_contributing.md` 强调：具体模式而非抽象建议（"用 SCAN 替代 KEYS *"而非"设计高效查询"）、量化影响（10x/50%）、多语言可运行示例（python/javascript/bash）、语义化命名、注释解释 why。
- **多形态输出**：同一内容三形态——`rules/` 单文件（细粒度注入）、`SKILL.md`（索引 + 速查）、`AGENTS.md`（编译全量文档）。SKILL.md 头部声明"29 rules across 11 categories, prioritized by impact to guide automated optimization and code generation"。
- **metadata.json**：版本/组织/摘要/官方文档引用，供市场与检索使用。

**借鉴价值**："规则即代码"治理管线：规则模板化 → 前缀自动归类 → 编译聚合 → 多入口消费（索引/速查/全量）；frontmatter 携带 impact 量化信息供 agent 排序；Correct-first + 反模式对照的写作规范。

## 5. qmind-knowledge-cn（qoder-marketplace，0.2.0）

**定位**：QMind 知识库工具集（RAG 问答、Notebook 管理、批量上传、知识编译/质量检查），限定 Qoder CN 公有云生产环境。**"CLI 即服务"型 skill**：不捆绑二进制，首用自动下载缓存。

**目录结构**：
```
qmind-knowledge-cn/0.2.0/
  .qoder-plugin/plugin.json
  README.md                 # 中文功能简介
  assets/icon.png
  skills/qmind-knowledge/SKILL.md   # 约 414 行完整手册
```

**核心机制要点**：
- **清单**：标准字段 + `category: "Coding"`、`tags`、`logo`、`skills: "./skills/"`。
- **CLI 自举模式**：SKILL.md 内嵌下载脚本（`uname`/`$ARCH` 探测 → `~/.cache/qmind/bin/qmind-<os>-<arch>` 固定缓存路径 → OSS URL 下载 → chmod）；Windows PowerShell 版本并行给出；`qmind_cn self-update` 自升级。**每次 shell 必须重新定义 runner 函数**（带 `QMIND_DASHBOARD_URL`/`QMIND_SASH_URL` 环境变量）。
- **环境隔离硬规则**：只认 `qoder.com.cn`/`openapi.qoder.com.cn`；禁止 `QMIND_ENV=prod`、禁止 `-sash`/`-dashboard` 显式覆盖、检测到 VPC/Global 环境必须停；登录凭证 `~/.qmind/credentials.json` 禁止 cat。
- **幂等性表**：每个操作一行（upload-folder 幂等、notebook create 不幂等需先 list、compile start 无幂等键消费 token 不可重放、delete 幂等 404）——**用表格把"哪步可重试、哪步不可重放"编码给 agent**。
- **异步长任务契约**：`compile start` 的返回被定义为 `accepted/rejected/uncertain` 三态，`uncertain` 必须保留证据并停止（POST 无幂等键绝不自动重放）；`compile watch -timeout 30m -poll 3s` 本地超时≠远程取消；退出码 0/1/2/3 语义化。
- **Agent Workflows 章节**：8 个端到端流程（上传文件夹、RAG 问答、知识库初始化、编译、lint、检索、单文件上传、文件管理），每个都带前置条件与"必须用户确认"标记。

**借鉴价值**：把外部 CLI 的"不可重放性/幂等性/环境约束/凭证安全"显式建模成 agent 可查表；能力探测触发一次性升级（`compile help` 里没有 `compile start` 才 self-update）；异步任务的证据保留与停止规则。

## 6. superpowers（qoder-marketplace，5.1.0）

**定位**：方法论 skill 库（上游 obra/superpowers，作者 Jesse Vincent）。14 个组合式 skill 强制"探需求→设计→拆任务→TDD→评审→合并"流程。Qoder 包装版把原 Claude Code 插件适配成 Qoder 插件。

**目录结构**：
```
superpowers/5.1.0/
  .qoder-plugin/plugin.json    # 运行时清单（skills + hooks）
  README.md / README-original.md
  qoder.md                     # 项目级 AI 指令（原 CLAUDE.md 适配；含对 agent 贡献者的强约束）
  LICENSE / assets/app-icon.png
  hooks/
    hooks.json                 # SessionStart hook 注册
    run-hook.cmd               # 跨平台 polyglot 分发器
    session-start              # 无扩展名 hook 脚本（上下文注入）
  skills/                      # 14 个 skill 目录（各含 SKILL.md，部分带 references/、scripts/）
    using-superpowers/ brainstorming/ writing-plans/ executing-plans/
    subagent-driven-development/ dispatching-parallel-agents/
    test-driven-development/ systematic-debugging/
    requesting-code-review/ receiving-code-review/
    verification-before-completion/ using-git-worktrees/
    finishing-a-development-branch/ writing-skills/
  scripts/sync-to-codex-plugin.sh, bump-version.sh
```

**核心机制要点**：
- **清单**：`skills: "./skills/"` + `hooks: "./hooks/hooks.json"`；含 `descriptionZh`（中文描述）。
- **Hooks 机制**（hooks.json）：`SessionStart` 事件、`matcher: "startup|clear|compact"`、`type: "command"`、`async: false`，命令 `"${QODER_PLUGIN_ROOT}/hooks/run-hook.cmd" session-start`。
- **跨平台 hook 分发**（`run-hook.cmd`）：**polyglot 脚本**——cmd 段用 `: << 'CMDBLOCK'` 包裹 bash 段；Windows 走 batch（找 Git for Windows bash → PATH bash → 找不到静默退出），Unix 走 bash 直接 exec；hook 脚本故意用无扩展名文件名（`session-start`），避免 Claude Code 的 `.sh` 自动前缀干扰。
- **上下文注入协议**（`hooks/session-start`）：读取 `skills/using-superpowers/SKILL.md` 全文 → bash 参数替换做 JSON 转义 → 输出 JSON。**跨平台输出格式分派**：`CURSOR_PLUGIN_ROOT` 存在→`additional_context`；`CLAUDE_PLUGIN_ROOT` 且非 Copilot→`hookSpecificOutput.additionalContext`（含 `hookEventName`）；否则→顶层 `additionalContext`。即：同一 hook 脚本适配 Cursor/Claude Code/Copilot 三种消费协议。legacy skills 目录存在时注入 `<important-reminder>` 警告。
- **强制 skill 调用哲学**（`using-superpowers/SKILL.md`）："1% 可能适用就必须调用 Skill 工具"；优先级：用户显式指令 > superpowers skills > 默认系统提示；子代理跳过（`<SUBAGENT-STOP>` 标记）；skill 通过描述触发（`description: "Use when starting any conversation..."`）。

# 三、机制横向总结（对 agentrt 直接可复用的规范）

**1. 插件清单格式**（两处权威：create-plugin 的 manifest 文档 + 实际插件）
- 双 manifest：发布 manifest（根 `plugin.json`，含 `marketplaceName`/`defaultEnabled`/`visibility`）与运行时清单（`.qoder-plugin/plugin.json`，被运行时消费）。
- 字段全集：`name/version/displayName/description/descriptionZh/author{name,email}/homepage/repository/license/logo/keywords/category/tags/skills/hooks/mcpServers/rules/agents/commands/interface{displayName,shortDescription,longDescription,developerName,category,capabilities,defaultPrompt,brandColor,screenshots}/marketplaceName/defaultEnabled/preserveUpstreamMetadata`。
- 组件路径规则：`./` 开头、无 `..`、非绝对、JSON 组件以 `.json` 结尾、命令源为 `.md`；声明必须对应真实文件。
- 打包规则：npm `files` 白名单；zip 根必须直接含 `.qoder-plugin/plugin.json`；禁止 `.codex-plugin`/`.cursor-plugin`/`.claude-plugin` 与本地运行时状态。

**2. Skill 格式规范**
- 目录约定：`skills/<skill-name>/SKILL.md`，单目录=单可调用单元；支持 `references/`（证据/指南）、`scripts/`（辅助脚本）、`assets/`。
- frontmatter：必填 `name`（与目录一致）+ `description`（承担语义触发路由，"Use when..."）；可选 `version/description_zh/user-invocable/argument-hint/license/metadata`。
- description 是触发入口（superpowers 的"1% 可能就调用"规则依赖它），内容才是行为规范；触发条件、安全约束、引用文件关系必须保留。

**3. Hooks 机制**
- 声明：`hooks: "./hooks/hooks.json"`，结构 `{"hooks": {"<Event>": [{"matcher": "...", "hooks": [{"type": "command", "command": "...", "timeout": N, "async": bool}]}]}}`。
- 事件：`SessionStart`（matcher `startup|clear|compact`）、`PostToolUse`（matcher `Edit|Write|MultiEdit|NotebookEdit`）、`Stop`（也可注册 `Bash` 等，见 security-scan 设计注释）。
- 协议：脚本 stdin 收 JSON；退出码 `0` 放行、`2` 阻止（blockable 事件）、其他=非阻塞错误；hook stdout 可输出 JSON（`additionalContext` 注入上下文）；`${QODER_PLUGIN_ROOT}` 占位符由运行时注入插件根路径。
- 多平台：polyglot `.cmd`（内嵌 bash 段）或"cmd 委托 bash"；无扩展名 hook 文件名规避 `.sh` 自动前缀；找不到 bash 时静默降级。

**4. MCP 集成方式**
- `mcp.json`/`.mcp.json`：`{"mcpServers": {"<name>": {"command": "...", "args": [], "cwd": ".", "env_vars": [...]}}}`；STDIO 本地 / SSE / Streamable HTTP 远程；manifest `mcpServers` 字段声明；凭据禁止入库，用占位符 + `CONNECTORS.md`。

**5. 规则文件组织**（redis 范式）
- 单规则文件：`<prefix>-<desc>.md`，frontmatter（`title/impact/impactDescription(量化)/tags/description/alwaysApply`），正文 Correct-first + Incorrect/When-to-use 二选一。
- 元文件：`_sections.md`（前缀→类别映射）、`_template.md`（模板）、`_contributing.md`（写作规范，排除出构建）。
- 多形态输出：rules/（细粒度）→ SKILL.md（索引）→ AGENTS.md（编译全量）；Qoder 规则另存 `.qoder/rules`，100,000 字符上限，优先级高于 AGENTS.md。

**6. 脚本/工具集成方式**
- bin/ 跨平台 launcher + bootstrap（下载二进制、版本钉扎 env、`QODER_PLUGIN_ROOT`/`QODERSEC_HOME` 注入、防子进程递归）。
- npm 生命周期：`postinstall`（chmod +x）、`prepublishOnly`、`files` 白名单。
- CLI 机器契约：`--json/--no-color/--quiet/--no-input/--dry-run/--yes`；stdout parser-safe；argv 数组分发；命令按 `workflow/advanced/maintainer` 分类。
- 自包含 bundle：vendored wasm 运行时，zip 解压即用。

**7. AI Agent 工作流设计**
- 意图路由优先（security-scan 的 6 级路由 + 固定 picker + 隐式 gate）。
- 显式状态机 + 强制工具调用（`AskUserQuestion` 必须真调用、`POST_FIX_HALT` 必须停）。
- 静默执行 + 结果只读白名单（不向模型暴露内部命令/日志；唯一透出 notice 白名单化）。
- 证据-评分脱钩（better-harness 七态证据 + ceiling 表）；finding 契约（一问题一 check、最小修复、验证路由）。
- 三条独立证据通道并行 + brief 隔离；intervention ledger 跨 session 学习连续性。
- 幂等/重放安全表（qmind：哪步可重试哪步不可重放）；异步任务证据保留与停止规则。
- 上下文注入（superpowers SessionStart 注入 skill 引导全文，替代改 system prompt）。

## A. 整体架构模型

### A.1 一句话概括

### A.3 Cordis 插件框架核心模型（vendor/cordis/src/）

Cordis 是 dsh 的地基，其核心概念（vendor/cordis/README.md、docs/cordis-primer.md）：

**1. Context（上下文 = 依赖容器）**——`vendor/cordis/src/context.ts`
- `new Context()` 创建根容器，内置四个服务：`reflect`（反射层）、`registry`（插件注册）、`events`（事件总线）、`logger`（日志）。
- Context 实例是 **Proxy**：普通属性读取走服务解析器（reflect.ts 的 `ProxyHandler`），`ctx.tools`、`ctx.llm`、`ctx.sessions` 这类服务键即服务定位符——插件通过**键**找服务，而不是 import 具体实现。
- 三个派生子上下文原语：
  - `extend(meta)`：原型继承的子上下文；
  - `isolate(name, label?)`：**服务作用域隔离**——为某服务名建立独立作用域标签，子域可提供不同实现而不影响父域；
  - `intercept(name, config)`：**配置拦截**——在子上下文下挂载的服务收到合并后的拦截配置（Service 的 `[symbols.resolveConfig]` 实现祖先前缀合并，fiber.ts 在创建时把 inject 的 intercept 配置写入子上下文）。

**2. Service（服务基类）**——`vendor/cordis/src/service.ts`
- `class Foo extends Service`，构造函数调 `super(ctx, 'foo')` 即通过 `ctx.reflect.provide(name, self, check)` 注册，随 fiber 卸载自动注销。
- 静态 symbol 钩子：`Service.init`（构造后运行的方法）、`Service.check`（可用性谓词，依赖方加载前咨询）、`Service.invoke`（可调用服务体）、`Service.extend`（派生扩展实例）、`Service.config`（phantom 配置类型参数）。
- 每个服务的拦截配置通过 `[symbols.resolveConfig]` 从祖先链合并。

**3. Fiber（插件生命周期单元）**——`vendor/cordis/src/fiber.ts`
- `ctx.plugin(plugin, config)` 启动插件返回 Fiber；Fiber 状态机：`PENDING → LOADING → ACTIVE → FAILED / UNLOADING → DISPOSED`。
- **inject 依赖等待**：Fiber 维护 `_store`（已解析依赖快照）与 `epoch`；`_refresh()` 检查所有注入服务是否可用（`_checkImpl` 逐个验证，含 `impl.check` 谓词），全部就绪才 `_reload()` 执行插件回调；任一依赖消失则 `_unload()`。**加载顺序由服务依赖声明决定，而非手工启动排序**（cordis-primer.md "Five Ideas" 第 3 条）。
- **注册即效应**：`ctx.effect(execute, label)` 立即执行并收集 disposer；fiber 卸载时按注册逆序执行所有 disposer；支持同步/异步/生成器效应。所有 `ctx.on()`、`ctx.provide()`、`ctx.mixin()` 都是 effect 的包装——**卸载必然撤销注册**，这是 HMR 与热重载安全的基础。
- 配置验证：`resolveConfig()` 用 standard-schema 验证（`ValidationError`）；`internal/config` waterfall 可在激活后再解析原始配置（vendor 本地修改 15 条"lazy config resolution"）。
- `update(config)` / `restart()`：支持配置热更新，先走 `internal/update` waterfall（监听者可以否决或替换重启）。

**4. Registry（插件注册表）**——`vendor/cordis/src/registry.ts`
- 三种插件形态：`Plugin.Function`（`(ctx, config)`）、`Plugin.Constructor`（类）、`Plugin.Object`（`{ apply(ctx, config) }`）。
- 共享元数据：`name`、`Config`（standard-schema 校验器）、`inject`（依赖声明，数组或 `{name: interceptConfig}` 映射）、`provide`（提供的服务名）、`intercept`。
- `@Inject(name, config?)` 装饰器：类级（合并进静态 inject）与方法级（延迟到依赖可用再调用）。

**5. Reflect（反射/服务解析层）**——`vendor/cordis/src/reflect.ts`
- `ctx.provide/get/set/accessor/mixin` 都在这层；`store` 按隔离标签（symbol）存实现记录 `Impl {name, fiber, value, check}`。
- `notify(names)` 在服务注册/注销时唤醒所有依赖该服务的 fiber（`_checkImpl` + `_refresh`），构成**响应式依赖图**。
- `mixin` 把服务方法混入 ctx（如 `ctx.on` 转发到 `ctx.events.on`）。

**6. Events（事件总线）**——`vendor/cordis/src/events.ts`、docs/cordis-primer.md
- **五种分发模式**（`DispatchMode`）：
  - `emit`：同步、不等待、无返回值——观察者；
  - `waterfall`：同步、洋葱中间件（listener 收 `(...args, next)`，调 `next()` 委托，不调则短路）——**拦截/策略/包装**，返回替换值；
  - `parallel`：并行 await 全部 listener；
  - `serial`：顺序 await 直到某 listener 返回 bail 值；
  - `bail`：同步顺序直到第一个 bail 值（非 null/false/undefined）。
- **类型化事件**：通过 TypeScript **declaration merging** 扩展 `interface Events` 声明事件名与签名（`'app/ready'(message: string): void`），事件 JSDoc 用 `@mode` 标注分发模式，生成目录校验声明与分发点一致。
- 内置框架事件：`internal/plugin`、`internal/status`、`internal/config`（waterfall）、`internal/update`（waterfall）、`internal/get`/`internal/set`（waterfall 拦截上下文属性读写）、`internal/listener`（bail 拦截监听注册）、`internal/dispatch`（事件分发诊断）。
- **上下文过滤**：`EventOptions.global` 与 `Context.filter` 让事件可按作用域过滤分发（dsh 的 `dsh-scope` 在此基础上做 per-agent 事件路由，见 `tools/execute` 等事件的 `Scoped<ToolRuntime>` 签名）。

**7. Loader（配置驱动加载）**——`@deepseek-ai/cordis-plugin-loader` + `-include`
- `cordis.yml` 是**插件行（entry）列表**：`- id: <唯一id> / name: <插件包名> / config: {...} / disabled: ...`（见 examples/acp-agent/cordis.yml 等真实文件）。
- `!!js` YAML 方言在 `config` 与 `disabled` 字段求值为 JS 表达式（如 `cwd: !!js process.cwd()`），其他元数据保持字面量；条件组合用 overlay 而非表达式（AGENTS.md:96）。
- Patch 层机制：profile（命名组合，按序叠 bundle）→ `cordis.patch.yml` → `--patch` overlay；patch 按 id 替换整行 config 或插入新行（architecture.md:15-37）。
- Loader 的本地修改（vendor/README.md 第 8、11、12、14、15 条）全部围绕**事务性配置重载**：先导入新名再处置旧实现、失败回滚、Include 子树串行化变更、EACCES 重试等——这是"插件系统可靠性"的工程样板。

## C. 能力缝隙（Capability Seams）概念与设计

定义（docs/architecture.md:98-102、docs/capability-seams.md、docs/glossary.md）：**seam = 可替换能力，由三个角色组成**：

1. **Service Definition**：声明接口的包（如 `packages/shell/shell` 声明 `ctx.shell`）；
2. **Service Provider**：实现该接口的包（`bash-local`、`bash-sandbox`、`pwsh-local` 注册进 `ctx.shell`）；
3. **Consumer**：使用该接口的包，通常是对模型开放的工具（`tool-bash`、`tool-pwsh` 消费 `ctx.shell`）。

规则：
- **一个 seam 必须三角色齐全**；仅一个角色不是 seam（AGENTS.md:109）；角色独立演化时才拆分。
- **Consumer 只依赖 Service Definition，绝不依赖具体 Provider**（packages/README.md:67：扩展插件依赖 Service Definition；`agent-loop` 可替换，UI/hook/tool 插件只用 `dsh-agent`）。
- **Provider 可整族替换**：filesystem 与 subprocess provider 共享一个执行世界，把它们指向远程沙箱（E2B），Bash/PTY/LSP 一起迁移，Consumer 零改动（capability-seams.md 表格中 `ctx.fs` 的 providers：fs-local/fs-sandbox/fs-e2b）。
- **事件门（event gate）**作为正交策略：`fs-observation-policy` 不改变 schema，而是监听 `fs/write-intent`、`fs/edit-intent`、`fs/observed` 事件实现"先读后写"策略（capability-seams.md:409 "svc_fs -. event gate .-> fs_observation_policy"）。
- 完整性守卫：`scripts/gen-doc-graphs.ts` 从 Cordis 声明发现服务，把 interface/implementation/consumer 角色分类，带 completeness guard，生成 capability-seams.md 的完整表（56 个 seam/core/bundle 服务：`ctx.attachments`、`ctx.llm`、`ctx.sessionPersistence`、`ctx.settings`、`ctx.credentials`、`ctx.shell`、`ctx.sandbox`、`ctx.fs`、`ctx.subagents`、`ctx.jobs`、`ctx.web`、`ctx.lsp`、`ctx.spillStore` 等，每行标注 Role/Owner/Implementations/Direct consumers/Note）。

典型 seam 示例（capability-seams.md:461）：
- `ctx.sessions`（core）：session 包所有，append-only Session 实例 + 持久事件流；
- `ctx.sessionPersistence`（seam）：session-persistence 定义，jsonl/sqlite 两后端，"Backends persist the same SessionEvent vocabulary; apps choose a backend at composition time"；
- `ctx.subagents`（seam）：subagent 定义，spawn-in-process/fork-in-process/acp/codex/claude-code/dsh-sdk 六个 provider，tool-subagent/tool-subagent-control/tool-ralph 消费；
- `ctx.agentLoop`（bundle）：唯一具体 loop 插件，扩展包依赖 dsh-agent 事件与服务而非它。

## D. Agent 生命周期与事件生产-消费模型

### D.1 Turn/Step 生命周期（docs/agent-lifecycle.md、architecture.md:63-90）

```
turn/start
  claim 下一轮输入 + 一条排队 prompt（agent/inbox/spliced, agent/inbox/claimed）
  agent/pre-step            # waterfall：权威决策 reject | enter(messages)
  step/start
  user/message*             # 进入步骤的消息
  system-prompt/assemble    # waterfall：prompt 段 + 工具 schema 组装
  agent/request             # waterfall：构建请求
  llm/stream                # waterfall：模型流
  assistant/chunk* → assistant/message
  tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  step/end
  （还有未决工具或新输入 → 再 claim → 下一步）
  agent/turn-stopping       # serial：turn 停止前的检查点（hooks 桥在此拦截）
turn/end
```

语义要点：
- **step = 一次模型请求 + 它调用的工具**；**turn = 零或多步**，开启于首输入被认领前，关闭于无所欠。
- `agent/pre-step` 返回 `{kind:'reject'} | {kind:'enter'; messages}`，是**权威决策**；被拒或空首 claim 仍关闭一个消耗零步的持久 turn（日志记录尝试本身）。
- 事件三分域（architecture.md:53-61）：
  - **Session events**：持久事实，追加进日志并经 `session/event` 广播（`turn/*`、`step/*`、`user/message`、`assistant/*`、`tool/*`、`todo/write`、`compaction/*` 等）——必须能跨重载存活；
  - **Agent events**（`agent/*`）：携带活体 Agent 的协调事件——inbox、status、request、error、turn-stopping；
  - **Capability events**：挂策略/适配器到 seam（`fs/*`、`tools/*`、`telemetry/*`），不 import loop。
- **模型可见 ⟺ 已记录**（AGENTS.md:107、architecture.md:96）：任何到达模型请求的内容必须能从 session 日志重建；新的模型可见输入 = 需要新 session 事件。`deriveMessages()` 从日志投影模型历史；原始 `assistant/chunk` 保留重放与 UI 保真。

### D.2 事件生产-消费矩阵（docs/event-producer-consumer.md）

生成式表格：每行 = 事件名 / 分发模式 / 声明处 / Dispatcher 包 / Listener 包。示例：
- `agent/pre-step`（waterfall）：agent-loop 分发，13 个 listener 包（agent-instructions、compaction-basic、hooks-claude-code、hooks-codex、plan-mode、repeat-tool-reminder、time-context 等）；
- `tools/pre-execute`/`tools/execute`/`tools/post-execute`（waterfall）：tools 分发，hooks 桥、timeout-policy、spill-policy 等监听；
- `session/event`（emit）：session 分发，约 24 个 listener 包；
- `llm/stream`（waterfall）：llm 分发，agent-loop、llm-replay、session-title 等监听。

### D.3 Agent 生命周期与驱动

- `Agent` 接口（packages/core/agent/src/runtime-types.ts）：`id/session/inbox/status/ctx` + `cancel/whenIdle/runMaintenance/send/followup/inject`；`AgentStatus = 'idle' | 'running'`，每次迁移发 `agent/status`。
- `ctx.agents` 是核心服务（`AgentRegistry extends Service`，index.ts:256），代理创建走 `setFactory` 注册的工厂（agent-loop 实现 `AgentFactory.createAgent/resume`）。
- **作用域世界**：`AgentRegistry.create` 先铸造未发布的 `agentCtx`，await `setup(agentCtx)` 完成 agent 局部世界装配（局部工具、prompt 段、listener、restrict），全部注册存在于 `session/created`/`agent/created`/`agent/session-start` 发布之前；失败则整体回滚不发布任一 id（index.ts:118-133 "setup composes, it never drives"）。
- 子 agent：`ctx.subagents`（seam）+ 6 个 provider；`subagent/start`/`subagent/end`/`subagent/descriptor`（持久描述符）事件；tool-subagent 选择一次性或可续委托，tool-subagent-control 投递后续消息。

## F. 与 Qoder 插件体系（skills/hooks/mcpServers 组件模型）的本质差异

> 说明：工作区内未找到 Qoder 本地参考文档，以下对比基于用户给出的描述（Qoder = skills/hooks/mcpServers 组件模型）与 dsh 已核实的事实。

| 维度 | Qoder 组件模型（用户描述） | DeepSeek Harness（已核实） |
|---|---|---|
| 插件本质 | **声明式组件清单**：skills 目录、hooks 配置、mcpServers 配置，由 IDE 宿主加载消费 | **编程式插件**：JS/TS 函数/类/对象，运行在共享 Context 中，通过服务键互操作 |
| 组合方式 | 宿主按固定目录/配置文件约定收集 | `cordis.yml` 有序 entry 列表 + patch 分层叠放，每行可配可禁 |
| 依赖管理 | 宿主隐式提供能力（skill 可用即可用） | **显式 `inject` 依赖声明**，插件等到所有依赖服务就绪才激活，加载顺序由依赖图决定 |
| 生命周期 | 组件被宿主挂载/卸载，缺乏统一状态机 | **Fiber 状态机**（PENDING/LOADING/ACTIVE/FAILED/UNLOADING/DISPOSED）+ 效应可逆（注册必返回 disposer，卸载自动撤销）+ HMR |
| 扩展点 | 宿主定义的一组固定 hook 点 | **类型化事件 + 五种分发模式**（emit/waterfall/parallel/serial/bail），事件声明走 declaration merging，可被任何插件扩展 |
| 作用域 | 全局或按项目 | **三级作用域**：context 继承（extend）、服务隔离（isolate）、per-agent 作用域（agent.ctx） |
| 服务注入 | 宿主注入固定能力集 | **服务定位 + 依赖注入**：`ctx.<key>` 代理解析，Provider 可整族替换（seam 三元角色） |
| 类型安全 | 配置即契约，弱类型 | 强类型：declaration merging 扩展 Context/Events；Typert 类型图跨进程生成 RPC 契约 |
| 插件间通信 | 无（组件各自为政） | 事件总线 + 服务调用双通道（"Prefer events for interception and policy; prefer service methods for direct capability calls"——cordis-primer.md:42） |

**本质差异**：Qoder 是"**宿主 + 声明式组件**"模型——插件是宿主消费的资源描述（skill 文本、hook 命令、MCP server 端点），宿主是唯一执行者；dsh 是"**运行时 + 编程式插件**"模型——插件是运行时的第一公民，宿主（harness）本身就是一个插件（agent-loop），没有特权核心，所有能力（含工具注册表、模型适配器、会话日志）都是可替换的插件，且插件可以**修改自己的运行时**（self-modification 包、tool-cordis 动态挂载/卸载插件）。在 dsh 中，一个"skill"（`ctx.skills` seam）也只是"提供 skill 内容的 provider"（skill-filesystem 等）之上的注册表，模型通过 `skill` 工具消费；hooks（hooks-claude-code/hooks-codex 包）是把 Claude Code/Codex 的 hook 协议桥接为 `agent/*`、`tools/*` 事件的 listener 插件，不是宿主固有机制。

## G. 对 agentrt（AirymaxRT：daemon + ecosystem 五叶仓 manager/prompts/markets/skills/agents + plugin_d/market_d/hook_d/agent_d）的插件模块设计借鉴清单

> 说明：工作区内未找到 agentrt/AirymaxRT 的代码或文档，以下基于用户给出的架构描述做对照分析。

### G.1 真可借鉴（架构性、可直接迁移的设计模式）

1. **Capability Seam 三元角色（定义/Provider/Consumer）**——把 plugin_d/market_d 的每个能力拆成"接口声明包 + 实现包 + 消费包"。收益：一个 Provider 换整族能力（如 dsh 的 fs/subprocess 共享执行世界，指向远程沙箱全家迁移）；Consumer（工具）永远只依赖接口。**建议 market_d 的每个 market 按此三件套组织。**
2. **"注册即效应"的 disposer 纪律**——所有注册（工具、hook、prompt 段、服务）必须返回 disposer 并挂在插件生命周期上；插件卸载/HMR 时逆序自动撤销。这是 dsh 插件体系热重载安全性的根本，直接解决"插件卸载残留"这一 plugin_d 的经典难题。
3. **inject 依赖声明替代手工启动排序**——manager 加载插件时按服务依赖解析顺序自动排序（dsh 的 Fiber 等到依赖就绪才激活）。五叶仓里 prompts/markets/skills/agents 的相互依赖可以全部用声明解决，消灭启动脚本里的顺序魔法。
4. **显式生命周期状态机**——PENDING→LOADING→ACTIVE→FAILED→UNLOADING→DISPOSED 六个状态 + `internal/status` 状态迁移事件。hook_d 的每个 hook 执行器、agent_d 的每个 agent 会话都值得一个这样的状态机（可观测、可诊断、可等待 quiescence）。
5. **事件分发模式区分（waterfall 做中间件）**——hook_d 完全可复用：观察用 emit、策略/拦截用 waterfall（listener 收 next，不调即短路）、顺序表决用 serial/bail。dsh 的 `agent/pre-step`、`tools/pre-execute/execute/post-execute` 是现成范式：策略即 listener，而非硬编码在 loop 里。
6. **"模型可见 ⟺ 已记录"**——prompts 仓的每一次注入（文件变更通知、skill 内容、上下文）都应是持久化事件，可重放重建；"新增模型可见输入 = 新增日志事件"这一不变量对 agentrt 的审计/回放/恢复极有价值。
7. **scope 隔离原语**——agent_d 的子 agent 必须有独立作用域（dsh 的 `agent.ctx` + `isolate`）：子 agent 的局部工具/prompt/策略注册不污染父域，销毁即撤销；agent 创建采用"先装配后发布、失败整体回滚"的事务性发布（dsh `AgentRegistry.create` 的 setup-commit 模式）。
8. **配置驱动 + 失败即大声**——部署差异全走配置（cordis.yml/patch），插件内禁硬编码可调参数；配置错误在加载时大声失败，绝不静默跳过缺失引用。plugin_d 的配置校验可直接用 schemastery 模式（standard-schema 校验器挂插件声明上）。
9. **生成式目录作为文档门控**——tool-catalog/persistence-catalog 的"boot 插件读真实 schema" + freshness 校验模式，可迁移为 agentrt 的 market/skill 目录自动生成与漂移检测。
10. **类型化事件（declaration merging）**——事件名/签名/`@mode` 作为类型声明一部分，跨包 merge-extensible；生成目录校验声明与分发点一致。对 plugin_d 的多包协作是低成本高收益的约束。

### G.2 伪可借鉴 / 不可借鉴（dsh 特定选择，不应照搬）

1. **Vendoring 整个 Cordis 框架**（vendor/ 策略）——dsh 因"完全拥有框架层、可审计可打补丁"而 vendored，且带着 18 条本地修改的同步成本。agentrt 若无此需求，直接依赖上游即可；**不要把 Cordis 本身搬进 agentrt**，借鉴的是其设计，不是其代码。
2. **SESSION_FORMAT_VERSION=0 无兼容承诺**——这是"开发预览期、无外部消费者"的立场（AGENTS.md:5-7 "foundation over blast radius"）。agentrt 若面向生产，持久化格式必须一上来就有版本演进策略。
3. **Typert 类型图 + 远程 BFF/RPC 网关**——dsh 为跨进程（web client ↔ host）生成的类型化 RPC 是独立大系统，对 agentrt 的 daemon 架构是否值得取决于协议面规模；不建议仅为"插件模块"引入。
4. **Code Mode（run_code）+ 自引用 Cordis 工具（tool-cordis 动态挂载/卸载插件）**——"agent 修改自己运行时"是 dsh 的示范性炫技（demo:cordis 脚本），安全边界极重（vm sandbox、dynamic runner）；agentrt 若不做自修改运行时，跳过。
5. **每包必带 invariant 运行时不变式 + 100% 单测覆盖门控**——优秀工程文化但成本高，属于"团队纪律"而非"插件模块设计"，agentrt 可按阶段引入。
6. **keyless 快照重放测试体系**（DSH_SNAPSHOT=record/replay）——极佳的测试基础设施，但与插件模块设计无关，且与 dsh 的 ACP/JSONL 协议强绑定。
7. **双语文档 + word budget + 生成文档站**——纯工程文化投入，不可直接迁移为 agentrt 的插件能力。
8. **Claude Code/Codex hook 桥**——具体协议适配（hooks-claude-code/codex），agentrt 若有自己宿主则无意义；但其**通用 hook 协议词汇**（hook/invoked、hook/result 事件 + waterfall 拦截点）值得学习。

### G.3 给 agentrt 的浓缩建议（基于上述分析的落地顺序）

- **第一阶段（地基）**：Context/服务定位 + inject 依赖 + Fiber 生命周期 + effect disposer 纪律 + 五种事件分发——这五件是 dsh 插件体系的最小完备集（cordis-primer.md "Five Ideas"），可对照实现或选用成熟框架。
- **第二阶段（能力化）**：把 plugin_d/market_d 的能力按"定义/Provider/Consumer"三元组织；每类能力一个注册表服务（如 ctx.tools/ctx.skills 模式）；hook_d 全部实现为事件 listener，禁止在 daemon 主循环硬编码 hook 点。
- **第三阶段（治理）**：配置驱动加载（patch 分层）+ 生成式目录门控 + "模型可见⟺已记录"不变量。

### E-1 技能注册表三处并存、命名体系互不相认（最严重的 SSoT 冲突）
1. **skills 叶仓**：5 个官方技能（code_review / text_summarization / security_audit / data_analysis / web_search）+ 3 个 contrib（browser / database / github，仅 README）。

## 结论（对 E 问题的直接回答）

- **职责重叠处**：技能概念（skills 定义 / manager 注册 / market_d 运行时表）与 Agent 概念（agents 执行体 / manager 注册 / market_d 运行时表）均为"三份并存"；hook 域存在 C daemon 薄壳（hook_d）与 Python SDK hooks 两个世界，ecosystem 层已完全退出 hooks。

## 核心结论

# B. 特别关注的三组报告深挖

## B1. #5 agentrt vs dsh 底座对比：对比维度与差距结论

**对比维度**（§一，7 维，源码事实）：
1. 形态本质：dsh 框架/库（单进程 Node + 进程内 DI）vs agentrt 平台外形（17 常驻 daemon + AIRY_HOME + 控制面/数据面分离）→ agentrt 占优
2. 控制面/数据面：dsh 无显式分离 vs agentrt 有 → agentrt 占优
3. 稳定契约：dsh 进程内 TS 类型、无跨进程 ABI vs agentrt 128B IPC 头 + [SC] 跨态契约（但 3 套分叉未收敛）→ 潜力 agentrt
4. **可组合扩展：dsh 强（Cordis DI + 能力接缝三角色 + profile/bundle）vs agentrt 弱（仅 memory vtable 全局单例，扩展点分散）→ dsh 占优**
5. 运行形态：dsh 进程内库 vs agentrt 托管运行时 → agentrt 占优
6. 生态开放：dsh 真开源可验证（MIT + npm + 100% 覆盖率）vs agentrt L3/L4 闭源、沙箱依赖 docker、无公开基准 → dsh
7. 工程成熟度：dsh 能跑已收敛（npx 即用）vs agentrt 不能收敛（385k 行手写 C，多套冗余）→ dsh

**物种判别**（§二）：「dsh ≈ agent 界的 Spring Boot / Koishi」；「agentrt ≈ 一个自称 K8s、但还没有 reconcile/etcd/CRD 的多进程运行时」。两者不在同一层竞争。

**差距结论**（§三/§四）：agentrt 缺的不是"平台本质"本身，而是"本质未被系统化"。四大差距中——reconcile 闭环**认知层已存在**（蓝图→GRAD→复核 DRIFT→回灌），只需延伸到生命周期/资源层；etcd 等价物**可推迟**（单机用事件流 + SQLite WAL + watch）；**统一扩展机制是真正需补的**（memory vtable 模式推广到四域 + 统一注册表，参考 dsh Cordis 三角色但用 agentrt 的 vtable 形态）；可验证开源属生态问题（L3/L4 闭源是商业策略可保留）。0.1.2 范围据此修正为「SSoT 收敛 → 平台本质补齐（reconcile 延伸 + 统一扩展）→ 云原生多机后置」。

8. **运行时 invariant companion**：每 package 有 `invariant.ts` 注册到 `ctx.invariants` 做关系断言（#7 摘要 3）

## B3. #1 的 SSoT/统一设计原则

**SSoT 四句话哲学**（§1.1）：① 机制在内核，策略在用户态；② 内核冷酷执法，用户温情裁决；③ **每个技术点只允许有一个权威源**——SSoT v2 单一权威源模型，[SC] 共享契约头物理宿主唯一，CI 强制逐字节校验；④ IPC 就是能力校验（Capability Folding 折叠到数据面 fastpath）。

**方法论核心**（§1.3/§三）：「每个冲突点 = 一个"技术点有多个权威源"，消解方式 = "收敛为唯一权威源"」。「这不是删功能，是消除"同一事实的多个权威定义"」。

**S-1~S-8 冲突点收敛清单**（§三，对插件系统设计最相关）：
- S-3 双 IPC 协议收敛：「IPC 头三处分叉……`airy_types.h` 旧 `airy_ipc_header_t`（AOSP magic）+ `corekern/are_ipc.h`（source/target 字符串）+ `airymax/ipc.h`（Layout C v4）→ A-IPC：`airymax/ipc.h` Layout C v4（magic ARE1 + badge + crc32，128B 冻结）」
- S-4 DAG 三套引擎 → 主链 `taskflow_advanced`（调度权威）+ `graph_engine`（图原语权威）
- S-6 事件流无权威源 → 「权威事件流：append-only 事件流 + 全局 seq + 运行时 invariant（对应 A-ULP Ring Buffer 是观测 SSoT）」
- S-8 [SC] 契约漂移 → 字节级对齐（`sc-dual-ci.yml` diff -q 通过）

**插件系统层面的推论**（§五 corekern/commons 加强方向）：corekern/commons 是"收敛后的**唯一权威源本身**"——IPC 契约收敛为跨态唯一权威源；统一原语 `airy_effect` 引入。

# C. 对"agentrt 插件系统设计"有约束力的既有决策/铁律/倾向（12 份报告综合）

按约束力排序（已决策/定案 > 阶段规划 > 倾向性共识）：

1. **不砍 corekern/commons，反而加强**（#1 摘要/§五 核心立场、#3 P0-5）：「corekern/commons **不砍反而加强**（它们是 [SC] 契约 + 微核心原语 + 跨平台抽象的承载者，未来 agent-linux 跨态复用的基石）」——插件系统的基础原语（airy_effect、品牌化 ID、invariant 注册、服务注册表）应落在 commons，而不是新建旁路。

2. **Unify Design SSoT 单一权威源思想是元方法论**（#1 全篇、#5 §三）：「每个技术点只允许有一个权威源」；「用唯一权威思想做变相削减复杂度」——插件系统的任何能力（工具、provider、schema、错误码、IPC 头）都必须有一个且只有一个权威定义；syscall.xml codegen + `--check` 防漂移（#9 §7.3）是已落地的范式。

3. **双 IPC 协议收敛为 `airymax/ipc.h` Layout C v4（128B 冻结）**（#1 S-3、#3 P1-8、#9 §3.4）：删除 `airy_types.h` 旧头（AOSP magic）与 `are_ipc.h` 分叉；magic ARE1 + capability_badge + crc32；对齐 `[SC]` 契约头逐字节（11 字段 aligned(64)）。**插件对外通信契约必须以 128B IPC 头为准，且与内核侧字节一致**。

4. **事件流单一真相源是必做项（0.1.2 必做⑥，P0）**（#1 §四、#3 暂缓项的反面、#7 对比 1）：append-only 事件流 + 全局 seq + 运行时 invariant（"模型可见 ⟺ 已记录"）；hall_store 是雏形需升级；CLI/TUI 决策链可视化建立在它之上（#1 §六）。**插件产生的可观测事实应写入权威事件流，而非各自记录**。

5. **memory_provider 17 槽 vtable 是差异化资产，保留并作为能力接缝母版**（#4 §五、#5 §三、#7 摘要 1）：「保留：`memory_provider` 的 17 槽 vtable（这是产品差异化，不是基础设施）」；「把 memory vtable 的"能力接缝"模式统一推广（LLM/tool/storage/sandbox 四域 + 统一注册表）」——这是 0.1.2 阶段 2 的"统一扩展机制"，也是 agentrt 插件系统的主形态。

6. **能力接缝三角色完整方为能力**（#6 吸取点 1、#7 吸取点 2）：「能力 = Service Definition（vtable）+ Provider（实现）+ Consumer（调用者）三角色」；与机制/策略分离 IRON 铁律天然契合。当前 agentrt 只实现了 Definition + Provider 两角色，**缺 Consumer 角色与三角色完整性原则**（#6 §四吸取点 1）。

7. **注册到"全局单例"是缺陷，必须演进为"按 key 查找的服务注册表"**（#7 对比 2/吸取点 2、#5 可组合扩展维度）：「agentrt 无法像 deepseek 那样"换一个 provider 就换掉整个产品行为"」；C 语言用 hash 表 + 字符串 key 实现（#7 §五吸取点 2）。

8. **注册即副作用 + disposer + 逆序回滚（`airy_effect` 原语）**（#1 §2.1-4、#3 P2-11、#6 吸取点 3）：commons 统一原语，P1 落地——所有插件/daemon 的注册必须可逆、可回滚。

9. **服务按 key 查找 + 依赖注入替代手写启动顺序——明确后置（P2）**（#1 §2.1-8、#3 暂缓项 16、#4 不推荐立即融合表）：「先手写启动顺序跑通，再抽象」。

10. **一个 daemon 一个职责面，新能力优先以插件/GCCP 工具形式加入，不无限新增 daemon**（#11 §3.3、#12 §四聚焦策略）：CodeGeeX 战略收缩教训——**插件化是控制运行时复杂度的手段**，插件形态即"GCCP 工具 / daemon 插件化"。

| **Context 服务仓库（ctx.\<key\>）** | 对应：注册表 cap_key 查找 | ✅ 真吸收（但 agentrt 跨进程，用 gateway 承载） |
| **inject 依赖声明驱动加载顺序** | **不覆盖**：校验函数只管"调用时"，不管"加载时依赖就绪" | ⚠️ 缺失，需另补 |
| **Fiber 生命周期 + effect 可逆注册** | 不覆盖：入口只管调用路径，不管插件生命周期 | ⚠️ 缺失，需另补 |
| **capability seam 三角色** | 部分：cap_key 隐含三角色，但入口本身不强制 | ⚠️ 半覆盖 |
| **profile/bundle 声明式组合** | 不覆盖 | ⚠️ 缺失 |
| **类型化事件五分发** | 不覆盖：入口只埋点，不做事件分发 | ⚠️ 缺失 |
| **invariant 运行时断言** | 不覆盖 | ⚠️ 缺失 |
| **模型可见⟺已记录** | 部分：调用事实入事件流做到了 | ✅ 真吸收 |

**结论：这个想法只是"调用面"的收敛（入口/校验/路由），不是插件系统的全部。dsh 的 9 条思想里它只覆盖 3 条，缺的是生命周期、依赖、作用域、事件分发这些"运行面"机制。**

## 真正要批判的三点

**1. "统一 SSoT 校验函数"本身可能是个伪需求。**
dsh 的校验是**分散且廉价**的：编译期类型检查（TS 类型系统）→ 加载期依赖就绪（inject）→ 运行期 invariant 断言。它没有一个"集中校验入口"。而 agentrt 已有 [SC] 字节级契约 + 契约测试 + IPC crc32——"校验"早就分散存在。"再包一个统一校验函数"如果只是为了简洁，可能只是把分散校验又集中起来制造单点。

**2. 真正的价值不在"校验函数"，而在"能力注册表 SSoT + 统一调用路径"。**
如果剥离"校验"这层皮，这个想法剩下的核心是：
- 能力注册表作为**唯一权威**（cap_key 登记一切内建/扩展能力）→ 这是 SSoT 的真正落点；
- 所有调用经统一路径 → 天然可观测（入事件流）+ 集中安全（fail-closed）。
这两点才是真价值。"校验函数"只是它们的伴生形态。

**3. dsh 证明了一个更轻的替代路径。**
dsh 让"开发者写插件"轻到极致：导出函数 + 声明 inject + Config schema，**框架代劳**加载顺序/依赖/生命周期，不需要开发者知道"校验入口"。agentrt 若让开发者必须"登记 cap_key + 过统一入口"，在**框架体验上反而比 dsh 重**。

## 那它到底有没有使用价值？

**有，但要放在正确的位置：**

- **对 agentrt 平台：有价值。** agentrt 是跨进程平台（K8s 类比），daemon 间必须经 IPC，对外必须经 gateway。把 gateway 从"每 daemon 一个命名空间的 JSON-RPC 路由器"升级为"**能力 apiserver**"（统一 cap_key + 能力发现/校验/路由 + 可观测），是平台形态的**必然收敛**，不是装饰。K8s apiserver 就是证明——集中认证授权 + 分散执行。
- **对开发者：价值不在"入口函数"，而在"注册表 SSoT 带来的确定性"。** 开发者最关心的是"我写的能力能被可靠发现、可靠调用、不冲突"——这是注册表 + 生成式目录（airy_cap_catalog）给的，不是"那个函数"给的。
- **相对 dsh：它不是替代品，是互补层。** dsh 的精华（生命周期、依赖就绪、invariant、作用域）要作为运行面机制补进来；这个想法只是把**调用面**做好了。

## 修正后的定位

你的想法的正确表述应该是：

> **agentrt 平台提供一个统一能力面（gateway 承载）：一切能力（内建/扩展）登记于单一权威注册表（SSoT），调用经统一路径完成校验与路由（可观测、可审计、fail-closed）——这是平台层；插件系统的运行面（生命周期、依赖、作用域、事件）仍按 v4.4 报告的设计补齐。**

一句话：**有价值，但它是"调用面"的设计，不是插件系统的全部；不要把它包装成"统一校验函数"（那是伪需求），要把它落地为"能力注册表 SSoT + 统一能力面"（那才是真需求）。** 如果你想，我可以把这个修正后的定位补进 v4.4 插件系统报告里作为"调用面设计篇"。

**Assistant**

好问题。"运行面"是我用来和"调用面"对照的说法。先一句话区分：

- **调用面**（你上次的想法）：**能力被调用的那一刻**发生什么——校验、路由、响应。
- **运行面**：**能力从装上到卸下的一生**以及它和别的能力的**关系**——谁先启动、谁能看见谁、坏了怎么办。

四个机制分别是：

## 1. 生命周期（能力的一生）

**问题**：插件不是"装上就能用"这么简单。它要经历：被找到 → 校验通过 → 初始化 → 正常运行 → 被禁用 → 被卸载。每个阶段失败怎么办？卸载时资源怎么释放？

**dsh 的做法**：Fiber 状态机（PENDING→LOADING→ACTIVE→FAILED→UNLOADING→DISPOSED），每次状态迁移发事件广播；"注册即副作用"——插件注册的任何东西（工具、回调）都返回一个撤销令牌，卸载时**逆序自动回滚**，绝不残留。

**agentrt 的做法**（我报告的 `airy_ext_state`）：`REGISTERED→ENABLED→ACTIVE→FAILED→DISABLED→REMOVED`，状态迁移写入权威事件流；配 `airy_effect` 撤销令牌。**没有它**：插件卸载后，它注册的工具可能还在，下次调用就崩——这就是"卸载残留"问题。

## 2. 依赖（谁先启动）

**问题**：插件 A 需要插件 B 提供的服务才能工作。谁保证 B 先就绪？如果靠人肉排启动顺序，加一个新插件就要改启动脚本。

**dsh 的做法**：插件声明 `inject: ['tools']`，框架**等依赖服务就绪才激活插件**——加载顺序由依赖图自动决定，不是手写。

**agentrt 的做法**（`airy_dep_contract`）：插件在 manifest 里声明依赖的服务 key（如 `airy_llm`），注册表等依赖就绪再激活。**没有它**：daemon 启动顺序靠脚本手写（agentrt 现在 18 个 daemon 就有这个问题），加插件就得改启动脚本。

## 3. 作用域（谁能看见谁）

**问题**：多 Agent 场景下，子 Agent 需要的工具集和父 Agent 不同。如果所有插件都是全局的，子 Agent 会看到不该看的能力——安全问题和污染问题。

**dsh 的做法**：每个 Agent 有独立的 `agent.ctx`——在它上面注册的工具、监听器都是 agent 局部的，Agent 销毁就一起撤销。

**agentrt 的做法**（`airy_agent_scope`）：per-agent 能力集隔离。**没有它**：多智能体协作时所有 agent 共享全部工具，无法做最小权限。

## 4. 事件（插件间怎么协作）

**问题**：插件 A 想在"工具执行前"做拦截（比如安全检查），插件 B 想在"工具执行后"做记录。它们不能直接改工具实现——怎么介入？

**dsh 的做法**：类型化事件总线，五种分发模式——观察（emit）、拦截（waterfall 洋葱中间件）、并行、顺序、表决。策略就是"监听事件"，不硬编码在循环里。

**agentrt 的做法**（`airy_event` 五模式）：hook_d 已有 pre/post_tool 等 8 类钩子，事件模型把它推广成通用机制。**没有它**：想加拦截逻辑就得改 daemon 主循环源码。

## 用一个场景串起来

假设开发者装一个"代码审查插件"：

1. **生命周期**：插件被扫描到 → 校验契约 → 初始化 → 进入 ACTIVE；如果初始化失败，走 FAILED，不会污染系统。
2. **依赖**：它声明"需要 `airy_llm` 服务"，注册表等 llm_d 就绪才激活它——不用手动保证 llm_d 先启动。
3. **作用域**：主 Agent 能用代码审查，子 Agent 没有这个权限（per-agent 隔离）。
4. **事件**：它在"工具执行前"事件上挂一个拦截器，审查所有文件写入——而不是修改 daemon 源码。

**没有运行面**，你的"统一调用面"就是一座没有地基的楼——校验做得再好，插件装上会残留、启动会撞顺序、多 Agent 会越权、想拦截没入口。所以我上次说：**调用面是"门面"，运行面是"房子本身"**。dsh 的 9 条思想里有 6 条属于运行面，这也是它"一切皆插件"能成立的原因。

# AirymaxOS Capability 模型与 Capability Folding 深度研究报告

## 0. 执行摘要（先说结论）

1. AirymaxOS 的 Capability 模型是一套**seL4 CNode/MDB 语义 + POSIX cap 兼容 + 静态数组物理存储**的混合模型；Capability Folding 的本质是"**把权限校验从独立控制面 syscall 折叠进 IPC 数据面 fastpath 的单次 64-bit 比对**"，其工程代价（静态数组、单写者、零锁读、数据结构隔离）和收益（~10ns 校验、零 syscall、可 CBMC 验证）是配套设计出来的。
2. 对 agentrt 用户态插件系统：**可复用的是"模式"而非"代码"**——权限位图模型、per-subject epoch 撤销、校验链分层（廉价在前）、自举路径、单写者多读者缓存、数据结构隔离三原则、离线缓存 + Reconciliation 的韧性思想，全部可以跨态移植；**不可照搬的是物理机制**——io_uring fastpath、kfifo、READ_ONCE/WRITE_ONCE/RCU、per-cpu 无锁、AIRY_ALIGNED(64) cache line 布局，这些是内核态原语。
3. 关键对照：agentrt plugin_d 目前的权限校验是**加载时一次性字符串→守卫类型映射 + 布尔裁决**（`plugin_permission.c`），与 Capability 模型差距在"无令牌化、无每次调用时校验、无撤销/对账、无代际"。Cupolas 的 `safety_guard_check_permission()` 目前仍被 `AIRY_ENABLE_V2_API` 宏门控（"planned for next release"）。
4. 对"gateway 统一能力网关 + airy_cap_invoke 统一入口"：**Capability Folding 思想在方向上印证该想法**（校验折叠进唯一调用路径），但 AirymaxOS 自己的文档明确 H3 约束"agentrt 用户态 capability_badge 恒为 0"——即**官方路线中 Badge 模型不进入 agentrt 用户态**。因此该想法应在 agentrt 内做"语义同源"的用户态实现（新的 token 化能力句柄），而非直接搬运 Badge 位布局。

另有一个必须诚实指出的重要背景（影响所有评估）：**这 4 份文档大量内容是"设计稿超前于实现"**。文档自证：
- `07-ipc-fastpath.md` §5.2 明确标注当前 `kernel/corekern/ipc/airy_ipc_fastpath.c` 实际只有 **91 行**（`airy_ipc_fastpath_send()` = frozen 门检查 + 委托 `airy_ipc_ring_post()`），C-S0~C-S12 校验链、`airy_uring_cmd`/`airy_ipc_validate`/`airy_ipc_deliver_fast` 均为设计稿（L382）；

## A. Capability 模型完整机制

来源：`/home/spharx/SpharxWorks/airymaxhub/docs/AirymaxOS/110-security/03-capability-model.md`（唯一权威源，SSoT 声明见 L14-18）

### A.1 cap_t 句柄（无句柄索引，token 即值）

- `typedef __u64 cap_t;`（§2.1 L74-80）：**刻意不引入 uint32_t 句柄**，cap_t 本身就是 64-bit 不透明令牌。"无 cap_idx_t（不引入 uint32_t 句柄，cap_t 即 64-bit 不透明令牌）"。内部 CNode 索引哨兵 `CAP_IDX_INVALID 0xFFFFFFFF` 仅为 [IND] 内部使用，不进 [SC] 共享契约。
- CNode 槽位结构 `struct airy_cnode`（§2.1 L130-140）：cap_type / cap_id / badge / randtag（v1.0.1 新增防伪造组件）/ owner_agent / MDB 树节点 / state / refcount（atomic_t）/ expires_ns，整体 `aligned(64)`。
- MDB 派生树节点 `struct cap_node_t`（L98-103）：parent/children/sibling/generation（generation 世代计数器防 use-after-free，约束 I6，附录 A.3 L2348）。

### A.2 capability_badge 64-bit Native Word 位布局

物理定义在 [SC] `include/uapi/linux/airymax/ipc.h`，消息头 offset 40-47（`02-ipc-protocol.md` §2 L96-108，D-9 修复后 8 字节自然对齐，`_Static_assert(offsetof == 40)`）：

```
63          48 47              16 15       0
┌────────────┬─────────────────┬────────────┐
│ Epoch 16bit │ RandomTag 32bit │ Perms 16bit │
└────────────┴─────────────────┴────────────┘
```

- **Epoch（16 bit）**：per-agent 代际快照，主撤销机制。`agent_caps[agent_id].epoch`（K9-1 改为 per-agent；`airy_cap_global_epoch` 降级为"补充性全局计数器"，仅 UNFREEZE 时用）。撤销沿 MDB 派生树**递归递增**（O(N) 级联）。
- **RandomTag（32 bit）**：sec_d 编译时 `get_random_bytes()` 生成，防伪造核心；校验时与 `agent_caps[src_task].randtag` 比对。
- **Perms（16 bit）**：权限位图，7 个有效位 `SEND 0x1 / RECV 0x2 / DERIVE 0x4 / KILL 0x8 / FILE_OPEN 0x10 / ROTATE 0x20 / SUPERVISE 0x40`，bits 7-15 必须为零（`AIRY_CAP_PERM_RESERVED 0xFF80`）（03 号 §2.5 L309-315；02 号 §2 L141-148）。
- 提取/编译宏为单指令位运算（L297-306）；权限检查宏 `airy_cap_has_perm(perms, opcode)` 采用**严格包含语义** `(perms & required) == required`，超集允许（§2.6.2 L413-427）。
- 安全性分析表（L324-334）：伪造→RandomTag 比对；重放→Epoch 比对；越权→Perms 位运算；泄露→编译时绑定 agent_id；暴力枚举→2^48 空间 + 3 次失败冻结 ring（§13.4.4）。Epoch 16 位溢出周期分析：单节点 Agent 终止频率 <1 次/秒时 >18 小时，溢出时 sec_d 全量重编译（L334）。
- **RandomTag 碰撞无安全影响**（§13.4.2）：Badge 校验锚定 `agent_caps[src_task]` 而不是全局查找，`src_task` 由内核填写不可伪造，因此碰撞只影响审计可读性。

### A.3 权限位图与 opcode→perms 契约

- §2.6.1（L344-393）：**1 opcode → 1 required_perms 位掩码**。SEND→PERM_SEND；RECV→PERM_RECV；SEND_BATCH 与 CANCEL 复用 SEND；FREEZE 复用 SUPERVISE（微监督者特权）；**CAP_REQUEST / CAP_RESPONSE → 0（自举与 sec_d 回复无需权限）**；非法 opcode → 0xFFFF（任何 perms 都不满足）。
- 映射表为设计契约（SSoT），`airy_op_required_perms()` 内核实现待 M2（L342）。

### A.4 存储：`agent_caps` 静态数组（Capability Folding 的物理前提）

- v1.0.1 从 radix tree 重构为静态数组（§2.4 L196-274）：`static struct airy_cap_slot __airymax_cap_table[AIRY_CAP_MAX_AGENTS=1024] AIRY_ALIGNED(64)`，slot 字段 80B、sizeof 128B、共 128KB；`agent_caps` 为 `__ro_after_init` 指针。
- **单写者多读者**：唯一写者 sec_d（经 `airy_sys_call + COMPILE_BADGE`），唯一读者 fastpath C-S9；同步为 WRITE_ONCE/READ_ONCE **零锁零 RCU**（L239-242）。
- slot 布局（L245-259）：badge/agent_id/flags/randtag/perms/epoch + MDB 派生树五字段（parent_agent/first_child/next_sibling/generation/revocable）+ 40B 对齐填充。
- 实际写并发是 per-bucket 散列锁（128 桶），register/derive 同锁消除 TOCTOU（§2.6.4 L475-488）；REVOKE 取全部桶锁（`cap_derive_lock_all()`）。
- 初始化：per-agent epoch 置 1（非 0），确保空 badge 无法通过 C-S9.EPOCH（§13.5.4 L1719-1733）。

### A.5 派生操作（7 种，seL4 CNode 对齐）

§3（L495-609）：COPY（克隆/降级）、MINT（始终降级 `new_perms & src.perms`）、MOVE（转移，badge 不变）、MUTATE（改权限位，不换 RandomTag）、**REVOKE（递归级联撤销）**、DELETE（单槽）、ROTATE（重新生成 RandomTag）。全部收敛到 `airy_cap_derive(src_agent, dst_agent, op, new_perms)` 单一入口（§3.2 L536-544）。MDB 派生链规则：子 badge 必须 ≤ 父 badge（权限只减不增，I1）；REVOKE 实现 `airy_cap_revoke_subtree()`（L590-604）：沿左孩子右兄弟树递归，对每个 revocable 后代执行 `WRITE_ONCE(slot->epoch, new_epoch)` + `WRITE_ONCE(slot->randtag, 0)`，O(N)，N≤1024。

### A.6 撤销（epoch bump）

- 两条撤销机制并存（§2.5 L286-289）：
  - **主机制**：per-agent `agent_caps[agent_id].epoch`，REVOKE 沿 MDB 树递归递增（`airy_cap_epoch_bump(agent_id)` / `airy_cap_derive + AIRY_CAP_OP_REVOKE`），爆炸半径=整棵派生子树；
  - **辅助**：`airy_cap_global_epoch` atomic_t（UNFREEZE 全局撤销用）。
- 撤销语义是"**代际失效而非物理删除**"（L584-586）：旧 Badge 因 Epoch 不匹配校验失败，语义等价 seL4 `cteRevoke` 且可恢复（重新 mint 即可）。
- K9-1 回归修复登记 §15.2（CAP-FIX-01~05）：REVOKE 空指针、派生未继承 epoch、DELETE/MOVE 未清 epoch、register 未初始化 epoch、rotate 缺并发控制——均为 per-agent epoch 引入的真实 P0 缺陷，经 seL4/Linux 6.6 双参考验证。

### A.7 CAP_REQUEST 自举（无 NULL Badge 硬编码）

- 02 号 §2.6（L279）+ 03 号 §9.1（L1069-1077）：Agent 首启发 `opcode=CAP_REQUEST`、`capability_badge=0`、`dst_task=sec_d` 的 IPC；C-S9 检测到该 opcode 直接放行（且**仅允许发往 sec_d**，否则 -AIRY_ECAP_BADGE）；sec_d 编译 Badge 后以 `CAP_RESPONSE` 返回。
- CAP_REQUEST 本身**不占 syscall**（原 592 号 syscall 移除），是纯数据面自举。

### A.8 引用计数与生命周期

- 令牌 7 状态机（§5 L770-812）：CREATED→ACTIVE/DERIVED/USED/TRANSFERRED/REVOKED/EXPIRED/DENIED；`expires_ns` 到期自动 EXPIRED（0=永不过期）。
- 引用计数：`airy_cnode.refcount`（atomic_t）+ MDB 约束 I4"refcount 必须 = MDB 子树中引用此 cap 的节点数；revoke 后 refcount 归零方可物理删除"（附录 A.3 L2346）。
- 生命周期与 syscall 的映射：见下 B.4（12→4）。

## B. Capability Folding 完整机制

来源：`02-ipc-protocol.md` §2.6（L242-296）+ `07-ipc-fastpath.md`（全文档）+ `03-capability-model.md` §12.5（L1401-1476）

### B.1 为什么折叠进 fastpath（核心理念）

- 工程定义（07 号 L13）：**"将 capability check 从独立控制面操作'折叠'到 IPC 数据面 fastpath 中"**；核心论断（02 号 L246）："**IPC 不是承载能力校验——IPC 就是能力校验**"。
- 动机链条（03 号 §12.5.4 L1464-1476 的 v1.0→v1.0.1 对比）：v1.0 独立前置 `airy_cap_check()` + radix tree + per-cpu cache 需 ~50-100ns、CSpace 读写锁、RCU 同步 + IPI 失效、9 个独立 syscall；v1.0.1 折叠后 ~10ns、零锁零 RCU 零 IPI、4 个 syscall、fastpath 100 行可 CBMC 全函数验证。
- 理论根基（07 号 L15）：seL4 fastpath 思想（ES-SEL4-4）——"无调度、无阻塞、内联检查"，把 seL4 的 capability 校验内联进 IPC fastpath，消除独立 capability syscall。
- 物理载体三件套（02 号 L248-255）：消息头 `capability_badge` 字段（offset 40-47）+ 执行点 `airy_cap_badge_ok()`（~10ns，3 个 READ_ONCE + 位运算 + 比较）+ 存储 `agent_caps[1024]` 静态数组。
- 6 条硬约束 H1-H6（02 号 L257-266；03 号 §12.5.1 L1405-1412）：H1 128B 头 + magic 不变；H2 字段进 [SC] 但校验属 [SS]；**H3 agentrt 用户态 badge 恒为 0**；H4 内核 badge 由 sec_d 编译、C-S9 校验；H5 纯 C LSM 职责不变；H6 [DSL] 降级 badge=0 跳过 C-S9。

### B.2 C-S0~C-S12 校验链（逐项）

发送方校验链表在 07 号 §3.1（L199-217），实现代码在 §5.2（L458-559）。逐项：校验什么 / 在哪儿 / 开销 / 失败后果：

| # | 校验内容 | 位置（实现） | 开销（设计估算） | 失败 → 错误码 |
|---|---------|------------|----------------|-------------|
| C-S0 | ring 未冻结 `frozen==false` | `airy_ipc_validate()` 入口 | ~1ns | ERROR → `AIRY_EIPC_FROZEN`(-53) |
| C-S1 | magic == 0x41524531 | 同 | ~1ns | ERROR → `AIRY_EIPC_MAGIC`(-41) |
| C-S2 | opcode 合法（7 种） | `airy_ipc_opcode_valid()` | ~1ns | ERROR → `AIRY_EIPC_OPCODE`(-42) |
| C-S3 | `payload_len <= MAX_PAYLOAD` | 同 | ~1ns | ERROR → `AIRY_EIPC_PAYLOAD`(-43) |
| C-S4 | hdr_size==128 且 reserved[72] 全零 | 循环检查 | ~2-4ns | ERROR → `AIRY_EIPC_HDRSIZE`(-44)/`RESERVED`(-45) |
| C-S5 | src/dst 同 CPU（per-cpu 无锁前提） | `smp_processor_id()==dst_cpu` | ~1ns | **SLOW_SEND**（非 ERROR，降级） |
| C-S6 | per-cpu kfifo 未满 | `kfifo_avail()>=hdr+payload`（在 `can_fast_deliver` 中） | ~1ns | SLOW_SEND（背压）→ `AIRY_EIPC_KFIFO`(-48) |
| C-S7 | `cmd->reclaim==false` | 同 | ~1ns | ERROR → `AIRY_EIPC_RECLAIM`(-49) |
| C-S8 | `in_task()`（非中断上下文） | 同 | ~1ns | SLOW_SEND → `AIRY_EIPC_CONTEXT`(-50) |
| **C-S9** | **Badge 校验（Capability Folding 执行点）** | 内联 `airy_cap_badge_ok()` | **~10ns（实测 2-10ns）** | ERROR → ECAP_BADGE(-78)/EPOCH(-79)/FORGED(-80)/PERM(-81) |
| C-S10 | flags 无 RESERVED 位、无 ENCRYPT/COMPRESS | 位测试 | ~1ns | ERROR → `AIRY_EIPC_FLAGS`(-46)/`NOTSUPP`(-47) |
| C-S11 | preempt_disable 准备（kfifo 保护） | 实际在 deliver_fast 中执行 | ~5ns（配对） | — |
| C-S12 | CRC32（覆盖 header[0:52)+payload） | `airy_ipc_crc32_ok()` 投递前 | ~15ns | ERROR + `AIRY_FAULT_RING_CORRUPT`(0x1003) → `AIRY_EIPC_CRC32`(-51) |

C-S9 内部 3 个子检查（§3.1.1 L219-296，**顺序固定 EPOCH→RANDTAG→PERMS**）：
- C-S9.EPOCH：`badge_epoch == READ_ONCE(agent_caps[src_task].epoch)`，不匹配 → -79（已撤销/过期）；
- C-S9.RANDTAG：`badge_randtag == READ_ONCE(agent_caps[src_task].randtag)`，不匹配 → 触发 `airy_security_fault(AIRY_FAULT_CAP_FORGED 0x1001)` + -80；
- C-S9.PERMS：`airy_cap_has_perm(badge_perms, opcode)` 严格包含 → 不满足 -81。
- 两个放行捷径：CAP_REQUEST（且仅限 dst=sec_d）与 badge==0（H3 agentrt / H6 降级；但 badge==0 + CAP_CARRY 置位视为非法 → -78）。
- 关键不变量（L293-296）：纯读零副作用（不持锁、不调度、不写共享内存）；`agent_caps[]` 用户态不可见（与 kfifo 物理隔离）；badge_epoch 与 slot_epoch 解耦避免竞态。

接收方（C-R1~C-R5，§3.2 L298-310）：**接收方不再重复校验 Badge**——"通过 C-S9 的消息已具备合法能力"，这是"IPC 就是能力校验"的语义保证。

校验链总耗时 ~68ns（锁内），FAST_SEND 端到端设计 ~158ns、实测 ~46ns（UML x86_64 KUnit `airy_fastpath_bench`，§5.3 L657）。

### B.3 fastpath 与 slowpath 分工

- 8 状态机（§2.1 L63-72）：IDLE/FAST_SEND/FAST_RECV/BATCH/CANCEL 为无阻塞路径（★），SLOW_SEND/SLOW_RECV 阻塞排队，ERROR 兜底。fastpath 硬约束（G-2）：禁止 `schedule()/mutex_lock()/wait_event*()`。
- slowpath 触发（§4.1 L328-338）：payload_len>0、跨 CPU、kfifo 满/高水位（75% 3072 项）、无匹配消息、ENCRYPT/COMPRESS、**C-S9 失败需 COMPLAIN 裁决时**（OS-SEC-009 经 A-IPC 询问 daemon）。
- io_uring 集成（§5）：`IORING_OP_URING_CMD` 统一复用 + `cmd_op` 区分（SQE128 模式，D-7 修复，§5.7）；`airy_uring_cmd()` 在 `ctx->uring_lock` 内仅做校验+快速投递，需要唤醒返回 -EAGAIN 交给 io-wq（L384, L411-449）。kfifo kthread 间通道（§6）：per-cpu SPSC 无锁 + 水位背压；SPSC ring 内存序修复用 `smp_store_release/smp_load_acquire` 配对（§6.5 L823-854）。

### B.4 syscall 12→4 精简逻辑

03 号 §5.3（L817-843）+ §9（L1053-1131）：
- 原 9 个 capability syscall（592-600）全部废弃；唯一保留 `airy_sys_call`(548) + 4 子命令：`COMPILE_BADGE`（含 MINT/COPY 等价）、`REVOKE_BADGE`、`LSM_CTL`、`WASM_LOAD`（**仅 sec_d 可调**）；另 3 个核心 syscall 549/550/551 属 rovol/sched/clt。
- 精简逻辑：**权限传递走数据面**（`AIRY_IPC_FLAG_CAP_CARRY` + fastpath C-S9，无 syscall）；**查询走 sysctl**（`kernel.airy.cap_*`）；**自举走 opcode**（CAP_REQUEST，无 syscall）；**只有"编译/撤销/策略/装载"这 4 类特权操作保留 syscall 且仅限 sec_d**。

### B.5 数据结构隔离三原则

03 号 §12.5.2（L1414-1433）：三个独立内存区域，更新路径独立、失败域独立：
1. `agent_caps[]`：能力数据（静态数组 128KB，sec_d 唯一写者，fastpath READ_ONCE 读，WRITE_ONCE/READ_ONCE 无锁）；
2. `kfifo`：数据投递缓冲区（per-cpu SPSC 无锁，写者 fastpath kfifo_in，读者接收方 CQE）；
3. `io_uring ring`：通信原语（写者发送方 SQE，读者接收方 CQE）。

隔离的目的是"使 fastpath 100 行代码 CBMC 全函数验证可行"（§10.6，P1-P5 属性规约：越界、溢出、preempt 配对、SPSC 不变量、错误码集合）。

## C. IPC 数据面自治

来源：`/home/spharx/SpharxWorks/airymaxhub/docs/AirymaxOS/110-security/04-ipc-data-plane-autonomy.md`（378 行，唯一权威源声明 L14）

### C.1 Ring 生命周期解耦（原则一，§2）

- 问题：传统控制面（名称服务/授权服务）宕机 → 数据面不可用，违反故障隔离。
- 机制：Ring 内存由内核 `alloc_pages(GFP_KERNEL)` 分配、mmap 映射，控制面进程仅持 opaque handle，**释放条件为 `refcount` 归零而非控制面进程退出**（L79-103：`airy_ipc_ring_release()` 中 `atomic_dec_and_test(&ring->refcount)` + `call_rcu` 延迟释放）。控制面崩溃时数据面仍引用 ring（refcount>0），Ring 存活、消息继续传递；恢复后经 RECONCILE 重新计数。

### C.2 离线缓存校验（原则二，§3）

- v1.0.1 重构说明（L129-135）：机制从 v1.0 radix tree 缓存 + TTL + 两层校验，升级为 `agent_caps[1024]` 静态数组 + 64-bit Badge 内联校验。**Badge 在控制面在线时由 sec_d 编译写入，控制面离线后 C-S9 仍可无锁内联校验**——"Badge 一旦 mint 出来，其校验不依赖授权者在线"（seL4 哲学，L55）。
- 离线容忍度（L203-211）：缓存命中且未过期→完全容忍；stale→部分容忍（放行但告警）；未命中→不容忍（返回 `-AIRY_EINVAL`，消息暂存离线队列）。
- v1.0 原始两层模型（L141-148）保留为语义参考：fastpath 查缓存不依赖控制面（~160ns），slowpath 完整校验依赖控制面（~10μs）。

### C.3 Reconciliation（原则三，§4）

- 触发：控制面重启/网络恢复后扫描比对（L215-244）。流程：扫描数据面实际状态（Ring 列表、缓存、离线队列）→ 与记录 diff → 差异修复 → 最终一致。
- reconciliation log（L250-267）：`enum airy_reconcile_op`（NEW_RING/DESTROY_RING/CAP_GRANT/CAP_REVOKE/MSG_PENDING）+ 条目结构。
- 保证（L269-278）：消息不丢、能力不越权（离线期间仅基于缓存无新增授权）、Ring 不泄漏、**30 秒内最终一致**；超时触发 [DSL] 降级（§5.4）。
- 03 号附录 A.2（L2327-2337）补充内核态版本：三阶段对账（Diff/Reconcile/Verify），Verify 阶段重算 MDB 派生链哈希比对；对账期间持 CSpace 读写锁、新操作降级 slowpath。
- 三原则协作关系（§5.2 L300-310）：解耦解决"Ring 消失"，缓存校验解决"校验不可用"，Reconciliation 解决"状态分裂"——缺一不可。

### D.2 内核态专属、不可照搬的机制

| 机制 | 为何不可照搬 |
|---|---|
| io_uring fastpath（IORING_OP_URING_CMD/SQE128/sqpoll/registered buffers） | Linux 内核专用；agentrt 用户态跨平台（libc/POSIX，macOS/Windows 无 io_uring） |
| kfifo / per-cpu SPSC 无锁队列 | 内核原语（`DECLARE_KFIFO_PTR`、`____cacheline_aligned_in_smp`），用户态需换 POSIX 队列或共享内存 ring |
| READ_ONCE/WRITE_ONCE/atomic_t/smp_store_release 内存序 | 内核内存模型；用户态用 C11 atomics（memory_order_acquire/release）等价实现，但语义级别不同 |
| RCU 延迟释放 / call_rcu / IPI | 内核机制；用户态无 RCU，用引用计数 + epoch-based reclamation 近似 |
| `AIRY_ALIGNED(64)`/cache line 布局/_Static_assert | 与内核编译链绑定；用户态跨编译器需自行封装（agentrt 已有 uapi_compat.h 思路） |
| Badge 位布局依赖消息头 offset 40-47 与 `src_task` 内核填写 | H3 明文规定 agentrt `capability_badge=0`；`src_task` 用户态可伪造，锚点前提不成立 |
| CBMC 全函数验证 fastpath 100 行 | 可借鉴方法论，但验证目标不同（用户态无内核上下文） |
| LSM 钩子注册（uring_cmd/task_kill/file_open 入口对称校验） | 内核钩子机制；用户态对应物是 gateway/daemon 方法入口 |
| syscall 12→4 | 用户态没有 syscall 收敛问题；对应物是"统一经 gateway 派发"（已 2026-08-25 落地） |

### D.3 plugin_d 16 项权限 vs Capability 模型：差距与融合点

差距（按严重度）：
1. **无令牌化**：16 项权限是 manifest 静态字符串，不是"调用者持有、调用时出示"的凭证。Capability 模型的核心是"凭证不可伪造、随调用携带、可撤销"，plugin_d 现在"加载时一次裁决，运行时不再校验"（D.0 已证）。
2. **无每次调用时校验（enforcement 缺失）**：Capability Folding 的核心论断是"数据传递即能力校验"；plugin_d 的 `execute` 直接 dlopen 调用，不经过任何守卫。这是与 Folding 思想差距最大的一点。
3. **无撤销/代际**：插件 unload 后仅从注册表移除，不存在"已派发的旧凭证失效"机制；而 AirymaxOS 有 epoch bump + 级联撤销。
4. **无离线缓存/对账**：cupolas_d 不可达时 plugin_d 仅降级为"本地校验"（README L29-30 明示），无"离线期间缓存裁决 + 恢复后 Reconciliation"设计。
5. **守卫 API 未发布**：`AIRY_ENABLE_V2_API` 门控下 `safety_guard_check_permission` 是规划 API，当前 plugin_d 权限模块的运行时行为依赖它。
6. **无能力派生/最小权限传递**：插件无法把能力子集传递给另一个插件（无 MINT 等价物）；安全值域只有"整包允许/拒绝"。
7. **身份单一**：gateway 对外部协议只有 `GW_EXTERNAL_AGENT_ID` 一个身份，无 per-caller 能力视图（对照 Badge 编译时绑定 agent_id）。

融合点（建议落地路径）：
- 用**16-bit 能力位图**替换字符串比较：`manifest.permissions[]` → `uint16_t cap_bits`，映射表即 `plugin_permission.c` 现有 14 守卫 + 2 预留位的位索引化（改动小，测试 `test_plugin_permission.c` 全量保留）。
- **调用路径注入校验（用户态 Capability Folding 最小版）**：plugin_d 的 `execute`/gateway 的 `<daemon>.<method>` 派发处加统一能力检查点（`airy_cap_badge_ok` 的用户态等价：读插件能力位 + 方法所需位掩码，`(bits & required) == required`），把"加载时一次裁决"升级为"每次调用检查"——这正是 E 节 airy_cap_invoke 的雏形。
- **能力 slot 表**：`struct airy_cap_slot`（badge/epoch/randtag/perms）的用户态映射——但注意 randtag 防伪在用户态需要不同的信任锚（进程身份 + SO_PEERCRED / 签名 manifest），不能照搬 32-bit 随机数。
- **撤销/对账**：plugin unload 或 config 变更时 bump per-plugin epoch，gateway/daemon 侧缓存 epoch 快照，不匹配即拒绝；plugin_d 重启后与 cupolas_d 对账（对照 04 号 §4）。

## E. 对"gateway 统一能力网关 + airy_cap_invoke 统一入口"的印证与反驳

### E.1 印证（Capability Folding 思想支持该方向）

1. **"校验折叠进调用路径"是 AirymaxOS 自己的核心决策**：03 号 §12.5.3（L1435-1462）明确 fastpath C-S9 是"唯一执行点"，11 号 §11.1（L1230-1243）明确"A-IPC 路径不再使用独立 capability 守卫——校验已折叠进 fastpath 内联"。gateway 统一派发（2026-08-25 架构约束"所有客户端必须经 gateway 派发"）在 agentrt 用户态正是这个"唯一调用路径"的角色——**把能力校验折叠进 gateway 派发链，与 Folding 是同构决策**。
2. **opcode→required_perms 契约可直接映射**：`<daemon>.<method>` 就是用户态 opcode；gateway 现有白名单表（`GW_PLUGIN_METHODS`/`GW_MEM_METHODS` 等，`gateway_biz_forward.c` L426-468）可以升级为"方法→所需能力位"的映射表，用 `(perm_bits & required) == required` 做统一检查（03 号 §2.6.2 严格包含语义）。
3. **自举与"仅授权方"思想可复用**：CAP_REQUEST 仅允许发往 sec_d 的约束（02 号 L279、03 号 L696-700），对应 agentrt 中"插件能力申请仅允许发往 cupolas_d"。
4. **数据结构隔离三原则支持 gateway 集中**：能力表（agent_caps 对应物）唯一写者（cupolas_d/plugin_d）、只读消费者（gateway 各派发路径），用读写锁或原子快照即可实现无锁读热路径。

### E.2 反驳与边界（必须遵守的约束）

1. **H3 硬约束**：AirymaxOS 官方路线中"agentrt 用户态 `capability_badge` 恒为 0，使用传统 cap_t 引用"（02 号 L118、L262；03 号 H3 L1409）。**Badge 64-bit 位布局不能直接搬进 agentrt**——它在内核侧依赖 `src_task` 不可伪造 + `agent_caps[]` 内核私有。用户态若复刻 Badge，`src_task` 可被进程伪造，RandomTag 防伪前提失效。因此"统一入口"应实现为**用户态自己的能力句柄（token）**，语义同源但物理独立（[SS] 层同源、[IND] 层独立——02 号 §8.1 四层模型的正确用法）。
2. **"IPC 就是能力校验"的前提在用户态不成立**：Folding 之所以能省掉独立校验，是因为内核在唯一投递路径上强制校验。agentrt 的 IPC 是用户态 socket/消息队列，消息经过的中间层都可绕过 gateway（daemon 间直连、插件 dlopen 后内存内调用）。**air 单一入口必须靠架构约束强制执行**（禁止直连 daemon socket——2026-08-25 约束已在 CLI 侧落地，但 daemon 间调用是否全部收敛到 `airy_sys_svc_call` 需审计）。
3. **gateway 本身成为新的故障点**：04 号三原则的教训正是"控制面故障时数据面继续运行"——若把所有能力校验集中在 gateway，gateway 崩溃 = 全部校验失效。融合时应保留"离线缓存校验 + Reconciliation"（插件已获能力在 gateway 恢复前仍可按缓存裁决），而不是 gateway 不可达即全拒。
4. **纯 ACK 的"统一入口"不等于 Capability**：gateway 现白名单是静态 ACL（fail-closed），无凭证、无代际、无按调用者区分。只有引入"调用者携带能力凭证 + 每次调用校验 + 可撤销"三者，才真正符合 Capability 语义；否则只是把分散 ACL 集中成单点 ACL。

### E.3 结论

- 方向成立：`airy_cap_invoke`（统一能力入口）是 Capability Folding 思想在 agentrt 用户态的正确投影——**校验应折叠进唯一调用路径（gateway 派发链）**，且应内联"廉价检查在前"（先方法白名单、再身份、再能力位）。
- 落地要点：用户态能力令牌（替代 Badge）、per-plugin epoch（替代内核 per-agent epoch）、gateway 能力检查点（替代 C-S9）、cupolas_d 为唯一写者（替代 sec_d）、离线缓存 + 对账（04 号三原则）、严格包含语义 `(bits & required) == required`（03 号 §2.6.2）。禁用项：io_uring/kfifo/READ_ONCE 等内核原语、直接复刻 Badge 位布局、把 gateway 做成无缓存的无状态单点。

2. **daemon 分离 = 进程隔离**：独立生命周期（单个重启）、独立资源限制、独立安全边界（Cupolas 守卫 per-daemon）、故障不传播。合并进程 = 牺牲这些平台价值。
3. **"重"的病根不在进程数**（上一轮已论证）：在"手写轮子 + 未收敛实现"。18 个 daemon 是平台形态的必然（agent-linux 也有 12 daemon），真正的冗余在别处。

## 真正该做的三个"减重"（比整合更有效）

1. **daemon 壳层共享化**：18 个 daemon 都复用 `daemon_event_driver`（common 33k 行里有）。让"socket + 服务发现 + 标准方法 + 事件循环"壳完全统一，**每个 daemon 只写业务模块**——瘦的是重复的壳代码，不是进程数。这才是"轻"的正解。
2. **管理面收敛**（依赖图自动加载，上轮结论）：18 个 daemon 的启动序列、WAIT_SOCKS、gateway 白名单、monit_d 健康检查——这四套管理面代码是重复最多的。manifest `depends_on` + 拓扑排序一次收敛四套。
3. **降格评估**：如果未来某个能力的独立进程价值确实低（没有独立故障域/资源域需求），**降格为 plugin_d 加载的插件或 GCCP 工具**（v4.3 决策的"插件化控复杂度"），而不是继续并排加 daemon。

## 一句话

**能整合的只有"管理面和壳层"，不能整合的是"职责和进程"。** 18 个 daemon 的数量本身不是问题——问题是有没有共享壳、有没有自动管理、有没有冗余实现。我们之前讨论的依赖图 + 插件系统，恰恰是把"运维 18 个进程"变成"声明式管理 18 个能力"的路径，那才是真正的减重。
