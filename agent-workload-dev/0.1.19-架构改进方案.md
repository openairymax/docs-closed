# 0.1.19 架构改进方案

> **纲领**：**机制与策略极致分离** —— 机制核零策略载荷，策略一律数据化注入或迁出生态层（§2.6）
> **最高约束**：**功能守恒** —— 所有对外功能一个都不能变
> **硬约束**：`agentrt` 八模块生产码总量 **< 100,000 行**（不含 `tests/`）
> **体验目标**：TUI 功能丰富、**不设总量上限**（体验账与机制账分立，§1.5）
> **主线**：**原子化 · 能力格 · 形态面** —— 立格（Slot）→ 造件（Atom）→ 成面（Facade）（§2）

***

## §0 阅读指南

### 0.1 纲领与主线

**一条纲领**：**机制与策略极致分离**。机制核（八模块）只留不含任何策略的原子件；厂商名、业务阈值、产品决策一律以「`ops` 函数表 + `.manifest` 数据」注入，或整体迁出生态层。本方案的一切手术，最终都在回答同一个问题：**这是机制，还是策略？** 答「机制」的留核并原子化，答「策略」的数据化或迁出——没有第三种处理。

**主线三步（本方案的任务核心主线）**：

1. **立格（能力格 Slot）** —— 先立 25+3 个能力格当坐标系；**格固定不变**，且**不留空格**——留格建件：格位是架构承诺，空格 = 基本能力缺位（§2.2）。
2. **造件（原子化 Atom）** —— 按准入三问裁定什么够格当原子件（§2.3）；98 个同类件塌缩成 18 类，**每格一件**（§3.3）。
3. **成面（形态面 Facade）** —— 原子件用 `⊗` 装配成组合件（Composite），按职责面收敛成 4 个形态面；**面 = 声明 + 生成 + 组合件装配，不写业务**——组合一律经组合件承载，**禁薄胶水串联**（薄胶水组合使系统不稳定，§2.4）。

**格格双达标判据（主线的验收尺，2026-09-25 复核强化）**：主线三步不是「做了就算」，**每个能力格的落点件必须双达标**：

- **① 有效扇入**：真实消费点（跨模块**符号调用/链接引用**的消费者文件数）实测 **≥ 3**（与准入三问 N≥3 同源）；`#include` 与伞形头扩散**不算消费**，只作定位真实消费点的初筛（2026-09-26 复核口径）；扇入 0 = 死件（G28 清扫），扇入 1~2 = 低扇入（就地内联或补消费者）；
- **② 运行正常**：落点件**有 tests 且接线 CI**（`add_test` + workflow），golden 全绿；**有测试未接线 = 未达标**（等同没测）。

**无空格豁免**：空格（有格无件）即**未达标态**——留格建件，事务/复制两格最迟 L5 建成母件并双达标（建件路径见 §2.2）。**为什么每个格都要有有效扇入**：扇入 ≥3 = 该能力被至少三个子系统真实复用，是公共基本能力而非私有代码；扇入 1~2 = 私有细节冒充能力（应内联）；扇入 0 = 死件占格；空格 = 该能力靠各处私搭维持。**每个格都有件且有有效扇入，系统的基本能力才是正常运行的状态**；任何一格缺件或缺扇入，系统就在那格上运行于不正常态。逐格实测审计见 **§2.8**，执法门禁 **G32**。

**两条硬约束托底**：功能守恒（一个功能都不能少）+ 生产码 < 100,000 行（验收硬门禁）。代码量靠三条减法达成：**迁出**（策略与体验面离开机制核）+ **塌缩**（同类件收敛）+ **生成**（样板不手写），功能一行不减。

## §1 双最高约束与总账

> **账目即纲领的投影**：迁出账记「策略与体验离开机制核」（§1.3），减重账记「机制核内塌缩归一」（§1.4）；两条最高约束各守一端——功能守恒守「面」，<100k 守「核」。

### 1.1 两条最高约束与守恒律

**约束一（功能守恒）**：改造前后**对外可见功能集合相等**，`|S₀∖S₁| = 0` 且 `|S₁∖S₀| = 0`。任何一步改造若导致功能消失，该步**立即回滚**。

**约束二（体积硬门禁）**：`agentrt` 八模块生产码（`*.c` + `*.h`，不含 `tests/`）总量 **< 100,000 行**。这是本版的**验收硬门禁**，不是方向性目标。

**守恒律（原 INV 系列，收编为四条）**：

| 名 | 内容 |
|----|------|
| 三账分立 | **减重 / 解耦 / 质量** 分别计量；禁以「归位」「口径变更」冒充减重 |
| 净减为正 | 每一轮施工真净减量必须为正、逐轮公示 |
| 归位不记账 | 归位（内容不变换目录）**不进减重账**（§4 单独记） |
| 禁双轨 | 新旧实现不得并存；禁留桩函数、禁留适配层 |

### 1.7 体积五元分解与杠杆判据

**五元分解**：`V = |A| + |closure∖A| + D + K + S`

- `|A|`：真正的原子件行数（不可再减的机制本体）
- `|closure∖A|`：原子件的闭包（头文件、类型、常量）—— 必要开销
- `D`：重复实现（同一机制多份）
- `K`：同类件散落（本可塌缩为一）
- `S`：样板胶水（本可生成）

**实测结论**：`K + S + D ≈ 62%` —— **六成以上代码是可减的**，这就是 <100k 可达的根据。

**杠杆效率 η 与收敛判据**（准入与收编的同一把尺）：

| 同类实现数 N | 裁定 | 记法 |
|-------------|------|------|
| N ≥ 8 | **必收** | η ≥ 3，收益确定 |
| 3 ≤ N < 8 | **应收** | η 正，收益可测 |
| N = 2 | **条件收** | 须证明两者语义同构 |
| N = 1 | **禁收** | 不得为「将来复用」造件 |

## §2 架构语言：Slot / Atom / Composite / Facade

> **总纲领**：**机制与策略极致分离**。贯穿本方案一切手术的唯一判据——**这是机制，还是策略？** 机制留核（原子化、填格、成面），策略让位（数据化注入或迁出生态层）。主线三步（立格 → 造件 → 成面）只处理机制的放置；策略的处置见 §2.6 四层模型。

### 2.1 一句话定义与关系式

- **Slot（能力格）**：能力的最小归类槽位。**格固定不变** —— 25+3 格是本工程永久的坐标系。
- **Atom（原子件）**：填入某个格、不可再分、只含机制的最小实现件。**件可替换** —— 换实现不换格。
- **Composite（组合件）**：两个及以上原子件按 `⊗` 装配得到的组件。
- **Facade（形态面）**：按职责面暴露的组合件集合，是服务层的「面」。

**核心关系式**：

```
面 Facade = 声明（manifest）+ 生成（样板）+ 组合件装配（Composite 承载）
格 Slot   ←固定→   件 Atom ←可变→
功能 = 原子件 ⊗ 装配 → 组合件 ⊗ 再装配 → 形态面
```

**一句话判据**：**固定的是格，变化的是件。** 讨论「要不要加一个模块」时，先问「它填哪个格」；答不出格的，就是不该造。

### 2.2 能力格总表（25 + 3）

| 层 | 格数 | 格名 |
|----|------|------|
| **基础层** | 10 | 同步 · 互斥 · 调度 · 隔离 · 命名 · 通信 · 序列化 · 事务 · 复制 · 恢复 |
| **中间层** | 8 | 增删改查（4 格合一族）· 发现 · 配置 · 缓存 · 路由 |
| **应用层** | 7 | 计算 · 校验 · 流转 · 通知 · 授权 · 记录 · 展示 |
| **补充格** | 3 | 韧性 · 流 · 校准 |

**留格建件（2026-09-26 裁决，替代旧「留格不建件」）**：格是坐标系，坐标系上每个格位都是**架构承诺**——系统必须有这块基本机制能力。格上无件 = 能力缺位，靠各处私搭乱建维持（K 病灶的根源：DAG ×7、checkpoint ×8 正是「格上无母件、各处自建」的实态）；有件无扇入 = 死件占格。因此**不留空格**：每个格都要有件，每个件都要有有效扇入——每个格都有有效扇入，系统的基本能力才是正常运行的状态。新建格上件适用「六个月判据」（语义更新）：最迟六个月内建成并双达标，逾期未建成须提交架构裁决；除名格位需公开辩护，默认不得除名。

> **事务格 / 复制格建件路径（原空置二格，2026-09-26 改判建件）**：
> - **事务格**：母件 = **heapstore 分区事务件**（多分区原子提交/回滚）——L5 与 D 通道分区收敛同场施工的直接产物，行数并入 D −30,000 收敛账，**不新增总账**。扇入来源：heapstore 分区写入、checkpoint 一致性快照、taskflow 作业原子性（≥3 天然成立）。
> - **复制格**：母件 = **状态快照复制件**（快照导出/导入 = 跨实例/跨时刻状态复制）——L5 与恢复格母件**同源分化**（一套序列化骨架：恢复格消费 kill -9 一致性恢复，复制格消费导出/导入），行数并入 K checkpoint −12,000 塌缩账，**不新增总账**。扇入来源：heapstore、mem_d 记忆快照、cognition 会话保存。
> - 两格最迟 **L5 建成**（checkpoint/分区母件落位时施工），G32 验收；建成前 ⏸ 记「待建件」整改态（**非豁免态**）。**双期限以先到者为准**：「最迟 L5」（工程序）与「六个月内建成」（日历，六个月判据）并存时取更早到期者；逾期即提交架构裁决。
>
> **格格双达标**：**全格无一豁免**——每格落点件必须**有效扇入 ≥3（真实消费点）且运行正常（tests 接线 CI 全绿）**，空格 = 未达标态——见 §2.8 逐格审计与 G32。

### 2.3 原子件准入三问

任何拟新增/保留的件，必须**三问全过**：

| 问 | 判据 | 不过的后果 |
|----|------|-----------|
| **① 是机制吗？** | 不含业务策略、不含厂商名、不含产品决策 | 不是 → 归**策略**，迁生态层 |
| **② 是收敛型抽象吗？** | 收编后总行数下降，且抽象带**语义**而非仅签名 | 不是 → 是**伪抽象**，禁止 |
| **③ 复用 N ≥ 3 吗？** | 独立使用点 ≥ 3（N=2 须证同构，N=1 禁） | 不是 → 不建件，就地内联 |

**反例（本版明令禁止）**：
- 为统一签名而设的「适配层」——签名统一不减少代码（N=1 型伪装）。
- 「一个策略一名多义」的接口 —— 同名承载两种语义，必须 fail-closed 拆分或拒绝。

### 2.4 形态面：4 面与五件套

**四个形态面（固定不变）**：

| 面 | 职责 | 例 |
|----|------|-----|
| **ingress** | 入口：接收、校验、反序列化 | `sched_d` 接 DAG 提交请求 |
| **execute** | 执行：调度、调用原子件、装配组合件 | 运行 DAG |
| **state** | 状态：持久化、查询、恢复 | 写 checkpoint |
| **governance** | 治理：策略裁定、限额、审计 | 拒绝越权计划 |

**daemon = 跨四面，不可拆**：一个 `*_d` 天然横跨四面，**四面是它的视图，不是四个可独立拆出的进程**（旧版误把四面当可拆单元，本版明确否定）。

**五件套（每个形态面的物理形态，固定五件）**：

| 件 | 形式 | 约束 |
|----|------|------|
| ① 声明 | `.manifest`（含 `slots` 字段） | 机器可读，缺失即门禁失败 |
| ② 入口 | `main.c` | **≤ 150 行**（只做装配与启动，不写逻辑） |
| ③ 实现 | `svc.c` | 主体逻辑 |
| ④ 组合 | `modules/` | 装配清单，声明用了哪些原子件 |
| ⑤ 装配 | **唯一私有头** | 全模块**唯一**一个私有头；装配经组合件承载，**禁薄胶水串联** |

**禁薄胶水组合（2026-09-26 纲领裁决，替代旧「面 = 声明 + 生成 + 薄胶水」）**：**不能用薄胶水层的方式组合——薄胶水组合使系统不稳定**：

> - **无契约**：薄胶水是过程代码里的隐式串联——无类型签名、无生命周期、无错误传播约定。原子件接口一变，胶水静默脆断，故障在组合点爆发且难定位；
> - **无测试**：薄 = 覆盖盲区。组合点恰是故障高发区（装配次序、状态一致性、错误传播），却游离在 tests/CI 之外——格格双达标对它失明；
> - **复杂度散落**：装配决策散成 N 处隐式胶水，每处都是独立失效模式，无单一可审计点——「系统怎么组合的」无法回答，只能考古；
> - **无问责**：胶水不是件——没格、没扇入、没双达标，架构语言三概念（格/件/面）对它全部失明。
>
> **替代：组合一律经组合件（Composite）承载**——`⊗` 显式装配，装配契约（输入/输出/生命周期/错误传播）落在组合件代码内；组合件有自己的 tests 且接线 CI（**双达标延伸到组合层**，台账并入 G32）；组合件可测扇入，装配关系可审计。`main.c` 只启动组合件，不直连原子件散件。代数不变：`F⊗F` 非法、面间只 `⊙`（铁律 7）。

**两条冻结律**：

- **引用律**：形态面**只引用公开头**；跨面调用必须经公开头，不得直接触碰他人私有头。
- **冻结律**：`.manifest` 一旦发布即**冻结**，变更须走版本递增，不得原地改语义。

**现状（0.1.18 末，17 户）**：

| 项 | 达标 | 说明 |
|----|------|------|
| `.manifest` | **0 / 17** | 全缺 |
| `main.c` ≤ 150 行 | **0 / 16** | 现 214 ~ 737 行（16 份，`scripts` 户为 CI 脚本集、无 `main.c`），**合计 7,825 行**（这 7,825 就是 S 通道的主要回收对象） |
| 唯一私有头 | **1 / 16** | 仅 `supervisor_d` 达标（`scripts` 户无 C 生产码，不计入） |

> **S 通道回收面公示（−20,000 口径）**：其中 `main.c` 收敛为**实测账**（7,825 → ≤2,400 = 16 户 × ≤150，回收 ≈5,425）；其余 ≈14,575（`svc.c` / `modules/` / 私有头样板与跨户胶水收敛）为**预算值非实测**——逐户按「生成 → diff → 替换」实测公示，S 通道总额以逐户实测累计为准。

### 2.5 组合代数：`⊗` 与 `⊙`

| 算子 | 时相 | 边界 | 类型 | 通道 |
|------|------|------|------|------|
| **`⊗` 装配** | 装配期 | 进程内 | `A×A→C/F`、`C×A→C/F` | 函数调用 |
| **`⊙` 编排** | 运行期 | 跨进程 | `F×F→F_sys` | **IPC / syscall（唯一通道）** |

**`⊗` 的五性质（装配合法性判定）**：

| 性质 | 内容 |
|------|------|
| 类型律 | `A×A→C/F`，`C×A→C/F` |
| **地位律** | **`F⊗F` 非法** —— 面不能与面装配（面之间只能 `⊙` 编排） |
| 闭合律 | 装配结果仍是 `C` 或 `F`，封闭在代数内 |
| 结合律 | `(a⊗b)⊗c = a⊗(b⊗c)` |
| 幂等律 | `x⊗x = x`（同件重复装配无额外语义） |

**为何 `F⊗F` 非法**：面是进程边界上的职责视图，**面与面的关系只能是运行期编排**；若允许面直接装配，就会退化为「一个大进程装下所有功能」，微核心架构即失效。**违反即 fail-closed 拒绝**（不是警告）。

### 2.6 纲领落地：策略数据化（机制与策略分离到极致）

本节是总纲领（§2 章首）的机制化落地：**分离不是口号，是四层结构与两条硬规**。

**分离四层**（自内向外）：

| 层 | 内容 | 形态 |
|----|------|------|
| L1 机制 | 不含任何策略的原子件 | 代码 |
| L2 契约 | 接口与数据结构 | 公开头 |
| L3 注入 | 策略经 `ops` 函数表 + `.manifest` 注入 | 数据 |
| L4 策略 | 具体决策（阈值、厂商、权重、规则） | 数据 / 生态层 |

**两条硬规**：

- **策略只经 `ops` 函数表 + `.manifest` 注入** —— 不得在机制件内 `#include` 具体策略、不得 `if (vendor == ...)`。
- **机制核零策略载荷** —— 机制核内出现厂商名、产品名、业务阈值即门禁失败。

**策略数据化收益**：策略变数据后，一类决策从「N 份代码」变成「1 个件 + N 份数据」，直接消灭 K 通道重复。

**策略剥离怎么做（四步，以 `if (vendor == …)` 为例）**：

| 步 | 动作 | 判据 |
|----|------|------|
| 1 | 定位载荷：`grep -rn "vendor\|阈值字面量" atoms/ daemons/` 得「策略点清单」（文件:行台账） | 清单逐条有归属 |
| 2 | 抽 `ops` 函数表：把每处 `if (vendor …)` 改写为 `ops->decide(ctx, input)`；`ops` 结构体定义在**公开头**（L2 契约层） | 机制件内 `grep vendor` 归零（G18） |
| 3 | 策略实现落 `.manifest` + 数据文件（阈值/权重/路由表进数据，不进代码）；生态层提供具体 `ops` 实现 | 机制核零厂商名/产品名/业务阈值（G19） |
| 4 | 回归：行为 golden 一致（R-8），不一致即回滚该步 | `|S₀∖S₁| = 0` |

`ops` 注入形态示例（示意，落地按各域公开头）：

```c
/* 契约层（公开头）：只含机制语义，不含任何策略 */
struct sched_policy_ops {
    int (*decide)(void *ctx, const struct sched_input *in);  /* 策略裁决点 */
};
/* 机制件：只见 ops 指针，不见厂商 */
int sched_submit(const struct sched_policy_ops *ops, void *ctx, ...);
```

### 2.7 结构规约：「`atoms` 怎么长」六条

只规约**结构**，**不规约域清单**（域清单由能力格决定，不由本规约锁定）：

| 条 | 规约 |
|----|------|
| 1 | 各模块 `src/` 内**按机制域分目录** |
| 2 | 公开头一律收进 `include/` |
| 3 | 私有头命名 `<域>_internal.h` |
| 4 | **跨域只走公开头**（不得引用他域 `_internal.h`） |
| 5 | 配套子库须登记理由（为何不复用既有件） |
| 6 | 枢纽头入度 ≤ 5（头被引超过 5 处即须拆分） |

> 与 daemons 侧「五件套」性质不同：五件套规约的是**装配期物理形态**，本规约规约的是**atoms 侧源码结构**。二者按不同名目使用，不得互称。

### 2.9 实证归因：llm.rpc 事件的格位解剖（2026-09-26 社区案例）

> **案例**：社区用户 `ubuntu` 主机运行 `think_d`，日志刷 17 次 `airy_ipc_connect: target not found, name=llm.rpc`（启动期 4 次 + 请求期 13 次），LLM 全程静默降级为启发式路径，且关停段日志时间戳（22:34:50）早于错误段（22:35:21）。本节以此为**活体解剖样本**——它同时发作了四个格位的病，是「任何一格缺件或缺扇入，系统就在那格上运行于不正常态」（§0.1）的实证。**本节全部落点为架构整改，禁止任何调用点补丁。**

**病因链（源码实证，七环）**：

| # | 现象 | 源码锚 | 机制解释 |
|---|------|--------|---------|
| 1 | `llm.rpc` 从何来 | `daemons/common/src/daemon/daemon_l2_bridge.c:583-599` | `<ns>.sock` 基名派生 `<ns>.rpc`；灰度策略（Blueprint 8.3.3）先试 corekern L2 通道，`unserved` 回退 socket |
| 2 | 为何必然报错 | `atoms/corekern/src/ipc/binder_channel.c:140-152,175-191` | binder 通道是**进程内**注册表（`binder_root_nodes` 链表）；纯 Linux 主机跨进程查 `llm.rpc` 必空（llm_d 未运行于本进程），`airy_ipc_connect` 记 **ERROR** 返回 `AIRY_ENOENT` |
| 3 | 回退为何无声 | `daemons/common/src/daemon/daemon_rpc_client.c:446` | 真正的回退决策只记 **DEBUG**（`L2 channel unserved - socket fallback`）——**级别倒置**：预期内回退触发 = ERROR，回退决策 = DEBUG |
| 4 | 4 次/13 次从何来 | `atoms/coreloopthree/src/lang_gateway/calibrator.c:457-464` | **不是重试循环**——单模型校准做 4 次 `count_tokens`（中英双样本 ×2），每样本 1 次 `rpc_call` = 1 次 connect；请求期 13 次 = 思考链 13 次真实 LLM 调用。**每次调用都重新发现、无负缓存、无熔断前置** |
| 5 | 为何静默降级 | 日志 `total_svcs=1`（SD 仅 think_d 自身）＋ orchestrator 照常 ready | llm_d 未运行，但 orchestrator 以 breaker=on、lang_gw=enabled「成功」启动——**硬依赖缺失软着陆**，无降级态显式上报 |
| 6 | 健康检查假阳性 | `atoms/coreloopthree/src/cognition/think/adapter/llm_svc_adapter.c:424` | `is_connected` = `access(socket, F_OK)`——只查 socket **文件存在**（僵尸文件即误报），不查服务可达，且不覆盖 binder 通道路径 |
| 7 | 时间线为何倒置 | `daemons/common/include/daemon_main.h:92`（SIG 行裸写无时间戳）＋ 全日志 wall 单时钟 | NTP step 回拨 ~31s → wall 时间戳乱序；信号处理器裸字符串写，无时间戳无 monotonic 配对 |

**缺陷 → 格位归因 → 系统性落点（无一为调用点补丁）**：

| 缺陷 | 归属格 | 补丁式修法（**禁止**） | 架构式落点（本方案） |
|------|--------|----------------------|---------------------|
| 级别倒置（#2/#3） | 记录 + 通知 | 在 binder_channel.c 改日志级别 | 记录格母件立**定级原则**：预期内回退 = 首次 INFO/后续 DEBUG，仅「全路径失败」= ERROR；错误载荷带 cause + remedy（可行动性契约，CLI 侧落 §5.6 #12 `diag::VocabIncident`，TUI 错误卡片为消费端） |
| 每调用重新发现（#4） | 韧性 + 发现 | 在 llm_svc_adapter 加 static 缓存 | 韧性母件内置**发现负缓存 + 熔断前置**：不可达即 open，后续调用直走降级不重复探测；恢复探测由 half-open 驱动——与 retry 252 处/72 文件塌缩同场（§2.8 韧性行、§3.3 第 5 类） |
| 传输选择混入调用路径（#1） | 通信 + 纲领 | 在 daemon_rpc_call 加 if 判断 | **传输选择前置为 init 期策略决策**（§2.6 L3 注入层）：能力探测/`.manifest` 声明一次定型，调用路径只消费已定型通道，**零 try-fail-fallback**；灰度开关（`daemon_l1_transport_enabled`）保留为定型输入之一 |
| 硬依赖软着陆（#5） | 通知 + 治理面 | 在 orchestrator 加一行 WARN | 依赖声明进 `.manifest`（`required`/`optional` 数据化）；启动期依赖检查 = governance 面职责：required 缺失 → **降级态显式上报**（health/badge/事件外发），禁止静默 ready |
| 健康假阳性（#6） | 发现 | 换成 connect 探测 | 发现格母件统一定义**健康 = 端到端可达**（SD 健康态消费），禁文件存在性冒充健康 |
| 时间源缺位（#7） | 记录 | 给 SIG 行手工拼时间 | 记录格母件增 **wall+mono 配对时间戳**：排序/耗时按 mono，绝对时刻按 wall；SIG 经 async-signal-safe 缓冲带时间戳写入 |

**案例结论（验证与增量）**：

1. **验证**：四格病（发现/韧性/通知/记录）同时发作于一个用户可见故障——「格格双达标」判据不是形式审计，是故障预防的充分条件；本案例即「格上无母件、各处自建」的反面教材全集。
2. **增量原则（本节提炼，全方案适用）**：**路由不得由错误驱动**——错误日志是记录格的输出，不是通信格的控制流；凡「try→fail→log ERROR→fallback」路径，一律前置为 init 期定型 + 熔断前置。
3. **施工挂靠**：定级原则与可行动错误契约随 L4 `daemons/common` 消解落；负缓存/熔断前置随 L5 韧性母件塌缩落；`.manifest` 依赖声明随 L2/L4 manifest 体系落；wall+mono 随记录格整改落。G32 复测时，本案例七环逐环回归验证（复跑 think_d 无 llm_d 场景：0 ERROR、降级态显式、日志时序单调）。

#### 5.7.1 ZCode（`apps/zcode-cli/packages/tui`，OpenTUI + React 19，~13,350 行）

**① OpenTUI 渲染架构：帧驱动渲染器 + React reconciler 双层**

ZCode 用 `createCliRenderer({targetFps: 30, useMouse: true, exitSignals: [...]})` 创建帧驱动终端渲染器，再 `createRoot(renderer)` 把 React 组件树投影到 OpenTUI 的 box/text/scrollbox 布局树上；渲染循环、flexbox 布局、cell 级增量重绘都归 OpenTUI 引擎，ZCode 只编排生命周期（`tui.tsx:23-51`）：

```ts
const renderer = await createCliRenderer({
  targetFps: 30, useMouse: true,
  exitOnCtrlC: false,
  exitSignals: ["SIGINT","SIGTERM","SIGQUIT","SIGABRT","SIGHUP","SIGBREAK","SIGBUS"], // 剔除 SIGPIPE
});
const root = createRoot(renderer);
// FRAME 事件后才做慢初始化，首绘不被阻塞（tui.tsx:113-123）
renderer.once(CliRenderEvents.FRAME, initialize);
```

- **首帧即生命周期钩子**：慢初始化挂到首个 `FRAME` 事件之后（注释原文 "FRAME is emitted after native output. No runtime work can block the first paint"），启动期先渲染轻量 `TuiStartupScreen`。
- **引用不变 = 不重绘**：reducer 语义无变化返回原引用，React `setState` 自然跳过（`app-workflow-mirror.ts:56-68`）。
- **滚动视口裁剪**：`<scrollbox stickyScroll stickyStart:"bottom" viewportCulling: true>`（`app-transcript-components.tsx:42-73`）。

#### 5.7.2 minimax-code（`packages/tui`，TypeScript）

**① TuiStateStore：Redux 极简单向数据流（monoclock 单源）**

`TuiStateStore` 持不可变 `TuiState`，`dispatch(action)` → 纯函数 `reduceTuiState` → `{state, effects}`，副作用由 `TuiEffectRunner` 串行消化（`state/store.ts:7-52`）：

  this.state = transition.state;
  for (const listener of this.listeners) listener(this.state, action);

- **状态结构**：`connection{phase: disconnected|snapshotting|subscribed|reconciling|live, generation}`、`TuiSessionViewState{execution 四 Map、interactions、四个 revision 计数、closedQuestionnaireIds 幂等防重放}`（`state/model.ts:48-76`）。

→ **我们的落地**：`airy/tui::monoclock`——全屏由单一时钟驱动投影，状态单源 + 每类交互一个单调 revision + `expectedRevision` 门闩，原样采用。

**④ KeyedSerialExecutor（concurrency-gate 的原型）**

`acp/agent.ts` 内按 key 维护 **promise 尾链**实现 per-key 串行、跨 key 并发（`agent.ts:1911-1923`）：

```ts
const previous = tails.get(key);
tails.set(key, current);
try { await previous; return await task(controller.signal); }
finally { release(); if (tails.get(key) === current) tails.delete(key); }
```

- **准入闸有界**：`detached ≤2/键、≤32 总；admitted ≤64/键、≤256 总`，超限抛 `requestCancelled`（`agent.ts:1889-1907`）——**队列本身有界**。
- **取消不等于泄漏**：abort 时 detach 幽灵续跑 + 计数钳制，`reset` 断链自愈（`agent.ts:1974-1982`）。
- 四个执行器按操作类别隔离 key 冲突域（`agent.ts:88-91`）。

→ **我们的落地**：`airy/ipc::concurrency-gate` 落 **agentrt ipc 侧**（跨 daemon 并发闸），形态 = 尾链串行 + 准入预算 + reset 断链三件套。

**⑤ 帧界合并与 epoch 自愈（交互流九机制来源）**：delta 合帧（`queueTextDelta` 累积 → `flushTextDeltas` 一次落库，`store.ts:174-200`）+ 帧率闸（`requestRender` 16ms 节流，用户输入 `requestImmediateRender` 抢占，`tui.tsx:784-810`）；epoch 自愈 = 连接代际 `generation+1` → 每 session 发 `runtime/reconcileSession`（`reducer.ts:241-258`）+ 交互 revision CAS。→ 九机制「delta 帧界合并 / epoch 自愈 / 审批队列化 / 多 agent 面板防环 4 段」（`agent-team/model.ts` 的 `STATUS_PRIORITY` + 深度钳位 32）逐一对应。

#### 5.7.3 deepseek-harness（`packages/core|interaction|guard`，TypeScript）

**① Capability Folding（能力折叠）：折叠谓词只有一个家**

工具经 `ctx.tools.register` 声明，按 scope 链影子叠加 + 掩码交集求可见目录（`core/tools/src/index.ts:1152-1193`）；展示模式为 `code` 时整个目录折叠为单个 `run_code` 传输层，模型直调其他工具**确定性拒绝**：

```ts
private collapses(name, scope, nested): boolean {          // index.ts:1324-1326
  return !nested && this.modeFor(scope) === 'code' && name !== RUN_CODE_NAME
}
```

- **关键纪律**：折叠调用在**策略管线之前**终止（`index.ts:1373-1437`，注释 "approval ask, and guards must never observe — or worse, approve — a call that can only fail"）——审批永不对必败调用表态。
- **展开**：`run_code` 子派发带 `parent` token 旁路折叠（`!nested`），逐子调用落 `tool/code-dispatch` 事件可重建（`code-mode.ts:464-524`）。
- **fold 两段式**：`planSurfaceEvent` 先纯校验生成 `SurfacePlan`（seq 连续性 → 资格 → 区间 → 溯源 → tool/result 重写仅可改 content），再 `applySurfacePlan` 原子提交；增量与全量重放共享同一转移函数（`session/src/surface.ts:320-395`）。

→ **我们的落地**：`airy/cli::twogate`（双闸校验）承接「折叠/展开共用同一谓词 + 必败调用在策略前终结」；策略注入单通道（§2.6）与 capability seam（Service/Provider/Consumer 三角色）同构。

**② 审批 fold fail-closed（failclosed 的完整语义）**

`ApprovalPolicy = 'ask' | 'never'` 二值闭联集；**`'never'` 在派发任何 answerer 之前由服务自身裁决为 `'rejected'`**（`user-approval/src/index.ts:304-312`，注释明言不用 listener 做 gate——注册顺序可绕过）：

```ts
if (this.effectivePolicy(session) === 'never') return 'rejected'   // 先于一切派发
```

- **全路径 fail-closed 收敛**：无 answerer / 抛错 / 返回越界值 / 无 agent / 无审批服务，一律 `'unavailable'` 或 deny（`:317-329`；消费端 `core/tools/src/index.ts:1693-1728` 四种结果 `default: assertNever(outcome)`）。
- **未知策略双重点卡**：setter 抛 `TypeError`（`:142-147`）+ schema `z.union(['ask','never'])`（`:193-195`）。
- **审计对 fold 进事件流**：`approval/asked` → `decide()` → `approval/decided`，要求 turn 内闭合（`:257-275`，崩溃尾巴在 reload 时被 repair 清掉）；策略切换 `approval/policy` 事件 last-wins 折叠（`:112-118`）。
- **失败可区分**：deny 有不同原因（`'rejected'`=人说不、`'unavailable'`=渠道坏），但出口只有拒绝。

→ **我们的落地**：`airy/approval::failclosed` 的 `Policy::Never → 确定性 Rejected`；`airy/exit::StatusTable` 穷尽枚举（新增分支不更新表即编译失败）承接 `assertNever` 纪律。

**③ 一切有界 + headless settle 落账**

- **上限断言在契约边界**：`assertBudget(value)` 构造时 loud fail（`output-retention/src/index.ts:129-134`）；并发 `maxParallelSubCalls` 默认 10，非正整数即抛（`core/tools/src/index.ts:773-780`）；锁重试 `20ms → 200ms 指数退避 / 2s 总超时`，到期抛错而非猜测（`atomic-write/src/index.ts:77-79`）。
- **超时→结构化落账**：deadline 到期把结果替换为 `TOOL_TIMEOUT`（`guard/timeout-policy/src/index.ts:41-80`）。
- **headless settle**（`bundle/headless/src/index.ts:120-133`）：`whenIdle()` 等静默 → `sessions.flush()` 落盘屏障 → **从已落盘事件区间折叠**出输出与退出码（`turn/end completed → 0，否则 1`）——**退出码只从落盘账本派生**，与输出不可能分叉。
- **中断即补账**：崩溃恢复不删历史，追加确定性合成事件补齐开放边界——未启动调用补 `TOOL_NOT_STARTED`、结果未知补 `TOOL_OUTCOME_UNKNOWN`，再补 `step/end` + `turn/end{interrupted}`（`core/session/src/repair.ts:27-133`）；时间戳复用最后事件，**永不伪造未来时间**。

→ **我们的落地**：`airy/cli::headless`（超时仍 settle 落账）；`budget.rs` 全部有界；错误码表（`TOOL_TIMEOUT` 等结构化码 + `assertNever`）进 StatusTable。

**④ 单一真相源事件流（fold(events) 的理论根）**：`Session.log` append-only，`seq = log.length` 全局连续；`surfaceOp` 标记决定事件进不进模型可见面；**运行时断言「模型可见 ⟺ 已记录」**——`JSON.stringify(request.messages) === JSON.stringify(session.deriveMessages())` 不等即 fail（`agent-loop/src/invariant.ts:39-52`）。→ 我们的 `TUI 输出 = fold(CLI 事件流)` 等式与「streamProjected 标记防双写」（守卫共享 `streamProjected`）同源。
