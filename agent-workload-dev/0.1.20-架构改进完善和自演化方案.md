## 证据分级与计量纪律

| 级别 | 来源 | 可否作为性能/正确性结论 |
|------|------|------------------------|
| A 类 | 服务端逐请求计时（llama.cpp `print_timing`、`usage`）、逐轮原始 jsonl | 可 |
| B 类 | 驱动侧轮级累计（cum/delta）、容器与主机采样 | 仅可作端到端与资源趋势 |
| C 类 | 设计推演、类比、单点估算 | 不可，必须标注"待实机" |

**计量纪律（本方案新增硬约束，违反即判证据无效）**

1. 任何 `tok/s` 必须标注口径：`decode` / `prefill` / `aggregate`，未标注视为无效。
2. `aggregate = (prefill_tokens + decode_tokens) / wall_time`，只用于估算 token 目标完成时点，**禁止**作为推理性能对外表述。
3. 推理性能判定一律取服务端逐请求 `eval time` 的 p50/p95/max，样本数 ≥100 且覆盖完整时段。
4. 失败轮必须区分"业务失败（fail-closed）"与"驱动截断伪影"，后者不得计入成功率分母。
5. 成功率必须注明分母定义（是否含截断轮、是否含驱动重试轮）。

> 纪律来源：本轮曾以 112.8 tok/s 的 aggregate 口径表述性能，实为 prefill 主导；纠正后 7B decode p50=39.55 tok/s。该错误已固化为项目记忆，本方案将其上升为文档级约束。

## §0 结论先行

### 0.1 一句话结论

0.1.19 构建的机制底座（递归互斥量、定长会话池、fail-closed、确定性四验骨架）已被 **8 小时 368 轮 / 325.97 万 token** 实机验证证明可用且稳定，零崩溃、零挂起、零资源泄漏。0.1.20 的主要矛盾已从"会不会挂死"转移为三类工程债：

## §1 定位、边界与非目标

### 1.1 定位

agentrt 是 AirymaxRT 的**本地/云混合智能运行时底座**：以 C 守护进程集群承载模型服务、网关、调度、工具、记忆、认知循环，向上暴露统一 RPC/HTTP、向下托管本地推理引擎（llama.cpp 为首选，Ollama 为兼容）。0.1.20 的目标不是重写，而是在已验证的机制底座上补齐**正确性契约、计量诚信、可观测性与自演化闭环**。

### 1.2 能力归属边界

| 能力 | 归属层 | 备注 |
|------|--------|------|
| 模型进程生命周期 | `daemons/llm_d` | 容器/SYCL 由环境层负责 |
| 协议入口（OpenAI/A2A/MCP） | `daemons/gateway_d` + `products/gateway_biz` | 入口须统一消息规范化 |
| 计划生成与批判 | `products/cognition`（grad） | A 生成 / B 审查 / C 四验 |
| 认知编排 | `atoms/coreloopthree` | 执行器、GCCP、意图 |
| 记忆 | `products/memoryrovol` | 0.1.20 不扩范围 |
| 策略与生态 | `ecosystem` | agents/markets/prompts/skills |
| 自演化 | 新增 `evolve` 能力面 | 见 §7 |

### 1.3 非目标

1. 不重写守护进程框架，不改已通过的递归互斥与 fail-closed 结构。
2. 不在本版本引入 vLLM（归 0.1.21 GPU 服务）。
3. 不做跨模型并发推理（实测跌至 11~12 tok/s，红线）。
4. 不以"演示/桩实现"充数，任何未闭环能力不得进入验收。
5. 不扩大 UKUI/GUI 范围（属 OS 方案，单独评审）。
6. 不把自演化体量并入功能体积账。
7. 不在本版本改变记忆引擎数据模型。

### 2.4 性能权威口径（llama.cpp 服务端逐请求，3620+ 请求）

| 模型 | 角色 | decode p50 | decode max | prefill p50 | prefill max |
|------|------|-----------|-----------|-------------|-------------|
| airy-7b | s2 / expert | **39.55 tok/s** | **40.98 tok/s** | 1054 tok/s | 1231 tok/s |
| qwen9b | verify | **34.39 tok/s** | 34.61 tok/s | 675 tok/s | — |

**口径拆解与纪律**

```
aggregate 112.8 tok/s
  = (prefill_tokens + decode_tokens) / wall_time
decode 占 token 总量约 31.1%  →  112.8 × 31.1% ≈ 35 tok/s
```
实测 decode p50 39.55 与 5h 纯补全 37.2 吻合；aggregate 不得作为推理性能。

**热漂移**：7B decode p95=40.38 与 max=40.98 差 <1.5 tok/s，8 小时零降频。尾部 2.5%（25–27 tok/s）对应 prompt cache 淘汰与 slot 切换瞬时争用，非持续劣化。

**端到端**：`AIRY_PERF_MODE=lightweight` 折叠前置非流式调用后，端到端 ≥40 tok/s 具备落地条件（A 类口径验证 p50 39.55）。

### 2.5 稳定性与资源

- 递归互斥量 + 定长会话池（64 会话 / 30min TTL / LRU）+ 迭代上界 3，经 596 轮累计验证无死锁、无泄漏；
- 采样 20s 粒度：mem_avail 全程 ≥11.1GB，load1 稳定在 1.0 附近；
- 双实例竞态已通过 `start_think.sh` 等待复活 12s 加固，但根因（supervisor 与自启并存）仍在 P3 清单。

### 2.7 端云混合矩阵

| 组合 | 定义 | 结果 | 判定 |
|------|------|------|------|
| M1 | B 终裁走云 | 全被上游 400 拒绝 | 不可用 |
| M2 | A 生成走云 | 全被上游 400 拒绝 | 不可用 |
| M3 | 云断→端接管 | 25/25 成功，p50=72s | 可用，但降级无显式告警 |

**M1/M2 根因**：`messages` 数组含 `content:null`，上游返回 `400 "content" is null / assistant must provide content`，curl 已复现。代码事实：`llm_d/src/rpc/dispatch.c` 的 `fill_msg` 要求 `content` 为字符串（null 直接判 `AIRY_ERR_INVALID_PARAM`），`providers/core/envelope.c` 对空指针兜底为 `""`，而 `gateway_d/src/protocol/gateway_llm_api.c` 原样转发 raw `messages`。三条路径语义不一致，是同一非法输入在不同入口表现不同的直接原因。

### 2.8 实机证伪清单（8 条被推翻的设计假设）

1. "双模型并联必然更快" → 单模型同分、耗时 -28.4%；
2. "aggregate 吞吐可代表推理性能" → 含 prefill，高估 3.2 倍；
3. "9B 可作为本地主力" → 29–33 tok/s，低于 35 红线；
4. "E-05 只会在自造 seed 上误触发" → 生产 A 生成计划同样触发；
5. "B 终裁可见计划" → B prompt 仅含 goal/report/节点数/guards；
6. "云端失败会快速熔断" → GRAD 调用链无断路器，逐轮重试；
7. "配置改动可热生效" → 仅打印 `restart to apply`，必须重启；
8. "Ollama 与 llama.cpp 参数等价" → `keep_alive` 在 llama.cpp 被忽略。

### 3.1 P0（5 条）

#### P0-1 E-05 判据语义错配（"或"而非"且"）

- **现象**：368 轮中 12 轮 E-05 驳回；同时存在"只有 cost、无 inputs"的计划可零因果验证通过。
- **证据**：`products/cognition/src/grad/grad_verifier.c` 中 `grad_check_causal` 仅对 `inputs_count>0` 的节点累加检查数，`grad_check_resource` 对 `cost>0` 的节点累加，二者共用 `report->checked_nodes`；E-05 判定为 `checked_nodes == 0`。
- **根因**：因果检查与成本检查共用一个计数器，语义从"每个节点都被因果验证"退化为"每个节点至少有 inputs 或 cost"。
- **影响**：一边误杀（A 计划缺元数据 → 整轮失败），一边漏放（cost-only 计划 → 零因果验证通过）。
- **归属**：任务面 C5（判据拆分）+ P0-2（生成侧补齐）。

#### P0-2 计划元数据契约缺失（E-05 的结构性来源）

- **现象**：A 生成的计划大量只含 `id/goal/role/depends`，不含 `inputs/outputs/cost`。
- **证据**：`grad_llm_s2_plan.c` 的 A 提示词仅要求"Generate an initial skeleton plan JSON. Keep it minimal but logically sound."，示例中 `"inputs":[]` 可被逐节点复制；`grad_parse_plan_json` 对缺失 `inputs/outputs/cost_time_ms` **零校验、零归一化、零修复**，静默构建空壳节点。
- **根因**：生成侧无元数据契约，解析侧无 schema 校验与定向修复，校验侧只能以 E-05 兜底。
- **影响**：E-05 成为唯一结构性失败原因；驳回后全量重绘，进一步放大延迟。
- **归属**：任务面 C1 + C4（元数据补全器与定向修补）。

#### P0-3 B 盲审 + A 全量重绘（延迟主因）

- **现象**：单轮 p50 76s、p99 153s、max 203s；驳回一次额外约 90s。
- **证据**：`grad_coordinator.c:406` 在驳回后调用 `s2_plan(goal, patch, &new_plan, ...)` 生成**全量**新计划；`grad_llm_s1_arbiter.c` 的 B prompt 只含 `goal + report 摘要 + 节点数 + guard 列表`，**不含计划正文**。
- **根因**：B 无法基于计划内容裁决（只能看统计摘要），A 无法增量修补（只能整份重画）。
- **影响**：驳回成本 ≈ 一次完整生成；B 的语义裁决（含 E-04）失去事实依据。
- **归属**：任务面 C2 + C6。

#### P0-4 超时体系与真实延迟不匹配

- **现象**：B50 观测到约 117s 后返回 `-32603`；实测单轮 p50 76s、p99 153s。
- **证据**：`daemons/common/src/daemon/daemon_rpc_client.c:48` `DAEMON_RPC_DEFAULT_TIMEOUT_MS 30000`；`gateway_d/src/svc.c` http 30s / a2a 60s / mcp 30s。
- **根因**：超时按"通用 RPC"设定，未按方法语义分档（模型生成、GRAD 审查、工具调用、健康检查差异巨大）。
- **影响**：任何走默认超时的同步调用在真实负载下必然超时；表现为"服务不可达"，误导排查。
- **归属**：任务面 D2。

#### P0-5 配置变更不可见、不可热生效

- **现象**：修改 `model.yaml` 后必须重启 `llm_d/gateway_d/think_d`，否则静默使用旧配置。
- **证据**：`daemons/common/src/svc/svc_model_watch.c:108-112` 检测到变更仅打印 `restart to apply`，无结构化事件、无 CLI/TUI 告警、无 SIGHUP 重载。
- **根因**：变更感知机制件已落地，但缺"通知—确认—重载"闭环。
- **影响**：用户误以为新配置生效，得到与配置不符的行为，属最高频运维陷阱。
- **归属**：任务面 D2（与 0.1.19 A2 缺陷承接）。

## §5 任务面 C：推理链强化（5.1K）

### 5.1 设计原则

1. **计划是契约，不是散文**：每个节点必须携带可校验元数据；
2. **审查必须看见事实**：B 必须拿到计划正文与摘要；
3. **驳回必须廉价**：只改被驳回的节点子集（Δk）；
4. **执行必须遵循 DAG**：声明即执行，不做"校验一套、执行一套"；
5. **门禁必须可复现**：温度 0、思考受控、判据确定；
6. **失败必须闭环**：fail-closed 同时产出可观测事件与定向补丁。

### 5.6 反向判断

以下情形表明推理链强化**未达目的**，应回退设计而非继续调参：

1. 补齐元数据后 E-05 仍 >2%，说明判据本身错误；
2. B 看见计划后驳回率不降反升，说明 B 能力不足或提示词失配；
3. Δk 修补后计划一致性检查频繁失败，说明节点间耦合被低估；
4. 确定性门禁后成功率下降 >3pp，说明原成功率依赖随机性；
5. 拓扑执行后出现新死锁，说明依赖图存在隐式环。

## §7 任务面 B：自演化（36–58K）

### 7.1 思想变化

自演化不再是"体积自演化"（删代码），而是**能力自演化**：在受控边界内自主修改目标函数、重写核心代码并自动上线。体积治理由 §8 的工程约束承担，不与演化账混同。

### 7.2 分层包络

| Tier | 范围 | 体积 | 触发条件 |
|------|------|------|----------|
| Tier 1 | 参数与提示词级（阈值、提示词、路由权重） | 8–12K | 默认开启 |
| Tier 2 | 模块级重写（单驱动 ≤2000 行） | 18–28K | 需门禁 + 金丝雀 |
| Tier 3 | 架构级（跨模块契约） | 10–18K | 需人工评审 + 双写回滚 |
| 合计 | | 36–58K | |

### 7.3 价值函数

```
V = w1·成功率 + w2·(1/延迟p95) + w3·(1/成本) + w4·稳定性 − w5·漂移
V0 = 1.0（以 8h 跑 96.47% / p95 112s / 零崩溃为基线）
```

### 7.4 门禁 K1-K6

| 编号 | 门禁 | 判据 |
|------|------|------|
| K1 | 正确性不回退 | 成功率 ≥基线，负向用例全绿 |
| K2 | 性能不回退 | decode p50 不低于基线 95% |
| K3 | 稳定性 | 8h 零崩溃、零挂起、资源漂移 ≤5% |
| K4 | 可回滚 | 一键回滚 ≤5min，且回滚后门禁全绿 |
| K5 | 可解释 | 变更必须携带目标函数差异与证据 |
| K6 | 边界 | 不得触碰 §6.7 红线与 §1.3 非目标 |

### 7.5 版本与时序防滚动抵消

- 每次演化生成独立版本号与 manifest；
- 金丝雀 10% → 50% → 100%，每级观察 ≥2h；
- 若两级间指标互相抵消（A 升 B 降），强制回滚并记录。

### 7.6 可回退与 kill switch

- 持久化件设字节边界；
- kill switch：环境变量 + 文件哨兵 + CLI 三通道；
- 触发后 30s 内停止一切自演化写入。

### 7.7 守恒公式

```
功能体积 = C(5.1K) + D必做(6.3K) + D4(0.9K) = 12.3K
必做口径 = 11.4K（不含 D4）
演化体积 = 36–58K（独立账，不并入功能体积）
```

三处口径（§10、§7.7、§11）必须一致，任何修订同步三处。

### 7.8 结论

自演化在 0.1.20 仅开放 Tier 1；Tier 2 需 C1-C8 与 D0-D3 全部验收后开启；Tier 3 不在本版本开放。

## §13 三问成文回答

### 13.1 能否在 0.1.20 达到 98% 成功率

**能，但有前提**：E-05 占失败轮 12/13，只要 C1+C4+C5 落地，理论失败上限降至 1/368 ≈0.27%；即便补全器有 30% 失效，成功率仍 ≥98.3%。前提是 C4 的 inferred 来源被 C5 正确区分，不得把"补出来的元数据"当作"真实元数据"通过因果检查。

### 13.2 双模型是否会拖慢系统

**会，但角色不可取消**：B50 A1 实测同角色双份加载使耗时 +28.4%，故"同角色不得重复加载"（P3-4）；但 A 生成与 B 审查是两个语义角色，取消 B 等于取消门禁。正确做法是让驳回变便宜（C6），而不是让审查缺席。

### 13.3 自演化是否会失控

**在 Tier 1 不会**：Tier 1 只改参数与提示词，受 K1-K6 与 kill switch 双重约束；Tier 2 需全部门禁绿后开启；Tier 3 本版本不开放。风险不在"改代码"，而在"改了但指标互相抵消"，故 §7.5 强制金丝雀分级与抵消回滚。

### 13.4 六准则（保留）

1. 先证伪，后证实；
2. 单点不成结论；
3. 口径先于数字；
4. 失败必须干净；
5. 契约先于实现；
6. 回滚先于上线。

### 13.5 反向判断（保留）

见 §5.6；另加：若 8h 复测成功率不升反降，第一嫌疑是 C4 补全质量，而非模型能力。
