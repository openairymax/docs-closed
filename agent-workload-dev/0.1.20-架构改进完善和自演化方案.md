## 证据分级与计量纪律

| 级别 | 来源 | 可否作为性能/正确性结论 |
|------|------|------------------------|
| A 类 | 服务端逐请求计时（llama.cpp `print_timing`、`usage`）、逐轮原始 jsonl | 可 |
| B 类 | 驱动侧轮级累计（cum/delta）、容器与主机采样 | 仅可作端到端与资源趋势 |
| C 类 | 设计推演、类比、单点估算 | 不可，必须标注"待实机" |

**计量纪律（本方案新增硬约束，违反即判证据无效）**

1. 任何 `tok/s` 必须标注口径：`decode` / `prefill` / `aggregate`，未标注视为无效。
2. `aggregate = (prefill_tokens + decode_tokens) / wall_time`，只用于估算 token 目标完成时点，**禁止**作为推理性能对外表述。
3. 推理性能判定一律取服务端逐请求 `eval time` 的 p50/p95/max，样本数 ≥100 且覆盖完整时段。
4. 失败轮必须区分"业务失败（fail-closed）"与"驱动截断伪影"，后者不得计入成功率分母。
5. 成功率必须注明分母定义（是否含截断轮、是否含驱动重试轮）。

> 纪律来源：本轮曾以 112.8 tok/s 的 aggregate 口径表述性能，实为 prefill 主导；纠正后 7B decode p50=39.55 tok/s。该错误已固化为项目记忆，本方案将其上升为文档级约束。

## §0 结论先行

### 0.1 一句话结论

0.1.19 构建的机制底座（递归互斥量、定长会话池、fail-closed、确定性四验骨架）已被 **8 小时 368 轮 / 325.97 万 token** 实机验证证明可用且稳定，零崩溃、零挂起、零资源泄漏。0.1.20 的主要矛盾已从"会不会挂死"转移为四类工程债：

1. **计划元数据契约缺失** —— E-05 占失败轮 12/13，是唯一结构性正确性缺口；
2. **驳回成本过高** —— B 盲审 + 全量重绘 + patch 无信息量，单轮 p50=76s、p99=153s、max=203s；
3. **计量与可观测缺口** —— 缓存命中、上游错误体、e04/e05 计数不可得，评测被迫脱离产品面抓取日志；
4. **执行层无失败语义（r3 新增）** —— 工具失败仅告警、分发无返回值、收尾无条件记成功。**这一条直接决定 96.47% 的适用范围**：该数字只证明"GRAD 门禁能拦住坏计划"，不证明"通过门禁的计划能正确执行"。0.1.20 起所有成功率表述必须注明分母与判定层（见 §2.6、§9.4）。

## §1 定位、边界与非目标

### 1.1 定位

agentrt 是 AirymaxRT 的**本地/云混合智能运行时底座**：以 C 守护进程集群承载模型服务、网关、调度、工具、记忆、认知循环，向上暴露统一 RPC/HTTP、向下托管本地推理引擎（llama.cpp 为首选，Ollama 为兼容）。0.1.20 的目标不是重写，而是在已验证的机制底座上补齐**正确性契约、计量诚信、可观测性与自演化闭环**。

### 1.2 能力归属边界

| 能力 | 归属层 | 备注 |
|------|--------|------|
| 模型进程生命周期 | `daemons/llm_d` | 容器/SYCL 由环境层负责 |
| 协议入口（OpenAI/A2A/MCP） | `daemons/gateway_d` + `products/gateway_biz` | 入口须统一消息规范化 |
| 计划生成与批判 | `products/cognition`（grad） | A 生成 / B 审查 / C 四验 |
| 认知编排 | `atoms/coreloopthree` | 执行器、GCCP、意图 |
| 记忆 | `products/memoryrovol` | 0.1.20 不扩范围 |
| 策略与生态 | `ecosystem` | agents/markets/prompts/skills |
| 自演化 | 新增 `evolve` 能力面 | 见 §7 |

### 1.3 非目标

1. 不重写守护进程框架，不改已通过的递归互斥与 fail-closed 结构。
2. 不在本版本引入 vLLM（归 0.1.21 GPU 服务）。
3. 不做跨模型并发推理（实测跌至 11~12 tok/s，红线）。
4. 不以"演示/桩实现"充数，任何未闭环能力不得进入验收。
5. 不扩大 UKUI/GUI 范围（属 OS 方案，单独评审）。
6. 不把自演化体量并入功能体积账。
7. 不在本版本改变记忆引擎数据模型。

### 2.4 性能权威口径（llama.cpp 服务端逐请求，3620+ 请求）

| 模型 | 角色 | decode p50 | decode max | prefill p50 | prefill max |
|------|------|-----------|-----------|-------------|-------------|

| qwen9b | verify | **34.39 tok/s** | 34.61 tok/s | 675 tok/s | — |

**口径拆解与纪律**

```
aggregate 112.8 tok/s
  = (prefill_tokens + decode_tokens) / wall_time
decode 占 token 总量约 31.1%  →  112.8 × 31.1% ≈ 35 tok/s
```
实测 decode p50 39.55 与 5h 纯补全 37.2 吻合；aggregate 不得作为推理性能。

**热漂移**：7B decode p95=40.38 与 max=40.98 差 <1.5 tok/s，8 小时零降频。尾部 2.5%（25–27 tok/s）对应 prompt cache 淘汰与 slot 切换瞬时争用，非持续劣化。

**端到端**：`AIRY_PERF_MODE=lightweight` 折叠前置非流式调用后，端到端 ≥40 tok/s 具备落地条件（A 类口径验证 p50 39.55）。

### 3.1 P0（8 条，r4 新增 P0-7/P0-8）

> 本节每条按"现象 → 证据链 → 根因链 → 影响 → 修复设计（字段/函数/判据）→ 负向用例"六段式书写。**凡未给出可施工判据的条目，不得进入 P0**。

#### P0-1 E-05 判据语义错配（"或"而非"且"）

- **现象**：368 轮中 12 轮 E-05 驳回；同时存在"只有 cost、无 inputs"的计划零因果验证通过。
- **证据链**：
  1. `checked_nodes` 全仓**仅两处累加**：`grad_verifier.c:302`（E-01 数据依赖检查，`report->checked_nodes++`）、`:367`（E-03 资源检查，`report->checked_nodes += costed_nodes`）；
  2. 唯一读取点 `:555`：`plan->task_plan_node_count > 0 && report->checked_nodes == 0` → `E05_VERIFY_INSUFFICIENT`；
  3. E-04 分支 `:496-499` 只做 `report->invariant_guards++`，从不计数（`grad_verifier.h:59-63` 注释声明这是"有意为之"）；
  4. 五条判据在 `:543-561` 为短路"或"关系，任一命中即 `return AIRY_SUCCESS`（错误码放 `report->error`），后续判据不再计算。
- **根因链**：因果检查与资源检查共用单一整数计数器 → 计数语义从"节点通过因果验证"退化为"节点至少有 inputs 或 cost" → E-05 无法区分"未验证"与"无需验证" → 一边误杀（A 输出缺元数据）、一边漏放（cost-only 计划）。
- **影响**：E-05 占失败轮 92%（12/13），是唯一结构性正确性缺口；同时构成一个未被度量的放行通道。
- **修复设计**：
  - `grad_report_t` 拆分三字段：`uint32_t causal_checked; uint32_t cost_checked; uint32_t metadata_ok;`（保留 `checked_nodes` 作为 `causal_checked` 的只读别名一个版本，避免下游一次性改造）；
  - E-01 分支累加 `causal_checked++`（每个 inputs 非空且被前驱满足的节点），E-03 累加 `cost_checked += costed_nodes`，C4 归一化后累加 `metadata_ok++`（`metadata_source != absent`）；
  - E-05 新判据：`node_count > 0 && (causal_checked < node_count || metadata_ok < node_count)`，`affected_node` 取首个未覆盖节点 id（不再恒为 `"all"`）；
  - 判据关系由短路"或"改为**逐项求值后汇总**：五条判据全部计算，`report->errors[]` 按 `[E-01..E-05]` 位图上报，首个错误仍作为主错误码，避免"修好 E-01 就看不到 E-03"。
- **负向用例**：①cost-only 计划（有 cost、无 inputs）必须 E-05；②空壳计划（仅 id/goal/role）必须同时命中 E-01 与 E-05；③合法计划 `causal_checked == node_count` 且零错误。
- **归属**：C5（判据拆分）+ C1/C4（生成侧补齐）。

#### P0-2 计划元数据契约缺失（E-05 的结构性来源）

- **现象**：A 生成的计划大量只含 `id/goal/role/depends`，不含 `inputs/outputs/cost`。
- **证据链**：
  1. `grad_llm_s2_plan.c:76-87` **只有两支提示词**：`patch_json` 非空 → "Generate the FULL corrected plan JSON (all nodes, consistent with the patch)"；否则 → "Generate an initial skeleton plan JSON. Keep it minimal but logically sound."，示例中 `"inputs":[]` 可被逐节点照抄。**不存在独立的第三支**（r3 勘误）；
  2. `grad_parse_plan_json`（`:95-264`）仅 4 项硬校验：参数非空、`cJSON_Parse` 成功、`nodes` 为数组、`nodes` 长度 > 0；
  3. 节点级全部**静默降级**：`id/goal/role` 缺失 → 字段置 NULL；`depends/inputs/outputs` 非数组 → 静默跳过；`cost` 非 number → 静默 0；`timeout_ms` 缺失 → 30000；`priority` 缺失 → 150；`entry` 为空时只补**第一个**零依赖节点随后 `break`（`:224` 附近）；
  4. 解析失败走 `grad_fallback_plan()`（`:309-314`），生成 `plan_id="fallback_grad_plan"` 的单节点计划，与真实目标无关。
- **根因链**：提示词把"最小可用"当默认 → 解析器把"缺字段"当容错 → 校验器只能事后用 E-05 兜底 → 兜底又因 P0-1 语义错配而不可靠。三段各自"合理"，连起来即契约真空。
- **影响**：E-05 成为唯一结构性失败原因；fallback 计划掩盖解析失败，使失败原因不可归因。
- **修复设计**：
  - **schema v1 必填表**（`products/cognition/src/grad/plan_schema.h`，字段表见 §5.2b.1）：`id`(string,非空,唯一)、`goal`(string,非空)、`role`(enum)、`depends`(array\<id\>)、`inputs`(array\<string\>)、`outputs`(array\<string\>)、`cost`(number,>0)、`invariant_guard`(bool)；
  - 解析器签名改为 `airy_status_t grad_parse_plan_json(const char *json, airy_task_plan_t **out, grad_parse_err_t *err)`，`err` 携带 `{node_index, node_id, field, reason}`，首个错误即返回 `AIRY_EINVAL`；
  - 禁止空壳：任一必填字段缺失 → 拒绝整份计划，**不允许**"部分节点可用即采纳"；
  - fallback 计划打标：`plan_origin=fallback` 且**不得进入执行**（由 C7 状态机与 G52 共同守门）；
  - 归一化器 `grad_normalize_plan()` 置于 parse 之后、verify 之前，仅补"可推导"字段并写 `metadata_source`（规则见 §5.2b.2）。
- **负向用例**：①缺 `inputs` 的 5 节点计划必须整份拒绝并给出行级错误；②两节点同 `id` 必须拒绝；③`cost` 为字符串必须拒绝（不得静默转 0）；④`depends` 指向不存在 id 必须拒绝。
- **归属**：C1 + C4。

#### P0-3 B 盲审 + A 全量重绘 + patch 无信息量（延迟主因，r3 补第三环）

- **现象**：单轮 p50 76s、p99 153s、max 203s；驳回一次额外约 90s。
- **证据链**：
  1. `grad_coordinator.c:406` 驳回后调用 `s2_plan(goal, patch, &new_plan, ...)`，且 `plan_owned` 先释放旧计划 → **全量重绘**；
  2. `grad_llm_s1_arbiter.c:132-148` B 的 prompt 仅含 goal JSON、C 的 report JSON、节点总数、guard 节点 `id (goal)` 列表——**无 DAG 结构、无逐节点成本、无历史轮次**；
  3. `grad_coordinator.c:331-338` B 驳回后生成的 patch 是**固定模板**：`affected_scope: []`、`suggestion: "recheck task alignment"`——不含缺陷定位、缺失字段或节点范围；
  4. `grad_llm_s2_plan.c:80` 要求 patch 分支输出 "FULL corrected plan"，与"增量修补"的设计意图相反；`grad_internal.h:74-75` 注释却写"s2_plan 仅增量修补"（见 P2-10）。
- **根因链**：B 看不到事实 → 裁决只能基于统计摘要 → 驳回意见无法定位 → patch 退化为模板 → A 只能整份重画 → 单次驳回成本 ≈ 一次完整生成 → p99 由驳回次数线性放大。
- **影响**：延迟主因；同时使 E-04 语义裁决失去事实依据（P1-4）；C6 若无 patch 改造则为空转。
- **修复设计**：
  - **B 输入契约**（`grad_arbiter_input_t`）：`goal`、`plan_nodes[]`（id/goal/role/depends/inputs/outputs/cost/invariant_guard）、`c_report`（五项判据位图 + `affected_node`）、`round_history[]`（每轮 verdict/defect 码，最多 3 条）、`token_budget`；裁剪策略见 §5.2b.4；
  - **B 输出契约**（JSON，强校验）：`{verdict: "accept"|"reject", confidence: 0..1, e04: "pass"|"fail"|"unknown", defects: [{node_id, code: "E-01"|"E-02"|"E-03"|"E-04"|"E-05"|"SEM", evidence, suggestion}], affected_scope: [node_id...]}`；
  - **patch 生成改造**：协调器不再写死模板，改为由 `defects[]` 投影生成 `affected_scope`（去重、保序、必须 ⊆ 计划节点集）；`affected_scope` 为空或含非法 id → 判 `patch_invalid`，**降级为"仅采纳 C 判定"并允许收敛**，禁止据此触发全量重绘；
  - **A 提示词补第三支**（repair）：显式指令"只输出 `affected_scope` 内节点，其余节点原样回传";输出后由 C6 做一致性校验（未受影响节点字段级比对）。
- **负向用例**：①B 返回模板 patch（`affected_scope:[]`）→ 必须判 `patch_invalid` 且不触发重绘；②B 返回不存在的 node_id → 拒绝该 patch；③B 返回非 JSON → 降级"采纳 C"并计 `arbiter_degraded`；④Δk 修补后未受影响节点被改动 → 一致性校验失败并回退该轮。
- **归属**：C2 + C6（+ C7 状态标记）。

#### P0-4 全链路无超时预算、无取消（r3 升级）

- **现象**：B50 观测约 117s 后 `-32603`；实测单轮 p50 76s、p99 153s、max 203s。
- **证据链**：
  1. `airy_grad_launch_t`（`engine_process_grad.c:100-122`）字段仅有 complete 闭包、goal、input、model 槽、workspace、max_tokens、progress——**无超时、无取消句柄**；
  2. `grad_ops->run(&grad_launch, plan, &grad_out)` 为唯一调用点（`:129`），同步阻塞；
  3. `llm_request_config_t`（`llm_service_types.h:55-66`）**无 `timeout_ms` 字段**，单次 LLM 调用无 per-call 上限；
  4. 协调器 `:442-443` 只统计 `total_time_ns`，不判定；`:480-482` 仅在未收敛时返回 `AIRY_ETIMEDOUT`，与"耗时超限"无关；
  5. RPC 层 `daemon_rpc_client.c:48` 统一 30s，`:491-493`/`:566-567` 仅当 `timeout_ms == 0` 才取默认，**无按方法超时表**。
- **根因链**：预算缺失 → 每轮 3 次 LLM 调用（A/C/B）各自无上限 → 3 轮最坏上界 = 9 次调用之和且各项无界 → **上界不存在**。观测到的 203s 只是"这次恰好结束"，不是"被限制在 203s"。RPC 30s 只约束单次传输，无法约束多轮多调用。
- **影响**：尾部延迟不可控、不可预测；同步调用方按 30s 设定超时则必然误杀，按 203s 设定则故障时无限等待。
- **修复设计**：
  - `grad_budget_t {uint32_t total_ms; uint32_t per_round_ms; uint32_t max_total_tokens; uint32_t max_prompt_chars; uint64_t deadline_mono_ns;}`，随 `airy_grad_launch_t` 下发（附录 A 注记为结构体扩展，需 ABI 评审）；
  - 检查点三处：每轮开始前、每次 LLM 调用前、每次调用返回后；判据 `now_mono_ns() >= deadline_mono_ns` → 立即返回 `AIRY_ETIMEDOUT` 并写 `grad_budget_exceeded{phase: plan|verify|arbiter, round, elapsed_ms}`；
  - `llm_request_config_t` 增 `uint32_t timeout_ms`（0 = 继承 RPC 默认），由 GRAD 按剩余预算向下取 `min(remaining, per_call_cap)`；
  - `daemon_rpc_client` 增静态表 `rpc_timeout_for(method)`：`llm.chat` 120s、`grad.verify` 90s、`health.check` 5s、其余 30s；表项未命中回落默认值；
  - stats 增 `budget_exceeded_count`、`phase_timeout{plan,verify,arbiter}`、`elapsed_ms_p95`。
- **负向用例**：①单次 A 调用被注入 200s 延迟 → 应在 `per_round_ms` 内中止并 fail-closed，不得等到 203s;②总预算耗尽时第 3 轮不得启动；③取消后不得残留工作线程（线程 join + 计数归零可观测）。
- **归属**：D2（传输与超时）+ C7（预算状态）。

#### P0-5 配置变更不可见、不可热生效

- **现象**：修改 `model.yaml` 后必须重启 `llm_d/gateway_d/think_d`，否则静默使用旧配置。
- **证据链**：
  1. `svc_model_watch.c:90-105` 廉价路径比对 `size + mtime_sec + mtime_nsec`，再以 FNV-1a 64 哈希消解 touch 误报；
  2. `:107-119` 检测到 `drifted:` 仅首次（`w->warned`）打印 WARN "restart to apply" 并写 marker 文件；
  3. **无 inotify、无轮询线程、无定时器、无回调注册**；
  4. 调用时机在请求侧 `service_request.c:352-353`（`svc_mw_check`）——**空闲进程永不发现漂移**。
- **根因链**：感知靠请求触发 + 结论只有一行日志 + 无重载入口 = 变更"不可见、不可确认、不可生效"三缺。
- **影响**：用户以为新配置生效；实机排查中出现"配置与行为不符"的高频误判。
- **修复设计**：
  - `svc_mw` 增 `check_interval_ms`（默认 5000）与 `svc_mw_tick()`，由 supervisor 周期 tick 或独立轻线程驱动，**不依赖请求**；
  - 变更时发结构化事件 `config_drift{file, old_hash, new_hash, applied:false}`（复用 `hall_evt_write`），并置进程内 `drift_pending=1`；
  - 新增 `SIGHUP` → `svc_reload()`：先解析到临时结构 → 校验（schema/引用完整性）→ 原子指针切换；失败则保留旧配置并发 `config_reload_failed{file, reason}`；
  - 重载成功后发 `config_applied{file, hash, generation}`，`generation` 单调递增供外部对账。
- **负向用例**：①写入语法错误的 yaml → reload 失败、旧配置继续生效、必须产生 error 事件；②仅 `touch` 文件 → 哈希不变，不得产生 drift 事件；③两个进程同时收到 SIGHUP → 各自 generation 独立递增，不得互相覆盖。
- **归属**：D2（与 0.1.19 A2 缺陷承接）。

#### P0-6 执行层无失败语义（r3 新增，独立于 GRAD）

- **现象**：工具调用失败（HTTP 5xx、超时、参数错误）时，整轮仍以 `success` 结束并计入成功率。
- **证据链**：
  1. `engine_exec_tool`（`engine_process.c:188-233`）：`req.tool_id = node->task_node_handler_name`；`req.params_json = node->task_node_id ? node->task_node_id : node->task_node_goal`（**把节点 id 当参数 JSON**，见 P1-3）；`tool_err == 0 && result->success == 0` 才 `engine_tool_store`，否则只 `AIRY_LOG_WARN`，注释明写 "P1.3.3: 工具失败不阻断管线"，函数返回 0；
  2. `engine_dispatch`（`:236`）签名为 `static void`，`:257-265` 按下标顺序遍历，仅跳过 NULL 与空 `handler_name`；
  3. `engine_finalize`（`:428-454`）**无条件** `stats_success_count++` 并输出 `"status":"success"`；
  4. `engine_tool_store`（`:169-186`）把结果写入 `task_node_output`、工作内存、记忆提供者，但**全目录无下游消费者**（与 P1-3 同根）。
- **根因链**：`exec_tool` 吞掉错误 → `dispatch` 无返回值可聚合 → `finalize` 无输入可判定 → 状态恒 `success`。三段缺口串联后，"执行正确性"这一维度**在系统中不存在**。
- **影响（这是本轮最重要的结论）**：8h 368 轮的 96.47% 只度量"GRAD 是否放行"，不度量"放行后是否执行成功"；G46 的 13/13 只覆盖 GRAD 失败轮的干净退出。**两个数字都不能外推为端到端成功率**。任何对外成功率表述必须标注判定层（§9.4）。
- **修复设计**：
  - `engine_exec_tool` 返回 `airy_status_t`：`success != 0` → `AIRY_ETOOL`，并把 `result->error` 归一到 ErrorModel v1 `{class, code, diag}`；
  - `engine_dispatch` 改为 `airy_status_t engine_dispatch(engine_t *e, plan_t *p, const char **failed_node_id)`：按策略聚合，`failed_node_id` 指向首个失败节点；
  - `engine_finalize(engine_t *e, airy_status_t status)`：`status != AIRY_SUCCESS` → `stats_failure_count++`、输出 `"status":"failed"` + `"failed_node"`，并走 `process_fail` 统一清理链；
  - 策略字段 `tool_failure_policy ∈ {fail_fast, continue_marked}`（默认 `fail_fast`）；`continue_marked` 下该轮状态为 `partial`，**不计入 success**，事件带 `failed_nodes[]`；
  - stats 增 `nodes_ok / nodes_failed / partial_rounds / tool_error_class{}`。
- **负向用例**：①单节点工具返回 500 → 轮状态必须非 `success`；②3 节点计划第 2 节点失败 → `failed_node` 必须等于该 id；③`continue_marked` 下 3 节点全跑完但 1 失败 → 状态 `partial` 且不计 success；④工具成功但结果为空 → 不得判失败（区分"空结果"与"失败"，由 handler 语义决定）。
- **归属**：C9（新增）。

#### P0-7 双思考不覆盖失败路径（r4 新增，推翻"双思考"表述）

- **现象**：368 轮中 13 个失败轮，全部由 C 单方裁定后直接进入 patch 生成；**没有任何一轮出现"B 复核 C 的否定结论"**。即 B 的裁决只在"计划已被 C 判为通过"时发生。
- **证据链**：
  1. `grad_coordinator.c:255-284`：`if (report.error == AIRY_GRAD_OK) { if (coord->config.s1_arbiter) { ... } }`——`s1_arbiter` 整个调用被包在**成功分支**内，无 else 分支；
  2. `grad_llm_s1_arbiter.c:119-148`：B 的 prompt 只含 goal JSON、`Verification report: %s`（C 的 report JSON）、节点总数、guard 节点 `id (goal)` 列表——**没有计划节点内容、没有失败节点快照**；
  3. 同文件 `:160-163`：LLM 调用失败（`err != AIRY_SUCCESS || !verdict`）时直接 `return AIRY_SUCCESS`，B 自身故障静默降级为"无意见"，协调器无法区分"B 同意"与"B 没跑成"；
  4. `grad_coordinator.c:331-338`：驳回 patch 为固定模板（`affected_scope: []`、`suggestion: "recheck task alignment"`）。
- **根因链**：C 报错 → 跳过 B → 直接生成模板 patch → A 全量重绘。语义层在**最需要它的场景**（结构已崩、E-04 目的漂移最可能发生）完全缺席；E-04 因此在失败轮从未被评估过哪怕一次。
- **影响**：本文 r1-r3 一直使用的"双思考"表述**不成立**，实际是"单思考（A）+ 确定性校验（C）+ 成功路径复核（B）"。直接后果有三：①§13.1 的 V9/V10"双模型收益"结论只对成功路径成立，须加限定（见 §13.6）；②E-04 的实际守门率远低于设计预期（P1-4）；③失败轮的成本全部花在"重画"而非"定位"，是 P0-3 延迟结构的第三个乘数。
- **修复设计**：
  - 协调器在 C 报错后、生成 patch 前插入失败路径裁决点：`airy_err_t grad_arbiter_on_failure(const grad_goal_t *goal, const airy_task_plan_t *plan, const grad_report_t *report, grad_failure_verdict_t *out)`；
  - 输入契约 v2（见 §5.2b.11）：`goal` + `c_report`（五项判据位图 + `affected_node` + `errors[]`）+ `failed_node_snapshot`（仅失败节点及其**直接前驱/后继**，深度 1，避免整图膨胀）+ `round_history[]`（最多 3 条）；
  - 输出契约：`{verdict:"accept"|"reject", defect_class:"structural"|"semantic"|"both", salvageable:bool, affected_scope:[node_id...], suggestion:string}`；`salvageable=true` 时允许 A 走增量修补分支（与 P0-3 的 repair 分支共用），否则全量重绘；
  - 模式开关 `arbiter_on_failure ∈ {off, e04_only, full}`，**默认 `e04_only`**：仅当 C 的失败码含 E-04，或 E-01 且 `affected_node` 为 guard 节点时才调用 B——避免失败轮延迟无条件翻倍；
  - 预算硬约束：失败路径 B 调用必须落在 `per_round_ms` 内；预算不足 → 跳过并记 `arbiter_skipped_budget`，**回退为纯 C 判定**（fail-closed，不阻塞、不放行）；
  - stats 增 `arbiter_failure_calls`、`arbiter_failure_override`（B 推翻 C 的次数）、`arbiter_skipped_budget`、`arbiter_internal_error`（与"同意"区分）。
- **负向用例**：①注入 C=E-04 失败 → B 必须被调用一次且 verdict 落盘；②B 自身超时/返回非 JSON → 必须回退 C 判定、记 `arbiter_internal_error`，不得阻塞整轮；③B 返回 `salvageable=true` 但 `affected_scope` 为空 → 判 `patch_invalid` 并回退全量重绘；④`arbiter_on_failure=off` → 不得调用 B，且 `arbiter_failure_calls==0`；⑤失败路径 B 调用导致超预算 → 必须在 `per_round_ms` 内中止。
- **归属**：C13（新增）+ G56。

#### P0-8 门禁采样不可复现 + 输出完整性无判定（r4 新增，吸收 P1-6）

- **现象**：同一输入重复裁决结论不一致（J-09 的 `same_input_10x_agreement ≥ 9` 从未达成）；服务端提前断流或返回被截断内容时，整次调用仍被判为成功，截断结果直接进入校验。
- **证据链**：
  1. `grad_llm_call.c:25-64`：`llm_cfg.temperature = 0.2f; llm_cfg.top_p = 1.0f; llm_cfg.max_tokens` 默认 4096（实际由 `chain_max_tokens` 抬到 8192）、`llm_cfg.stream = 0`——**无 `seed`、无 `response_format`、无 `grammar`、无 per-call timeout**；
  2. `envelope.c:200-233`：请求体字段集固定为 `model / temperature / max_tokens / top_p / stream / stop`，上述四个字段在传输层**无处承载**；
  3. `sse.c:355-408`：`CURLE_OK` 且未收到 `[DONE]` 时仍 `return AIRY_OK`——提前断流不判失败；
  4. `toolstream.c:266-283`：`resp->finish_reason = acc->finish_reason ? acc->finish_reason : AIRY_STRDUP(LLM_FINISH_STOP)`——`finish_reason` 缺失被伪装为正常结束，`length` 截断与 `stop` 不可区分；
  5. 解析侧 `grad_parse_plan_json` 裸 `cJSON_Parse`，失败落 `grad_fallback_plan()`（P0-2 证据链第 4 条）。
- **根因链**：采样随机（temp=0.2、无 seed）→ 同输入不同输出 → 裁决不可复现 → 门禁判据（J-09、G42）失去判别力；传输层"收到字节即成功"→ 截断/断流内容进入校验 → 产生**随机归因的失败**（同代码同输入，这次 E-05、下次通过）。两条缺口叠加，使"改进前后对比"缺对照基线。
- **影响**：96.47% 基线无法复算；任何以"重跑通过"为验收依据的门禁都不可信；模型侧偶发截断被误记为计划质量问题，污染 E-01~E-05 分布统计（P1-5 修复后该污染会直接可见）。
- **修复设计**：
  - `llm_request_config_t` 增三字段：`uint32_t seed`（0 = 不指定；GRAD 路径固定 `0x47524144`）、`const char *grammar`（GBNF，nullable）、`uint8_t response_format`（`LLM_RF_TEXT` / `LLM_RF_JSON_OBJECT`）；
  - `envelope.c` 序列化补齐 `seed` / `response_format` / `grammar`，并对 `local` adapter 的 `num_ctx` 做能力位判断（见 §5.2b.8）；
  - GRAD 全路径固定 `temperature = 0.0f`（确定性判据必须贪心解码）；`top_p` 在 temp=0 下不参与采样，字段保留不再作为可调项；
  - 完整性判定（`sse.c` / `toolstream.c`）：`[DONE]` 缺失 → `AIRY_ESTREAM`；`finish_reason == "length"` → `AIRY_ETRUNC` 且 fail-closed；`finish_reason` 缺失 → `AIRY_EBADMSG`（**不再默认 `stop`**）；
  - 结构化输出统一入口 `grad_json_out()`：`cJSON_Parse` + schema v1 校验，失败 `AIRY_EBADMSG`，**禁止**落 fallback 计划（与 P0-2 的 fallback 打标互为表里）。
- **负向用例**：①同一计划连跑 10 次 → `verdict + defect_code 序列` 必须 10/10 一致（G57）；②服务端在第 5 个 delta 后断连 → 必须 `AIRY_ESTREAM`，不得进入校验；③`finish_reason:"length"` → 必须判失败并计 `truncated_count`；④缺 `finish_reason` → 必须 `AIRY_EBADMSG`；⑤返回非法 JSON → 必须 `AIRY_EBADMSG` 且不生成 fallback 计划；⑥`seed` 相同的两次请求 → 请求体必须字节级一致（G57 的辅助断言）。
- **归属**：C11（新增）+ C3 + D2-9 + G57/G59。

## §5 任务面 C：推理链强化（6.8K）

### 5.1 设计原则

1. **计划是契约，不是散文**：每个节点必须携带可校验元数据；
2. **审查必须看见事实**：B 必须拿到计划正文与摘要；
3. **驳回必须廉价**：只改被驳回的节点子集（Δk）；
4. **执行必须遵循 DAG**：声明即执行，不做"校验一套、执行一套"；
5. **门禁必须可复现**：温度 0、思考受控、判据确定；
6. **失败必须闭环**：fail-closed 同时产出可观测事件与定向补丁；
7. **（r3 新增）执行必须能失败**：`exec_tool` 的错误必须能上浮到轮状态，否则前六条全部只作用于"计划是否被放行"，而非"任务是否完成"。
8. **（r4 新增）审查必须覆盖失败路径**：只复核成功结论的审查，等于没有审查——失败轮必须有一个语义裁决者，否则"驳回归因"全靠固定模板猜（P0-7）。
9. **（r4 新增）采样必须确定**：判据要能判别，输入到输出的映射必须可重放；`temp>0` 或 `seed` 缺失的路径**不得**用于门禁验收（P0-8）。
10. **（r4 新增）上下文与并发必须有预算**：模型容量、token 长度、在途请求数都是有限资源，无预算即意味着失败以"随机截断/随机超时"的形式出现，无法归因（P1-13/P1-14）。

#### 5.2b.2 元数据推导规则（C4 算法）

输入：通过 schema 校验的计划 + `role_baseline[]`（角色成本基线表）。输出：补全后的计划 + 每节点 `metadata_source ∈ {explicit, inferred, absent}`。

```
for node in topo_order(nodes):            # 拓扑序，保证前驱先算
    # 1) inputs 推导
    if node.inputs is empty and node.depends not empty:
        node.inputs = [ f"{p.id}.{node.outputs[0] or p.id+'.out'}" for p in node.depends ]
        mark(node, inferred)
    # 2) outputs 推导
    if node.outputs is empty:
        node.outputs = [ slug(node.goal)[:24] ]        # slug: 小写、非字母数字→'_'、去重后缀
        mark(node, inferred)
    # 3) cost 估算
    if node.cost is None:                              # 仅当 schema 放宽为可缺省时可达
        node.cost = role_baseline[node.role].fixed + role_baseline[node.role].per_kchar * len(node.goal)/1000
        mark(node, inferred)
    # 4) 递推一致性
    if node.depends and node.inputs and outputs_unresolved(node.inputs):
        reject(node, "inputs_unresolvable")
```

判据（用于 G33/G34 与 E-05）：

- **`metadata_source == absent` 的节点数必须为 0**，否则 E-05 fail；
- `inferred` 节点占比 >`GRAD_INFERRED_MAX_RATIO`(0.5) → 记 `metadata_inferred_high` 事件（不 fail，用于观察 A 输出质量趋势）；
- 推导**不得**改变 `explicit` 字段：一旦某字段用户/LLM 显式给出，推导器跳过他（防"补全覆盖真值"）；
- 推导完成后重算 `plan_digest`（E1），保证 digest 覆盖补全结果。

#### 5.2b.3 Δk 修补算法（C6）

前置：C2 的 B 输出已含 `defects[]`（`{node_id, code, evidence, suggestion}`）。

```
Δk_repair(plan, defects):
    scope = unique([d.node_id for d in defects if d.code in {E-01,E-03,E-04,E-05,SEM}])
    scope = closure(scope, plan, depth=1)          # 一阶闭包：受影响节点 + 其直接后继
    if scope is empty or not subset(scope, plan.ids):
        return {status: patch_invalid, fallback: accept_c_verdict}
    frozen = plan.nodes - scope
    patch  = {scope: scope, per_node: group(defects, by=node_id)}
    new_sub = A_repair(plan.goal, subplan(plan, scope), patch)   # 只请求 scope 内节点
    candidate = merge(plan, new_sub, frozen)                     # frozen 原样回填
    if not field_equal(candidate.frozen, plan.frozen):
        return {status: patch_inconsistent, rollback: true}      # 未受影响节点被改动
    if not validates_against_schema_v1(candidate):
        return {status: patch_invalid, rollback: true}
    return {status: repaired, plan: candidate}
```

判据：

- `scope` 上界 `GRAD_PATCH_MAX_NODES`(8) 或 `ceil(0.5 * node_count)`，取小者；超界 → 允许升为**整份重绘**，但必须打标 `repair_mode=full`（这是唯一允许 full 的路径，与 `grad_llm_s2_plan.c:80` 的默认行为区分开）；
- 未受影响节点的字段级比对必须**逐字段精确相等**（含 `timeout_ms`/`priority`），不做语义等价；
- 一致性失败**不得**重试修补（避免"修补再修补"叠加），直接记 `patch_inconsistent` 并允许下一次完整生成。

#### 5.2b.4 B 摘要裁剪策略（C2）

B 的 prompt 预算 `GRAD_ARBITER_PROMPT_MAX_CHARS`(默认 12000)。装配顺序与降级顺序（先保事实，后保上下文）：

| 优先级 | 片段 | 超预算时处置 |
|--------|------|--------------|
| 1 | `goal`（用户目标原文） | 不裁剪；超长则截断到 4000 字符并标 `goal_truncated` |
| 2 | `c_report`（五项判据位图 + `affected_node`） | 不裁剪 |
| 3 | 被驳回节点的全文（`id/goal/role/depends/inputs/outputs/cost/guard`） | 不裁剪（通常 ≤8 节点） |
| 4 | 其余节点摘要（仅 `id, role, depends`） | 按 `priority` 降序逐条丢弃，丢弃计数写 `nodes_omitted` |
| 5 | `round_history[]`（最多 3 条 verdict/defect 码） | 保留最近 1 条 |
| 6 | guard 节点 `id (goal)` 列表 | 与第 3 项合并去重 |

输出契约强校验：`verdict` ∈ `{accept,reject}`、`confidence` ∈ [0,1]、`defects[]` 每项 `code` 必须在枚举内且 `node_id` 必须存在于计划；`e04` ∈ `{pass,fail,unknown}`。任一项不合规 → `arbiter_parse_error`，按 P0-3 负向用例③降级为"采纳 C 判定"，**不得**把非法 JSON 当作 accept。

#### 5.2b.5 预算与取消（P0-4 落地）

```c
typedef struct {
    uint32_t total_ms;          /* 默认 180000，可配 */
    uint32_t per_round_ms;      /* 默认 60000 */
    uint32_t per_call_ms;       /* 默认 90000，作单次 LLM 上限 */
    uint32_t max_total_tokens;  /* 默认 120000（A+B+C 合计） */
    uint32_t max_prompt_chars;  /* 默认 48000 */
    uint64_t deadline_mono_ns;  /* 进入 GRAD 时一次性计算 */
    uint8_t  cancel_flag;       /* 原子；外部置 1 即中止 */
} grad_budget_t;
```

检查点（三处，缺一不可）：

| 检查点 | 位置 | 判据 | 处置 |
|--------|------|------|------|
| CP-1 | 每轮开始前（`grad_coordinator.c` 循环头） | `now >= deadline` 或 `rounds >= max_iterations` | 返回 `AIRY_ETIMEDOUT`，写 `grad_budget_exceeded{phase:"round", round}` |
| CP-2 | 每次 LLM 调用前 | `remaining = deadline - now <= 0` 或 `tokens_used >= max_total_tokens` | 不发起调用，直接 fail-closed |
| CP-3 | 每次调用返回后 | 更新 `tokens_used`；`elapsed > per_round_ms` | 终止本轮，记 `phase_timeout{plan\|verify\|arbiter}` |

取消语义：`cancel_flag` 由 RPC 侧断开连接时置位；`grad_ops->run` 必须在每个等待点轮询该标志（LLM 调用阻塞在 `daemon_rpc_call` 时，靠 `timeout_ms = min(remaining, per_call_ms)` 做到"最迟在该点返回"）。**禁止**在未实现轮询前声称"支持取消"。

`rpc_timeout_for(method)` 静态表（D2 落地）：`llm.chat`=120s、`grad.verify`=90s、`grad.s2_plan`=120s、`health.check`=5s、`model.load`=300s、其余 30s。调用方显式传入的 `timeout_ms` 非 0 时优先。

#### 5.2b.6 拓扑执行与失败聚合（C8 + C9 合并语义）

```c
airy_status_t engine_dispatch(engine_t *e, plan_t *p, const char **failed_node_id);
```

算法：

```
indeg = count_deps(p); ready = [n for n if indeg==0]
if ready empty and p.nodes not empty: return AIRY_ECYCLE      # 环
while ready not empty:
    n = pop_by_priority(ready)
    rc = engine_exec_tool(e, n)                                # 现在返回 airy_status_t
    if rc != AIRY_SUCCESS:
        stats.nodes_failed++
        if policy == fail_fast:
            *failed_node_id = n.id
            return rc
        else:
            mark(n, failed); continue                          # continue_marked
    stats.nodes_ok++
    inject_outputs(n, p)                                       # n.outputs → 后继 inputs
    for s in successors(n): if --indeg[s]==0: ready.push(s)
return (stats.nodes_failed > 0) ? AIRY_EPARTIAL : AIRY_SUCCESS
```

聚合判据：

| 轮状态 | 条件 | 计 success | 输出字段 |
|--------|------|-----------|----------|
| `success` | `nodes_failed == 0` 且无环 | 是 | `status:"success"` |
| `partial` | `policy=continue_marked` 且 `nodes_failed > 0` | **否** | `status:"partial"`, `failed_nodes[]` |
| `failed` | `policy=fail_fast` 且首错 | 否 | `status:"failed"`, `failed_node`, `error_class` |
| `cycle` | 环检测 | 否 | `status:"failed"`, `reason:"cycle"` |

`inject_outputs` 的确定性规则：以 `n.id + "." + out_name` 为键写入轮级 KV；下游 `inputs` 中匹配该键者取值。**键缺失不得静默为空字符串**——必须返回 `AIRY_EINPUT`（这是 P1-3 "上游 outputs 不进入下游 inputs" 的判据）。

#### 5.2b.9 上下文预算与裁剪算法（C12）

**可用上下文的确定顺序**（前者缺失取后者，全缺取保守默认）：

```
n_ctx_effective = first_nonzero( model.yaml: n_ctx,              // 部署侧显式值（新增字段）
                                 ep.context_window,              // 现有字段，r4 起被真正读取
                                 4096 )                          // 保守默认，并置 ctx_unknown=1
reserve_completion = min(max_tokens, n_ctx_effective / 4)        // 生成侧预留，不超过 1/4
prompt_budget = n_ctx_effective - reserve_completion
```

**token 上界估计**（请求侧无 tokenizer，必须用上界而非近似值）：

```
est_tokens(s) = ceil(utf8_bytes(s) / 3)                          // CJK 约 3 bytes/token，ASCII 约 4
k = EWMA(max(1.0, actual_prompt_tokens / est_tokens), α=0.2)     // 在线校准，来自 usage 回填
send_budget = prompt_budget / (k × 1.1)                          // 1.1 为安全系数
```

> `est_tokens` 是**上界**估计：CJK 密集文本约 1 token / 3 bytes，ASCII 约 1 token / 4 bytes，取 3 即对两类文本都不低估。`k` 的初值为 1.0；首个请求返回后用 `usage.prompt_tokens` 修正，此后按 EWMA 更新，`k` 单调不小于 1.0。

**裁剪算法**（确定性、可从结果反推输入）：

1. 计算三段体积：`S1 = goal 全文`（**永不裁**）、`S2 = affected_scope 内节点全文`、`S3 = 其余节点的 `{id, goal≤120字符, role, depends}` 摘要`；
2. 保留 `S1 + S2`，若 `est(S1+S2) > send_budget` → **不裁剪、直接 `AIRY_ETOOLARGE`**（裁剪到无法表达缺陷的 prompt 无意义，且会产生误导性裁决）；
3. 否则按 `S3` 尾部（节点 id 逆序）逐个移除，直到 `est(S1+S2+S3) ≤ send_budget`；
4. 移除数 > 0 → prompt 头部写 `truncated: true, omitted_nodes: N`，并进事件 `prompt_truncated{omitted_nodes, est_tokens, send_budget}`；
5. 裁剪顺序与节点顺序均为**确定**的（不依赖哈希表遍历序），故同一输入必得同一 prompt（G57 辅助断言）。

**并发闸门**（`grad_inflight_sem`）：容量 `max_inflight = first_nonzero(model.yaml: max_concurrent, 1)`；获取超时 `queue_ms = per_round_ms / 4`，超时 → `AIRY_EBUSY`（**不排队到预算耗尽**，避免一个慢请求拖垮整轮）；`max_inflight` 与 llama.cpp 的 `--parallel` 必须一致——**不一致的后果是排队发生在服务端，而观测发生在客户端**，这正是 P1-14 的归因失真的来源，故门禁 G58 断言 `max_inflight ≤ server_parallel`（由部署检查脚本读取启动参数比对）。

#### 5.2b.10 断流判定与传输侧超时（D2-9 配套）

| 项 | 设计 |
|----|------|
| 超时三拆 | `connect_ms`（默认 3000）、`read_ms`（默认 30000，**空闲间隔**）、`total_ms`（= GRAD 剩余预算）。现有 `LOCAL_DEFAULT_TIMEOUT 120.0` 是 total，必须保留但同时补 read |
| 断流检测 | read 空闲超过 `read_ms` → `AIRY_ESTREAM`；`total_ms` 超 → `AIRY_ETIMEDOUT`；两者在 stats 分列（`stream_stall_count` / `total_timeout_count`），因为处置不同：前者重试，后者 fail-closed |
| 重试矩阵 | `PROVIDER_RETRY_CONNECT_ONLY` → `{connect: retry×1(0.5s), read: retry×1(0.5s), estream: retry×1(0.5s), total: 不重试}`。**前提**：仅在确实幂等时（`temperature==0 && seed!=0`）允许重试，否则重试会改变结果 |

#### 5.2b.11 B 失败路径输入契约 v2 与消偏（C13）

```c
typedef struct {
    const char *goal_json;              /* G 的结构化原文 */
    const char *c_report_json;          /* C 的 report：五项位图 + affected_node + errors[] */
    const char *failed_node_json;       /* 失败节点全文（id/goal/role/depends/inputs/outputs/cost） */
    const char *neighbors_json;         /* 直接前驱 + 直接后继（深度 1），各限 4 个 */
    uint32_t    round;                  /* 当前轮次 */
    const char *round_history_json;     /* 最多 3 条 {round, defect_codes[], affected_scope[]} */
    uint32_t    token_budget;           /* 本 prompt 的 token 上界，由 5.2b.9 计算 */
} grad_arbiter_failure_input_t;
```

**三条消偏规则**（每条都对应一个已知失效模式）：

1. **不给 B 看自己上一轮的 verdict 原文**，只给 `defect_codes[]`。理由：B 见到自己上一次的判断会产生锚定，进而"为了自洽而坚持"，这在 P2-11 的连续同缺陷复现中已被观察到（同一缺陷连续 3 轮）。
2. **必须给 B 看 C 的完整 report**（含 `affected_node` 与 `errors[]`）。理由：B 的价值在于**判断 C 的否定是否成立**，若不告诉它 C 说了什么，它只能重做一遍 C 的工作，这正是当前成功路径 prompt 的缺陷（`grad_llm_s1_arbiter.c:119-148` 已注入 report，但只注入聚合 JSON，无 `errors[]`）。
3. **必须给 B 看失败节点正文**。理由：E-04 的判据是"该节点产出是否仍服务于 G"，只有读到节点 goal 与 outputs 才能判；当前 B 的 prompt 无任何节点正文，故 E-04 实际是在盲判（P1-4）。

**A 的历史记忆注入格式**（追加到 A 的 patch 分支提示词，不改分支结构）：

```
Previous rounds (most recent last, max 3):
  round 1: rejected by C [E-01,E-05]; affected_scope=[n3]; arbiter=reject(structural)
  round 2: rejected by C [E-05];      affected_scope=[n3,n4]; arbiter=skipped_budget
Do NOT reproduce the same defect. If the same defect recurs, state why the plan cannot avoid it.
```

**无进展即停判据**：`defect_code_seq(i) == defect_code_seq(i-1)` 且 `affected_scope(i) == affected_scope(i-1)` → 立即 `no_progress` fail-closed，不再发起第 3 轮。理由：同缺陷同范围重复出现，说明 A 在当前能力下无法收敛；继续重画只会把 p99 推向 203s 以上（P0-3 实测）。

### 5.6 反向判断

以下情形表明推理链强化**未达目的**，应回退设计而非继续调参：

1. 补齐元数据后 E-05 仍 >2%，说明判据本身错误；
2. B 看见计划后驳回率不降反升，说明 B 能力不足或提示词失配；
3. Δk 修补后计划一致性检查频繁失败，说明节点间耦合被低估；
4. 确定性门禁后成功率下降 >3pp，说明原成功率依赖随机性；
5. 拓扑执行后出现新死锁，说明依赖图存在隐式环；
6. **（r3）C9 落地后端到端成功率显著低于 GRAD 放行率**——这不是回归，而是**此前口径失真的暴露**。此时不得回退 C9，应据此重定验收基线；
7. **（r3）预算生效后大量轮次落在 `per_round_ms` 边界**——说明预算值小于真实分布，应先测量 p50/p95 再定档，不得直接放大预算掩盖慢路径；
8. **（r4）`temperature=0` + 固定 seed 后 E-04 判定力下降 >5pp**（B 的驳回率显著下降且人工复核确认漏判）——说明确定性采样牺牲了语义分辨力。此时**不得**回退到 `temperature=0.2`，正确方向是"确定性基座 + 受控语义复核"：基座（C 的 E-01/E-02/E-03/E-05）保持 temp=0；仅 B 的 E-04 允许 `temperature=0.1` 且**必须** `seed` 固定、`top_p=1.0`，并在 stats 中单列 `e04_nondeterministic_runs`，G42 对 E-04 改判"缺陷码集合一致"而非"逐字一致"（§13.6）；
9. **（r4）引入 `send_budget` 裁剪后计划质量下降 >3pp**（首轮 GRAD 通过率、节点数合理性同时恶化）——说明预算过紧或裁剪优先级错误。先核对 `k` 的 EWMA 是否收敛（`k` 持续 <1.0 说明 `est_tokens` 高估），再核对 S3（节点摘要）是否裁掉了 `affected_scope` 之外的关键上下文。**不得**直接放大 `n_ctx` 掩盖裁剪缺陷——放大 `n_ctx` 只推迟问题，`llama.cpp` 的 KV cache 内存随 `n_ctx × parallel` 线性增长，放大后极易 OOM。

## §7 任务面 B：自演化（36–58K）

### 7.1 思想变化

自演化不再是"体积自演化"（删代码），而是**能力自演化**：在受控边界内自主修改目标函数、重写核心代码并自动上线。体积治理由 §8 的工程约束承担，不与演化账混同。

### 7.2 分层包络

| Tier | 范围 | 体积 | 触发条件 |
|------|------|------|----------|
| Tier 1 | 参数与提示词级（阈值、提示词、路由权重） | 8–12K | 默认开启 |
| Tier 2 | 模块级重写（单驱动 ≤2000 行） | 18–28K | 需门禁 + 金丝雀 |
| Tier 3 | 架构级（跨模块契约） | 10–18K | 需人工评审 + 双写回滚 |
| 合计 | | 36–58K | |

### 7.3 价值函数

```
V = w1·成功率 + w2·(1/延迟p95) + w3·(1/成本) + w4·稳定性 − w5·漂移
V0 = 1.0（以 8h 跑 96.47% / p95 112s / 零崩溃为基线）
```

### 7.4 门禁 K1-K6

| 编号 | 门禁 | 判据 |
|------|------|------|
| K1 | 正确性不回退 | 成功率 ≥基线，负向用例全绿 |
| K2 | 性能不回退 | decode p50 不低于基线 95% |
| K3 | 稳定性 | 8h 零崩溃、零挂起、资源漂移 ≤5% |
| K4 | 可回滚 | 一键回滚 ≤5min，且回滚后门禁全绿 |
| K5 | 可解释 | 变更必须携带目标函数差异与证据 |
| K6 | 边界 | 不得触碰 §6.7 红线与 §1.3 非目标 |

### 7.5 版本与时序防滚动抵消

- 每次演化生成独立版本号与 manifest；
- 金丝雀 10% → 50% → 100%，每级观察 ≥2h；
- 若两级间指标互相抵消（A 升 B 降），强制回滚并记录。

### 7.6 可回退与 kill switch

- 持久化件设字节边界；
- kill switch：环境变量 + 文件哨兵 + CLI 三通道；
- 触发后 30s 内停止一切自演化写入。

### 7.7 守恒公式

```
功能体积 = C(6.8K) + D必做(7.1K) = 13.9K（必做口径）
         = 13.9K + D4(0.9K) = 14.8K（含 D4 全口径）
```

**r3 口径变更说明（相对 r2）**：

- C 由 5.1K → **5.9K**：新增 C9（执行层失败语义，600 行）与 C10（发射层守卫，200 行），二者均非"并入既有条目"可吸收；

- r2 声称"P0/P1/P2 修复全部并入既有条目、净增 0"——该表述**作废**（见 §0.3 Z22）：吸收成立的前提是条目本身已覆盖该工作，而 C9/C10 在 r2 中根本不存在；
- 账一 5.1K 是**施工量**而非净增：触核必须同 commit 等量配减，故账一对 LOC 硬线的净贡献为 0，但对**工作量预算**为 5.1K。二者不可混谈。

- 校验：`5.9 + 8.0 = 13.9`；`13.9 + 0.9 = 14.8`；`13.9 + 1.6 = 15.5`（全量口径）。
- **禁止**再用"r4 修复并入 r3 条目"的表述：C11 的 `seed`/`grammar` 透传需要同时改 `llm_request_config_t`、`envelope.c`、三个 provider adapter 与 `grad_llm_call.c`，跨 4 个模块，无法被任一条既有卡片吸收。

### 7.8 结论

自演化在 0.1.20 仅开放 Tier 1；Tier 2 需 C1-C8 与 D0-D3 全部验收后开启；Tier 3 不在本版本开放。

### 9.4 计量纪律

**（1）判定层标注纪律**

## §13 三问成文回答

### 13.1 能否在 0.1.20 达到 98% 成功率

**能，但有三个前提**：

1. **口径前提（r3 新增）**：上述 98.3% 是 `grad_pass` 层推算，**不等于 `e2e`**。r3 已证 `exec_success` 在 C9 落地前根本不可产生（P0-6），故"达到 98%"必须先由 C9/C10（G52/G53）建立 `e2e` 口径，再报数；未过 G52 前，任何 98% 表述无效（§9.4）。
2. **补全前提**：E-05 占失败轮 12/13，只要 C1+C4+C5 落地，理论失败上限降至 1/368 ≈0.27%；即便补全器有 30% 失效，成功率仍 ≥98.3%。
3. **来源前提**：C4 的 `inferred` 来源必须被 C5 正确区分，不得把"补出来的元数据"当作"真实元数据"通过因果检查（否则是判据自欺，而非成功率提升）。

**反证**：若 C9 落地后 `e2e` < `grad_pass` 的幅度 >2pp，说明执行层失败是此前被掩盖的主因，`e2e` 基线须重定，且 98% 目标期限顺延——此时**不得**通过回退 C9 或放宽 G52 来"恢复"数字（§5.6 第 6 条）。

### 13.2 双模型是否会拖慢系统

**会，但角色不可取消**：B50 A1 实测同角色双份加载使耗时 +28.4%，故"同角色不得重复加载"（P3-4）；r9 实测双思考全链代价为延迟 +20.3%、token +7.9%（V10），且此前该成本**在生产侧无计量**（P2-8），0.1.20 起由 G50 强制分角色入账、可生产复算。但 A 生成与 B 审查是两个语义角色，r7 已证同档自审自裁无效（V9），取消 B 等于取消门禁。正确做法是让驳回变便宜（C6）、让成本可见（G50），而不是让审查缺席。

**r4 限定**：上述 +20.3% / +7.9% 的测量前提是"B 在成功路径上被调用"。r4 取证确认 `grad_coordinator.c:260` 把 B 整个包在 `if (report.error == AIRY_GRAD_OK)` 内，**失败轮根本不产生 B 的调用与成本**——因此 V10 的成本数字**只覆盖了成功轮**，是全链成本的下界而非全貌。C13 落地后（`arbiter_on_failure=e04_only`）失败轮会新增约 0.3 次/轮的 B 调用，V10 数字必须重测，**不得**用旧值做 0.1.20 的延迟预算依据。

### 13.3 自演化是否会失控

**在 Tier 1 不会**：Tier 1 只改参数与提示词，受 K1-K6 与 kill switch 双重约束；Tier 2 需全部门禁绿后开启；Tier 3 本版本不开放。风险不在"改代码"，而在"改了但指标互相抵消"，故 §7.5 强制金丝雀分级与抵消回滚。

### 13.4 六准则（保留）

1. 先证伪，后证实；
2. 单点不成结论；
3. 口径先于数字；
4. 失败必须干净；
5. 契约先于实现；
6. 回滚先于上线。

### 13.5 反向判断（保留）

见 §5.6；另加：若 8h 复测成功率不升反降，第一嫌疑是 C4 补全质量，而非模型能力。

### 13.6 「双思考是否真的优于单思考」的 r4 限定（新增）

**先说命名**：本方案自 r4 起统一称 **三段式（A 生成 → C 确定性校验 → B 成功路径复核）**，不再以"双思考"作为架构描述。"双思考"暗示两次独立语义推理互为校验，而代码事实不支持该暗示。

**代码事实（四条，均可复核）**：

1. `grad_coordinator.c:255-284`：B（`s1_arbiter`）整个调用被 `if (report.error == AIRY_GRAD_OK)` 包裹——**C 一旦判失败，B 不会被调用**；
2. `grad_llm_s1_arbiter.c:119-148`：B 的输入只有 goal JSON、C 的 report JSON、节点计数与 guard 列表，**没有计划节点的正文**，B 无法判断"节点内容是否偏离目的"，只能复核"结构与报告是否自洽"；
3. `grad_llm_s1_arbiter.c:160-163`：B 的 LLM 调用失败时 `return AIRY_SUCCESS`——**静默降级为"采纳 C"**，且该降级在 stats 中与"B 主动 accept"不可区分；
4. `grad_coordinator.c:264-284`：B 返回的 `opinion` 字段未被任何下游读取，仅 `verdict` 生效——**B 的解释不进入下一轮 A 的上下文**（对应 P2-11）。

**由此把既有结论拆成两个命题**：

| 命题 | 内容 | r4 判定 |
|------|------|---------|
| **P1** | 在 C 已判通过的计划上，追加 B 复核可降低**误放行率** | **有证据支持**（r9/V10 的对照实验均在此前提下取得），但成本数字只覆盖成功轮（§13.2 r4 限定） |
| **P2** | B 能拦截 **C 漏判的失败计划** | **无证据支持，且当前代码结构上不可能成立**（事实 1）。r4 起 P2 视为**未证伪的假设**，不得引用 |

**证伪 P2 的方式（批次 3b 的准入门槛）**：在 ≥20 例黄金集中，必须包含一类专用样本——**C 判 pass 但执行层失败（`exec_success=false`）的真负例**，且数量 ≥5。若 B 对这类样本的拦截率 <10%，则 P2 判**不成立**，B 的定位永久固化为"成功路径复核器"，§13.2 的成本收益陈述与 §6.3 的 D3 验收口径同步改写。

**设计层面的四个可能问题点（r4 结论，均已给落点）**：

1. **B 与 A 的采样同源风险**——若 A/B 共用同一端点与同一 `temperature/seed`，两次采样高度相关，交叉校验的独立性被削弱。落点：C11 要求 A/B 各自独立 `seed`（不同常量），G57 断言两者请求体 SHA-256 不同；
2. **B 的输入裁剪导致盲审**——C2 的计划摘要若裁掉节点正文，B 只能判结构不能判语义。落点：§5.2b.11 消偏规则 3 强制给出 `failed_node` 正文；`arbiter_on_failure=e04_only` 时 E-04 正需要正文；
3. **B 的输出无 schema 约束**——B 目前返回自由文本 JSON，`grad_parse_plan_json` 是裸 `cJSON_Parse`，无法保证 `verdict/affected_scope/opinion` 三字段齐备。落点：C11 的 `response_format` + GBNF grammar，G59 的 `json_schema_ok`；
4. **B 无历史记忆导致重复驳回**——A 看不到上轮驳回理由（P2-11），B 看不到自己上轮的 verdict，形成"同缺陷反复驳回"的死循环。落点：C13 的 `round_history` 注入 + `defect_code_seq` 连续两轮相同即 `stopped`（J-16/G56）。

**三条硬约束**：

- 对外文档与汇报**一律称"三段式"**，"双思考"仅可作为历史术语在 §0.3 台账中引用；
- 任何"B 提升成功率"的表述必须**分离 P1/P2 数据**，禁止把 P1 的效果说成 P2；
- C13 未落地前，"失败路径也被审查"的说法**不得出现**——这在 r3 稿中曾隐含成立，r4 判定为**表述失实**（§0.3 Z 台账）。
