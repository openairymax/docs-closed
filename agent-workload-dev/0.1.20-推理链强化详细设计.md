## §0 结论摘要

1. **0.1.19 改善的是启动与首字延迟，不是推理质量。** D1/D2/D3（仅 `keep_alive`）/D4 已落地，能改善冷加载与首字延迟（G37 有实测口径）；但 mimo 思考爆炸、端侧长输出超时、质量下滑三项**均未被 0.1.19 触及**，其中 `performance_mode=lightweight` 反而把 GRAD 整条关掉（`think_d/src/svc.c:180-192`），属于**用质量换时延**，与「更稳地提升准确率」方向相反。
2. **B（t1-f 语境终裁）会被调用，但看不到计划。** 生产路径上 C 通过后每轮确实调用 B（`grad_coordinator.c:260-266`）；但 B 的 prompt 只含 goal + C 报告 + guard 名单 + 节点数（`grad_llm_s1_arbiter.c:119-148`），**不含任何节点内容**。所谓「语境终裁」退化为「对 C 报告的复述」——这是「双思考不提准确率」的第一断点。
3. **A（t2 生成）在首轮被 seed 短路。** `grad_coordinator.c:162-173` 收到 `seed_plan` 就直接借用，不调 A；而 seed 来自 reactive planner——线性 DAG、无 handler、自造 cost/guard（`planner/reactive.c:410-447`）。于是「生成—验证—仲裁」三权分立实际退化为「单模型自检 + 一次复述」。
4. **C（t1-p 四验）大部分恒真。** E-01 因 `inputs` 从不下发而全跳过；E-03 因 reactive 自造 `cost>0` 而把节点记入 `checked_nodes`（`grad_verifier.c:353-367`），使 E-05「零节点被严格验证」的防线**永不触发**（`grad_verifier.c:555`）；E-04 只有标签计数，语义判定依赖 B，而 B 又看不到 guard 的语义。**四验实际只剩 E-02（Kahn 无环）是真门。**
5. **「省 token 又更准」的参照系错了。** 原始设计的省 token 是对「token 级流式批判（每 15 token 一次 S1）」的替代；TC3 文本批判循环已于 2026-08-07 被用户裁定废止（`engine_process.c:357-365`），**历史基线不存在**，所以「省」无对象。相对「不开双思考」的实测是 **+20.3%（轻任务）/ +7.9%（多步工具任务）**，而同批次准确率实测为 0.94（全 mimo）/ 0.50（三级分档）/ 0.44（全本地）/ 0.62（仅换决策档）——**token 增加、准确率未增**。真正的问题不是「双思考不划算」，而是**审方没有信息增益**。
6. **任务大厅与 DAG 图纸是「观测面成立、执行闭环不成立」。** `airy_work_hall_create` 全仓仅 tests 调用（生产零实例化）；cognition 内部执行是线性 for 且只派发有 handler 的节点（`engine_process.c:404-419`），reactive 计划恒无 handler → 空转；sched_d 的 `dag_submit` 是唯一真实边驱动执行器（`sched_dag_engine.c:100-153`）。**同一语义四套执行器，验的图与跑的图不是同一份。**

> 一句话：0.1.20 的任务面 C 不是「再造一个更强的模型」，而是**先让现有的 A/B/C 三权真正互相看得见、让四验真正能失败、让降级真的被记录**，再在同一套骨架上做「风险触发的审方」与「结构化批判证据链」，把 token 花在能改变结论的地方。

## §2 三件套有效性裁决

### 2.1 双思考（GCCP + GRAD）：机制成立，接线不成立

| 环节 | 设计意图 | 实现现状 | 证据 | 判定 |
|------|----------|----------|------|------|
| GCCP（G） | 事实锁：目标可证伪 | LLM 启发式 probe/step/confirm，阈值 0.6；OCP/PMP/TPBVP 未实现 | `07-gccp.md:20` | 成立（弱形式） |
| A（t2 生成） | 生成/修订 DAG 图纸 | 首轮被 seed 短路；修订轮要求全量重绘 | `grad_coordinator.c:162-173`；`grad_llm_s2_plan.c:76-81` | **不成立** |
| C（t1-p 四验） | 零 token 硬逻辑门 | E-02 真；E-01 全跳过；E-03 恒不超（自造 cost 未超预算）；E-04 只计数；E-05 被击穿 | `grad_verifier.c:293-301,353-367,496-499,555` | **仅 1/4 有效** |
| B（t1-f 仲裁） | 语境终裁、元验证 | 每轮调用一次，但无计划输入；失败/解析失败 fail-open | `grad_llm_s1_arbiter.c:119-163`；`grad_coordinator.c:273-313` | **形式存在、信息量为零** |
| 差分（V3.0） | 只验 Δk + 一阶闭包 | closure 计算正确；但 E-03 不吃 closure、统计记全量 | `grad_verifier.c:417-482,543`；`grad_coordinator.c:233-234` | **能力在、收益不可观测** |
| 未收敛处置 | fail-closed | 转 `manual_review_required` 并中止本轮（2026-08-26 改） | `engine_process.c:348-355`；`grad_coordinator.c:426-437` | 成立 |
| 降级 | 显式 | 无 LLM 静默 return 0；lightweight 直接关 | `engine_process_grad.c:95-98`；`svc.c:180-192` | **不成立** |

**裁决**：GRAD 的**骨架是对的**（三权分立、fail-closed、差分设计、契约与策略分离都在），**但四处接线断裂**使得「1 + 1 + 1」退化为「0 + 1 + 0」。

### 2.2 任务大厅：观测面成立，执行闭环不成立

- 模块完整：`work_hall.c` / `_agent` / `_auth` / `_cb` / `_deleg` / `_flow` / `_ops` / `_persist` / `_review` / `_sched`、`hall_store*.c`、`gateway_sse_hall_watch.c`、`cli_hall.c` 均在。
- **生产零实例化**：`airy_work_hall_create` 全仓调用者仅 tests。
- 文档仍宣称「宿主与执行中枢」「CLI 完整闭环」（`08-work-hall.md:13,132-141`），与代码事实不符。
- 实际可达的是**观测面**：`hall.board` / `hall.watch`（SSE）/ `hall_store` 持久化。

**裁决**：大厅当前是「看板」，不是「执行中枢」。0.1.20 不应假装闭环，应二选一：**要么接线成执行面，要么在文档与自模型中降级为观测面**。本方案选后者（任务面 C 不做大厅重构），并在 §5 对账中修正文档。

### 2.3 DAG 图纸：四套执行器，验跑不一

| 路径 | 入口 | 是否边驱动 | 证据 | 判定 |
|------|------|-----------|------|------|
| sched_d | `sched.dag_submit` | **是**（ready 集 + 上游产出拼接） | `sched_dag_engine.c:100-153` | 唯一真实执行器 |
| cognition 内部 | `engine_process` 主链 | 否（线性 for，只派发有 handler 的节点） | `engine_process.c:404-419` | 线性空转 |
| taskflow | CLI 任务流 | 否（只执行 initial_node） | `26-coreloopthree-dag-integration.md:230` | 未完成 |
| work_hall | 大厅 | — | 生产零实例化 | 不可达 |

**核心风险**：GRAD **验证的图**是 cognition 内存里的 `airy_task_plan_t`，**执行的图**若走 sched_d 则是 CLI 序列化后的另一份。两者字段不一致（N-02/N-03）→ **验的不是跑的**。这是「DAG 图纸无效」的根因，不是 DAG 设计错了。

### 2.4 「省 token 又更准」为什么没有兑现：五个断点

```
设计承诺： A 生成图纸  →  C 零成本硬验  →  B 语境终裁  →  只改 Δk
实际链路： seed 借用   →  1/4 有效     →  复述报告     →  全量重绘
           断点①          断点②            断点③           断点④
                                                   ↓
                                        降级静默（断点⑤）
```

| 断点 | 机制 | 后果 | 对应 C 项 |
|------|------|------|-----------|
| ① A 被 seed 短路 | `grad_coordinator.c:162-173` | 生成侧无任何改进；图纸来自 reactive（无 handler、线性、自造元数据） | C3 |
| ② C 四验恒真 | `grad_verifier.c:293-301,353-367,496-499,555` | 验证不产生信息；错误图纸不被拦 | C5 |
| ③ B 无计划输入 | `grad_llm_s1_arbiter.c:119-148` | 仲裁无信息增益，只增加 token | C2 |
| ④ 修订全量重绘 | `grad_llm_s2_plan.c:76-81` | 差分验证省下的算力被生成侧抵消；token 反升 | C6（生成约束）+ C1（schema） |
| ⑤ 降级静默 | `engine_process_grad.c:95-98`；`grad_llm_s1_arbiter.c:156-163`；`grad_coordinator.c:273-313`；`svc.c:180-192` | 用户以为「双思考在跑」，实际可能完全没跑；无法归因 | C7 |

> 这解释了实测：**+20.3% token 买到的是「一次看不到图纸的复述」**。要让双思考「更准」，必须让 ②③ 产生信息，而不是继续加模型。

## §4 0.1.20 任务面 C：推理链强化

### 4.1 定位、边界与 A/B 的关系

| 项 | 内容 |
|----|------|
| **定位** | 把 GRAD 三权分立的**接线补全**，并在同一骨架上做两项增强：**风险触发的审方**（把 B 的 token 花在能改变结论的地方）与**结构化批判证据链**（B 必须引用节点与不变式） |
| **不做什么** | 不重写 GRAD 架构；不恢复 TC3 文本级批判循环（2026-08-07 用户裁定，不得翻案）；不新建第二个调度器；不改任务面 A 的 A1~A7；不实现 Tier 2 提案箱 |
| **与任务面 A** | A 解决「健康信号可信、工具可用、结构治理」；C 解决「推理链可用」。**C 依赖 A1（运行时缺陷清零）与 §6 前置阻断项 3/4**，但两者**代码不混 commit** |
| **与任务面 B** | B 的自模型三视图要求「健康/结构/目标」可读；C 把 `grad_status`、`verified_scope`、`plan_origin` 纳入自模型，**是 B 的输入面之一**，但 C 不依赖 B |
| **优先级** | A > C > B。理由：A 不清，C 的观测数据不可信；C 不通，B 的「自我思考」没有可信的认知底座 |
| **LOC 口径** | 计入 0.1.19 生产码总账（同 0.1.20 §4.0 纪律 3 中任务面 A 的处理）；不记演化账 |

### 4.2 设计原则（承 0.1.19 工程思想）

1. **机制/策略分离**：契约变更只落在 `atoms/coreloopthree/include/grad.h` 与 `cognition.h`；提示词、解析、协调器循环仍在 `products/cognition`。
2. **一切降级显式**（no silent pass）：没有 LLM、B 失败、B 解析失败、lightweight、seed 借用，全部产出一个可枚举的 `grad_status`，进 trace、进 engine feedback、进自模型。
3. **未知 ≠ 通过**：元数据缺失一律判 `skipped/insufficient`，不得计入 `checked`；合成元数据必须打标。
4. **可观测先于可优化**：先让 `verified_scope`、`plan_origin`、分段 token 可见，再谈差分收益。
5. **一 commit 一逻辑变更**：C1~C8 每项独立 commit，附门禁证据。
6. **fail-closed 不外扩**：C 只加严「验证不足」的判定；**不新增**会阻断主链的硬失败（避免重蹈「未收敛即中止」造成的可用性回退），除非该项明确声明。

### 4.3 C1：计划 JSON 单一 schema 与单一解析器

**缺陷**（F1、N-02、N-03）：执行侧不解析 `inputs/outputs`，序列化也不写；跨面往返即丢 E-01 元数据。

**方案**：
1. 定义**唯一权威 schema**（写入 `09-grad.md` 与 `26-coreloopthree-dag-integration.md`）：
```json
{
  "task_plan_id": "p-...",
  "entry_points": ["n1"],
  "nodes": [
    {
      "id": "n1",
      "goal": "…",
      "handler": "fs.read",
      "role": "executor",
      "depends": [],
      "inputs": [],
      "outputs": ["artifact:/tmp/a"],
      "cost_time_ms": 1200,
      "cost_mem_mb": 64,
      "invariant_guard": false,
      "invariant": "不得删除用户原始文件"
    }
  ]
}
```
2. `plan_model.c` 增加 `inputs`/`outputs`/`invariant` 解析（与 `grad_llm_s2_plan.c:175-205` 对齐，去重为公共函数或保持同构实现 + 属性测试）。
3. `think_service.c` 序列化补齐上述字段；`cli_dag.c` 透传 `handler`/`inputs`/`outputs`/`invariant_guard`（当前只发 `{id,goal,role,depends}`）。
4. 属性测试：`parse(serialize(plan))` 在全部 GRAD 元数据上等价。

**验收（G39）**：往返保真测试 100%；跨面（CLI→sched_d）提交的图含 `inputs/outputs`；`handler` 缺失率在 A 生成计划中为 0。

### 4.4 C2：审方有输入（B 真正看到图纸）

**缺陷**（F2、N-04）：prompt 只给 goal + report + guard 名单 + 节点数。

**方案**：
1. 新增 `grad_plan_digest_json(plan, max_tokens)`：输出结构化摘要（每节点 `id/goal/handler/depends/invariant_guard/invariant`），**预算 800~1200 token**。
2. 超预算时的降采样规则（确定性、可复现）：优先保留 `invariant_guard` 节点 → 本轮变更节点 → 入口节点 → 其余按拓扑序截断，并写 `"truncated":true`。
3. B 输出 schema 扩展，**强制引用证据**：
```json
{"verdict":"accept|reject","confidence":0.0-1.0,
 "e04":"pass|fail|not_applicable",
 "cited_nodes":["n1","n3"],
 "violated_invariant":"…",
 "opinion":"…"}
```
4. 规则收紧：
   - `verdict=reject` 且 `cited_nodes` 为空 → 判定为**无效仲裁**，记 `degraded_b_invalid`，**不采纳该 reject**（避免无依据驳回导致重绘烧 token），但也不静默 accept——按 C 结果继续并显式标记。
   - `e04=fail` 且 `cited_nodes` 非空 → **硬驳回**（不受 `confidence` 阈值约束）；这是唯一允许「低置信也驳回」的情形，因为证据可核。
   - 其余维持 `AIRY_GRAD_ARBITER_MIN_CONF=0.55`。
5. **风险触发**（省 token 的关键）：B 不再无条件调用，按风险分 `r = w1·节点数 + w2·变更幅度 + w3·guard 缺失数 + w4·A 重绘轮次` 决定；`r < θ_r` 时跳过 B 并记 `b_skipped_low_risk`。省下的 token 用于「高风险时给 B 完整摘要」。

**验收（G40）**：盲审注入实验——构造 10 个「四验全过但含目标偏离节点」的计划，B 必须检出 ≥ 8 并指名节点；改造前基线预期为 0（无计划输入）。同时记录 B 的调用率与 token。

### 4.5 C3：A 首轮真生成，或显式声明 seed 借用

**缺陷**（F3、F11）：`seed_plan` 存在即借用，无标记；reactive seed 结构上无法执行。

**方案**：
1. 契约新增 `airy_grad_launch_t.seed_policy`（`0=verify_seed` / `1=regenerate`），机制核按 profile 传入；默认 `regenerate`。
2. `grad_coordinator.c` 分支显式化，并写入 `plan_origin`：
   - `verify_seed`：沿用现行为，trace 记 `plan_origin="seed_adopted"`；
   - `regenerate`：即使有 seed 也调 A 生成；A 失败 → **返回错误**（fail-closed），不得回退到「seed already valid」；
   - 自动策略：seed 节点 `handler` 缺失率 > 0 或节点数 ≥ 2 且无 `inputs/outputs` → 强制 `regenerate`（reactive seed 必命中）。
3. `plan_origin` 进 `airy_grad_outcome_t` 与 engine feedback。

**验收（G41）**：trace 中每轮 `plan_origin` 非空；reactive seed 场景下 `a_generated` 比例 ≥ 90%；A 不可用时返回非 `AIRY_SUCCESS`（不得静默采纳 seed）。

**风险**：regenerate 会增加一次 A 调用（token 上升）。缓解：与 C2 的风险触发联动——A 生成只在「seed 不可执行」时触发，正常 CLI 计划（带 handler）不受影响。

### 4.6 C4：guard 语义化（E-04 真正生效）

**缺陷**（F4、F5、N-06）：guard 由构造决定（末节点），无 guard 即 trivially pass。

**方案**：
1. 节点新增 `task_node_invariant_text`（`char *`，可空），与 `task_node_invariant_guard` 并存：flag 表示「本节点承载不变式」，text 表示「不变式内容」。
2. reactive 不再自造末节点 guard；改为**按 goal 关键词生成 0~2 条不变式**，生成不出则不设 guard（宁可 not_applicable，也不造假）。
3. C 层报告新增 `e04_applicable`（0/1）；`invariant_guards` 保留计数。
4. B 层：`grad_collect_guards` 改为 `grad_collect_invariants`，收集全部节点的 `(id, goal, guard_flag, invariant_text)`；无 guard → B 必须输出 `e04=not_applicable`，**不得输出 pass**。
5. 统计口径：`e04_status ∈ {pass, fail, not_applicable}` 三分，`not_applicable` 不计入 pass 率。

**验收（G42）**：注入「末节点 guard=1、中间节点偏离目标」的计划 → B 必须 `e04=fail` 并指名中间节点；无 guard 计划 → `not_applicable`（不得 pass）；三分计数在 trace 中可对账。

### 4.7 C5：未知 ≠ 通过（合成标记 + 计数分离）

**缺陷**（F6、F7、N-01）：自造 cost 把节点记入 `checked_nodes`，E-05 永不触发。

**方案**：
1. `airy_task_node_t` 新增 `uint8_t task_node_meta_synthetic`；reactive 置 1，A 生成置 0，解析器支持 `"meta_synthetic":true`（仅供内部与测试）。
2. `airy_grad_report_t` 计数分离：
```c
uint32_t causal_checked;   /* E-01 实际检查的节点数 */
uint32_t cost_checked;     /* E-03 计入求和的节点数 */
uint32_t verified_nodes;   /* 非 synthetic 且至少过 E-01/E-03 之一的节点数 */
uint32_t synthetic_nodes;
uint8_t  e04_applicable;
```
3. E-05 判据改为：`plan->task_plan_node_count > 0 && report->verified_nodes == 0` → `AIRY_GRAD_E05_VERIFY_INSUFFICIENT`。`checked_nodes` 保留为兼容字段（= causal_checked + cost_checked），不再作为 E-05 依据。
4. E-03：synthetic 节点的 cost **计入展示但不参与硬判**，报告 `cost_synthetic=1`，避免「自造预算超限」造成假驳回。

**验收（G43）**：reactive seed 计划必须触发 E-05（当前实测为 OK）；A 生成且带 `inputs/outputs` 的计划必须产生 `causal_checked > 0`；单元测试覆盖「全 synthetic → E05」「部分 synthetic → 不误判」。

### 4.8 C6：差分可观测 + 成本分账 + 生成侧约束

**缺陷**（F8、F9、F10、N-05）。

**方案**：
1. `grad_coordinator.c`：`round.verified_scope = report.checked_nodes`（真实检查数），新增 `round.scope_nodes_json`（本轮 closure 的节点 id 列表）；`total_nodes` 不变。
2. `grad_check_resource` 增加 `closure/closure_count` 参数，E-03 只对闭包求和（与 E-01 同口径）；全量验证时传 NULL。
3. `airy_grad_outcome_t` 增加 `s2_tokens` / `s1_tokens` / `b_calls` / `b_skipped_low_risk`；trace 每轮记录三项 token。
4. **生成侧约束**：`grad_llm_s2_plan.c` 的修订 prompt 从 "FULL corrected plan" 改为「只输出变更节点 + 受影响节点（Δk），格式 `{"patch_nodes":[...],"removed":[...]}`」；解析后合并到 seed 计划。与 `09-grad.md:88,141` 及 `grad_internal.h:72-75` 对齐。
   - 兼容：若 LLM 仍返回全量，解析器识别 `nodes` 字段并走全量替换，记 `s2_full_redraw=1`（可观测其发生率）。

**验收（G44）**：≥5 节点线性链、单节点 patch 场景下 `verified_scope/total_nodes ≤ 0.6`；`s2_tokens + s1_tokens == total_tokens`（误差 0）；`s2_full_redraw` 发生率在修订轮 ≤ 10%。

### 4.9 C7：降级显式（四条路径统一）

**缺陷**（F11、F05 旧结论修正）。

**方案**：
1. 契约新增枚举（`grad.h`）：
```c
typedef enum {
    AIRY_GRAD_STATUS_FULL = 0,
    AIRY_GRAD_STATUS_DEGRADED_NO_LLM,
    AIRY_GRAD_STATUS_DEGRADED_B_UNAVAILABLE,
    AIRY_GRAD_STATUS_DEGRADED_B_INVALID,
    AIRY_GRAD_STATUS_DISABLED_LIGHTWEIGHT,
    AIRY_GRAD_STATUS_SKIPPED_NO_GOAL
} airy_grad_status_t;
```
`airy_grad_outcome_t` 增加 `status`；`degraded` 保留但必须与 `status != FULL` 一致（互断言）。
2. 四条路径点：
   - 无 LLM（`engine_process_grad.c:95-98`）：不再静默 `return 0`；产 `DEGRADED_NO_LLM`，engine feedback 带 `reasoning_chain=degraded_no_llm`，回复元数据可见。
   - B 不可用（`grad_llm_s1_arbiter.c:156-163`）：`DEGRADED_B_UNAVAILABLE`。
   - B 解析失败/无证据驳回（`grad_coordinator.c:273-313`）：`DEGRADED_B_INVALID`。
   - lightweight（`svc.c:180-192`）：**不再 `enable_grad=0`**；改为 `max_iterations=1` + 仅 C（确定性）验证 + 跳过 B，状态 `DISABLED_LIGHTWEIGHT`。E-02 环检测必须保留。
3. 自模型/健康视图暴露 `grad_status` 计数（供任务面 B 消费）。

**验收（G45）**：四条路径各一条自动化测试，断言 `status` 非 FULL 且非空；lightweight 下 E-02 仍生效（构造带环计划必须被拦）。

### 4.10 C8：执行器单一（验的图 = 跑的图）

**缺陷**（F12、F13）：四套执行器；`params_json` 用 `node_id` 而非上游产出。

**方案（0.1.20 最小闭环）**：
1. `engine_process` 主链改为**拓扑序执行**：按 Kahn 序推进，节点就绪条件 = 全部 `depends` 完成；`params_json` 改为「上游产出的拼接 + 本节点 goal」，复用 sched_d 的 `"\n\n--- 上游产出 [id] ---\n"` 语义。
2. **无 handler 节点 = 节点失败**（fail-closed），不再静默跳过。
3. 新增 `exec_graph_hash` 与 `verify_graph_hash`（规范 JSON `{id,depends}` 排序后哈希），两者不等 → 记 `graph_mismatch=1` 并 fail-closed（不执行）。
4. 预留 `exec_backend: inproc | sched_d`（默认 `inproc`）；0.1.21 默认切 `sched_d`，cognition 只负责计划与验证。

**验收（G46）**：diamond DAG（A→{B,C}→D）实测 B/C 均拿到 A 产出、D 拿到 B+C 产出；`exec_graph_hash == verify_graph_hash` 100%；无 handler 节点必失败。

### 4.15 回滚与风险
