# Tri-Opt Agent 执行引擎：输入-规划-工具 全链路 Token 效率优化方案

> 本方案基于历史对话中验证的 **输入优化 (Input Opt)**、**预算感知规划 (Plan Max)**、**工具增强 (Tool Max)** 三大支柱，并引入 **验证反馈闭环** 与 **上下文台账 (Context Ledger)** 机制，在保证任务成功率 (Accuracy) 的前提下，实现系统级 Token 开销降低 **55%~75%**。

二、 模块详细设计与实施
模块 1：智能输入网关
核心目标：让进入 LLM 的上下文“精简且纯粹”，去除噪音与冗余。

1.1 动态语言路由（基于 Tokenizer 校准）
校准机制：新模型注册时，自动触发冷启动校准。使用标准化语料（如 "人工智能是未来的核心技术" vs "Artificial Intelligence is the core"）计算 lang_ratio = 中文Token数 / 英文Token数。

决策逻辑：

ratio > 1.35：用户输入若为中文，自动翻译为英文后再送入 LLM（节省 30%~50% 输入 Token）。

ratio < 0.85：保持中文输入，不翻译。

0.85~1.35：跟随模型原生语言。

注意：输出语言始终对齐用户原始输入语言（用户中文问，强制中文答）。

1.2 提示词分层压缩
不可压缩区（硬保护）：System Prompt 和 Tool Definitions 绝对不压缩，防止工具调用准确率掉点。

可压缩区（主动压缩）：仅对用户输入的冗长背景、RAG 检索的文档块进行压缩。

工具选型：集成 LLMLingua-2（微软）或 CompactPrompt。设置压缩比 target_ratio=0.5（压缩至 50%），测试表明在知识密集型任务中准确率损失 < 2%，但 Token 直降 50%。

1.3 上下文台账（Context Ledger）
机制：维护一个外部 KV 缓存（Redis/Memcached）。如果某一长文本（如 PDF 内容）已经在本次会话中被读取并压缩过，后续轮次直接引用 Doc_ID 占位符，不再重复传输原文，极大降低多轮对话的上下文膨胀。

模块 2：预算感知规划引擎
核心目标：杜绝 Agent“无限思考”或“过度规划”，用最少的步骤解决任务。

2.1 规划-执行解耦（ReWOO 模式改造）
传统 ReAct：思考 -> 行动 -> 观察 -> 思考...（上下文随步骤线性膨胀）。

本方案策略：

Planner（规划器）：一次性生成包含 #E1, #E2... 占位符的完整任务蓝图（DAG 图）。
Worker（工作器）：仅执行工具调用，将结果填入占位符，此阶段不调用主 LLM，阻断 Token 堆积。
Solver（求解器）：将填好的蓝图一次性喂给 LLM 生成最终答案。
收益：长任务（>5步）Token 消耗减少约 80%。

2.2 动态预算分配（BATS / BAVT 策略）
预算定义：为每次执行设定 max_tokens 和 max_tool_calls 硬顶。

复杂度预检：通过一个轻量级分类器（或仅看前 32 个 Token）判断任务复杂度。

简单任务（如天气查询）：分配 500 Token 预算，强制 1 步完成。

复杂任务（如代码生成）：分配 4000 Token 预算，允许最多 5 步。

执行中监控：当已用 Token 达到预算的 80% 时，注入系统提醒 "Budget almost exhausted, please simplify final response."，引导模型快速收尾。

2.3 规划即代码（Plan-as-Code）剪枝
实践发现：LangChain 等框架强制生成的 write_todos（任务列表）会消耗大量基础 Token（约 4k），且移除后对效果无负面影响。

方案：移除 Agent 提示词中强制要求输出 Todo List 的指令，让模型直接输出 YAML 格式的简洁计划，立即减少 60%~70% 的基础规划 Token。

模块 3：动态工具管理层
核心目标：工具调用通常是 Agent 的 Token 吞金兽（占比 >80%），必须精细化管理。

3.1 工具发现模式（Tool Search Tool）
旧模式：将 50 个工具的全量定义（几十万 Token）直接塞入上下文。

新模式：采用 Anthropic Tool Search 模式。

索引：所有工具存储在外部向量库。
路由：LLM 初始只拿到一个 search_tool 的定义。
按需加载：LLM 先搜索，系统返回最相关的 Top-3 工具定义展开到上下文。
收益：单次 Tool 调用上下文从 30k Tokens 降至 1.5k Tokens（降低 95%）。

3.2 工具指令极简主义（EASYTOOL 范式）
现状：工具文档往往冗长（包含参数示例、详细描述）。

方案：使用 EASYTOOL 框架将工具描述统一重构为 {Name: func, Description: 一句话核心作用, Args: [必需参数列表]} 的极简结构。

收益：工具描述总 Token 压缩 34%~64%。

3.3 智能响应截断与“外挂计算器”
截断策略（Smart Truncation）：

限制工具输出最大长度（如 500 字符）。

优先保留首尾关键信息（对于日志和 JSON），中间部分用 [Truncated...] 替代。

硬计算外挂：

识别到数学表达式（如 125 * 38 / 7.2）时，不交给 LLM 推理，直接路由到 Python eval 或 Wolfram MCP 服务计算，结果仅返回数值（约 5 Tokens），避免长篇累牍的推理过程（约 200 Tokens）。

模块 4：验证与反馈闭环（质量保险丝）
核心目标：防止因过度压缩导致的“幻觉”或“错误”被直接输出，消耗修正成本。

4.1 快速一致性检查（Self-Consistency）
机制：对于关键数值或事实性回答，用极低的采样温度（Temperature=0）重复生成两次。

对比：如果两次回答的核心结论一致，直接输出；如果不一致，触发回退机制——丢弃压缩后的上下文，用原始完整上下文重跑一次（兜底保障准确率）。

4.2 语义缓存（Semantic Cache）
机制：引入 GPTCache。如果用户问的是语义相似的问题（相似度 > 95%），直接返回缓存结果。

收益：对于高频查询场景（如客服），Token 消耗趋近于 0。

五、 关键避坑指南（必须遵守）
永不压缩系统角色与工具定义：压缩这两个部分会严重破坏指令遵循能力，导致工具调用错乱，即便 Token 减少也没有意义。

ReWOO 不适合极度动态任务：如果任务每一步都高度依赖上一步的随机结果（如开放世界游戏），全盘规划可能失效。此时应保留传统 ReAct，但启用预算感知强制限制最大步数。

语义缓存的时效性：涉及实时数据（如股价、天气）的请求务必绕过缓存，或设置极短的 TTL（如 30 秒）。

监控决策轨迹：必须记录每个请求的 decision_reason（为什么路由到英文/中文/压缩/不压缩）。定期复盘异常值，持续优化决策树的阈值（如将 ratio > 1.35 调整至 1.30）。
