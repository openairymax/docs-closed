## §1 问题总账（社区反馈 → 根因 → 对策映射）

### 1.1 性能类

| # | 现象 | 根因（源码取证） | 对策 |
|---|---|---|---|
| P1 | 对话输入后几十秒无反应 | 双思考管线每轮对话前置 **2~3 个非流式 LLM 调用**：Phase 0 指令分解（`engine_phase0.c:134` `stream=0`）+ planner 规划（`planner/llm_client.c:196/254/364` `stream=0`）；本地 7B 每阶段生成完整 JSON 耗 20~60s，串行叠加即首字延迟 50s+ | D1 轻量模式、D2 前置合并 |
| P2 | 每次对话都慢（而非仅首次） | Ollama `keep_alive` 默认 5 分钟过期即卸载模型，下次请求重载 4.7GB 权重；llm_d local adapter **未透传 keep_alive/options 任何 Ollama 专有参数**（`providers/adapters/local.c` 全文无 keep_alive/num_ctx/num_predict） | D3 参数透传 |
| P3 | 偶发分钟级无响应后失败 | local 默认 timeout 60s（`local.c:36`）× 可重试判定（`retry.c:26-28`）× 最多 3 次——CPU 上跑不完 60s 的非流式请求被当瞬时故障重试，最坏 3×60s ≈ 3 分钟 | D4 超时重试策略修正 |

### 1.2 稳定性类（含 0.1.19 §3.5 已入账四条）

| # | 现象 | 根因 | 对策 |
|---|---|---|---|
| S1 | 网络不稳定："network request to provider failed" | curl 真实错误码（connect refused / DNS 失败 / 超时）被上层笼统化，文案不在 AirymaxRT 源码内（SDK 层包装），排查方向被误导 | D6 错误透传体系 |
| S2 | 工具不稳定 | 工具暴露与守护进程存活**未联动**（maths_d 缺席工具照常暴露，三连败后报"服务不可达"）；IPC 高频重连抖动 481 次/2h，日志噪声掩盖真实错误 | D7 降噪、D8 可用性联动 |

## §2 优化设计

### 2.1 性能：本地低算力适配

#### D1 轻量对话模式（performance_mode）

**机制与策略分离**：模式判定是策略，跳过/合并的执行路径是机制。

- `model.yaml` 顶层新增 `performance_mode: full | lightweight | auto`（默认 `full`，现网行为零变化）；env 覆盖 `AIRY_PERF_MODE`（优先级 env > yaml，与 think 段惯例一致）
- `lightweight` 语义：
  - `think.enabled` 强制失效（跳过 GRAD 批判循环）——复用现有降级路径（`engine_phase0.c` LLM 不可用时退化为单元素 JSON，路径已存在且有测试覆盖）
  - Phase 0 分解与 planner 规划**合并为单次直连生成**（见 D2）
  - `tool_rounds` 缺省降为 32（完整 1000 轮在本地模型上无意义）
- `auto` 语义：首请求探测端点首字延迟，> 5s 且 `mode: local` → 日志与 status **提示**建议切 lightweight（不自动改配置，见 §5 待决 1）

#### D2 前置阶段合并（调用次数 3→1）

- 将 Phase 0（指令分解）与 planner（计划生成）合并为**单次调用**：一个 prompt 同时产出子任务分解与行动计划 JSON
- full 模式下保持两段式（质量优先）；lightweight 模式下单段式
- 本地 CPU 7B 首字延迟预期：50~120s → 15~40s（前置 3 调用 → 1 调用）

#### D3 Ollama 专有参数透传

local adapter 请求体新增字段（从 model.yaml 派生，不新增用户配置面）：

| 请求字段 | 来源 | 默认 |
|---|---|---|
| `keep_alive` | 新增高级字段 `keep_alive` | `"30m"`（防 5 分钟过期卸载） |
| `options.num_ctx` | `context_window` | 映射现有字段 |
| `options.num_predict` | `max_output` | 映射现有字段 |

安装文档同步给出 `OLLAMA_KEEP_ALIVE=-1` 指导（服务级常驻）。

#### D4 本地端点超时与重试策略修正

- local provider：`CURLE_OPERATION_TIMEDOUT` **不重试**（慢推理是预期行为，重试只会叠加等待）；timeout 默认 60s → 120s
- 可重试白名单收窄为 `CURLE_COULDNT_RESOLVE_HOST` / `CURLE_COULDNT_CONNECT`（真实瞬时故障），且 local 场景重试上限降为 1 次
- 云端 provider 策略不变

#### D5 端点健康探测与冷加载识别

- llm_d 启动时及每 5 分钟对 local 端点 `GET /v1/models` 探测；记录往返延迟
- 请求侧检测冷加载特征（首 token > 10s）→ 日志标注并附 `OLLAMA_KEEP_ALIVE` 建议
- `airymaxrt status` 新增"模型端点健康"项（可达性 / 延迟 / 冷加载标记）——落地 0.1.20 §6 阻断 3 的"能力存在 ≠ 能力可用"原则在 LLM 面的体现

### 2.2 稳定性加固

#### D6 错误透传体系

- llm_d 侧建立 curl 错误码 → 结构化错误（`code` + 用户可读 `diag`）映射表：

| curl 错误 | diag 文案（透传至 TUI） |
|---|---|
| `CURLE_COULDNT_CONNECT` | 模型端点连接失败：服务未启动或端口错误（base_url=%s） |
| `CURLE_COULDNT_RESOLVE_HOST` | 模型端点域名无法解析（base_url=%s） |
| `CURLE_OPERATION_TIMEDOUT` | 模型端点响应超时：本地模型可能冷加载或推理慢，可调大 timeout 或换轻量模式 |
| HTTP 4xx/5xx | 保留原始状态码与响应体摘要 |

- gateway/TUI 层**禁止笼统化**：透传 `code + diag` 原文——这是 0.1.19 §3.5② 错误误映射问题的机制性修复（工具面与 LLM 面统一）

#### D7 IPC 重连退避与日志降噪

- 重连改指数退避（200ms 起倍增，上限 5s），消除高频抖动
- 同类错误窗口聚合：60s 窗口内同一 target 的重复失败只记 1 条 + 累计计数，替代当前 481 次/2h 的日志洪水

#### D8 工具暴露与守护进程可用性联动

- tool registry 订阅 supervisor 存活事件：daemon 掉线 → 其工具即时标记 `unavailable`，**不得暴露给 agent**（工具列表在暴露时就过滤）
- daemon 恢复 → 自动重新暴露
- 根除"工具暴露成功 → 调用三连败 → 报服务不可达"的时序矛盾

#### D9 配置变更引导

- daemon 启动时记录 model.yaml 的 mtime + hash；请求侧检测文件变更 → 日志 + `airymaxrt status` 提示"配置已修改，需重启生效"
- 0.1.20 若实现热重载则以热重载替代（本文不做热重载，避免版本线膨胀）

#### D10 §3.5 原条款落地（引用，不重复设计）

启动器逐行解析（①）、fs_write mkdir -p（③）、相对路径锚点（④）——按 `0.1.19-架构改进方案.md` §3.5 原设计执行，本文不重复。

## §3 预期效果与验收口径

### 3.1 首字延迟预算表

| 部署形态 | 现状（0.1.18） | 目标（0.1.19） |
|---|---|---|
| 云端 API | < 2s | < 2s（不回归） |
| 本地 GPU（7B 全显存） | 5~15s | < 5s（lightweight） |
| 本地纯 CPU（7B） | 50~120s+ | < 40s（lightweight）；status 给出换 1.5B/3B 模型建议 |

### 3.2 稳定性验收

- 错误透传率 100%：TUI 可见的每条 LLM/工具错误必含结构化 code+diag，无笼统化文案
- IPC 日志噪声下降 ≥ 90%（以 2h 压测对比 481 次基线）
- 工具零误暴露：任意 daemon kill 后 5s 内其工具从 agent 可见列表消失
- 配置变更提示：改 model.yaml 不重启 → status 必现提示

### 3.3 门禁

- 增设 **G37（性能预算门禁）**：3.1 表全部档位达标方可过；复用 0.1.19 G 系列相关稳定性门禁做 3.2 验收（对应关系施工图定）
- G 编号衔接：0.1.19 G1~G32、0.1.20 G33~G36，本文 G37 起

## §4 施工任务分解（100~200 行/任务，沿 0.1.19 泳道纪律）

| # | 任务 | 内容 | 估量 | 依赖 |
|---|---|---|---|---|
| T1 | performance_mode 解析 | model.yaml schema 扩展 + env 覆盖（llm_d config 层） | ~150 行 | 无 |
| T2 | lightweight 执行路径 | think 跳过 + 前置合并单调用（coreloopthree） | ~200 行 | T1 |
| T3 | Ollama 参数透传 | local adapter keep_alive/options（llm_d） | ~120 行 | 无 |
| T4 | 本地超时重试修正 | timeout 白名单与次数（llm_d providers/core） | ~80 行 | 无 |
| T5 | 端点健康探测 | 探测 + status 展示（llm_d + CLI） | ~200 行 | T3 |
| T6 | 错误透传映射表 | http.c 映射 + gateway 透传（llm_d + gateway_d） | ~150 行 | 无 |
| T7 | IPC 退避降噪 | 指数退避 + 聚合（commons ipc） | ~120 行 | 无 |
| T8 | 工具可用性联动 | registry 订阅存活事件（tool 面 + supervisor） | ~200 行 | 无 |
| T9 | 配置变更提示 | mtime/hash 检测（llm_d/gateway_d） | ~100 行 | 无 |

并行分组：{T1→T2} 串行；{T3→T5} 串行；{T4、T6、T7、T8、T9} 相互独立可并行。全部完成后统一过 G37 与 3.2 验收。
