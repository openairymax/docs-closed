## 0. 全链根因模型（九项根因链终态）

蓝图调度挂死不是单点故障，而是**九项缺陷的串联放大**：任一环超时/失败/静默，都会让上层把"慢"放大成"挂死"。九项根因链在预备期已全部定位，其中六项已修复并验证：

| # | 根因                                                      | 状态                                | 证据 / 修复                                         |
| - | ------------------------------------------------------- | --------------------------------- | ----------------------------------------------- |
| ① | tool\_d `fs_grep` 无界扫描，大目录下单次工具调用即耗尽全部预算                | ✅ 已修（p9）                          | builtin 工具全量有界化：签名统一 + deadline 注入 + 噪音目录排除     |
| ② | IPC 双向超时不对称（请求方远短于执行方），慢工具被请求方先行放弃                      | ✅ 已修（p9）                          | 预算链统一（见 §2.1）                                   |
| ③ | runner 侧 `[Errno 2]` 连环失败（工作目录被清理后每轮工具调用必炸）             | ✅ 已修（p12）                         | workspace chdir 状态机 + SyscallProxy 恢复           |
| ④ | tool\_d 执行面单线程，单个工具被占即全服务停摆，且无取消能力                      | ⬜ **本版 §3.1 R1**                  | 预备期仅完成有界化（①），并发/取消模型未动                          |
| ⑤ | runner LLM 工具循环连败无 fast-fail，16 轮烧尽才返                   | ◐ 截断类已修（p6）；**通用连败本版 §3.1 R1**    | 指纹检测（同参同果连续重复）已有，但异型连败（连续不同错误）无熔断               |

**结论**：①③⑥⑦⑧ 五项已闭环；②随预算链闭环；残余 **④（tool\_d 并发/取消）、⑤（通用连败 fast-fail）、⑨（C 侧角色词汇表 SSoT）** 三项，构成本版 R1。

## 2. 预备期专项结论（预算链 / CI 保留 / 截断根因）

### 2.1 预算链终态（已固化，防回归基线）

```
tool 执行 20s < runner IPC 30s < agent_d invoke 170s < CLI 总预算 180s
```

### 2.2 CI 版本保留策略（p5，用户指令落地）

用户指令：**「社区只保留 3 个版本——当前版本 + 上两个版本，每次 CI 发布时都要进行版本处理」**。

- 与 0.1.13 H3「tag 双端自动同步」机制兼容：atomgit 侧同规则修剪。

### 2.3 runner LLM 截断根因与修复（p6，已闭环 + 防回归）

**现象**：fs\_write 大 payload 时内容截断，蓝图节点空转挂死，16 轮烧尽后 `TOOL_LOOP_OVERFLOW`。

**根因链（全部位于 runner 执行体 LLM 客户端层，不经过 llm\_d——LLMClient aiohttp 直连厂商端点，llm\_d 流式聚合嫌疑彻底排除）**：

1. 厂商默认输出上限截断 arguments JSON；
2. `finish_reason` 完全未检查；
3. `json.loads` 失败后静默降级 `{"_raw": …}`，截断信号被吞；
4. 指纹检测对「每次截断内容不同」不敏感（指纹含 raw\_args，每次都不同 → 永不判重）。

**修复（三处系统性修复，非补丁）**：

- `orchestration/core/llm.py`：`_resolve_max_tokens()`（显式参数 > `$AIRY_LLM_MAX_TOKENS` > None 不发送，沿用厂商默认）；`chat()` payload 按解析结果发送/省略 `max_tokens`（L250-263、L344-346）；
- `orchestration/agents/llm.py`：`execute()` 检测 `finish_reason in ("length", "max_tokens")`（L203-204）——截断且 args JSON 损坏 → **立即 fast-fail** **`TOOL_ARGS_TRUNCATED`，不烧轮次**（L251-266）；纯 content 截断 → 显式标记 + `metrics.truncated`（L206-223）；
- `_invoke_tool` 畸形 args 显式回传错误 JSON（`invalid tool arguments JSON` + `arguments_head`），废弃 `_raw` 静默降级（L408-419）。

**测试**：`test_llm_client.py` TestResolveMaxTokens 4 用例 + TestChatPayload 3 用例（fake aiohttp 经 `sys.modules` 注入命中懒导入，L358）；`test_llm_agent.py` 4 用例覆盖 fast-fail 不烧轮次 / 合法不误杀 / content 标记 / 畸形显式回传。**全量回归 158 passed**。

**残余登记**：本修复只覆盖「截断」这一类连败；⑤ 的通用连败 fast-fail（连续异型错误熔断）仍开放，归 §3.1 R1。

## 3. 本版施工清单

### 3.1 R1 蓝图调度挂死收尾（④⑤⑨）

**R1-a tool\_d 并发与取消模型（④）—— 已落地（含本轮根因收口）**

- 现状：tool\_d 执行面单线程；p9 的有界化只保证「单个工具必返回」，不保证「一个慢工具不拖死其它会话」。
- 施工：执行面改造为有界并发（worker 池）+ 每任务携带 deadline（p9 已注入的预算参数复用）+ 取消语义（deadline 到期即终止该工具执行并回报，不影响 worker 池其它任务）。
- 验收：并发两个会话，其一注入超时工具，另一会话工具调用不受影响；被取消工具返回明确取消错误码。

**本轮根因收口（单点 deadline 全链同源）**

p9 落地的池解决了「隔离」，但 deadline 存在**双口径**：池按 `max(meta, executor_timeout)` 等待，
而执行面外部 execvp 路径只取 `executor_timeout`。后果有三：per-tool 预算被忽略（外部路径按默认值计时）、
被判超时的进程其实仍在跑（detach 变成"假取消"）、`max_workers` 配置面是死字段。收口为**唯一 deadline 所有者**：

- `executor_budget_ms(exec, meta)` 成为唯一取值面：per-tool 元数据优先，未声明回退 `executor_timeout_sec`。
  三条路径同源——内置路径 `btimeout_ms`、外部 execvp 路径 `timeout_ms`（经
  `tool_execute_args_t.timeout_ms` → `airy_sandbox_invoke` → `sys_tool_execute` →
  `airy_process_run_capture`，进程到期即 SIGKILL）、池等待 `wait_budget_ms`。
- `executor_pool.c` 的等待预算改为 `executor_budget_ms(...) + WAIT_SLACK_MS (+ 交互审批上限)`：
  slack 只需覆盖 SIGKILL 后的 drain/reap 窗口，进程期限与等待期限 lockstep。
- 缺口 ④ 接线：worker 数来源优先级 **env** **`AIRY_TOOL_EXEC_WORKERS`** **>** **`executor.max_workers`** **> 内置默认 2**
  （越界回落默认），`executor_max_workers()` 为取值 API，`tool_executor_create` 不再硬写 1。

  「次次失败但参数各异」的系统性故障；截断类仍走既有 `TOOL_ARGS_TRUNCATED` 即时 fast-fail，不占连败额度。

预备期端到端审查发现：即便调度不挂死，**DAG 产物在语义层面不可信**。三缺陷：

**A. 规划降级为纯校验（最重）**

#### 3.5.1 对标基准：Claude Code 的三条结构事实

一手输入：`works-engineering/Claude产品结构.md`（241 行）。该文件揭示的三条结构事实，
直接决定本方案的**排序**与**形态**：

1. **单入口多模式，不存在第二个用户面程序**：`claude`（REPL）/ `-p`（headless）/
   `-c` / `-r` / `--from-pr` / `attach <id>` / `mcp` / `daemon` / `update` 皆同一入口的模式分流。
   启动哲学是「**薄入口 + 重模式提前分流 + 主模块延迟加载**」——
   `claude mcp` 永不加载 React REPL，重型模块（OTel ~400KB + gRPC ~700KB）动态 `import()`。
2. **两条渲染路径，一份渲染层**：经典（行式，输出进滚动历史）+ 全屏（备用屏，输入框固定底部），
   由**同一渲染引擎**提供，`/tui fullscreen` 或 `CLAUDE_CODE_NO_FLICKER=1` 切换。
   **不存在两份全屏实现**；终端是「另一个前端容器」，不是文本输出设备。
3. **先稳主路径，再抽共享能力**：`QueryEngine.ts`（约 46K 行）已存在但**主路径不走它**——
   策略原话是「**先把 REPL 路径做稳，再把共享能力向外抽取**」。

**由此纠正的施工排序**：airymax 的真正瓶颈**不是"缺抽象层"**，而是
**入口三套并存 + 状态所有权错置**（审批权威在 `tool_d`、会话权威在 `mem_d`，
而 C 侧 CLI 对二者**零用户面视图**）。故 R5 内部顺序**固定**为：

```
G6 入口唯一化  →  G4/G5 视图归一（前端只读 + 回传 daemon 权威）
              →  G3 客户端归一（agentrt-rs）  →  G1/G2/G7 目录·渲染·元数据收口
```

即**抽象抽取排在最后**——与第 3 条事实一致；先把「唯一入口 + 正确所有权」做稳，
再谈共享能力外抽。（此顺序修订 §7 施工顺序，理由见本节。）

#### 3.5.3 子进程等价形态的接线契约（用户裁定 ④ 的落地语义）

CLI 为父进程、持有除终端以外的一切；TUI 为子进程、持有终端：

| 关注点 | CLI（父，`airy_cli`） | TUI（子，`agentrt-tui`） |
| ------ | -------------------- | ----------------------- |
| 模式决策 | **唯一**（`--tui` 与否 / TTY 探测 / `AIRYRT_FORCE_CLI`） | 无 |
| gateway 客户端 | **唯一**持有（`cli_gw`，A-IPC） | **无**（不持协议客户端） |
| 审批 | **唯一**决议权（`tool.pending` / `tool.approve`） | 只渲染 + 回传按键 |
| 会话 / 记忆 | **唯一**读取 `mem.recent` 并装配视图 | 只渲染 |
| 终端（备用屏 / 原始输入 / 鼠标） | 无 | **唯一**持有 |
| 输入回路 | 收 TUI 上报的按键/文本事件 | 只收事件、只回输入 |

- **通道**：CLI ⇄ TUI 采用**继承 fd 上的 JSON Lines 事件流**（CLI→TUI 事件 / TUI→CLI 输入）。
- **判据说明（必须登记）**：该通道位于「**TUI 是 CLI 的渲染层**」这一**同层内部边界**，
  不属服务面通信，故**通信铁律（全链统一 A-IPC）不适用**；此为**已登记例外**，
  须写入门禁 T2/T5 判据集，避免后续评审反复。
- **失败可判读（判据④）**：TUI 子进程退出码 ≠ 0 时，CLI **只报错、不接力**——
  删除现有 `sdk/tui/scripts/airymaxrt` 的「TUI `rc!=0` → 自动续接 `airy_cli`」逻辑。
  该逻辑会制造**双份终端状态**（备用屏未还原 + 第二套 UI 接管）与**用户面不一致**，
  是"运行不稳定"的直接来源之一。

### 4.5 前移项施工实况（含被取证推翻的方案预估）

前移裁决不等于原方案描述可照抄——本轮施工有 **3 项**的方案预估被一手取证推翻（F6 / maths\_d / WS-8），
按「不打补丁、找根本原因」改判后落地的实况如下。

**F6 heapstore 并发回滚**：原记指向 `heapstore/kernel/services/trace_store_service.c`
（`static uint32_t counter` 无锁、batch 逐条调用无回滚）。取证推翻该定位——该文件与
`log_store_service.c` **无头文件声明、全仓零调用方、无历史**，仅被 `heapstore/CMakeLists.txt`
编入 `airy_heapstore`，属**不可达废体**，其缺陷不可触发。故**物理移除废体**（连同
`kernel/README.md` 与空目录 `kernel/services/`），CMake 源清单与中英 README 仓库布局同步收敛。
真实并发面在 `heapstore/src/heapstore_trace.c`（有 `.h` 导出，被 core/examples/tests/benchmark 调用），
修三处实证缺陷：① `heapstore_trace_query_by_trace` 分配后**提前解锁**再于锁外读共享 `s_span_buffer`
（数据竞争）且函数末**重复解锁**（UB）→ 全程持锁、深拷贝失败路径补解锁、函数末唯一解锁点；
② 同函数深拷贝失败分支未解锁即返回（锁泄漏）同批修正；③ `heapstore_trace_write_spans_batch`
缺 `attributes` 深拷贝（调用方释放自有副本后缓冲内残留悬垂指针），补深拷贝并**任一条分配失败即
回滚已深拷贝前缀槽位、不增计数**，`write_span` 失败槽位补 NULL 归零。回归锁
`heapstore_tests` 三用例（roundtrip 含时间范围包含语义 / batch 提交后立即释放调用方副本 / 4 写 ×100 与
2 查 ×200 交叉）：`ctest -R heapstore` **8/8**，TSan 与 ASan+LSan **零报告**。配套：函数名基线
去掉已消失的 `log_store_service_*` / `trace_store_service_*` 等 **77 项**陈旧债务。

**D9-a `cli_gw_call` 失败填因**：原判「一行级」。实况是所有权收口——`g_cli_gw_err` 由跨 TU 可写裸全局
收为 `cli_gw.c` 模块内 `static` 唯一权威，对外仅经 `cli_gw_last_err()`（只读）/
`cli_gw_err_take()`（一次性消费）/ `cli_gw_err_set()`（上层写入）三个访问器，四处跨 TU 声明清零；
`cli_gw_call` 此前静默 `return -1` 的五条失败路径（请求缓冲分配失败、信封构造溢出、响应非 JSON、
响应缺 `result`、响应序列化失败）全部填因，调用方契约路径（`method` / `out_result` 为空）同步补因，
现函数内 10 处失败出口全部可判读。回归：`cli_gw_e2e` **39/39**；门禁 T3 新增「静默 `return -1` 禁止」
断言——以 awk 提取 `cli_gw_call` 函数体，逐条 `return -1;` 回溯 15 行内必须存在错误写入，
否则 T3 失败（**负例已实测可捕获**，断言非空转）。

**maths\_d docker 部署面**：构建面早已完整（`daemons/CMakeLists.txt` 已 `add_subdirectory(maths_d)`、
`install(TARGETS maths_d DESTINATION bin)`、`Dockerfile.daemon` 的 `COPY --from=builder` 已带入镜像），
缺陷**仅在运行编排面**：`supervisord.conf` 的 program 清单与进程组均漏登，`docker-compose.yml` 无对应

**不接受 `--manager`**，仅监听 Unix socket `maths.sock`，故 supervisord command 写无参。落盘四处：
`[program:maths_d]`（autostart/autorestart、startretries=3、startsecs=5、stopwaitsecs=10、日志轮转 20MB×5）、
`[group:daemon-services]` 追加至 **15 成员**、compose 新增 `maths_d` service（轻量减配 1.0 CPU / 256M）、
README 计数 13→14 与 15→16。机械自检三重通过（YAML 解析 services **16** 且 maths\_d present；
configparser programs **15**、missing `[]`、unreferenced `[]`；全仓 supervisord.conf 引用仅两个 Dockerfile）。
端到端旁证：网关侧 `GW_NS_OWNER` 与 `maths.health_check` 能力早已登记，编排面补齐后自网关至 daemon 全通。

**WS-8 阶段 3「翻默认」**：方案预估「仅配置变更」被本轮取证推翻。corekern binder L1 为**纯进程内传输**
（进程内链表、`ch->fd=-1`），多进程生产拓扑下 L2-first 连接必然 ENOENT；而 daemon 侧 `daemon_rpc_call`
对 L2 miss **fail-fast 无回退**（原理由「开关是运维显式动作」在默认翻转后失效——默认 on 时「开关开」
不再蕴含「桥已挂载」）。若不修，llm\_d cache 读写、agent\_d think/tool/complete、sched\_d
spawn/invoke/terminate、CLI health/shutdown 等调用在生产拓扑全部断链。修正为**可证明未派发才回退**的
安全集：ENOENT（本进程无桥，跨进程灰度常态）与 CANCELED/ECANCELED（信封丢弃/目标已死，均未触达
dispatch）回退 socket 路径（DEBUG 留痕不刷日志）；**GENERIC_FAIL（业务 error 折叠）与 ETIMEDOUT

`gw_aipc_call` 全量回退语义不变；流式与可取消调用维持 socket 路径（chunked 回复暂无 L2 映射）。
「jsonrpc」保留为运维回退逃生门，未知值仍 fail-closed WARN。测试同步：默认断言由
`test_transport_default_off` 改为 `test_transport_default_on`，off 路径改用显式逃生门触发。
证据：传输关联面 15 测试全过、全量 **216/216**、TSan l1/l2 零报告（容器内 ASLR 冲突以 `setarch -R` 直跑 14/14）。

**D9-b TSan 13 项清零**：方案承诺「至少完成复扫定性，修复量力入版」，本轮**超额全清**。定性结论：
13 项（含复扫新增暴露面）**全部为测试侧 mock harness 竞态，产品代码零报告**——worker/服务线程实现
（如 `thread_pool.c` 出队持锁、执行独立）逐帧核验无罪，竞态对端均为测试主线程无同步裸读或 mock 停机
次序不当。按竞态类别归一修法四类：① 测试侧 **`_Atomic` 化（11 文件）**——跨线程共享标志/计数 `volatile`
统一升格 C11 `_Atomic`（定义/extern/struct 字段三形态），GCC 内建 5 处替换为标准原子操作，
`test_e2e_core.c` 回调指针根修（`(int*)` cast 后自增仍是普通写 → 双向 `(_Atomic int*)`）；
② **`listen_fd` 先于 join 置位（3 处同构）**——roundtrip / aipc / llm\_d 三个 mock 原在 `pthread_join`
之前置 `listen_fd = -1`，与服务线程 `accept()` 读竞态，统一重排为 `shutdown/close → join → 置位`；
③ **exec 日志双计数器发布**——原占位式自返（`fetch_add` 占位后写槽，count 达标时槽位可能未写完），
返工为「占位选槽 + 完成后发布」双计数器，14 处 reset 收敛为 `exec_log_reset()` 唯一入口；
④ **栈缓冲发布边沿**——aipc `stream_arg.last_req` 补 `_Atomic int ready` 发布标志。
排除项：`g_cli_cancel` 维持 `volatile sig_atomic_t` 不动——POSIX 信号语义 SSoT（产品定义、头文件 extern、
门禁断言三处一致），升格反而破坏契约。验证链三轮演进：**9 失败 / 25 WARNING → 4 失败 / 6 WARNING →
216/216 PASS、WARNING 0、退出码 0**。过程机制留档：TSan 检出 warning 后即使 `halt_on_error=0` 进程退出码
仍被置 66，且 WARNING 只落 `LastTest.log` 不上 ctest stdout——**CI 判定必须双查退出码与日志**。

**架构铁律（五句话）**：TUI 渲染，CLI 组织，gateway 翻译，daemon 干活，内核机制只被 daemon 服务面访问；其中 TUI 是 CLI 的增强包，是 CLI 的渲染层。

上述两项是**判据**而非口号：任何设计若违反，即便功能可用也须整改（逐条落判见 §11.2，可执行动作与验收证据见 §3.5「R5 终端 / CLI / TUI 分层收敛」）。

### 11.3 通信铁律例外登记（已登记，防评审反复）

CLI ⇄ TUI 采用**继承 fd 上的 JSON Lines 事件流**（CLI→TUI 事件 / TUI→CLI 输入）。该通道位于「**TUI 是 CLI 的渲染层**」这一**同层内部边界**，**不属服务面通信**，故**通信铁律（全链统一 A-IPC）不适用**——此为**已登记例外**，已写入门禁 T2 / T5 / T7 判据集（§13.3），禁止后续评审按「A-IPC 全链统一」铁律误判为违规。

### 12.2 轨迹结论与三类系统性缺口

0.1.9–0.1.16 的成本结构是「**设计先行、接线滞后**」——方案覆盖度已足，但存在三类系统性缺口（本轮取证证明）：

1. **能力已建、主链路未接**（语义缓存 / 台账 / 压缩；见 §12.3 与 §3.6.1）；
2. **门禁未覆盖运行态**（0.1.13 审查已指出，0.1.15/0.1.16 补 e2e 但仍非全量）；
3. **取证口径本身有盲区**（`.gitignore` 白名单缺失，见 §12.4）。

因此 0.1.17 的收敛原则是：**不再新增设计面，只做「接线 + 根因 + 判据固化」**。据此，§4.2 中属"架构面重构"的项一律不前移（F1 / F2 / F3 / S5 / I3-I5 / J-K-M），而 W / N / L / S / B / T 六组接线项全部入版（§3.6）。
