# 0.1.19 架构文档

> **文档定位**：`agentrt` **0.1.19 目标态架构**的权威描述——说清「0.1.19 的 agentrt 长什么样」。
> **配套文档**：`0.1.19-架构改进方案.md`（说清「怎么改造成这样」）。本文只描述**架构本身**，施工步骤、账目明细、门禁执行细则见方案。
> **纲领**：**机制与策略极致分离**
> **主线**：**原子化 · 能力格 · 形态面** —— 立格（Slot）→ 造件（Atom）→ 成面（Facade）
> **最高约束**：功能守恒（对外功能一个都不能少） + 生产码 `agentrt` **机制核五单元**（`atoms` + `commons` + `heapstore` + `gateway` + `cmake/`）**SLOC 有效行 < 80,000 行**（`*.c`/`*.h`，不含 `tests/`、`third_party/`，扣除空行与整行注释；口径终裁见方案 §1.2 丙 r3）
> **体验账**：`sdk/tui` **不设总量上限**，以能力矩阵无空格为准
> **主要读者**：Airymax 核心开发组

## §1 架构总纲

### 1.1 一条纲领

**机制与策略极致分离**。

`agentrt` 的一切代码只用一个问题裁定归属：**这是机制，还是策略？**

- 答「**机制**」→ 留核，原子化、填格、成面；
- 答「**策略**」→ 让位，经 `ops` 函数表 + `.manifest` **数据化注入**，或整体**迁到生态层**。

机制核**零策略载荷**：不含厂商名、不含产品名、不含业务阈值、不含 `if (vendor == …)`。凡出现，即为架构违例（门禁 G18 / G19 静态断言，fail-closed）。

> **三义辨（防混算，方案 §1.1）**：**(a) 体积核**（LOC 硬门禁）= `atoms` + `commons` + `heapstore` + `gateway` + `cmake/`，**SLOC 有效行**现值 **85,535**（对应 PLOC 133,880）；**(b) 策略扫描面**（G19）= `agentrt/` **八模块全量**（含 `daemons`/`protocols`/`tools`，台账 §66，1,323 文件），**非体积口径**；**(c) 纲领留核** = 机制/策略**语义裁定面**。三者不可混算——G19 扫全量，G2/G31 只量体积核。

### 1.2 主线三步

| 步 | 名             | 内容                                             | 验收执法                      |
| - | ------------- | ---------------------------------------------- | ------------------------- |
| 1 | **立格** Slot   | 25 + 3 个能力格构成永久坐标系；**格固定不变，且不留空格**（留格建件）       | G17 `slots` 字段 / G11 准入留痕 |
| 2 | **造件** Atom   | 每格一件；同类件塌缩归一；准入三问裁定什么够格当原子件                    | G9 N 判据 / G32 双达标         |
| 3 | **成面** Facade | 原子件经 `⊗` 装配为组合件，按职责面收敛为 4 个形态面；`main.c` 只启动组合件 | G16 五件套 / G15 四面不混        |

**格件关系**：**固定的是格，变化的是件。** 讨论「要不要加一个模块」时，先问「它填哪个格」；答不出格的，就是不该造。

### 1.3 三条减法托底

功能一行不减，体积靠三条减法达成：

| 减法     | 含义                            | 通道   |
| ------ | ----------------------------- | ---- |
| **迁出** | 策略与体验面离开机制核（搬迁，非删除；功能在别处继续提供） | 迁出账  |
| **塌缩** | 同类件收敛为每格一件                    | K 通道 |
| **生成** | 五件套样板由生成器产出，不手写               | S 通道 |

## §2 架构语言：Slot / Atom / Composite / Facade

### 2.1 四个概念

| 中文      | 英文            | 定义                    |
| ------- | ------------- | --------------------- |
| **能力格** | **Slot**      | 能力的最小归类槽位，**固定不变**    |
| **原子件** | **Atom**      | 填入某个格、不可再分、只含机制的最小实现件 |
| **组合件** | **Composite** | 两个及以上原子件按 `⊗` 装配得到的组件 |
| **形态面** | **Facade**    | 按职责面暴露的组合件集合，是服务层的「面」 |

> **统一自检句**：`Taskflow is an atom in the flow slot, exposed by the sched_d facade.`

### 2.2 核心关系式

```
面 Facade = 声明（manifest）+ 生成（样板）+ 组合件装配（Composite 承载）
格 Slot   ←固定→   件 Atom ←可变→
功能 = 原子件 ⊗ 装配 → 组合件 ⊗ 再装配 → 形态面
```

### 2.3 术语规范

**用语规范（全文强制）**：「死码」→ **死代码**；「出清」→ **清理**；「收口」→ **收敛**；「方言」→ **适配实现**；「打样」→ **样板改造**。

**禁止旧称（不得新增使用）**：capability lattice、aspect、面化、功能面、形态层、原子原语、原子组件、复合件、composition；**`Atomic`** **不得作可数名词**（形容词不作名词，且与 C11 `<stdatomic.h>` 冲突）；`manifest` 字段 `aspects` 更名 **`slots`**。

**术语权威源**：`docs-workload/00-requirements/10-terminology.md`；手册侧见《agentrt 工程标准规范手册》§1.6。

### 3.2 留格建件（不留空格）

格是坐标系，坐标系上每个格位都是**架构承诺**。格上无件 = 能力缺位，靠各处私搭乱建维持（DAG ×7、checkpoint ×8 正是「格上无母件、各处自建」的实态）；有件无扇入 = 死件占格。

**因此不留空格**：每个格都要有件，每个件都要有有效扇入——**每个格都有有效扇入，系统的基本能力才是正常运行的状态**。

**待建二格路径**：

| 格      | 母件                                     | 施工同场                                           | 扇入来源                                               |
| ------ | -------------------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| **事务** | heapstore **分区事务件**（多分区原子提交 / 回滚）      | L5 与 D 通道分区收敛同场（行数并入 D 账，不新增总账）                | heapstore 分区写入 · checkpoint 一致性快照 · taskflow 作业原子性 |
| **复制** | **状态快照复制件**（快照导出 / 导入 = 跨实例 / 跨时刻状态复制） | L5 与恢复格母件**同源分化**（一套序列化骨架；行数并入 K checkpoint 账） | heapstore · mem\_d 记忆快照 · cognition 会话保存           |

**双期限以先到者为准**：「最迟 L5」（工程序）与「六个月内建成」（日历）并存时取更早到期者；逾期提交架构裁决。建成前记为 ⏸ **待建件**（**非豁免态**）。

### 3.3 格格双达标（全格无豁免）

主线三步不是「做了就算」，**每个能力格的落点件必须双达标**：

| 判据         | 内容                                                                                                     | 不达标处置                                      |
| ---------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| **① 有效扇入** | 真实消费点（跨模块**符号调用/链接引用**的消费者文件数）实测 **≥ 3**（与准入三问 N ≥ 3 同源）；`#include` 与伞形头扩散**不算消费**，仅作初筛（2026-09-26 口径） | 扇入 0 = 死件（G28 清扫）；扇入 1\~2 = 低扇入（就地内联或补消费者） |
| **② 运行正常** | 落点件**有 tests 且接线 CI**（`add_test` + workflow），golden 全绿                                                 | **有测试未接线 = 未达标**（等同没测）                     |

**扇入口径**：有效扇入 = 真实消费点——跨模块**符号调用/链接引用**的消费者文件数（本模块自用不计；`#include` 与伞形头扩散仅作初筛，不计为扇入）。

**为什么每个格都要有有效扇入**：扇入 ≥ 3 = 该能力被至少三个子系统真实复用，是公共基本能力而非私有代码；扇入 1\~2 = 私有细节冒充能力（应内联）；扇入 0 = 死件占格；空格 = 该能力靠各处私搭维持。

**28 格终态 = 全部有件 + 全部有效扇入 ≥3 + 全部接线运行正常。**

### 3.4 落点格与格上件

支撑其他格的核心格位与其落点（完整审计见方案 §2.8）：

| 格       | 落点件                                                        | 状态                                |
| ------- | ---------------------------------------------------------- | --------------------------------- |

## §4 组合件与形态面

### 4.1 组合代数：`⊗` 与 `⊙`

| 算子             | 时相  | 边界  | 类型                  | 通道                      |
| -------------- | --- | --- | ------------------- | ----------------------- |
| **`⊗`** **装配** | 装配期 | 进程内 | `A×A→C/F`、`C×A→C/F` | 函数调用                    |
| **`⊙`** **编排** | 运行期 | 跨进程 | `F×F→F_sys`         | **IPC / syscall（唯一通道）** |

**`⊗`** **五性质**：

| 性质      | 内容                                        |
| ------- | ----------------------------------------- |
| 类型律     | `A×A→C/F`，`C×A→C/F`                       |
| **地位律** | **`F⊗F`** **非法** —— 面不能与面装配（面之间只能 `⊙` 编排） |
| 闭合律     | 装配结果仍是 `C` 或 `F`，封闭在代数内                   |
| 结合律     | `(a⊗b)⊗c = a⊗(b⊗c)`                       |
| 幂等律     | `x⊗x = x`（同件重复装配无额外语义）                    |

**为何** **`F⊗F`** **非法**：面是进程边界上的职责视图，面与面的关系只能是运行期编排；若允许面直接装配，就会退化为「一个大进程装下所有功能」，微核心架构即失效。**违反即 fail-closed 拒绝**（门禁 G14，不是警告）。

### 4.2 四个形态面（固定不变）

| 面              | 职责                | 例                    |
| -------------- | ----------------- | -------------------- |
| **ingress**    | 入口：接收、校验、反序列化     | `sched_d` 接 DAG 提交请求 |
| **execute**    | 执行：调度、调用原子件、装配组合件 | 运行 DAG               |
| **state**      | 状态：持久化、查询、恢复      | 写 checkpoint         |
| **governance** | 治理：策略裁定、限额、审计     | 拒绝越权计划               |

**daemon = 跨四面，不可拆**：一个 `*_d` 天然横跨四面，**四面是它的视图，不是四个可独立拆出的进程**。

> **编号警示（铁律 13）**：`coreloopthree` 的「三面」（认知 / 规划 / 执行）**≠ 形态面四面**（3 ≠ 4），**严禁互称**。

### 4.3 五件套（形态面的物理形态）

| 件    | 形式                        | 约束                        |
| ---- | ------------------------- | ------------------------- |
| ① 声明 | `.manifest`（含 `slots` 字段） | 机器可读，缺失即门禁失败；发布即冻结        |
| ② 入口 | `main.c`                  | **≤ 150 行**（只做装配与启动，不写逻辑） |
| ③ 实现 | `svc.c`                   | 主体逻辑                      |
| ④ 组合 | `modules/`                | 装配清单，声明用了哪些原子件            |
| ⑤ 装配 | **唯一私有头**                 | 全模块唯一一个私有头                |

**目标态**：16 个 C daemon × 5 件齐全 + `scripts` 户仅登记 `.manifest`（G16；`scripts` 户为 CI 脚本集、无 C 生产码）；现状 `main.c` 合计 7,825 行 → 目标 16 × ≤150 ≈ **≤ 2,400 行**。

### 4.4 禁薄胶水组合

**不能用薄胶水层的方式组合——薄胶水组合使系统不稳定**：

| 缺陷        | 说明                                                               |
| --------- | ---------------------------------------------------------------- |
| **无契约**   | 薄胶水是过程代码里的隐式串联——无类型签名、无生命周期、无错误传播约定。原子件接口一变，胶水静默脆断，故障在组合点爆发且难定位  |
| **无测试**   | 薄 = 覆盖盲区。组合点恰是故障高发区（装配次序、状态一致性、错误传播），却游离在 tests/CI 之外——格格双达标对它失明 |
| **复杂度散落** | 装配决策散成 N 处隐式胶水，每处都是独立失效模式，无单一可审计点——「系统怎么组合的」无法回答，只能考古            |
| **无问责**   | 胶水不是件——没格、没扇入、没双达标，架构语言三概念（格 / 件 / 面）对它全部失明                      |

**替代：组合一律经组合件（Composite）承载**——

- `⊗` **显式装配**，装配契约（输入 / 输出 / 生命周期 / 错误传播）落在组合件代码内；
- 组合件有自己的 tests 且接线 CI（**双达标延伸到组合层**）；
- 组合件可测扇入，装配关系可审计；
- `main.c` **只启动组合件**，不直连原子件散件。

### 4.5 组合件层审计（与原子件同尺）

| 审计项   | 判据                                                                | 台账落点                                     |
| ----- | ----------------------------------------------------------------- | ---------------------------------------- |
| 组合件登记 | 每个组合件登记「装配了哪些原子件（`⊗` 链）」；薄胶水串联（散落 if / 转发调用直接串原子件、无组合件实体）= 未登记组合件 | `.manifest` `slots` 字段 + `modules/` 装配清单 |
| 组合件扇入 | 组合件被 **≥ 3 处**消费；1\~2 内联，0 删除                                     | 逐件 `#include` / 调用点实测                    |
| 组合件运行 | 组合件 tests 接线 CI、golden 全绿                                         | `add_test` + workflow                    |

**已知组合件实例**：GRAD（`grad_verifier` + `grad_coordinator` + `stream_critic`）、GCCP、双思考（`dual_model` + `arbiter`）、`hall_store` 家族、恢复母件 + 复制件（同源分化对）。

### 4.6 两条冻结律

- **引用律**：形态面**只引用公开头**；跨面调用必须经公开头，不得直接触碰他人私有头。
- **冻结律**：`.manifest` 一旦发布即**冻结**，变更须走版本递增，不得原地改语义。

## §5 机制与策略分离（纲领落地）

### 5.1 分离四层（自内向外）

| 层         | 内容                             | 形态       |
| --------- | ------------------------------ | -------- |
| **L1 机制** | 不含任何策略的原子件                     | 代码       |
| **L2 契约** | 接口与数据结构                        | 公开头      |
| **L3 注入** | 策略经 `ops` 函数表 + `.manifest` 注入 | 数据       |
| **L4 策略** | 具体决策（阈值、厂商、权重、规则）              | 数据 / 生态层 |

### 5.2 两条硬规

1. **策略只经** **`ops`** **函数表 +** **`.manifest`** **注入** —— 不得在机制件内 `#include` 具体策略、不得 `if (vendor == …)`。
2. **机制核零策略载荷** —— 机制核内出现厂商名、产品名、业务阈值即门禁失败。

### 5.3 注入形态

```c
/* L2 契约层（公开头）：只含机制语义，不含任何策略 */
struct sched_policy_ops {
    int (*decide)(void *ctx, const struct sched_input *in);  /* 策略裁决点 */
};

/* L1 机制件：只见 ops 指针，不见厂商 */
int sched_submit(const struct sched_policy_ops *ops, void *ctx, ...);
```

**收益**：策略变数据后，一类决策从「N 份代码」变成「1 个件 + N 份数据」，直接消灭 K 通道重复。

### 5.4 结构规约：「`atoms` 怎么长」六条

只规约**结构**，**不规约域清单**（域清单由能力格决定，不由本规约锁定）：

| 条 | 规约                                |
| - | --------------------------------- |
| 1 | 各模块 `src/` 内**按机制域分目录**           |
| 2 | 公开头一律收进 `include/`                |
| 3 | 私有头命名 `<域>_internal.h`            |
| 4 | **跨域只走公开头**（不得引用他域 `_internal.h`） |
| 5 | 配套子库须登记理由（为何不复用既有件）               |
| 6 | 枢纽头入度 ≤ 5（头被引超过 5 处即须拆分）          |

> 与 daemons 侧「五件套」性质不同：五件套规约的是**装配期物理形态**，本规约规约的是 `atoms` 侧**源码结构**。二者按不同名目使用，不得互称。

### 5.5 原子件准入三问

任何拟新增 / 保留的件，必须**三问全过**：

| 问                 | 判据                        | 不过的后果             |
| ----------------- | ------------------------- | ----------------- |
| **① 是机制吗？**       | 不含业务策略、不含厂商名、不含产品决策       | 不是 → 归**策略**，迁生态层 |
| **② 是收敛型抽象吗？**    | 收编后总行数下降，且抽象带**语义**而非仅签名  | 不是 → 是**伪抽象**，禁止  |
| **③ 复用 N ≥ 3 吗？** | 独立使用点 ≥ 3（N=2 须证同构，N=1 禁） | 不是 → 不建件，就地内联     |

**杠杆判据（准入与收编同一把尺）**：

| 同类实现数 N   | 裁定      | 记法          |
| --------- | ------- | ----------- |
| N ≥ 8     | **必收**  | η ≥ 3，收益确定  |
| 3 ≤ N < 8 | **应收**  | η 正，收益可测    |
| N = 2     | **条件收** | 须证明两者语义同构   |
| N = 1     | **禁收**  | 不得为「将来复用」造件 |

## §7 运行视图

### 7.1 进程与通道

- **跨进程**：唯一通道 = **IPC / syscall**（`⊙` 编排）；**零进程内符号引用**（门禁 G23）。
- **进程内**：唯一装配方式 = `⊗`（函数调用），装配经**组合件**承载。
- **层界单向**：不出现反向依赖（门禁 G21）。

### 7.2 运行不变量（2026-09-26 llm.rpc 社区案例实证提炼）

五条运行时不变量，违反任一 = 架构违例（案例七环归因与源码锚见方案 §2.9）：

1. **路由不得由错误驱动**——错误日志是记录格的输出，不是通信格的控制流；传输选择在 init 期一次性定型（能力探测 / `.manifest` 声明），调用路径**零 try-fail-fallback**。
2. **健康 = 端到端可达**——发现格母件给出唯一健康定义（SD 健康态消费）；socket 文件存在、进程存活等代理指标不得冒充健康（僵尸 socket 文件误报 connected = 违例样本）。
3. **硬依赖缺失必须降级态显式上报**——`.manifest` `required` 声明 + governance 面启动检查；**禁止静默 ready**（llm\_d 缺位而 orchestrator 照常启动 = 违例样本）。
4. **时间序单调**——记录格 wall+mono 配对时间戳：排序与耗时按 monotonic，绝对时刻按 wall；信号处理器输出经 async-signal-safe 缓冲带戳写入（NTP 回拨致日志倒序 = 违例样本）。
5. **失败必可行动**——错误载荷带 cause + remedy；「target not found」类裸错误（不指明哪个服务缺位、如何恢复）= 违例。

### 7.3 体验面：TUI 只是 CLI 的渲染

**核心等式**：

```
TUI 输出 = fold(CLI 事件流)
```

| 边        | 内容                                                                          |
| -------- | --------------------------------------------------------------------------- |
| **纯投影**  | TUI 是 CLI 事件流的**纯投影**，**零业务决策**——不判断、不重试、不裁剪业务                              |
| **接线契约** | **CLI 父进程持除终端外的一切**（状态、会话、业务），**TUI 子进程唯一持终端**；通道 = **继承 fd 上的 JSON Lines** |
| **单所有者** | 同一终端同时只有一个持有者；切换须经所有权移交（`lifecycle::singleowner`）                           |

**唯一实现**：`sdk/tui`。`agentrt` 内 C 版体验面**全屏套件消亡、行式（readline 系）留守 CLI**。详见 `0.1.19-TUI建设方案.md`。

### 7.4 认知负载

认知负载**只打在** **`think_d`**（门禁 G22）。

## §9 架构速查

### 9.1 一页纸

```
纲领      机制与策略极致分离
主线      立格(Slot) → 造件(Atom) → 成面(Facade)
坐标系    25+3 格（基础 10 · 中间 8 · 应用 7 · 补充 3）
件        每格一件；同类件塌缩归一；准入三问（机制？收敛？N≥3？）
面        4 面（ingress/execute/state/governance）× 五件套
组合      ⊗ 装配（进程内）· ⊙ 编排（跨进程）· F⊗F 非法 · 禁薄胶水
验收      格格双达标（有效扇入 ≥3 + tests 接线 CI）· 全格无豁免
运行      路由不由错误驱动 · 健康=端到端可达 · 降级必显式 · 时间序单调 · 失败必可行动
体积      机制核（atoms+commons+heapstore+gateway+cmake）85,535 → <80,000（SLOC 有效行）
体验      sdk/tui 不设上限；TUI = fold(CLI 事件流)
```

### 9.2 自检句

- `Taskflow is an atom in the flow slot, exposed by the sched_d facade.`
- 「这是机制，还是策略？」——答不出，即违例。
- 「它填哪个格？」——答不出格的，就是不该造。
- 「组合怎么承载的？」——答不出组合件实体的，就是薄胶水。
