## 3. B1 设计：payload 层落地

### 3.1 规范矛盾裁决（必须先定）

`02-ipc-protocol.md` §3 自称「payload 协议类型由 payload 体首字段携带」，
但其定义的 5 个结构体**首字段均非 type**（如 REQUEST 首字段是 request_id）。
设计裁决（回写规范时一并修正）：

- payload 线格式 = **4 字节判别头 + 结构体体**：
  `struct airy_ipc_payload { __u32 type; __u32 reserved; __u8 body[]; }`，
  `type ∈ {0x0001 REQUEST … 0x0005 CONTROL}`（`AIRY_IPC_PT_*` 宏，与规范
  §3 表格同值）；
- 规范中 5 个结构体 = `body` 段（即「体」），字段零改动，保持与文档逐字段
  同构；文档措辞由「体首字段」修正为「payload 首部判别字段」。

### 3.2 [SC] 契约层新增（commons/include/airymax/ipc.h）

只新增、不改既有布局（128B 头冻结不动）：

1. `AIRY_IPC_PT_REQUEST/RESPONSE/EVENT/STREAM/CONTROL` 五宏（0x0001–0x0005）；
2. `struct airy_ipc_payload`（8B 判别头）+ 5 个 body 结构体，字段与规范 §3.1–3.5
   完全一致（uint64_t request_id / uint32_t method_id / uint32_t timeout_ms /
   柔性数组 params 等）；
3. `AIRY_IPC_STREAM_FLAG_FIN/RST/MORE`、`AIRY_IPC_CTRL_HELLO…FLOW_ON` 常量组；
4. `_Static_assert` 锁判别头：`sizeof(airy_ipc_payload)==8`、`type @ offset 0`、
   各 body 结构体首字段 8 字节对齐。

### 3.3 L2 桥升级（daemons/common/src/daemon/daemon_l2_bridge.c）

- `daemon_l2_envelope_encode/decode` 增 type 参数：payload 前置
  `airy_ipc_payload` 判别头；**既有 JSON-RPC 文本标记为 PT_REQUEST/
  PT_RESPONSE**，线格式变更随本版本双侧同步发布（L2 为 opt-in 灰度通道、
  非默认，无存量兼容负担；overlay version 字段同步 +1 作机器判别）；
- 新增判别头帧化助手（与 `daemon_l2_envelope_encode/decode` 同层）：
  - `daemon_l2_payload_frame(type, body, len, out, cap, out_len)`：封装
    `[8B 判别头][body]`，未知 type（越出 0x0001–0x0005）拒收；
  - `daemon_l2_payload_parse(payload, len, &type, &body, &len)`：解复用判别头，
    非零 reserved 拒收（`AIRY_ERR_PROTOCOL`），legacy JSON-RPC 文本归为无类型
    （`type == 0`）透传，由调用方映射到 REQUEST/RESPONSE；
- 新增三个 typed 发送 API（与 `daemon_l2_rpc_call` 同层，均 fire-and-forget）：
  - `daemon_l2_publish_event(channel, topic_id, priority, data, len)` → PT_EVENT
    （`event_id` 由单调时钟赋值）；
  - `daemon_l2_stream_send(channel, stream_id, seq, flags, chunk, len)` → PT_STREAM
    （单一发送入口；flags 携带 `AIRY_IPC_STREAM_FLAG_MORE/FIN/RST`）；
  - `daemon_l2_ctrl_send(channel, opcode, arg)` → PT_CONTROL（HELLO/BYE/PING/PONG/
    FLOW_OFF/ON 即插即用）；
- 消费侧语义（实测口径，非「双向/订阅」）：`daemon_l2_bridge` 对 typed
  EVENT/STREAM/CONTROL 一律经 `notify` 回调 fire-and-forget 上抛（无应答），
  typed REQUEST/RESPONSE 不入该路径；L2 桥是**类型化透传层**，不承担分片重组、
  乱序拒收与订阅维护——顺序判定/重组/重连由消费方承担。

### 3.4 退出判据

- [SC] 头新增结构全部过 `_Static_assert` 与既有合规严格模式（`-Werror`、
  banned_functions）；
- 新增 ctest（`svc_test_daemon_l2_bridge`）：L2 桥 EVENT 发布往返、STREAM 分片
  传输（MORE/FIN(EOF)/RST 三态保真，seq/flags 原样透传、不重排不拒收）、
  CONTROL PING/PONG 往返、类型判别错误注入（未知 type 拒收、非零 reserved
  拒收、legacy JSON 文本归无类型）；
- 口径修正（2026-09-14 施工期实测）：原判据「STREAM 分片重组（乱序拒收）」在
  本层不可达——L2 桥为**类型化透传层**，无重组状态、无 seq 顺序判定；已按
  §3.3 消费侧语义收敛为「三态（MORE/FIN/RST）保真 + seq 原样透传」，乱序判定
  与分片重组归消费方职责；
- 规范文档回写：判别字段措辞修正 + 「已实现」状态标注（归 B8）。

## 5. B2+B4 设计：CLI 收回与构建收口

### 5.1 B2 取证结论（本设计实测，风险重估）

CLI 对 corekern 的**运行时机制消费近乎为零**：

- `airy_loop_*`（loop 引擎）定义在 **coreloopthree 自身**（`loop/loop.c`），
  非微核心；`airy_task_plan_t` 亦为 coreloopthree 类型（`cognition.h:119`）；
- 真正的微核心机制调用仅 `airy_time_*`（无状态时钟函数，4 个符号）；
- `AIRY_CALLOC` 等 = libc malloc 包装（`alloc.c:213` AIRY_MALLOC 直通），
  无池化状态依赖；
- `airy_ipc_*`/`airy_oom_*`/`airy_persist_*` 在 coreloopthree **零函数调用**
  （31 处命中均为类型/注释）。

结论：`airy_init()` 在 CLI 内**实际只提供日志初始化与状态位**，摘除是低风险
动作；历史「地基归位」的实质需求（拿 coreloopthree/契约层头文件）已由 atoms
自身 CMake 接口目标满足，corekern include 属借道残留。

### 5.2 迁移步骤

1. `main.c`：删除 `airy_init()`/`airy_shutdown()` 调用与 `airy_rt.h`；
   启动诊断改为 gateway 连通性探测（「badge=0 降级」概念一并废除）；
2. CLI 源码 5 处 `airy_rt.h` → 换窄头（coreloopthree / `airymax/` 契约头；
   逐文件核对类型来源）；
3. `tools/airy_cli/CMakeLists.txt`：删 `airy_atoms`（:102/:113/:124）与
   corekern include（:154-158）；
4. `link-whitelist.txt:50`：`airy_cli` 行删 `airy_atoms`；
5. `main.c:176-195` 注释提及的 8.4.2 运行门禁 grep 串同步更新（搜
   「corekern core initialized」消费点）；
6. 施工时验证两处登记项：`AIRY_LOG_*` 未 airy_init 时的默认行为；CLI 全量
   ctest 回归。

### 5.3 B4 构建收口

1. 根 CMakeLists：删除 :789/:805/:833 三处 `atoms/corekern/include` 全局
   注入；改为 atoms 内部目标（corekern 库自身 + coreloopthree 经 atoms
   CMake 接口获取所需头，不暴露 corekern 头）；
2. :1032 `install(DIRECTORY … include/agentrt/corekern)` 移除（内核头不进
   发布面；agent-linux 的 uapi 走其自身发行）；
3. `link-whitelist.txt` 头注补第 2 句判据：「客户端目标禁链 airy_atoms /
   corekern；违规即为缺陷」；
4. 门禁（入 verify_release_gates.sh，实测口径）：
   - 组 P · P1 白名单断言：`airy_cli` 链接允许集不含 `airy_atoms`（进程内
     微核心收回固化）；
   - 组 P · P2 全局面：根 CMakeLists 无 `atoms/corekern/include` 全局注入；
   - 组 P · P3 include 面：CLI 源树与构建文件零 corekern 头引用（仅断言
     真实 `#include` 指令与非注释构建路径，说明性注释豁免）；
   - 组 P · P4 产物符号：`nm` 扫描 `airy_cli` 产物不得出现
     `airy_init`/`airy_oom_*`/`airy_persist_*` 内核机制符号（产物定位由
     ctest 注入 `AIRY_GATE_BUILD_DIR`，显式指定而产物缺失即 fail-closed）；
   - B3 侧 `socket(AF_UNIX` 逐文件白名单为组 N（§4.3）。

### 5.4 退出判据

- CLI 构建、链接、ctest 全绿；组 P（P1–P4）与组 N 门禁全绿；
- `airy_init` 在 CLI/TUI 树内零引用（grep 门禁）；
- daemons 服务面（tool_d/sched_d 等）链 `airy_atoms` 行为不变。

## 7. B6 设计：物理移除退役 SSE 编排死代码（2026-09-14 改判）

### 7.1 改判依据（实测）

原设计假设「工具执行循环滞留 gateway，需新增 `tool.execute_round` 下沉 tool_d」。
勘察证实该前提不成立：

- live 多轮工具循环**已在 daemon 侧**：`agent_d` 的 `agent_run_loop.c`
  `agent_run_tool_loop`，0.1.9 P3 下沉事实上已完成；
- gateway 侧 `handle_chat_stream_sse` 自 0.1.13（B11 清零）起首句即
  `410 Gone`（B6 前 `http_gateway_sse.c:503-515`，该文件已随 B6 裁剪至
  仅存共享助手），其后整段状态机（含 EXEC_TOOLS 相位）为不可达死代码；
- `gateway_sse_tool.c`（工具循环 RPC / 结果格式化 / 会话管理）、
  `gateway_sse_frame.c`、`gateway_sse_stream.c`、`gateway_sse_memory.c` 及其
  单测**仅被该死状态机引用**（daemons/tools 零消费者）；
- tool_d 现注册 11 个方法，**无批量/多轮/会话 RPC**，证实不应为死端点新增
  `execute_round`。

故改判为：**物理移除退役编排死代码**，而非「新增下沉」。

### 7.2 目标态

- gateway/src **零编排**：无 EXEC_TOOLS 相位、无 `GW_SSE_MAX_TOOL_LOOPS` 类
  编排常量、无工具循环 RPC 翻译；§2「gateway 翻译、daemon 干活」由
  「死代码移除」达成（而非新增下沉路径）；
- 保留 live 端点：`handle_run_stream_sse`（`/api/v1/agent/run/stream`，
  `gw_aipc_stream` 纯流翻译）、`handle_hall_watch_sse`（`/api/v1/hall/watch`），
  以及二者共享的 `gw_sse_send_json_error`、`GW_SSE_BLOCK_SIZE`、
  `gateway_hall_store.h`。
