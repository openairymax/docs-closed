### 1.2 两处误判的澄清（避免把预期行为当故障）

1. **11438 裸调 `401` 属预期**：代理对 `Authorization` 是透传，不带 key 时上游返回 `Invalid API Key`。带 `secrets.env` 的 `MODEL_1_API_KEY`（51 字符）后为 `200`。网关调用链自带 key（`llm_d` 日志 `model=mimo ... http_code=200`），故 401 不代表环境坏。
2. **`/daemons` HTTP 404 属预期**：8080 无该路由（`-32601 Not Found`），daemon 健康应走 CLI。`airymaxrt status`（23:26:13）→ `gateway: 在线`、`daemon 群: 核心链路（llm/think/agent/tool）全部就绪`。

### 1.3 `think.process -32603` 的真实根因（本次新增一手证据）

一次完整调用（23:23:31 → 23:25:23）的逐请求台账：

| 阶段 | 模型 | 起止 | 耗时 | completion tokens |
|------|------|------|------|-------------------|
| t1-p 专业校验 | airy-7b | 23:23:31.889–23:23:46.255 | 14.4s | 151 |
| t1-p 复审 | airy-7b | 23:23:46.270–23:23:58.471 | 12.2s | 134 |
| t2 慢思考 ×4 | mimo | 23:23:58.473–23:24:10.903 | 5.6/0.5/3.9/2.4s | 109/40/119/202 |
| t1-f 终裁 | qwen9b | 23:24:10.905–23:24:14.090 | 3.2s | 87 |
| **Phase2 DAG 综合** | mimo（max_tokens=8192, temp=0.70） | 23:24:14.092–23:25:23.915 | **69.8s** | **2425** |

- `think_d` 在 23:25:23.917 明确记录 `ThinkDual: process ok (result_len=2734)`，**产物是成功生成的**；
- 但调用方在 **123.9s** 收到 `{"code":-32603,"message":"Service returned invalid response"}`，即 **gateway 侧 ~120s 硬超时**在 think_d 完成前 4s 将其丢弃；
- 同轮 `Goal alignment: DRIFT (score=0.57)`，说明该轮计划本身也未收敛；
- `gateway_d` 二进制中**不存在**任何 timeout 环境变量（`strings` 仅有 `AIRY_GATEWAY_*` 开关族），`think.timeout_ms: 240000` 只作用于 think_d 内部，**改不动 gateway 的 120s**。

**结论**：`-32603` 不是「思考爆炸」的残留，也不是配置错误，而是 **phase-2 8192-token 综合（单次 69.8s）+ 上游单次抖动（本轮另有 47.3s 的一次 mimo 调用）叠加后击穿 120s 硬预算**。0.1.18 上**不可配置修复**，只能：
- 测量时把 `-32603` 作为「慢路径失败」单独计账（不得与模型答错混算）；
- 在 0.1.20 中作为必改项（gateway 预算可配 / phase2 分段 / 综合步减小 max_tokens / 流式回传）。

### 10.4 尚未被方案覆盖的问题（按严重度）

1. **G47 的统计功效不成立（决定性）**。A0 sd=36.77、A1 sd=41.03、配对差 sd=46.88，15 对中仅 5 对非零（`0,0,0,0,−80,+100,0,0,−40,−80,0,0,0,0,+80`），符号检验 p=1.000，配对差 95% CI 约 `[−32.7, +19.4]`。按两样本 80% power/α=0.05：**n=30/臂只能检出 ≈28pp**（配对设计 ≈24pp）；要检出 +5pp 需 **≈952 组/臂（独立）或 ≈690 组/臂（配对）**。方案写「≥30 轮 +5pp」，在当前判分器方差下**既不可能通过、也不可能被推翻**。
2. **G40 缺对称对照，可被常量输出通过**。判据只有「注入 10 例检出 ≥8」，一个恒 `reject` 的模型 100% 通过；而现网 `b_arbiter/round_0.json` 16 个工件**全部 `accept`、confidence 0.95–1.0**，是恒接受。两种退化都必须被门禁挡住，因此必须加干净臂。
3. **prompt 未纳入版本管理**。同一模型同一案例 1/8→4/8→5/8→7/8，仅取决于措辞与 shot 数。G40 若不锁定「prompt 文本哈希 + 判定粒度 + few-shot 内容」，结果不可复现、不可回归。
4. **`grad_llm_call.c` 是 `temperature = 0.2f`**，且**没有任何 thinking 控制字段**。前者让 G40 十例在边界上可翻转；后者意味着「关闭思考」完全依赖仓库外的 `qwen_proxy.py`（注入 `chat_template_kwargs.enable_thinking=false`），换环境即静默失效——本窗口实测：thinking 默认开启时 9B **8/8 次 `content` 为空**（400 token 被思考块吃满），B 直接失效。
5. **`max_output: 2k` 与 C2 的 digest 预算冲突**。C2 要求 `grad_plan_digest_json` 占 800–1200 token，叠加 system prompt 与 report 后单次 B 调用可逼近 2k 上限；现网已出现 `clipped (2048)` 31 次（A0）与 `output truncated at max_tokens=1024 (airy-7b)`。C2 落地前必须把 B 的预算单列，且不得复用 qwen 代理的全局 2048 限幅。
6. **swap 被 /tmp tmpfs 吃掉，而非内存压力**。`SwapFree` 仅 510 852 kB，但所有进程 VmSwap 合计 ~62 MB，`/tmp` 占 7.5G。任何「OOM/抖动」归因必须先排除这一项，否则会把构建残留误判为推理链缺陷。
7. **同源模型使「三权分立」退化**。B50 只有 Qwen3.5-9B 与 Qwen2.5-7B 两族；A/B/C 同源 → 误差相关，本地实验**只能证明 B 的工程可行性，不能证明异构纠错增益**。后者必须走 11438 的 mimo。
8. **GPU/CPU 未升频，G37 时延预算无法验**。GPU `cur 1767 / max 2600`（空载 1200），governor `powersave`，且无 `sensors` 无法取温度/功耗。当前测得的时延是「降频态」数值，不能作为 0.1.20 的预算基线。
9. **`grad_llm_s1_arbiter.c:160-163` 是 fail-open**（B 调用失败 `return AIRY_SUCCESS`），与 C7 的「降级必须显式」直接冲突；且 prompt 只给 `goal + report + 节点数 + guard 名`，本窗口的 7/8 是在**给了逐节点内容**的前提下才达到的——不改 prompt 内容，任何模型都只会恒 accept。

**阶段 1：C1/C2/C6 的原型回归（不依赖改码，用 bench 侧 harness）**

**（5）方案复检：五处不合理**

1. **端口规划**：方案把容器当「另起一套」，另开 12435/12436，迫使 gateway/proxy/bench 改 4 处。正确做法是「自托管服务固定占用 11435/11436，容器只是实现方式」——已按此改正。
2. **容量假设过保守**：方案按 8k×2 设计上下文预算，实测 16k×4 同吞吐、同内存量级。8k 的选择没有实测依据，属于「按显存放不开」的估计；实测证伪。
3. **「双模型并行以保证时延」不成立**：总吞吐被 GPU 钉在 ~35 tok/s，9B+7B 并行只会让单请求变慢（28.9 s vs 单模型 ~15 s）。方案中的「9B 执行 / 7B 校验并行」必须改为串行分工，或 7B 仅在 9B 队列空闲时启用。

档 C 揭示两件事：

- **`think.enabled=false` 只关 GRAD，不关思考引擎**。日志原文 `ThinkDual: dual-thinking disabled (enabled=0), GRAD off`，之后 Phase 0 / GCCP / Cognitive review / Phase 2 照常执行，云调用仍是 5 次。它省下来的只有 GRAD 那 1 次本地调用（端侧 5→4 次，耗时再降 3.3 s）。
- **GRAD 在 5 题上的净贡献为 0**：档 B（GRAD on）100/80/100/40/80，档 C（GRAD off）100/100/100/20/80，均分相同，逐题呈 ±20 的双向波动（2001 变好、2003 变差），而云成本一分未变。这是单次跑批、5 题样本，只能作为「GRAD 未证明有效」的证据，不能作为「GRAD 无效」的定论——与 §10.11 的样本量警告同一口径。

**结论：云端调用 6→4→2 的曲线在这台机器上不存在。** 配置级最低就是 5 次（Phase 0 一次 + 认知审查 4 角色并行），因为这两处不读 `think2_slow_model` / `think1_*` 任何键——`model.yaml` 全文只有 `models / default_model / think` 三段，`think_d` 二进制里也只暴露 `AIRY_THINK_ENABLED / AIRY_THINK2_SLOW_MODEL / AIRY_THINK1_FAST_MODEL / AIRY_THINK1_PROF_MODEL / AIRY_THINK_TIMEOUT_MS / AIRY_CPR_PARALLEL`，**没有阶段→模型的映射项**。要再往下砍只有三条路，都必须改产品代码：

1. 把 Cognitive review 的 4 角色合并为 1 次多角色输出（省 3 次，但合并契约在 9B 上已证明不稳，见验证 2 第 3 点）；
2. 让 Phase 0 与 review 也能走 `think1_fast_model`（省全部云端调用，代价是 9B 的分解质量未知）；
3. 把审查改成「仅高风险节点触发」，即验证 2 的 top-k 思路前移到 think 引擎内部。

**（4）本轮结论**

- 双思考的 token 代价可以压到 **+148%**，但压不到 G47 的 ≤15%；收益 +3.5pp 与「审得准」强相关，与「审得多」无关。
- 双模型常驻**没有收益**：单模型逐题同分、耗时 −28.4%，7B 的 37.74 tok/s CPU 推理就是那部分尾延迟。
- 云端规划调用**配置级下限为 5 次/轮**；砍到 5 次即拿到 −17.7% 云 token / −21% 云成本且质量不动，继续下探需要改产品代码暴露阶段级模型映射。
- GRAD（`think.enabled`）在本样本上**未证明有效**：关掉它质量均值不变、省 1 次本地调用与 3.3 s，但逐题波动 ±20，需 ≥30 轮才能定论。
