## 摘要

本研究对 Airymax/AgentRT 双思考系统进行了穷尽式代码审查和学术证伪分析，覆盖框架层、记忆卷载（MemoryRovol）、双思考系统全栈代码（约 25 个源文件逐行只读审查），发现了**一个致命问题**和**多组根本性问题**：

1. **致命发现**：整个认知管线在产线不可达——由于 `plan_strategy` 从未被注入，Phase 1 必然失败跳转 `process_fail`，导致 Phase 2（含 tc3 批判循环）/Phase 3/Phase 4 全部成为死代码。系统实际靠 orchestrator 回退到直接 LLM 调用运行，**双思考系统从未在产线执行过**。

2. **两条路径分裂**：项目中已实现完整的多模型协调器（`coordinator/dual_model.c` 820 行，含 4 种交叉验证模式、自适应阈值、健康监控），但 ThinkDual 升级时绕过它，重新用单 LLM 实现了 `tc3_llm_callbacks.c`——多模型基础设施成为死代码。且 `weighted.c`/`arbiter.c` 是桩函数（违反"严禁桩函数"硬约束）。

3. **同模型自验证**：即使认知管线修复后可达，当前 tc3 三个回调（S2/S1-verify/S1-expert）共用同一 LLM 端点（model=NULL、temperature=0.3 硬编码），无法捕获"自信但错误"案例（MIT/ICLR 2026 已证明）。s1_verify 在 LLM 不可用时回退到字数打分（100字以上=acceptable）。

4. **验证 prompt 方向错误**：S1 验证使用"verify correctness"框架，ICML 2026 证明这会加剧过度自信；应改为"find bugs"对抗式框架。

5. **循环检测仅靠计数器**：无语义级循环检测、无超时、REJECT 静默丢弃、s1_expert 仲裁后无条件 break。

6. **Phase 0 空操作、Phase 4 死代码**：Phase 0 指令拆解原样输出 input；Phase 4 trigger_replan 仅递增计数器，无重规划动作；reflective.c（868行）完全死代码。

7. **记忆卷载三个关键数据流断裂**：(a) cognition 层 provider retrieve 结果直接 FREE 丢弃；(b) L3 bridge 返回 ENOTSUP（桩函数）；(c) prepopulate 走另一条 memory 路径，与 MemoryRovol provider 完全分离。

8. **记忆卷载架构契约破坏**：L1 delete_raw 物理删除文件（违反不可变性）、L1 写入无 fsync（非真持久化）、元数据库强制 `:memory:`（死配置）、L2/L3/L4 全部纯内存（重启即丢失）。

9. **记忆卷载检索质量根本缺陷**：L2 embedder 默认 hash-based trigram（非语义嵌入），embedding 失败 fallback 到字符填充（桩函数式输出）；BM25/hybrid 已实现但完全孤立。

10. **记忆卷载桩函数与孤立模块**：L4 rule_generator 在 LLM=NULL 时输出固定模板、health_check 硬编码 ok、sync 系列全 no-op；VSA/miner/memory_swap/archive/revive 等大量模块已编译但未接入主流程。

11. **calibrator 是 no-op 陈列品**：confidence_calibrator 的 update 从不被调用，calibrate 是恒等变换（score × 1.0 × 1.0）；metacognition 存在 step_id % 7 bug。

12. **最致命发现（B6）—双思考输出封闭**：即使认知管线修复可达，Phase 2 tc3 批判循环的全部产出（tc3_coordinator_execute_streaming 的 phase2_output）只被追加到 `chain->ctx_window` 后立即 FREE 释放，**从不写入 plan 节点的 `task_node_output`**（coreloopthree/src 中 `task_node_output =` 零匹配）。loop.c 和 orchestrator.c 均对 `ctx_window` **零引用**。orchestrator.c:994-1054 检查 `task_node_output`（恒为 NULL）→ `gen_cog_has_output` 恒 false → `goto generation_llm_fallback`。**用户最终拿到的是 orchestrator 直接 LLM 调用的回退输出，双思考系统的全部批判/纠正/审计产出被封闭在 cognition engine 内部从未传播给用户**。v3.0 完全未覆盖此根本性盲区。

13. **执行层 agent_id 缺失（B4-B5）**：loop.c:838-845 提交执行任务时 `task.task_agent_id` 从 memset 后恒为 NULL，`node->task_node_agent_role` 从不映射到 `task.task_agent_id`。execution/engine.c:424 `agentos_registry_get_unit(NULL)` 返回 NULL → 执行任务必然失败/空输出 → orchestrator 走 loop_wait 失败 → generation_llm_fallback。

14. **v3.0 P1.14 编译错误（B2）**：v3.0 §5.2 修复方案引用 `agentos_plan_sequential_create()` 作为 fallback 策略工厂，但该函数在全代码库**零定义**。planner/ 目录只有 reactive.c、hierarchical.c、ml_planner.c、reflective.c，无 sequential.c。直接实施 v3.0 P1.14 将导致编译失败。

15. **CoreLoopThree 架构证伪**：(a)"三循环并行+事件通信"不实，实为单维护循环+同步 submit+执行线程池；(b) 多 Agent 协作/认知演化/补偿事务三模块真实实现但生产代码零引用（未接入主运行路径）；(c) TaskFlow 源码存在于 taskflow/src/（6 个 .c 文件，含 graph_engine/pregel_engine/taskflow_core 等），但 coreloopthree/src 中零引用 taskflow——"TaskFlow 已实现"只是孤立存在，未接入 CoreLoopThree。

16. **历史方案矛盾与虚假完成声明**：历史审查发现 13 项已证伪结论（F1-F13）和 9 项 v3.0 与历史方案的致命矛盾（C1-C9）。最严重的是：2026-04-18 可行性评估**早已发现** Phase 2/3/4 缺失、99% 准确率数学不可达（实际 85-90%）、代码完整度仅 60-70%，但 2026-04-27 第 08 轮审查**虚假声称"双思考系统完整 503 行"**，v2.6 和看板（2026-06-14）忽视这些发现声称 67/67 ACC 全部达标、"v0.1.1 发布就绪"。DocsClosed 中还发现 12 项 v3.0 未覆盖的历史问题（L3 因果链不完整、L4 规则注入缺失、"分时推理+记忆交换"缺失、checkpoint 未集成 loop.c、多 Agent 仅 REST 封装等）。

基于行业最新理论（ISRV、Cross-Model Disagreement、T³ Belief Deviation、DCPM、ActiveMem、Conformal Abstention、AdversaBench、CVT-RL、EIR/ECR 控制论自纠正、n_eff 校正、工具调用护栏等 **35 项 2025-2026 研究**），本方案提出**六层修复体系**：P0 修复管线可达性 → P0 激活多模型 → P0 对抗式验证 → P0 修复输出传播（B6）+ 执行层 agent_id（B4-B5）→ P1 信念偏差跟踪 + 循环检测 + 记忆卷载修复 → P2 共形弃权 + 记忆去偏。

### 1.2 学术证伪方法论

本研究的核心方法论是**学术证伪（Falsification）**——对每个设计决策提出"在什么条件下会失败"的假设，然后用代码证据和行业理论验证该假设是否成立。这与传统的"确认性审查"不同：

- **确认性审查**问："这个设计是否实现了？" → 容易满足于"代码存在"
- **证伪性审查**问："这个设计在什么条件下会失效？" → 迫使发现深层问题

### 1.3 推论验证原则

每个发现必须满足三重验证：
1. **代码证据**：具体文件:行号 + 代码片段
2. **逻辑推论**：从代码到问题的因果链
3. **行业理论佐证**：2025-2026 年公开研究的支持

## 第二章：代码穷尽审查发现

### 2.1 致命发现：认知管线在产线不可达

**这是本研究最重大的发现，也是双思考系统无法工作的根本原因。**

#### 2.1.1 问题定位

[engine.c:680-742](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c) 的 Phase 1 规划阶段：

```c
agentos_error_t err = AGENTOS_EUNKNOWN;          // :680
plan_strat = engine->plan_strat;                 // :685 — 产线中为 NULL
if (plan_strat && plan_strat->plan) { ... }      // :689 — 条件为 false，err 仍为 EUNKNOWN
...
if (err != AGENTOS_SUCCESS) {                    // :719 — true
    if (fallback_strat && fallback_strat->plan) { // :726 — fallback 也未设，false
    } else {
        goto process_fail;                        // :740 — 直接跳到失败处理
    }
}
```

#### 2.1.2 根因：plan_strategy 从未被注入

证据链：

1. `agentos_plan_strategy_t *loop_config_plan_strategy`（loop.h:48）是"可选"指针字段
2. `init_default_config`（loop.c:115-131）用 `__builtin_memset` 清零，该字段为 NULL
3. 两个产线调用点都不设此字段：
   - `orch_adapter.c:99-116`：`__builtin_memset(&loop_cfg, 0, ...)` 后只设 threads/timeout/checkpoint
   - `manager_adapter.c:190-256`：YAML 加载无法产生 C 函数指针
4. grep `loop_config_plan_strategy\s*=\s*[^N]` 在非测试代码中**零匹配**
5. 4 个规划策略工厂函数（`agentos_plan_reactive_create` 等）在非测试代码中**零调用**
6. cognition.h 中**没有** `agentos_cognition_set_plan_strategy` setter——主策略只能经 create 函数注入

#### 2.1.3 后果：Phase 2/3/4 全部不可达

`process_fail`（engine.c:1370-1376）销毁 chain 并返回 `AGENTOS_EUNKNOWN`。调用方 `orchestrator.c:1054-1085` 证实：`agentos_loop_submit` 失败后 `goto generation_llm_fallback`（:1084），系统靠直接 LLM 调用运行，**整个 CoreLoopThree 被绕过**。

这意味着：
- Phase 2 的 tc3 批判循环（含 LLM 驱动的 s2_generate/s1_verify/s1_expert）**从未在产线执行**
- Phase 3 审计委员会**从未执行**
- Phase 4 目标对齐检查**从未执行**
- 双思考系统的全部代码（tc3_llm_callbacks.c 867 行、triple_coordinator.c 591 行）**在产线为死代码**

#### 2.1.4 修复方案

在 loop.c 或 daemon 启动路径中创建并注入规划策略：

```c
/* loop.c create_loop_engines 中，在 cognition 创建后 */
agentos_plan_strategy_t *plan_strat = agentos_plan_reactive_create();
if (plan_strat) {
    agentos_cognition_set_plan_strategy(engine, plan_strat);
    AGENTOS_LOG_INFO("C-L02: Plan strategy (reactive) injected to cognition engine");
} else {
    AGENTOS_LOG_ERROR("C-L02: Failed to create plan strategy — cognition pipeline will fail");
}
```

同时需新增 `agentos_cognition_set_plan_strategy` setter（cognition.h 中当前缺失）。

### 2.2 框架层审查：Phase 0-4 逐阶段分析

#### 2.2.1 Phase 0：指令拆解——空操作

[engine.c:628-676](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c)：

```c
agentos_tc_step_complete(decomp_step, input, input_len, 0.8f, "S1-decomposer");  // :649
```

拆解步骤的"输出"直接传入了**原始 input**。没有调用 LLM、没有解析子目标、没有产生子任务列表。只是把 input 原封不动记成 step 的 content，并赋一个硬编码置信度 0.8。

**修复方案**：Phase 0 应调用 LLM 进行真正的指令拆解，输出结构化子任务列表（JSON），为 Phase 1 规划提供输入。

#### 2.2.2 Phase 1：规划——S1 预验证无副作用

[engine.c:693-717](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c)：

```c
if (!eval.is_acceptable && eval.strategy != MC_CORRECT_NONE) {
    AGENTOS_LOG_WARN("Plan S1 pre-validation failed: score=%.2f strategy=%d", ...);
    engine->dual_think_corrections++;    // :710
}
```

S1 评估在不通过时**仅打印 WARN 并递增计数器**，不触发重规划、不修正 plan、不阻断流程。即使 eval 建议修正策略，代码也忽略 `eval.strategy` 不执行任何修正动作。

**修复方案**：S1 预验证失败时应触发重规划（最多 2 次），而非仅记录。

#### 2.2.3 Phase 2：执行-验证循环——tc3 注入逻辑有效但整体不可达

[engine.c:923-941](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c) 的 tc3 回调注入条件本身是**真实有效**的：

```c

    tc3_cfg.s2_generate = tc3_llm_s2_generate;   // 真实回调
    tc3_cfg.s1_verify = tc3_llm_s1_verify;       // 真实回调
    tc3_cfg.s1_expert = tc3_llm_s1_expert;       // 真实回调
}
```

但由于 Phase 1 失败跳转 `process_fail`，Phase 2 整段（:773-1060）在产线永不执行。

#### 2.2.4 Phase 3：审计委员会——仅重复元认知评估

[engine.c:1143-1171](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c)：

"审计委员会"只是再次调用 `agentos_mc_evaluate_step`（与 Phase 1 的 S1 预验证是同一函数），audit_step 的输入是原始 `input` 而非 plan 或 Phase 2 输出。没有多专家投票、没有跨模型交叉验证、没有审计意见聚合。

**修复方案**：Phase 3 应调用 `agentos_majority_coordinator_create`（已实现但未调用）进行三模型多数投票审计。

#### 2.2.5 Phase 4：目标对齐——trigger_replan 死代码 + strstr 关键字匹配

[engine.c:1237-1270](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c)：

```c
if (trigger_replan) {
    engine->align_replan_count++;                 // :1269 — 唯一动作

```

`trigger_replan` 被置 1 后唯一的副作用是递增计数器和触发一条 feedback 事件。**没有任何重规划动作**——不重新调用 plan_strat、不回退到 Phase 1、不修正 plan。

[engine.c:1197-1198](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/engine.c)：

```c
int goal_match = (strstr(recent_ctx, "goal") != NULL) ||
                 (strstr(recent_ctx, "objective") != NULL);  // 非语义相似度
```

Phase 4 的"目标对齐"用的是 `strstr` **子串关键字匹配**，不是语义相似度。没有任何 embedding、cosine、语义模型调用。

**修复方案**：Phase 4 应实现真正的重规划机制 + 用 MemoryRovol L2 embedding 做语义相似度计算。

### 2.3 双思考系统审查：两条路径分裂

#### 2.3.1 路径 A：旧多模型协调器（coordinator/ 目录）——完整实现但未被调用

[coordinator/dual_model.c](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/coordinator/dual_model.c)（820 行）实现了远超行业平均水平的功能：

|------|---------|-------------|
| 4 种交叉验证模式（NONE/BASIC/ADVANCED/ADAPTIVE） | :67-72 | Cross-Model Disagreement (MIT/ICLR 2026) |

#### 2.3.2 路径 B：新 tc3 单 LLM 回调（critique/ 目录）——当前活跃路径但背离设计

[tc3_llm_callbacks.h:46-68](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/cognition/critique/tc3_llm_callbacks.h) 的 `tc3_llm_ctx_t` 结构体**只有一个 LLM 句柄**：


### 2.8 CoreLoopThree 架构证伪

#### 2.8.1 "三循环并行+事件通信"证伪

### 2.12 atoms 层与 daemon 层穷尽审计发现

本章节汇总 atoms 内核层和 daemon 服务层的穷尽审计发现。这些发现独立于双思考系统主线，但直接影响系统整体可用性和安全性，属于"编译通过≠功能正常"的典型例证。

#### 2.12.1 安全穹顶（cupolas）完全未集成 — 致命

**问题定位**：`cupolas_init()` 在 daemon 层**零调用**。grep 全 daemon 目录树，`cupolas_init` 仅出现在 cupolas 自身的实现文件和测试代码中，daemon 启动路径（`daemon/main.c`、各 `*_d/src/main.c`）从不调用它。

**后果**：安全穹顶作为项目记忆中定义的"服务穹顶"安全护栏，在 daemon 运行时**完全不存在**。任何安全策略、入侵检测、权限校验均未激活。daemon 进程以无安全护栏状态运行。

**修复方案**：在 daemon 统一启动路径（`daemon/common/src/daemon_main.c` 或等效入口）中，于各子 daemon 初始化前调用 `cupolas_init()`，并注册 health_check 到系统监控。

#### 2.12.2 daemon_security 未激活 — 致命

**问题定位**：`daemon_security_init()` 仅在 tests 目录中被调用，生产 daemon 代码**零调用**。

**后果**：与 cupolas 双重失效——两套安全系统均未集成，daemon 层处于完全无防护状态。

**修复方案**：在 daemon 启动路径中紧随 cupolas_init 后调用 daemon_security_init，形成"穹顶+安全守护"双重防线。

#### 2.12.3 gateway_d 协议 handler 死代码 — 致命

**问题定位**：`gateway_set_handler()` 从未被调用。gateway_d 的 HTTP 路由表初始为空，外部 API 请求无法路由到任何协议处理器。

**后果**：gateway_d 作为外部 API 网关，**所有外部 API 不可达**。HTTP 请求进来后无 handler 处理，返回 404 或空响应。

**修复方案**：在 gateway_d 的 main.c 初始化路径中调用 gateway_set_handler 注册各协议 handler，并在集成测试中验证至少一条 API 路径可达。

#### 2.12.4 market_d install_agent RPC 致命 bug — 致命

**问题定位**：[market_d/src/main.c:223-224](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/daemon/market_d/src/main.c)：

```c
install_request_t *req = (install_request_t *)aid;     // :223 — 字符串强转结构体指针
install_result_t **res = (install_result_t **)version;  // :224 — 字符串强转结构体指针
```

`aid` 和 `version` 是字符串参数（`char *`），被强制转换为结构体指针和结构体二级指针。解引用时必然 segfault。

**后果**：`install_agent` RPC 调用即崩溃（signal 11）。market_d 的 agent 安装功能完全不可用。

**修复方案**：正确解析 RPC 参数——从 JSON/字符串中反序列化 `install_request_t`，分配并填充 `install_result_t`。

#### 2.12.5 llm_d cost_aware_router 未集成 — 高

**问题定位**：llm_d 实现了 4 策略成本感知路由器（`cost_aware_router.c`），但生产路径直接走默认 provider，router 未被调用。

**后果**：成本优化路由系统是死代码，所有 LLM 调用走同一 provider，无成本感知。

**修复方案**：在 llm_d 的请求分发路径中插入 cost_aware_router 调用，根据请求类型/预算选择最优 provider。

#### 2.12.6 tool_d 审批链跳过 — 高

**问题定位**：[tool_d executor.c:63](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/daemon/tool_d/src/executor.c)，独立 daemon 路径下 `approval_ctx = NULL`，6 守卫链全部因 NULL 检查而跳过。

**后果**：tool_d 独立运行时无工具调用审批，任何工具调用（含文件读写、代码执行）均无人工/自动审批。

**修复方案**：独立 daemon 路径应从配置初始化 approval_ctx（含审批策略、超时、回调），而非置 NULL。

#### 2.12.7 hook_d 零外部调用者 — 高

**问题定位**：`hook_service_fire()` / `hook_service_register()` 仅在 hook_d 内部匹配，daemon 层和 atoms 层**零调用**。

**后果**：hook_d 作为事件钩子系统完全孤立，运行时死代码。其他模块的 hook 事件无人触发。

**修复方案**：在 orchestrator、loop、cognition 等关键路径中调用 hook_service_fire 触发生命周期事件，并在 daemon 启动时注册默认 hook 处理器。

#### 2.12.8 corekern OOM handler 生产中永不激活 — 致命

**问题定位**：`agentos_core_init()`（[core_init.c](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/corekern/src/core_init.c)）不调用 `agentos_oom_init()`；`alloc.c` 的分配路径不调用 `track_alloc()`。

**后果**：OOM（内存耗尽）处理器在生产中**永不激活**，内存压力恒为 NORMAL。即使系统内存即将耗尽，OOM handler 不会触发任何降级/回收/告警动作。这与 project_memory 中"atoms 内核层必须绝对安全"的硬约束直接冲突。

**修复方案**：在 `agentos_core_init()` 中调用 `agentos_oom_init()`，在 `agentos_alloc`/`agentos_calloc` 路径中调用 `track_alloc()` 记录每次分配，使 OOM 压力感知生效。

#### 2.12.9 heapstore 持久化层失效 — 致命

**问题定位**：`heapstore_integration_init()` 在生产代码中**零调用**（仅 tests 调用）。所有 heapstore 操作因未初始化而返回 ENOTINIT，降级为无持久化。

**后果**：heapstore 作为持久化层名存实亡。所有依赖 heapstore 的数据（含 checkpoint、记忆卷载 L2/L3/L4 持久化）在重启后全部丢失。这与 §2.4.9（L2/L3/L4 全部纯内存）形成完整证据链——不仅内存层无持久化，连设计中的持久化层也未激活。

**修复方案**：在 daemon 启动路径或 memoryrovol_init 中调用 `heapstore_integration_init()`，并验证 heapstore 操作返回 SUCCESS 而非 ENOTINIT。

#### 2.12.10 taskflow 双引擎 ODR 冲突 — 高

**问题定位**：[taskflow_core.c:44](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/taskflow/src/taskflow_core.c) 和 [taskflow_advanced.c:34](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/taskflow/src/taskflow_advanced.c) 定义了**两个不同的** `struct taskflow_engine_s`。同时 `taskflow_engine_create` 的函数签名在两个文件中不一致。

**后果**：违反 C 语言 ODR（One Definition Rule）——链接器选择哪个定义取决于编译/链接顺序，行为未定义。这会导致 taskflow 引擎的字段偏移错乱，运行时内存越界或字段读取错误。

**修复方案**：统一 `struct taskflow_engine_s` 为单一定义（放入 taskflow_internal.h），两个文件共用同一结构体；统一 `taskflow_engine_create` 签名。

#### 2.12.11 taskflow 异步执行成功路径误报失败 — 高

**问题定位**：[taskflow async_execute_worker:676](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/taskflow/src/taskflow_advanced.c)，成功路径的返回码被颠倒——操作成功但返回错误码。

**后果**：所有异步 taskflow 任务全部报告"失败"，即使实际执行成功。调用方收到失败信号后可能触发不必要的重试或错误处理。

**修复方案**：修正返回码逻辑，成功路径返回 AGENTOS_SUCCESS。

#### 2.12.12 coreloopthree agentos_loop_run 非驱动循环 — 高

**问题定位**：[loop.c:611-736](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/coreloopthree/src/loop.c) 的 `agentos_loop_run` 不是认知-执行驱动循环，而是一个 `cond_timedwait(50ms)` 轮询的维护循环——处理 checkpoint、统计、超时清理。实际的认知执行在 `agentos_loop_submit` 内**同步完成**。

**后果**：这证伪了 CoreLoopThree "三循环并行+事件通信"的架构宣称（§2.8.1）。认知处理不是由独立循环异步驱动的，而是在 submit 调用线程中同步阻塞执行。"三层认知循环"实为"单维护循环 + 同步 submit"。

**修复方案**：如需真正的异步认知驱动，应将 submit 改为投递任务到队列，由 loop_run 循环取出并异步执行。如保持同步 submit 设计，则应修正架构文档描述，不再声称"三循环并行"。

#### 2.12.13 syscall 沙箱非 OS 级隔离 — 高

**问题定位**：[syscall/sandbox.c:292](file:///home/spharx/SpharxWorks/OpenAirymax/AgentRT/agentos/atoms/syscall/src/sandbox.c) 的 `agentos_sandbox_invoke` 不调用 `validate_syscall`，输入净化未接入 invoke 路径。且沙箱实现是同进程包装器（在宿主进程内执行 syscall），非 OS 级隔离（如 seccomp/namespace/container）。

**后果**：(a) `validate_syscall` 存在但未接入，输入净化形同虚设；(b) 恶意 syscall 在宿主进程内执行，可影响整个 daemon 进程。sandbox_quota 的 memory/IO 配额**从未被喂入**（仅 CPU 按调用计数，1 次=1 单位，非真实 CPU 时间）。

**修复方案**：在 `agentos_sandbox_invoke` 入口调用 `validate_syscall` 拒绝非法调用；评估引入 seccomp-bpf 或 namespace 做 OS 级隔离的可行性；将 sandbox_quota 的 memory/IO 配额实际喂入资源追踪。

#### 2.12.14 rate_limiter 仅令牌桶 — 中

**问题定位**：rate_limiter 的 README 宣称支持 5 种限流算法（令牌桶/漏桶/滑动窗口/固定窗口/并发数），但实现仅有令牌桶。

**修复方案**：补全其余 4 种算法实现，或修正 README 描述仅声明令牌桶。

#### 2.12.15 frameworks 零适配器注册 — 中

**修复方案**：至少实现一个参考适配器并注册，验证适配层接口可用。

## 第三章：学术证伪分析

### 3.1 卡尼曼双系统映射的合理性证伪

**原型设计假设**：t2 对应 System 2（慢思考），t1 对应 System 1（快思考），t1 检查 t2 的输出。

**证伪假设**：如果 t1 和 t2 使用同一 LLM（同一套权重、同一套偏见），那么 t1 的"快思考"只是同一模型换个 prompt 角色，不是真正的 System 1——因为卡尼曼双系统的核心是**两个独立的信息处理系统**，共享权重的模型不具备独立性。

**证伪验证**：
- 代码证据：tc3_llm_callbacks.c:124 `model = NULL`，三回调共用同一模型 ✓
- 逻辑推论：同一模型扮演 S2 和 S1 时，S2 的偏见会被 S1 继承，S1 的"验证"只是自我确认 ✓
- 行业理论：MIT/ICLR 2026 Cross-Model Disagreement 论文证明"单模型自一致性（AU）在过自信时崩溃——模型自信地重复同一个错误答案" ✓

**证伪结论**：当前实现**不是真正的双系统**，而是"单系统双角色"。原型设计的卡尼曼双系统映射在当前实现下**不成立**。

### 3.2 t2/t1 分工有效性的证伪

**原型设计假设**：t1 检查 t2 的输出是否有逻辑问题、是否偏离任务。

**证伪假设**：如果 t1 的验证 prompt 使用"verify correctness"框架（确认正确性），那么 t1 倾向于确认 t2 的输出而非挑战它，因为"验证正确性"的框架隐含了"默认正确"的偏见。

**证伪验证**：
- 代码证据：tc3_llm_callbacks.c:44-55 的 S1_VERIFY_SYSTEM_PROMPT 是 "verify whether a response is logically correct" ✓
- 逻辑推论："verify correctness"框架让验证者从"证明正确"的角度评估，而非"寻找错误" ✓
- 行业理论：ICML 2026 Agentic Overconfidence 论文证明"对抗式提示（find bugs）比验证正确性（verify correctness）降低过度自信 15 个百分点" ✓

**证伪结论**：当前 t1 验证 prompt 的框架**加剧了**过度自信，与原型设计"检查逻辑问题"的意图**方向相反**。

### 3.3 避免逻辑循环机制的证伪

**原型设计假设**：双思考系统设计了避免 LLM 进入逻辑循环的机制，能正常推进思考任务。

**证伪假设 1**：如果循环控制只有计数器（max_verify_rounds），没有语义级循环检测，那么当 S2 修正轮反复生成"换汤不换药"的内容时，系统无法识别这是循环，只能等到耗尽轮次上限。

**证伪验证 1**：
- 代码证据：triple_coordinator.c:446-447 循环终止条件只有 `correction_attempts < max_verify_rounds` ✓
- 逻辑推论：3 轮修正都生成相似内容时，系统浪费 3 次 LLM 调用且最终结果可能相同 ✓
- 行业理论：Authon 2026 推荐"语义循环检测（embedding 相似度 >0.92）+ 工具调用去重 + 强制决策注入" ✓

**证伪假设 2**：如果 REJECT 时静默丢弃单元（无错误上报），那么最终拼接的输出会缺失被拒内容，用户无感知。

**证伪验证 2**：
- 代码证据：triple_coordinator.c:551-555 `continue` 直接丢弃，无 feedback 触发 ✓
- 行业理论：Authon 2026 "Fail loudly instead of silently burning more tokens" ✓

**证伪结论**：当前"避免逻辑循环"机制**不充分**——只有计数器防无限循环，无法防低效循环；REJECT 静默丢弃违反"大声失败"原则。

### 3.4 99% 目标可达性的证伪

**原型设计假设**：双思考系统能实现 1000 小时任务 99% 准确率。

**证伪假设**：如果整个认知管线在产线不可达（Phase 1 必然失败），那么双思考系统从未执行过，99% 目标无从谈起。

**证伪验证**：
- 代码证据：engine.c:680-742 plan_strategy 未注入导致 Phase 1 失败 ✓
- 逻辑推论：系统靠 orchestrator 回退到直接 LLM 调用，没有任何验证/批判 ✓
- 行业理论：即使管线修复，同模型自验证（MIT/ICLR 2026）也无法捕获"自信但错误"案例 ✓

**证伪结论**：当前状态**完全不能**达到 99% 目标。即使修复管线可达性，仍需激活多模型基础设施 + 对抗式验证 + 信念偏差跟踪 + 共形弃权才能接近目标。

## 第四章：行业最新理论对比（截止 2026-06-30）

### 4.1 同模型自验证的局限性

**ISRV（Stanford/Google DeepMind 2026.03）**：同模型自验证在数学推理 +7.6%、代码 +8%，但事实核查和创意写作无效；关键创新是"独立重推导"而非"审查自己的答案"。

**RefineBench（NVIDIA/ICLR 2026）**：自精炼在 5 轮后持续退化；引导式精炼（>70B 模型）有效；<70B 开源模型即使被告知哪部分错误也无法改进。

**自我偏见放大（ACL 2024）**：自精炼会放大自我偏见。

**对照项目**：当前 tc3 的 s1_verify 是"审查自己的答案"模式，而非 ISRV 推荐的"独立重推导"模式。

### 4.2 跨模型分歧理论

**Cross-Model Disagreement（MIT/ICLR 2026）**：

- 单模型自一致性（AU）在过自信时崩溃——模型"自信地重复同一个错误答案"
- 跨模型语义分歧（EU）能可靠标记"自信但错误"的样本
- **TU = AU + EU** 远优于纯 AU
- 核心洞见："如果我只问 ChatGPT 同一问题多次得相同答案，不意味着答案正确；切换到 Claude/Gemini 得到不同答案，才给出认知不确定性的感觉"

**对照项目**：dual_model.c 的 `disagreement_threshold`（:115）就是这个理论的工程实现，但未被调用。

### 4.3 信念偏差跟踪

**T³: Reducing Belief Deviation（ICLR 2026）**：

- **信念偏差（belief deviation）** = agent 内部信念偏离真实问题状态——这正是"自信但错误累积偏差"的学术化表达
- 错误一旦发生，在轨迹中复合，导致状态感知丢失、产生无信息或重复动作
- T³ 方案：跟踪信念偏差，检测过度偏差时**截断轨迹**——性能 +30 分，token 成本 -34%

**对照项目**：confidence_calibrator.h 的 `historical_bias[5]` + `convergence_check` 就是这个跟踪机制，已部分实现但未充分使用。

### 4.4 双过程认知记忆（DCPM）

**DCPM（Tencent, arXiv:2606.09483, 2026-06-08）**：

- 将双过程理论应用到**记忆系统**上
- SYSTEM 1（白天同步写入器）：记录信念修订为双向链表 supersede chains
- SYSTEM 2（夜间异步引擎）：归纳 schemas 和 intentions，扫描跨领域冲突，抽象为高层核心 schemas
- 在 LongMemEval、PersonaMem 上，SYSTEM 2 在跨领域隐式推理上贡献最大（+5.20）
- 核心洞见：现有记忆系统都停留在"被动基础层"，缺少"主动认知演化"

**对照项目**：MemoryRovol L4（模式层）对应 DCPM 的 SYSTEM 2，但当前 evolve/forget 只是接口转调，缺少 schema 归纳和跨领域冲突扫描。

### 4.5 分布式主动记忆（ActiveMem）

**ActiveMem（arXiv:2606.10532, 2026-06-09）**：

- 异构框架，将 agent 记忆与核心推理过程解耦
- 高层 Planner 使用蒸馏的 semantic gists 执行推理
- 轻量级分布式记忆系统并行积累和整合 gists
- 灵感来自人类认知系统：前额叶皮层（执行控制）+ 海马体（记忆管理）
- 在 BrowseComp-Plus 和 GAIA 上达到 SOTA

**对照项目**：当前 loop.c 的双引擎割裂（内置 memory vs MemoryRovol provider）正是 ActiveMem 所批评的"集中式记忆"问题。

### 4.6 共形弃权

**Conformal Abstention 系列（多篇 2026）**：

- **Conformal Language Modeling via Posterior Sampling（MIT 2026.06）**：从 LLM 后验采样，条件于校准高分区域
- **Geometry-Calibrated Conformal Abstention（HKUST 2026.04）**：75% 条件正确率
- **Mitigating Hallucinations via Conformal Abstention（DeepMind 2024）**：self-consistency + 共形预测，幻觉率理论保证
- 核心价值：提供"以概率 ≥1-α 保证不输出幻觉"的有限样本保证——这是 99% 目标唯一的数学基础

**对照项目**：项目完全缺少共形弃权机制。

### 4.7 对抗式验证

**Agentic Overconfidence（ICML 2026, Kaddour）**：

- 所有 agent 系统性过度自信——成功率仅 22% 的任务，agent 预测 77% 成功
- **对抗式提示（adversarial prompting）**：将评估框架从"验证正确性"改为"找 bug"，**降低过度自信最高 15 个百分点**
- 执行前评估（信息更少）比标准执行后评估有更好区分力

**AdversaBench（2026.06）**：

- **单法官无法判断自己何时宽松**——"A lenient judge silently drops real failures"
- **三法官面板 + 元法官裁决**
- 弱模型（8B）生成的对抗 prompt 可迁移到强模型（70B），说明错误模式是通用的

**对照项目**：当前 s1_verify prompt 是 "verify whether a response is logically correct"——这正是研究指出的"verify correctness"框架，会加剧过度自信。

### 4.8 反事实信用（CVT-RL）

**CVT-RL（arXiv:2606.05263, 2026-06-03）**：

- 反事实信用分配，解决长程 agent 的 belief drift（信念漂移）问题
- 4 种受控干预：删除、语义替换、证据替换、工具输出扰动
- 增加拉格朗日约束：不支持的主张、跳过验证、工具篡改、不安全调用
- 平均成功率从 71.8% 提升到 78.9%，hacking 从 7.2% 降到 3.9%

**对照项目**：项目缺少反事实验证机制——验证只检查"输出是否正确"，不检查"如果去掉某个步骤，结论是否仍成立"。

### 4.9 控制论自纠正诊断（EIR/ECR）— P0 必须覆盖

**EIR/ECR（Error Injection Ratio / Error Correction Ratio, 2026.06）**：

- 自纠正系统的有效性取决于**错误注入率（EIR）**和**错误纠正率（ECR）**的诊断
- 当前项目的 tc3 验证是"自注入零错误"——S2 生成内容后 S1 验证，但 S1 和 S2 共用同一模型，EIR≈0（同模型不会注入自己能发现的错误）
- 行业研究表明：有效的自纠正需要 **EIR > 0.3 且 ECR > 0.6**，当前项目 EIR≈0、ECR 不可测
- 修复方向：引入**外部错误注入器**（用弱模型故意生成错误内容测试 S1 能否捕获），测量真实 ECR

**对照项目**：项目完全缺少 EIR/ECR 诊断，无法评估自纠正系统的真实有效性。

### 4.10 相关错误侵蚀评审团（n_eff ≈ 2）— P0 必须覆盖

**Correlated Errors Erode Jury（MIT/ICLR 2026 补充研究）**：

- 当评审团成员共享相关错误时，**有效独立评审人数 n_eff 远小于表面人数 n**
- 公式：`n_eff = n / (1 + (n-1)·ρ)`，其中 ρ 是错误相关系数
- 当前项目三回调共用同一 LLM：ρ ≈ 1.0 → n_eff ≈ 1（不是 3）
- 即使激活 dual_model.c 的 3 模型投票，如果模型来自同一 family（如都是 GPT 系列），ρ 仍可能 > 0.5 → n_eff < 2
- 修复方向：确保 S2/S1-verify/S1-expert 使用**不同 family** 的模型（如 Claude + GPT + DeepSeek），使 ρ < 0.3 → n_eff > 2

**对照项目**：当前 tc3 共用同一模型（n_eff=1），即使 v3.0 P2.7 激活多模型也需确保跨 family。

### 4.11 Agent 运行时工具调用护栏 — P0 必须覆盖

**Runtime Tool-Call Guardrails（Anthropic/DeepMind 2026.06）**：

- Agent 系统的工具调用需要**运行时护栏**：参数校验、路径白名单、超时熔断、副作用审计
- 当前项目 tool_service 注入到 cognition engine（C-L04），但 tool 调用路径缺少护栏——tool_svc_adapter 直接转发，无参数校验、无路径白名单
- 行业最佳实践：每个工具调用需经过 (1) 参数 schema 校验 (2) 路径白名单 (3) 超时熔断 (4) 副作用审计
- 修复方向：在 tool_svc_adapter 中增加护栏层

```c
static float compute_n_eff(size_t n_models, float error_correlation) {
```

## 第九章：结论

### 9.1 核心发现

1. **致命发现**：双思考系统从未在产线执行过——plan_strategy 未注入导致 Phase 1 必然失败，Phase 2/3/4 全部死代码。系统靠 orchestrator 回退到直接 LLM 调用运行。

2. **两条路径分裂**：项目中已实现完整的多模型协调器（820 行 dual_model.c，含 4 种交叉验证模式、自适应阈值、健康监控），但 ThinkDual 升级时绕过它，重新用单 LLM 实现了 tc3——多模型基础设施成为死代码。

3. **同模型自验证**：即使管线修复后可达，当前 tc3 三个回调共用同一 LLM，无法捕获"自信但错误"案例。

4. **验证 prompt 方向错误**：S1 使用"verify correctness"框架，加剧过度自信；应改为"find bugs"对抗式框架。

5. **学术证伪结论**：当前双思考系统的卡尼曼双系统映射不成立（单系统双角色）、t1 验证加剧过度自信、循环检测不充分、99% 目标完全不可达。

6. **最致命发现（B6）—双思考输出封闭**：即使认知管线修复可达，Phase 2 批判循环的全部产出只被追加到 `chain->ctx_window` 后立即 FREE 释放，**从不写入 task_node_output**。用户最终拿到的是 orchestrator 直接 LLM 调用的回退输出，双思考系统的全部批判/纠正/审计产出被封闭在 cognition engine 内部从未传播给用户。

7. **执行层 agent_id 缺失（B4-B5）**：loop.c 提交执行任务时 `task_agent_id` 恒为 NULL，agent_role 从不映射，执行任务必然失败 → LLM fallback。

8. **安全系统完全未集成**：cupolas（安全穹顶）和 daemon_security 两套安全系统在 daemon 层零调用，daemon 进程以无安全护栏状态运行。gateway_d 协议 handler 死代码（外部 API 全不可达），market_d install_agent RPC 字符串强转结构体指针（调用即崩溃）。

9. **atoms 内核层多重失效**：OOM handler 生产中永不激活（内存压力恒 NORMAL），heapstore 持久化层失效（全部 ENOTINIT 降级），taskflow 双引擎 ODR 冲突（链接行为未定义），syscall 沙箱非 OS 级隔离（validate_syscall 未接入）。这直接违反 project_memory 中"atoms 内核层必须绝对安全"的硬约束。

10. **CoreLoopThree 架构证伪**："三循环并行+事件通信"不实（实为单维护循环+同步 submit）；多 Agent 协作/认知演化/补偿事务三模块真实实现但生产代码零引用；TaskFlow 源码存在但未接入 CoreLoopThree。

### 9.2 行业理论佐证

截止 2026-06-30 的 **35 项**行业最新研究全面佐证了本报告的发现和修复方向（完整对照见 §4.20 综合汇总表）：

- **MIT/ICLR 2026**：证明同模型自验证在过自信时崩溃 → 需激活多模型
- **ICML 2026**：证明对抗式 prompt 优于验证正确性 → 需改造 S1 prompt
- **T³ ICLR 2026**：证明信念偏差跟踪+截断提升 30 分 → 需扩展 calibrator
- **DCPM 2026.06**：证明双过程记忆的 SYSTEM 2 在跨领域推理上贡献最大 → 需增强 L4
- **Conformal Abstention 2026**：提供 99% 目标的数学基础 → 需引入共形弃权
- **EIR/ECR 2026.06**（T18）：控制论自纠正诊断 → 需引入 EIR×ECR 联合度量
- **n_eff 2026.06**（T19）：相关错误侵蚀评审团 → 需确保 S2/S1/S1-expert 来自不同模型家族
- **工具调用护栏 2026.06**（T20）：三层护栏 → 需在 tool_d/sandbox 接入完整护栏链
- **Proof-of-Guardrail 2026**（T25）：护栏可验证 → 需 cupolas health_check 真实检测而非硬编码

### 9.3 修复路径

本报告提出**六层修复体系**，按优先级分阶段实施：

1. **P0-致命（第一层）**：修复管线可达性（plan_strategy 注入）+ B6 输出传播 + B4-B5 agent_id 映射——让双思考系统先能跑起来且产出可达用户
2. **P0-根本（第二层）**：激活多模型基础设施（coordinator/ 接入）+ 对抗式验证改造 + Phase 0/4 修复——让跨模型验证生效、验证方向正确
3. **P0-关键（第三层）**：cupolas/daemon_security 集成 + gateway/market 致命 bug 修复 + OOM/heapstore 激活——让系统安全和持久化基线可用
4. **P1-重要（第四层）**：信念偏差跟踪 + 循环检测 + 双引擎统一 + CoreLoopThree 三模块接入——让系统鲁棒
5. **P1-重要（第五层）**：EIR/ECR 诊断 + n_eff 校正 + 工具调用护栏 + taskflow ODR 修复——让系统可诊断可防护
6. **P2-增强（第六层）**：共形弃权 + 记忆去偏 + 双过程记忆——让 99% 目标有数学基础

完成 P0（第一至三层）后，双思考系统将在产线真实执行且产出可达用户，安全护栏和持久化基线激活。完成 P1（第四至五层）后，系统具备跨模型验证、对抗式验证、信念偏差跟踪、语义循环检测、EIR/ECR 诊断能力。完成 P2（第六层）后，共形弃权为 99% 目标提供数学保证（以弃权率为代价）。

### 9.4 关键洞见

**项目最大的问题不是缺少技术，而是已有技术未被使用。**

coordinator/ 目录的多模型基础设施（dual_model.c/majority.c/arbiter.c）已经实现了行业 2026 年才论文化的理论（Cross-Model Disagreement、AdversaBench 三法官），但 ThinkDual 升级时**绕过**了它们。confidence_calibrator 已经实现了 T³ 的信念偏差跟踪，但未充分使用。**激活已有资产**比引入新技术更紧迫。

Airymax 的设计思想是超前的（多模型交叉验证在 2026 年被行业验证），问题在于**实现路径偏离了设计**——ThinkDual 升级选择了单 LLM 的"简化"路径，且 plan_strategy 从未被注入导致整个管线不可达。

**B6 输出封闭是最具欺骗性的问题**：即使修复管线可达性让 Phase 2 执行，批判产出仍被封闭在 cognition engine 内部的 ctx_window 中从不传播给用户。这意味着"双思考系统在运行"与"双思考系统产出可达用户"是两个完全不同的问题——历史审查只验证了前者（通过日志确认 Phase 2 执行），从未验证后者（task_node_output 从未检查）。这是学术证伪方法的核心价值：**确认性审查会满足于"Phase 2 执行了"，证伪性审查追问"Phase 2 的产出去哪了"**。

**atoms 内核层的多重失效揭示了"编译通过≠功能正常"的根本教训**：OOM handler、heapstore 持久化、taskflow ODR、syscall 沙箱——这些模块全部编译通过，部分甚至有单元测试，但在生产路径中从未被激活或存在定义冲突。安全系统（cupolas/daemon_security）的双重未集成更加剧了这一问题。**发布前必须引入端到端冒烟测试（ACC-DT00）**，验证从用户输入到用户输出的全链路贯通，而非仅验证各模块独立编译通过。
