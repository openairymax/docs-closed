# 模块边界与基石底座界定

> **版本**: v1.1.0 | **日期**: 2026-08-22 | **团队**: A
> **代码路径**: `agentrt/`（commons / atoms / cupolas / gateway 四基石）
> **文档属性**: 内部开发性文档（closed-docs），开源文档不承载本文件

> 战略定位：AirymaxRT 的目标是成为行业标准底座。底座的意义不在代码量，而在**契约**——被冻结的接口、ABI、协议与安全边界才是"不可动摇"的实体。本文界定核心四大模块的精确边界、社区开发者自由开发的接口面，以及"除了核心，一切都是服务"的工程化路径（第 4 节科研论证）。

## 1. 基石底座：commons + atoms + cupolas + gateway

| 模块 | 角色 | 不可动摇的契约实体 |
|------|------|--------------------|
| `commons` 统一基础库 | 跨模块共享的平台原语（platform/error/logger/memory/compat/effect） | 平台 API、错误码体系、路径体系（AIRY_HOME）、内存与线程抽象、回卷机制契约 |
| `atoms` 核心系统层 | 运行时内核机制（corekern 微核心 / coreloopthree 认知 / memoryrovol 记忆 / taskflow / syscall） | 系统调用接口、认知循环协议（GCCP/GRAD）、DAG 执行契约 |
| `cupolas` 安全穹顶 | 权限、净化、治理的安全边界 | 权限裁决语义、fail-closed 约定、ACL 契约 |
| `gateway` 网关层 | 对外协议边界（HTTP/WS/Stdio） | 协议（ARE Standards / L1-L3 运行时接口 / 服务发现），而非具体实现 |

这四者是**微核心哲学的编码化**：它们定义了"机制在平台内、策略由产品注入"的框架契约。契约一经发布即冻结（source/binary 兼容），其**实现**仅能通过架构评审演进，社区开发者不得绕过或分叉。

## 2. "不可动摇"的精确语义

"不能改动"针对的是**契约**，不是代码：

1. **接口冻结（SSoT）**：`commons` 的公开 API、`atoms` 的 syscall 与认知协议、`cupolas` 的权限语义、`gateway` 的线上协议，任何演进必须向后兼容，重大变更走 RFC + 版本化发布。
2. **实现可演进，但需背书**：四者内部的实现（如 coreloopthree 的调度算法）允许在架构评审批准下优化，但不允许以"改造"名义改变对外行为契约。
3. **扩展必须从外围接入**：新能力一律以服务/插件形式挂载到契约之上，不得修改核心源码。这是"除了核心，一切都是服务"的铁律。

## 3. 社区开发者可自由开发的边界

以下全部属于开放面，开发者可按契约自由实现、拔插、替换，不影响核心：

- `daemons/` 用户态服务（新 daemon 遵循 daemon 契约注册）
- `tools/` CLI/TUI 前端
- Skill / Agent / 工具集（通过契约动态发现与组合）
- 输入法、记忆策略、认知提示词等基础系统级插件功能（置于 `commons/utils/`，不进入 atoms 核心）
- gateway 的传输实现（HTTP/WS/Stdio 均可替换，协议不变）

自由开发的判据：**改动是否触及被冻结的契约实体。** 未触及即可自由开发；触及则必须走架构评审。

## 4. "一切皆插件"科研论证与落地结论

> 本节针对外部工程范式（DeepSeek Harness 的 Cordis 插件运行时）做科研型论证，回答三个问题：**机制的本质是什么？是否必要？如何在纯 C 内核中以 Airymax 自有语义落地？** 论证结论纳入开发计划（4.5）。

### 4.1 研究问题与方法

**研究问题**：行业标准底座要求"核心稳定、外围繁荣"。核心稳定需要契约冻结，外围繁荣需要**低门槛、可逆、可组合**的扩展机制。那么：

- Q1：构成"一切皆插件"的最小机制集是什么？
- Q2：这些机制在纯 C 内核（无对象模型、无 GC、无动态加载语言）下是否可实现、可验证？
- Q3：实现后如何与 AirymaxRT 既有的双思考系统（t2/t1-f/t1-p）、GCCP 意图完备确认、GRAD 计划级批判、工作大厅、记忆卷 memoryrovol 融合？

**研究方法**：对 DeepSeek Harness（github.com/deepseek-ai/deepseek-harness，v0.1.0-rc.x，MIT）全部源码做工程研究（含其 vendored 的 Cordis 插件运行时、core 服务脊柱、boot 组合机制、preset 会话组合、自进化演示），并检索 2025-2026 最新技术资料（2026-08-13 发布，与 DeepSeek V4 Pro 同步；Cordis 血统源自 Koishi；Star 11.5 万+；社区插件 1000+ 仓库）。将其"一切皆插件"的**表象**抽象为**机制本质**（4.2），再逐一论证在 C 内核下的等价物（4.3）。

### 4.2 机制本质（最小机制集）

对调研对象去品牌化抽象后，其扩展能力由八个正交机制构成。每一行给出工程本质（机制为何成立）：

| # | 表象（外部命名） | 机制本质（工程原理） | 必要性论证 |
|---|------------------|----------------------|-----------|
| M1 | 插件生命周期状态机（PENDING→…→DISPOSED） | **可逆组合语义**：注册即副作用，卸载按逆序回滚；组合的撤销是栈式、确定性的 | 无回滚则拔插会留下资源泄漏与状态污染，"可拔插"名存实亡 |
| M2 | 依赖声明（inject） | **声明式依赖图**：组件声明所需服务，运行时按依赖拓扑激活；消除手工排序，依赖不满足时组件不被激活 | 无依赖图则加载顺序靠人工，规模增长即崩溃点 |
| M3 | 服务仓库按名解析（Context Proxy） | **名称→实现的间接层（IoC 容器）**：消费者只认名字，不认实现；换实现不碰消费者 | 无间接层则"替换 provider"必然侵入消费方代码，破坏契约冻结 |
| M4 | 类型化事件四分发（emit/waterfall/parallel/serial） | **结构化扩展点**：广播=观察者，流水=中间件链（装饰），并行=扇出聚合，串行=责任链 | 无扩展点则新能力只能改核心，违反"扩展从外围接入" |
| M5 | 能力三角（Definition/Provider/Consumer） | **契约-实现-消费三分离**：一个能力 = 接口声明 + 实现 + 消费模型工具，三者独立演进 | 三分离是标准化的前提：接口冻结、实现竞争、消费多样 |
| M6 | 组合清单（Profile/Bundle 分层覆盖） | **声明式装配 + 分层覆盖**：运行实例 = 插件树；配置补丁层热生效 | 无装配清单则"大规模拔插"无法配置化表达，只能改代码 |
| M7 | 会话级 preset | **实例组合与隔离**：同一进程内多个装配实例并行，会话间互不可见 | 无会话级隔离则多 Agent 无法共享内核，底座无多租户能力 |
| M8 | 自进化（self-modification） | **元级受控反射**：运行时检查并修改自身插件树（内存内） | 远期目标；未受控的元级修改是安全与稳定风险，须沙箱约束 |

**判定**：M1-M7 是构成"一切皆插件"的**必要机制集**；M8 为充分性增强项（可选）。该机制集具有**机制完备性**——覆盖了"注册（M1）→ 装配（M2/M6）→ 解析（M3）→ 扩展（M4）→ 标准化（M5）→ 隔离（M7）"的完整生命周期。

### 4.3 C 内核等价性论证（Q2）

纯 C 内核没有对象模型、代理、动态加载语言特性。逐一论证等价实现与代价：

| # | C 侧等价实现 | 可行性 | 关键约束 |
|---|--------------|--------|----------|
| M1 | 注册表 + disposer 函数指针栈；`airy_effect` 已落地（commons/utils/effect） | ✅ 已验证 | 无 GC，disposer 必须显式登记，禁止隐式资源 |
| M2 | 显式依赖表（数组 {服务名, 提供者}）+ 拓扑排序激活 | ✅ | 依赖关系须静态声明，不做反射式自省 |
| M3 | 服务索引表（名称→getter 函数指针），`method_dispatcher` 同构扩展 | ✅ 已有雏形 | 键为字符串常量表，禁止动态拼接键 |
| M4 | 事件总线：回调表 + 四分发器（广播/流水/并行/串行），语义与现有认知事件对齐 | ✅ | 并行分发须由调度器（sched）执行，认知循环内保持确定性 |
| M5 | 契约头文件 + 实现注册 + 消费声明三文件分离 | ✅ | 契约即头文件 ABI，实现为 .so/.a 插件 |
| M6 | 编成单（YAML 纯数据，禁止表达式注入）+ 补丁覆盖合并 | ✅ | 配置保持纯数据，不引入 DSL |
| M7 | 进程内装配上下文（arena 作用域）+ 会话级快照/恢复 | ✅ | 隔离粒度按会话，共享只读内核数据 |
| M8 | 沙箱内内存插件表检查 + 受控挂载/卸载 | ⚠️ 可行性成立，风险高 | 需先具备 M1 完全回滚与状态保存，默认关闭 |

**结论**：M1-M7 在纯 C 内核下全部可实现且代价可控；M8 可行性成立但须后置。无对象模型不构成障碍——注册表 + 函数指针 + 显式依赖表足以表达全部机制语义。

### 4.4 Airymax 自有语义命名（Q3 之融入）

为避免直接沿用外部术语，同时与项目既有命名体系（corekern/coreloopthree/memoryrovol/work_hall/airy_effect）对齐，采用以下 Airymax 语义命名：

| # | 机制本质 | Airymax 命名 | 与既有系统的融合点 |
|---|----------|--------------|--------------------|
| M1 | 可逆组合语义 | **回卷机制（rollback effect）** | 复用 `airy_effect`，从请求级推广到 daemon 级作用域 |
| M2 | 声明式依赖图 | **依赖宣言（dependency manifest）** | 挂在 daemon 契约注册表，拓扑激活由 sched 驱动 |
| M3 | 服务按名解析 | **服务索引（service index）** | 与 `method_dispatcher` 同构扩展为 daemon 级索引 |
| M4 | 结构化扩展点 | **认知事件总线（cognition bus）** | 双思考系统事件（t2 生成/t1-p 四验/t1-f 终裁）经总线分发；GCCP/GRAD 成为可组合认知策略 |
| M5 | 契约-实现-消费三分离 | **能力契约环（capability ring）** | 以契约头文件为环心，实现注册、消费声明环绕其上 |
| M6 | 声明式装配 | **能力编成单（capability manifest）** | 与工作大厅任务编成（DAG）衔接：编成单→任务 DAG→sched 执行 |
| M7 | 会话级组合隔离 | **会话能力套件（session cap-suite）** | 双思考系统按会话装配；记忆卷 memoryrovol 作为套件可挂载项 |
| M8 | 受控元级反射 | **自成长（self growth）** | 远期；受控沙箱内检查/调整能力编成 |

**融合特色**：AirymaxRT 的认知循环天然是"能力组合"的实例——t2（主思考/生成）、t1-f（快思考/语境终裁）、t1-p（专业思考/逻辑验证）三角色模型即能力契约环的消费者；GCCP 意图完备确认是会话级认知策略；GRAD 计划级批判（E-01~E-04 四验 + 语境终裁）是认知事件总线上的确定性串行链。因此该机制集不是对内核的改造，而是对既有认知循环的**机制显式化**。

### 4.5 开发计划结论

**论证结论：纳入开发计划。** 依据：

1. **必要性**：M1-M7 是"除了核心，一切都是服务"的充分必要工程化表达；没有它们，该原则只是口号而非可执行机制。
2. **可行性**：纯 C 等价实现全部可行，且第一块基石（`airy_effect` 回卷机制）已验证通过。
3. **融合性**：机制集与双思考系统/GCCP/GRAD/工作大厅/记忆卷天然对接，落地即显式化现有设计。

**分阶段计划（全部由外围实现，不触碰四基石契约）**：

| 阶段 | 内容 | 目标版本 | 验收标准 |
|------|------|----------|----------|
| P0 | 回卷机制铺开（daemon 级 effect 作用域）+ 服务索引化 | v0.2.0 | 任一 daemon 卸载后无资源残留、白名单/方法/工具全部经索引解析 |
| P1 | 依赖宣言 + 认知事件总线（四分发） | v0.2.x | 依赖不满足的插件不被激活；认知事件可被外围订阅/包装 |
| P2 | 能力编成单（声明式装配 + 补丁层热生效） | v0.3.0 | 组合清单变更不重启进程；拔插某 daemon 不影响其余 |
| P3 | 会话能力套件（双思考系统按会话装配） | v0.3.x | 同一进程内多会话不同认知策略并行，互不可见 |
| P4 | 自成长（受控沙箱元级反射） | 远期评估 | 默认关闭，仅配置化启用，具备完整回滚 |

**否定项（明确不纳入）**：不引入 DSL（配置保持纯数据）；不照搬 TS 对象模型（C 侧用注册表/函数指针/显式依赖表）；不在 `atoms` 核心内置具体插件实现；HMR 热重载默认关闭（先具备完整回滚与状态保存）。
