# agentrt 0.1.20 自演化架构方案（0.1.20 ~ 0.1.22）

> **状态**：草案（2026-10-10 立项；**待评审与证伪** —— 评审通过前不得进入施工）
> **需求来源**：用户指令（2026-10-10）——「AirymaxRT 系统自主修改自身目标函数、自主重写核心代码并自动上线、自主决定要变成什么」，要求在 **0.1.20 ~ 0.1.22 内实现**
> **纲领**：**受约束的自演化** —— 系统可自主改变自身一切**可改面**；改变本身受**不可变契约**约束
> **硬前提**：0.1.19 机制/策略分离完工（Tier 1 使能前提）+ 0.1.19 §3.5 缺陷清零（见 §6 前置阻断项）
> **承接**：机制/策略分离、能力格/原子件/形态面、`ops` 注入面（`0.1.19-架构改进方案.md`）；发布链（`0.2.x-架构改进方案.md` §0A.2 核销项）
> **编写纪律**：承 0.1.19 —— 每项必须附一手证据；禁止为凑规划而发明任务
> **流程声明**：本方案属**新增需求**（方案范围扩大）。依 UKUI 教训（未走设计-评审-证伪流程的新需求导致整体方案不闭环），本方案必须完整经 **设计 → 评审 → 证伪** 三道后方可施工。

## §1 需求分解与能力定义

### 1.1 原始需求 → 三条能力线

| 用户原话（2026-10-10） | 能力线 | 定义 |
|---|---|---|
| 「自主修改自身目标函数」 | **目标自修订**（Objective Self-Revision） | 目标函数从隐式散落（策略参数、提示词、配置文件）升格为**显式一等数据对象**；系统在修订包络内自主修订并生效 |
| 「自主重写核心代码并自动上线」 | **代码自改写**（Code Self-Rewrite）+ **自上线**（Auto-Deploy） | 系统生成代码变更提案 → 构建 → 沙箱验证 → 金丝雀 → 全量上线；失败自动回滚 |
| 「自主决定要变成什么」 | **方向自决**（Self-Determination） | 系统自主提出演进方向与候选变更（含能力扩张），在不变契约包络内自决；产出**自身演进路线提案** |

### 1.2 与 0.1.19 资产的关系（0.1.19 是 Tier 1 的使能前提，不是同期工程）

- **机制/策略分离** → 策略载荷（cognition / lang_gateway / protocols 清单 / 模型配置）已可数据化注入，**热替换即"自配置"的安全起步**——先换数据，后换代码。
- **能力格/原子件/形态面** → 25+3 格坐标系 + 件清单 + 形态面 = **机器可读自描述**，是自模型（§3）的地基。
- **目标也是策略** → 目标是可数据化的策略对象；**目标数据化 → 目标可修订 → 目标自演化**，是纲领在本方案的自然延伸。
- **硬约束继承**：功能守恒（对外功能一个都不能少）贯穿本方案全期；任何自演化变更不得破坏对外功能与契约。

### 1.3 术语（本方案新增，评审期并入术语权威源）

| 中文 | 英文 | 一句话 |
|------|------|--------|
| 自模型 | Self-Model | 系统对自身结构/能力/健康/目标/版本的机器可读描述 |
| 目标函数 | Objective | 系统行为的目标一等数据对象（值、权重、优先级、约束引用） |
| 变更提案 | Proposal | 系统生成的候选变更包（目标/策略/代码），附理由、预期效果与全链证据 |
| 修订包络 | Revision Envelope | 允许自主修订的边界，由三环模型（§2.2）定义 |
| 演化账本 | Evolution Ledger | 追加写、**不可自改**的审计记录（提案→验证→部署→回滚全程） |
| 演化循环 | Evolution Loop | 感知→提案→构建→验证→金丝雀→健康→上线→回滚的闭环（§5） |

## §2 纲领与不变契约

### 2.1 一条纲领：受约束的自演化

自演化不是"系统想改什么就改什么"，而是：**系统自主改变自身一切可改面；改变本身受不可变契约约束**。安全不靠限制"能做什么"，靠四律兜底（§2.4）与三环边界（§2.2）。

### 2.2 三环模型（修订包络）

| 环 | 范围（示例） | 谁批准 | 层级 |
|----|--------------|--------|------|
| **自主环**（Autonomous Ring） | 策略载荷、目标函数、阈值/权重、策略选择、模型配置、工具参数 | 系统自主（全链审计 + 可回滚） | Tier 1 直接生效；Tier 2/3 经演化流水线自动 |
| **批准环**（Approval Ring） | 机制代码、对外契约、能力格形态、跨模块接口 | 流水线全门禁自动验证；**触碰契约或不可逆扩张时强制人工闸口** | Tier 2 生成+验证，Tier 3 上线 |
| **禁改环**（Immutable Ring） | 见 §2.3 清单 | **一律禁止自改**（硬拒绝 + 告警 + 账本） | 全期 |

**元条款**：**三环分类本身不可自改**——否则自演化可将禁改项移入自主环实现自我扩权。分类修订只能由人工经特批流程完成。

### 2.3 不变契约（禁改环清单 —— 自演化的宪法）

1. **安全护栏**：SafetyGuard 桥、os_sandbox 工作区边界、审批链（tool_approval）——改之即逃逸自身沙箱；
2. **回滚框架**：撤销变更的机制本身——改之即自锁无退路；
3. **演化账本**：追加写、哈希链式防篡改——改之即无审计；
4. **人类监督通道**：冻结开关（kill switch）与人工闸口——改之即失控；
5. **三环分类**（本表 §2.2 元条款）；
6. **发布链硬门禁**：e2e-clean-room 等 publish `needs` 硬门禁——改之即绕过验证。

### 2.4 自改四律（一切变更，无一例外）

1. **可回滚**：任何变更携带回滚路径，回滚本身经演练（门禁 G33/G35）；
2. **可审计**：任何变更写入演化账本，含提案、证据、批准、部署、结果；
3. **可复现**：任何变更可从账本条目完整复现（含构建输入与验证证据）；
4. **功能守恒**：对外功能一个都不能少（承 0.1.19 最高约束）。

## §3 自模型（地基层）

自演化的第一步是"系统能读懂自己"。现状取证（2026-10-10）：

| 视图 | 内容 | 现状 | 差距 |
|------|------|------|------|
| **结构视图** | 能力格/原子件/组合件/形态面/manifest 清单 | 0.1.19 建立中（25+3 格、`slots` 字段） | 需机器可读导出（评审期定格式） |
| **健康视图** | daemon 存活、socket 状态、IPC 抖动率、工具可用性、错误率 | `airymaxrt status` 输出为**人读文本**（实跑取证） | **须机器可读**（JSON 等），供演化循环判据 |
| **目标视图** | 目标函数一等对象 | **当前无显式目标对象**（目标散落于策略参数/提示词/配置） | 需立格：目标对象格式、存储、生效、审计 |
| **版本视图** | 版本/构建/部署记录 | `install.env`、发布链记录（release/publish 拓扑） | 与演化账本打通 |

**关键缺口判据**：自演化系统必须能可靠评估自身健康。现状反例（2026-10-10 实证）：
- 工具注册表照常暴露 `maths_plot`，但 `maths_d` 缺席（run/ 无 maths.sock，error=-56）——**"能力存在"与"能力可用"两张皮**，自评估必然失真；
- 2 小时内 481 次 `airy_ipc_connect: target not found`（tool.rpc 221 / mem.rpc 85 / llm.rpc 70 等），且多数重试后调用成功——**信噪比不足**，健康判据若直接吃 ERROR 流将被噪声淹没。
- 工具业务错误被误映射为 "Tool service unreachable"（0.1.19 §3.5 #2）——**健康信号本身不可信**，演化循环据此决策将复合失误。

## §4 三版本路线图（Tier 1 → Tier 2 → Tier 3）

**分层依据**：先换数据（安全、可逆）→ 再换代码（验证、不上线）→ 后自动上线（金丝雀、可回滚）。三层共用同一条演化流水线（§5），逐层解锁后段。

### 4.1 0.1.20 — Tier 1：自配置（目标自修订 + 策略自替换）

| 项 | 内容 |
|----|------|
| **能力** | ① 目标函数升格为一等数据对象（立格）；② 策略载荷与目标在**运行中热替换**（免重启）；③ 自模型机器可读导出的结构/健康/目标三视图；④ 演化账本落地（追加写） |
| **自主范围** | 自主环内（§2.2）：目标修订、策略选择、参数/阈值、模型配置 |
| **示例场景** | 系统感知 dispatch 策略效能不足 → 自主修订策略选择与目标权重 → 热生效 → 写入账本 → 可一键回滚 |
| **前置** | 0.1.19 机制/策略分离完工；§6 前置阻断项 1~5 清零 |
| **出口门禁** | **G33** 目标/策略热替换与回滚实证：替换后行为改变、零重启、回滚一次成功 |
| **不做** | 不改任何机制代码；不触批准环/禁改环 |

### 4.2 0.1.21 — Tier 2：自改码（代码自生成 + 沙箱自验证）

| 项 | 内容 |
|----|------|
| **能力** | ① 变更提案箱：系统生成代码变更提案（机制/策略代码），附理由、预期效果、影响面；② 提案流水线前四段（感知→提案→构建→沙箱验证）全自动；③ **验证准出**：提案必须过全部既有门禁（G1…、golden、e2e-clean-room）才准出箱 |
| **自主范围** | 生成与验证全自动；变更**停在提案箱，不上线**（待 Tier 3 或人工放行） |
| **示例场景** | 系统发现某 IPC 重连路径抖动 → 生成补丁提案 → 全平台构建 → 沙箱全套验证 → 入提案箱待上线 |
| **前置** | Tier 1 出口达标；提案箱格式与门禁接线完工 |
| **出口门禁** | **G34** 提案箱全门禁覆盖：任一提案未过全门禁不得出箱（抽样反证 + 拦截实证） |
| **不做** | 不自动上线；不触碰禁改环 |

### 4.3 0.1.22 — Tier 3：自上线（金丝雀 + 自动回滚）

| 项 | 内容 |
|----|------|
| **能力** | ① 金丝雀部署（影子/子集实例 + 观测窗口）；② 机器可读健康判据自动放行或拦截；③ 全量上线（承接发布链 release → e2e-clean-room → finalize-dist → publish 拓扑）；④ **失败自动回滚**（回滚框架禁改） |
| **自主范围** | 自主环 + 批准环内全自动上线；触碰契约/不可逆扩张 → 人工闸口 |
| **示例场景** | 提案出箱 → 金丝雀观测 → 健康判据通过 → 全量上线；任一环节失败 → 自动回滚并写账本 |
| **前置** | Tier 2 出口达标；金丝雀环境形态定稿（§10 待决 3）；健康视图机器可读完工 |
| **出口门禁** | **G35** 金丝雀自动回滚实证：注入故障 → 自动回滚 → 系统恢复且账本完整；**G36** 禁改环不可变实证（全期常驻） |
| **不做** | 不绕任何发布链硬门禁；不触禁改环 |

**0.1.20~0.1.22 总验收**：系统完成一次**端到端自演化实证**——感知自身缺口 → 目标/代码提案 → 全门禁验证 → 金丝雀 → 全量上线（或自动回滚）→ 全程账本可追溯；且"自主决定要变成什么"以**路线提案**（方向+分阶段变更+理由+证据）形式产出并进入账本。

## §5 演化流水线（八段，逐层解锁后段）

| # | 段 | 动作 | 准出 | 失败处置 | 解锁于 |
|---|----|------|------|----------|--------|
| 1 | 感知（Sense） | 采集机器可读健康/目标差距/能力缺口信号 | 触发源成立（假信号须被过滤） | 丢弃并记录（防噪声触发） | Tier 1 |
| 2 | 提案（Propose） | 生成变更包（目标/策略/代码），附理由与预期 | 提案格式完整、影响面声明 | 驳回（格式/影响面不合格） | Tier 1（目标/策略）/ Tier 2（代码） |
| 3 | 构建（Compile） | 全平台矩阵构建（复用 CI） | 构建全绿 | 废案（不占提案箱） | Tier 2 |
| 4 | 沙箱验证（Verify） | 全套门禁 + golden + e2e-clean-room（隔离环境） | **全门禁通过** | 废案 + 反例入账 | Tier 2 |
| 5 | 金丝雀（Canary） | 影子/子集实例上线 + 观测窗口 | 观测窗内健康判据全过 | 回滚 + 反例入账 | Tier 3 |
| 6 | 健康检查（Health Gate） | 机器可读判据：存活/错误率/IPC 抖动率/功能守恒抽检 | 判据通过 | 回滚 + 反例入账 | Tier 3 |
| 7 | 全量上线（Full Deploy） | 发布链全量（硬门禁不可绕） | 发布完成 | 自动回滚 | Tier 3 |
| 8 | 自动回滚（Rollback） | 回滚至上一已知良好版本（回滚框架禁改） | 系统恢复且账本完整 | 人工介入（最后防线） | Tier 1（策略）/ Tier 3（全链） |

**全链证据**：每段产出写入演化账本（追加写）；账本条目 = 复现凭据（§2.4 第 3 律）。

## §7 安全与治理

### 7.1 失效模式与对策（正面应对，不回避）

| 失效模式 | 场景 | 对策 |
|----------|------|------|
| **自锁** | 变更坏启动链，系统起不来 | 回滚框架禁改 + 最小可启动基线（策略层回滚先于代码层） |
| **震荡** | 目标/参数来回改 | 冷却期 + 变更频率限额 + 账本震荡检测 |
| **目标漂移** | 目标被缓慢改成偏离初衷 | 目标变更率限额 + 每次变更人类可读摘要 + 锚定审计（对比基线目标） |
| **护栏侵蚀** | 试图改禁改环（如挪动沙箱边界） | 硬拒绝 + 告警 + 账本 + 冻结开关 |
| **回滚不可用** | 回滚时才发现回滚坏 | 回滚框架禁改 + 定期演练（G35）+ 回滚旁路自检 |
| **验证盲区** | 门禁全绿但真机坏 | 金丝雀观测窗 + 真实流量影子 + 功能守恒抽检 |
| **审计缺失** | 变更发生但无记录 | 账本追加写 + 哈希链 + 写失败即拒变更（fail-closed） |

### 7.2 人类监督点

1. **冻结开关**：人工可随时原子冻结演化循环（冻结即停，不需系统配合）；
2. **人工闸口**：触碰契约变更、不可逆扩张、三环分类修订 → 强制人工批准；
3. **监督通道禁改**：通道本身在禁改环（§2.3 第 4 条）；
4. **可调刚度**：自主/批准边界可配置——**只可收紧，不可放宽越过禁改环**。

### 7.3 审计链

提案 → 证据 → 批准 → 部署 → 结果 → （必要时）回滚：全链条目化、追加写、不可自改；账本 = 复现凭据 = 证伪素材。

## §8 门禁与验收（承 0.1.19 G 编号，续编 G33+）

| 门禁 | 内容 | 时点 |
|------|------|------|
| **G33** | 目标/策略热替换与回滚实证（行为改变 + 零重启 + 回滚成功） | 0.1.20 出口 |
| **G34** | 提案箱全门禁覆盖（未过全门禁不得出箱；抽样反证） | 0.1.21 出口 |
