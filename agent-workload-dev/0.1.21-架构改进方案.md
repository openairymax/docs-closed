## 2. 目标、非目标与总原则

### 2.1 目标（可证伪）

1. **GPU 服务可用**：在**具备 GPU 的目标机**上，AgentRT 能以 GPU 后端完成一次完整对话（`gate:runtime`），
   并在**无 GPU 机器**上给出**明确降级与原因**（不是崩溃、不是静默走 CPU）。
2. **版本可自证**：任一二进制在启动 30s 内、`/health`、安装清单三处报告的版本与构建标识**完全一致**，
   且与发行 tag 可对账。
3. **安装可核验**：安装产物为真实文件（r98 已确认 `install.sh` 以 `cp -rf` 落地，与 `/tmp` 无关），
   每件可校验 sha256，可干净卸载。
4. **失败可判**：执行层不再把审批拒绝/失败路径判成成功（`success` 字段语义反转）；任一失败路径都能在日志与返回码上被判红。
5. **账本可解释**：三账与 `WARN 276` 每一处偏离都有 `RATCHET-JUSTIFY`，无静默漂移。
6. **文档可信**：0.1.20 的 6 处过期/冲突口径全部修正，读表不再误判。

### 2.2 非目标

- 不做多租户、不做分布式调度、不做跨进程 binder、不做跨族 MTP、不做 iGPU 换内核。
- 不做第 22 个 ops 族、不做 `G33–G63`、不做任务面 C 大厅重构。
- 不追求「平均 CCN<2.5」在 0.1.21 达标（是阶梯目标，本版只做可解释化与棘轮）。
- 不承诺 U 面 20 卡全部转为承诺项（L-5 的合法结论可以是「维持现状」）。

### 2.3 总原则（沿用 0.1.20，不新增教条）

| 原则 | 落地要求 |
|---|---|
| 真实生产 | 禁演示数据、禁桩、禁「只在 lab 绿」就宣布交付 |
| 可证伪判据 | 每条判据必须能被一个具体命令判出 PASS/FAIL；写不出判据的任务不许进批次 |
| 回退已验证 | 有行为变更的项必须附回退路径，且回退路径本身跑过一次 |
| 必须上账 | 增删行必须同步三账与 pin，`RATCHET-JUSTIFY` 随提交落库 |
| 真实集成 | 组件级绿不算；必须走真实调用链（`gate:runtime`） |
| 机制与策略分离 | 修复落在机制层，不在调用点打补丁（r144 的 `-r` 覆盖即范例） |

## 3. 任务面 A：运行态自证与安装形态

> 这一面承接 0.1.20 §4.4 中**尚未闭合**的 P-D②③ / P-E①③ / P-F②③④ / P-I②③，
> 另加两项**新增能力**（A-1 构建标识、A-2 逐件清单与卸载）；P-A 与 P-G 已闭，不在此重做。
> 共性是「发行物到了用户机器上之后无法自证」——本地全绿、装完不知构建号、日志无上限、审计写进 `$HOME`。

### A-1 发行版本与构建标识贯穿

- **现象**：装完只知道「有 14 个 daemon 在线」，不知道是哪个发行版、哪个 commit、哪次 CI 构建。
- **证据**：`commons/utils/compat/compat.h:395/400` 声明 `airy_version_string()` / `airy_build_info()`，
  `commons/utils/compat/compat.c:161/166` 实现。**`airy_build_info()` 全树零调用**；
  `commons/tests/unit/test_types.c:501` 断言的是 `airy_version_string()`（与 `AIRYRT_VERSION` 相等），
  **不是** `airy_build_info()`。且后者的内容是
  `"AgentRT v%s | Compiler: %s | Platform: %s | Build: %s %s"`（`__DATE__ __TIME__`，`compat.c:166-174`）——
  那是**编译时刻**，不是构建标识，且直接破坏可复现构建，不能作为 build_id 载体。
  `daemon_boot.c:181-182` 打印的 `version %s` 取 per-target 编译期 `DAEMON_VERSION`，r129 已在
  十四 daemon 横幅上如实打出 `version 0.1.20`——**版本号有了，构建标识没有**。
  发行侧已有版本来源：`scripts/install.sh:709-718` 写 `release.env`（`AIRY_VERSION=v%s`、
  可选 `AIRY_ARTIFACT_SHA256`、`AIRY_RELEASE_ID`）；但 C 侧**零消费点**，`/health` 与安装清单无版本字段。
- **根因**：版本信息有两个互不相通的来源（编译期 `DAEMON_VERSION`、发行期 `release.env`），
  前者进了日志但不含构建信息，后者写了文件却无人读取；`/health` 与清单更是完全没有出口。
  另有第三个**伪来源** `airy_build_info()`：名字像构建标识，实为编译时刻且零调用。
- **做法**：
  1. 发行期在既有 `release.env` 上补 `AIRY_BUILD_ID`（`run<id>.<attempt>` + commit 前 12 位），不另造第二份版本文件；
  2. 新增 `airy_build_id()`（语义 = 发行构建标识，**不是编译时刻**），解析 `release.env` 进进程内缓存，
     三处消费：启动日志首行、`/health` 的 `version` 字段、安装清单 `build` 段；
  3. `airy_version_string()` 保留，语义收敛为「发行版本」，与 `AIRY_RELEASE_ID` 同源；`release.env` 缺失时
     回落 `DAEMON_VERSION` 并在日志标注 `release=unknown`；
  4. **不改造** `airy_build_info()` 承载 build_id——`__DATE__/__TIME__` 破坏可复现构建；若保留，
     仅限人读诊断，不得进入 `/health` 与清单。
- **判据**：
  - `gate:lab`：新增单测断言三处取值同源且格式合法（`vX.Y.Z` + `g<sha12>` + `run<id>.<attempt>`）。
  - `gate:runtime`：干净机安装后，`agentrt --version`、`curl /health`、`manifest` 三者逐字段相等，且与发行 tag 对账。
- **回退**：注入通道用环境变量缺省值兜底（缺省回落 `DAEMON_VERSION`），关掉注入不影响启动。
- **规模**：约 200 行（含注入脚本与单测）。

### A-2 安装形态：逐件清单 + 卸载入口（新增能力，非 P-G 残余）

- **现象**：装完无法逐件核验；卸载入口**存在但会毁数据**——`--uninstall --keep-data` 的语义与实际相反；
  卸载根目录取自可被伪造的 `install.env`；无 dry-run、无删除清单。
- **证据**：原 P-G 的「`/tmp` 符号链接」归因已于 r98 **撤销**——`scripts/install.sh:720-734` 以 `cp -rf`
  落真实文件，`bin`/`lib`/`include`/`share` 是指向**安装根内** `current/<d>` 的链接，`current` 指向
  `releases/<ver>`，全程不涉及 `/tmp`。`release.env` 只有**包级** `AIRY_ARTIFACT_SHA256`
  （`install.sh:709-718`），没有逐件哈希。
  **原判「安装器无卸载子命令」不成立**：`install.sh:366-409` 已有 `do_uninstall`，但有三处实缺陷：
  1. `--keep-data` 分支先 `rm -rf "$home"`（:396）再 `mkdir -p "$home/data"`（:397）——
     **用户 data/ 被整目录删除后才重建空目录**，保留语义完全失效；
  2. `$home` 在 `:368-372` 直接从 `config/install.env` 的 `AIRY_HOME=` 取值覆盖，**未做 `is_install_home` 校验**
     （同文件 `discover_install_home` 有校验，卸载路径却绕过了它），伪造一行 `AIRY_HOME=/` 即可让 `rm -rf` 指向任意目录；
  3. 无 dry-run、无删除清单，执行前无法核对将被删除的路径集合。
- **根因**：安装器把「能跑起来」当目标，未把「可审计、可移除」当目标；卸载逻辑沿用了安装期
  「信任 `install.env`」的假设，却没有安装期那套 `is_install_home` 校验与路径归一化。
- **做法**：
  1. 安装根下写 `install-manifest.json`（每件：相对路径、大小、sha256、来源 tag、`release.env` 摘要）；
  2. **修 `do_uninstall`**：`--keep-data` 改为「先移动 data/ 到同级临时目录 → 删其余 → 再移回」
     （或逐项删除 data 之外的路径），禁止「先 `rm -rf` 根目录」；`$home` 必须过 `is_install_home`
     + 白名单前缀 + 非 `/`、非 `$HOME` 本身；
  3. 提供 `--dry-run`（打印删除集合，零副作用）与 `--purge`，按清单逆序删除，不碰用户数据；
  4. 清单的 `build` 段与 A-1 同源，避免两套版本描述。
- **判据**：
  - `gate:ci`：新建 `e2e-clean-room` 作业（当前 `.github/workflows/` **无此作业**，需随本项一并落地），
    跑「装 → 逐件校验清单 → `--keep-data` 卸载 → **data/ 逐件仍在** →
    `--purge` → 目录清净」五步，缺一步判红；另加反例：伪造 `AIRY_HOME=/tmp/evil` 的 `install.env`，
    卸载**必须拒绝**（非零退出且无删除动作）。
  - `gate:runtime`：`--dry-run` 输出集合与实际删除集合完全一致（多删/漏删均判红）。
- **回退**：清单与 dry-run 均为**增量**，不动现有版本化布局；清单缺失时卸载退回「只删 `releases/<ver>`」。
- **规模**：约 280 行（含 `do_uninstall` 缺陷修复与反例测试）。

### A-3 安全审计日志轮转与体积上限

- **现象**：安全审计文件持续增长，实测到 **8,406,889 B（≈8.0 MiB）** 仍无上限。
- **证据**：分层日志已有轮转——`commons/utils/logging/logging_backend_file.c:60-67` 缺省 `10*1024*1024`、
  `:110` 备份重命名；但 `daemons/common/src/security/daemon_security_audit.c` 为裸 `fwrite` 追加，
  **无 size 检查、无轮转、无加密**。
  契约实为 `docs/docs-linux/50-engineering-standards/20-contracts/contracts.md`（原写 `docs-workload/...`
  是**错误路径**，该目录不存在），其要求：审计日志 **500MB/天、保留 365 份、zstd 压缩 + 加密、
  由 `agentrt-log-rotator` 管理**。
- **根因**：审计写入与分层日志是两套设施；审计侧没有接入任何轮转。另需注意 `logging_backend_file`
  是**模块级全局单例**（`g_*` 状态 + 单一文件句柄），**没有 per-file 实例 API**，无法直接拿来给审计开第二个文件。
- **做法**：二选一并写进契约——(a) 审计复用 `logging_backend_file`；(b) 实现独立 `agentrt-log-rotator`。
  **优选 (b)**，理由有三：
  1. 契约本身要求专用 rotator 且参数（500MB/天、365 份、zstd+加密）与分层日志（10MB×5、明文、60s 刷盘）
     **完全不同**，用 (a) 必须改契约；
  2. `logging_backend_file` 无 per-file 实例 API，走 (a) 要先做实例化改造，工作量不低于写 rotator；
  3. 审计需要「加密 + 不可篡改」语义，混入应用日志会破坏其独立取证价值。
  短期若必须先用 (a) 兜底，**必须先提契约变更评审**，不得默认按 10MB×5 落地后仍声称符合契约。
- **判据**：
  - `gate:lab`：写入 > 上限的数据，断言产生 `.zst` 备份、主文件回落到阈值内、备份可解密还原。
  - `gate:ci`：契约测试校验 **rotator 存在且参数逐项等于契约值**（500MB/365/zstd/加密），参数不符判红。
  - `gate:runtime`：长跑 30min 后审计目录总体积有界，且最新备份可读。
- **回退**：轮转参数可配置，上限置 0 表示关闭轮转（仅用于排障）。
- **规模**：约 160 行（含 zstd/加密接线与契约测试）。

### A-4 测试隔离门禁（P-F③④ + P-I②）

- **现象**：测试会写 `$HOME`；存量已被污染；门禁只覆盖一条腿，`tools` 腿无覆盖；把门禁改坏也不会判红。
- **证据**：0.1.20 §4.4 P-F③④、P-I② 均记为未闭。一手锚点：`.github/workflows/sanitizers.yml:137-142`
  **直接调用 `ctest`**，未重定向 `HOME`/`XDG_*`/`TMPDIR`；`tools/scripts/ci/quality/gates/verify_release_gates.sh:234-279`
  **只对 B-2 子测**临时重定向 `HOME`，其余腿与 `tools` 腿无隔离；全树未见「反例注入」自检。
- **根因**：门禁只有「正向跑通」判据，没有「门禁本身失效要判红」的自证。
- **做法**：
  1. `ctest`/门禁启动前把 `HOME`、`XDG_*`、`TMPDIR` 重定向到沙箱目录，跑完断言 `$HOME` 零新增

  2. 覆盖两腿：`tests` 与 `tools` 各自独立判据，缺一腿判红；
  3. **反例注入**：门禁内置一个故意写 `$HOME` 的探针用例，必须被判红；若探针通过则该门禁自身判 FAIL；
  4. 存量污染清单化（哪些文件、哪条用例写的），清理后加白名单防复发。
- **判据**：`gate:ci` 三件事同时成立——正向绿、探针被拦、`tools` 腿有独立结论。
- **回退**：探针可 `AIRY_GATE_SELFTEST=0` 关闭（仅排障），CI 中禁关。
- **规模**：约 260 行。

### A-5 overflow 惰性创建与 0 字节件清理

- **现象**：实测 **516** 个 0 字节文件：**500** 个 `logs/cupolas/audit_overflow_*.log`、
  8 个 heapstore 件、7 个 `logs/*.out`、1 个 hall 件。
- **证据**（两处独立成因，比例悬殊）：
  1. **主因（500/516）**：`agent-workload/products/cupolas/src/audit/audit_overflow.c`
     `overflow_handler_create():242-248` 在**创建时**就调 `open_new_overflow_file():80-99`（`fopen` 在 `:90`）
     生成带时间戳的文件名（唯一调用点 `:428`），于是**每次启动都留一个 0 字节 `audit_overflow_*.log`**，
     与 stdout 重定向无关；
  2. **次因（7/516）**：`daemons/supervisor_d/src/proc/proc.c:245-248` 先
     `open(O_WRONLY|O_CREAT|O_APPEND, 0644)` 再 `dup2` 后 `exec`，为「子进程 fd 一定有效」而预创建，
     无输出的 daemon 即留下空 `*_d.out`。
- **根因**：两处都是「先建文件、后写内容」，且都没有「零事件/零输出则不落盘」的判据。
- **做法**：
  1. cupolas 侧改**惰性创建**：首次真实溢出事件时才打开文件（或先写内存环形缓冲，命中阈值再落盘）；
  2. supervisor 侧改**延迟 open**；若必须保证 fd 有效，改用 `pipe` + pump（父进程代写），
     **明确排除 `O_TMPFILE`**——无名文件在最后一个 fd 关闭时内容即丢，无法作为持久日志；
  3. 同时纠正一个错误设想：`poll`/`select` **无法**在父进程判断子进程「是否已写」，因为空文件与已写文件的
     fd 都处于可写状态；
  4. 提供 `airymaxrt doctor --gc-empty-out` 清存量，只删「白名单前缀 + size==0 + mtime 早于 N 天」三条件同时满足者。
- **判据**：
  - `gate:lab`：启动一个**不输出**的 daemon 与一个**零溢出事件**的 cupolas，断言均不留 0 字节文件；
    制造一次真实溢出/输出后，断言文件存在且有内容。
  - `gate:runtime`：干净机首启后 `find -size 0` 命中数为 0（允许显式白名单，且白名单需附理由）。
- **回退**：环境变量 `AIRY_PREOPEN_OUT=1` 恢复旧行为（仅排障）。
- **规模**：约 200 行（cupolas 惰性化 + supervisor 延迟 open + gc 子命令）。

### A-6 安装后自检 + Gate 路径一致性 + 热重载门禁化

- **现象**：装完没有**可信**的一键自检；lab 门禁与生产 gate 走的路径不一致；热重载只有一次性手工证据。

  - `gate:runtime`：doctor 全项 PASS，且**人为破坏任一项时返回非零**（自证非恒绿）；

- **回退**：doctor 为只读，不影响运行；热重载失败必须回落到旧配置（断言旧配置仍生效）。
- **规模**：约 340 行（含恒绿修复、`airy_paths_query()` 导出与两腿对齐）。

### A-7 无 key 定向引导与 `*_d.out` 判据

- **现象**：没配 key 时用户只看到一行普通日志；`*_d.out` 是否为空无法作为健康判据。
- **证据**：`daemons/providers/src/core/http.c:444` 现为 `SVC_LOG_INFO("C-L02: PROVIDER: no API key
  configured for api_base=%s ...")`（原 WARN 已降级）；`daemon_boot.c:176-178` 已把缺省改为

- **规模**：约 120 行。

## 4. 任务面 B：GPU 服务（本版唯一新增能力）

> 本面是用户硬指令（「0.1.21 必须实现 GPU 服务功能」），但仓库此前**零设计**。
> 因此本面的第一件事不是写代码，而是**证伪**：确认这套机器、这个后端到底能不能跑。
> 纪律：**先有可跑的 GPU 推理，才有「GPU 服务」这个词**；没有 GPU 证据前不得在任何文档、
> CLI 输出、发行说明中声称支持 GPU。

### B-0 可行性证伪与后端终论（前置闸门，必须先做）

- **现象**：仓库无 GPU 设计；现有自托管是 CPU-only。
- **证据**：0.1.20 交付的 `llama-server b11712` 为 CPU 构建；B50 为 llama.cpp SYCL 路径；
  全树 `vllm` 仅 **7 处**注释/提示串（`llm_service_types.h:71` / `cli_chat.c:267` / `local.c:31` /
  `think_service.h:26` / `envelope.c:36` / `envelope.c:246` / `CHANGELOG.md:948`），**无一行实现**；
  无 GPU 契约、无判据、无验收标准。
- **根因**：能力从未被规划，只被口头要求。
- **做法**：按顺序做三条探测，**任何一条不通过就降档，不得跳步**：
  1. **硬件层**：按厂商分路——NVIDIA `nvidia-smi`、AMD `rocm-smi`、**Intel `sycl-ls` / `xpu-smi`**
     （目标机 Arc B50 只认 Intel 路径，缺这两条会**必然假阴性**、把终论误判为 R3）；
     辅以 `lspci -nn` 与 `clinfo` 确认设备在册；记录驱动/运行时版本与可用内存
     （Intel iGPU 为共享内存，**没有独立显存**，不得按 dGPU 口径判显存）；
  2. **运行时层**：目标后端能否在本机加载一个最小模型并完成一次 `completion`（含 CUDA/ROCm/SYCL/Vulkan 任一）；
  3. **集成层**：该后端是否暴露 OpenAI 兼容 `/v1/chat/completions`；流式是否可用；错误码是否可透传。
- **终论三选一（必须择一写入本文档与本版发行说明）**：
  - **R1「vLLM 可用」**：三层全通 → 按 B-2 接 vLLM，文档可称 vLLM。
  - **R2「仅 llama.cpp-SYCL / 其他加速路径可用」** → 接实际后端，**文档与 CLI 一律写实际后端名**，
    禁止出现「vLLM」字样（含注释、提示串、发行说明）。
  - **R3「本机无可用加速器」** → 只交付 B-1 抽象层 + B-3 探测 + B-5 的 L0 档；
    **必须在发行说明中显式写明「0.1.21 未交付 GPU 推理」**，并把 GPU 推理顺延到有硬件的版本。
    此为**诚实降档**，不是失败，但**禁止**把 R3 写成「已支持 GPU」。
- **判据**：`gate:runtime` —— 一条可复跑命令输出三层探测结论（硬件 / 最小推理 / OpenAI 兼容），
  三者与终论一致；R3 时该命令必须给出「无加速器」的明确原因串。
- **回退**：B-0 为只读探测，无回退需求；但 R1/R2 的接入必须在 B-7 保证 CPU 路径不受影响。
- **规模**：约 150 行（探测脚本 + 结论落文）。

### B-1 provider 抽象扩展与能力协商

- **现象**：现有 provider 抽象只区分「远端 API / 本地 Ollama 兼容」，没有「加速器类型 / 显存 / 上下文上限 /
  流式支持」等能力位，无法做选路。
- **证据**：`daemons/providers/src/adapters/local.c:31` 注释即写明「localhost:11434 / vLLM 走 8080/v1——
  实际以…」，说明抽象层当时就没有定论。
- **根因**：抽象层按「协议」建模，没有按「能力」建模。
- **做法**：在 provider 描述里增加能力位（`accelerator`、`vram_bytes`、`max_context`、`supports_stream`、
  `supports_tools`），由 B-3 探测填充；选路按能力位匹配，不按 provider 名字硬编码。
- **判据**：`gate:lab` —— 给定三组能力位组合，选路结果符合预期；未知能力位必须走「保守可用」而非崩溃。
- **回退**：能力位全部可缺省；缺省时退化为「按名字选路」的旧行为。
- **规模**：约 200 行。

### B-2 后端接入（按 B-0 结论落实际后端）

- **做法**：
  - R1：接 vLLM 的 OpenAI 兼容面（`/v1/chat/completions`、`/v1/models`、`/health`）；
  - R2：接实际加速后端（如 llama.cpp SYCL / CUDA 构建），复用同一条 OpenAI 兼容适配器；
  - R3：不实现后端，只保留适配器骨架与「未配置」的可判读错误。
- **判据**：
  - `gate:runtime`（R1/R2）：一次真实对话，**响应含 `usage`**——须固定请求形态为**非流式**，
    或流式下显式带 `stream_options.include_usage=true`（`envelope.c:30-43` 已声明该选项，但
    `envelope.c:36` 注释明说 vLLM/llama.cpp **默认不回传 usage**，不固定请求形态此判据不可判）；
    且**进程确实占用 GPU**：主判据为「**目标 PID 稳态 GPU 占用 > 0**」
    （`nvidia-smi --query-compute-apps=pid,used_memory` / `rocm-smi --showpids` / Intel `xpu-smi`），
    辅以「后端启动日志声明 device=CUDA/ROCm/SYCL」。
    **不得以「请求前后显存增量 > 0」作唯一判据**——模型启动即预加载，请求前后增量恒为 0；
    Intel iGPU 为共享内存、无独立显存；其他进程会污染总量。
  - `gate:runtime`（R3）：请求返回明确「后端未配置」错误码，且**在 5s 内返回**。
    原表述「不超时 30s 以上」歧义（30s 本身是否可接受未定），改为硬上限 5s。
- **回退**：后端接入必须是**可拔插**的——关掉 GPU provider，CPU 自托管路径行为不变（B-7 验证）。
- **规模**：约 300 行。

### B-3 `doctor` 探测与降级选路

- **做法**：在 **A-6 改造后的 `airymaxrt doctor`** 上增加 GPU 段（**不是新建第二个 doctor**）：
  加速器类型、驱动版本、可用内存、可用后端列表、当前选中的 provider、不可用原因；
  选路顺序 = 显式配置 > 能力匹配 > 远端 API > CPU 自托管；每次降级必须打印**降级原因**。
- **判据**：`gate:runtime` 三场景——有 GPU、无 GPU、GPU 存在但驱动不可用，doctor 三种结论互不相同且均可执行。
- **回退**：doctor 只读；选路顺序可被显式配置覆盖。
- **规模**：约 150 行。

### B-4 多 provider 生产化（选路 / 熔断 / 降级 / 错误码透传）

- **现象**：多 provider 并存时没有统一下沉策略；错误码语义在适配层被反转（与 C-2 同源）。
- **做法**：在 provider 层统一实现——首选/备选选路、失败计数与熔断（接 C-3 的 GRAD 预算）、
  降级链（GPU → CPU → 远端）、错误码原样透传到上层与 CLI。
- **判据**：`gate:runtime` 注入故障（后端 500 / 超时 / 空响应），断言：熔断在 N 次内触发、
  降级到下一 provider、上层拿到可判读错误码；**不得**出现「上层 success 但实际无输出」。
- **回退**：熔断阈值可配置为「不触发」，回到单 provider 行为。
- **规模**：约 280 行。

### B-5 验收分档 L0 / L1 / L2（诚实分级）

| 档 | 含义 | 判据 | 允许出现在发行说明的措辞 |
|---|---|---|---|
| L0 | 抽象层 + 探测 + 降级可用 | B-1/B-3 判据全绿 | 「具备 GPU 探测与降级能力，未交付 GPU 推理」 |
| L1 | GPU 后端可完成单次对话 | B-2 判据（per-PID 稳态 GPU 占用 > 0 + 后端声明 device + `usage`） | 「支持 <实际后端名> 推理」 |
| L2 | 多 provider + 熔断 + 长跑稳定 | B-2 + B-4 + C-7 长压测 | 「GPU 服务生产可用」 |

**铁律**：无 GPU 硬件的环境**必须显式 SKIP 并带原因**，SKIP **不得**计为 PASS；
CI 报告中 SKIP 与 PASS 必须分列统计。

### B-6 不做项（写进方案，避免反复拉扯）

跨进程 binder、跨族 MTP、iGPU 换内核、分布式推理、多卡张量并行、模型量化自研、GPU 显存复用池——
本版均不做。理由：任一项都会把 0.1.21 从「可用」拖成「不可验收」。

### B-7 非 GPU 路径不减配

- **判据**：`gate:ci` + `gate:runtime` —— 关闭 GPU provider 后，0.1.20 的全部 CPU 自托管用例
  （T-1~T-8 已闭部分）逐条复跑仍绿；九平台产物构建不受影响。
- **意义**：GPU 是新能力，**不允许**以「加了 GPU」为由削减原有 CPU 路径。

## 5. 任务面 C：推理链与执行语义

> 这一面的共同点：**系统会「假装成功」**。返回码是 0，上层记 success，用户看到空内容或旧内容。
> 这是比崩溃更危险的一类缺陷，因为它在指标上表现为「健康」。

### C-1 自托管缺陷台账逐条闭环

- **现象**：llama.cpp 自托管存在十项生产级缺陷（memory L67），r128 起整改，结项时仍有未闭环项。
- **做法**：**开工首日重读台账逐条建表**（缺陷 / 复现命令 / 现状 / 判据 / 结论），
  禁止凭记忆施工；已闭项逐条复跑并留证据，未闭项按下表归类处理：
  进程管理（僵尸/孤儿/fd 泄漏）→ 启动就绪判据 → 超时与重试 → 资源回收 → 并发安全 → 日志可判读。
- **判据**：台账中每一行都有「复现命令 + 结论 + 证据路径」；**不允许**留「已知问题不处理」的空行，
  确不处理的必须写明理由并进 §12。
- **回退**：逐项独立可回退；台账本身随提交维护。
- **规模**：约 300 行（含复跑脚本）。

### C-2 执行层失败语义（真实缺陷：`success` 字段语义反转）

- **现象**：审批拒绝的工具调用被上层记成成功——字段名叫 `success`，实际语义是错误码（0 才表示成功）。
- **证据**：原 memory L70「`engine_process` 吞错返回 0、`dispatch` 无返回值」已被代码**证伪**：
  1. `atoms/coreloopthree/src/cognition/think/engine_process.c:258-337` 错误路径 **`return err`** 并
     `stats_failure_count++`，且已有 `partial` 语义与 `status:"partial"`；
  2. `dispatch` 返回 `airy_err_t`（`cognition.h:206`），不是无返回值；
  3. **真实缺陷**在工具适配器与派发判定：
     `atoms/coreloopthree/src/adapter/tool_svc_adapter.c:435` 在审批拒绝
     （`AIRY_ERR_PERMISSION_DENIED`、`exit_code=1`）时仍设 `(*out_result)->success = 1`；
     而 `engine_dispatch.c:240` 以 `tool_err == 0 && result->success == 0` 判成功——
     两处对 `success` 的理解**恰好相反**，结果是拒绝被当成功。
- **根因**：结果结构体的 `success` 字段命名与语义漂移（名为布尔、实为错误码），写入方与读取方
  各自按自己的理解赋值/解读，无类型约束，也没有覆盖「审批拒绝」路径的用例。
- **做法**：
  1. 结果结构体改为显式两字段：`err_code`（`airy_err_t`，0=成功）与只读派生 `ok`（`err_code == 0`）；
     删除 `success` 字段，让旧读写点在**编译期**全部暴露；
  2. `tool_svc_adapter.c:435` 按 `err_code` 赋值，审批拒绝必须是 `AIRY_ERR_PERMISSION_DENIED`；
  3. 派发判定统一为 `err_code == 0 && result->ok`；
  4. 上层 success 判定改为「`ok` 且产出非空」；`partial` 单独一档，**不得**折算为成功。
- **判据**：`gate:lab` 注入 6 类失败（进程退出非 0 / 超时 / 空输出 / 部分输出 / 协议错 / **审批拒绝**），
  断言上层**全部判失败**且错误码可区分；审批拒绝必须有独立用例（当前会被判成功）；
  `gate:runtime` 用真实后端复现至少 2 类。
- **回退**：`err_code` 与派生 `ok` 并存一个版本，旧路径读 `ok`；`success` 字段不留别名。
- **规模**：约 320 行（含全树 `success` 读写点迁移与拒绝路径用例）。

### C-3 熔断 / 超时 / token 预算接入 GRAD

- **现象**：熔断在 **provider 层没有接线**；超时与 token 预算未进 GRAD。
- **证据**：原 memory L69「熔断不可达」只对 provider 层成立，对 orchestrator/heapstore **已被证伪**：
  1. `atoms/coreloopthree/src/orchestrator/orchestrator.c:176` 调 `cb_allow_request`，
     `:110-121` 有 `cb_record_timeout/success/failure`，`:195` 有 `enable_circuit_breaker`；
     `heapstore/tests/test_heapstore_circuit.c:98` 断言 trips ≥ +1——**存量单测已能触发熔断**；
  2. `atoms/coreloopthree/src/governance/governance.c:120-160` 已有 `circuit_breaks` 计数，token 预算耗尽时递增；
  3. 真实缺口：`daemons/providers/` 全树 **零 `cb_` 引用**（只有 `retry_class`），
     「连续后端失败 → 熔断」这条链在 provider 层不存在。
- **根因**：熔断设施在 coreloopthree 内部完成，provider 作为独立 daemon 没有复用同一设施、
  也没有上报失败计数——「有熔断器，但没给它喂信号」。
- **做法**：
  1. provider 层接入同一套 `cb_*`（或经 IPC 上报失败计数给 orchestrator），失败/成功/超时三类事件必报；
  2. 「失败计数 / 冷却窗口 / 预算余量」作为 GRAD 判定输入；熔断触发后必须**降级或快速失败**；
  3. 预算耗尽与熔断共用 `circuit_breaks` 口径，避免两套计数器。
- **判据**：
  - `gate:lab`：**在 provider 层**注入连续 N 次失败，断言第 N+1 次**必然**走熔断分支（计数器断言，
    且必须断言 `daemons/providers` 路径上的计数变化——**不得**复用 orchestrator/heapstore 的存量用例冒充）。
  - `gate:runtime`：真实后端断网 30s 内快速失败，不堆积请求。
- **回退**：阈值配置化，可置为无穷（关闭）。
- **规模**：约 260 行（provider 侧接线 + 注入用例）。

### C-4 双思考 B 侧读正文 + schema + 黄金集

- **现象**：双思考结构下 B 侧未读正文，判据有漏洞（memory L68）。
- **做法**：B 侧读取正文而非只读结构字段；输出加 schema 校验（字段存在性 + 类型 + 非空）；
  建黄金集（固定输入 → 期望结构 + 关键断言），回归时逐条比对。
- **判据**：`gate:lab` 黄金集全绿；故意破坏 schema 的样本必须判红；`gate:runtime` 至少 1 次真实双思考链路。
- **回退**：schema 校验可分级（warn / fail），缺省 fail。
- **规模**：约 260 行。

### C-5 端云混合 `null content` 判定 + 断路器

- **现象**：`null content` 未被判定为失败，链路继续并按成功计。
- **做法**：`content == null` 或 `content == ""` 一律判失败并记明确错误码；连续失败接 C-3 断路器；
  端云切换必须打印切换原因。
- **判据**：`gate:lab` 构造 `null` / 空串 / 只有 `reasoning` 无 `content` 三种响应，全部判失败；
  `gate:runtime` 断网后端云切换成功且有原因日志。
- **回退**：断路器阈值可关；`null` 判定不可关（这是缺陷本身）。
- **规模**：约 160 行。

### C-6 T-1 ~ T-8 自托管运行态项

| 编号 | 场景 | 判据要点 |
|---|---|---|
| T-1 | 首次拉模 | 有进度、可中断、可续、失败可重试 |
| T-2 | 断网 | 明确错误而非挂起 |
| T-3 | 模型缺失 | 引导到下载命令，不崩 |
| T-4 | 并发请求 | 并发 N 无串话、无 fd 泄漏 |
| T-5 | 内存/显存不足 | 明确 OOM 语义，进程不进入未知状态 |
| T-6 | OOM 后恢复 | 可重启并恢复服务 |
| T-7 | 重启恢复 | 配置与会话不丢 |
| T-8 | 日志可判读 | 关键阶段均有结构化日志与阶段码 |

**判据**：八项各有独立 `gate:runtime` 证据；任一项缺证据则该组不算完成。

### C-7 长压测基线 + 285H 崩溃归因

- **现象**：r113 长压测无基线；`llama-server b11712` 在本机崩溃仅记录未归因。
- **做法**：
  1. 建立可复跑长压测（时长、并发、请求分布、判定阈值全部固化到脚本），产出基线报告（P50/P95/P99、
     失败率、内存/显存曲线、fd 数）；
  2. 崩溃归因：采集 core / 退出码 / 最后 200 行日志，最小复现，给出「已修 / 有绕行 / 上游问题」三选一结论。
- **判据**：`gate:ci` 短压测（如 5min）进流水线；`gate:runtime` 长压测（≥30min）有报告且阈值达标；
  崩溃归因有三选一结论并附证据。
- **回退**：长压测不进发版阻断，只作 L2 档（B-5）前提。
- **规模**：约 220 行。

## 6. 任务面 D：可观测与 CLI 一致性

> 这一面的共同点：**面板有数字，但数字没有意义**（全等、恒定、空）。用户看到的「健康」是假健康。

### D-1 TUI 自托管专页

- **做法**：TUI 增加自托管专页：模型、后端、显存占用、并发、队列深度、失败率、最近错误；
  数据来自真实采集接口，**禁止**用常量占位。
- **判据**：`gate:runtime` 页面数据与 `doctor`/日志同源一致；断开后端后面板显示降级而非旧值。
- **规模**：约 250 行。

### D-2 密钥装配引导

- **做法**：`agentrt key`（或等价子命令）引导式装配：选 provider → 填 key → 写入正确位置 → 立即连通性验证 →
  失败给出原因。与 A-7 的引导文案同源。
- **判据**：`gate:runtime` 空环境 → 引导 → 连通成功一条龙；中途取消不留半成品。
- **规模**：约 180 行。

### D-3 per-family 校准

- **现象**：校准结果 ratio 全等 `0.636…`、`confidence` 恒 `0.5`、`provider` 为空——等于没校准。
- **根因**：校准输入未按 family 分组，或分组后仍用全局值填充。
- **做法**：按 family 分别统计样本量与比例；样本不足的 family 显式标「样本不足（N<阈值）」而**不是**填默认值；
  `provider` 字段必须回填真实来源。
- **判据**：`gate:lab` 构造三组不同 family 的样本，输出 ratio 互不相同且与期望一致；
  样本不足组输出「不足」而非 `0.5`。
- **规模**：约 200 行。

### D-4 大厅与语义缓存空态

- **现象**：`entries=0` / `hits=0` / `hit_rate=-1` 长期不动。
- **做法**：区分三种状态——「未启用」「已启用无数据」「已启用有数据」；`hit_rate=-1` 只在「未启用」时出现；
  启用后若长期 0 命中，doctor 给出「缓存未生效」告警。
- **判据**：`gate:runtime` 三状态各一次截图/接口证据；启用后写入+读取能产生非零命中。
- **规模**：约 150 行。

### D-5 嵌套 JSON 键扫描

- **现象**：取字段时按「全串首次出现 `"key"` + 冒号」匹配，嵌套/同名键会取错。
- **证据**：`atoms/coreloopthree/src/orchestrator/orchestrator_phase_llm.c:382-383` 调用
  `extract_bool_from_json` / `extract_field_string`；底层 `commons/utils/string/json_key.h:30-57`
  的注释自述是「非完整解析器」，实现为无层级扫描。
- **做法**：新增 **带 out 参数与错误码**的 API——`json_key_find(path, out_ptr, out_len)`、
  `json_key_find_bool(path, out_bool)`，支持 `a.b[0].c` 路径，命中 0 次与命中多次返回**可区分**错误。
  不能沿用现有 `json_key.h:30-57`：它返回首个匹配的 `const char*`、无错误出口，且非冒号分支直接 `p++`
  继续扫描，会把**字符串值内的 `"key":`** 误当键，无法在其上补层级判断。
  **不保留**「调用点传唯一键路径」的过渡方案——它解决不了上述内嵌误匹配。
- **判据**：`gate:lab` 三样本——同名键嵌套（取到正确层）、字符串值内嵌 `"key":`（取到真实字段而非内嵌串）、
  键确实不存在（返回 NOT_FOUND 而非空串）；命中多处必须报错而非取首个。
- **回退**：保留旧函数签名，内部改走新解析；旧行为可由开关恢复（仅排障）。
- **规模**：约 220 行。

### D-6 `model` 子命令（T-17 / T-18）

- **现象**：`set` 只做单键 awk 替换/追加；`remove` 直接 `rm -f` 且无确认、无 dry-run。
- **证据**：`tools/scripts/ops/bin/airy-local:616` 调 `airy_config_set "$registry" "active_model"`；
  setter `tools/scripts/ops/lib/common.sh:309-323`；`airy-local:659-685` 的 remove 直接 `rm -f` + 6 次
  `airy_config_del`；`common.sh:343` 有 `airy_confirm` 但**未被调用**。
- **做法**：`agentrt model list/use/remove`；`use` 校验模型存在并原子写；`remove` 必须走
  `airy_confirm` + `--dry-run` + 引用检查（被引用则拒绝或要求 `--force`）。
- **判据**：`gate:lab` 三件事——dry-run 不产生变更、未确认不删除、被引用时拒绝；
  `gate:runtime` 完整 use→verify→remove 链路。
- **规模**：约 250 行。

### D-7 T-14 / T-19 / T-20 运行态复验 + Q19 成功率四元组实测

- **现象**：Q19「成功率四元组」**成文未实测**（0.1.20 §11）。
- **做法**：四元组（请求数 / 成功数 / 失败数 / 超时数）落为可采集指标，并要求分母非零；
  同时复验 T-14/T-19/T-20 的运行态结论，逐条给证据。
- **判据**：`gate:runtime` 报告含四元组且 `成功+失败+超时 == 请求数`（自洽）；连续两次采集差值可解释。
- **规模**：约 200 行。

## 7. 任务面 L：账本与工程质量

> 本面不产出功能，只产出**可信度**。它决定下个版本还能不能判断「改动是变好还是变坏」。

### L-1 BK-2：`cupolas` 增量溯源（现行 pin 已是 17,560）

- **现象**：0.1.20 §7.5.1 记 `cupolas` 17,314→17,342（+28）缺 `RATCHET-JUSTIFY`；
  **但现行 pin 已不是 17,314**——`tools/scripts/ci/quality/v16-loc-budget-baseline.txt:259-261` 实为
  `core=79185 / facade=65878 / cupolas=17560`；本轮实跑 `g42-ledger-consistency.sh` **rc=0，
  输出「三表对齐，差异 0」**。
- **证据**：原文「回到 17,314」的依据已过期；按该要求施工会**破坏当前三表对齐**并让 g42 变红。
  真实待办只剩「17,342→17,560 的增量是否有成文理由」，不是「回退」。
- **做法**：只做溯源与登记——在账本补 `RATCHET-JUSTIFY`，说明 17,342→17,560 由哪些任务/提交引入，
  逐条给出 commit 或任务编号。**不执行任何行数回退**。
- **判据**：`gate:ci` g41 `ratchet audit clean` **且 g42 rc=0**；账本中 17,560 有可读理由链
  （每个增量点名到 commit/任务），且无一条「保留 + 不解释」。
- **回退**：本条不删代码，无代码回退；若溯源发现无主增量，单独立项处理，不在本条内顺手删。
- **规模**：约 60 行（多为账本记录与溯源）。

### L-2 度量棘轮：`WARN 276` 可解释基数

- **现象**：`FAIL 0 / BLOCK 0 / WARN 276`、`rc=2`；最高 CCN 25 共 11 个函数；平均 CCN<2.5 未达标。
- **证据**：r148 实测；`275→276` 的唯一增量来自 r141 的 `merge_mapping_into` 由 15 升至 16
  （哨兵槽判据 `cap <= tgt+src` 与容量回传两处分支），是越界崩溃整改的必要代价。
- **做法**：
  1. 建立 `WARN` 基数台账：每个 **CCN 16–25** 的函数登记「为何不能拆 / 计划何时拆」；
  2. 门禁改为「**WARN 总数 ≤ 276 且不得新增 CCN>25**」（只减不增）；
  3. 拆分目标改为「**一次拆到 ≤15 才算消除**」——`thresholds.conf:18-20` 的 `CCN_FN_PASS=15` 才是过线，
     把 25 拆成两个 18 会让 WARN **+1**，因此拆分项若未降到 15 以下，不计入成果；
  4. 「平均 CCN<2.5」目前**没有对应门禁项**（`complexity-check.sh` 只做逐函数分档），
     本条不承诺该指标；若要纳入，须先新增度量脚本并单独立项。
- **判据**：`gate:ci` WARN 数 ≤ 276、无 CCN>25，且本轮每个拆分项在报告中 CCN ≤15（否则视为未完成）；
  台账每行有记录。
- **回退**：基数只减不增，回退即恢复旧阈值（不允许放宽）。
- **规模**：约 190 行（含拆分到 15 以下的额外工作量）。

### L-3 T8 / P2-6 三档基线实测（0.15K 档）
