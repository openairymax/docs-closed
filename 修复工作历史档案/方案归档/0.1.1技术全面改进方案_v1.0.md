> **版本**: v1.0 | **日期**: 2026-06-10 | **状态**: 方案制定
> **定位**: 本文档是 AgentOS v0.1.0 → v0.1.1 的全面技术改进方案。在 v0.1.0 代码质量加固（Phase 1 100%完成）的基础上，吸收 6 个参考项目的成熟工程实践，将 AgentOS 从"实验室顶级工程"推向"行业底层可投产平台"。

> **配套文档**: [0.1.0技术加强方案.md](0.1.0技术加强方案.md) v5.0 | [工程规范化标准手册09.md](工程规范化标准手册09.md) v20.0 | [TERMINOLOGY.md](../Docs/TERMINOLOGY.md) v3.0

## 第二章：核心设计决策

### 2.1 决策一：C 核心 + Rust/Python 生态扩展

```
┌─────────────────────────────────────────────────────┐
│              生态扩展层（不改核心代码）                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Python   │  │  Rust    │  │ TypeScript│          │
│  │ 插件 SDK │  │ 插件 SDK │  │  工具链   │          │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘           │
│       │              │              │                │
│  ┌────┴──────────────┴──────────────┴─────┐          │
│  │         Plugin Bridge (C FFI)          │          │
│  └────────────────────┬───────────────────┘          │
├───────────────────────┼───────────────────────────────┤
│               C 核心层（性能关键路径）                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ CoreKern │  │CoreLoop3 │  │MemoryRovol│          │
│  │ 微内核   │  │ 三循环   │  │ 四层记忆  │          │
│  └──────────┘  └──────────┘  └──────────┘           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Cupolas  │  │ TaskFlow │  │ HeapStore│           │
│  │ 安全穹顶 │  │ 图计算   │  │ 数据分区 │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│  ┌──────────┐  ┌──────────┐                         │
│  │ 10 Daemon│  │ Gateway  │                         │
│  │ 守护进程 │  │  网关    │                         │
│  └──────────┘  └──────────┘                         │
└─────────────────────────────────────────────────────┘
```

**原则**：

| 层 | 语言 | 理由 |
|----|------|------|
| CoreKern / MemoryRovol / Cupolas / TaskFlow | **C** | 性能关键路径、内存精确控制、零 GC 暂停 |
| Plugin SDK Bridge | **C FFI** | 提供 C→Rust/Python 的稳定 ABI |
| Plugin 运行时 | **Rust** | 内存安全 + 高性能 + 丰富生态 |
| CLI / 脚手架 / TUI | **Rust** | 单二进制分发、启动快、跨平台 |
| AI Agent 插件 / Prompt 模板 | **Python** | AI 生态最成熟、团队最熟悉 |
| Desktop (已有) | **TypeScript** | 保持现有 Electron 技术栈 |

### 2.2 决策二：声明式配置 — 一个 YAML 文件控制全系统

**现状问题**：配置散落在 5+ 个头文件中：
- `memoryrovol/include/config.h` — MemoryRovol 配置
- `cupolas/cupolas_config.c` — Cupolas 配置
- `daemon/llm_d/` 自有配置
- `daemon/gateway_d/` 自有配置
- `atoms/corekern/` 编译时常量

**目标方案**：一个 `agentos.yaml` 文件：

2. 各子系统通过 `agentos_config_t *config` 统一入口读取配置
3. 环境变量覆盖：`AGENTOS_LLM_PROVIDERS_OPENAI_API_KEY` 可覆盖 YAML 中的对应路径
4. 配置热重载：`agentos config reload` 命令无停机更新配置

### 2.3 决策三：统一 LLM 接入 — 30 秒接入新模型，无厂商锁定

**现状**：9 种协议类型（MCP/A2A/OpenAI/Claude/OpenJiuwen/OpenClaw/ChinaEco/AGNTCY/LangChain/AutoGen），但接入新模型的路径深（protocols → integrations → daemon）。

**目标**：任何 OpenAI-compatible API 的模型，只需在 `agentos.yaml` 中加 3 行配置即可接入：

```yaml
llm:
  providers:
    my_new_model:
      type: "openai-compatible"         # 标准协议类型
      base_url: "https://my-model-api.example.com/v1"
      api_key_env: "MY_API_KEY"
```

**实现架构**：

```
agentos.yaml (声明式注册)
        │
        ▼
llm_d config hot-reload
        │
        ▼
provider registry (动态注册)
        │
        ├── OpenAI-compatible  →  /v1/chat/completions  (覆盖 90% 的模型)
        ├── Anthropic          →  /v1/messages
        ├── Ollama             →  /api/generate
        └── Custom Provider    →  plugin SDK 自定义适配器
```

**Provider 插件化**：对于非标准协议的 Provider，通过 Rust/Python Plugin SDK 实现自定义适配器（见第四章插件系统设计）。

## 第三章：插件系统设计

### 3.1 设计目标

1. **不改 C 核心代码就能扩展 AgentOS**
2. 支持三种插件类型：Provider（LLM提供商）、Tool（工具）、Hook（生命周期钩子）
3. 插件可使用 **Rust** 或 **Python** 编写
4. 参考 openclaw 2519 行的 `loader.ts` 和 claude-code 的四合一插件模型

### 3.2 插件模型

```
Plugin = Manifest + Type + Implementation

PluginManifest (plugin.yaml):
  name: "my-custom-tool"
  version: "1.0.0"
  type: "tool"                   # tool | provider | hook | skill
  language: "rust"               # rust | python
  description: "A custom tool for weather queries"
  author: "community"
  dependencies: []
  entrypoint:
    rust: "target/release/libmy_plugin.so"
    python: "plugin.py"
  hooks:                         # 插件可以声明自己监听的Hook
    - on_tool_call
    - on_agent_start
  permissions:                   # 插件需要的权限
    - network:api.weather.com
    - filesystem:read:/tmp
  config_schema:                 # 插件的配置Schema
    api_key:
      type: string
      env: "WEATHER_API_KEY"
```

### 3.3 插件类型详解

#### Provider 插件

用于接入非标准协议的 LLM 提供商：

```rust
// Rust Provider Plugin
use agentos_plugin_sdk::prelude::*;

#[derive(AgentOSProvider)]
#[provider(name = "my-custom-llm")]
pub struct CustomProvider {
    config: ProviderConfig,
}

impl LlmProvider for CustomProvider {
    fn chat(&self, request: ChatRequest) -> Result<ChatResponse, PluginError> { ... }
    fn stream(&self, request: ChatRequest) -> Result<StreamHandle, PluginError> { ... }
    fn token_count(&self, text: &str) -> Result<u32, PluginError> { ... }
    fn list_models(&self) -> Vec<ModelInfo> { ... }
}
```

#### Tool 插件

用于扩展 Agent 的工具能力：

```python
# Python Tool Plugin
from agentos_plugin_sdk import ToolPlugin, tool

class WeatherPlugin(ToolPlugin):
    name = "weather"
    version = "1.0.0"
    
    @tool(description="Get current weather for a city")
    def get_weather(self, city: str, units: str = "metric") -> dict:
        # 实现天气查询
        return {"city": city, "temperature": 22.5, "condition": "sunny"}
```

#### Hook 插件

在 Agent 生命周期关键节点注入自定义逻辑：

```python
from agentos_plugin_sdk import HookPlugin, on_event

class AuditHook(HookPlugin):
    
    @on_event("on_tool_call")
    def audit_tool_call(self, event: ToolCallEvent):
        # 记录所有工具调用到审计日志
        logger.audit(f"Tool called: {event.tool_name} by {event.agent_id}")
    
    @on_event("on_memory_write")
    def audit_memory_write(self, event: MemoryWriteEvent):
        logger.audit(f"Memory written: {event.record_id} layer={event.layer}")
```

#### Skill 插件

参考 claude-code 的 SKILL.md 格式，定义可复用的 Agent 技能：

```markdown
# skill: code-review
# type: agent-skill

## 行为
当用户请求代码审查时，Agent 会：
1. 分析代码变更（diff）
2. 检查代码质量（参考 BAN 规则）
3. 检查安全漏洞
4. 输出结构化审查报告

## 输入
- code_diff: string（git diff 输出）
- file_type: string（文件类型）

## 输出
- review_report: {severity, findings[], suggestions[]}

## 使用的工具
- agentos_tool_read_file
- agentos_tool_run_linter
- agentos_tool_security_scan
```

### 3.4 插件生命周期

```
Discovery → Load → Validate → Activate → [Run] → Deactivate → Unload

1. Discovery: agentos 启动时扫描 plugin_dirs
2. Load: 读取 plugin.yaml manifest
3. Validate: 检查权限、依赖、兼容性
4. Activate: 注册到对应的 registry（provider_registry / tool_registry / hook_registry）
5. Run: 插件在 Agent 运行时被调用
6. Deactivate: 热卸载或关闭时注销
7. Unload: 释放资源
```

### 4.4 Hook 实现模式

**模式一：Shell Hook**（参考 atomcode）

最简单的方式——一个可执行脚本：

```bash
#!/bin/bash
# hooks.d/security_audit.sh
# 接收 JSON 事件 via stdin
EVENT=$(cat)
TOOL_NAME=$(echo "$EVENT" | jq -r '.tool_name')
AGENT_ID=$(echo "$EVENT" | jq -r '.agent_id')
TIMESTAMP=$(echo "$EVENT" | jq -r '.timestamp')

echo "[AUDIT] $TIMESTAMP | $AGENT_ID called $TOOL_NAME" >> /var/log/agentos/tool_audit.log
exit 0  # 返回非0可中断流程
```

**模式二：Python Hook**

```python
# hooks.d/security_audit.py
from agentos_hook_sdk import hook

@hook("on_tool_call", priority=100)
def security_audit(event):
    if event.tool_name in BANNED_TOOLS:
        return {"allow": False, "reason": f"Tool {event.tool_name} is banned"}
    logger.audit(f"{event.agent_id} called {event.tool_name}")
    return {"allow": True}
```

**模式三：Webhook**（参考 openclaw）

```yaml
hooks:
  webhooks:
    on_memory_write:
      url: "https://my-service.example.com/agentos/memory-events"
      secret_env: "WEBHOOK_SECRET"
      retry: 3
```

```yaml
name: "extract_facts"
version: "1.0.0"
description: "从对话中提取原子事实（7规则）"
model_family: "any"
temperature: 0.3
max_tokens: 2000

system: |
  You are a fact extraction system. Extract atomic facts from the conversation.
  
  Follow these 7 rules:
  1. **Atomicity**: Each fact MUST be a single, indivisible piece of information.
  2. **Third-person**: Always use third-person perspective. "The user" not "I".
  3. **Context-rich**: Include all necessary context so the fact is self-contained.
  4. **Noise filtering**: Ignore greetings, small talk, and repeated information.
  5. **Strict JSON**: Output ONLY valid JSON array. No markdown, no commentary.
  6. **Categorize**: Assign one of [personal, work, preference, technical, project, decision].
  7. **Empty result**: If no new facts, return empty array [].

user_template: |
  Extract atomic facts from this conversation:
  
  {conversation_text}

output_schema:
  type: array
  items:
    type: object
    properties:
      title:
        type: string
        description: "Brief title summarizing the fact"
      summary:
        type: string
        description: "One-sentence summary with full context"
      content:
        type: string
        description: "Detailed fact content with all available details"
      category:
        type: string
        enum: ["personal", "work", "preference", "technical", "project", "decision"]
      tags:
        type: array
        items:
          type: string

examples:
  - input: "My name is Alice and I work at Acme Corp as a data engineer."
    output:
      - title: "User Name"
        summary: "The user's name is Alice."
        content: "The user introduced herself as Alice."
        category: "personal"
        tags: ["identity", "name"]
      - title: "User Employment"
        summary: "The user works at Acme Corp as a data engineer."
        content: "The user works at Acme Corp in the role of data engineer."
        category: "work"
        tags: ["employment", "company", "role"]

metrics:                         # 调优指标（用于 A/B 测试）
  target_precision: 0.90
  target_recall: 0.85
  max_hallucination_rate: 0.02
```

### 9.2 Docker 化

```dockerfile
# Dockerfile.agentos — 单容器部署
FROM ubuntu:24.04

RUN apt-get update && apt-get install -y \
    build-essential cmake libyaml-dev libcurl4-openssl-dev \
    libsqlite3-dev libzstd-dev python3 python3-pip rustc cargo

COPY . /opt/agentos
WORKDIR /opt/agentos
RUN mkdir build && cd build && cmake .. && make -j$(nproc)

EXPOSE 8080 9090

CMD ["./build/agentos", "run", "--config", "/etc/agentos/agentos.yaml"]
```

```yaml
services:
```

## 第十一章：风险与应对

| 风险 | 可能性 | 影响 | 应对策略 |
|------|--------|------|---------|
| C FFI Bridge 稳定性不足 | 中 | 高 | 先用 Rust FFI 验证，Python 通过 Rust 桥接 |

| Prompt 模板维护成本高 | 高 | 低 | 版本化管理 + 自动化调优降低人力成本 |
| Multi-Agent A2A 性能瓶颈 | 低 | 中 | IPC 共享内存通信，P50 < 6μs 已有的 CoreKern IPC 作为基础 |
| CLI 功能膨胀 | 中 | 低 | 插件可注册自己的 CLI 子命令，核心 CLI 保持精简 |
