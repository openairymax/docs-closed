## 第一章：关键决策与设计原则

### 1.1 五大关键决策（不可动摇）

| # | 决策 | 内涵 |
|---|------|------|
| **决策一** | `AgentOS/` → **AgentRT**；`agentos/` 不变 | 外层目录更名为 AgentRT（Agent Runtime Platform），内层 `agentos/` 作为"智能体原生操作系统"品牌名保留。项目独有命名体系全数保留 |
| **决策二** | **分离生态层、整合 SDK、移动部署配置** | C 核心与 Python 生态明确分层；四语言 SDK 整合为 `sdk/`；部署配置独立为 `deploy/` |
| **决策三** | **先整合已有资产，再新建缺失能力** | Manager/OpenLab/toolkit/deploy 均已有成熟实现，先完成整合连接，再补齐缺失 |
| **决策四** | **commons 是统一基础库，不可随意变动** | `agentos/commons/` 的目录结构、文档、代码均需保持稳定，不删除任何目录 |
| **决策五** | **MemoryRovol 独立成库** | 商业化核心，独立开发/构建/发布/计费，`agentos/atoms/memoryrovol/` 仅保留桥接层 |

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **命名美学优先** | Atoms/CoreKern/CoreLoopThree/Cupolas/TaskFlow/HeapStore/MemoryRovol 不可修改。参考项目技术融入时必须重新命名 |
| **C 核心不动摇** | C 语言边界 = { Agent 运行时执行引擎 } ∪ { 关键基础设施 } ∪ { FFI Bridge } |
| **生态层用最适合的语言** | Manager/OpenLab 保持 Python；CLI/TUI 用 Rust；Prompt 用 YAML；Plugin SDK 支持 Rust/Python |
| **Provider 模式** | 可拔插架构贯穿始终：MemoryRovol 提供商、LLM 提供商、插件提供商 |
| **零抄袭风险** | 所有融入技术必须重新命名和重新设计接口 |
| **生产级优先** | 每一项能力都必须达到"可投产"标准，不接受"原型级"交付 |

## 第四章：生态层分离与统一配置中心

### 4.1 分离逻辑

```
C 核心层 (agentos/)                    生态层 (ecosystem/)
─────────────────────────              ─────────────────────
• 性能关键路径                          • 配置管理与校验
• 内存精确控制                          • Agent 市场与应用分发
• 系统调用与安全边界                     • Prompt 模板管理
• 确定性调度                            • Hook/Plugin/Skill 脚本
• 编译为静态库/可执行文件                • Python 包 / pip 安装
• 语言：纯 C                            • 语言：Python / YAML
```

### 4.2 Manager 整合

**现状**：`agentos/manager/` — 11 JSON Schema + 三层配置覆盖 + 热重载 + 审计日志 + 漂移检测

**整合操作**：移至 `ecosystem/manager/`，保持所有功能不变。

**Manager 已有资产**：

| 资产 | 功能 |
|------|------|
| `schema/` (11 个 JSON Schema) | 272 项校验规则 |
| `kernel/` | 内核参数管理 |
| `model/` | LLM Provider 声明 |
| `security/` | 安全策略配置 |
| `environment/` | 多环境配置（dev/staging/prod） |
| `agent/` | Agent 元数据注册 |
| `skill/` | Skill 元数据注册 |
| `monitoring/` | Prometheus + Grafana |
| `audit/` | 结构化审计日志 |
| `tools/` | 配置 diff、漂移检测 |

### 4.3 OpenLab 整合

**现状**：`agentos/openlab/` — Agent 市场 + 应用框架 + 社区贡献

**整合操作**：移至 `ecosystem/openlab/`，保持所有功能不变。

#### 5.3.3 Prompt 调优框架（完整设计）

参考 openJiuwen 的 `dev_tools/tune/base.py`（Case/EvaluatedCase 模型），设计完整的 Prompt 调优工具链：

```python
# ecosystem/prompts/tuner/evaluate.py

class PromptCase:
    """单个评测用例"""
    input: str                    # 输入文本
    expected_output: dict         # 期望输出结构
    category: str                 # 用例分类
    difficulty: str               # easy/medium/hard

class EvaluatedCase(PromptCase):
    """评测后的用例（含结果）"""
    actual_output: dict           # 实际输出
    precision: float              # 精确率
    recall: float                 # 召回率
    hallucination: bool           # 是否幻觉
    latency_ms: int               # 延迟

class PromptEvaluator:
    """Prompt 评测引擎"""
    def evaluate(self, prompt_name, version, dataset_path) -> EvaluationReport
    def ab_test(self, prompt_name, baseline_version, candidate_version) -> ABTestReport
    def score(self, prompt_name, version, metrics) -> ScoreReport
```

## 第七章：LLM 智能路由与网关增强

### 7.1 成本感知路由（hermes-agent 核心资产）

参考 hermes-agent 的智能模型路由，在 `llm_d/router/` 中实现：

```c
// daemon/llm_d/router/cost_aware_router.h

typedef enum {
    AGENTOS_ROUTE_COST_AWARE,       // 成本优先（默认）
    AGENTOS_ROUTE_ROUND_ROBIN,      // 轮询
    AGENTOS_ROUTE_LEAST_LATENCY,    // 最低延迟
    AGENTOS_ROUTE_QUALITY_FIRST     // 质量优先（用最强模型）
} agentos_route_strategy_t;

typedef struct {
    agentos_route_strategy_t strategy;
    char **fallback_chain;          // 降级链 ["openai", "anthropic", "deepseek"]
    double cost_budget_daily_usd;   // 日预算
    double cost_spent_today_usd;    // 今日已花费
} agentos_router_config_t;

// 路由决策
int agentos_router_select_provider(
    agentos_router_config_t *config,
    const char *task_type,          // "chat" | "code" | "reasoning" | "embedding"
    int estimated_tokens,
    char **selected_provider,       // 输出：选中的 Provider
    char **selected_model);         // 输出：选中的模型

// 预算检查
bool agentos_router_check_budget(agentos_router_config_t *config);

// 降级处理
int agentos_router_fallback(agentos_router_config_t *config, 
                             const char *failed_provider,
                             char **fallback_provider);
```

**路由策略详解**：

| 策略 | 决策逻辑 | 适用场景 |
|------|---------|---------|
| `cost_aware` | 简单任务用便宜模型，复杂任务用强模型 | 日常使用（默认） |
| `round_robin` | 轮询所有可用 Provider | 负载均衡 |
| `least_latency` | 选择响应最快的 Provider | 实时交互 |
| `quality_first` | 始终用最强模型 | 关键决策 |

**成本感知路由的决策树**：

```
请求到达
├── 预算检查：今日花费 < 日预算？
│   ├── 否 → 使用最便宜的 Provider
│   └── 是 → 继续判断
├── 任务类型判断：
│   ├── reasoning → 使用最强模型（o3/claude-opus）
│   ├── code → 使用编码模型（gpt-4o/claude-sonnet）
│   ├── chat → 使用便宜模型（gpt-4o-mini/deepseek-chat）
│   └── embedding → 使用专用嵌入模型
├── 降级链：首选 Provider 失败？
│   └── 按 fallback_chain 顺序尝试下一个
└── 缓存检查：相似请求已有缓存？
    └── 直接返回缓存结果
```
