### 1.4 内存管理现状评估

> **背景**: AgentRT 以 C 语言为核心，内存安全是系统可靠性的地基。以下评估基于源代码审计发现。

| 模块 | 内存管理现状 | 已有机制 | 缺失能力 |
|------|------------|---------|---------|
| `atoms/corekern/` | `alloc.c` + `pool.c` + `guard.c` + `oom_handler.c` | 五级 OOM 框架、canary 守卫、双重释放检测、内存池 | per-thread 缓存层、Slab 分配器、Arena 分配器 |
| `atoms/coreloopthree/` | 通过 `AGENTOS_MALLOC/FREE` 分配 | 安全宏封装 | 请求作用域 Arena、内存增长控制 |
| `atoms/memory/` | `memory_provider.h` 可拔插提供商 | builtin/MemoryRovol 双提供商 | 提供商内存预算隔离 |
| `cupolas/` | `safety_guard.h` 资源配额 | 配额管理、审计 | 内存配额强制执行 |
| `daemon/*` | 各 daemon 独立分配 | `AGENTOS_MALLOC/FREE` | 统一 OOM 回调注册、内存泄漏检测 |
| `commons/utils/memory/` | 完整三层体系 | `memory.c` + `memory_pool.c` + `memory_debug.c` + `memory_stats_reporter.c` + `memory_prealloc.c` | per-thread 缓存、Arena 分配器 |
| `MemoryRovol/` | `memory_pool.c` + `garbage_collector.c` + `frag_monitor.c` | 引用计数、GC、碎片监控 | 各层内存预算上限、嵌入计算内存不足降级 |

**关键发现**：
1. **已有优势**：五级 OOM 框架（`oom_handler.h`）属业界前沿；canary 守卫（`guard.c`）和双重释放检测（`pool.c`）已覆盖主要安全场景
2. **主要缺口**：缺少 per-thread 分配缓存（热路径锁竞争）；缺少 Arena/Slab 分配器（高频场景碎片化）；缺少所有权模型和引用计数规范；缺少 daemon 级内存预算和泄漏检测
3. **风险点**：CoreLoopThree 长时间运行内存增长未监控；MemoryRovol 大规模嵌入计算可能超出内存预算；IPC 共享内存缺乏引用计数管理

## 第二章：关键决策与设计原则

### 2.1 五大关键决策（不可动摇）

| # | 决策 | 内涵 |
|---|------|------|
| **决策一** | `AgentOS/` → **AgentRT**；`agentos/` 不变 | 外层目录更名为 AgentRT（Agent Runtime Platform），内层 `agentos/` 作为"智能体原生操作系统"品牌名保留。项目独有命名体系全数保留 |
| **决策二** | **分离生态层、整合 SDK、移动部署配置** | C 核心与 Python 生态明确分层；四语言 SDK 整合为 `sdk/`；部署配置独立为 `deploy/` |
| **决策三** | **先连接已有资产，再补齐缺失能力** | 已有 A2A/MCP/Orchestrator/Checkpoint/SafetyGuard 等均需先完成端到端连接，再补齐 Hook/CLI/Prompt |
| **决策四** | **commons 是统一基础库，不可随意变动** | `agentos/commons/` 的目录结构、文档、现有代码均需保持稳定——不删除任何目录/文件，不修改现有接口签名。可以新增文件（如新增工具函数），但新增文件需经过严格评审，且不能引入外部依赖。 |
| **决策五** | **MemoryRovol 独立成库** | 商业化核心，独立开发/构建/发布/计费，`agentos/atoms/memoryrovol/` 仅保留桥接层 |

### 2.2 设计原则

| 原则 | 说明 |
|------|------|
| **命名美学优先** | Atoms/CoreKern/CoreLoopThree/Cupolas/TaskFlow/HeapStore/MemoryRovol 不可修改 |
| **C 核心不动摇** | C 语言边界 = { Agent 运行时执行引擎 } ∪ { 关键基础设施 } ∪ { FFI Bridge } |
| **生态层用最适合的语言** | Manager/OpenLab 保持 Python；CLI/TUI 用 Rust；Prompt 用 YAML |
| **Provider 模式** | 可拔插架构：MemoryRovol 提供商、LLM 提供商、安全守卫 |
| **零抄袭风险** | 所有融入技术必须重新命名和重新设计接口 |
| **生产级优先** | 每一项能力都必须达到"可投产"标准 |
| **连接优先于新建** | 已有资产先完成端到端连接，再新建缺失能力 |
| **合约优先** | 跨团队接口通过 `contracts/` 合约文件定义，优先于任何代码实现。合约文件是团队间唯一的接口真理来源（详见 §2.4） |
| **三权分立执行** | 团队A（核心引擎）、团队B（生态+SDK）、团队C（基础设施）24/7 并行执行。同一文件只属一个团队，交叉点通过接口合约解耦（详见 §2.5） |

### 2.4 合约优先策略（v2.6 新增）

> **核心原则**: 在执行任何代码修改前，三团队必须先就跨团队接口达成一致，以合约文件形式冻结。合约是团队间唯一的接口真理来源。

**合约文件规范**：所有跨团队接口必须通过 `contracts/` 目录下的合约文件定义：

```
contracts/
├── contract_A_B.h    # 团队A ↔ 团队B 接口合约
├── contract_A_C.h    # 团队A ↔ 团队C 接口合约
└── contract_B_C.h    # 团队B ↔ 团队C 接口合约
```

**每份合约文件必须包含**：
1. **函数签名**（精确到参数类型、const 修饰、错误码）
2. **数据结构内存布局**（`static_assert` 验证 `sizeof`）
3. **时序图约束**（消息流的先后顺序，用 Doxygen 注释描述）
4. **错误码映射表**（源错误码 → 目标错误码的完整映射）
5. **版本号**（`#define CONTRACT_A_B_VERSION 0x00010000`）

**合约验证**：每合约附带 `contract_test.c` — 可独立编译运行的接口验证代码。CI 中执行 `cmake --build build --target contract_tests`。

**合约版本变更规则**：
- 任何修改必须 bump 版本号（遵循 semver）
- CI 自动检测版本变更 → 在所有受影响团队的待合并 PR 上标记 "⚠️ Contract Changed"
- 不兼容的接口变更（MAJOR bump）需要所有受影响团队的 PR 同步合入

### 2.5 三权分立执行模型（v2.6 新增）

> **执行模型**: 三智能体团队 24/7 并行执行。T1 类（系统性批量修改）效率 5-8x；T2 类（标准化代码生成）3-5x；T3 类（重构/集成）2-3x；T4 类（创造性设计）1-1.5x。

| 团队 | 智能体标识 | 主要职责 | 唯一代码目录 | 主要技能 |
|------|:---:|------|-------------|------|
| **团队A（核心引擎）** | Agent-Team-A | C 核心引擎 + 12 条连接线 + Hook 系统 | `agentos/atoms/`、`agentos/cupolas/`、`agentos/daemon/`、`MemoryRovol/` | C、CMake、Linux 系统编程 |
| **团队B（生态+SDK）** | Agent-Team-B | 生态层 + 四语言 SDK + CLI/TUI + Prompt 体系 | `ecosystem/`、`sdk/`、`agentos/gateway/`、`agentos/heapstore/`、`agentos/protocols/` | Python、Rust、Go、TypeScript |
| **团队C（基础设施）** | Agent-Team-C | CI/CD + 部署 + 测试 + 文档 + 质量保障 | `deploy/`、`scripts/`、`tests/`、`Docs/` | CI/CD、Docker、K8s、测试框架 |

**非交叉红线**：

| 团队 | 严禁修改 | 例外 |
|------|---------|------|
| 团队A | `ecosystem/`、`sdk/`、`deploy/` | 无 |

#### 3.5.2 硬编码路径预防规则

| 规则 | 内容 | 检测方式 |
|------|------|---------|

| **PATH-BAN-2** | 所有运行时路径必须通过 `agentos.yaml` 配置或 `commons/path_manager.h` 获取 | Code review |

#### 3.5.3 CI 自动检测脚本

将以下检查集成到 `quality-gate.sh`：

```bash
# 硬编码路径泄露扫描
echo "[PATH-SCAN] Scanning for hardcoded dev paths..."
FORBIDDEN_PATTERNS=(
    '/home/[a-z]+/project'     # Linux home dirs
    '/Users/[a-z]+/project'    # macOS home dirs
    'C:\\\\Users\\\\'           # Windows user dirs
    'D:\\\\SPHARX'             # Dev machine specific
    'SpharxWorks'              # Dev workspace name
)
for pattern in "${FORBIDDEN_PATTERNS[@]}"; do
    matches=$(grep -rn "$pattern" --include="*.c" --include="*.h" --include="*.py" \
              --include="*.sh" --include="*.rs" --include="*.go" agentos/ 2>/dev/null | \
              grep -v "path_manager\|path_scan\|FORBIDDEN_PATTERNS" || true)
    if [ -n "$matches" ]; then
        echo "[PATH-SCAN] FAIL: Hardcoded path detected:"
        echo "$matches"
        exit 1
    fi
done
echo "[PATH-SCAN] PASS: No hardcoded dev paths found"
```

│  • 安全宏封装 + 统计追踪 + 调试标记                       │

**0.1.1 需新增的分配器**：

| 分配器 | 实现位置 | 用途 | 优先级 |
|--------|---------|------|:---:|
| Arena 分配器 | `commons/utils/memory/src/arena.c` | 请求作用域零碎片分配 | P0 |
| per-Thread 缓存层 | `commons/utils/memory/src/tcache.c` | 减少 pool.c 全局锁竞争 | P0 |
| Slab 分配器 | `commons/utils/memory/src/slab.c` | IPC 消息块/任务描述符对象复用 | P1 |
| mempool 最小保证 | `commons/utils/memory/src/mempool.c` | IPC 路径预留紧急内存 | P1 |

**所有权模型**：每个内存分配必须有明确的所有权归属，通过 `@ownership` Doxygen 注解标注。共享所有权对象使用原子引用计数（`_Atomic uint32_t refcount`）。

**RAII 模式**：所有函数内分配的资源必须使用 `goto cleanup` 模式（Linux 内核标准）或 `__attribute__((cleanup))` 自动清理。

#### 7.1.1 Hook 生命周期事件

└── on_l4_rule           ← L4 规则发现后

#### 7.1.2 Hook 实现架构

```
hook_d (daemon/hook_d/)                          ← 新建
├── hook_registry.c       ← Hook 注册表（按事件分类）
├── hook_executor.c       ← 顺序/并行执行 Hook 链
├── hook_interceptor.c    ← 拦截型 Hook 处理器（连接 Cupolas SafetyGuard）
└── hook_timeout.c        ← Hook 执行超时保护（默认 5s）
```

三种 Hook 实现模式：
- **Shell Hook**：可执行脚本，接收 JSON via stdin
- **Python Hook**：基于 Python SDK 的 HookPlugin 基类
- **Webhook**：HTTP POST 到外部服务，支持签名和重试

#### 7.1.3 Hook 注册 API

```c
// daemon/hook_d/include/hook_api.h

typedef enum {
    AGENTOS_HOOK_SHELL,
    AGENTOS_HOOK_PYTHON,
    AGENTOS_HOOK_WEBHOOK
} agentos_hook_type_t;

typedef struct {
    const char *name;
    agentos_hook_type_t type;
    const char *entrypoint;       // 脚本路径 / URL / Python 模块
    const char **events;          // 监听的事件列表
    size_t event_count;
    int priority;                 // 0-100，越高越先执行
    bool blocking;                // 是否可拦截操作
    uint32_t timeout_ms;          // 超时时间
} agentos_hook_descriptor_t;

// 注册 Hook
int agentos_hook_register(agentos_hook_descriptor_t *desc);

// 注销 Hook
int agentos_hook_unregister(const char *name);

// 触发 Hook 链
int agentos_hook_trigger(const char *event, const char *context_json, 
                         bool *blocked, char **result_json);
```

#### 7.1.4 与 Cupolas SafetyGuard 的集成

Hook 系统的拦截型 Hook 直接调用 Cupolas 的 SafetyGuard 守卫链：

```c
// hook_interceptor.c 中的关键集成点
safety_decision_t hook_intercept_check(const char *tool_name, const char *params_json) {
    safety_event_t event = {
        .type = SAFETY_EVENT_ACCESS_REQUEST,
        .subject = current_agent_id,
        .action = tool_name,
        .resource = params_json,
    };
    safety_result_t result;
    return safety_guard_check_chain(guard_ctx, &event, &results, &count);
}
```

CLI (Rust) ──HTTP──▶ gateway (C) ──内部路由──▶ gateway_d ──IPC Bus──▶ 各 daemon

CLI 的 `agentrt init` 和 `agentrt create` 是纯本地文件操作，不经过 gateway。

### 9.3 工具调用审批链（TurnRunner）

利用已有的 Cupolas SafetyGuard 守卫链实现工具审批：

```c
// 在 tool_d/executor.c 中集成 SafetyGuard
agentos_approve_result_t tool_approve(const char *tool_name, const char *params_json) {
    safety_event_t event = {
        .type = SAFETY_EVENT_ACCESS_REQUEST,
        .subject = current_agent_id,
        .action = tool_name,
        .resource = params_json,
    };
    safety_result_t results[SAFETY_MAX_GUARDS];
    size_t result_count;
    safety_decision_t decision = safety_guard_check_chain(ctx, &event, &results, &result_count);
    
    switch (decision) {
        case SAFETY_DECISION_ALLOW: return AGENTOS_APPROVE_ALLOW;
        case SAFETY_DECISION_DENY:  return AGENTOS_APPROVE_DENY;
        case SAFETY_DECISION_CONDITIONAL: return AGENTOS_APPROVE_MODIFY;
        default: return AGENTOS_APPROVE_DENY;
    }
}
```

- `SAFETY_GUARD_PERMISSION` — 权限守卫（RBAC）
- `SAFETY_GUARD_INPUT` — 输入守卫（注入检测）
- `SAFETY_GUARD_RESOURCE` — 资源守卫（配额管理）
- `SAFETY_GUARD_AUDIT` — 审计守卫
- `SAFETY_GUARD_RATE_LIMIT` — 限流守卫
- `SAFETY_GUARD_CONTENT_FILTER` — 内容过滤守卫
