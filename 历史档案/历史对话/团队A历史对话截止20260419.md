#### 修复 #1: embedder.c — JSON解析NULL指针防护（2处致命缺陷）

**问题分析**:
embedder.c中有两个embedding解析函数（OpenAI和DeepSeek），它们都存在相同的JSON解析链缺陷：

```c
// 问题代码（OpenAI版本，约line 274-298）：
cJSON* root = cJSON_Parse(chunk.data);        // ← 可能返回NULL
cJSON* embedding_obj = cJSON_GetArrayItem(data, 0); // ← 如果root=NULL则崩溃
cJSON* embedding_arr = cJSON_GetObjectItem(embedding_obj, "embedding"); // ← 同上
size_t count = (size_t)cJSON_GetArraySize(embedding_arr); // ← 解引用NULL
```

**影响评估**: 🔴 致命 — 当LLM服务返回非标准响应格式时，整个嵌入流程崩溃。

**修复方案**: 在JSON解析链的每一层添加NULL保护：

```c
// 修复后代码：
cJSON* root = cJSON_Parse(chunk.data);
if (!root) {
    AGENTOS_FREE(chunk.data);
    return 0;
}

cJSON* embedding_obj = cJSON_GetArrayItem(data, 0);
if (!embedding_obj) {
    cJSON_Delete(root);
    AGENTOS_FREE(chunk.data);
    return 0;
}

cJSON* embedding_arr = cJSON_GetObjectItem(embedding_obj, "embedding");
if (!embedding_arr || !cJSON_IsArray(embedding_arr)) {
    cJSON_Delete(root);
    AGENTOS_FREE(chunk.data);
    return 0;
}

size_t count = (size_t)cJSON_GetArraySize(embedding_arr);
float* emb = (float*)AGENTOS_MALLOC(count * sizeof(float));
if (emb) {
    for (size_t i = 0; i < count; i++) {
        cJSON* val = cJSON_GetArrayItem(embedding_arr, i);
        emb[i] = val ? (float)val->valuedouble : 0.0f;  // ← 也对val做了NULL保护
    }
    *out_embedding = emb;
}
cJSON_Delete(root);
AGENTOS_FREE(chunk.data);
return emb ? count : 0;
```

DeepSeek版本的函数也应用了完全相同的修复模式。

#### 修复 #2: vector_store.c — SQL查询结果完整保护

**问题分析**:
vector_store.c中的list_ids函数存在多个问题：
1. 当count=0时仍分配内存（浪费）
2. ids数组未初始化（如果后续STRDUP失败会导致free未分配内存崩溃）
3. STRDUP未检查NULL
4. 循环边界可能越界（i可能超过count）

**修复方案**: 重写整个函数体，添加5层防护：

```c
// 修复后代码（关键改动）：
/* 计算结果数量 */
size_t count = 0;
while (sqlite3_step(stmt) == SQLITE_ROW) { count++; }

if (count == 0) {  /* 第1层：空结果早期返回 */
    sqlite3_finalize(stmt);
    *out_ids = NULL;
    *out_count = 0;
    return AGENTOS_SUCCESS;
}

char** ids = (char**)AGENTOS_MALLOC(count * sizeof(char*));  /* 分配 */
if (!ids) { sqlite3_finalize(stmt); return AGENTOS_ENOMEM; }
memset(ids, 0, count * sizeof(char*));  /* 第2层：零初始化 */

sqlite3_reset(stmt);
size_t i = 0;
while (sqlite3_step(stmt) == SQLITE_ROW && i < count) {  /* 第3层：双重边界 */
    const char* id = (const char*)sqlite3_column_text(stmt, 0);
    ids[i] = id ? AGENTOS_STRDUP(id) : NULL;  /* 第4层：column_text NULL保护 */
    if (!ids[i]) {  /* 第5层：STRDUP失败级联清理 */
        for (size_t j = 0; j < i; j++) AGENTOS_FREE(ids[j]);
        AGENTOS_FREE(ids);
        sqlite3_finalize(stmt);
        return AGENTOS_ENOMEM;
    }
    i++;
}
```

#### 修复 #3: unbinder.c — VLA栈溢出消除（gk/gu 2个数组）

**问题分析**:
unbind_real_q1函数中使用变长数组(VLA)：
```c
static void unbind_real_q1(...) {
    if (mat) {
        float gk[dim];      // ← VLA! dim是运行时变量
        memset(gk, 0, dim * sizeof(float));
        // ... 使用gk ...
        float gu[dim];      // ← 又一个VLA!
        // ... 使用gu ...
    }
}
```

**风险**: 当dim很大时（如4096维向量），两个数组各占用16KB栈空间。如果递归调用或栈已较深，可能导致栈溢出(SO)。

**修复方案**: 替换为堆分配：
```c
float* gk = (float*)AGENTOS_MALLOC(dim * sizeof(float));
float* gu = (float*)AGENTOS_MALLOC(dim * sizeof(float));
if (!gk || !gu) {
    AGENTOS_FREE(gk);
    AGENTOS_FREE(gu);
    memset(out, 0, dim * sizeof(float));  // 降级：输出全零
    return;
}
// ... 正常逻辑 ...
AGENTOS_FREE(gk);
AGENTOS_FREE(gu);
```

for (uint32_t iter = 0; iter < net->manager.max_iterations; iter++) {

#### 修复 #5: miner.c — 整数溢出防护

**问题分析**:
```c
float* dist = (float*)AGENTOS_MALLOC(count * count * sizeof(float));
// 当count=65536时：count*count = 4,294,967,296 > SIZE_MAX(通常4,294,967,295 on 32位)
// 或者count*sizeof(float)溢出
```

**修复方案**: 三层溢出检查：
```c
if (count == 0) return NULL;
if (count > SIZE_MAX / count) return NULL;          // 第1层：count²溢出
size_t matrix_size = count * count;
if (matrix_size > SIZE_MAX / sizeof(float)) return NULL;  // 第2层：总大小溢出
float* dist = (float*)AGENTOS_MALLOC(matrix_size * sizeof(float));
```

#### 修复 #6: memoryrovol.c — STRDUP失败原子回滚

**问题分析**: 在填充搜索结果时，如果某个record_id的STRDUP失败，前面已分配的结果不会被释放：
```c
for (size_t i = 0; i < result_count; i++) {
    (*out_results)[i].record_id = AGENTOS_STRDUP(result_ids[i]);
    (*out_results)[i].score = scores[i];  // ← 即使上一步STRDUP失败也继续
}
```

**修复方案**: 添加原子回滚机制：
```c
for (size_t i = 0; i < result_count; i++) {
    (*out_results)[i].record_id = AGENTOS_STRDUP(result_ids[i]);
    if (!(*out_results)[i].record_id) {
        for (size_t j = 0; j < i; j++) {
            AGENTOS_FREE((*out_results)[j].record_id);
            AGENTOS_FREE((*out_results)[j].data);
        }
        AGENTOS_FREE(*out_results);
        *out_results = NULL;
        AGENTOS_FREE(result_ids);
        AGENTOS_FREE(scores);
        return AGENTOS_ENOMEM;
    }
    (*out_results)[i].score = scores[i];
}
```

#### 修复 #7-9: sync_rwlock.c Windows API修正（3处）+ trace.c整数下溢

**sync_rwlock.c问题**: Windows SRWLock API被误用为WaitForSingleObject（用于mutex/event，不适用于SRWLock）。具体：
- read_lock: `WaitForSingleObject(rwlock->rwlock, ...)` → 应为 `AcquireSRWLockShared(&rwlock->rwlock)`
- write_lock: 同上 → 应为 `AcquireSRWLockExclusive(&rwlock->rwlock)`
- unlock: 硬编码 `ReleaseSRWLockExclusive` → 应根据锁类型选择Shared/Exclusive

**解决方案**: 在sync_types.h中添加`bool is_writer`字段追踪锁类型，在lock时设置，在unlock时判断。

**trace.c问题**: `buffer_size - 512` 当buffer_size<512时下溢为巨大值。
**修复**: 改为 `if (buffer_size > 512 && offset >= buffer_size - 512)`

## 关键技术决策记录

### 9.1 决策 #1: memmove替代元素位移循环（index.c HNSW排序）

**场景**: index.c的HNSW搜索结果插入排序中，原代码在循环体内逐个移动数组元素并free旧值，存在use-after-free。

**选项对比**:
- A) 在每次shift前保存ids[m-1]的副本，shift后再STRDUP副本 → 需要临时变量，代码复杂
- B) 先free最后一个元素，memmove批量移动，最后STRDUP新值 → **选中**，简洁高效
- C) 改用qsort后截断top-K → 改变算法语义

**选择B的理由**: memmove是标准库函数，高度优化，一次性完成批量移动，避免了逐元素的中间状态不一致。

### 9.2 决策 #2: VLA消除策略（统一使用堆分配）

**场景**: 3个文件中共3处VLA（unbinder.c 2处 + attractor.c 1处）

**选项对比**:
- A) 使用alloca() — 仍然是栈分配，只是显式化，本质不变
- B) 使用静态最大尺寸数组 `float buf[MAX_DIM]` — 浪费内存，MAX_DIM难以确定
- C) 堆分配(MALLOC) + 失败降级 — **选中**

**选择C的理由**: 
1. 安全性最高：不会栈溢出
2. 内存可控：用完即FREE
3. 降级合理：分配失败时输出零向量，不影响系统稳定性
4. 符合SEC-016内存安全强化规范

### 9.3 决策 #3: STRDUP NULL检查的两种模式

**模式A: 显式if-check（用于复杂清理链）**
```c
ptr = AGENTOS_STRDUP(str);
if (!ptr) {
    // 多行清理代码...
    return AGENTOS_ENOMEM;
}
```
适用场景：需要释放多个已分配资源时

**模式B: 三元操作符（用于简单单行返回）**
```c
return (ptr = AGENTOS_STRDUP(str)) ? code : AGENTOS_ENOMEM;
```
适用场景：无需额外清理，只需返回错误码时

**决策**: 两种模式并存，根据上下文复杂度选择。browser.c大量使用模式B（5处），而memoryrovol.c使用模式A（需要级联回滚）。

### 9.4 决策 #4: sync_rwlock.c Windows锁类型追踪

**场景**: SRWLock的Shared和Exclusive需要不同的Release函数，但原始代码硬编码了ReleaseSRWLockExclusive。

**选项对比**:
- A) 维护两个独立的lock函数(lock_shared/lock_exclusive) — 改动API
- B) 在结构体中添加bool is_writer字段 — **选中**
- C) 使用TLS(Thread-Local Storage)存储锁类型 — 过度工程

**选择B的理由**: 最小侵入性，只在现有struct上加一个bool字段，不改变任何API签名。

### 9.5 决策 #5: 抗回退策略演进

**经历的过程**:
- Rounds 7-8: 每次发现回退就立即重应用（被动响应）
- Round 9-10: 开始在修复前先grep验证当前状态（主动检查）
- Round 11-12: 建立了"6个关键文件"定期检查清单
- Round 13-17: 检查清单扩展，每次编译前都验证

**最终策略**: 
1. 每轮开始时用grep验证关键修复是否保留
2. 编译验证后再次确认
3. 在todo list中明确标注"第N次重应用"
4. 接受某些"优化版"回退（如llm_client.c的第9次修改保留了NULL检查但简化了错误路径）
